# 8.4.4 REVOKE (Retirer une autorisation/refus)

## Introduction

Vous savez maintenant comment **donner** des permissions avec GRANT et **bloquer** avec DENY. Mais comment faire marche arrière ? Comment annuler une permission ou un refus que vous avez accordé ?

C'est exactement le rôle de **REVOKE**.

**Analogie simple** : Imaginez que vous gérez les clés d'un bâtiment.

- 🟢 **GRANT** = Donner une clé à quelqu'un ("Vous pouvez accéder à cette salle")
- 🔴 **DENY** = Mettre un verrou spécial ("Vous ne pouvez PAS accéder à cette salle, même avec une clé")
- ⚪ **REVOKE** = Reprendre la clé OU retirer le verrou ("Finalement, on annule")

REVOKE est l'opération d'**annulation** : elle retire ce qui a été fait avec GRANT ou DENY.

## Qu'est-ce que REVOKE ?

**REVOKE** est une commande SQL qui fait partie du **DCL (Data Control Language)**. Elle permet de **retirer une permission** ou un **refus** précédemment accordé.

### Syntaxe de base

```sql
REVOKE <permission(s)>
ON <objet>
TO <principal>
[CASCADE];
```

La syntaxe est identique à GRANT et DENY, mais l'effet est différent.

## Les deux types de REVOKE

Il est crucial de comprendre que REVOKE peut retirer deux choses différentes :

### 1. REVOKE d'un GRANT (retirer une permission)

```sql
-- Étape 1 : Donner une permission
GRANT SELECT ON dbo.Clients TO Jean;

-- Jean peut maintenant lire les clients
SELECT * FROM dbo.Clients;  -- ✅ Fonctionne

-- Étape 2 : Retirer la permission
REVOKE SELECT ON dbo.Clients TO Jean;

-- Jean ne peut plus lire les clients
SELECT * FROM dbo.Clients;  -- ❌ Échoue
```

### 2. REVOKE d'un DENY (retirer un blocage)

```sql
-- Étape 1 : Bloquer explicitement
DENY DELETE ON dbo.Produits TO Jean;

-- Jean ne peut PAS supprimer de produits
DELETE FROM dbo.Produits WHERE ProduitID = 1;  -- ❌ Échoue

-- Étape 2 : Retirer le blocage
REVOKE DELETE ON dbo.Produits TO Jean;

-- Maintenant :
-- - Le DENY est retiré ✅
-- - MAIS Jean n'a toujours pas la permission DELETE (il faudrait un GRANT)
DELETE FROM dbo.Produits WHERE ProduitID = 1;  -- ❌ Échoue toujours (pas de GRANT)
```

## REVOKE : L'opération "Effacer"

Voici le concept clé à comprendre :

**REVOKE = retour à l'état "neutre"**

```
État initial    →  Action          →  Résultat après REVOKE
─────────────────────────────────────────────────────────────
Pas d'accès     →  GRANT SELECT    →  Pas d'accès (neutre)
Pas d'accès     →  DENY SELECT     →  Pas d'accès (neutre)
```

REVOKE **efface** ce qui a été fait, mais ne donne ni ne refuse rien par lui-même.

### Schéma visuel complet

```
┌─────────────────────────────────────────────────────────┐
│                    ÉTAT INITIAL                         │
│               Jean n'a aucune permission                │
│             (état neutre = pas d'accès)                 │
└────────────────────┬────────────────────────────────────┘
                     │
        ┌────────────┴────────────┐
        │                         │
        ↓                         ↓
┌──────────────┐          ┌──────────────┐
│ GRANT SELECT │          │ DENY SELECT  │
│   TO Jean    │          │   TO Jean    │
└──────┬───────┘          └──────┬───────┘
       │                         │
       ↓                         ↓
┌──────────────┐          ┌──────────────┐
│ Jean peut    │          │ Jean ne peut │
│ lire ✅      │          │ PAS lire ❌  │
└──────┬───────┘          └──────┬───────┘
       │                         │
       │ REVOKE SELECT           │ REVOKE SELECT
       │ TO Jean                 │ TO Jean
       ↓                         ↓
┌─────────────────────────────────────────┐
│     RETOUR À L'ÉTAT NEUTRE              │
│   Jean n'a plus aucune permission       │
│   (ni GRANT ni DENY = pas d'accès)      │
└─────────────────────────────────────────┘
```

## REVOKE vs DENY : Différence cruciale

C'est une confusion très courante chez les débutants. Clarifions :

### ❌ REVOKE n'est PAS un DENY

```sql
-- Beaucoup de débutants pensent que ceci bloque l'accès :
REVOKE SELECT ON dbo.Clients TO Jean;

-- FAUX ! REVOKE ne bloque pas, il RETIRE une permission.
-- Si Jean n'avait pas de GRANT au départ, REVOKE ne fait rien.
```

### Tableau comparatif

| Commande | Effet | Résultat si appliqué sans permission préalable |
|----------|-------|-----------------------------------------------|
| **GRANT** | Donne une permission | Jean obtient l'accès ✅ |
| **DENY** | Bloque explicitement | Jean est bloqué ❌ |
| **REVOKE** | Retire une permission/blocage existant | Aucun effet (rien à retirer) |

### Scénario de démonstration

```sql
-- Situation initiale : Jean n'a aucune permission sur Produits
-- (il ne peut pas lire)

-- Tentative 1 : Utiliser REVOKE pour bloquer
REVOKE SELECT ON dbo.Produits TO Jean;
-- Résultat : AUCUN EFFET (rien à retirer)
-- Jean ne peut toujours pas lire (mais pas à cause du REVOKE)

-- Tentative 2 : Utiliser DENY pour bloquer
DENY SELECT ON dbo.Produits TO Jean;
-- Résultat : Jean est EXPLICITEMENT bloqué ❌
-- Même si on lui donne un GRANT plus tard, le DENY bloquera

-- Moralité :
-- Pour bloquer : utilisez DENY
-- Pour annuler : utilisez REVOKE
```

## Exemples pratiques de REVOKE

### Exemple 1 : Retirer une permission simple

```sql
-- Contexte : Un stagiaire avait des permissions temporaires

-- 1. Donner des permissions temporaires
GRANT SELECT ON dbo.Commandes TO Stagiaire;
GRANT SELECT ON dbo.Clients TO Stagiaire;
GRANT SELECT ON dbo.Produits TO Stagiaire;

-- Le stagiaire peut maintenant consulter ces tables

-- 2. Fin du stage - Retirer toutes les permissions
REVOKE SELECT ON dbo.Commandes TO Stagiaire;
REVOKE SELECT ON dbo.Clients TO Stagiaire;
REVOKE SELECT ON dbo.Produits TO Stagiaire;

-- Le stagiaire n'a plus aucun accès
```

### Exemple 2 : Retirer un DENY (lever une restriction)

```sql
-- Contexte : Un manager junior était bloqué sur les salaires
-- Maintenant il est promu, on lève la restriction

-- 1. État initial : Manager bloqué
DENY SELECT ON dbo.Salaires TO ManagerJunior;

-- ManagerJunior ne peut PAS voir les salaires ❌

-- 2. Promotion : Lever le blocage
REVOKE SELECT ON dbo.Salaires TO ManagerJunior;

-- Le DENY est retiré ✅
-- MAIS il faut maintenant donner la permission
GRANT SELECT ON dbo.Salaires TO ManagerJunior;

-- Maintenant ManagerJunior peut voir les salaires ✅
```

### Exemple 3 : REVOKE après WITH GRANT OPTION

```sql
-- Contexte : Un superviseur pouvait transmettre des permissions

-- 1. Donner une permission transmissible
GRANT SELECT ON dbo.Rapports TO Superviseur WITH GRANT OPTION;

-- 2. Le superviseur transmet la permission à un analyste
-- (Superviseur se connecte et exécute)
GRANT SELECT ON dbo.Rapports TO Analyste1;

-- 3. Plus tard, on retire la permission du superviseur
REVOKE SELECT ON dbo.Rapports TO Superviseur;

-- Résultat :
-- - Superviseur n'a plus accès ❌
-- - Analyste1 GARDE son accès ✅ (pas affecté)
```

⚠️ **Important** : Un REVOKE simple ne cascade pas. Pour affecter aussi ceux qui ont reçu la permission, il faut utiliser CASCADE.

### Exemple 4 : REVOKE CASCADE

```sql
-- Même scénario, mais avec CASCADE

-- 1. Donner une permission transmissible
GRANT SELECT ON dbo.Rapports TO Superviseur WITH GRANT OPTION;

-- 2. Le superviseur transmet à plusieurs personnes
GRANT SELECT ON dbo.Rapports TO Analyste1;
GRANT SELECT ON dbo.Rapports TO Analyste2;
GRANT SELECT ON dbo.Rapports TO Analyste3;

-- 3. Retirer avec CASCADE
REVOKE SELECT ON dbo.Rapports TO Superviseur CASCADE;

-- Résultat :
-- - Superviseur perd l'accès ❌
-- - Analyste1 perd l'accès ❌ (cascade)
-- - Analyste2 perd l'accès ❌ (cascade)
-- - Analyste3 perd l'accès ❌ (cascade)
```

💡 **CASCADE** retire la permission à toute la chaîne de transmission.

## REVOKE sur différents niveaux

Tout comme GRANT et DENY, REVOKE fonctionne à différents niveaux de granularité.

### 1. REVOKE au niveau objet

```sql
-- Retirer l'accès à une table spécifique
REVOKE SELECT ON dbo.Clients TO Jean;

-- Retirer l'accès à une vue
REVOKE SELECT ON dbo.VueVentes TO Jean;

-- Retirer le droit d'exécuter une procédure
REVOKE EXECUTE ON dbo.CalculerCA TO Jean;
```

### 2. REVOKE au niveau schéma

```sql
-- Retirer toutes les permissions SELECT sur un schéma entier
REVOKE SELECT ON SCHEMA::Ventes TO RoleAnalystes;

-- Retirer les permissions d'écriture sur un schéma
REVOKE INSERT, UPDATE, DELETE ON SCHEMA::Test TO Developpeur;

-- Retirer le droit d'exécuter toutes les procédures d'un schéma
REVOKE EXECUTE ON SCHEMA::Administration TO RoleSupport;
```

### 3. REVOKE au niveau colonne

```sql
-- Retirer l'accès à des colonnes spécifiques
REVOKE SELECT ON dbo.Employes (Salaire, Bonus) TO ManagerJunior;

-- Retirer le droit de modifier certaines colonnes
REVOKE UPDATE ON dbo.Produits (PrixCoutant) TO VendeurExterne;
```

### 4. REVOKE au niveau base de données

```sql
-- Retirer le droit de créer des tables
REVOKE CREATE TABLE TO Developpeur;

-- Retirer le droit de sauvegarder la base
REVOKE BACKUP DATABASE TO OperateurBackup;
```

### 5. REVOKE au niveau serveur

```sql
-- Retirer le droit de créer des bases de données
REVOKE CREATE DATABASE TO [DOMAINE\Developpeurs];

-- Retirer d'un rôle serveur
ALTER SERVER ROLE dbcreator DROP MEMBER [DOMAINE\JeanDupont];
```

## Cas d'usage courants

### Cas 1 : Fin de contrat / Départ d'employé

```sql
-- Un employé quitte l'entreprise, nettoyer toutes ses permissions

-- Méthode 1 : REVOKE manuel (fastidieux)
REVOKE SELECT ON dbo.Clients TO EmplyePartant;
REVOKE SELECT ON dbo.Commandes TO EmplyePartant;
REVOKE INSERT ON dbo.Tickets TO EmplyePartant;
-- ... etc.

-- Méthode 2 : Retirer des rôles (recommandé)
ALTER ROLE RoleVentes DROP MEMBER EmplyePartant;
ALTER ROLE RoleSupport DROP MEMBER EmplyePartant;

-- Méthode 3 : Désactiver le Login (encore mieux)
ALTER LOGIN [DOMAINE\EmplyePartant] DISABLE;

-- Méthode 4 : Supprimer complètement
DROP USER EmplyePartant;  -- Niveau base de données
DROP LOGIN [DOMAINE\EmplyePartant];  -- Niveau serveur
```

💡 **Recommandation** : Désactiver le login est souvent préférable à supprimer, car cela conserve l'historique.

### Cas 2 : Changer le modèle de permissions

```sql
-- Contexte : Vous aviez donné des permissions individuelles
-- Vous voulez passer à un modèle basé sur les rôles

-- 1. État actuel (mauvais pattern)
GRANT SELECT ON dbo.Produits TO User1;
GRANT SELECT ON dbo.Produits TO User2;
GRANT SELECT ON dbo.Produits TO User3;

-- 2. Migration vers les rôles
-- a) Créer le rôle
CREATE ROLE RoleCatalogue;
GRANT SELECT ON dbo.Produits TO RoleCatalogue;

-- b) Retirer les permissions individuelles
REVOKE SELECT ON dbo.Produits TO User1;
REVOKE SELECT ON dbo.Produits TO User2;
REVOKE SELECT ON dbo.Produits TO User3;

-- c) Ajouter les users au rôle
ALTER ROLE RoleCatalogue ADD MEMBER User1;
ALTER ROLE RoleCatalogue ADD MEMBER User2;
ALTER ROLE RoleCatalogue ADD MEMBER User3;
```

### Cas 3 : Rotation des permissions temporaires

```sql
-- Contexte : Rotation mensuelle des accès aux données sensibles

-- Début du mois : Donner accès à l'équipe A
GRANT SELECT ON dbo.DonneesSensibles TO EquipeA;

-- Fin du mois : Rotation vers l'équipe B
REVOKE SELECT ON dbo.DonneesSensibles TO EquipeA;  -- Retirer équipe A
GRANT SELECT ON dbo.DonneesSensibles TO EquipeB;   -- Donner à équipe B

-- Le mois suivant : Rotation vers l'équipe C
REVOKE SELECT ON dbo.DonneesSensibles TO EquipeB;  -- Retirer équipe B
GRANT SELECT ON dbo.DonneesSensibles TO EquipeC;   -- Donner à équipe C
```

### Cas 4 : Levée d'une restriction temporaire

```sql
-- Contexte : Un DENY temporaire pour maintenance

-- Pendant la maintenance : Bloquer toute modification
DENY INSERT, UPDATE, DELETE ON dbo.Commandes TO PUBLIC;

-- Message aux users : "Système en maintenance, lecture seule"

-- Après la maintenance : Lever le blocage
REVOKE INSERT, UPDATE, DELETE ON dbo.Commandes TO PUBLIC;

-- Et redonner les permissions normales si nécessaire
GRANT INSERT, UPDATE ON dbo.Commandes TO AppWeb;
```

### Cas 5 : Nettoyage après des tests

```sql
-- Contexte : Permissions de test qu'il faut nettoyer

-- Phase de test : Permissions temporaires
GRANT SELECT ON SCHEMA::Test TO Developpeur;
GRANT CREATE TABLE TO Developpeur;
GRANT CREATE PROCEDURE TO Developpeur;

-- Fin des tests : Nettoyage
REVOKE SELECT ON SCHEMA::Test TO Developpeur;
REVOKE CREATE TABLE TO Developpeur;
REVOKE CREATE PROCEDURE TO Developpeur;
```

## Vérifier l'effet de REVOKE

### Avant REVOKE : Voir les permissions existantes

```sql
-- Lister toutes les permissions de Jean
SELECT
    permission_name AS Permission,
    state_desc AS Type,  -- GRANT ou DENY
    OBJECT_NAME(major_id) AS Object
FROM
    sys.database_permissions
WHERE
    USER_NAME(grantee_principal_id) = 'Jean'
ORDER BY
    state_desc, permission_name;
```

### Après REVOKE : Vérifier que c'est bien retiré

```sql
-- Même requête - doit retourner moins de lignes
SELECT
    permission_name AS Permission,
    state_desc AS Type,
    OBJECT_NAME(major_id) AS Object
FROM
    sys.database_permissions
WHERE
    USER_NAME(grantee_principal_id) = 'Jean'
ORDER BY
    state_desc, permission_name;
```

### Tester concrètement

```sql
-- Se mettre dans le contexte de Jean
EXECUTE AS USER = 'Jean';

-- Essayer l'opération qui devrait être révoquée
SELECT * FROM dbo.Clients;  -- Doit échouer si REVOKE a fonctionné

-- Revenir au contexte normal
REVERT;
```

## REVOKE ALL (déconseillé)

Il existe une syntaxe `REVOKE ALL` qui retire toutes les permissions, mais elle est **déconseillée**.

```sql
-- ⚠️ Syntaxe obsolète et peu claire
REVOKE ALL ON dbo.Clients TO Jean;

-- ✅ Préférez être explicite
REVOKE SELECT, INSERT, UPDATE, DELETE ON dbo.Clients TO Jean;
```

**Pourquoi éviter `REVOKE ALL` ?**
- Manque de clarté (quelles permissions exactement ?)
- Difficile à auditer
- Peut avoir des effets inattendus
- Syntaxe dépréciée dans les versions modernes de SQL Server

## Gérer les permissions héritées via les rôles

Une subtilité importante : REVOKE ne retire que les permissions **directes**, pas celles héritées via des rôles.

### Scénario problématique

```sql
-- 1. Jean a une permission directe
GRANT SELECT ON dbo.Produits TO Jean;

-- 2. Jean est aussi membre d'un rôle
ALTER ROLE RoleCatalogue ADD MEMBER Jean;
GRANT SELECT ON dbo.Produits TO RoleCatalogue;

-- 3. On tente de retirer la permission à Jean
REVOKE SELECT ON dbo.Produits TO Jean;

-- Résultat : Jean peut TOUJOURS lire Produits !
-- Car il hérite de la permission via RoleCatalogue
```

### Solution complète

```sql
-- Pour vraiment retirer l'accès à Jean :

-- Option 1 : REVOKE direct + retirer du rôle
REVOKE SELECT ON dbo.Produits TO Jean;
ALTER ROLE RoleCatalogue DROP MEMBER Jean;

-- Option 2 : DENY (surpasse tout, même les rôles)
DENY SELECT ON dbo.Produits TO Jean;
-- Jean ne peut plus accéder, même via le rôle
```

## Erreurs courantes et solutions

### Erreur 1 : "Cannot find the user"

```sql
-- ❌ Tentative de REVOKE sur un user inexistant
REVOKE SELECT ON dbo.Clients TO UtilisateurInconnu;
-- Erreur : Cannot find the user 'UtilisateurInconnu'
```

**Solution** : Vérifier que le user existe d'abord.
```sql
-- Vérifier l'existence
IF EXISTS (SELECT * FROM sys.database_principals WHERE name = 'UtilisateurInconnu')
BEGIN
    REVOKE SELECT ON dbo.Clients TO UtilisateurInconnu;
END
```

### Erreur 2 : REVOKE sans effet apparent

```sql
-- Vous faites un REVOKE
REVOKE SELECT ON dbo.Clients TO Jean;

-- Mais Jean peut toujours accéder !
```

**Causes possibles** :
1. Jean hérite de la permission via un rôle
2. Jean a la permission au niveau schéma
3. Jean est membre de db_owner ou db_datareader

**Solution** : Investiguer toutes les sources de permissions
```sql
-- Voir toutes les permissions de Jean (directes et via rôles)
EXECUTE AS USER = 'Jean';
SELECT * FROM fn_my_permissions('dbo.Clients', 'OBJECT');
REVERT;
```

### Erreur 3 : "Cannot revoke or deny permissions to or from special roles"

```sql
-- ❌ Tentative de REVOKE sur public
REVOKE SELECT ON dbo.Clients TO public;
-- Peut échouer selon la configuration
```

**Solution** : Éviter de modifier `public` directement. Utilisez des rôles personnalisés.

### Erreur 4 : REVOKE CASCADE sans WITH GRANT OPTION

```sql
-- Si Jean n'avait pas WITH GRANT OPTION au départ
GRANT SELECT ON dbo.Clients TO Jean;  -- Sans WITH GRANT OPTION

-- CASCADE n'a aucun effet (personne n'a reçu la permission de Jean)
REVOKE SELECT ON dbo.Clients TO Jean CASCADE;
-- Fonctionne, mais CASCADE est inutile
```

## Scripts utiles pour la gestion des permissions

### Script 1 : Nettoyer toutes les permissions d'un user

```sql
-- Générer automatiquement tous les REVOKE nécessaires
SELECT
    'REVOKE ' + permission_name +
    ' ON ' + OBJECT_SCHEMA_NAME(major_id) + '.' + OBJECT_NAME(major_id) +
    ' TO ' + USER_NAME(grantee_principal_id) + ';' AS CommandToExecute
FROM
    sys.database_permissions
WHERE
    USER_NAME(grantee_principal_id) = 'Jean'
    AND major_id > 0;  -- Exclut les permissions au niveau base

-- Copiez les résultats et exécutez-les
```

### Script 2 : Retirer tous les DENY d'un user

```sql
-- Lever tous les blocages DENY
SELECT
    'REVOKE ' + permission_name +
    ' ON ' + ISNULL(OBJECT_SCHEMA_NAME(major_id) + '.' + OBJECT_NAME(major_id), 'DATABASE') +
    ' TO ' + USER_NAME(grantee_principal_id) + ';' AS CommandToExecute
FROM
    sys.database_permissions
WHERE
    USER_NAME(grantee_principal_id) = 'Jean'
    AND state_desc = 'DENY';
```

### Script 3 : Comparer les permissions avant/après

```sql
-- Créer une table temporaire pour stocker l'état initial
SELECT
    USER_NAME(grantee_principal_id) AS UserName,
    permission_name,
    state_desc,
    OBJECT_NAME(major_id) AS ObjectName
INTO #PermissionsAvant
FROM
    sys.database_permissions
WHERE
    USER_NAME(grantee_principal_id) = 'Jean';

-- Faire vos REVOKE ici
REVOKE SELECT ON dbo.Clients TO Jean;
REVOKE INSERT ON dbo.Commandes TO Jean;

-- Comparer avec l'état actuel
SELECT
    'Permission retirée' AS Action,
    *
FROM
    #PermissionsAvant
WHERE
    NOT EXISTS (
        SELECT 1
        FROM sys.database_permissions p
        WHERE USER_NAME(p.grantee_principal_id) = UserName
          AND p.permission_name = permission_name
          AND p.major_id = OBJECT_ID(ObjectName)
    );

-- Nettoyage
DROP TABLE #PermissionsAvant;
```

## Bonnes pratiques REVOKE

### 1. Utilisez REVOKE pour nettoyer, pas pour bloquer ✅

```sql
-- ✅ BON : Retirer une permission accordée par erreur
GRANT SELECT ON dbo.Salaires TO Stagiaire;  -- Oops, erreur
REVOKE SELECT ON dbo.Salaires TO Stagiaire;  -- Correction

-- ❌ MAUVAIS : Utiliser REVOKE pour bloquer
REVOKE DELETE ON dbo.HistoriqueAudit TO AppWeb;
-- N'a aucun effet si AppWeb n'avait pas DELETE au départ
-- Utilisez DENY pour bloquer explicitement
```

### 2. Documentez vos REVOKE importants ✅

```sql
-- ✅ BON : Documentation claire
/*
REVOKE des permissions temporaires de maintenance
User: AdminTemporaire
Raison: Fin de la période de maintenance
Date: 2024-01-15
Effectué par: DBA_Jean
*/
REVOKE CREATE TABLE TO AdminTemporaire;
REVOKE ALTER ON SCHEMA::Production TO AdminTemporaire;
```

### 3. Préférez retirer des rôles plutôt que REVOKE individuel ✅

```sql
-- ❌ FASTIDIEUX : REVOKE individuel
REVOKE SELECT ON dbo.Table1 TO Jean;
REVOKE SELECT ON dbo.Table2 TO Jean;
REVOKE SELECT ON dbo.Table3 TO Jean;
REVOKE INSERT ON dbo.Table1 TO Jean;
-- ... 20 lignes plus tard

-- ✅ SIMPLE : Retirer du rôle
ALTER ROLE RoleAnalystes DROP MEMBER Jean;
```

### 4. Utilisez CASCADE avec précaution ⚠️

```sql
-- ⚠️ CASCADE peut avoir des effets en chaîne importants
-- Vérifiez qui sera affecté avant d'utiliser CASCADE

-- Voir qui a reçu des permissions de cet user
SELECT
    grantor.name AS DonnePar,
    grantee.name AS RecuPar,
    permission_name AS Permission,
    OBJECT_NAME(major_id) AS Objet
FROM
    sys.database_permissions p
    JOIN sys.database_principals grantor ON p.grantor_principal_id = grantor.principal_id
    JOIN sys.database_principals grantee ON p.grantee_principal_id = grantee.principal_id
WHERE
    grantor.name = 'Superviseur';

-- Puis décider si CASCADE est approprié
REVOKE SELECT ON dbo.Rapports TO Superviseur CASCADE;
```

### 5. Testez avant d'appliquer en production ✅

```sql
-- En développement : Tester le REVOKE
BEGIN TRANSACTION;

REVOKE SELECT ON dbo.Clients TO RoleTest;

-- Vérifier l'impact
EXECUTE AS USER = 'UserTest';
SELECT * FROM dbo.Clients;  -- Doit échouer
REVERT;

-- Si OK, valider ; sinon annuler
-- COMMIT;
ROLLBACK;  -- Pour annuler le test
```

### 6. Auditez après les REVOKE massifs ✅

```sql
-- Après avoir révoqué des permissions, vérifier l'état
-- S'assurer qu'aucun user critique n'est bloqué

-- Users qui n'ont PLUS aucune permission
SELECT
    name AS UserName
FROM
    sys.database_principals
WHERE
    type IN ('S', 'U')
    AND name NOT IN ('dbo', 'guest', 'INFORMATION_SCHEMA', 'sys')
    AND NOT EXISTS (
        SELECT 1
        FROM sys.database_permissions p
        WHERE p.grantee_principal_id = principal_id
          AND p.state_desc = 'GRANT'
    )
    AND NOT EXISTS (
        SELECT 1
        FROM sys.database_role_members rm
        WHERE rm.member_principal_id = principal_id
    );
```

## Récapitulatif complet : GRANT / DENY / REVOKE

### Tableau de décision

| Objectif | Commande à utiliser |
|----------|---------------------|
| Donner une permission | **GRANT** |
| Bloquer explicitement (même si permission existe via rôle) | **DENY** |
| Annuler un GRANT | **REVOKE** |
| Annuler un DENY | **REVOKE** |
| Retirer toutes les permissions d'un user | Retirer des rôles + **REVOKE** si nécessaire |
| S'assurer qu'un user n'aura JAMAIS accès | **DENY** |

### Matrice des effets

| État initial | Action | Résultat |
|-------------|--------|----------|
| Aucune permission | GRANT SELECT | User peut lire ✅ |
| Aucune permission | DENY SELECT | User ne peut pas lire (bloqué) ❌ |
| Aucune permission | REVOKE SELECT | Aucun changement (rien à retirer) |
| GRANT SELECT actif | REVOKE SELECT | Permission retirée, user ne peut plus lire ❌ |
| GRANT SELECT actif | DENY SELECT | DENY surpasse GRANT, user ne peut pas lire ❌ |
| DENY SELECT actif | REVOKE SELECT | DENY retiré, retour à neutre (toujours pas d'accès sans GRANT) |
| DENY SELECT actif | GRANT SELECT | DENY surpasse GRANT, user ne peut toujours pas lire ❌ |

### Séquences typiques

**Séquence 1 : Donner puis retirer une permission**
```sql
-- État : Neutre (pas d'accès)
GRANT SELECT ON dbo.Clients TO Jean;
-- État : Jean peut lire ✅
REVOKE SELECT ON dbo.Clients TO Jean;
-- État : Neutre (plus d'accès) ❌
```

**Séquence 2 : Bloquer puis débloquer**
```sql
-- État : Neutre
DENY SELECT ON dbo.Salaires TO Jean;
-- État : Jean bloqué ❌
REVOKE SELECT ON dbo.Salaires TO Jean;
-- État : Neutre (mais toujours pas d'accès sans GRANT)
GRANT SELECT ON dbo.Salaires TO Jean;
-- État : Jean peut lire ✅
```

**Séquence 3 : Gestion complète d'un accès temporaire**
```sql
-- 1. Donner accès temporaire
GRANT SELECT, INSERT ON dbo.DonneesSensibles TO ConsultantExterne;

-- 2. Pendant la mission, bloquer une action spécifique
DENY DELETE ON dbo.DonneesSensibles TO ConsultantExterne;

-- 3. Fin de mission : tout retirer
REVOKE SELECT, INSERT ON dbo.DonneesSensibles TO ConsultantExterne;
REVOKE DELETE ON dbo.DonneesSensibles TO ConsultantExterne;

-- État final : Neutre (aucun accès)
```

## Scénario complet : Cycle de vie d'un projet

Mettons tout en pratique avec un scénario réaliste de A à Z.

```sql
-- ═══════════════════════════════════════════════════════════
-- PHASE 1 : MISE EN PLACE DU PROJET
-- ═══════════════════════════════════════════════════════════

-- Créer l'équipe projet
CREATE ROLE RoleProjetAlpha;

-- Permissions de développement
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::Dev TO RoleProjetAlpha;
GRANT CREATE TABLE TO RoleProjetAlpha;
GRANT CREATE PROCEDURE TO RoleProjetAlpha;

-- Ajouter les membres de l'équipe
ALTER ROLE RoleProjetAlpha ADD MEMBER Dev1;
ALTER ROLE RoleProjetAlpha ADD MEMBER Dev2;
ALTER ROLE RoleProjetAlpha ADD MEMBER Dev3;

-- Protection : Bloquer toute modification en production
DENY INSERT, UPDATE, DELETE ON SCHEMA::Production TO RoleProjetAlpha;


-- ═══════════════════════════════════════════════════════════
-- PHASE 2 : PENDANT LE DÉVELOPPEMENT (3 mois)
-- ═══════════════════════════════════════════════════════════

-- L'équipe travaille dans l'environnement Dev
-- Tout fonctionne comme prévu


-- ═══════════════════════════════════════════════════════════
-- PHASE 3 : TESTS EN PRÉ-PRODUCTION
-- ═══════════════════════════════════════════════════════════

-- Donner accès en lecture seule à la pré-production
GRANT SELECT ON SCHEMA::PreProd TO RoleProjetAlpha;

-- Un dev a besoin temporairement d'écrire en pré-prod
GRANT INSERT, UPDATE ON SCHEMA::PreProd TO Dev1;


-- ═══════════════════════════════════════════════════════════
-- PHASE 4 : MISE EN PRODUCTION
-- ═══════════════════════════════════════════════════════════

-- Retirer les permissions de développement
REVOKE CREATE TABLE TO RoleProjetAlpha;
REVOKE CREATE PROCEDURE TO RoleProjetAlpha;

-- Retirer l'accès temporaire de Dev1 en pré-prod
REVOKE INSERT, UPDATE ON SCHEMA::PreProd TO Dev1;

-- Lever le DENY sur production (projet terminé et validé)
REVOKE INSERT, UPDATE, DELETE ON SCHEMA::Production TO RoleProjetAlpha;

-- Donner les permissions de maintenance
GRANT SELECT ON SCHEMA::Production TO RoleProjetAlpha;


-- ═══════════════════════════════════════════════════════════
-- PHASE 5 : FIN DU PROJET
-- ═══════════════════════════════════════════════════════════

-- Retirer tous les membres du rôle
ALTER ROLE RoleProjetAlpha DROP MEMBER Dev1;
ALTER ROLE RoleProjetAlpha DROP MEMBER Dev2;
ALTER ROLE RoleProjetAlpha DROP MEMBER Dev3;

-- Nettoyer toutes les permissions du rôle
REVOKE SELECT, INSERT, UPDATE, DELETE ON SCHEMA::Dev TO RoleProjetAlpha;
REVOKE SELECT ON SCHEMA::PreProd TO RoleProjetAlpha;
REVOKE SELECT ON SCHEMA::Production TO RoleProjetAlpha;

-- Supprimer le rôle (optionnel)
DROP ROLE RoleProjetAlpha;
```

## Conclusion

**REVOKE** est l'outil d'**annulation** des permissions dans SQL Server. C'est la troisième et dernière pièce du puzzle de gestion des permissions.

**Les trois commandes DCL** :
1. 🟢 **GRANT** = Donner une permission
2. 🔴 **DENY** = Bloquer explicitement
3. ⚪ **REVOKE** = Annuler (retirer un GRANT ou un DENY)

**Points essentiels à retenir** :

1. **REVOKE ≠ DENY**
   - REVOKE retire une permission existante
   - DENY bloque explicitement

2. **REVOKE = Retour au neutre**
   - Efface ce qui a été fait
   - Ne donne ni ne refuse rien par lui-même

3. **CASCADE avec précaution**
   - Affecte toute la chaîne de transmission
   - Vérifiez l'impact avant d'utiliser

4. **Permissions héritées**
   - REVOKE ne retire que les permissions directes
   - Les permissions via rôles restent actives

5. **Bonnes pratiques**
   - Documentez vos REVOKE importants
   - Préférez retirer des rôles
   - Testez avant la production
   - Auditez après les changements

Avec **GRANT**, **DENY** et **REVOKE**, vous avez maintenant tous les outils pour gérer complètement et finement les permissions dans SQL Server !

---

**Points clés à retenir** :
- REVOKE = Retirer une permission ou un blocage
- Syntaxe : `REVOKE permission ON objet TO principal`
- Retire les GRANT (permissions) et les DENY (blocages)
- REVOKE ramène à l'état neutre (aucune permission)
- CASCADE retire aussi les permissions transmises
- REVOKE direct ne retire pas les permissions héritées via rôles
- Toujours vérifier l'effet après un REVOKE
- Préférer retirer des rôles plutôt que des REVOKE multiples
- Documenter et tester les REVOKE importants
