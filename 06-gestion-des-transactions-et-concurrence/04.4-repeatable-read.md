# 6.4.4 REPEATABLE READ

## Introduction

Nous avons vu que **READ COMMITTED** (et sa variante RCSI) empêche les Dirty Reads mais autorise les Non-Repeatable Reads : une même donnée peut changer de valeur entre deux lectures dans la même transaction. Le niveau d'isolation **REPEATABLE READ** va plus loin en garantissant qu'une fois qu'une donnée a été lue, elle **restera identique** pendant toute la durée de la transaction.

C'est un niveau d'isolation plus **strict** qui offre plus de **cohérence**, mais au prix de plus de **verrous** et potentiellement plus de **blocages**.

---

## Qu'est-ce que REPEATABLE READ ?

### Définition

**REPEATABLE READ** est un niveau d'isolation qui garantit que :
1. Une transaction ne peut lire **que des données validées** (comme READ COMMITTED)
2. Si une transaction lit une donnée, **cette donnée ne peut pas être modifiée** par d'autres transactions tant que la transaction n'est pas terminée
3. Les **mêmes lectures donnent toujours les mêmes résultats** au sein d'une transaction

En d'autres termes : il bloque les **Dirty Reads** ET les **Non-Repeatable Reads**, mais autorise toujours les **Phantom Reads**.

### Caractéristiques principales

| Caractéristique | REPEATABLE READ |
|-----------------|-----------------|
| **Dirty Reads** | ❌ Bloquées |
| **Non-Repeatable Reads** | ❌ Bloquées |
| **Phantom Reads** | ✅ Autorisées |
| **Verrous de lecture** | 🔒 Maintenus jusqu'au COMMIT |
| **Verrous d'écriture** | 🔒 Maintenus jusqu'au COMMIT |
| **Performances** | ⭐⭐⭐ Moyennes |
| **Cohérence** | ⭐⭐⭐⭐ Élevée |
| **Risque de blocage** | ⚠️ Élevé |

### Analogie : La réservation de livre à la bibliothèque

Imaginez une bibliothèque où :
- Quand vous empruntez un livre, vous le **réservez pour vous seul** jusqu'à ce que vous le rendiez
- **Personne d'autre** ne peut modifier ou emprunter ce livre pendant que vous l'avez
- Vous pouvez le consulter **plusieurs fois** et il sera toujours identique
- Mais de **nouveaux livres** peuvent être ajoutés aux étagères pendant que vous avez votre livre

C'est exactement le comportement de REPEATABLE READ : les données que vous lisez sont "réservées" pour vous et ne peuvent pas changer, mais de nouvelles données peuvent apparaître.

---

## Comment fonctionne REPEATABLE READ ?

### Le principe de base

Avec REPEATABLE READ :
1. **Des verrous partagés** sont placés lors des lectures (SELECT)
2. Ces verrous sont **maintenus jusqu'à la fin de la transaction** (COMMIT ou ROLLBACK)
3. Tant qu'un verrou partagé existe, aucune autre transaction ne peut **modifier** ces données
4. Les **mêmes lectures produisent toujours les mêmes résultats**

### Schéma de fonctionnement

```
Transaction A (lecture REPEATABLE READ)   Transaction B (écriture)
────────────────────────────────────────────────────────────────────
BEGIN TRANSACTION
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ

SELECT Prix FROM Produits
WHERE ProduitID = 1
-- Résultat : 100€
-- Verrou partagé MAINTENU
                                          BEGIN TRANSACTION

                                          UPDATE Produits SET Prix = 150
                                          WHERE ProduitID = 1
                                          -- BLOQUÉE ! Doit attendre A

-- Deuxième lecture (même requête)
SELECT Prix FROM Produits
WHERE ProduitID = 1
-- Résultat : 100€ (identique)
-- Verrou toujours actif
                                          -- Toujours en attente...

COMMIT
-- Verrou libéré maintenant
                                          -- Peut enfin continuer
                                          -- Update effectué
                                          COMMIT
```

**Résultat :** Transaction A lit toujours 100€, même si B veut modifier à 150€. La valeur reste "répétable".

---

## Différence avec READ COMMITTED

### Comportement des verrous de lecture

#### READ COMMITTED (rappel)

```
Transaction A (READ COMMITTED)            Transaction B (écriture)
────────────────────────────────────────────────────────────────────
BEGIN TRANSACTION

SELECT Prix FROM Produits WHERE ProduitID = 1
-- Résultat : 100€
-- Verrou partagé placé puis LIBÉRÉ immédiatement
                                          BEGIN TRANSACTION
                                          UPDATE Produits SET Prix = 150
                                          WHERE ProduitID = 1
                                          COMMIT
                                          -- Modification validée
-- Deuxième lecture
SELECT Prix FROM Produits WHERE ProduitID = 1
-- Résultat : 150€ (différent !)

COMMIT
```

**Non-Repeatable Read autorisé** : La même lecture donne des résultats différents.

#### REPEATABLE READ

```
Transaction A (REPEATABLE READ)           Transaction B (écriture)
────────────────────────────────────────────────────────────────────
BEGIN TRANSACTION
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ

SELECT Prix FROM Produits WHERE ProduitID = 1
-- Résultat : 100€
-- Verrou partagé MAINTENU
                                          BEGIN TRANSACTION
                                          UPDATE Produits SET Prix = 150
                                          WHERE ProduitID = 1
                                          -- BLOQUÉE !
-- Deuxième lecture
SELECT Prix FROM Produits WHERE ProduitID = 1
-- Résultat : 100€ (identique garanti)

COMMIT
-- Verrou libéré
                                          -- Peut maintenant continuer
                                          COMMIT
```

**Non-Repeatable Read bloqué** : La même lecture donne toujours le même résultat.

### Tableau comparatif

| Aspect | READ COMMITTED | REPEATABLE READ |
|--------|----------------|-----------------|
| **Verrous de lecture** | Libérés immédiatement | Maintenus jusqu'au COMMIT |
| **Relecture identique** | ❌ Pas garanti | ✅ Garanti |
| **Blocage** | Faible | Élevé |
| **Cohérence** | Bonne | Très bonne |
| **Performance** | Excellente | Moyenne |

## Les Non-Repeatable Reads sont bloqués

### Pourquoi c'est important

Certaines opérations nécessitent que les données restent cohérentes pendant toute la transaction.

### Exemple concret : Calcul de rapport financier

**Problème avec READ COMMITTED :**

```sql
-- ===== Transaction A : Génération d'un rapport =====
BEGIN TRANSACTION;
-- Rapport mensuel : comparaison des ventes

-- 1. Lecture des ventes de janvier
SELECT @VentesJanvier = SUM(Montant)
FROM Ventes
WHERE MONTH(DateVente) = 1;
-- Résultat : 100 000€

-- Petite pause (calculs intermédiaires)
WAITFOR DELAY '00:00:05';

-- 2. Lecture des ventes de février
SELECT @VentesFevrier = SUM(Montant)
FROM Ventes
WHERE MONTH(DateVente) = 2;
-- Résultat : 120 000€

-- 3. RE-lecture de janvier pour comparaison
SELECT @VentesJanvierVerif = SUM(Montant)
FROM Ventes
WHERE MONTH(DateVente) = 1;
-- Résultat : 105 000€ (différent !)
-- Une correction a été appliquée entre-temps

-- Calcul du pourcentage d'augmentation
-- Basé sur des données incohérentes !
COMMIT;
```

**Problème :** Le rapport compare janvier (100K) avec février (120K), mais janvier a été modifié (105K). Les calculs sont faux.

**Solution avec REPEATABLE READ :**

```sql
-- ===== Transaction A : Génération d'un rapport =====
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 1. Lecture des ventes de janvier
SELECT @VentesJanvier = SUM(Montant)
FROM Ventes
WHERE MONTH(DateVente) = 1;
-- Résultat : 100 000€
-- Verrous maintenus sur ces données

-- 2. Lecture des ventes de février
SELECT @VentesFevrier = SUM(Montant)
FROM Ventes
WHERE MONTH(DateVente) = 2;
-- Résultat : 120 000€

-- 3. RE-lecture de janvier
SELECT @VentesJanvierVerif = SUM(Montant)
FROM Ventes
WHERE MONTH(DateVente) = 1;
-- Résultat : 100 000€ (identique garanti !)

-- Calcul du pourcentage d'augmentation
-- +20% (calcul cohérent)

COMMIT;
-- Verrous libérés maintenant
```

**Avantage :** Les données de janvier restent figées à 100K pendant toute la transaction. Le rapport est cohérent.

## Les Phantom Reads sont toujours autorisés

### Qu'est-ce qu'un Phantom Read ?

REPEATABLE READ empêche la **modification** des données existantes, mais n'empêche pas l'**insertion** ou la **suppression** de nouvelles lignes qui correspondent aux critères de recherche.

### Pourquoi ?

Les verrous partagés protègent les **lignes lues**, mais ne peuvent pas empêcher l'insertion de **nouvelles lignes** qui n'existaient pas au moment de la première lecture.

### Exemple

```sql
-- ===== Transaction A : Comptage des employés =====
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Premier comptage
SELECT COUNT(*) AS NombreEmployes
FROM Employes
WHERE Departement = 'IT';
-- Résultat : 10 employés
-- Verrous sur les 10 employés existants

WAITFOR DELAY '00:00:05';

-- Deuxième comptage (même requête)
SELECT COUNT(*) AS NombreEmployes
FROM Employes
WHERE Departement = 'IT';
-- Résultat : 11 employés (ligne fantôme !)

COMMIT;
```

```sql
-- ===== Transaction B : Nouvel employé (en parallèle) =====
BEGIN TRANSACTION;

INSERT INTO Employes (Nom, Departement, Salaire)
VALUES ('Dupont', 'IT', 3500);
-- Nouvelle ligne insérée
-- Pas de conflit de verrou (ligne n'existait pas avant)

COMMIT;
```

**Résultat :** Une nouvelle ligne "fantôme" est apparue entre les deux comptages.

### Schéma explicatif

```
Première lecture (Transaction A)
┌──────────┬────────────┬─────────────┐
│EmployeID │    Nom     │ Departement │
├──────────┼────────────┼─────────────┤
│    1     │   Martin   │     IT      │ ← Verrou partagé
│    2     │   Durand   │     IT      │ ← Verrou partagé
│    3     │   Bernard  │     IT      │ ← Verrou partagé
│   ...    │    ...     │     IT      │
│   10     │   Petit    │     IT      │ ← Verrou partagé
└──────────┴────────────┴─────────────┘
COUNT = 10

Transaction B insère une nouvelle ligne
┌──────────┬────────────┬─────────────┐
│   11     │   Dupont   │     IT      │ ← NOUVELLE ligne (pas de verrou)
└──────────┴────────────┴─────────────┘

Deuxième lecture (Transaction A)
┌──────────┬────────────┬─────────────┐
│EmployeID │    Nom     │ Departement │
├──────────┼────────────┼─────────────┤
│    1     │   Martin   │     IT      │ ← Toujours les mêmes (protégés)
│    2     │   Durand   │     IT      │
│   ...    │    ...     │     IT      │
│   10     │   Petit    │     IT      │
│   11     │   Dupont   │     IT      │ ← Ligne fantôme visible
└──────────┴────────────┴─────────────┘
COUNT = 11 (différent !)
```

### Est-ce un problème ?

**Pour la plupart des applications : NON**

Les phantom reads sont rarement problématiques en pratique. Les cas où ils posent vraiment problème :
- Systèmes critiques nécessitant une isolation maximale
- Transactions financières très strictes
- Calculs nécessitant une vue complètement figée

→ Dans ces cas, utilisez **SERIALIZABLE** ou **SNAPSHOT**.

## Syntaxe et utilisation

### Définir le niveau d'isolation REPEATABLE READ

```sql
-- Méthode 1 : Au niveau de la transaction
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT * FROM Produits WHERE ProduitID = 1;
-- Autres opérations...

COMMIT;
```

```sql
-- Méthode 2 : Au niveau de la session
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Toutes les transactions suivantes utilisent REPEATABLE READ
BEGIN TRANSACTION;
SELECT * FROM Produits;
COMMIT;

BEGIN TRANSACTION;
SELECT * FROM Commandes;
COMMIT;
```

### Exemple complet

```sql
-- Transaction nécessitant une cohérence stricte
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Lecture du solde du compte
DECLARE @Solde DECIMAL(10,2);
SELECT @Solde = Solde FROM Comptes WHERE CompteID = @CompteID;

-- Calculs basés sur ce solde
DECLARE @Interets DECIMAL(10,2);
SET @Interets = @Solde * 0.05;  -- 5% d'intérêts

-- RE-lecture du solde pour vérification
DECLARE @SoldeVerif DECIMAL(10,2);
SELECT @SoldeVerif = Solde FROM Comptes WHERE CompteID = @CompteID;

-- Le solde est GARANTI identique (@Solde = @SoldeVerif)
-- Peut procéder en toute confiance

-- Application des intérêts
UPDATE Comptes
SET Solde = @Solde + @Interets
WHERE CompteID = @CompteID;

COMMIT;
```

## Avantages de REPEATABLE READ

### 1. Garantie de cohérence entre lectures

**La principale force :** Les mêmes requêtes donnent **toujours** les mêmes résultats dans une transaction.

```sql
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Ces trois lectures donneront le même résultat
SELECT Prix FROM Produits WHERE ProduitID = 1;  -- 100€
-- ... autres opérations ...
SELECT Prix FROM Produits WHERE ProduitID = 1;  -- 100€ (garanti)
-- ... autres opérations ...
SELECT Prix FROM Produits WHERE ProduitID = 1;  -- 100€ (garanti)

COMMIT;
```

### 2. Idéal pour les rapports et analyses

Les rapports qui nécessitent plusieurs lectures des mêmes données bénéficient de cette garantie.

```sql
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Rapport comparatif cohérent
SELECT @T1 = SUM(Montant) FROM Ventes WHERE Trimestre = 1;
SELECT @T2 = SUM(Montant) FROM Ventes WHERE Trimestre = 2;
SELECT @T3 = SUM(Montant) FROM Ventes WHERE Trimestre = 3;
SELECT @T4 = SUM(Montant) FROM Ventes WHERE Trimestre = 4;

-- Re-calcul de T1 pour double-vérification
SELECT @T1Verif = SUM(Montant) FROM Ventes WHERE Trimestre = 1;
-- @T1 = @T1Verif (garanti)

-- Les calculs de pourcentages sont cohérents
COMMIT;
```

### 3. Prévention des erreurs logiques

Élimine les bugs difficiles à reproduire causés par des modifications concurrentes.

```sql
-- Sans REPEATABLE READ : Bug intermittent
-- Avec REPEATABLE READ : Comportement prévisible
```

## Inconvénients de REPEATABLE READ

### 1. Risque de blocage élevé

**Le principal problème :** Plus de verrous maintenus plus longtemps = plus de blocages.

```sql
-- Transaction A (REPEATABLE READ)
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM Produits WHERE ProduitID = 1;
-- Verrou maintenu...

-- Transaction B tente de modifier
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
-- BLOQUÉE ! Peut attendre longtemps si A est lente

COMMIT;  -- Transaction A doit finir pour libérer B
```

### 2. Risque de deadlock augmenté

Plus de verrous maintenus = plus de risques d'interblocage.

```sql
-- Transaction A
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM Table1 WHERE ID = 1;  -- Verrou sur Table1
-- Tente de verrouiller Table2...

-- Transaction B
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM Table2 WHERE ID = 2;  -- Verrou sur Table2
-- Tente de verrouiller Table1...

-- DEADLOCK ! Chacune garde un verrou et attend l'autre
```

### 3. Impact sur les performances

```
READ COMMITTED    : 1000 transactions/seconde
REPEATABLE READ   : 400 transactions/seconde (avec contention)
```

La réduction des performances peut être significative dans les environnements avec beaucoup de concurrence.

### 4. Transactions doivent être courtes

Si une transaction REPEATABLE READ est longue, elle bloque les écritures pendant toute sa durée.

```sql
-- ❌ TRÈS MAUVAIS
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT * FROM Produits;  -- Verrous sur toute la table

-- L'utilisateur part en pause café (10 minutes)
-- Pendant ce temps, AUCUNE modification de Produits n'est possible !

COMMIT;
```

## Quand utiliser REPEATABLE READ ?

### Cas d'usage appropriés ✅

**1. Rapports financiers critiques**
```sql
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Rapport annuel qui nécessite une cohérence absolue
SELECT @RevenuQ1 = SUM(Revenu) FROM Ventes WHERE Trimestre = 1;
SELECT @RevenuQ2 = SUM(Revenu) FROM Ventes WHERE Trimestre = 2;
SELECT @RevenuQ3 = SUM(Revenu) FROM Ventes WHERE Trimestre = 3;
SELECT @RevenuQ4 = SUM(Revenu) FROM Ventes WHERE Trimestre = 4;

-- Re-calculs et vérifications multiples
-- Les données restent cohérentes

COMMIT;
```

**2. Calculs basés sur plusieurs lectures**
```sql
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Calcul d'une moyenne pondérée nécessitant plusieurs passes
DECLARE @Somme DECIMAL(18,2), @NbElements INT;

SELECT @Somme = SUM(Valeur) FROM Mesures WHERE TypeMesure = 'A';
SELECT @NbElements = COUNT(*) FROM Mesures WHERE TypeMesure = 'A';

-- Re-lecture pour validation
SELECT @SommeVerif = SUM(Valeur) FROM Mesures WHERE TypeMesure = 'A';
-- Garanti : @Somme = @SommeVerif

COMMIT;
```

**3. Opérations de comparaison "avant/après"**
```sql
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Lire l'état avant
SELECT @StockAvant = Stock FROM Produits WHERE ProduitID = 1;

-- Effectuer une opération
EXEC sp_TraiterCommande @CommandeID;

-- Lire l'état après
SELECT @StockApres = Stock FROM Produits WHERE ProduitID = 1;

-- La comparaison est valide car Stock n'a pas pu être modifié par ailleurs

COMMIT;
```

**4. Transactions avec logique de validation complexe**
```sql
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Lire des données
SELECT @Prix = Prix FROM Produits WHERE ProduitID = 1;
SELECT @Remise = TauxRemise FROM Clients WHERE ClientID = @ClientID;

-- Logique métier complexe basée sur ces valeurs
-- ... calculs ...

-- Re-vérification avant validation finale
SELECT @PrixVerif = Prix FROM Produits WHERE ProduitID = 1;

IF @Prix = @PrixVerif
    -- Peut procéder en toute confiance
    INSERT INTO Commandes ...

COMMIT;
```

### Cas où NE PAS utiliser REPEATABLE READ ❌

**1. Applications web standard**
```sql
-- ❌ MAUVAIS pour un site e-commerce
-- Trop restrictif, trop de blocages
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM Produits WHERE Categorie = 'Livres';
```

**2. Transactions longues**
```sql
-- ❌ MAUVAIS : Bloque les écritures trop longtemps
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM GrosseTable;  -- 10 millions de lignes
-- Traitement long...
COMMIT;
```

**3. Opérations simples ne nécessitant pas de cohérence stricte**
```sql
-- ❌ INUTILE : READ COMMITTED suffit
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM Produits WHERE ProduitID = 1;
-- Une seule lecture, pas besoin de REPEATABLE READ
COMMIT;
```

**4. Environnements avec forte concurrence**
```
1000 utilisateurs simultanés + REPEATABLE READ = Blocages massifs
→ Utiliser READ COMMITTED ou RCSI à la place
```

## Exemple pratique complet

### Scénario : Système de calcul de primes annuelles

```sql
-- ========================================
-- CALCUL DE PRIMES ANNUELLES
-- Nécessite REPEATABLE READ pour garantir
-- la cohérence entre plusieurs lectures
-- ========================================

BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

DECLARE @EmployeID INT = 123;
DECLARE @SalaireBase DECIMAL(10,2);
DECLARE @NbVentes INT;
DECLARE @ChiffreAffaires DECIMAL(12,2);
DECLARE @TauxRendement DECIMAL(5,2);
DECLARE @Prime DECIMAL(10,2);

-- 1. Lecture du salaire de base
SELECT @SalaireBase = Salaire
FROM Employes
WHERE EmployeID = @EmployeID;
-- Verrou maintenu sur cette ligne

-- 2. Calcul des performances de vente
SELECT
    @NbVentes = COUNT(*),
    @ChiffreAffaires = SUM(Montant)
FROM Ventes
WHERE EmployeID = @EmployeID
AND YEAR(DateVente) = 2025;
-- Verrous maintenus sur ces lignes de ventes

-- 3. Calcul du taux de rendement (basé sur le salaire)
SET @TauxRendement = (@ChiffreAffaires / @SalaireBase) * 100;

-- 4. Re-vérification du salaire (peut avoir changé en READ COMMITTED)
DECLARE @SalaireVerif DECIMAL(10,2);
SELECT @SalaireVerif = Salaire
FROM Employes
WHERE EmployeID = @EmployeID;

-- AVEC REPEATABLE READ : @SalaireBase = @SalaireVerif (GARANTI)
-- SANS REPEATABLE READ : Pourrait être différent (incohérence)

-- 5. Calcul de la prime basé sur plusieurs critères
IF @TauxRendement > 200
    SET @Prime = @SalaireBase * 0.20;  -- 20% de prime
ELSE IF @TauxRendement > 150
    SET @Prime = @SalaireBase * 0.15;  -- 15% de prime
ELSE IF @TauxRendement > 100
    SET @Prime = @SalaireBase * 0.10;  -- 10% de prime
ELSE
    SET @Prime = 0;

-- 6. Enregistrement de la prime
INSERT INTO Primes (EmployeID, Annee, Montant, DateCalcul)
VALUES (@EmployeID, 2025, @Prime, GETDATE());

-- 7. Mise à jour du salaire avec la prime
UPDATE Employes
SET SalaireAvecPrime = @SalaireBase + @Prime
WHERE EmployeID = @EmployeID;

COMMIT;

-- Grâce à REPEATABLE READ :
-- - Le salaire de base n'a pas pu changer pendant le calcul
-- - Les ventes n'ont pas pu être modifiées
-- - Le calcul est cohérent du début à la fin
```

**Pourquoi REPEATABLE READ est essentiel ici :**
1. ✅ Le salaire reste constant pendant tout le calcul
2. ✅ Les ventes ne peuvent pas être modifiées/supprimées
3. ✅ Les multiples lectures donnent des résultats cohérents
4. ✅ La prime calculée est basée sur des données figées

## Stratégies d'optimisation

### 1. Limiter la portée de REPEATABLE READ

```sql
-- ❌ MAUVAIS : Toute la session en REPEATABLE READ
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- Toutes les transactions suivantes sont affectées

-- ✅ BON : Uniquement la transaction qui en a besoin
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- Opérations critiques...
COMMIT;

-- Retour au niveau par défaut
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### 2. Garder les transactions courtes

```sql
-- ❌ MAUVAIS
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM GrosseTable;
-- Traitement très long...
COMMIT;

-- ✅ BON
-- Préparer les données AVANT la transaction
DECLARE @Donnees TABLE (...);
INSERT INTO @Donnees SELECT ...;

-- Transaction courte
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- Opérations rapides basées sur @Donnees
COMMIT;
```

### 3. Lire uniquement les données nécessaires

```sql
-- ❌ MAUVAIS : Verrouille toute la table
SELECT * FROM Produits;

-- ✅ BON : Verrouille uniquement les lignes nécessaires
SELECT ProduitID, Prix
FROM Produits
WHERE Categorie = 'Electronique' AND Stock > 0;
```

### 4. Combiner avec des index appropriés

```sql
-- Sans index : Scan de table (beaucoup de verrous)
SELECT * FROM Employes WHERE Departement = 'IT';

-- Avec index : Seek (peu de verrous)
CREATE INDEX IX_Employes_Dept ON Employes(Departement);
```

## Résumé

### Points clés

| Aspect | Description |
|--------|-------------|
| **Niveau d'isolation** | Plus strict que READ COMMITTED |
| **Principe** | Les lectures répétées donnent toujours le même résultat |
| **Dirty Reads** | ❌ Bloquées |
| **Non-Repeatable Reads** | ❌ Bloquées (principale différence) |
| **Phantom Reads** | ✅ Autorisées |
| **Verrous de lecture** | 🔒 Maintenus jusqu'au COMMIT |
| **Risque de blocage** | ⚠️ Élevé |
| **Performance** | ⭐⭐⭐ Moyenne |
| **Cohérence** | ⭐⭐⭐⭐ Élevée |

### Quand l'utiliser

✅ **OUI** pour :
- Rapports financiers ou légaux nécessitant une cohérence stricte
- Calculs basés sur plusieurs lectures des mêmes données
- Transactions avec logique de validation complexe
- Opérations de comparaison "avant/après"

❌ **NON** pour :
- Applications web standard (trop restrictif)
- Environnements avec forte concurrence
- Transactions longues
- Lectures simples ne nécessitant pas de cohérence stricte

### L'essentiel à retenir

1. REPEATABLE READ **maintient les verrous de lecture** jusqu'au COMMIT
2. Garantit que les **mêmes lectures donnent les mêmes résultats**
3. Bloque les **Non-Repeatable Reads** (mais pas les Phantom Reads)
4. **Augmente le risque de blocage** et de deadlock
5. Idéal pour les **rapports et calculs critiques**
6. Nécessite des **transactions courtes** pour éviter les blocages excessifs
7. Plus de **cohérence**, moins de **performance**

### Commande d'activation

```sql
-- Au niveau de la transaction (recommandé)
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- Vos opérations critiques...
COMMIT;
```
