# 7.2.4 Coût des index (Ralentissement des écritures DML)

## Introduction

Dans toutes les sections précédentes, nous avons célébré les **bénéfices** des index :
- ⚡ Recherches ultra-rapides (Index Seek vs Table Scan)
- 🎯 Covering Index pour éliminer les Key Lookups
- 📦 Index filtrés pour réduire la taille
- 💎 INCLUDE pour optimiser les performances

**Mais il y a un prix à payer.**

Jusqu'ici, nous avons principalement parlé des **lectures** (SELECT). Maintenant, il est temps de parler des **écritures** : INSERT, UPDATE, DELETE.

**La réalité** : Les index **ralentissent** les opérations d'écriture. Plus vous avez d'index, plus vos écritures sont lentes.

## Le Paradoxe des Index

### La dualité fondamentale

Les index ont une **nature paradoxale** :

```
┌────────────────────────────────────────────┐
│  LECTURES (SELECT)                         │
│  Plus d'index = Plus rapide ⚡             │
└────────────────────────────────────────────┘
                    VS
┌────────────────────────────────────────────┐
│  ÉCRITURES (INSERT, UPDATE, DELETE)        │
│  Plus d'index = Plus lent 🐌               │
└────────────────────────────────────────────┘
```

**Ce n'est pas un bug, c'est une caractéristique fondamentale.**

### L'analogie de la bibliothèque

Imaginez une **bibliothèque** :

**Sans index** :
- Ajouter un livre : Posez-le sur une étagère → Rapide ⚡
- Trouver un livre : Cherchez partout → Lent 🐌

**Avec 1 index** (par titre) :
- Ajouter un livre :
  1. Posez le livre sur l'étagère
  2. Mettez à jour l'index par titre
  → Un peu plus lent ⚠️
- Trouver un livre : Consultez l'index → Rapide ⚡

**Avec 10 index** (titre, auteur, année, genre, éditeur, ISBN, langue, etc.) :
- Ajouter un livre :
  1. Posez le livre sur l'étagère
  2. Mettez à jour l'index par titre
  3. Mettez à jour l'index par auteur
  4. Mettez à jour l'index par année
  5. ... (10 mises à jour au total)
  → Beaucoup plus lent 🐌🐌🐌
- Trouver un livre : Consultez l'index approprié → Très rapide ⚡⚡⚡

**C'est exactement le même principe avec les index SQL Server.**

## Pourquoi les Index Ralentissent les Écritures ?

### INSERT : Insérer une nouvelle ligne

#### Sans index

```sql
-- Table sans index
INSERT INTO Clients (Nom, Prenom, Email)
VALUES ('Dupont', 'Marie', 'marie@email.com');

-- Opération SQL Server :
-- 1. Trouver de l'espace libre dans la table
-- 2. Écrire la nouvelle ligne
-- Total : 1 opération d'écriture
```

**Temps** : ~1 ms

#### Avec 5 index

```sql
-- Table avec 5 index :
-- - PRIMARY KEY (clustered) sur ClientID
-- - Index sur Email
-- - Index sur (Nom, Prenom)
-- - Index sur Ville
-- - Index sur DateInscription

INSERT INTO Clients (Nom, Prenom, Email, Ville, DateInscription)
VALUES ('Dupont', 'Marie', 'marie@email.com', 'Paris', '2024-11-18');

-- Opérations SQL Server :
-- 1. Écrire dans la table (index clustered)
-- 2. Mettre à jour l'index sur Email
-- 3. Mettre à jour l'index sur (Nom, Prenom)
-- 4. Mettre à jour l'index sur Ville
-- 5. Mettre à jour l'index sur DateInscription
-- Total : 5 opérations d'écriture
```

**Temps** : ~5 ms (5x plus lent)

### UPDATE : Modifier une ligne existante

#### Cas 1 : UPDATE ne touche pas les colonnes indexées

```sql
-- UPDATE sur une colonne non indexée
UPDATE Clients
SET Telephone = '0612345678'
WHERE ClientID = 3;

-- Opérations :
-- 1. Trouver la ligne (via PRIMARY KEY)
-- 2. Modifier Telephone dans la table
-- Les index ne sont PAS affectés (Telephone n'est pas indexé)

-- Coût : Minimal
```

#### Cas 2 : UPDATE touche une colonne indexée

```sql
-- UPDATE sur une colonne indexée (Email)
UPDATE Clients
SET Email = 'nouveau@email.com'
WHERE ClientID = 3;

-- Opérations :
-- 1. Trouver la ligne (via PRIMARY KEY)
-- 2. Modifier Email dans la table
-- 3. Supprimer l'ancienne entrée dans l'index IX_Clients_Email
-- 4. Ajouter la nouvelle entrée dans l'index IX_Clients_Email

-- Coût : Double (suppression + insertion dans l'index)
```

#### Cas 3 : UPDATE touche plusieurs colonnes indexées

```sql
-- UPDATE touchant 3 colonnes indexées
UPDATE Clients
SET Email = 'nouveau@email.com',
    Nom = 'Martin',
    Ville = 'Lyon'
WHERE ClientID = 3;

-- Opérations :
-- 1. Trouver la ligne
-- 2. Modifier dans la table
-- 3. Mettre à jour l'index sur Email (suppression + insertion)
-- 4. Mettre à jour l'index sur (Nom, Prenom) (suppression + insertion)
-- 5. Mettre à jour l'index sur Ville (suppression + insertion)

-- Coût : Important (3 index à mettre à jour)
```

### DELETE : Supprimer une ligne

```sql
-- DELETE d'une ligne
DELETE FROM Clients WHERE ClientID = 3;

-- Opérations :
-- 1. Trouver la ligne
-- 2. Supprimer de la table
-- 3. Supprimer de l'index sur Email
-- 4. Supprimer de l'index sur (Nom, Prenom)
-- 5. Supprimer de l'index sur Ville
-- 6. Supprimer de tous les autres index

-- Coût : Proportionnel au nombre d'index
```

### Tableau récapitulatif

| Opération | Sans index | Avec 1 index | Avec 5 index | Avec 10 index |
|-----------|------------|--------------|--------------|---------------|
| **INSERT** | 1 écriture | 2 écritures | 6 écritures | 11 écritures |
| **UPDATE** (1 col indexée) | 1 écriture | 3 écritures | 3 écritures* | 3 écritures* |
| **UPDATE** (toutes cols) | 1 écriture | 3 écritures | 11 écritures | 21 écritures |
| **DELETE** | 1 écriture | 2 écritures | 6 écritures | 11 écritures |

*Si seule 1 colonne indexée est modifiée

## Impact Chiffré : Benchmarks


## L'Équilibre Lecture/Écriture

### Le ratio critique

Pour décider du nombre d'index, vous devez connaître le **ratio lecture/écriture** de votre application.

```
Ratio Lecture/Écriture = Nombre de SELECT / Nombre de INSERT+UPDATE+DELETE
```

### Profils d'applications

#### Application OLTP (transactionnelle)

**Exemple** : Site e-commerce, application bancaire, ERP

**Caractéristiques** :
- Beaucoup d'écritures (INSERT, UPDATE)
- Lectures fréquentes mais ciblées
- Transactions courtes
- Ratio lecture/écriture : **50/50** ou **70/30**

**Stratégie d'indexation** :
- ✅ Index **minimal** : PRIMARY KEY + Foreign Keys + 2-5 index ciblés
- ❌ **Éviter** : Trop d'index (ralentit les transactions)

**Exemple concret** :
```sql
-- Table Commandes (OLTP)
CREATE TABLE Commandes (
    CommandeID INT PRIMARY KEY,
    ClientID INT,
    DateCommande DATE,
    Statut NVARCHAR(20),
    MontantTotal DECIMAL(10,2)
);

-- Index MINIMAL pour OLTP
CREATE INDEX IX_Commandes_Client ON Commandes (ClientID);  -- Foreign key
CREATE INDEX IX_Commandes_Date ON Commandes (DateCommande);  -- Recherches fréquentes
-- Total : 3 index (PRIMARY + 2)
-- Priorité : Écritures rapides
```

#### Application OLAP (analytique)

**Exemple** : Datawarehouse, Business Intelligence, Reporting

**Caractéristiques** :
- Peu d'écritures (chargements batch)
- Beaucoup de lectures complexes
- Requêtes longues
- Ratio lecture/écriture : **95/5** ou **99/1**

**Stratégie d'indexation** :
- ✅ Index **nombreux** : 10-30 index par table
- ✅ Index **composites** larges
- ✅ Index **covering** avec INCLUDE
- ✅ **Priorité** : Lecture ultra-rapide

**Exemple concret** :
```sql
-- Table VentesFait (OLAP)
CREATE TABLE VentesFait (
    VenteID INT PRIMARY KEY,
    DateID INT,
    ProduitID INT,
    ClientID INT,
    MagasinID INT,
    Quantite INT,
    Montant DECIMAL(10,2)
);

-- Index NOMBREUX pour OLAP
CREATE INDEX IX_Ventes_Date ON VentesFait (DateID);
CREATE INDEX IX_Ventes_Produit ON VentesFait (ProduitID);
CREATE INDEX IX_Ventes_Client ON VentesFait (ClientID);
CREATE INDEX IX_Ventes_Magasin ON VentesFait (MagasinID);
CREATE INDEX IX_Ventes_Date_Produit ON VentesFait (DateID, ProduitID);
CREATE INDEX IX_Ventes_Date_Magasin ON VentesFait (DateID, MagasinID);
CREATE INDEX IX_Ventes_Produit_Client ON VentesFait (ProduitID, ClientID);
-- ... jusqu'à 20-30 index
-- Total : 20+ index
-- Priorité : Lectures ultra-rapides
```

#### Application mixte

**Exemple** : Application web moderne, CRM

**Caractéristiques** :
- Écritures modérées
- Lectures fréquentes
- Ratio lecture/écriture : **80/20**

**Stratégie d'indexation** :
- ✅ Index **ciblés** : 5-10 index par table
- ✅ Focus sur les requêtes **les plus fréquentes**
- ✅ Surveillance et ajustement continu

### Tableau de décision

| Type d'application | Ratio Lecture/Écriture | Nombre d'index recommandé | Priorité |
|-------------------|------------------------|---------------------------|----------|
| **OLTP pur** | 50/50 | 2-5 index | Écritures rapides |
| **OLTP dominant** | 70/30 | 3-7 index | Équilibre |
| **Mixte** | 80/20 | 5-10 index | Légèrement lectures |
| **OLAP dominant** | 95/5 | 10-20 index | Lectures |
| **OLAP pur** | 99/1 | 15-30+ index | Lectures ultra-rapides |

## Cas Spéciaux : Coûts Additionnels

### 1. Page Splits (Division de pages)

Quand un index est **trié** et qu'une nouvelle valeur doit être insérée **au milieu**, SQL Server peut devoir **diviser une page**.

#### Exemple : Index sur Date avec insertions désordonnées

```sql
-- Index sur DateCommande
CREATE INDEX IX_Commandes_Date ON Commandes (DateCommande);

-- Insertions dans l'ordre chronologique : PAS de problème
INSERT INTO Commandes (DateCommande, ...) VALUES ('2024-11-18', ...);
INSERT INTO Commandes (DateCommande, ...) VALUES ('2024-11-19', ...);
-- Ajout à la fin de l'index → Rapide ✓

-- Insertion désordonnée : PROBLÈME (correction de données anciennes)
INSERT INTO Commandes (DateCommande, ...) VALUES ('2024-01-15', ...);
-- Doit insérer au MILIEU de l'index
-- Si la page est pleine → Page Split (division)
-- Coût : 3-5x plus lent
```

**Visualisation d'un Page Split** :

```
Avant l'insertion (Page pleine) :
┌───────────────────────────────┐
│ Page 100 (pleine)             │
│ 2024-01-10, 2024-01-12,       │
│ 2024-01-14, 2024-01-16,       │
│ 2024-01-18, 2024-01-20        │
└───────────────────────────────┘

Insertion : 2024-01-15 (au milieu)
↓

Page Split (division en deux pages) :
┌───────────────────────────────┐  ┌───────────────────────────────┐
│ Page 100 (moitié)             │  │ Page 101 (nouvelle, moitié)   │
│ 2024-01-10, 2024-01-12,       │  │ 2024-01-15, 2024-01-16,       │
│ 2024-01-14                    │  │ 2024-01-18, 2024-01-20        │
└───────────────────────────────┘  └───────────────────────────────┘

Coût : Création d'une nouvelle page + Déplacement de données + Mise à jour des pointeurs
```

**Impact** :
- Ralentissement temporaire des écritures
- Fragmentation de l'index
- Nécessite une maintenance périodique (REBUILD)

### 2. Index sur UNIQUEIDENTIFIER (GUID)

Les **GUID** (Globally Unique Identifiers) générés avec `NEWID()` sont **aléatoires**.

```sql
-- Table avec GUID comme clé primaire
CREATE TABLE Documents (
    DocumentID UNIQUEIDENTIFIER DEFAULT NEWID() PRIMARY KEY,
    Titre NVARCHAR(500),
    Contenu NVARCHAR(MAX)
);

-- INSERT
INSERT INTO Documents (Titre, Contenu) VALUES ('Doc 1', '...');
-- DocumentID = '8F3C2A15-...' (aléatoire)

INSERT INTO Documents (Titre, Contenu) VALUES ('Doc 2', '...');
-- DocumentID = '2B7E9F31-...' (aléatoire)
```

**Problème** : Les GUID aléatoires causent des **Page Splits constants**.

```
Index sur DocumentID (GUID aléatoires) :
┌─────────────────────────────────────────┐
│ 12ABC... 2B7E9... 8F3C2... A4D5F...     │
└─────────────────────────────────────────┘
             ↑
     Insertion aléatoire partout
     Page Splits fréquents
     Fragmentation élevée
```

**Solution** : Utilisez `NEWSEQUENTIALID()` ou un INT IDENTITY.

```sql
-- ✅ MIEUX : GUID séquentiel
CREATE TABLE Documents (
    DocumentID UNIQUEIDENTIFIER DEFAULT NEWSEQUENTIALID() PRIMARY KEY,
    ...
);

-- ✅ ENCORE MIEUX : INT auto-incrémenté
CREATE TABLE Documents (
    DocumentID INT IDENTITY(1,1) PRIMARY KEY,
    ...
);
```

### 3. Index sur colonnes larges

Plus une colonne est **large**, plus l'index est **volumineux** et coûteux à maintenir.

```sql
-- ❌ Index sur colonne très large
CREATE INDEX IX_Documents_Contenu
ON Documents (Contenu);  -- NVARCHAR(MAX) → Énorme !

-- Coût INSERT : Très élevé
-- Taille index : Gigantesque
-- Maintenance : Cauchemar
```

**Recommandation** :
- Indexez les colonnes **étroites** (INT, DATE, VARCHAR(50))
- Utilisez **Full-Text Search** pour les grandes colonnes de texte

### 4. Triggers et index

Si vous avez des **triggers** sur la table, ils s'exécutent à chaque opération DML.

```sql
-- Trigger AFTER INSERT
CREATE TRIGGER trg_Clients_AfterInsert
ON Clients
AFTER INSERT
AS
BEGIN
    -- Code du trigger (ex: audit, validation)
    INSERT INTO AuditLog (...)
    SELECT ... FROM INSERTED;
END;

-- INSERT
INSERT INTO Clients (...) VALUES (...);

-- Coût :
-- 1. Mise à jour de la table Clients + tous ses index
-- 2. Exécution du trigger
-- 3. Mise à jour de AuditLog + tous ses index
-- Total : Coût cumulé
```

**Impact** : Triggers + beaucoup d'index = Écritures très lentes.

## Stratégies pour Minimiser le Coût

### Stratégie 1 : Index seulement sur les colonnes nécessaires

**Principe** : Créez des index uniquement pour les requêtes **fréquentes** et **lentes**.

```sql
-- ❌ MAUVAIS : Index "au cas où"
CREATE INDEX IX_Clients_Nom ON Clients (Nom);
CREATE INDEX IX_Clients_Prenom ON Clients (Prenom);
CREATE INDEX IX_Clients_Telephone ON Clients (Telephone);
CREATE INDEX IX_Clients_Adresse ON Clients (Adresse);
CREATE INDEX IX_Clients_Ville ON Clients (Ville);
CREATE INDEX IX_Clients_CodePostal ON Clients (CodePostal);
CREATE INDEX IX_Clients_DateInscription ON Clients (DateInscription);
CREATE INDEX IX_Clients_DateModification ON Clients (DateModification);
-- 8 index !

-- ✅ BON : Index ciblés pour requêtes réelles
CREATE INDEX IX_Clients_Email ON Clients (Email);  -- Recherche login (fréquent)
CREATE INDEX IX_Clients_Ville ON Clients (Ville);  -- Recherche géographique (fréquent)
-- 2 index seulement
```

### Stratégie 2 : Index filtrés pour réduire la taille

```sql
-- ❌ Index complet (10 millions de lignes)
CREATE INDEX IX_Commandes_Client ON Commandes (ClientID);

-- ✅ Index filtré (200 000 lignes seulement)
CREATE INDEX IX_Commandes_Actives_Client
ON Commandes (ClientID)
WHERE Statut IN ('En cours', 'En préparation');

-- Avantages :
-- - 50x plus petit
-- - INSERT/UPDATE/DELETE beaucoup plus rapides (si Statut != 'En cours')
```

### Stratégie 3 : Désactiver les index pendant les chargements massifs

Pour des **imports en masse** (ETL, migration), désactivez temporairement les index.

```sql
-- 1. Désactiver tous les index non-clustered
ALTER INDEX ALL ON Clients DISABLE;

-- 2. Charger les données (beaucoup plus rapide)
BULK INSERT Clients FROM 'data.csv' ...
-- Ou : INSERT INTO Clients SELECT * FROM StagingTable;

-- 3. Réactiver les index (reconstruction)
ALTER INDEX ALL ON Clients REBUILD;
```

**Gain** : 5-10x plus rapide pour les gros chargements (> 100 000 lignes).

### Stratégie 4 : Utiliser des tables de staging

Pour les chargements complexes :

```sql
-- 1. Créer une table de staging SANS index
CREATE TABLE Clients_Staging (
    Nom NVARCHAR(100),
    Email NVARCHAR(255),
    ...
);
-- Pas d'index du tout

-- 2. Charger dans la staging (très rapide)
BULK INSERT Clients_Staging FROM 'data.csv' ...

-- 3. Valider et nettoyer les données
DELETE FROM Clients_Staging WHERE Email IS NULL;
UPDATE Clients_Staging SET Nom = TRIM(Nom);

-- 4. Insérer dans la table finale (avec index)
INSERT INTO Clients (Nom, Email, ...)
SELECT Nom, Email, ... FROM Clients_Staging;

-- 5. Supprimer la staging
DROP TABLE Clients_Staging;
```

### Stratégie 5 : Batching (lots)

Au lieu d'insérer ligne par ligne, insérez par **lots** (batches).

```sql
-- ❌ LENT : Ligne par ligne (10 000 INSERT)
DECLARE @i INT = 1;
WHILE @i <= 10000
BEGIN
    INSERT INTO Clients (Nom, Email) VALUES ('Client ' + CAST(@i AS NVARCHAR), 'email' + CAST(@i AS NVARCHAR) + '@test.com');
    SET @i = @i + 1;
END;
-- Temps : ~60 secondes

-- ✅ RAPIDE : Par lots de 1000
INSERT INTO Clients (Nom, Email)
SELECT
    'Client ' + CAST(Number AS NVARCHAR),
    'email' + CAST(Number AS NVARCHAR) + '@test.com'
FROM master..spt_values
WHERE Type = 'P' AND Number BETWEEN 1 AND 10000;
-- Temps : ~5 secondes (12x plus rapide)
```

**Principe** : Moins de commits = Moins d'overhead = Plus rapide.

### Stratégie 6 : Éviter les index redondants

```sql
-- ❌ REDONDANT
CREATE INDEX IX_Clients_Email ON Clients (Email);
CREATE INDEX IX_Clients_Email_Ville ON Clients (Email, Ville);
-- Le premier est inutile, le second couvre le premier

-- ✅ BON : Un seul index composite
CREATE INDEX IX_Clients_Email_Ville ON Clients (Email, Ville);
-- Couvre : WHERE Email = ... ET WHERE Email = ... AND Ville = ...
```

### Stratégie 7 : Fill Factor pour réduire les Page Splits

Le **Fill Factor** détermine le pourcentage de remplissage des pages d'index.

```sql
-- Par défaut : Fill Factor = 100% (pages pleines)
CREATE INDEX IX_Commandes_Date ON Commandes (DateCommande);

-- Avec Fill Factor = 80% (20% d'espace libre)
CREATE INDEX IX_Commandes_Date ON Commandes (DateCommande)
WITH (FILLFACTOR = 80);

-- Avantages :
-- - Moins de Page Splits (espace libre disponible)
-- - INSERT plus rapides

-- Inconvénients :
-- - Index 25% plus gros
-- - SELECT légèrement plus lents (plus de pages à lire)
```

**Usage** : Tables avec beaucoup d'INSERT au milieu (pas seulement à la fin).

## Surveillance des Coûts

### Identifier les index inutilisés

```sql
-- Index qui ne sont jamais ou rarement utilisés
SELECT
    OBJECT_NAME(s.object_id) AS TableName,
    i.name AS IndexName,
    s.user_seeks AS Seeks,
    s.user_scans AS Scans,
    s.user_lookups AS Lookups,
    s.user_updates AS Updates,
    s.user_seeks + s.user_scans + s.user_lookups AS TotalReads,
    CASE
        WHEN s.user_seeks + s.user_scans + s.user_lookups = 0 THEN 'JAMAIS UTILISÉ'
        WHEN s.user_updates > (s.user_seeks + s.user_scans + s.user_lookups) * 10 THEN 'COÛTEUX'
        ELSE 'OK'
    END AS Statut
FROM sys.dm_db_index_usage_stats s
INNER JOIN sys.indexes i ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE s.database_id = DB_ID()
  AND i.type_desc = 'NONCLUSTERED'
  AND OBJECT_NAME(s.object_id) NOT LIKE 'sys%'
ORDER BY s.user_updates DESC;
```

**Interprétation** :
- **Seeks = 0, Scans = 0, Lookups = 0** : Index jamais utilisé → **Supprimer**
- **Updates >> Reads** (ex: 10 000 updates, 10 reads) : Index coûteux → **Évaluer**

### Mesurer l'impact des index sur les écritures

```sql
-- Statistiques d'écriture par table
SELECT
    OBJECT_NAME(object_id) AS TableName,
    SUM(user_updates) AS TotalUpdates
FROM sys.dm_db_index_usage_stats
WHERE database_id = DB_ID()
GROUP BY OBJECT_NAME(object_id)
ORDER BY TotalUpdates DESC;

-- Statistiques par index
SELECT
    OBJECT_NAME(s.object_id) AS TableName,
    i.name AS IndexName,
    s.user_updates AS Updates,
    s.user_seeks + s.user_scans + s.user_lookups AS Reads,
    CASE
        WHEN s.user_updates > (s.user_seeks + s.user_scans + s.user_lookups) THEN 'PROBLÈME'
        ELSE 'OK'
    END AS Evaluation
FROM sys.dm_db_index_usage_stats s
INNER JOIN sys.indexes i ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE s.database_id = DB_ID()
ORDER BY s.user_updates DESC;
```

### Index manquants vs Index coûteux

SQL Server suggère des **index manquants** :

```sql
-- Index manquants suggérés par SQL Server
SELECT
    d.statement AS TableName,
    d.equality_columns,
    d.inequality_columns,
    d.included_columns,
    s.avg_user_impact AS AvgImpact,
    s.user_seeks AS Seeks,
    s.user_scans AS Scans
FROM sys.dm_db_missing_index_details d
INNER JOIN sys.dm_db_missing_index_groups g ON d.index_handle = g.index_handle
INNER JOIN sys.dm_db_missing_index_group_stats s ON g.index_group_handle = s.group_handle
WHERE d.database_id = DB_ID()
ORDER BY s.avg_user_impact DESC;
```

**Attention** : Ne créez pas **tous** les index suggérés ! Évaluez :
- Le bénéfice (avg_user_impact, seeks, scans)
- Le coût (nombre d'écritures sur la table)

## Exemples de Décisions

### Exemple 1 : Table de Commandes (OLTP)

**Contexte** :
- Table : 5 millions de commandes
- Opérations : 1000 INSERT/minute, 500 UPDATE/minute, 100 DELETE/minute
- Requêtes : 5000 SELECT/minute

**Ratio** : 5000 / 1600 = 3.1 (76% lectures, 24% écritures)

**Décision** :
```sql
-- Index MINIMAL pour OLTP
CREATE INDEX IX_Commandes_Client ON Commandes (ClientID);  -- Recherches fréquentes
CREATE INDEX IX_Commandes_Date ON Commandes (DateCommande);  -- Tri chronologique
-- Total : 3 index (PRIMARY + 2)

-- ❌ NE PAS créer :
-- CREATE INDEX IX_Commandes_Statut ON Commandes (Statut);  -- Faible sélectivité
-- CREATE INDEX IX_Commandes_Montant ON Commandes (MontantTotal);  -- Rarement utilisé seul
```

### Exemple 2 : Table de Ventes (Datawarehouse)

**Contexte** :
- Table : 100 millions de ventes
- Opérations : Chargement nocturne (1x/jour), pas d'écritures en journée
- Requêtes : 10 000 SELECT/minute pendant la journée

**Ratio** : ~99.9% lectures, 0.1% écritures

**Décision** :
```sql
-- Index NOMBREUX pour lecture optimale
CREATE INDEX IX_Ventes_Date ON Ventes (DateID);
CREATE INDEX IX_Ventes_Produit ON Ventes (ProduitID);
CREATE INDEX IX_Ventes_Client ON Ventes (ClientID);
CREATE INDEX IX_Ventes_Magasin ON Ventes (MagasinID);
CREATE INDEX IX_Ventes_Date_Produit ON Ventes (DateID, ProduitID) INCLUDE (Quantite, Montant);
CREATE INDEX IX_Ventes_Date_Magasin ON Ventes (DateID, MagasinID) INCLUDE (Montant);
CREATE INDEX IX_Ventes_Produit_Client ON Ventes (ProduitID, ClientID);
CREATE INDEX IX_Ventes_Date_Client ON Ventes (DateID, ClientID);
-- ... 15-20 index au total

-- Chargement nocturne :
-- 1. DISABLE tous les index
-- 2. BULK INSERT
-- 3. REBUILD tous les index
```

### Exemple 3 : Table de Logs (écriture intensive)

**Contexte** :
- Table : 50 millions de logs
- Opérations : 10 000 INSERT/seconde, 0 UPDATE, 0 DELETE
- Requêtes : 10 SELECT/minute (recherches occasionnelles)

**Ratio** : 10 / 600 000 = 0.00017 (99.998% écritures, 0.002% lectures)

**Décision** :
```sql
-- Index MINIMAL ou AUCUN
CREATE CLUSTERED INDEX IX_Logs_DateLog ON Logs (DateLog);  -- Clustering par date
-- Pas d'autre index

-- Pour les recherches occasionnelles : accepter le Table Scan
-- Ou : utiliser une table de staging + archivage périodique
```

### Situation initiale : Application web (OLTP)

**Table Produits** :
- 100 000 produits
- 1000 INSERT/jour (nouveaux produits)
- 10 000 UPDATE/jour (prix, stock)
- 100 000 SELECT/jour

```sql
-- Configuration AVANT : 12 index
CREATE INDEX IX_Produits_Nom ON Produits (Nom);
CREATE INDEX IX_Produits_Prix ON Produits (Prix);
CREATE INDEX IX_Produits_Stock ON Produits (Stock);
CREATE INDEX IX_Produits_Categorie ON Produits (CategorieID);
CREATE INDEX IX_Produits_Marque ON Produits (MarqueID);
CREATE INDEX IX_Produits_SKU ON Produits (SKU);
CREATE INDEX IX_Produits_DateAjout ON Produits (DateAjout);
CREATE INDEX IX_Produits_Actif ON Produits (Actif);
CREATE INDEX IX_Produits_Nom_Categorie ON Produits (Nom, CategorieID);
CREATE INDEX IX_Produits_Categorie_Prix ON Produits (CategorieID, Prix);
CREATE INDEX IX_Produits_Marque_Prix ON Produits (MarqueID, Prix);
CREATE INDEX IX_Produits_Actif_Nom ON Produits (Actif, Nom);
-- 12 index non-clustered + 1 clustered = 13 total
```

**Performances AVANT** :
- SELECT moyen : 15 ms (correct)
- UPDATE moyen : 45 ms (lent !)
- INSERT moyen : 30 ms (lent !)
- Taille des index : 800 MB

**Analyse** :
```sql
-- Statistiques d'utilisation
-- IX_Produits_Nom : 5000 seeks, 2000 updates → Utile
-- IX_Produits_SKU : 8000 seeks, 2000 updates → Très utile (recherches fréquentes)
-- IX_Produits_Categorie : 3000 seeks, 2000 updates → Utile
-- IX_Produits_Prix : 10 seeks, 2000 updates → INUTILE (peu utilisé)
-- IX_Produits_Stock : 5 seeks, 10000 updates → TRÈS COÛTEUX
-- IX_Produits_DateAjout : 50 seeks, 2000 updates → Peu utile
-- IX_Produits_Actif : 100 seeks, 2000 updates → Peu utile
-- ... plusieurs index peu ou pas utilisés
```

### Configuration optimisée

```sql
-- Configuration APRÈS : 5 index ciblés
CREATE UNIQUE INDEX IX_Produits_SKU ON Produits (SKU);  -- Recherche exacte
CREATE INDEX IX_Produits_Nom ON Produits (Nom);  -- Recherche par nom
CREATE INDEX IX_Produits_Categorie_Prix
ON Produits (CategorieID, Prix)
INCLUDE (Nom, Stock, MarqueID)  -- Covering index
WHERE Actif = 1;  -- Filtré sur produits actifs

CREATE INDEX IX_Produits_Marque_Categorie
ON Produits (MarqueID, CategorieID);  -- Navigation catalogue

-- 5 index au total (dont 1 filtré avec INCLUDE)
```

**Performances APRÈS** :
- SELECT moyen : 10 ms (meilleur !)
- UPDATE moyen : 12 ms (4x plus rapide !)
- INSERT moyen : 8 ms (4x plus rapide !)
- Taille des index : 250 MB (3x plus petit)

**Gains** :
- 🚀 Écritures 4x plus rapides
- 💾 75% d'économie d'espace
- ⚡ Lectures aussi rapides (voire meilleures grâce aux covering index)

#### 1. Ne créez pas trop d'index "par sécurité"

```sql
-- ❌ MAUVAIS : 15 index sur une table OLTP
-- Coût énorme sur les écritures
```

#### 2. N'indexez pas toutes les colonnes

```sql
-- ❌ MAUVAIS

CREATE INDEX IX_Produits_Col2 ON Produits (Col2);

```

```sql
-- Si user_seeks = 0 et user_updates = 100 000
-- Supprimez l'index !

```

#### 4. N'utilisez pas NEWID() pour les clés primaires

```sql

    DocumentID UNIQUEIDENTIFIER DEFAULT NEWID() PRIMARY KEY,
    ...
);

-- ✅ BON : INT auto-incrémenté
CREATE TABLE Documents (
    DocumentID INT IDENTITY(1,1) PRIMARY KEY,
    ...
);
```

## Résumé et Points Clés

### 🎯 Concepts essentiels

1. **Les index ont un coût**
   - Plus d'index = Lectures plus rapides MAIS Écritures plus lentes
   - Chaque index doit être maintenu lors des INSERT/UPDATE/DELETE

2. **Le coût est proportionnel**
   - 1 index = 2x plus d'écritures
   - 5 index = 6x plus d'écritures
   - 10 index = 11x plus d'écritures

3. **Ratio lecture/écriture détermine la stratégie**
   - OLTP (50/50 à 70/30) : 2-5 index
   - Mixte (80/20) : 5-10 index
   - OLAP (95/5) : 15-30+ index

4. **Coûts additionnels**
   - Page Splits : Insertions au milieu de l'index
   - GUID aléatoires : Fragmentation constante
   - Colonnes larges : Index volumineux
   - Triggers : Coût cumulé

5. **Stratégies d'optimisation**
   - Index filtrés : Moins de lignes = Moins de coût
   - Désactivation temporaire : Pour chargements massifs
   - Fill Factor : Espace libre pour éviter les Page Splits
   - Surveillance : Supprimez les index inutilisés

### ⚖️ L'équilibre parfait

```
                    Index MINIMAL              Index OPTIMAL             Index EXCESSIF
                         │                           │                          │
Lectures                 │ Lentes 🐌                 │ Rapides ⚡               │ Très rapides ⚡⚡
Écritures                │ Rapides ⚡                │ Acceptables ⚠️           │ Très lentes 🐌🐌
Espace disque            │ Minimal 💾                │ Modéré 💾💾              │ Énorme 💾💾💾
Maintenance              │ Facile ✅                 │ Gérable ⚠️               │ Difficile ❌
                         │                           │                          │
                         │                           ▼                          │
                         │                    C'EST ICI                         │
                         │                   QU'IL FAUT ÊTRE !                  │
```

### ✅ Checklist de décision

Avant de créer un index, demandez-vous :

- [ ] Est-ce que cette requête est fréquente (> 100 fois/jour) ?
- [ ] Est-ce qu'elle est lente (> 100 ms) ?
- [ ] Le gain en lecture justifie-t-il le coût en écriture ?
- [ ] Le ratio lecture/écriture de ma table le permet-il ?
- [ ] Ai-je vérifié les statistiques d'utilisation des index existants ?
- [ ] Ai-je envisagé un index filtré ou composite au lieu de plusieurs index séparés ?

### 📋 Actions concrètes

```sql
-- 1. Identifiez les index inutilisés
SELECT ... FROM sys.dm_db_index_usage_stats WHERE user_seeks = 0 ...

-- 2. Supprimez-les
DROP INDEX IX_Inutile ON MaTable;

-- 3. Surveillez l'impact des index sur les écritures
SELECT ... user_updates ... ORDER BY user_updates DESC;

-- 4. Créez des index filtrés quand possible
CREATE INDEX ... WHERE condition;

-- 5. Ajustez selon votre ratio lecture/écriture
```

## Conclusion

Les **index sont essentiels** pour les performances de lecture, mais ils ont un **coût réel** sur les écritures. La clé du succès est de trouver le **bon équilibre** entre :
- 📖 Performances de lecture (SELECT)
- ✍️ Performances d'écriture (INSERT, UPDATE, DELETE)

**La règle d'or** :
> Ne créez un index que si le gain en performances de lecture justifie largement le coût en performances d'écriture.

**Principe de Pareto appliqué aux index** :
- 20% des index fournissent 80% des gains de performance
- Les 80% restants coûtent cher pour peu de bénéfice
- Concentrez-vous sur les 20% d'index vraiment utiles
