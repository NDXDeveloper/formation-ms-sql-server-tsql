# 8.6.3 Modèles d'achat (DTU vs. vCore)

## Introduction

Lorsque vous créez une base de données Azure SQL, l'une des questions les plus importantes est : **"Quelle taille et quelle puissance choisir ?"**

Dans le cloud, contrairement aux serveurs physiques, vous ne choisissez pas directement la RAM ou le processeur. À la place, Microsoft Azure propose **deux modèles d'achat** différents pour dimensionner vos bases de données :

1. **DTU** (Database Transaction Unit) - Modèle simplifié basé sur des unités combinées
2. **vCore** (Virtual Core) - Modèle détaillé basé sur les ressources CPU

Cette section vous aide à comprendre ces deux approches et à choisir celle qui convient le mieux à vos besoins.

## Analogie générale : Restaurant vs. Menu à la carte

Pour comprendre la différence fondamentale entre ces deux modèles, imaginez deux façons de commander au restaurant :

**Modèle DTU = Menu fixe**
- Vous choisissez un "Menu 1", "Menu 2" ou "Menu 3"
- Chaque menu contient entrée + plat + dessert + boisson
- Simple : vous ne choisissez pas les détails
- Prix fixe par menu

**Modèle vCore = À la carte**
- Vous choisissez exactement ce que vous voulez
- 2 entrées, pas de dessert, double portion du plat
- Plus de contrôle et de personnalisation
- Prix selon ce que vous prenez

C'est exactement la différence entre DTU et vCore !

## Qu'est-ce qui est inclus dans les ressources ?

Avant de détailler chaque modèle, comprenons ce qui compose les "ressources" d'une base de données :

### Les trois piliers des performances

```
┌─────────────────────────────────────────────────────────────┐
│         Ressources d'une base de données                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1️⃣  CPU (Processeur)                                       │
│      • Calculs, exécution de requêtes                       │
│      • Traitement des données                               │
│                                                             │
│  2️⃣  Mémoire (RAM)                                          │
│      • Cache des données                                    │
│      • Buffer pool                                          │
│      • Exécution des requêtes complexes                     │
│                                                             │
│  3️⃣  I/O (Entrées/Sorties disque)                           │
│      • Lecture des données depuis le stockage               │
│      • Écriture des données                                 │
│      • Vitesse d'accès au disque                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Dans Azure SQL :**
- **Modèle DTU** : Ces trois éléments sont **combinés** dans une seule unité
- **Modèle vCore** : Vous choisissez principalement le **CPU**, et la RAM et I/O sont proportionnels

## Le modèle DTU (Database Transaction Unit)

### Concept fondamental

Une **DTU** (Database Transaction Unit) est une **unité de mesure abstraite** qui combine CPU, mémoire et I/O dans une seule métrique.

**Définition simple :**
> 1 DTU = Une unité de puissance qui mélange processeur, mémoire et I/O dans des proportions fixes déterminées par Microsoft

### Analogie : La voiture avec moteur unique

Imaginez acheter une voiture où on vous dit :
- "Modèle A : 50 unités de puissance"
- "Modèle B : 100 unités de puissance"

Vous ne savez pas exactement combien il y a de chevaux, quelle est la consommation, ou la taille du réservoir, mais vous savez que "100 unités" est deux fois plus puissant que "50 unités".

**C'est exactement le principe de la DTU :** Une mesure simplifiée de la puissance globale.

### Les niveaux de service DTU

Azure SQL Database propose **trois niveaux** dans le modèle DTU :

```
┌─────────────────────────────────────────────────────────────────┐
│                    Niveaux de service DTU                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  🔹 Basic                                                       │
│     • 5 DTU                                                     │
│     • 2 Go max                                                  │
│     • ~5 €/mois                                                 │
│     • Usage : Dev/test très léger                               │
│                                                                 │
│  🔸 Standard (S0 à S12)                                         │
│     • 10 à 3000 DTU                                             │
│     • Jusqu'à 1 To                                              │
│     • ~15 € à ~2300 €/mois                                      │
│     • Usage : Production standard                               │
│                                                                 │
│  🔺 Premium (P1 à P15)                                          │
│     • 125 à 4000 DTU                                            │

│     • ~450 € à ~11000 €/mois                                    │
│     • Usage : Haute performance, latence faible                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Détail des niveaux DTU

#### Basic (5 DTU)

**Caractéristiques :**
- 5 DTU (puissance minimale)
- 2 Go de stockage maximum
- 1 base de données active à la fois
- Pas de restauration à un instant T étendue (7 jours max)

**Cas d'usage :**
- Apprentissage et expérimentation
- Très petites bases de données de test
- Applications de preuve de concept

**Analogie :** Une trottinette électrique - ça marche, mais pas pour aller loin ou vite.

#### Standard (S0 à S12)

**Gamme :**
| Niveau | DTU | Stockage max | Prix indicatif/mois | Usage typique |
|--------|-----|--------------|---------------------|---------------|
| S0 | 10 | 250 Go | ~15 € | Dev/test |
| S1 | 20 | 250 Go | ~30 € | Petites apps |
| S2 | 50 | 250 Go | ~75 € | Apps moyennes |
| S3 | 100 | 1 To | ~150 € | Apps production |
| S4 | 200 | 1 To | ~300 € | Apps importantes |
| S6 | 400 | 1 To | ~600 € | Apps chargées |
| S7 | 800 | 1 To | ~1200 € | Apps très chargées |
| S9 | 1600 | 1 To | ~2400 € | Forte charge |
| S12 | 3000 | 1 To | ~4500 € | Charge maximale |

**Caractéristiques clés :**
- Restauration à un instant T : 35 jours
- Réplication géographique disponible (à partir de S3)
- Convient à **la plupart des applications de production**

**Cas d'usage :**
- Applications web professionnelles
- Sites e-commerce moyens
- Applications d'entreprise standards
- Bases de données OLTP (transactions)

**Analogie :** Une voiture familiale - fiable, efficace, adaptée au quotidien.

#### Premium (P1 à P15)

**Gamme :**
| Niveau | DTU | Stockage max | Prix indicatif/mois | Usage typique |
|--------|-----|--------------|---------------------|---------------|
| P1 | 125 | 1 To | ~450 € | Haute perf. débutant |
| P2 | 250 | 1 To | ~900 € | Haute performance |
| P4 | 500 | 1 To | ~1800 € | Très haute perf. |
| P6 | 1000 | 1 To | ~3600 € | Performance critique |
| P11 | 1750 | 4 To | ~6300 € | Ultra performance |
| P15 | 4000 | 4 To | ~11000 € | Maximum |

**Caractéristiques clés :**
- **I/O ultra-rapides** : Latence < 2 ms
- Restauration à un instant T : 35 jours
- Réplication géographique active
- **In-Memory OLTP** disponible
- Performances prévisibles et constantes

**Cas d'usage :**
- Applications critiques avec exigences SLA strictes
- Trading financier (latence minimale requise)
- Applications avec pics de charge très élevés
- Bases de données nécessitant In-Memory OLTP

**Analogie :** Une voiture de sport haute performance - rapide, réactive, mais coûteuse.

### Comment fonctionne la mesure DTU ?

Microsoft a créé un **benchmark standardisé** qui simule une charge de travail typique :

```
Benchmark DTU = Transactions par seconde dans un scénario mixte
├─ Lectures de données
├─ Écritures de données
├─ Requêtes complexes (JOIN, GROUP BY)
└─ Transactions concurrentes
```

**Exemple concret :**
- 1 DTU = Capacité de traiter environ **1 transaction par seconde** dans ce benchmark
- 100 DTU = Capacité de traiter environ **100 transactions par seconde**

**Important :** Ces chiffres sont des **approximations**. La performance réelle dépend de votre charge de travail spécifique.

### Avantages du modèle DTU

| Avantage | Explication |
|----------|-------------|
| **Simplicité** | Un seul chiffre à choisir (50 DTU, 100 DTU, etc.) |
| **Pas de calculs complexes** | Pas besoin de connaître RAM/CPU/I/O séparément |
| **Bon pour débuter** | Facile à comprendre pour les non-experts |
| **Prix prévisible** | Coût fixe par niveau |
| **Migration facile entre niveaux** | Passer de S2 à S3 en un clic |

### Inconvénients du modèle DTU

| Inconvénient | Explication |
|--------------|-------------|
| **Manque de granularité** | Impossible de choisir CPU indépendamment de la RAM |
| **Proportions fixes** | Les ressources sont dans des proportions imposées par Microsoft |
| **Moins prévisible** | Difficile de savoir exactement combien de CPU/RAM vous avez |
| **Pas de réservation** | Pas d'option pour réserver et réduire les coûts |
| **Limité en taille** | Maximum 1 To (Standard) ou 4 To (Premium) |

### Quand choisir le modèle DTU ?

**✅ Choisir DTU si :**
1. **Vous débutez avec Azure SQL**
   - Pas d'expertise cloud requise
   - Simple à comprendre

2. **Vous voulez de la simplicité**
   - Pas envie de calculer CPU/RAM séparément
   - Juste besoin d'une base qui fonctionne

3. **Bases de données de petite à moyenne taille**
   - Moins de 1 To de données
   - Charge standard prévisible

4. **Budget limité et prévisible**
   - Coûts mensuels fixes
   - Pas de surprise sur la facture

**Exemple de profil idéal :**
Une PME avec un site web e-commerce, 100 Go de données, 1000 utilisateurs par jour, équipe IT de 2 personnes sans spécialiste cloud.

## Le modèle vCore (Virtual Core)

### Concept fondamental

Le modèle **vCore** (Virtual Core) vous permet de choisir précisément le **nombre de cœurs de processeur** (vCores) que vous voulez, avec des ressources de mémoire et d'I/O proportionnelles.

**Définition simple :**
> 1 vCore = 1 cœur de processeur virtuel avec RAM et I/O proportionnels

### Analogie : Construire son ordinateur

Imaginez acheter un ordinateur en choisissant :
- Processeur : 2 cœurs, 4 cœurs, ou 8 cœurs ?
- RAM : Proportionnelle au nombre de cœurs
- Disque : SSD standard ou ultra-rapide ?

**C'est exactement le modèle vCore :** Vous choisissez les composants principaux et obtenez une configuration proportionnelle.

### Les composantes du modèle vCore

```
┌─────────────────────────────────────────────────────────────┐
│              Configuration vCore                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1️⃣  Nombre de vCores                                       │
│      • 2, 4, 6, 8, 10, 12... jusqu'à 80 vCores              │
│      • Vous choisissez exactement                           │
│                                                             │
│  2️⃣  Génération de matériel                                 │
│      • Gen5 (standard, Intel)                               │
│      • Fsv2 (optimisé calcul)                               │
│      • M-series (optimisé mémoire)                          │
│                                                             │
│  3️⃣  Niveau de service                                      │
│      • General Purpose (usage standard)                     │
│      • Business Critical (haute performance)                │
│      • Hyperscale (très grandes bases)                      │
│                                                             │
│  4️⃣  Stockage                                               │
│      • Taille : 5 Go à 4 To (GP) ou 100 To (Hyperscale)     │
│      • Type : SSD standard ou ultra-rapide                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Les niveaux de service vCore

#### 1. General Purpose (Usage général)

**Concept :** Équilibre entre performance et coût pour la plupart des charges de travail.

**Caractéristiques techniques :**
- Stockage distant (Azure Premium Storage)
- Latence I/O : 5-10 ms
- 2-80 vCores disponibles
- RAM : 5,1 Go par vCore
- Taille max : 4 To

**Architecture :**
```
┌────────────────────────────────────────┐
│      General Purpose                   │
│                                        │
│  ┌──────────────────┐                  │
│  │  Compute (SQL)   │                  │
│  │  2-80 vCores     │                  │
│  └────────┬─────────┘                  │
│           │                            │
│           │ Réseau                     │
│           ↓                            │
│  ┌──────────────────┐                  │
│  │ Stockage distant │                  │
│  │ (Premium SSD)    │                  │
│  └──────────────────┘                  │
│                                        │
│  Haute disponibilité via réplicas      │
│  automatiques                          │
└────────────────────────────────────────┘
```

**Avantages :**
- ✅ Bon rapport qualité/prix
- ✅ Suffisant pour 80% des applications
- ✅ Scaling facile (ajout de vCores)

**Inconvénients :**
- ⚠️ Latence I/O plus élevée (5-10 ms vs 1-2 ms en Business Critical)
- ⚠️ Pas de réplicas en lecture inclus

**Prix indicatif :**
- 2 vCores : ~200-350 €/mois
- 4 vCores : ~400-700 €/mois
- 8 vCores : ~800-1400 €/mois

**Cas d'usage :**
- Applications web standard
- APIs REST
- Applications d'entreprise classiques
- Bases de données OLTP sans exigences de latence extrêmes

#### 2. Business Critical (Critique pour l'entreprise)

**Concept :** Performance maximale avec réplicas locaux pour haute disponibilité et lectures déchargées.

**Caractéristiques techniques :**
- Stockage local (SSD ultra-rapide)
- Latence I/O : 1-2 ms
- 2-80 vCores disponibles
- RAM : 5,1 Go par vCore
- **Réplicas en lecture inclus** (1 à 4 selon config)
- In-Memory OLTP inclus

**Architecture :**
```
┌───────────────────────────────────────────────────┐
│           Business Critical                       │
│                                                   │
│  ┌────────────────┐    ┌────────────────┐         │
│  │ Réplica 1      │    │ Réplica 2      │         │
│  │ (Primaire)     │◄──►│ (Secondaire)   │         │
│  │                │    │ Lecture seule  │         │
│  │ Compute + SSD  │    │ Compute + SSD  │         │
│  │     local      │    │     local      │         │
│  └────────────────┘    └────────────────┘         │
│                                                   │
│  AlwaysOn intégré, basculement < 30 secondes      │
│  Stockage local = latence ultra-faible            │
└───────────────────────────────────────────────────┘
```

**Avantages :**
- ✅ Latence I/O ultra-faible (1-2 ms)
- ✅ Réplicas en lecture inclus (décharger les rapports)
- ✅ In-Memory OLTP disponible
- ✅ Performance maximale et prévisible

**Inconvénients :**
- ⚠️ Coût environ **2,5x plus élevé** que General Purpose
- ⚠️ Pas toujours nécessaire pour applications standard

**Prix indicatif :**
- 2 vCores : ~500-900 €/mois
- 4 vCores : ~1000-1800 €/mois
- 8 vCores : ~2000-3600 €/mois

**Cas d'usage :**
- Applications financières (trading, transactions)
- ERP critiques avec SLA stricts
- Applications nécessitant latence < 5 ms
- Déchargement de reporting sur réplicas secondaires
- Bases nécessitant In-Memory OLTP

#### 3. Hyperscale

**Concept :** Architecture spéciale pour bases de données **très volumineuses** (jusqu'à 100 To).

**Caractéristiques uniques :**
- Taille : 10 Go à **100 To**
- Architecture multi-couches
- Sauvegardes quasi-instantanées (snapshots)
- Scaling du stockage automatique
- Jusqu'à 4 réplicas secondaires en lecture

**Architecture :**
```
┌──────────────────────────────────────────────────────────┐
│                    Hyperscale                            │
│                                                          │
│  ┌──────────────┐                                        │
│  │ Compute      │ ←── Votre application se connecte ici  │
│  │ (Primaire)   │                                        │
│  └──────┬───────┘                                        │
│         │                                                │
│         ↓                                                │
│  ┌──────────────────────────────────────────┐            │
│  │    Page Servers (stockage distribué)     │            │
│  │    Scaling automatique jusqu'à 100 To    │            │
│  └──────────────────────────────────────────┘            │
│                                                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                │
│  │Réplica 1 │  │Réplica 2 │  │Réplica 3 │(Lecture seule) │
│  └──────────┘  └──────────┘  └──────────┘                │
│                                                          │
│  Sauvegardes en snapshots (quasi-instantanées)           │
└──────────────────────────────────────────────────────────┘
```

**Avantages :**
- ✅ Supporte des bases **énormes** (100 To)
- ✅ Croissance du stockage **automatique** (pas de limite à définir)
- ✅ Sauvegardes et restaurations **quasi-instantanées**
- ✅ Jusqu'à 4 réplicas en lecture
- ✅ Scaling de compute indépendant du stockage

**Inconvénients :**
- ⚠️ Plus complexe à comprendre
- ⚠️ Coût plus élevé pour petites bases
- ⚠️ Certaines limitations (pas de support complet de toutes les fonctionnalités)

**Prix indicatif :**
- 2 vCores + 100 Go : ~350-500 €/mois
- 4 vCores + 1 To : ~700-1000 €/mois
- Stockage : ~0,12 €/Go/mois (croît automatiquement)

**Cas d'usage :**
- Bases de données de plusieurs To
- Applications SaaS multi-tenant avec croissance rapide
- Data warehouses
- Applications nécessitant plusieurs réplicas en lecture

### Générations de matériel vCore

Dans le modèle vCore, vous pouvez choisir la **génération de matériel** :

| Génération | Processeur | RAM par vCore | Usage |
|------------|------------|---------------|-------|
| **Gen5** | Intel Xeon E5-2673 v4 | 5,1 Go | Standard (recommandé) |
| **Fsv2-series** | Intel Xeon Platinum 8168 | 2 Go | Optimisé pour calcul intensif |
| **M-series** | Intel Xeon E7-8890 v3 | 29 Go | Optimisé pour mémoire (très coûteux) |

**Recommandation :** Gen5 pour la plupart des cas.

### Options vCore : Provisionné vs Serverless

#### Modèle Provisionné (par défaut)

- Ressources réservées **24/7**
- Facturation continue (même si inutilisé)
- Performance constante et prévisible

**Usage :** Production, bases actives en continu

#### Modèle Serverless (option spéciale)

**Concept révolutionnaire :** Paiement à la seconde, avec pause automatique.

**Fonctionnement :**
```
Base de données active
    ↓
Aucune connexion pendant X minutes (configurable)
    ↓
Pause automatique (arrêt du compute)
    ↓
Facturation = 0 € pour le compute (uniquement stockage)
    ↓
Nouvelle connexion
    ↓
Réveil automatique (quelques secondes)
    ↓
Retour à la facturation à la seconde d'utilisation
```

**Caractéristiques :**
- Facturation à la **seconde** d'utilisation
- Pause automatique après inactivité (1h à 7 jours, configurable)
- Réveil automatique lors de connexion
- 0,5 à 40 vCores (auto-scaling dans cette plage)
- General Purpose uniquement

**Avantages :**
- ✅ **Économies massives** pour bases intermittentes
- ✅ Auto-scaling automatique selon charge
- ✅ Idéal pour dev/test

**Inconvénients :**
- ⚠️ Délai de réveil (quelques secondes)
- ⚠️ Pas pour production critique 24/7

**Prix indicatif (Serverless) :**
- 0,5 vCore minimum : ~0,09 €/heure quand actif
- 4 vCores maximum : ~0,72 €/heure quand actif
- En pause : ~0 € (stockage seulement)

**Exemple de coût réel :**
```
Base de données de développement
Utilisée 8h/jour (lundi-vendredi) = 40h/semaine = 160h/mois
Pause le reste du temps

Coût Serverless :
- Compute : 160h × 0,20 €/h = 32 €
- Stockage : 50 Go × 0,12 € = 6 €
- Total : ~38 €/mois

Coût Provisionné équivalent :
- 2 vCores 24/7 : ~300 €/mois

Économie : ~262 €/mois (87%)
```

**Cas d'usage Serverless :**
- Environnements de développement
- Bases de données de test
- Applications utilisées seulement certaines heures
- Prototypes et POC

### Avantages du modèle vCore

| Avantage | Explication |
|----------|-------------|
| **Contrôle précis** | Choisir exactement le nombre de vCores |
| **Prévisibilité** | Savoir exactement les ressources CPU/RAM |
| **Flexibilité** | Choix du niveau de service et génération matériel |
| **Réservation possible** | Azure Hybrid Benefit (BYOL) pour réduire coûts |
| **Grandes bases** | Jusqu'à 100 To avec Hyperscale |
| **Serverless** | Option de paiement à l'usage |
| **Réplicas en lecture** | Inclus dans Business Critical |

### Inconvénients du modèle vCore

| Inconvénient | Explication |
|--------------|-------------|
| **Plus complexe** | Plusieurs choix à faire (vCore, génération, niveau) |
| **Requiert expertise** | Besoin de comprendre les ressources nécessaires |
| **Coût potentiellement élevé** | Surtout Business Critical |
| **Calculs nécessaires** | Dimensionnement plus technique |

### Quand choisir le modèle vCore ?

**✅ Choisir vCore si :**

1. **Vous voulez du contrôle précis**
   - Besoin de savoir exactement les ressources
   - Optimisation fine des performances

2. **Vous avez des licences SQL Server existantes**
   - Azure Hybrid Benefit (BYOL) = économies importantes
   - Amortissement des investissements on-premise

3. **Grandes bases de données**
   - Plus de 1 To (jusqu'à 100 To avec Hyperscale)
   - Croissance importante prévue

4. **Besoins de performance spécifiques**
   - Latence ultra-faible requise (Business Critical)
   - Réplicas en lecture nécessaires
   - In-Memory OLTP

5. **Charges intermittentes** (avec Serverless)
   - Dev/test qui ne tourne pas 24/7
   - Économies sur environnements non-production

**Exemple de profil idéal :**
Une grande entreprise migrant vers Azure, avec licences SQL Server existantes (Software Assurance), base de 2 To, besoin de haute performance et réplicas en lecture pour reporting.

### Checklist de décision

**Choisissez DTU si vous cochez 3+ cases :**
- [ ] Première utilisation d'Azure SQL
- [ ] Base de données < 1 To
- [ ] Pas de licences SQL Server existantes à réutiliser
- [ ] Budget limité (< 500 €/mois)
- [ ] Besoin de simplicité maximale
- [ ] Pas d'exigences de latence strictes
- [ ] Application standard (web, API, CRUD)

**Choisissez vCore si vous cochez 3+ cases :**
- [ ] Base de données > 1 To
- [ ] Licences SQL Server existantes (Software Assurance)
- [ ] Besoin de contrôle précis des ressources
- [ ] Besoin de haute performance (Business Critical)
- [ ] Besoin de réplicas en lecture
- [ ] Charge intermittente (Serverless pour dev/test)
- [ ] Budget flexible (> 500 €/mois)
- [ ] Équipe avec expertise Azure

## Optimisation des coûts

### Stratégies pour DTU

1. **Commencer petit, scaler ensuite**
   - Démarrer avec S2 ou S3
   - Monitorer les performances
   - Augmenter si nécessaire

2. **Utiliser Elastic Pools pour multi-tenant**
   - Partager des DTU entre plusieurs bases
   - Économies importantes (30-50%)

3. **Différencier prod et non-prod**
   - Production : Standard/Premium
   - Dev/Test : Basic ou Standard bas niveau

### Stratégies pour vCore

1. **Azure Hybrid Benefit (BYOL)**
   - Si vous avez des licences SQL Server avec Software Assurance
   - Économies : 30-55% sur les coûts de compute
   ```
   Sans Azure Hybrid Benefit : 700 €/mois
   Avec Azure Hybrid Benefit  : 315 €/mois (55% d'économie)
   ```

2. **Réservation (Reserved Instances)**
   - Engagement 1 ou 3 ans
   - Économies : jusqu'à 80% par rapport au paiement à l'usage
   ```
   À l'usage (pay-as-you-go) : 700 €/mois
   Réservation 3 ans         : 140 €/mois (80% d'économie)
   ```

3. **Serverless pour non-production**
   - Dev/Test/Staging en Serverless
   - Pause automatique = 0 € de compute
   - Économies : 70-90% sur environnements non-prod

4. **Scaler intelligemment**
   - Nuit/weekend : réduire les vCores
   - Heures de pointe : augmenter
   - Automatisation via Azure Automation

**Exemple de stratégie complète :**
```
Production :
- 4 vCores Business Critical
- Réservation 3 ans
- Azure Hybrid Benefit
- Coût : ~280 €/mois (au lieu de 1600 €)

Dev/Test :
- 2 vCores Serverless
- Pause automatique
- Coût : ~40-80 €/mois (au lieu de 350 €)

Total économisé : ~1600 €/mois (75%)
```

## Recommandations par type de projet

### Applications web / APIs standard

**Recommandation : DTU Standard S2-S4** ou **vCore 2-4 GP**
- Bon équilibre coût/performance
- Suffisant pour la majorité des cas
- Facile à gérer

### Applications critiques / Finance

**Recommandation : vCore Business Critical**
- Latence minimale
- Haute disponibilité
- Réplicas en lecture pour reporting
- Performance prévisible

### Data Warehouse / Analytics

**Recommandation : vCore Hyperscale** ou **Azure Synapse**
- Très grandes quantités de données
- Scaling horizontal
- Performance pour requêtes complexes

### Environnements Dev/Test

**Recommandation : vCore Serverless** ou **DTU Basic/S0**
- Économies maximales
- Pause automatique
- Facturation à l'usage

### Applications SaaS multi-tenant

**Recommandation : DTU avec Elastic Pools** ou **vCore GP avec pools élastiques**
- Partage de ressources
- Isolation par tenant
- Optimisation des coûts

## Migration entre modèles

### Passer de DTU à vCore

**Processus :**
1. Évaluer la charge actuelle (Azure Portal → Metrics)
2. Choisir l'équivalent vCore (voir tableau plus haut)
3. Créer une nouvelle base en vCore
4. Copier les données (Azure Data Migration Service)
5. Basculer l'application

**Temps d'arrêt :** Quelques minutes à quelques heures selon taille

**Alternative sans arrêt :**
- Utiliser la réplication géographique active
- Basculer vers le vCore sans temps d'arrêt

### Passer de vCore à DTU

**Moins courant mais possible si :**
- Vous simplifiez l'architecture
- Base < 1 To
- Pas besoin de fonctionnalités avancées

## Conclusion

### Récapitulatif : DTU vs vCore

**DTU - Pour la simplicité**
- ✅ Simple à comprendre et utiliser
- ✅ Bon pour débuter
- ✅ Prix fixe et prévisible
- ❌ Moins de contrôle
- ❌ Limité à 4 To
- ❌ Pas d'options d'optimisation coûts (BYOL, réservation)

**vCore - Pour la flexibilité et les économies**
- ✅ Contrôle total des ressources
- ✅ Jusqu'à 100 To (Hyperscale)
- ✅ Azure Hybrid Benefit (30-55% économie)
- ✅ Réservations (jusqu'à 80% économie)
- ✅ Serverless (70-90% économie sur non-prod)
- ✅ Réplicas en lecture (Business Critical)
- ❌ Plus complexe
- ❌ Nécessite expertise

### Conseils finaux

1. **Commencez par évaluer vos besoins réels**
   - Taille de la base de données
   - Charge de travail (CPU, I/O, mémoire)
   - Budget disponible
   - Exigences de performance

2. **Commencez petit, ajustez ensuite**
   - Mieux vaut sous-dimensionner légèrement au début
   - Azure permet de scaler rapidement
   - Utilisez les métriques pour décider

3. **Profitez des outils Azure**
   - Azure Pricing Calculator : Estimer les coûts
   - Azure Advisor : Recommandations d'optimisation
   - Query Performance Insight : Identifier les goulots

4. **Optimisez progressivement**
   - Commencer sans optimisation
   - Ajouter BYOL si licences disponibles
   - Considérer réservation après quelques mois
   - Utiliser Serverless pour non-prod

5. **Ne négligez pas le monitoring**
   - Surveillez l'utilisation réelle (CPU, DTU%)
   - Ajustez selon les métriques
   - Évitez de sur-provisionner

**En résumé :**
- **Débutants, PME, petites bases** → DTU
- **Entreprises, grandes bases, optimisation coûts** → vCore
- **En doute** → Commencez par DTU, migrez vers vCore si besoin

Le bon choix dépend de votre contexte spécifique, mais Azure vous permet de changer facilement si vous découvrez que votre choix initial n'était pas optimal.
