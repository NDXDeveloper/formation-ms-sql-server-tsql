# 5.7.2 Triggers DML (AFTER / FOR)

## Introduction aux Triggers DML

Les **triggers DML** (Data Manipulation Language) sont les triggers les plus couramment utilisés. Ils réagissent aux opérations de manipulation de données sur les tables :

- **INSERT** - Insertion de nouvelles lignes
- **UPDATE** - Modification de lignes existantes
- **DELETE** - Suppression de lignes

Le terme **DML** fait référence à ces trois opérations qui modifient le contenu des tables (par opposition à **DDL** qui modifie la structure des objets de la base de données).

## AFTER vs FOR : Quelle différence ?

### La réponse courte : Aucune !

**AFTER** et **FOR** sont des **synonymes parfaits** en T-SQL. Ils font exactement la même chose.

```sql
-- Ces deux syntaxes sont identiques :
CREATE TRIGGER trg_Exemple1
ON MaTable
AFTER INSERT  -- Utilise AFTER
AS
...

CREATE TRIGGER trg_Exemple2
ON MaTable
FOR INSERT    -- Utilise FOR
AS
...
```

### Quelle syntaxe choisir ?

**Recommandation** : Utilisez **AFTER** car c'est plus explicite et plus moderne.

- ✅ **AFTER** dit clairement "ce trigger s'exécute APRÈS l'opération"
- ⚠️ **FOR** peut être ambigu (on pourrait penser "pour" au sens de "pour chaque")

Dans ce cours, nous utiliserons systématiquement **AFTER**.

## Quand le Trigger AFTER s'exécute-t-il ?

### Chronologie d'une opération avec un trigger AFTER

Prenons l'exemple d'un INSERT :

```
1. L'utilisateur exécute : INSERT INTO Clients (...) VALUES (...)
2. SQL Server vérifie les contraintes (PRIMARY KEY, FOREIGN KEY, CHECK, etc.)
3. Si tout est OK, les données sont insérées dans la table
4. 👉 Le trigger AFTER s'exécute maintenant
5. Si le trigger réussit, la transaction est validée
6. L'utilisateur reçoit la confirmation
```

**Point important** : Le trigger AFTER s'exécute **après que les données ont été modifiées**, mais **avant que la transaction ne soit validée** (COMMIT).

### Conséquence importante

Si votre trigger AFTER génère une erreur ou fait un ROLLBACK, **toute l'opération est annulée**, y compris la modification initiale !

```sql
CREATE TRIGGER trg_Validation
ON Commandes
AFTER INSERT
AS
BEGIN
    IF EXISTS (SELECT 1 FROM INSERTED WHERE Montant < 0)
    BEGIN
        RAISERROR('Le montant ne peut pas être négatif', 16, 1);
        ROLLBACK TRANSACTION;  -- Annule tout, y compris l'INSERT initial !
    END
END;
```

## Syntaxe de base d'un Trigger AFTER

### Structure générale

```sql
CREATE TRIGGER nom_du_trigger
ON nom_de_la_table
AFTER {INSERT | UPDATE | DELETE | INSERT, UPDATE | INSERT, DELETE | UPDATE, DELETE | INSERT, UPDATE, DELETE}
AS
BEGIN
    -- Instructions T-SQL
    -- Votre logique ici
END;
```

### Éléments de la syntaxe

1. **CREATE TRIGGER** : Mot-clé pour créer le trigger
2. **nom_du_trigger** : Nom unique pour identifier votre trigger
3. **ON nom_de_la_table** : La table à surveiller
4. **AFTER** suivi de l'événement : Quand déclencher (INSERT, UPDATE, DELETE)
5. **AS BEGIN ... END** : Le code à exécuter

### Convention de nommage recommandée

```sql
-- Format suggéré : trg_NomTable_TypeOperation_Description
CREATE TRIGGER trg_Clients_Insert_Audit
CREATE TRIGGER trg_Employes_Update_Salaire
CREATE TRIGGER trg_Produits_Delete_Prevention
```

## Trigger AFTER INSERT

### Exemple simple : Audit des nouvelles insertions

```sql
CREATE TRIGGER trg_Clients_Audit_Insert
ON Clients
AFTER INSERT
AS
BEGIN
    -- Enregistre chaque nouveau client dans une table d'audit
    INSERT INTO Audit_Clients (ClientID, Action, DateAction, Utilisateur)
    SELECT
        ClientID,
        'INSERT',
        GETDATE(),
        SYSTEM_USER
    FROM INSERTED;  -- INSERTED contient les nouvelles lignes
END;
```

**Ce qui se passe** :
1. Un utilisateur insère un nouveau client
2. Le trigger s'exécute automatiquement
3. Une ligne est ajoutée dans la table Audit_Clients
4. L'utilisateur ne voit pas cette opération d'audit (elle est transparente)

### Exemple avec validation métier

```sql
CREATE TRIGGER trg_Commandes_Validate_Stock
ON Commandes
AFTER INSERT
AS
BEGIN
    -- Vérifie qu'il y a assez de stock pour les produits commandés
    IF EXISTS (
        SELECT 1
        FROM INSERTED i
        INNER JOIN Produits p ON i.ProduitID = p.ProduitID
        WHERE i.Quantite > p.StockDisponible
    )
    BEGIN
        RAISERROR('Stock insuffisant pour cette commande', 16, 1);
        ROLLBACK TRANSACTION;  -- Annule l'insertion
    END
END;
```

## Trigger AFTER UPDATE

### Exemple : Tracer les modifications de salaires

```sql
CREATE TRIGGER trg_Employes_Audit_Salaire
ON Employes
AFTER UPDATE
AS
BEGIN
    -- Enregistre uniquement si le salaire a changé
    IF UPDATE(Salaire)  -- Fonction spéciale qui teste si la colonne a été modifiée
    BEGIN
        INSERT INTO Audit_Salaires (
            EmployeID,
            AncienSalaire,
            NouveauSalaire,
            DateModification,
            Utilisateur
        )
        SELECT
            d.EmployeID,
            d.Salaire,      -- DELETED contient les anciennes valeurs
            i.Salaire,      -- INSERTED contient les nouvelles valeurs
            GETDATE(),
            SYSTEM_USER
        FROM INSERTED i
        INNER JOIN DELETED d ON i.EmployeID = d.EmployeID
        WHERE i.Salaire != d.Salaire;  -- Seulement si le salaire a vraiment changé
    END
END;
```

**Détails importants** :
- `UPDATE(Salaire)` : Vérifie si la colonne Salaire a été mentionnée dans l'UPDATE (même si la valeur n'a pas changé)
- `DELETED` : Contient les valeurs **avant** la modification
- `INSERTED` : Contient les valeurs **après** la modification

### Exemple : Empêcher certaines modifications

```sql
CREATE TRIGGER trg_Employes_Prevent_Salary_Decrease
ON Employes
AFTER UPDATE
AS
BEGIN
    -- Empêche de réduire un salaire
    IF EXISTS (
        SELECT 1
        FROM INSERTED i
        INNER JOIN DELETED d ON i.EmployeID = d.EmployeID
        WHERE i.Salaire < d.Salaire
    )
    BEGIN
        RAISERROR('Impossible de réduire le salaire d''un employé', 16, 1);
        ROLLBACK TRANSACTION;
    END
END;
```

## Trigger AFTER DELETE

### Exemple : Empêcher la suppression de données importantes

```sql
CREATE TRIGGER trg_Clients_Prevent_Delete
ON Clients
AFTER DELETE
AS
BEGIN
    -- Empêche la suppression de clients qui ont des commandes
    IF EXISTS (
        SELECT 1
        FROM DELETED d
        INNER JOIN Commandes c ON d.ClientID = c.ClientID
    )
    BEGIN
        RAISERROR('Impossible de supprimer un client avec des commandes existantes', 16, 1);
        ROLLBACK TRANSACTION;
    END
END;
```

### Exemple : Archivage automatique

```sql
CREATE TRIGGER trg_Employes_Archive_On_Delete
ON Employes
AFTER DELETE
AS
BEGIN
    -- Déplace les employés supprimés vers une table d'archive
    INSERT INTO Employes_Archives (
        EmployeID,
        Nom,
        Prenom,
        DateSuppression
    )
    SELECT
        EmployeID,
        Nom,
        Prenom,
        GETDATE()
    FROM DELETED;
END;
```

**Note** : Avec ce trigger, quand vous "supprimez" un employé, il est en fait déplacé vers une table d'archive. C'est une forme de "suppression logique".

## Trigger pour plusieurs opérations

Vous pouvez créer un trigger qui réagit à plusieurs types d'opérations :

### Exemple : Audit complet (INSERT, UPDATE, DELETE)

```sql
CREATE TRIGGER trg_Produits_Audit_All
ON Produits
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    DECLARE @Action VARCHAR(10);

    -- Détermine quel type d'opération a eu lieu
    IF EXISTS (SELECT 1 FROM INSERTED) AND EXISTS (SELECT 1 FROM DELETED)
        SET @Action = 'UPDATE';
    ELSE IF EXISTS (SELECT 1 FROM INSERTED)
        SET @Action = 'INSERT';
    ELSE IF EXISTS (SELECT 1 FROM DELETED)
        SET @Action = 'DELETE';

    -- Enregistre l'action
    INSERT INTO Audit_Produits (ProduitID, Action, DateAction)
    SELECT
        COALESCE(i.ProduitID, d.ProduitID),  -- Prend l'ID de INSERTED ou DELETED
        @Action,
        GETDATE()
    FROM INSERTED i
    FULL OUTER JOIN DELETED d ON i.ProduitID = d.ProduitID;
END;
```

**Logique de détection** :
- Si INSERTED et DELETED existent tous les deux → **UPDATE**
- Si seulement INSERTED existe → **INSERT**
- Si seulement DELETED existe → **DELETE**

## Gestion des opérations en masse (Bulk Operations)

### Point crucial : Un trigger s'exécute UNE FOIS par instruction

Même si vous insérez 1000 lignes en une seule instruction INSERT, le trigger ne s'exécute qu'**une seule fois** et doit traiter toutes les lignes.

```sql
-- Cette instruction insère 3 lignes
INSERT INTO Clients (Nom, Prenom)
VALUES
    ('Dupont', 'Jean'),
    ('Martin', 'Marie'),
    ('Durand', 'Pierre');

-- Le trigger s'exécute UNE FOIS
-- La table INSERTED contient les 3 lignes
```

### Erreur fréquente des débutants

```sql
-- ❌ MAUVAISE PRATIQUE - Ne fonctionne QUE si une seule ligne est insérée !
CREATE TRIGGER trg_Exemple_Mauvais
ON Commandes
AFTER INSERT
AS
BEGIN
    DECLARE @CommandeID INT;
    DECLARE @Montant DECIMAL(10,2);

    -- Ceci ne récupère qu'UNE ligne de INSERTED, même s'il y en a plusieurs !
    SELECT @CommandeID = CommandeID, @Montant = Montant FROM INSERTED;

    -- Traitement...
END;
```

### Bonne pratique : Traiter toutes les lignes

```sql
-- ✅ BONNE PRATIQUE - Traite toutes les lignes insérées
CREATE TRIGGER trg_Exemple_Bon
ON Commandes
AFTER INSERT
AS
BEGIN
    -- Utilise un INSERT ... SELECT ou UPDATE ... FROM
    -- pour traiter TOUTES les lignes d'INSERTED en une seule fois

    INSERT INTO Audit_Commandes (CommandeID, Montant, DateCreation)
    SELECT
        CommandeID,
        Montant,
        GETDATE()
    FROM INSERTED;  -- Toutes les lignes sont traitées
END;
```

### Si vous devez absolument traiter ligne par ligne

Utilisez un curseur (mais évitez si possible, c'est lent) :

```sql
CREATE TRIGGER trg_Exemple_Curseur
ON Commandes
AFTER INSERT
AS
BEGIN
    DECLARE @CommandeID INT;
    DECLARE @Montant DECIMAL(10,2);

    DECLARE curseur CURSOR FOR
        SELECT CommandeID, Montant FROM INSERTED;

    OPEN curseur;
    FETCH NEXT FROM curseur INTO @CommandeID, @Montant;

    WHILE @@FETCH_STATUS = 0
    BEGIN
        -- Traitement ligne par ligne

        FETCH NEXT FROM curseur INTO @CommandeID, @Montant;
    END;

    CLOSE curseur;
    DEALLOCATE curseur;
END;
```

## Bonnes pratiques pour les Triggers AFTER

### 1. Gardez vos triggers courts et rapides

```sql
-- ✅ BON : Simple et rapide
CREATE TRIGGER trg_Simple
ON Clients
AFTER INSERT
AS
BEGIN
    INSERT INTO Audit SELECT * FROM INSERTED;
END;

-- ❌ MAUVAIS : Complexe et lent
CREATE TRIGGER trg_Complexe
ON Clients
AFTER INSERT
AS
BEGIN
    -- 50 lignes de code complexe
    -- Plusieurs jointures
    -- Des calculs lourds
    -- Des appels à des fonctions externes
    -- ⚠️ Chaque INSERT sur Clients sera lent !
END;
```

### 2. Utilisez SET NOCOUNT ON

```sql
CREATE TRIGGER trg_Exemple
ON MaTable
AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;  -- ✅ Recommandé : Empêche les messages "X lignes affectées"

    -- Votre code ici
END;
```

**Pourquoi** : Sans `SET NOCOUNT ON`, SQL Server envoie des messages "X lignes affectées" pour chaque instruction dans le trigger, ce qui peut confondre les applications clientes.

### 3. Gérez les erreurs proprement

```sql
CREATE TRIGGER trg_Avec_Gestion_Erreur
ON Commandes
AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRY
        -- Votre logique ici
        IF EXISTS (SELECT 1 FROM INSERTED WHERE Montant < 0)
        BEGIN
            THROW 50001, 'Le montant ne peut pas être négatif', 1;
        END

        -- Autres traitements...

    END TRY
    BEGIN CATCH
        -- En cas d'erreur, on rollback tout
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;

        -- On relance l'erreur pour que l'appelant soit informé
        THROW;
    END CATCH
END;
```

### 4. Attention aux triggers récursifs

Par défaut, SQL Server empêche qu'un trigger se déclenche lui-même (récursion). Mais il faut faire attention aux récursions indirectes :

```sql
-- Trigger sur TableA modifie TableB
CREATE TRIGGER trg_A ON TableA AFTER INSERT
AS BEGIN
    UPDATE TableB SET ...  -- ⚠️ Va déclencher trg_B
END;

-- Trigger sur TableB modifie TableA
CREATE TRIGGER trg_B ON TableB AFTER UPDATE
AS BEGIN
    UPDATE TableA SET ...  -- ⚠️ Va déclencher trg_A
END;

-- 💥 Boucle infinie (jusqu'à ce que SQL Server l'arrête après 32 itérations)
```

### 5. Documentez vos triggers

```sql
/*
================================================================
TRIGGER: trg_Clients_Audit_Insert
AUTEUR: Jean Dupont
DATE CRÉATION: 2024-01-15
OBJECTIF: Enregistre tous les nouveaux clients dans la table d'audit
DÉCLENCHÉ PAR: INSERT sur la table Clients
TABLES UTILISÉES:
    - INSERTED (table virtuelle)
    - Audit_Clients (enregistrement)
NOTES:
    - Ce trigger est requis pour la conformité RGPD
    - Il s'exécute pour chaque lot d'insertions
DÉPENDANCES: Nécessite que la table Audit_Clients existe
================================================================
*/
CREATE TRIGGER trg_Clients_Audit_Insert
ON Clients
AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO Audit_Clients (ClientID, Action, DateAction)
    SELECT ClientID, 'INSERT', GETDATE()
    FROM INSERTED;
END;
```

## Gestion et Administration des Triggers

### Voir tous les triggers d'une table

```sql
-- Voir tous les triggers sur une table spécifique
SELECT
    name AS NomTrigger,
    is_disabled AS EstDesactive,
    create_date AS DateCreation
FROM sys.triggers
WHERE parent_id = OBJECT_ID('Clients');
```

### Désactiver temporairement un trigger

```sql
-- Désactiver
DISABLE TRIGGER trg_Clients_Audit_Insert ON Clients;

-- Réactiver
ENABLE TRIGGER trg_Clients_Audit_Insert ON Clients;

-- Désactiver TOUS les triggers d'une table
DISABLE TRIGGER ALL ON Clients;
```

**Usage** : Utile lors d'imports en masse pour améliorer les performances.

### Supprimer un trigger

```sql
DROP TRIGGER trg_Clients_Audit_Insert;
```

### Modifier un trigger

```sql
-- Utiliser ALTER au lieu de CREATE
ALTER TRIGGER trg_Clients_Audit_Insert
ON Clients
AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;
    -- Nouveau code ici
END;
```

## Pièges courants à éviter

### Piège 1 : Oublier que INSERTED/DELETED peuvent contenir plusieurs lignes

```sql
-- ❌ ERREUR : Suppose qu'il n'y a qu'une seule ligne
DECLARE @ID INT = (SELECT ClientID FROM INSERTED);  -- Et s'il y en a plusieurs ?

-- ✅ CORRECT : Traite toutes les lignes
INSERT INTO Audit SELECT * FROM INSERTED;
```

### Piège 2 : Modifier la même table dans le trigger

```sql
-- ❌ PROBLÉMATIQUE : Risque de récursion
CREATE TRIGGER trg_Auto_Update
ON Clients
AFTER UPDATE
AS
BEGIN
    UPDATE Clients
    SET DerniereModif = GETDATE()
    WHERE ClientID IN (SELECT ClientID FROM INSERTED);
    -- Ce trigger va se redéclencher lui-même !
END;
```

**Solution** : Utiliser une colonne calculée ou un trigger INSTEAD OF (voir section suivante).

### Piège 3 : Utiliser des SELECT sans but

```sql
-- ❌ INUTILE : N'a aucun effet
CREATE TRIGGER trg_Inutile
ON Clients
AFTER INSERT
AS
BEGIN
    SELECT * FROM INSERTED;  -- Ceci ne fait rien d'utile !
END;
```

### Piège 4 : Faire confiance à @@ROWCOUNT dans un trigger

```sql
-- ⚠️ ATTENTION : @@ROWCOUNT peut ne pas être ce que vous pensez
CREATE TRIGGER trg_Confus
ON Clients
AFTER INSERT
AS
BEGIN
    INSERT INTO Audit SELECT * FROM INSERTED;

    -- @@ROWCOUNT contient maintenant le nombre de lignes dans Audit,
    -- PAS le nombre de lignes insérées dans Clients !
    IF @@ROWCOUNT > 0  -- Ceci teste la mauvaise chose
        ...
END;
```

## Résumé

### Points clés à retenir

1. **AFTER = FOR** : Deux mots-clés identiques, préférez AFTER
2. **Exécution après modification** : Le trigger s'exécute après l'opération, mais avant le COMMIT
3. **Une exécution par instruction** : Même pour 1000 lignes insérées en une fois
4. **INSERTED et DELETED** : Tables virtuelles contenant les données affectées
5. **Peut annuler l'opération** : Avec ROLLBACK TRANSACTION
6. **Gardez-les simples** : Plus c'est simple, plus c'est maintenable

### Quand utiliser un trigger AFTER

✅ **Utilisez pour** :
- Audit automatique
- Validation métier complexe
- Maintien de données dénormalisées
- Actions systématiques qui doivent TOUJOURS se produire

❌ **N'utilisez PAS pour** :
- Logique métier complexe (mettez-la dans l'application)
- Opérations longues ou externes
- Calculs qui pourraient être des colonnes calculées
- Compenser une mauvaise conception de base de données
