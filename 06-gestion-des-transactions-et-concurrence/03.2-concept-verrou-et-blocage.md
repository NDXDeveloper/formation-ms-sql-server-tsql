# 6.3.2 Le concept de verrou (Locks) et de blocage (Blocking)

## Introduction

Nous avons vu dans la section précédente les problématiques de concurrence qui peuvent survenir lorsque plusieurs transactions accèdent simultanément aux mêmes données. Mais comment SQL Server empêche-t-il ces anomalies ? La réponse : **les verrous (locks)**.

Dans cette section, nous allons comprendre :
- Ce qu'est un verrou et pourquoi il est nécessaire
- Les différents types de verrous
- Le concept de blocage (blocking)
- L'impact sur les performances

---

## Qu'est-ce qu'un verrou (Lock) ?

### Définition simple

Un **verrou** est un mécanisme que SQL Server utilise pour contrôler l'accès concurrent aux données. C'est comme un système de réservation qui garantit qu'une ressource (table, ligne, page) ne peut pas être modifiée de manière incohérente par plusieurs transactions simultanées.

### Analogie : La bibliothèque

Imaginez une bibliothèque où plusieurs personnes veulent consulter ou emprunter le même livre :

- **Lecture** : Plusieurs personnes peuvent lire le même livre en même temps (dans la salle de lecture)
- **Emprunt** : Si quelqu'un emprunte le livre pour le modifier (annoter), personne d'autre ne peut l'emprunter en même temps
- **Modification exclusive** : Si le bibliothécaire doit réparer le livre, personne ne peut le consulter pendant ce temps

Les verrous SQL Server fonctionnent selon le même principe : ils régulent qui peut lire ou modifier les données, et quand.

---

## Pourquoi avons-nous besoin de verrous ?

Les verrous sont essentiels pour :

1. **Garantir l'intégrité des données** : Éviter que deux transactions modifient la même donnée simultanément
2. **Prévenir les anomalies de concurrence** : Empêcher les Dirty Reads, Non-Repeatable Reads, et Phantom Reads
3. **Assurer la cohérence** : S'assurer qu'une transaction voit un état cohérent de la base de données
4. **Respecter les propriétés ACID** : En particulier l'Isolation

### Sans verrous : Le chaos

Imaginez deux guichets automatiques qui permettent de retirer de l'argent du même compte en même temps, sans coordination :

```
Solde initial : 1000€

Guichet A lit le solde : 1000€
Guichet B lit le solde : 1000€
Guichet A retire 600€ → nouveau solde = 400€
Guichet B retire 500€ → nouveau solde = 500€

Résultat : Le compte affiche 500€ au lieu de -100€ (ou la transaction B aurait dû être refusée)
```

Les verrous empêchent ce genre de situation.

---

## Les différents types de verrous

SQL Server utilise plusieurs types de verrous en fonction de l'opération effectuée. Voici les principaux :

### 1. Verrou Partagé (Shared Lock - S)

**Utilisé pour :** Les opérations de **lecture** (SELECT)

**Principe :**
- Plusieurs transactions peuvent obtenir un verrou partagé sur la même ressource simultanément
- Tant qu'un verrou partagé existe, aucune transaction ne peut obtenir un verrou exclusif (donc aucune modification)

**Analogie :** Plusieurs personnes peuvent regarder la même vitrine d'un magasin en même temps, mais personne ne peut modifier la vitrine pendant qu'on la regarde.

```sql
-- Transaction A lit des données
BEGIN TRANSACTION;
SELECT * FROM Employes WHERE EmployeID = 1;
-- Un verrou partagé est placé sur la ligne

-- Transaction B peut aussi lire
SELECT * FROM Employes WHERE EmployeID = 1;
-- Pas de problème : plusieurs verrous partagés sont possibles
```

### 2. Verrou Exclusif (Exclusive Lock - X)

**Utilisé pour :** Les opérations de **modification** (INSERT, UPDATE, DELETE)

**Principe :**
- Une seule transaction peut obtenir un verrou exclusif sur une ressource
- Aucune autre transaction ne peut obtenir de verrou (ni partagé, ni exclusif) tant que le verrou exclusif existe

**Analogie :** Si quelqu'un entre dans les toilettes et verrouille la porte, personne d'autre ne peut entrer (ni pour utiliser, ni même pour regarder).

```sql
-- Transaction A modifie des données
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
-- Un verrou exclusif est placé sur la ligne

-- Transaction B tente de lire
SELECT * FROM Employes WHERE EmployeID = 1;
-- Transaction B est BLOQUÉE et doit attendre la fin de Transaction A
```

### 3. Verrou de Mise à Jour (Update Lock - U)

**Utilisé pour :** Anticiper une modification (pendant la lecture qui précède un UPDATE)

**Principe :**
- C'est un verrou intermédiaire entre le verrou partagé et le verrou exclusif
- Il permet d'éviter les deadlocks (interblocages) dans certaines situations
- Il peut coexister avec des verrous partagés (lecture), mais pas avec un autre verrou de mise à jour ou exclusif

**Analogie :** Vous dites "je vais bientôt avoir besoin de modifier ce document, mais pour l'instant je ne fais que le lire". D'autres peuvent encore le lire, mais personne d'autre ne peut réserver le droit de le modifier.

### 4. Verrou d'Intention (Intent Locks - IS, IX, SIX)

**Utilisé pour :** Indiquer qu'un verrou existe à un niveau inférieur de la hiérarchie

**Principe :**
- SQL Server utilise une hiérarchie : Base de données → Table → Page → Ligne
- Les verrous d'intention indiquent qu'un verrou existe à un niveau inférieur sans avoir à vérifier toutes les lignes

**Types :**
- **IS** (Intent Shared) : Intention de placer un verrou partagé
- **IX** (Intent Exclusive) : Intention de placer un verrou exclusif
- **SIX** (Shared with Intent Exclusive) : Combinaison des deux

**Analogie :** C'est comme une pancarte "Travaux en cours dans une chambre" placée sur la porte d'un hôtel. Pas besoin de vérifier chaque chambre : la pancarte à l'entrée indique qu'il y a des travaux quelque part à l'intérieur.

---

## Granularité des verrous

Les verrous peuvent être placés à différents niveaux :

| Niveau | Description | Exemple |
|--------|-------------|---------|
| **Ligne (Row)** | Verrou sur une seule ligne | Modification d'un employé spécifique |
| **Page** | Verrou sur une page (environ 8 Ko de données) | Modification de plusieurs lignes adjacentes |
| **Table** | Verrou sur la table entière | TRUNCATE TABLE ou modification massive |
| **Base de données** | Verrou sur toute la base | Opérations de maintenance |

**Principe général :** SQL Server commence généralement par des verrous au niveau des lignes (plus de concurrence possible) et peut escalader vers des niveaux supérieurs si trop de verrous sont nécessaires (optimisation des ressources).

---

## Le concept de blocage (Blocking)

### Qu'est-ce que le Blocking ?

Le **blocage** se produit lorsqu'une transaction doit attendre qu'une autre transaction libère un verrou sur une ressource dont elle a besoin.

**Important :** Le blocking est un comportement **normal** et **nécessaire** dans SQL Server. Il garantit l'intégrité des données.

### Analogie : La file d'attente

Imaginez un guichet de banque avec un seul employé :
- Client A est en train d'effectuer une opération
- Client B arrive et doit **attendre** (il est bloqué)
- Quand Client A termine, Client B peut être servi

C'est exactement ce qui se passe avec les verrous : une transaction attend qu'une autre libère la ressource.

### Exemple de Blocking

```sql
-- Transaction A (commence à 10:00:00)
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
-- Verrou exclusif placé, transaction non terminée
-- L'utilisateur prend un café et ne fait pas COMMIT...

-- Transaction B (commence à 10:00:05)
BEGIN TRANSACTION;
SELECT * FROM Produits WHERE ProduitID = 1;
-- Transaction B est BLOQUÉE : elle attend que Transaction A libère le verrou
-- L'utilisateur de Transaction B voit son application "geler"

-- À 10:05:00, Transaction A revient
COMMIT;
-- Le verrou est libéré

-- Transaction B peut enfin continuer
-- Elle récupère les données mises à jour
```

### Visualiser le Blocking

Dans cet exemple :
- **Transaction A** est appelée la **transaction bloquante** (blocker)
- **Transaction B** est appelée la **transaction bloquée** (victim)

---

## Différence entre Lock et Blocking

Il est important de bien distinguer ces deux concepts :

| Concept | Définition | Nature |
|---------|------------|--------|
| **Lock (Verrou)** | Mécanisme de contrôle d'accès | Outil technique |
| **Blocking (Blocage)** | État d'attente d'une transaction | Conséquence |

**Analogie :**
- Le **verrou** est la serrure sur la porte
- Le **blocage** est le fait d'attendre que quelqu'un ouvre la porte

---

## Durée des verrous

La durée pendant laquelle un verrou est maintenu dépend du type de verrou et du niveau d'isolation :

### Verrous Partagés (Shared Locks)

**Comportement par défaut (READ COMMITTED) :**
- Les verrous partagés sont **libérés dès que la lecture est terminée**
- Ils ne sont pas maintenus jusqu'à la fin de la transaction

```sql
BEGIN TRANSACTION;
SELECT * FROM Employes WHERE EmployeID = 1;
-- Verrou partagé placé, puis immédiatement libéré après la lecture

-- Même si la transaction continue, le verrou n'existe plus
UPDATE AutreTable SET ...;
COMMIT;
```

### Verrous Exclusifs (Exclusive Locks)

**Comportement :**
- Les verrous exclusifs sont **maintenus jusqu'à la fin de la transaction** (COMMIT ou ROLLBACK)
- Cela garantit que personne ne peut voir les données modifiées avant leur validation

```sql
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
-- Verrou exclusif placé

-- Même si le UPDATE est terminé, le verrou reste actif
-- D'autres opérations...
-- Le verrou n'est libéré qu'au COMMIT
COMMIT;
```

## Impact sur les performances

### Le compromis Cohérence vs Performance

Les verrous créent un compromis :

**Avantages :**
- ✅ Garantissent l'intégrité des données
- ✅ Préviennent les anomalies de concurrence
- ✅ Assurent la cohérence

**Inconvénients :**
- ❌ Réduisent la concurrence (moins de transactions simultanées)
- ❌ Peuvent créer des files d'attente (blocking)
- ❌ Peuvent ralentir les applications

### Facteurs aggravants

Certaines situations augmentent le risque de blocking excessif :

1. **Transactions longues** : Plus une transaction dure, plus elle garde des verrous longtemps
2. **Transactions non terminées** : Oublier de faire COMMIT ou ROLLBACK
3. **Gros volumes de données** : Modifier des milliers de lignes en une seule transaction
4. **Mauvaise conception** : Effectuer des opérations lentes (calculs, appels externes) à l'intérieur d'une transaction

### Exemple problématique

```sql
-- ❌ MAUVAISE PRATIQUE
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = Salaire * 1.1;  -- Modifie 10 000 employés

-- L'utilisateur reçoit un email et prend 5 minutes pour le lire...
-- Pendant ce temps, tous les autres utilisateurs sont bloqués !

COMMIT;
```

---

## Bonnes pratiques pour minimiser le Blocking

### 1. Garder les transactions courtes

```sql
-- ✅ BONNE PRATIQUE
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
COMMIT;
-- Transaction rapide, verrous libérés rapidement
```

### 2. Effectuer les calculs AVANT la transaction

```sql
-- ❌ MAUVAIS
BEGIN TRANSACTION;
DECLARE @NouveauPrix DECIMAL(10,2);
SET @NouveauPrix = (SELECT Prix FROM Produits WHERE ProduitID = 1) * 1.2;
UPDATE Produits SET Prix = @NouveauPrix WHERE ProduitID = 1;
COMMIT;

-- ✅ BON
DECLARE @NouveauPrix DECIMAL(10,2);
SET @NouveauPrix = (SELECT Prix FROM Produits WHERE ProduitID = 1) * 1.2;
BEGIN TRANSACTION;
UPDATE Produits SET Prix = @NouveauPrix WHERE ProduitID = 1;
COMMIT;
```

### 3. Traiter les données par lots (batches)

Au lieu de modifier 100 000 lignes en une seule transaction, les traiter par groupes de 1000.

### 4. Optimiser les requêtes

Des requêtes lentes = des verrous maintenus plus longtemps = plus de blocking.

### 5. Utiliser le bon niveau d'isolation

Choisir le niveau d'isolation approprié pour équilibrer cohérence et performance (voir sections 6.4.1 à 6.4.6).

## Outils de diagnostic du Blocking

SQL Server propose plusieurs outils pour identifier les situations de blocking :

### 1. La vue système `sys.dm_exec_requests`

Cette vue montre les requêtes en cours d'exécution et celles qui sont bloquées.

```sql
SELECT
    session_id,
    blocking_session_id,
    wait_type,
    wait_time,
    status
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;
```

**Interprétation :**
- `session_id` : Identifiant de la session bloquée
- `blocking_session_id` : Identifiant de la session qui bloque
- `wait_time` : Temps d'attente en millisecondes

### 2. L'Activity Monitor dans SSMS

SQL Server Management Studio (SSMS) propose un moniteur d'activité graphique qui affiche :
- Les processus actifs
- Les situations de blocking
- Les requêtes en attente

**Accès :** Clic droit sur le serveur → Activity Monitor

### 3. La procédure stockée `sp_who2`

Une commande rapide pour voir qui bloque qui :

```sql
EXEC sp_who2;
```

Cette procédure affiche une liste des sessions actives avec les informations de blocking.

## Résumé

### Les verrous (Locks)

- **Définition** : Mécanisme de contrôle d'accès aux données
- **Types principaux** : Partagé (lecture), Exclusif (modification), Mise à jour, Intention
- **Granularité** : Ligne, Page, Table, Base de données
- **Objectif** : Garantir l'intégrité et la cohérence des données

### Le blocage (Blocking)

- **Définition** : État d'attente lorsqu'une transaction ne peut pas obtenir un verrou
- **Nature** : Comportement normal et nécessaire
- **Problème** : Peut impacter les performances si excessif
- **Solutions** : Transactions courtes, optimisation des requêtes, bon niveau d'isolation

### Points clés à retenir

1. Les verrous sont **essentiels** pour maintenir l'intégrité des données
2. Le blocking est **normal**, mais doit être **minimisé**
3. Les transactions **doivent être courtes** et **toujours terminées** (COMMIT/ROLLBACK)
4. SQL Server fournit des **outils** pour diagnostiquer le blocking
5. Le choix du **niveau d'isolation** influence le comportement des verrous
