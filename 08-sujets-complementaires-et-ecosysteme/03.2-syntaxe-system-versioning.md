# 8.3.2 Syntaxe SYSTEM_VERSIONING

## Introduction

Maintenant que vous comprenez le **concept** d'historisation automatique (section 8.3.1), passons à la **pratique** ! Dans cette section, nous allons voir comment créer concrètement des tables temporelles avec la syntaxe `SYSTEM_VERSIONING`.

Pas d'inquiétude si la syntaxe semble complexe au premier abord : nous allons décomposer chaque élément étape par étape avec des exemples commentés.

## Les composants essentiels d'une table temporelle

Pour créer une table temporelle, vous avez besoin de **4 éléments obligatoires** :

1. ✅ **Deux colonnes de type DATETIME2** pour suivre les périodes de validité
2. ✅ **Une contrainte PERIOD** qui lie ces deux colonnes
3. ✅ **La clause SYSTEM_VERSIONING = ON** pour activer l'historisation
4. ✅ **Une clé primaire** (obligatoire pour les tables temporelles)

## Syntaxe 1 : Créer une nouvelle table temporelle

### Exemple de base complet

Créons une table `Produits` avec historisation automatique :

```sql
-- Création d'une table temporelle pour gérer les produits
CREATE TABLE Produits
(
    -- Colonnes métier classiques
    ProduitID INT PRIMARY KEY,
    Nom NVARCHAR(100) NOT NULL,
    Prix DECIMAL(10, 2) NOT NULL,
    CategorieID INT NOT NULL,

    -- Colonnes temporelles obligatoires (ajoutées à la fin par convention)
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL,

    -- Définition de la période temporelle
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH
(
    -- Activation de l'historisation automatique
    SYSTEM_VERSIONING = ON
    (
        HISTORY_TABLE = dbo.Produits_History  -- Nom de la table d'historique
    )
);
```

### Décortiquons cette syntaxe

#### 1. Les colonnes métier (partie classique)

```sql
ProduitID INT PRIMARY KEY,
Nom NVARCHAR(100) NOT NULL,
Prix DECIMAL(10, 2) NOT NULL,
CategorieID INT NOT NULL,
```

Cette partie est identique à une table normale. Vous définissez vos colonnes comme vous le faites habituellement.

⚠️ **Important** : Une **clé primaire est obligatoire** pour les tables temporelles.

#### 2. Les colonnes temporelles

```sql
ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL,
ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL,
```

Analysons chaque mot-clé :

| Élément | Signification |
|---------|---------------|
| `DATETIME2` | Type de données pour stocker date et heure avec haute précision |
| `GENERATED ALWAYS` | SQL Server gère automatiquement ces colonnes (vous ne pouvez pas les modifier) |
| `AS ROW START` | Indique que c'est la colonne de début de validité |
| `AS ROW END` | Indique que c'est la colonne de fin de validité |
| `HIDDEN` | Les colonnes ne sont pas retournées dans un `SELECT *` (optionnel mais recommandé) |
| `NOT NULL` | Obligatoire pour les colonnes temporelles |

💡 **Le mot-clé HIDDEN** : Très pratique ! Vos requêtes `SELECT * FROM Produits` ne retourneront pas ces colonnes techniques, ce qui simplifie l'affichage. Si vous voulez les voir, vous devez les demander explicitement : `SELECT *, ValidFrom, ValidTo FROM Produits`.

#### 3. La contrainte PERIOD

```sql
PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
```

Cette ligne crée une **contrainte spéciale** qui dit à SQL Server :
- "Ces deux colonnes forment une période de temps"
- "ValidFrom doit toujours être inférieur à ValidTo"
- "Utilise-les pour gérer l'historisation"

⚠️ Les noms `ValidFrom` et `ValidTo` sont des conventions, vous pouvez utiliser d'autres noms (comme `DateDebut`, `DateFin`), mais ces noms doivent correspondre à ceux déclarés dans vos colonnes.

#### 4. La clause SYSTEM_VERSIONING

```sql
WITH
(
    SYSTEM_VERSIONING = ON
    (
        HISTORY_TABLE = dbo.Produits_History
    )
)
```

Cette clause active l'historisation et indique :
- `SYSTEM_VERSIONING = ON` : Active la fonctionnalité
- `HISTORY_TABLE = dbo.Produits_History` : Spécifie le nom de la table d'historique (format : `schéma.nom_table`)

💡 **Bon à savoir** : Si vous omettez le nom de la table d'historique, SQL Server en créera une automatiquement avec un nom généré (ex: `MSSQL_TemporalHistoryFor_123456789`).

## Syntaxe 2 : Créer la table d'historique manuellement (optionnel)

Vous pouvez créer la table d'historique **avant** la table principale si vous voulez plus de contrôle :

```sql
-- Étape 1 : Créer d'abord la table d'historique
CREATE TABLE Produits_History
(
    ProduitID INT NOT NULL,
    Nom NVARCHAR(100) NOT NULL,
    Prix DECIMAL(10, 2) NOT NULL,
    CategorieID INT NOT NULL,
    ValidFrom DATETIME2 NOT NULL,
    ValidTo DATETIME2 NOT NULL
);

-- Étape 2 : Créer un index sur la table d'historique (recommandé pour les performances)
CREATE CLUSTERED INDEX IX_Produits_History
ON Produits_History (ValidTo, ValidFrom);

-- Étape 3 : Créer la table principale et la lier à l'historique existant
CREATE TABLE Produits
(
    ProduitID INT PRIMARY KEY,
    Nom NVARCHAR(100) NOT NULL,
    Prix DECIMAL(10, 2) NOT NULL,
    CategorieID INT NOT NULL,
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL,
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH
(
    SYSTEM_VERSIONING = ON
    (
        HISTORY_TABLE = dbo.Produits_History
    )
);
```

### Pourquoi créer manuellement la table d'historique ?

- ✅ **Contrôle de l'indexation** : Vous pouvez optimiser les index pour vos requêtes d'historique
- ✅ **Partitionnement** : Pour les très grandes tables, vous pouvez partitionner la table d'historique
- ✅ **Compression** : Vous pouvez activer la compression sur la table d'historique pour économiser de l'espace

## Syntaxe 3 : Ajouter l'historisation à une table existante

Vous avez déjà une table `Clients` sans historisation ? Vous pouvez l'ajouter après coup !

### Étape par étape

```sql
-- Table existante (sans historisation)
-- Supposons que vous ayez déjà cette table :
CREATE TABLE Clients
(
    ClientID INT PRIMARY KEY,
    Nom NVARCHAR(100) NOT NULL,
    Email NVARCHAR(255) NOT NULL,
    Telephone NVARCHAR(20)
);

-- Étape 1 : Ajouter les colonnes temporelles
ALTER TABLE Clients
ADD
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL
        CONSTRAINT DF_Clients_ValidFrom DEFAULT SYSUTCDATETIME(),
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL
        CONSTRAINT DF_Clients_ValidTo DEFAULT CONVERT(DATETIME2, '9999-12-31 23:59:59.9999999'),
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo);

-- Étape 2 : Activer l'historisation
ALTER TABLE Clients
SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.Clients_History));
```

### Explications des valeurs par défaut

```sql
DEFAULT SYSUTCDATETIME()  -- Remplit ValidFrom avec la date/heure actuelle en UTC
DEFAULT CONVERT(DATETIME2, '9999-12-31 23:59:59.9999999')  -- Remplit ValidTo avec la date maximale
```

Ces valeurs par défaut permettent d'initialiser correctement les colonnes temporelles pour les lignes existantes dans la table.

💡 **SYSUTCDATETIME()** : Fonction SQL Server qui retourne la date et l'heure actuelles en **UTC (temps universel coordonné)**. C'est préférable à `GETDATE()` car UTC est indépendant du fuseau horaire du serveur.

## Syntaxe 4 : Désactiver temporairement l'historisation

Il peut être nécessaire de désactiver temporairement l'historisation, par exemple pour :
- Effectuer des suppressions définitives (RGPD)
- Effectuer des modifications massives sur la structure
- Nettoyer l'historique

### Désactiver l'historisation

```sql
-- Désactive l'historisation mais conserve les deux tables
ALTER TABLE Produits
SET (SYSTEM_VERSIONING = OFF);
```

⚠️ **Attention** : Une fois désactivée :
- La table d'historique n'est plus alimentée automatiquement
- Les colonnes temporelles restent dans la table, mais ne sont plus mises à jour automatiquement
- Vous pouvez maintenant modifier ou supprimer des données dans la table d'historique

### Réactiver l'historisation

```sql
-- Réactive l'historisation en utilisant la même table d'historique
ALTER TABLE Produits
SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.Produits_History));
```

### Supprimer complètement l'historisation

Si vous voulez enlever complètement la fonctionnalité :

```sql
-- Étape 1 : Désactiver l'historisation
ALTER TABLE Produits
SET (SYSTEM_VERSIONING = OFF);

-- Étape 2 : Supprimer la contrainte PERIOD
ALTER TABLE Produits
DROP PERIOD FOR SYSTEM_TIME;

-- Étape 3 : Supprimer les colonnes temporelles
ALTER TABLE Produits
DROP COLUMN ValidFrom, ValidTo;

-- Étape 4 : Supprimer la table d'historique (si vous n'en avez plus besoin)
DROP TABLE Produits_History;
```

## Options avancées de SYSTEM_VERSIONING

### Contrôler la rétention de l'historique

SQL Server permet de définir une **politique de rétention** pour supprimer automatiquement l'historique ancien :

```sql
CREATE TABLE Produits
(
    ProduitID INT PRIMARY KEY,
    Nom NVARCHAR(100) NOT NULL,
    Prix DECIMAL(10, 2) NOT NULL,
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL,
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH
(
    SYSTEM_VERSIONING = ON
    (
        HISTORY_TABLE = dbo.Produits_History,
        HISTORY_RETENTION_PERIOD = 6 MONTHS  -- Conserve 6 mois d'historique
    )
);
```

**Options de rétention disponibles** :
- `DAYS` : Jours (ex: `90 DAYS`)
- `WEEKS` : Semaines (ex: `12 WEEKS`)
- `MONTHS` : Mois (ex: `6 MONTHS`)
- `YEARS` : Années (ex: `7 YEARS`)
- `INFINITE` : Conservation infinie (par défaut)

⚠️ **Note** : La suppression automatique s'effectue en arrière-plan. SQL Server ne garantit pas la suppression immédiate une fois la période expirée.

### Vérifier la cohérence des données (DATA_CONSISTENCY_CHECK)

Lorsque vous activez `SYSTEM_VERSIONING`, SQL Server vérifie par défaut que les données existantes sont **temporellement cohérentes** (chaque `ValidFrom` ≤ `ValidTo` correspondant). On peut l'expliciter avec l'option `DATA_CONSISTENCY_CHECK` :

```sql
CREATE TABLE Produits
(
    -- ... (colonnes) ...
)
WITH
(
    SYSTEM_VERSIONING = ON
    (
        HISTORY_TABLE = dbo.Produits_History,
        DATA_CONSISTENCY_CHECK = ON  -- Vérifie la cohérence des données (ON par défaut)
    )
);
```

> 💡 **À ne pas confondre avec la compression** : sur les tables d'historique créées automatiquement, SQL Server applique la **compression de page** par défaut pour économiser de l'espace ; elle se gère via l'option `DATA_COMPRESSION` de la table, **indépendamment** de `SYSTEM_VERSIONING`.

## Exemples complets commentés

### Exemple 1 : Table de gestion de stock

```sql
-- Création d'une table pour suivre les niveaux de stock dans le temps
CREATE TABLE Stock
(
    -- Clé primaire composite (entrepôt + produit)
    EntrepotID INT NOT NULL,
    ProduitID INT NOT NULL,

    -- Données métier
    Quantite INT NOT NULL,
    QuantiteMinimale INT NOT NULL,
    DernierReapprovisionnement DATE,

    -- Colonnes temporelles
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL,

    -- Clé primaire composite
    CONSTRAINT PK_Stock PRIMARY KEY (EntrepotID, ProduitID),

    -- Contrainte temporelle
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH
(
    SYSTEM_VERSIONING = ON
    (
        HISTORY_TABLE = dbo.Stock_History,
        HISTORY_RETENTION_PERIOD = 2 YEARS  -- Conserve 2 ans d'historique de stock
    )
);
```

**Cas d'usage** : Vous pouvez voir quelle était la quantité en stock d'un produit à n'importe quelle date passée, ce qui est très utile pour analyser les ruptures de stock, optimiser les réapprovisionnements, etc.

### Exemple 2 : Table de configuration d'application

```sql
-- Table pour stocker des paramètres de configuration avec leur historique
CREATE TABLE ConfigurationApp
(
    -- Clé primaire
    ParametreID INT IDENTITY(1,1) PRIMARY KEY,

    -- Données métier
    Cle NVARCHAR(100) NOT NULL UNIQUE,
    Valeur NVARCHAR(MAX) NOT NULL,
    Description NVARCHAR(500),
    ModifiePar NVARCHAR(100) NOT NULL,  -- Qui a fait la modification

    -- Colonnes temporelles (non masquées pour audit)
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START NOT NULL,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END NOT NULL,

    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH
(
    SYSTEM_VERSIONING = ON
    (
        HISTORY_TABLE = dbo.ConfigurationApp_History
    )
);
```

💡 **Note** : Ici, nous avons enlevé le mot-clé `HIDDEN` pour que les dates soient visibles dans les requêtes normales, car c'est important pour l'audit de configuration.

### Exemple 3 : Conversion d'une table existante

```sql
-- Supposons que vous ayez déjà une table Employes
-- Voici comment ajouter l'historisation

-- Étape 1 : Ajouter les colonnes et la contrainte temporelle
ALTER TABLE Employes
ADD
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL
        CONSTRAINT DF_Employes_ValidFrom DEFAULT SYSUTCDATETIME(),
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL
        CONSTRAINT DF_Employes_ValidTo DEFAULT '9999-12-31 23:59:59.9999999',
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo);

-- Étape 2 : Créer manuellement la table d'historique avec un index optimal
CREATE TABLE Employes_History
(
    EmployeID INT NOT NULL,
    Nom NVARCHAR(100) NOT NULL,
    Prenom NVARCHAR(100) NOT NULL,
    Salaire DECIMAL(10, 2) NOT NULL,
    DepartementID INT NOT NULL,
    ValidFrom DATETIME2 NOT NULL,
    ValidTo DATETIME2 NOT NULL
);

-- Index clustered sur les colonnes temporelles pour optimiser les requêtes temporelles
CREATE CLUSTERED INDEX IX_Employes_History
ON Employes_History (ValidTo, ValidFrom);

-- Étape 3 : Activer l'historisation
ALTER TABLE Employes
SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.Employes_History));
```

## Vérifier qu'une table a l'historisation active

Comment savoir si une table est temporelle ? Plusieurs méthodes :

### Méthode 1 : Interroger les vues système

```sql
-- Lister toutes les tables temporelles de la base de données
SELECT
    SCHEMA_NAME(t.schema_id) AS SchemaName,
    t.name AS TableName,
    t.temporal_type_desc AS TemporalType,
    SCHEMA_NAME(h.schema_id) + '.' + h.name AS HistoryTable
FROM
    sys.tables t
    LEFT JOIN sys.tables h ON t.history_table_id = h.object_id
WHERE
    t.temporal_type = 2;  -- 2 = SYSTEM_VERSIONED_TEMPORAL_TABLE
```

### Méthode 2 : Examiner les colonnes temporelles

```sql
-- Afficher les colonnes temporelles d'une table
SELECT
    c.name AS ColumnName,
    c.generated_always_type_desc AS GeneratedType
FROM
    sys.columns c
WHERE
    c.object_id = OBJECT_ID('Produits')
    AND c.generated_always_type IN (1, 2);  -- 1 = ROW START, 2 = ROW END
```

### Méthode 3 : Utiliser SSMS

Dans SQL Server Management Studio :
1. Développez votre base de données
2. Développez "Tables"
3. Les tables temporelles ont une icône spéciale (avec une horloge)
4. Elles ont un nœud enfant "History Table"

## Erreurs courantes et solutions

### Erreur 1 : Oubli de la clé primaire

```sql
-- ❌ ERREUR : Pas de clé primaire
CREATE TABLE Test
(
    ID INT,
    Nom NVARCHAR(100),
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL,
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH (SYSTEM_VERSIONING = ON);

-- Message d'erreur :
-- "Cannot set SYSTEM_VERSIONING to ON when table does not contain a PRIMARY KEY constraint."
```

✅ **Solution** : Ajoutez une clé primaire :
```sql
CREATE TABLE Test
(
    ID INT PRIMARY KEY,  -- ← Ajout de la clé primaire
    -- ... reste identique ...
);
```

### Erreur 2 : Colonnes temporelles autorisant NULL

```sql
-- ❌ ERREUR : Colonnes temporelles avec NULL
CREATE TABLE Test
(
    ID INT PRIMARY KEY,
    Nom NVARCHAR(100),
    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN,  -- Manque NOT NULL
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN,      -- Manque NOT NULL
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH (SYSTEM_VERSIONING = ON);
```

✅ **Solution** : Ajoutez `NOT NULL` aux colonnes temporelles :
```sql
ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN NOT NULL,
ValidTo DATETIME2 GENERATED ALWAYS AS ROW END HIDDEN NOT NULL,
```

### Erreur 3 : Tentative de modifier manuellement les colonnes temporelles

```sql
-- ❌ ERREUR : Tentative de mise à jour manuelle
UPDATE Produits
SET ValidFrom = '2024-01-01'
WHERE ProduitID = 1;

-- Message d'erreur :
-- "Cannot update GENERATED ALWAYS columns in table 'Produits'."
```

✅ **Explication** : C'est normal ! Les colonnes `GENERATED ALWAYS` sont gérées exclusivement par SQL Server. Vous ne pouvez pas les modifier directement.

### Erreur 4 : Structure différente entre table principale et historique

Si vous créez manuellement la table d'historique, elle **doit** avoir la même structure (même colonnes, mêmes types) que la table principale.

```sql
-- ❌ ERREUR : Structure incohérente
CREATE TABLE Produits_History
(
    ProduitID INT,
    Nom NVARCHAR(50),  -- ← Différent de la table principale (NVARCHAR(100))
    -- ...
);
```

✅ **Solution** : Assurez-vous que les colonnes correspondent exactement.

## Bonnes pratiques

### 1. Nommage cohérent
- Table principale : `NomTable`
- Table d'historique : `NomTable_History` ou `NomTable_Hist`
- Colonnes temporelles : `ValidFrom` / `ValidTo` (ou `SysStartTime` / `SysEndTime`)

### 2. Utilisez HIDDEN pour simplifier les requêtes
```sql
HIDDEN NOT NULL  -- Les colonnes n'apparaissent pas dans SELECT *
```

### 3. Créez des index sur la table d'historique
```sql
CREATE CLUSTERED INDEX IX_NomTable_History
ON NomTable_History (ValidTo, ValidFrom);
```
Cela optimise les requêtes temporelles (`FOR SYSTEM_TIME AS OF ...`).

### 4. Définissez une politique de rétention appropriée
- **Conformité réglementaire** : Conservez l'historique selon les obligations légales (ex: 7 ans pour la comptabilité)
- **Analyse métier** : Conservez suffisamment d'historique pour vos analyses
- **Espace disque** : Équilibrez entre besoins métier et coûts de stockage

### 5. Utilisez UTC pour les dates
```sql
DEFAULT SYSUTCDATETIME()  -- Recommandé (UTC)
-- Plutôt que :
DEFAULT GETDATE()  -- Dépend du fuseau horaire du serveur
```

### 6. Documentez vos tables temporelles
Ajoutez des commentaires ou une documentation pour expliquer pourquoi l'historisation est activée :
```sql
EXEC sp_addextendedproperty
    @name = N'MS_Description',
    @value = N'Table temporelle pour audit réglementaire (7 ans de rétention)',
    @level0type = N'SCHEMA', @level0name = N'dbo',
    @level1type = N'TABLE', @level1name = N'Produits';
```

## Récapitulatif : Checklist de création

Lorsque vous créez une table temporelle, vérifiez :

- [ ] La table a une **clé primaire**
- [ ] Vous avez ajouté **deux colonnes DATETIME2** avec `GENERATED ALWAYS`
- [ ] Les colonnes temporelles sont marquées `NOT NULL`
- [ ] Vous avez ajouté `PERIOD FOR SYSTEM_TIME (colonne1, colonne2)`
- [ ] Vous avez activé `SYSTEM_VERSIONING = ON`
- [ ] Vous avez spécifié le nom de la **table d'historique** (optionnel mais recommandé)
- [ ] Vous avez défini une **politique de rétention** si nécessaire
- [ ] Vous avez créé des **index** sur la table d'historique pour les performances

## Conclusion

La syntaxe `SYSTEM_VERSIONING` peut sembler intimidante au premier abord, mais une fois comprise, elle est assez logique :

1. **Ajoutez deux colonnes temporelles** (`GENERATED ALWAYS AS ROW START/END`)
2. **Définissez une PERIOD FOR SYSTEM_TIME**
3. **Activez SYSTEM_VERSIONING = ON**

Et voilà ! SQL Server s'occupe du reste automatiquement.

Dans la prochaine section (8.3.3), nous verrons comment **interroger** ces tables temporelles pour voyager dans le temps et consulter l'historique de vos données avec la clause `FOR SYSTEM_TIME AS OF`.

---

**Points clés à retenir** :
- Une table temporelle nécessite une clé primaire et deux colonnes DATETIME2
- `GENERATED ALWAYS` indique que SQL Server gère ces colonnes automatiquement
- `HIDDEN` cache les colonnes temporelles dans les `SELECT *`
- `PERIOD FOR SYSTEM_TIME` définit la période de validité
- `SYSTEM_VERSIONING = ON` active l'historisation
- Vous pouvez ajouter l'historisation à une table existante avec `ALTER TABLE`
- Une politique de rétention permet de limiter la taille de l'historique
