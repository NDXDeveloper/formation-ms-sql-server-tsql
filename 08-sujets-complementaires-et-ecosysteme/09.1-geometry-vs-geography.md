# 8.9.1 GEOMETRY (plan) vs GEOGRAPHY (ellipsoïde terrestre)

## Introduction

Avant de manipuler des données spatiales, il faut choisir le bon type — `GEOMETRY` ou `GEOGRAPHY` — et comprendre la notion de **SRID**. Cette sous-section clarifie ce choix, montre comment **créer** des objets spatiaux, et met en garde contre le piège le plus courant : l'inversion latitude/longitude.

---

## GEOMETRY : le plan plat (euclidien)

Le type **`GEOMETRY`** travaille dans un **plan plat** à deux dimensions, avec des coordonnées **X** et **Y** sans unité prédéfinie. C'est la géométrie « du collège » : le théorème de Pythagore s'applique directement.

```sql
DECLARE @a GEOMETRY = geometry::Point(0, 0, 0);
DECLARE @b GEOMETRY = geometry::Point(3, 4, 0);
SELECT @a.STDistance(@b) AS Distance;   -- 5  (Pythagore : √(3²+4²))
```

**Quand l'utiliser ?**
- Plans de bâtiments, CAO, agencements d'entrepôt.
- Données déjà **projetées** sur un plan (cartes locales).
- Espaces non géographiques (coordonnées d'écran, de jeu).

➡️ Sur de petites zones, `GEOMETRY` est simple et suffisant. Mais à l'échelle d'un pays, ignorer la courbure de la Terre fausse les distances.

---

## GEOGRAPHY : la Terre courbe (ellipsoïde)

Le type **`GEOGRAPHY`** travaille sur un **ellipsoïde** représentant la Terre. Les coordonnées sont la **longitude** et la **latitude** (en degrés), et les distances sont retournées en **mètres réels**.

```sql
DECLARE @paris GEOGRAPHY = geography::Point(48.8566, 2.3522, 4326);
DECLARE @lyon  GEOGRAPHY = geography::Point(45.7640, 4.8357, 4326);
SELECT @paris.STDistance(@lyon) AS Metres;   -- ≈ 392 000 (≈ 392 km)
```

**Quand l'utiliser ?**
- **Positions GPS** réelles (la grande majorité des cas).
- Cartographie à l'échelle régionale, nationale ou mondiale.
- Tout calcul de **distance réelle** entre des lieux.

---

## Le SRID (Spatial Reference Identifier)

Un **SRID** est un identifiant du **système de référence spatial** : il dit *comment* interpréter les coordonnées.

- **SRID 4326** = **WGS 84**, le système des **GPS**. C'est celui que vous utiliserez quasi systématiquement avec `GEOGRAPHY`.
- **SRID 0** = plan sans référence géographique, courant avec `GEOMETRY`.

⚠️ **Deux objets spatiaux doivent avoir le même SRID** pour qu'on puisse les comparer ou calculer une distance entre eux. Calculer une distance entre des objets de SRID différents renvoie `NULL`.

```sql
SELECT geography::Point(48.85, 2.35, 4326).STSrid;   -- 4326
```

---

## ⚠️ LE piège : l'ordre latitude / longitude

C'est l'erreur la plus fréquente, et elle est sournoise car elle ne provoque pas d'erreur — juste des résultats faux (vos points se retrouvent au mauvais endroit sur Terre).

| Méthode | Ordre attendu |
|---------|---------------|
| `geography::Point(lat, long, srid)` | **latitude d'abord**, puis longitude |
| WKT `POINT(long lat)` | **longitude d'abord**, puis latitude |

```sql
-- Paris (lat 48.8566, long 2.3522) — DEUX écritures équivalentes :

-- 1) Avec Point() : latitude puis longitude
DECLARE @p1 GEOGRAPHY = geography::Point(48.8566, 2.3522, 4326);

-- 2) Avec WKT : longitude puis latitude (inversé !)
DECLARE @p2 GEOGRAPHY = geography::STGeomFromText('POINT(2.3522 48.8566)', 4326);
```

> 💡 **Moyen mnémotechnique** : en WKT, on écrit les coordonnées comme **X Y**, donc **longitude (X) puis latitude (Y)**. Avec `Point()`, c'est l'inverse : **latitude puis longitude**. En cas de doute, vérifiez qu'un point connu retombe bien au bon endroit.

---

## Créer des objets spatiaux : les principales méthodes

```sql
-- Un point
geography::Point(48.8566, 2.3522, 4326)

-- À partir de WKT (n'importe quelle forme)
geography::STGeomFromText('POINT(2.3522 48.8566)', 4326)
geography::STGeomFromText('LINESTRING(2.35 48.85, 4.83 45.76)', 4326)
geography::STGeomFromText('POLYGON((2.2 48.8, 2.5 48.8, 2.5 49.0, 2.2 49.0, 2.2 48.8))', 4326)

-- Parse (équivalent à STGeomFromText, SRID 4326 par défaut pour geography)
geography::Parse('POINT(2.3522 48.8566)')
```

## Stocker des données spatiales dans une table

```sql
CREATE TABLE Magasins (
    MagasinID  INT IDENTITY PRIMARY KEY,
    Nom        NVARCHAR(100),
    Position   GEOGRAPHY               -- colonne spatiale
);

INSERT INTO Magasins (Nom, Position) VALUES
('Magasin Paris', geography::Point(48.8566, 2.3522, 4326)),
('Magasin Lyon',  geography::Point(45.7640, 4.8357, 4326)),
('Magasin Lille', geography::Point(50.6292, 3.0573, 4326));

-- Lire les positions sous forme lisible (WKT)
SELECT Nom, Position.STAsText() AS WKT FROM Magasins;
```

## Particularités du type GEOGRAPHY

Travailler sur une sphère introduit quelques subtilités absentes du plan :

- **Orientation des polygones** : pour `GEOGRAPHY`, l'ordre des points d'un polygone définit « l'intérieur ». Un polygone mal orienté peut désigner… tout le reste de la planète ! (Règle de la main gauche : l'intérieur est à gauche du parcours des sommets.)
- **Taille limite** : historiquement, un polygone `GEOGRAPHY` devait tenir dans un hémisphère (limite assouplie dans les versions récentes).
- **Validité** : une forme peut être invalide (auto-intersection). On la teste avec `STIsValid()` et on la corrige avec `MakeValid()`.

```sql
SELECT @zone.STIsValid();   -- 1 si valide
SET @zone = @zone.MakeValid();
```

## Quel type choisir ? Récapitulatif

```
Vos coordonnées sont des latitudes/longitudes GPS ?
   ├── OUI → GEOGRAPHY (SRID 4326)         ← le cas le plus fréquent
   └── NON (plan local, écran, CAO, projeté) → GEOMETRY
```

> 💡 En cas de doute pour une application de géolocalisation classique : **`GEOGRAPHY` avec SRID 4326**. C'est le choix qui « fait ce qu'on attend » (distances en mètres, sur la vraie Terre).

## Pièges courants

| Piège | Cause | Solution |
|-------|-------|----------|
| `STDistance` renvoie `NULL` | SRID différents entre les deux objets | Harmoniser les SRID (vérifier `.STSrid`) |
| Distances absurdes (millions de km) | lat/long inversés, ou `GEOMETRY` au lieu de `GEOGRAPHY` | Vérifier l'ordre des coordonnées et le type |
| Polygone qui « contient toute la Terre » | Orientation des sommets incorrecte (GEOGRAPHY) | Respecter la règle d'orientation / `ReorientObject()` |
| Forme refusée à l'insertion | Forme invalide (auto-intersection) | `STIsValid()` puis `MakeValid()` |

## Questions fréquentes

**Q : Comment convertir un `GEOMETRY` en `GEOGRAPHY` (ou l'inverse) ?**
R : Il n'y a pas de conversion implicite « correcte » : les deux modèles diffèrent. On reconstruit l'objet dans le bon type à partir de son WKT et du bon SRID.

**Q : Quel SRID pour la France ou le monde ?**
R : **4326 (WGS 84)** convient pour le monde entier en `GEOGRAPHY`. Pour des cartes projetées locales en `GEOMETRY`, on utilise un SRID projeté adapté — sujet SIG plus avancé.

**Q : Les colonnes spatiales peuvent-elles être indexées ?**
R : Oui, via un **index spatial** (voir §8.9.2), indispensable pour les performances sur de gros volumes.

---

## Résumé

- **`GEOMETRY`** = plan plat (X/Y, unités arbitraires) ; **`GEOGRAPHY`** = Terre courbe (longitude/latitude, mètres).
- Le **SRID** définit le système de coordonnées ; **4326 (WGS 84)** est celui des GPS. Deux objets doivent partager le même SRID.
- ⚠️ Attention à l'ordre : `Point(lat, long, srid)` mais WKT `POINT(long lat)`.
- On crée des objets avec `Point()`, `STGeomFromText()`, `Parse()` ; on les lit avec `STAsText()`.
- Pour `GEOGRAPHY`, surveiller l'**orientation** des polygones et la **validité** (`STIsValid` / `MakeValid`).
- En géolocalisation classique, choisir **`GEOGRAPHY` SRID 4326**.

Place aux opérations : mesurer, tester l'inclusion, l'intersection… et accélérer tout cela avec un index spatial.
