# 1.1.2 Le Modèle Relationnel (Entités, Relations)

## Introduction

Maintenant que nous comprenons la différence entre données et informations, explorons comment organiser ces données de manière efficace. Le **modèle relationnel** est la base théorique sur laquelle reposent la plupart des bases de données modernes, dont Microsoft SQL Server.

Inventé par Edgar F. Codd en 1970, ce modèle a révolutionné la façon dont nous stockons et organisons les données. Son principe ? Représenter les données sous forme de **tables** (aussi appelées **relations**) qui peuvent être liées entre elles.

## Qu'est-ce que le modèle relationnel ?

Le **modèle relationnel** est une façon d'organiser les données en les structurant dans des tableaux (tables) où :
- Chaque table représente un type d'objet ou de concept (une **entité**)
- Les tables peuvent être reliées entre elles par des **relations**
- Les données sont organisées en lignes et en colonnes

### Analogie simple : le classeur de fiches

Imaginez un classeur traditionnel avec différentes sections :
- Une section pour vos **clients** (avec une fiche par client)
- Une section pour vos **produits** (avec une fiche par produit)
- Une section pour vos **commandes** (avec une fiche par commande)

Le modèle relationnel fonctionne de manière similaire, mais avec la puissance de créer des liens entre ces différentes sections !

## Les Entités : Qu'est-ce que c'est ?

Une **entité** représente un objet, un concept ou une "chose" du monde réel que vous souhaitez représenter dans votre base de données.

### Définition simple

Une entité est quelque chose dont vous voulez stocker des informations parce que c'est important pour votre organisation.

### Exemples d'entités

Dans différents contextes, on peut identifier diverses entités :

**Dans une entreprise de commerce :**
- Client
- Produit
- Commande
- Fournisseur
- Employé

**Dans une école :**
- Étudiant
- Professeur
- Cours
- Salle de classe
- Note

**Dans une bibliothèque :**
- Livre
- Auteur
- Adhérent
- Emprunt
- Catégorie

### Comment identifier une entité ?

Posez-vous ces questions :
1. Est-ce quelque chose dont je dois stocker plusieurs occurrences ?
2. Est-ce quelque chose qui possède des caractéristiques propres ?
3. Est-ce quelque chose qui existe de manière indépendante ?

Si vous répondez **oui** à ces questions, il s'agit probablement d'une entité.

## Les Attributs : Les caractéristiques d'une entité

Chaque entité possède des **attributs**, c'est-à-dire des caractéristiques qui la décrivent.

### Exemple : L'entité Client

Un **Client** pourrait avoir les attributs suivants :
- Numéro de client (identifiant unique)
- Nom
- Prénom
- Adresse email
- Téléphone
- Date d'inscription
- Ville

### Exemple : L'entité Produit

Un **Produit** pourrait avoir les attributs suivants :
- Code produit (identifiant unique)
- Nom du produit
- Description
- Prix unitaire
- Quantité en stock
- Catégorie

### Représentation visuelle

On peut représenter une entité et ses attributs comme ceci :

```
┌─────────────────────────┐
│       CLIENT            │
├─────────────────────────┤
│ NuméroClient (PK)       │
│ Nom                     │
│ Prénom                  │
│ Email                   │
│ Téléphone               │
│ DateInscription         │
│ Ville                   │
└─────────────────────────┘

(PK = Primary Key = Clé Primaire)
```

## Les Relations : Lier les entités entre elles

Le vrai pouvoir du modèle relationnel réside dans sa capacité à créer des **relations** (ou **liens**) entre les différentes entités.

### Pourquoi créer des relations ?

Dans le monde réel, les objets sont souvent liés entre eux :
- Un **client** passe des **commandes**
- Une **commande** contient des **produits**
- Un **étudiant** est inscrit à des **cours**
- Un **livre** est écrit par un **auteur**

Les relations nous permettent de représenter ces liens dans notre base de données.

### Types de relations

Il existe trois types principaux de relations entre entités :

#### 1. Relation Un-à-Un (1:1)

**Définition :** Une occurrence de l'entité A est liée à une seule occurrence de l'entité B, et vice versa.

**Exemple :**
- Un **employé** a **un seul** badge d'accès
- Un **badge** est attribué à **un seul** employé

```
EMPLOYÉ ←──(1:1)──→ BADGE
```

**Cas d'usage :** Assez rare, souvent utilisé pour séparer des informations sensibles ou peu fréquemment consultées.

#### 2. Relation Un-à-Plusieurs (1:N)

**Définition :** Une occurrence de l'entité A peut être liée à plusieurs occurrences de l'entité B, mais une occurrence de B est liée à une seule occurrence de A.

**Exemple :**
- Un **client** peut passer **plusieurs commandes**
- Une **commande** appartient à **un seul client**

```
CLIENT ──(1)────(N)→ COMMANDE

Un client → Plusieurs commandes
Une commande → Un seul client
```

**Autres exemples :**
- Un département → Plusieurs employés
- Un auteur → Plusieurs livres
- Une catégorie → Plusieurs produits

**Cas d'usage :** C'est le type de relation le plus courant dans les bases de données.

#### 3. Relation Plusieurs-à-Plusieurs (N:M)

**Définition :** Une occurrence de l'entité A peut être liée à plusieurs occurrences de l'entité B, et vice versa.

**Exemple :**
- Un **étudiant** peut être inscrit à **plusieurs cours**
- Un **cours** peut avoir **plusieurs étudiants**

```
ÉTUDIANT ←──(N:M)──→ COURS
```

**Autres exemples :**
- Un produit peut être présent dans plusieurs commandes, et une commande peut contenir plusieurs produits
- Un acteur peut jouer dans plusieurs films, et un film peut avoir plusieurs acteurs

**Important :** Dans une base de données relationnelle, on ne peut pas implémenter directement une relation N:M. On doit la décomposer en créant une **table intermédiaire** (aussi appelée **table de jonction** ou **table d'association**).

### Table de jonction : Résoudre le N:M

Pour gérer une relation plusieurs-à-plusieurs, on crée une table intermédiaire qui contient les clés des deux entités.

**Exemple : Étudiants et Cours**

Au lieu de :
```
ÉTUDIANT ←──(N:M)──→ COURS
```

On crée :
```
ÉTUDIANT ──(1:N)──→ INSCRIPTION ←──(N:1)── COURS
```

La table **INSCRIPTION** devient :

```
┌─────────────────────────┐
│     INSCRIPTION         │
├─────────────────────────┤
│ ID_Étudiant (FK)        │
│ ID_Cours (FK)           │
│ DateInscription         │
│ Note                    │
└─────────────────────────┘
```

Ainsi, la relation N:M est transformée en deux relations 1:N !

## Exemple complet : Système de gestion de commandes

Imaginons un système simple de e-commerce avec trois entités principales.

### Les entités et leurs attributs

**1. CLIENT**
- NuméroClient (identifiant unique)
- Nom
- Prénom
- Email
- Téléphone

**2. COMMANDE**
- NuméroCommande (identifiant unique)
- DateCommande
- NuméroClient (qui a passé la commande ?)
- Statut
- MontantTotal

**3. PRODUIT**
- CodeProduit (identifiant unique)
- NomProduit
- PrixUnitaire
- Stock

**4. LIGNE_COMMANDE** (table de jonction)
- NuméroCommande
- CodeProduit
- Quantité
- PrixLigne

### Les relations

```
        CLIENT
           │
           │ (1:N) Un client peut passer plusieurs commandes
           ↓
       COMMANDE
           │
           │ (1:N) Une commande contient plusieurs lignes
           ↓
   LIGNE_COMMANDE ←──(N:1)── PRODUIT
                              (Un produit peut être dans plusieurs commandes)
```

### Lecture du modèle

- **CLIENT → COMMANDE** (1:N) : Un client peut passer plusieurs commandes, mais une commande appartient à un seul client
- **COMMANDE → LIGNE_COMMANDE** (1:N) : Une commande contient plusieurs lignes (plusieurs produits)
- **PRODUIT → LIGNE_COMMANDE** (1:N) : Un produit peut apparaître dans plusieurs lignes de commande différentes
- **COMMANDE ↔ PRODUIT** (N:M via LIGNE_COMMANDE) : Une commande peut contenir plusieurs produits, et un produit peut être dans plusieurs commandes

## Les clés : Identifier et lier les données

Pour que le modèle relationnel fonctionne, nous avons besoin de **clés** pour identifier de manière unique chaque enregistrement et créer des liens.

### Clé Primaire (Primary Key - PK)

Une **clé primaire** est un attribut (ou un ensemble d'attributs) qui identifie de manière **unique** chaque occurrence d'une entité.

**Caractéristiques :**
- **Unique** : Pas de doublon possible
- **Non nulle** : Doit toujours avoir une valeur
- **Immuable** : Ne devrait jamais changer

**Exemples :**
- NuméroClient pour CLIENT
- NuméroCommande pour COMMANDE
- CodeProduit pour PRODUIT
- Numéro de Sécurité Sociale pour PERSONNE

### Clé Étrangère (Foreign Key - FK)

Une **clé étrangère** est un attribut dans une table qui fait référence à la clé primaire d'une autre table. C'est le mécanisme qui crée les **relations** entre les tables.

**Exemple :**

Dans la table COMMANDE :
- `NuméroCommande` est la **clé primaire** (identifie la commande)
- `NuméroClient` est une **clé étrangère** (référence le client dans la table CLIENT)

Cela signifie : "Cette commande appartient au client dont le numéro est X."

### L'intégrité référentielle en action

La clé étrangère ne se contente pas de **relier** les tables : elle **protège** la cohérence des données. Le SGBDR refuse automatiquement toute opération qui romprait un lien. Voyons-le concrètement avec une table `CLIENT` contenant les clients 1 et 2 :

```
CLIENT
┌──────────────┬────────┬────────┐
│ NuméroClient │ Nom    │ Prénom │
├──────────────┼────────┼────────┤
│ 1            │ Dupont │ Jean   │
│ 2            │ Martin │ Marie  │
└──────────────┴────────┴────────┘
```

**Cas 1 — Créer une commande pour un client qui n'existe pas :**
- ✅ Commande avec `NuméroClient = 1` → **acceptée** (le client 1 existe).
- ❌ Commande avec `NuméroClient = 99` → **refusée** : aucun client n°99. La clé étrangère empêche une commande « orpheline », rattachée à un client fantôme.

**Cas 2 — Supprimer un client qui a des commandes :**
- ❌ Supprimer le client n°1 alors qu'il a des commandes → **refusé** par défaut : cela laisserait des commandes pointant vers un client disparu.
- On *peut* choisir un autre comportement (par exemple supprimer en cascade les commandes liées, via `ON DELETE CASCADE`, vu au chapitre 2), mais **par défaut, SQL Server protège** la cohérence.

> 🧠 **C'est exactement cela, l'intégrité référentielle** : la garantie — assurée par le SGBDR lui-même, et non par le code applicatif — que les liens entre les tables restent **toujours valides**. C'est l'une des grandes forces du modèle relationnel.

## Avantages du modèle relationnel

### 1. Éviter la redondance des données

Au lieu de répéter les informations du client dans chaque commande, on stocke le client une seule fois et on le référence.

❌ **Mauvaise approche (sans modèle relationnel) :**
```
Table COMMANDE_COMPLETE :
NuméroCommande | DateCommande | NomClient | PrénomClient | EmailClient | ...
1              | 2024-01-15   | Dupont    | Jean         | j.d@mail.com| ...
2              | 2024-01-16   | Dupont    | Jean         | j.d@mail.com| ...
3              | 2024-01-17   | Dupont    | Jean         | j.d@mail.com| ...
```
→ Les informations de "Dupont Jean" sont répétées 3 fois !

✅ **Bonne approche (modèle relationnel) :**
```
Table CLIENT :
NuméroClient | Nom    | Prénom | Email
1            | Dupont | Jean   | j.d@mail.com

Table COMMANDE :
NuméroCommande | DateCommande | NuméroClient
1              | 2024-01-15   | 1
2              | 2024-01-16   | 1
3              | 2024-01-17   | 1
```
→ Les informations du client ne sont stockées qu'une seule fois !

### 2. Maintenir l'intégrité des données

Si l'email de Jean Dupont change, il suffit de le modifier à un seul endroit (dans la table CLIENT), et toutes ses commandes référenceront automatiquement la bonne information.

### 3. Flexibilité et évolutivité

Il est facile d'ajouter de nouvelles entités et relations sans perturber la structure existante.

### 4. Faciliter les requêtes complexes

Le langage SQL permet de "joindre" facilement les tables pour obtenir des informations complètes :
- "Afficher toutes les commandes du client Dupont avec les détails des produits"
- "Trouver tous les clients qui ont acheté le produit X"

## Terminologie : Table vs Relation

Dans le modèle relationnel théorique, on parle de **relations**. Dans la pratique et dans SQL Server, on parle de **tables**. Ces deux termes désignent la même chose :

- **Relation** = terme théorique
- **Table** = terme pratique (ce que vous verrez dans SQL Server)

De même :
- **Tuple** (théorique) = **Ligne** ou **Enregistrement** (pratique)
- **Attribut** (théorique) = **Colonne** (pratique)

## Résumé

- Le **modèle relationnel** organise les données en **tables** (relations)
- Une **entité** représente un objet ou concept du monde réel (Client, Produit, Commande...)
- Chaque entité possède des **attributs** (caractéristiques)
- Les **relations** permettent de lier les entités entre elles
- Il existe trois types de relations : **1:1**, **1:N**, et **N:M**
- Une **clé primaire** (PK) identifie de manière unique chaque enregistrement
- Une **clé étrangère** (FK) crée un lien vers une autre table
- Les relations **N:M** nécessitent une **table de jonction**
- Ce modèle évite la **redondance** et garantit l'**intégrité** des données

Le modèle relationnel est la fondation sur laquelle repose SQL Server et la majorité des bases de données actuelles. Comprendre ces concepts vous permettra de concevoir des bases de données efficaces et de maîtriser le langage SQL pour interroger et manipuler ces données.
