# 7.4.3 Problèmes de statistiques obsolètes (Parameter Sniffing - concept)

## Introduction

Dans les sections précédentes, nous avons compris le rôle crucial des statistiques et comment les maintenir à jour. Mais même avec toutes ces connaissances, il existe des situations particulières où les statistiques peuvent vous jouer des tours et causer des problèmes de performance difficiles à diagnostiquer.

Dans cette section, nous allons explorer les **problèmes les plus courants liés aux statistiques obsolètes**, avec une attention particulière pour un phénomène mystérieux et frustrant : le **Parameter Sniffing**.

## Les symptômes de statistiques obsolètes

### Le mystère de la requête incohérente

Vous avez probablement déjà vécu cette situation frustrante :

**Scénario :**
- Une requête fonctionne parfaitement pendant des semaines
- Soudainement, sans changement apparent, elle devient très lente
- Vous la relancez : parfois elle est rapide, parfois elle est lente
- Le comportement semble aléatoire et imprévisible

**Bienvenue dans le monde des problèmes de statistiques !**

### Les symptômes classiques

#### 1. Performance dégradée progressivement

**Le pattern :**
```
Semaine 1 : Requête en 2 secondes ✅
Semaine 4 : Requête en 5 secondes ⚠️
Semaine 8 : Requête en 30 secondes ❌
Semaine 12 : Timeout ! 🔥
```

**Cause probable :** Statistiques devenues obsolètes au fil des modifications de données.

#### 2. Performance inconsistante

**Le pattern :**
```
Exécution 1 : 1 seconde ✅
Exécution 2 : 45 secondes ❌
Exécution 3 : 2 secondes ✅
Exécution 4 : 38 secondes ❌
```

**Cause probable :** Parameter Sniffing (nous y reviendrons).

#### 3. Plans d'exécution radicalement différents

**Le pattern :**
- Parfois : Index Seek, Nested Loops, 2 secondes
- Parfois : Table Scan, Hash Match, 45 secondes
- Même requête, même données, plans différents !

**Cause probable :** Statistiques incohérentes ou Parameter Sniffing.

## Problème 1 : Statistiques obsolètes classiques

### Comprendre le problème

C'est le cas le plus simple : vos statistiques ne reflètent plus la réalité actuelle de vos données.

### Exemple concret

#### Situation initiale (Janvier 2024)

```sql
-- Table Commandes
Nombre total de lignes : 100 000
Commandes de 2024 : 10 000 lignes (10%)

-- Les statistiques sont à jour
-- Distribution :
-- 2020 : 25 000 (25%)
-- 2021 : 25 000 (25%)
-- 2022 : 25 000 (25%)
-- 2023 : 25 000 (25%)
-- 2024 : 10 000 (10%)
```

**Requête :**
```sql
SELECT *
FROM Commandes
WHERE YEAR(DateCommande) = 2024;
```

**Plan choisi par l'optimiseur :**
- Estime : 10 000 lignes (10%)
- Choisit : **Index Seek** + Nested Loops
- Performance : ✅ Rapide (2 secondes)

#### Situation 6 mois plus tard (Juillet 2024)

```sql
-- Table Commandes
Nombre total de lignes : 200 000
Commandes de 2024 : 110 000 lignes (55%)

-- MAIS les statistiques n'ont PAS été mises à jour !
-- Elles disent encore :
-- Distribution :
-- 2020 : 25 000 (25%)
-- 2021 : 25 000 (25%)
-- 2022 : 25 000 (25%)
-- 2023 : 25 000 (25%)
-- 2024 : 10 000 (10%)  ← FAUX ! C'est en réalité 55%
```

**Même requête :**
```sql
SELECT *
FROM Commandes
WHERE YEAR(DateCommande) = 2024;
```

**Plan choisi par l'optimiseur :**
- Estime : 10 000 lignes (10%) ← Basé sur statistiques obsolètes
- Choisit : **Index Seek** + Nested Loops (adapté pour 10K lignes)
- **Réalité** : 110 000 lignes à traiter !
- Performance : ❌ Catastrophique (45 secondes ou timeout)

### Pourquoi cela arrive-t-il ?

Rappelez-vous le seuil de mise à jour automatique :

```
Seuil = 500 + 20% du nombre de lignes

Table de 100 000 lignes : 500 + 20 000 = 20 500 modifications nécessaires
```

Dans notre exemple :
- 100 000 nouvelles lignes ont été ajoutées
- Mais réparties progressivement sur 6 mois
- Le seuil est atteint, mais la mise à jour n'a peut-être pas capté le changement de distribution

### La solution

```sql
-- Mettre à jour les statistiques
UPDATE STATISTICS Commandes WITH FULLSCAN;

-- Maintenant l'optimiseur sait que 2024 = 55%
-- Il choisit : Hash Match ou Merge Join
-- Performance : ✅ Rapide à nouveau (3 secondes)
```

## Problème 2 : Le Parameter Sniffing

### Qu'est-ce que le Parameter Sniffing ?

Le **Parameter Sniffing** (littéralement "reniflage de paramètres") est un comportement de SQL Server où l'optimiseur "regarde" les **valeurs des paramètres** lors de la première compilation d'une requête pour créer un plan d'exécution.

#### Analogie : Le restaurant et le chef

Imaginez un restaurant où le chef prépare des recettes :

**Scénario normal :**
1. Premier client commande : "Salade César pour 2 personnes"
2. Le chef prépare une recette adaptée (petit saladier, 10 minutes)
3. Cette recette est notée et réutilisée

**Scénario avec Parameter Sniffing :**
1. Premier client commande : "Salade César pour **100 personnes**" (événement exceptionnel)
2. Le chef prépare une recette adaptée (énorme saladier, préparation industrielle, 2 heures)
3. Cette recette est notée et **réutilisée pour tous les clients suivants** !
4. Deuxième client : "Salade César pour 2 personnes"
5. Le chef utilise la recette pour 100 personnes ! (gaspillage énorme, temps perdu)

C'est exactement ce qui se passe avec le Parameter Sniffing : SQL Server crée un plan pour une valeur de paramètre spécifique, puis le réutilise pour toutes les autres valeurs, même si elles sont très différentes.

### Comment ça fonctionne techniquement

#### Étape 1 : Première exécution avec un paramètre

```sql
-- Procédure stockée
CREATE PROCEDURE GetClientsByVille
    @Ville VARCHAR(50)
AS
BEGIN
    SELECT *
    FROM Clients
    WHERE Ville = @Ville;
END;
GO

-- Première exécution avec 'Paris'
EXEC GetClientsByVille @Ville = 'Paris';
```

**Ce qui se passe :**
1. SQL Server **compile** la procédure
2. Il **"sniffe"** (regarde) la valeur du paramètre : 'Paris'
3. Il consulte les statistiques : Paris = 80% des clients (800 000 lignes)
4. Il crée un plan optimisé pour **80% des données** : Hash Match, Table Scan
5. Il met ce plan **en cache** pour les exécutions futures

#### Étape 2 : Exécutions suivantes avec d'autres paramètres

```sql
-- Deuxième exécution avec 'Lyon'
EXEC GetClientsByVille @Ville = 'Lyon';
-- Lyon = 2% des clients (20 000 lignes)
-- Mais SQL Server réutilise le plan créé pour Paris !
-- Plan : Hash Match, Table Scan (adapté pour 800K lignes)
-- Résultat : INEFFICACE pour seulement 20K lignes
-- Un Index Seek aurait été bien meilleur !

-- Troisième exécution avec 'Toulouse'
EXEC GetClientsByVille @Ville = 'Toulouse';
-- Toulouse = 1% des clients (10 000 lignes)
-- Même problème : plan inadapté réutilisé
```

### Exemple concret détaillé

#### Contexte

```sql
-- Table Produits
Total : 1 000 000 produits

-- Distribution par catégorie :
Électronique : 850 000 produits (85%)
Livres : 100 000 produits (10%)
Jouets : 30 000 produits (3%)
Sports : 15 000 produits (1.5%)
Autres : 5 000 produits (0.5%)

-- Index sur Categorie
CREATE INDEX IX_Produits_Categorie ON Produits(Categorie);
```

#### La procédure stockée

```sql
CREATE PROCEDURE GetProduitsByCategorie
    @Categorie VARCHAR(50)
AS
BEGIN
    SELECT *
    FROM Produits
    WHERE Categorie = @Categorie;
END;
```

#### Scénario A : Premier appel avec 'Électronique'

```sql
EXEC GetProduitsByCategorie @Categorie = 'Électronique';
```

**Ce qui se passe :**
1. Compilation de la procédure
2. Parameter Sniffing : @Categorie = 'Électronique'
3. Consultation des statistiques : 85% des produits
4. **Décision de l'optimiseur :**
   - 85%, c'est énorme !
   - Autant faire un **Table Scan** (lire toute la table)
   - Index Seek + 850K Key Lookups serait pire
5. Plan créé : **Table Scan**
6. Plan mis en cache
7. **Performance pour Électronique : ✅ Bon** (3 secondes)

#### Scénario B : Appels suivants avec petites catégories

```sql
-- Deuxième appel
EXEC GetProduitsByCategorie @Categorie = 'Sports';
```

**Ce qui se passe :**
1. SQL Server trouve le plan en cache
2. **Il réutilise le plan créé pour 'Électronique' !**
3. Plan réutilisé : **Table Scan** (lit 1 000 000 produits)
4. Alors qu'il ne cherche que 15 000 produits Sports (1.5%)
5. Un **Index Seek** aurait été 60× plus rapide !
6. **Performance pour Sports : ❌ Mauvaise** (3 secondes pour trouver 15K lignes)

```sql
-- Troisième appel
EXEC GetProduitsByCategorie @Categorie = 'Jouets';
```

**Même problème :**
- Plan en cache réutilisé : Table Scan
- Cherche 30 000 produits Jouets (3%)
- **Performance : ❌ Mauvaise** (3 secondes pour 30K lignes)

#### Scénario C : Inversons l'ordre !

Maintenant, redémarrons SQL Server et appelons d'abord avec 'Sports' :

```sql
-- Première exécution après redémarrage
EXEC GetProduitsByCategorie @Categorie = 'Sports';
```

**Ce qui se passe :**
1. Compilation de la procédure
2. Parameter Sniffing : @Categorie = 'Sports'
3. Consultation des statistiques : 1.5% des produits
4. **Décision de l'optimiseur :**
   - 1.5%, c'est très peu !
   - Un **Index Seek** est parfait
5. Plan créé : **Index Seek**
6. Plan mis en cache
7. **Performance pour Sports : ✅ Excellent** (0.1 seconde)

```sql
-- Deuxième exécution avec Électronique
EXEC GetProduitsByCategorie @Categorie = 'Électronique';
```

**Ce qui se passe :**
1. SQL Server trouve le plan en cache (créé pour Sports)
2. **Il réutilise le plan : Index Seek !**
3. Mais pour 850 000 produits ! (85% de la table)
4. 850 000 Index Seek + Key Lookups !
5. **Performance pour Électronique : ❌ CATASTROPHIQUE** (5 minutes ou timeout !)

### Le paradoxe du Parameter Sniffing

Le Parameter Sniffing crée une situation paradoxale :

**Le bon et le mauvais dépendent de la première exécution :**

| Première exécution | Plan créé | Bon pour | Mauvais pour |
|-------------------|-----------|----------|--------------|
| Catégorie fréquente (85%) | Table Scan | Catégories fréquentes | Catégories rares |
| Catégorie rare (1.5%) | Index Seek | Catégories rares | Catégories fréquentes |

**Résultat :** La performance est **imprévisible** et dépend de circonstances hors de votre contrôle (quelle valeur est arrivée en premier).

### Pourquoi SQL Server fait-il cela ?

#### L'objectif initial (bon)

Le Parameter Sniffing est une **fonctionnalité**, pas un bug ! L'objectif est d'optimiser pour les valeurs réelles :

**Avantage :**
- Évite de recompiler le plan à chaque exécution
- Utilise les vraies valeurs pour de meilleures estimations
- Performance optimale... si les valeurs sont similaires

#### Le problème (mauvais)

Mais cela devient problématique quand :
- Les valeurs de paramètres ont des **distributions très différentes**
- Le plan optimal pour une valeur est **terrible** pour une autre
- La première valeur utilisée est **atypique** (exception)

### Détecter le Parameter Sniffing

#### Symptôme 1 : Performance inconsistante

```sql
-- Parfois rapide
EXEC GetProduitsByCategorie @Categorie = 'Sports';  -- 0.1 seconde

-- Parfois lent
EXEC GetProduitsByCategorie @Categorie = 'Sports';  -- 3 secondes

-- Même paramètre, temps différents !
```

**Explication :** Le plan en cache a changé (recompilation entre les deux).

#### Symptôme 2 : Réinitialisation qui résout le problème

```sql
-- Requête lente
EXEC GetProduitsByCategorie @Categorie = 'Électronique';  -- 5 minutes

-- Vider le cache des plans
DBCC FREEPROCCACHE;

-- Même requête, maintenant rapide !
EXEC GetProduitsByCategorie @Categorie = 'Électronique';  -- 3 secondes
```

**Explication :** Le plan a été recréé avec la bonne valeur.

#### Symptôme 3 : Écart entre estimations et réalité dans le plan

```sql
-- Afficher le plan d'exécution réel
SET STATISTICS XML ON;
EXEC GetProduitsByCategorie @Categorie = 'Sports';

-- Dans le plan :
-- Estimated Rows : 850 000  (estimation pour 'Électronique')
-- Actual Rows : 15 000       (réalité pour 'Sports')
-- Ratio : 56× !
```

**Explication :** Le plan a été créé pour une autre valeur de paramètre.

## Solutions au Parameter Sniffing

### Solution 1 : RECOMPILE (Recompiler à chaque exécution)

#### Niveau requête

```sql
CREATE PROCEDURE GetProduitsByCategorie
    @Categorie VARCHAR(50)
AS
BEGIN
    SELECT *
    FROM Produits
    WHERE Categorie = @Categorie
    OPTION (RECOMPILE);  -- Force la recompilation
END;
```

**Avantages :**
- ✅ Plan toujours optimal pour la valeur actuelle
- ✅ Pas de problème de Parameter Sniffing
- ✅ Solution simple

**Inconvénients :**
- ❌ Overhead de compilation à chaque exécution
- ❌ Peut ralentir si la requête est appelée très fréquemment
- ❌ Perte du bénéfice du cache de plans

**Quand l'utiliser :**
- Requêtes avec distributions très variables
- Requêtes peu fréquentes mais critiques
- Quand le coût de compilation est négligeable vs le gain

### Solution 2 : OPTIMIZE FOR (Optimiser pour une valeur spécifique)

```sql
CREATE PROCEDURE GetProduitsByCategorie
    @Categorie VARCHAR(50)
AS
BEGIN
    SELECT *
    FROM Produits
    WHERE Categorie = @Categorie
    OPTION (OPTIMIZE FOR (@Categorie = 'Sports'));  -- Optimise toujours pour 'Sports'
END;
```

**Avantages :**
- ✅ Plan prévisible et cohérent
- ✅ Optimisé pour la valeur la plus courante
- ✅ Pas d'overhead de recompilation

**Inconvénients :**
- ❌ Peut être sous-optimal pour d'autres valeurs
- ❌ Nécessite de connaître la valeur "typique"

**Quand l'utiliser :**
- Vous savez quelle valeur est la plus fréquente
- 80% des appels utilisent la même catégorie de valeurs
- Performance acceptable pour toutes les valeurs avec ce plan

### Solution 3 : OPTIMIZE FOR UNKNOWN (Plan générique)

```sql
CREATE PROCEDURE GetProduitsByCategorie
    @Categorie VARCHAR(50)
AS
BEGIN
    SELECT *
    FROM Produits
    WHERE Categorie = @Categorie
    OPTION (OPTIMIZE FOR UNKNOWN);  -- Plan générique, pas de Parameter Sniffing
END;
```

**Ce que ça fait :**
- SQL Server ignore la valeur du paramètre
- Il crée un plan **générique** basé sur les statistiques globales (moyenne)
- Pas de Parameter Sniffing du tout

**Avantages :**
- ✅ Performance prévisible
- ✅ Pas de surprise selon la première exécution
- ✅ Plan mis en cache réutilisable

**Inconvénients :**
- ❌ Peut ne pas être optimal pour aucune valeur spécifique
- ❌ Compromis "moyen" plutôt qu'optimisation ciblée

**Quand l'utiliser :**
- Distributions très variables
- Aucune valeur n'est vraiment dominante
- Performance "acceptable partout" préférable à "excellent parfois, terrible parfois"

### Solution 4 : Variables locales (Désactiver le Sniffing)

```sql
CREATE PROCEDURE GetProduitsByCategorie
    @Categorie VARCHAR(50)
AS
BEGIN
    -- Copier le paramètre dans une variable locale
    DECLARE @CategorieLocal VARCHAR(50);
    SET @CategorieLocal = @Categorie;

    SELECT *
    FROM Produits
    WHERE Categorie = @CategorieLocal;  -- Variable locale, pas de Sniffing
END;
```

**Ce que ça fait :**
- SQL Server ne peut pas "sniffer" les variables locales
- Il crée un plan générique (comme OPTIMIZE FOR UNKNOWN)

**Avantages :**
- ✅ Évite le Parameter Sniffing
- ✅ Simple à mettre en œuvre
- ✅ Performance prévisible

**Inconvénients :**
- ❌ Perd l'optimisation potentielle du Sniffing
- ❌ Estimations génériques (moins précises)

**Note :** Cette technique était populaire dans les anciennes versions de SQL Server. OPTIMIZE FOR UNKNOWN est maintenant préférable.

### Solution 5 : Procédures multiples (Séparer les cas)

```sql
-- Pour les catégories rares (< 5%)
CREATE PROCEDURE GetProduitsByCategorie_Rare
    @Categorie VARCHAR(50)
AS
BEGIN
    SELECT *
    FROM Produits
    WHERE Categorie = @Categorie
    OPTION (OPTIMIZE FOR (@Categorie = 'Sports'));
END;

-- Pour les catégories fréquentes (> 50%)
CREATE PROCEDURE GetProduitsByCategorie_Frequent
    @Categorie VARCHAR(50)
AS
BEGIN
    SELECT *
    FROM Produits
    WHERE Categorie = @Categorie
    OPTION (OPTIMIZE FOR (@Categorie = 'Électronique'));
END;

-- Logique d'application choisit la bonne procédure
```

**Avantages :**
- ✅ Chaque plan est optimal pour son cas d'usage
- ✅ Performance maximale

**Inconvénients :**
- ❌ Code dupliqué
- ❌ Maintenance plus complexe
- ❌ Logique métier dans l'application

**Quand l'utiliser :**
- Différence de performance énorme entre les cas
- Quelques catégories bien identifiées
- Application peut gérer la logique de sélection

### Solution 6 : Requêtes dynamiques avec sp_executesql

```sql
CREATE PROCEDURE GetProduitsByCategorie
    @Categorie VARCHAR(50)
AS
BEGIN
    DECLARE @SQL NVARCHAR(MAX);

    SET @SQL = N'
        SELECT *
        FROM Produits
        WHERE Categorie = @Categorie';

    EXEC sp_executesql @SQL,
                       N'@Categorie VARCHAR(50)',
                       @Categorie = @Categorie;
END;
```

**Ce que ça fait :**
- Chaque valeur unique de @Categorie crée son propre plan en cache
- 'Sports' a son plan, 'Électronique' a son plan, etc.

**Avantages :**
- ✅ Plan optimal pour chaque valeur
- ✅ Plans en cache pour les valeurs fréquentes

**Inconvénients :**
- ❌ Beaucoup de plans en cache (consommation mémoire)
- ❌ Overhead de SQL dynamique
- ❌ Plus complexe à maintenir

**Quand l'utiliser :**
- Nombre limité de valeurs distinctes possibles
- Chaque valeur est suffisamment fréquente pour justifier son propre plan

|----------|---------------|-------------|------------|-------|
| **RECOMPILE** | ✅✅✅ Excellent | ✅✅✅ Optimal | ✅✅✅ Simple | Requêtes peu fréquentes |
| **OPTIMIZE FOR** | ✅✅ Bon | ✅✅ Bon pour valeur cible | ✅✅ Simple | 1 valeur dominante |
| **OPTIMIZE FOR UNKNOWN** | ✅✅✅ Excellent | ✅ Moyen partout | ✅✅✅ Simple | Distributions variables |
| **Variables locales** | ✅✅ Bon | ✅ Moyen | ✅✅ Simple | SQL Server ancien |
| **Procédures multiples** | ✅✅✅ Excellent | ✅✅✅ Optimal | ❌ Complexe | Cas bien distincts |
| **SQL dynamique** | ✅✅ Bon | ✅✅✅ Optimal | ❌ Complexe | Valeurs limitées |

## Problème 3 : Corrélation de colonnes non détectée

### Le problème

SQL Server suppose généralement que les colonnes sont **indépendantes**, même quand elles sont **corrélées**.

### Exemple

```sql
-- Table Employés
Total : 100 000 employés

-- Distribution par département :
Ventes : 30 000 (30%)
IT : 20 000 (20%)
RH : 15 000 (15%)
Marketing : 35 000 (35%)

-- Distribution par niveau :
Junior : 40 000 (40%)
Senior : 60 000 (60%)

-- MAIS dans la réalité :
-- IT : 90% Senior, 10% Junior (beaucoup de seniors)
-- Ventes : 30% Senior, 70% Junior (beaucoup de juniors)
-- Corrélation forte entre Département et Niveau !
```

**Requête :**
```sql
SELECT *
FROM Employés
WHERE Departement = 'IT'
  AND Niveau = 'Senior';
```

**Estimation de SQL Server (sans corrélation) :**
```
IT : 20% × Senior : 60% = 12% des employés
Estimation : 12 000 lignes
```

**Réalité (avec corrélation) :**
```
IT ET Senior : 18% des employés (90% de IT)
Réalité : 18 000 lignes
```

Écart de 50% ! Peut causer de mauvais choix de plan.

### Solution

Créer des statistiques multi-colonnes :

```sql
CREATE STATISTICS Stats_Dept_Niveau
ON Employés (Departement, Niveau)
WITH FULLSCAN;
```

Maintenant, SQL Server comprend la corrélation et estime correctement.

## Bonnes pratiques pour éviter les problèmes

### 1. Maintenir les statistiques à jour

```sql
-- Automatique : Laisser activé
AUTO_UPDATE_STATISTICS = ON

-- Manuel : Après gros changements
UPDATE STATISTICS TableCritique WITH SAMPLE 30 PERCENT;
```

### 2. Surveiller les plans d'exécution

```sql
-- Toujours comparer Estimated vs Actual
-- Si ratio > 10, investiguer !
```

### 3. Documenter les colonnes corrélées

```sql
-- Si vous savez que deux colonnes sont corrélées
CREATE STATISTICS Stats_Pays_Ville ON Clients (Pays, Ville);
```

### 4. Utiliser RECOMPILE judicieusement

```sql
-- Pour requêtes avec distributions très variables
... OPTION (RECOMPILE);
```

### 5. Tester avec différentes valeurs

```sql
-- Ne testez pas qu'avec une seule valeur !
-- Testez les extrêmes :
EXEC GetProduits @Categorie = 'Électronique';  -- Fréquent
EXEC GetProduits @Categorie = 'Sports';         -- Rare
```

### 6. Monitorer le cache de plans

```sql
-- Voir quels plans sont en cache
SELECT
    cp.objtype,
    cp.cacheobjtype,
    cp.usecounts,
    SUBSTRING(st.text, 1, 100) AS query_text
FROM sys.dm_exec_cached_plans cp
CROSS APPLY sys.dm_exec_sql_text(cp.plan_handle) st
WHERE st.text LIKE '%GetProduitsByCategorie%'
ORDER BY cp.usecounts DESC;
```

## Cas pratique complet

### La situation

Vous avez une application e-commerce avec une procédure de recherche de produits :

```sql
CREATE PROCEDURE SearchProduits
    @Mot VARCHAR(100),
    @Categorie VARCHAR(50) = NULL
AS
BEGIN
    SELECT *
    FROM Produits
    WHERE (@Categorie IS NULL OR Categorie = @Categorie)
      AND Nom LIKE '%' + @Mot + '%';
END;
```

### Les symptômes

- Parfois la recherche prend 0.5 seconde ✅
- Parfois elle prend 45 secondes ❌
- Aucun pattern clair
- Plaintes des utilisateurs

### Le diagnostic

```sql
-- Afficher le plan d'exécution
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Tester avec différents paramètres
EXEC SearchProduits @Mot = 'USB', @Categorie = 'Électronique';
-- Estimated: 850 000 lignes, Actual: 5 000 lignes
-- Plan: Table Scan, 45 secondes ❌

-- Vider le cache
DBCC FREEPROCCACHE;

EXEC SearchProduits @Mot = 'USB', @Categorie = 'Électronique';
-- Estimated: 5 000 lignes, Actual: 5 000 lignes
-- Plan: Index Seek, 0.5 seconde ✅
```

**Conclusion :** Parameter Sniffing ! Le premier appel a utilisé @Categorie = NULL, créant un plan pour "toutes les catégories".

### La solution

```sql
-- Option 1 : RECOMPILE (simple et efficace)
CREATE PROCEDURE SearchProduits
    @Mot VARCHAR(100),
    @Categorie VARCHAR(50) = NULL
AS
BEGIN
    SELECT *
    FROM Produits
    WHERE (@Categorie IS NULL OR Categorie = @Categorie)
      AND Nom LIKE '%' + @Mot + '%'
    OPTION (RECOMPILE);  -- Plan recréé à chaque fois
END;

-- Option 2 : Branches séparées (plus optimal)
CREATE PROCEDURE SearchProduits
    @Mot VARCHAR(100),
    @Categorie VARCHAR(50) = NULL
AS
BEGIN
    IF @Categorie IS NULL
    BEGIN
        -- Plan spécifique pour recherche globale
        SELECT *
        FROM Produits
        WHERE Nom LIKE '%' + @Mot + '%';
    END
    ELSE
    BEGIN
        -- Plan spécifique pour recherche par catégorie
        SELECT *
        FROM Produits
        WHERE Categorie = @Categorie
          AND Nom LIKE '%' + @Mot + '%';
    END
END;
```

### Le résultat

- Performance prévisible ✅
- Toujours entre 0.3 et 1 seconde
- Utilisateurs satisfaits
- Problème résolu !

## Conclusion

Les problèmes de statistiques obsolètes, et particulièrement le Parameter Sniffing, sont parmi les problèmes de performance les plus frustrants et difficiles à diagnostiquer en SQL Server.

### Points clés à retenir

**Statistiques obsolètes :**
- Causent des estimations incorrectes
- Mènent à de mauvais choix de plans
- Se résolvent par UPDATE STATISTICS

**Parameter Sniffing :**
- Fonctionnalité qui peut devenir problématique
- Plan créé pour la première valeur, réutilisé pour toutes
- Cause des performances inconsistantes

**Solutions disponibles :**
- **RECOMPILE** : Simple, toujours optimal, overhead de compilation
- **OPTIMIZE FOR** : Bon pour une valeur dominante
- **OPTIMIZE FOR UNKNOWN** : Performance prévisible, compromis moyen
- **Procédures multiples** : Optimal mais complexe
- **SQL dynamique** : Flexible mais maintenance difficile

**Diagnostic :**
- Chercher les écarts Estimated vs Actual
- Tester avec différentes valeurs de paramètres
- Vider le cache et réessayer (DBCC FREEPROCCACHE)
- Analyser les plans d'exécution réels

**Prévention :**
- Maintenir les statistiques à jour
- Créer des statistiques multi-colonnes pour corrélations
- Tester avec des valeurs variées, pas seulement typiques
- Monitorer les performances en production

Le Parameter Sniffing n'est pas toujours un problème — souvent, c'est une optimisation bénéfique. Mais quand il cause des problèmes, savoir le diagnostiquer et le résoudre est une compétence précieuse qui peut transformer des requêtes frustrantes et imprévisibles en requêtes rapides et fiables.

---

**Points à retenir :**
- Les statistiques obsolètes causent de mauvaises estimations et des plans sous-optimaux
- Le Parameter Sniffing crée un plan pour la première valeur, réutilisé pour toutes les autres
- Symptôme principal : performance inconsistante pour la même requête
- RECOMPILE force la recompilation avec la valeur actuelle (simple et efficace)
- OPTIMIZE FOR UNKNOWN crée un plan générique prévisible
- Les statistiques multi-colonnes aident avec les colonnes corrélées
- Surveillez les écarts entre Estimated Rows et Actual Rows dans les plans
- Testez toujours avec des valeurs variées, pas seulement les cas typiques
