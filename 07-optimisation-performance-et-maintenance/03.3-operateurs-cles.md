# 7.3.3 Opérateurs clés (Seek vs Scan, Loop vs Hash vs Merge Join)

## Introduction

Dans un plan d'exécution, certains **opérateurs** reviennent très fréquemment et ont un impact majeur sur les performances de vos requêtes. Comprendre ces opérateurs clés vous permettra d'identifier rapidement les problèmes de performance et de savoir comment les résoudre.

Dans cette section, nous allons étudier deux catégories d'opérateurs essentiels :
1. **Les opérateurs d'accès aux données** : Seek vs Scan (comment SQL Server lit les données)
2. **Les opérateurs de jointure** : Loop vs Hash vs Merge (comment SQL Server combine plusieurs tables)

## Partie 1 : Opérateurs d'accès aux données

Ces opérateurs déterminent **comment** SQL Server récupère les données dans les tables et les index.

### Table Scan (Parcours de table)

#### Qu'est-ce qu'un Table Scan ?

Un **Table Scan** signifie que SQL Server lit **toutes les lignes** de la table, de la première à la dernière, sans exception.

#### Analogie : Chercher dans un dictionnaire

Imaginez que vous cherchez le mot "Zèbre" dans un dictionnaire, mais que vous commencez à la page 1 et que vous lisez **chaque mot de chaque page** jusqu'à tomber sur "Zèbre". C'est exactement ce qu'est un Table Scan !

#### Quand SQL Server utilise-t-il un Table Scan ?

SQL Server fait un Table Scan dans plusieurs situations :
- La table **n'a pas d'index** approprié
- Vous demandez de récupérer **la majorité** des lignes de la table (ex: 80% ou plus)
- La table est **très petite** (quelques dizaines de lignes) - le coût d'utiliser un index ne vaut pas la peine
- Les statistiques sont obsolètes et SQL Server fait un mauvais choix

#### Performance

- ✅ **Acceptable** pour les petites tables (< 1000 lignes)
- ⚠️ **Problématique** pour les tables moyennes (> 10 000 lignes)
- ❌ **Catastrophique** pour les grandes tables (> 1 million de lignes)

#### Icône dans le plan

L'icône ressemble à une **table** avec des lignes horizontales. Vous verrez le nom `Table Scan` ou `Clustered Index Scan` (si la table a un index cluster).

#### Comment l'optimiser ?

La solution principale : **créer un index** sur les colonnes utilisées dans le WHERE, JOIN ou ORDER BY.

---

### Index Scan (Parcours d'index)

#### Qu'est-ce qu'un Index Scan ?

Un **Index Scan** signifie que SQL Server lit **toutes les entrées** d'un index, de la première à la dernière.

#### Différence avec Table Scan

La différence avec un Table Scan est que :
- SQL Server lit l'**index** plutôt que la table elle-même
- L'index est généralement **plus petit** et plus organisé que la table
- Mais SQL Server parcourt quand même **toutes les entrées** de l'index

#### Analogie

C'est comme lire **tout l'index** d'un livre de A à Z au lieu de lire tout le livre. C'est plus rapide, mais vous lisez quand même tout l'index.

#### Quand SQL Server utilise-t-il un Index Scan ?

- Quand vous avez un index, mais que SQL Server doit quand même lire beaucoup de données
- Quand vous utilisez ORDER BY et que l'index peut fournir les données déjà triées
- Quand vous demandez des colonnes qui ne sont pas incluses dans l'index (mais l'index reste utile pour le tri)

#### Performance

- ✅ **Meilleur** qu'un Table Scan (l'index est plus compact)
- ⚠️ **Pas idéal** - On peut souvent faire mieux avec un Index Seek
- Le gain dépend de la taille de l'index vs la taille de la table

---

### Index Seek (Recherche dans l'index)

#### Qu'est-ce qu'un Index Seek ?

Un **Index Seek** est l'opération la plus efficace ! SQL Server utilise l'index pour aller **directement** aux lignes qui correspondent à votre critère, sans lire toutes les données.

#### Analogie : L'index d'un livre

Imaginez que vous cherchez "Zèbre" dans un dictionnaire. Au lieu de lire toutes les pages, vous :
1. Ouvrez le dictionnaire à la section "Z"
2. Trouvez "Zè"
3. Localisez directement "Zèbre"

Vous avez sauté des milliers de mots inutiles ! C'est ça, un Index Seek.

#### Quand SQL Server utilise-t-il un Index Seek ?

SQL Server fait un Index Seek quand :
- Un index approprié **existe** sur les colonnes utilisées dans votre condition
- Vous recherchez un **nombre limité** de lignes (généralement < 20% de la table)
- Votre condition WHERE utilise les colonnes de l'index de manière **efficace** (SARGable - nous y reviendrons)

#### Icône dans le plan

L'icône montre une **flèche pointant vers des données**. Le nom sera `Index Seek` suivi du nom de l'index utilisé.

#### Performance

- ✅✅✅ **Excellent** - C'est ce que vous voulez voir !
- Peut être des milliers de fois plus rapide qu'un Scan sur de grandes tables
- Coût généralement très faible (quelques pourcents)

#### Exemple concret

```sql
-- Table Clients avec un index sur la colonne Ville
SELECT *
FROM Clients
WHERE Ville = 'Paris';
```

Si vous avez un index sur `Ville` :
- **Index Seek** : SQL Server va directement aux entrées "Paris" dans l'index (rapide ⚡)

Si vous n'avez PAS d'index sur `Ville` :
- **Table Scan** : SQL Server lit toutes les lignes pour trouver celles où Ville = 'Paris' (lent 🐌)

---

### Clustered Index Scan vs Clustered Index Seek

#### Petite précision importante

Vous verrez parfois :
- **Clustered Index Scan** au lieu de "Table Scan"
- **Clustered Index Seek** au lieu de "Index Seek"

**Pourquoi ?** Parce que dans SQL Server, les données de la table sont physiquement stockées **dans** l'index cluster (si la table en a un). Donc :
- Lire la table = lire l'index cluster
- `Clustered Index Scan` = Parcours complet de la table
- `Clustered Index Seek` = Recherche ciblée dans la table via l'index cluster

Les principes Scan vs Seek restent les mêmes !

---

### Key Lookup (Recherche de clé)

#### Qu'est-ce qu'un Key Lookup ?

Un **Key Lookup** (aussi appelé RID Lookup) se produit quand :
1. SQL Server fait un **Index Seek** sur un index non-cluster
2. Mais l'index ne contient **pas toutes les colonnes** dont vous avez besoin
3. SQL Server doit alors retourner à la table pour récupérer les colonnes manquantes

#### Analogie

C'est comme regarder l'index d'un livre pour trouver le mot "Zèbre" à la page 1247, mais l'index ne vous dit que le numéro de page. Vous devez alors **aller à la page 1247** pour lire la définition complète. C'est un aller-retour supplémentaire.

#### Icône dans le plan

Vous verrez un `Key Lookup` connecté à un `Index Seek` par un opérateur `Nested Loops`.

#### Performance

- ⚠️ **Acceptable** si peu de lignes sont concernées (quelques dizaines)
- ❌ **Problématique** si beaucoup de lignes nécessitent un Key Lookup (plusieurs milliers)
- Chaque Key Lookup nécessite une lecture supplémentaire sur le disque

#### Comment l'optimiser ?

Ajouter les colonnes manquantes à l'index avec la clause **INCLUDE** :

```sql
CREATE INDEX IX_Clients_Ville
ON Clients(Ville)
INCLUDE (Nom, Prenom, Email);
```

Maintenant, l'index contient toutes les colonnes nécessaires, et le Key Lookup disparaît !

---

### Résumé visuel : Seek vs Scan

| Opérateur | Vitesse | Quand l'utiliser ? | Icône |
|-----------|---------|-------------------|-------|
| **Index Seek** | ⚡⚡⚡ Très rapide | Recherche ciblée, index approprié | Flèche → données |
| **Index Scan** | ⚡ Moyen | Beaucoup de lignes, tri par index | Table avec flèche |
| **Table Scan** | 🐌 Lent | Pas d'index, ou table très petite | Table simple |
| **Key Lookup** | ⚡⚡ Rapide mais... | Index incomplet, peu de lignes | Clé + flèche |

**Règle d'or :** Vous voulez voir des **Index Seek** autant que possible, surtout sur les grandes tables !

## Partie 2 : Opérateurs de jointure

Lorsque votre requête combine plusieurs tables (avec JOIN), SQL Server doit choisir une **stratégie** pour effectuer cette jointure. Il existe trois opérateurs principaux de jointure, chacun adapté à des situations différentes.

### 1. Nested Loops (Boucles imbriquées)

#### Comment ça fonctionne ?

L'opérateur **Nested Loops** est le plus simple conceptuellement :

1. SQL Server prend la **première table** (table externe)
2. Pour **chaque ligne** de cette table, il cherche les lignes correspondantes dans la **deuxième table** (table interne)
3. Il répète ce processus pour toutes les lignes de la première table

#### Analogie : Double boucle

C'est comme deux boucles imbriquées en programmation :

```
POUR chaque client DANS TableClients :
    POUR chaque commande DANS TableCommandes :
        SI commande.ClientID = client.ClientID :
            Retourner la jointure
```

#### Analogie du monde réel

Imaginez que vous avez une **liste de 10 clients** et que vous devez trouver leurs commandes dans un **classeur bien organisé** :
- Vous prenez le client n°1, vous ouvrez directement son dossier de commandes (Index Seek)
- Vous prenez le client n°2, vous ouvrez directement son dossier de commandes (Index Seek)
- Et ainsi de suite...

C'est très efficace si vous avez **peu de clients** et un **classeur bien organisé** (index).

#### Quand SQL Server utilise-t-il Nested Loops ?

SQL Server choisit Nested Loops quand :
- La **première table** (externe) est **petite** (quelques dizaines à quelques milliers de lignes)
- La **deuxième table** (interne) a un **index efficace** sur la clé de jointure
- Il peut faire des **Index Seek** sur la table interne

#### Icône dans le plan

Vous verrez deux flèches qui convergent en une, avec le nom `Nested Loops`.

#### Performance

- ✅✅✅ **Excellent** quand la table externe est petite et qu'il y a un bon index
- ❌❌ **Catastrophique** si la table externe est grande et sans index sur la table interne
- Coût proportionnel à : `Nombre de lignes externe × Coût de recherche dans l'interne`

#### Exemple de bon usage

```sql
-- 10 clients VIP dans une table de 1 million de clients
SELECT c.Nom, co.NumeroCommande
FROM ClientsVIP c           -- Petite table (10 lignes)
INNER JOIN Commandes co     -- Grande table avec index sur ClientID
ON c.ClientID = co.ClientID;
```

Ici, Nested Loops fait 10 Index Seek dans la table Commandes. Très efficace ! ⚡

#### Exemple de mauvais usage

```sql
-- Tous les clients (1 million) sans index
SELECT c.Nom, co.NumeroCommande
FROM Clients c              -- Grande table (1 million)
INNER JOIN Commandes co     -- Grande table SANS index sur ClientID
ON c.ClientID = co.ClientID;
```

Ici, Nested Loops fait 1 million de Table Scan. Catastrophe ! 🔥

---

### 2. Hash Match (Jointure par hachage)

#### Comment ça fonctionne ?

L'opérateur **Hash Match** utilise une technique plus sophistiquée :

1. SQL Server lit la **plus petite table** (table de construction - "build input")
2. Il crée une **table de hachage** en mémoire avec cette table (comme une table d'index temporaire)
3. Il lit la **deuxième table** (table de sondage - "probe input")
4. Pour chaque ligne, il cherche dans la table de hachage s'il y a une correspondance (très rapide)

#### Analogie : Le système de casiers

Imaginez une bibliothèque avec un système de casiers numérotés :

1. Vous prenez tous les livres du rayon A (petite table)
2. Vous les rangez dans des casiers numérotés par catégorie (construction de la table de hachage)
3. Vous prenez les livres du rayon B (grande table)
4. Pour chaque livre, vous regardez son numéro de casier et trouvez instantanément les correspondances

#### Quand SQL Server utilise-t-il Hash Match ?

SQL Server choisit Hash Match quand :
- Les deux tables sont **grandes** (des milliers ou millions de lignes)
- Il n'y a **pas d'index approprié** sur les clés de jointure
- Il n'y a **pas d'ordre de tri** exploitable
- Il a suffisamment de **mémoire** pour construire la table de hachage

#### Icône dans le plan

Vous verrez une icône avec le symbole **#** (dièse) et le nom `Hash Match`.

#### Performance

- ✅✅ **Bon** pour les grandes tables sans index
- ⚠️ **Consomme de la mémoire** pour la table de hachage
- ❌ **Problématique** si pas assez de mémoire (débordement sur disque - "spill to disk")
- Coût proportionnel à : `Taille table 1 + Taille table 2` (une lecture de chaque)

#### Avantages

- Peut traiter de **très grandes tables** efficacement
- Ne nécessite **pas d'index** sur les clés de jointure
- Ne nécessite **pas de tri préalable**

#### Inconvénients

- Nécessite de la mémoire (peut être un problème si tables très grandes)
- Lit **toutes les lignes** des deux tables (pas de possibilité d'optimisation avec des index)

#### Exemple typique

```sql
-- Jointure entre deux grandes tables sans index approprié
SELECT c.Nom, co.NumeroCommande
FROM Clients c              -- 1 million de clients
INNER JOIN Commandes co     -- 5 millions de commandes, SANS index sur ClientID
ON c.ClientID = co.ClientID;
```

SQL Server va probablement choisir Hash Match car :
- Les deux tables sont grandes
- Pas d'index utilisable sur ClientID dans Commandes
- Nested Loops serait catastrophique (1M × 5M opérations)

---

### 3. Merge Join (Jointure par fusion)

#### Comment ça fonctionne ?

L'opérateur **Merge Join** est le plus efficace **quand les données sont déjà triées** :

1. SQL Server prend la **première table** (déjà triée sur la clé de jointure)
2. Il prend la **deuxième table** (déjà triée sur la clé de jointure)
3. Il parcourt les deux tables **en parallèle**, comme une fermeture éclair, en faisant correspondre les valeurs

#### Analogie : Fusion de deux listes triées

Imaginez que vous avez :
- Une liste de **noms de clients** triés alphabétiquement
- Une liste de **commandes** triées par nom de client

Vous pouvez les fusionner très facilement :
1. Vous parcourez les deux listes en même temps
2. Quand les noms correspondent, vous faites la jointure
3. Vous avancez dans les deux listes simultanément

C'est comme une **fermeture éclair** ⚡ : très fluide et rapide !

#### Quand SQL Server utilise-t-il Merge Join ?

SQL Server choisit Merge Join quand :
- Les **deux tables** sont déjà **triées** sur la clé de jointure (grâce à des index ordonnés)
- OU il est rentable de **trier** les tables avant de faire la jointure
- Les deux tables sont de taille **comparable** (ou grandes toutes les deux)

#### Icône dans le plan

Vous verrez deux flèches qui se rejoignent avec le nom `Merge Join`.

#### Performance

- ✅✅✅ **Excellent** si les données sont déjà triées (pas besoin de trier)
- ✅✅ **Très bon** même avec un tri préalable (sur de grandes tables)
- Coût proportionnel à : `Taille table 1 + Taille table 2` (une lecture de chaque)
- Plus efficace que Hash Match car **pas de table de hachage en mémoire**

#### Les pré-requis : Opérateurs de tri

Si les données ne sont pas déjà triées, vous verrez souvent des opérateurs **Sort** avant le Merge Join dans le plan :

```
[Merge Join] ← [Sort] ← [Table A]
               ↑
            [Sort] ← [Table B]
```

Le tri a un coût, mais si les tables sont grandes, c'est souvent rentable.

#### Avantages

- **Très efficace** sur de grandes tables
- Ne nécessite **pas de mémoire** pour une table de hachage
- Bénéficie des **index ordonnés** existants

#### Inconvénients

- Nécessite que les **données soient triées** (coût de tri si pas d'index approprié)
- Si un tri est nécessaire, le gain peut être annulé

#### Exemple typique

```sql
-- Jointure entre deux grandes tables avec index cluster
SELECT c.Nom, co.NumeroCommande
FROM Clients c              -- Index cluster sur ClientID
INNER JOIN Commandes co     -- Index cluster sur ClientID
ON c.ClientID = co.ClientID;
```

Les index cluster garantissent que les deux tables sont déjà triées par ClientID. Merge Join est parfait ici ! ⚡⚡

---

### Comparaison des trois opérateurs de jointure

| Opérateur | Meilleur usage | Condition importante | Performance |
|-----------|----------------|---------------------|-------------|
| **Nested Loops** | Petite table × Grande table avec index | Index sur table interne | ⚡⚡⚡ si conditions OK<br>🐌🐌 sinon |
| **Hash Match** | Grande × Grande, sans index | Mémoire disponible | ⚡⚡ en général<br>⚠️ si manque mémoire |
| **Merge Join** | Grande × Grande, données triées | Données triées (ou index ordonnés) | ⚡⚡⚡ si déjà trié<br>⚡⚡ avec tri |

#### Quelle jointure SQL Server choisit-il ?

SQL Server fait ce choix **automatiquement** en fonction de :
- La taille des tables
- La présence d'index appropriés
- La mémoire disponible
- Les statistiques sur les données

Votre rôle en tant que développeur est de :
1. **Identifier** quel opérateur est utilisé dans le plan
2. **Comprendre** pourquoi SQL Server a fait ce choix
3. **Optimiser** si nécessaire (créer des index, réécrire la requête, etc.)

## Comment identifier ces opérateurs dans un plan ?

### Accès aux données

Cherchez les icônes représentant des **tables** ou des **index** :
- **Table avec lignes horizontales** → Table Scan ou Clustered Index Scan
- **Flèche vers données** → Index Seek ou Clustered Index Seek
- **Clé avec flèche** → Key Lookup (ou RID Lookup)

### Jointures

Cherchez les icônes où **deux flèches convergent** :
- **Deux flèches simples** → Nested Loops
- **Symbole #** → Hash Match
- **Deux flèches parallèles fusionnant** → Merge Join

### Vérifier les détails

Survolez l'opérateur avec la souris ou consultez les propriétés pour voir :
- Le **type exact** de l'opérateur
- Le **nombre de lignes** traitées
- Les **tables ou index** utilisés
- Le **coût** de l'opération

## Cas d'études et diagnostics

### Cas 1 : Table Scan coûteux

**Symptôme :** Vous voyez un `Table Scan` représentant 80% du coût total.

**Diagnostic :** Pas d'index approprié.

**Solution :** Créer un index sur les colonnes utilisées dans WHERE ou JOIN :
```sql
CREATE INDEX IX_Clients_Ville ON Clients(Ville);
```

---

### Cas 2 : Nested Loops avec coût élevé

**Symptôme :** Vous voyez un `Nested Loops` avec un coût > 50%, et la table interne montre un `Table Scan`.

**Diagnostic :** Pas d'index sur la clé de jointure de la table interne.

**Solution :** Créer un index sur la clé de jointure :
```sql
CREATE INDEX IX_Commandes_ClientID ON Commandes(ClientID);
```

---

### Cas 3 : Hash Match avec avertissement de mémoire

**Symptôme :** Vous voyez un `Hash Match` avec un triangle jaune (⚠️) indiquant un "Spill to disk".

**Diagnostic :** Pas assez de mémoire pour la table de hachage, SQL Server a dû écrire sur le disque (très lent).

**Solutions possibles :**
- Ajouter un index pour permettre un Merge Join ou Nested Loops
- Optimiser la requête pour réduire le nombre de lignes traitées
- Augmenter la mémoire disponible (solution d'infrastructure)

---

### Cas 4 : Merge Join avec Sort coûteux

**Symptôme :** Vous voyez un `Merge Join` précédé de deux opérateurs `Sort` représentant 60% du coût total.

**Diagnostic :** Les données ne sont pas triées, SQL Server doit les trier avant la jointure.

**Solution :** Créer des index ordonnés sur les clés de jointure :
```sql
CREATE INDEX IX_Clients_ClientID ON Clients(ClientID);
CREATE INDEX IX_Commandes_ClientID ON Commandes(ClientID);
```

---

### Cas 5 : Key Lookup en cascade

**Symptôme :** Vous voyez un `Index Seek` suivi d'un `Key Lookup`, et ce pattern se répète des milliers de fois.

**Diagnostic :** L'index utilisé ne contient pas toutes les colonnes nécessaires.

**Solution :** Ajouter les colonnes manquantes à l'index avec INCLUDE :
```sql
CREATE INDEX IX_Clients_Ville
ON Clients(Ville)
INCLUDE (Nom, Prenom, Email, Telephone);
```

---

## Stratégies d'optimisation générales

### Pour les accès aux données

1. **Évitez les Table Scan** sur les grandes tables
   - Créez des index sur les colonnes de filtrage (WHERE)
   - Créez des index sur les colonnes de jointure (JOIN)
   - Créez des index sur les colonnes de tri (ORDER BY)

2. **Privilégiez les Index Seek**
   - Assurez-vous que vos index couvrent les conditions de recherche
   - Utilisez des prédicats SARGable (pas de fonctions dans WHERE)

3. **Éliminez les Key Lookup coûteux**
   - Utilisez la clause INCLUDE pour ajouter les colonnes fréquemment consultées

### Pour les jointures

1. **Nested Loops** : Assurez-vous qu'il y a un index sur la table interne
2. **Hash Match** : Acceptable si tables grandes sans index, mais vérifiez la mémoire
3. **Merge Join** : Créez des index ordonnés sur les clés de jointure

### Règle générale

**"Le meilleur opérateur est celui que SQL Server choisit naturellement quand vous avez les bons index"**

Votre travail n'est pas de forcer SQL Server à utiliser un opérateur spécifique, mais de lui donner les outils (index) pour faire le meilleur choix.

---

## Conclusion

Les opérateurs d'accès aux données et de jointure sont au cœur de la performance de vos requêtes. En comprenant comment ils fonctionnent et quand ils sont utilisés, vous pouvez :

1. **Diagnostiquer** rapidement les problèmes de performance en regardant les plans d'exécution
2. **Créer les bons index** pour permettre à SQL Server de choisir les opérateurs les plus efficaces
3. **Comprendre** les compromis entre différentes stratégies

**Récapitulatif des opérateurs :**

**Accès aux données :**
- ⚡⚡⚡ **Index Seek** → Idéal
- ⚡ **Index Scan** → Acceptable
- 🐌 **Table Scan** → Problématique sur grandes tables
- ⚡⚡ **Key Lookup** → OK si peu de lignes

**Jointures :**
- **Nested Loops** → Parfait pour petite × grande avec index
- **Hash Match** → Bon pour grande × grande sans index
- **Merge Join** → Excellent pour grande × grande avec données triées

Avec cette connaissance, vous êtes maintenant équipé pour analyser efficacement les plans d'exécution et identifier les opportunités d'optimisation !

---

**Points à retenir :**
- Index Seek est presque toujours préférable à un Scan pour les grandes tables
- Le choix de l'opérateur de jointure dépend de la taille des tables et des index disponibles
- Les index appropriés permettent à SQL Server de choisir automatiquement les meilleurs opérateurs
- Surveillez les avertissements (triangles jaunes) dans les plans d'exécution
- Un Key Lookup répété des milliers de fois peut être éliminé avec un index INCLUDE
