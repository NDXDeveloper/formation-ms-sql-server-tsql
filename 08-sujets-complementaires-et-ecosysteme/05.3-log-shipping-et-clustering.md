# 8.5.3 Log Shipping et Clustering (Aperçu conceptuel)

## Introduction

Nous avons vu les Groupes de disponibilité AlwaysOn dans les sections précédentes. Cependant, SQL Server offre d'autres technologies de haute disponibilité et de reprise après sinistre qui ont été introduites **avant** AlwaysOn. Ces technologies continuent d'être utilisées aujourd'hui, soit par nécessité (contraintes de licence, compatibilité), soit parce qu'elles correspondent mieux à certains besoins spécifiques.

Cette section présente deux technologies importantes :
- **Log Shipping** (envoi de journaux)
- **Failover Clustering** (cluster de basculement)

## 1. Log Shipping (Envoi de journaux)

### Qu'est-ce que le Log Shipping ?

Le **Log Shipping** est une technique de haute disponibilité basée sur la **copie et la restauration automatique des sauvegardes** du journal de transactions d'une base de données.

### Analogie simple

Imaginez que vous tenez un journal intime :
- Chaque soir, vous écrivez les événements de la journée dans votre journal
- Vous faites une photocopie de ces pages
- Vous envoyez la photocopie à un coffre-fort dans une autre ville
- Quelqu'un là-bas colle les pages dans une copie de votre journal

Si votre journal original est détruit, la copie dans l'autre ville peut reprendre le relais (avec peut-être juste la dernière journée manquante).

C'est exactement le principe du Log Shipping avec les bases de données.

### Architecture et fonctionnement

#### Les trois rôles

```
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│  [Serveur Primaire]                                            │
│  ┌──────────────────┐                                          │
│  │ Base de données  │                                          │
│  │    PRODUCTION    │                                          │
│  │                  │                                          │
│  │  Transactions    │                                          │
│  │  en cours...     │                                          │
│  └────────┬─────────┘                                          │
│           │                                                    │
│           │ 1. Sauvegarde du journal toutes les X minutes      │
│           ↓                                                    │
│  ┌──────────────────┐                                          │
│  │  Fichiers .TRN   │ ──────┐                                  │
│  │  (Transaction    │       │                                  │
│  │   Log Backup)    │       │ 2. Copie vers le secondaire      │
│  └──────────────────┘       │                                  │
└─────────────────────────────┼──────────────────────────────────┘
                              │
                              │ Réseau / Partage de fichiers
                              │
┌─────────────────────────────┼──────────────────────────────────┐
│                             ↓                                  │
│  [Serveur Secondaire]                                          │
│  ┌──────────────────┐                                          │
│  │  Fichiers .TRN   │                                          │
│  │    copiés        │                                          │
│  └────────┬─────────┘                                          │
│           │                                                    │
│           │ 3. Restauration des journaux                       │
│           ↓                                                    │
│  ┌──────────────────┐                                          │
│  │ Base de données  │                                          │
│  │   SECONDAIRE     │                                          │
│  │                  │                                          │
│  │ (En mode         │                                          │
│  │  RECOVERING      │                                          │
│  │  ou STANDBY)     │                                          │
│  └──────────────────┘                                          │
│                                                                │
└────────────────────────────────────────────────────────────────┘

Optionnel : [Serveur Monitor] - Surveille le processus et génère des alertes
```

#### Le processus en détail

**1. Sauvegarde (Backup Job) - Sur le serveur primaire**
- Un travail SQL Agent s'exécute à intervalle régulier (ex: toutes les 15 minutes)
- Il crée une sauvegarde du journal de transactions (.TRN)
- Le fichier est placé dans un dossier partagé accessible au secondaire

```sql
-- Exemple de sauvegarde du journal
BACKUP LOG [Ventes]
TO DISK = '\\ServeurPartage\Backups\Ventes_Log_20241119_1400.trn'
WITH COMPRESSION;
```

**2. Copie (Copy Job) - Sur le serveur secondaire**
- Un autre travail SQL Agent s'exécute à intervalle régulier (ex: toutes les 5 minutes après la sauvegarde)
- Il copie les fichiers .TRN du dossier partagé vers un dossier local sur le secondaire

**3. Restauration (Restore Job) - Sur le serveur secondaire**
- Un troisième travail SQL Agent s'exécute à intervalle régulier (ex: toutes les 5 minutes après la copie)
- Il restaure les fichiers .TRN dans la base de données secondaire
- La base secondaire reste en état RECOVERING (ou STANDBY)

```sql
-- Exemple de restauration du journal
RESTORE LOG [Ventes]
FROM DISK = 'C:\Backups\Ventes_Log_20241119_1400.trn'
WITH NORECOVERY;  -- Ou WITH STANDBY
```

### Modes de restauration

#### Mode NORECOVERY (RECOVERING)
- La base de données secondaire est **inaccessible**
- Elle reste en attente de la prochaine restauration de journal
- **Avantage** : Restaurations plus rapides
- **Inconvénient** : Impossible de faire des lectures

#### Mode STANDBY
- La base de données secondaire est **accessible en lecture seule**
- Entre les restaurations, les utilisateurs peuvent exécuter des SELECT
- Pendant la restauration, les connexions sont interrompues
- **Avantage** : Peut servir pour des rapports
- **Inconvénient** : Restaurations légèrement plus lentes

### Délai de réplication (Latency)

Contrairement à AlwaysOn qui synchronise en temps quasi-réel, Log Shipping a un **délai inhérent** :

```
t=0    : Transaction validée sur le primaire
t=15   : Sauvegarde du journal (toutes les 15 minutes)
t=20   : Copie terminée (5 minutes après)
t=25   : Restauration terminée (5 minutes après)

➡️ Latency totale : 25 minutes
```

Ce délai signifie :
- En cas de basculement, vous pouvez **perdre jusqu'à 25 minutes de données** (selon votre configuration)
- Le secondaire est toujours "en retard" de X minutes

### Basculement avec Log Shipping

Le basculement est **TOUJOURS MANUEL** avec Log Shipping.

**Processus de basculement :**

1. **Sur le primaire (s'il est encore accessible) :**
   ```sql
   -- Faire une dernière sauvegarde du journal
   BACKUP LOG [Ventes]
   TO DISK = '\\Partage\Backups\Ventes_Log_Final.trn'
   WITH NORECOVERY;
   ```

2. **Sur le secondaire :**
   ```sql
   -- Copier et restaurer toutes les sauvegardes restantes
   RESTORE LOG [Ventes]
   FROM DISK = 'C:\Backups\Ventes_Log_Final.trn'
   WITH NORECOVERY;

   -- Restaurer la base en mode accessible (RECOVERY)
   RESTORE DATABASE [Ventes] WITH RECOVERY;

   -- La base est maintenant en lecture/écriture
   ```

3. **Reconfigurer les applications :**
   - Modifier les chaînes de connexion pour pointer vers le nouveau serveur
   - Redémarrer les applications

**Durée typique du basculement :** 15-30 minutes (principalement manuel)

### Avantages du Log Shipping

| Avantage | Explication |
|----------|-------------|
| **Simplicité** | Technologie simple basée sur sauvegardes/restaurations |
| **Pas de matériel spécifique** | Fonctionne sur n'importe quel serveur SQL |
| **Peu coûteux** | Disponible dans les éditions Web, Standard et Enterprise (mais **pas** Express, qui ne fournit pas SQL Server Agent) |
| **Plusieurs secondaires** | Vous pouvez avoir autant de serveurs secondaires que vous voulez |
| **Distance illimitée** | Fonctionne même avec une connexion lente ou intermittente |
| **Moins de risque de corruption** | Si le primaire est corrompu, le secondaire peut ne pas l'être (délai de propagation) |

### Inconvénients du Log Shipping

| Inconvénient | Explication |
|--------------|-------------|
| **Basculement manuel uniquement** | Aucun basculement automatique possible |
| **Perte de données possible** | Dépend de la fréquence des sauvegardes (RPO > 0) |
| **Temps de basculement long** | Processus manuel (15-30 minutes) |
| **Complexité de gestion** | Nécessite de surveiller 3 jobs différents |
| **Mode SIMPLE incompatible** | La base doit être en mode de récupération FULL ou BULK_LOGGED |
| **Niveau base de données** | Chaque base doit être configurée séparément |

### Cas d'usage du Log Shipping

**Quand utiliser Log Shipping :**

1. **Budget limité**
   - Vous ne pouvez pas acheter Enterprise Edition
   - L'édition Standard (ou Web) suffit

2. **Reprise après sinistre géographique**
   - Secondaire dans un datacenter distant
   - Connexion réseau lente ou intermittente acceptable

3. **Besoin de plusieurs copies**
   - Vous voulez 5 serveurs secondaires pour différents usages

4. **Reporting différé**
   - Vous avez besoin d'une copie décalée de quelques heures pour des rapports historiques

5. **Protection contre les corruptions logiques**
   - Le délai offre une "fenêtre" pour détecter les erreurs avant propagation

**Exemple concret :**
Une PME avec SQL Server Standard Edition qui veut protéger sa base de données en envoyant des copies vers un datacenter distant à 500 km, avec un RTO (temps de reprise) acceptable de 30 minutes et un RPO (perte de données) acceptable de 15 minutes.

## 2. Failover Clustering (Cluster de basculement)

### Qu'est-ce qu'un Cluster de basculement ?

Le **Failover Clustering** est une technologie de haute disponibilité où **plusieurs serveurs (nœuds) partagent le même stockage** et peuvent prendre le relais instantanément en cas de panne.

### Analogie simple

Imaginez deux gardiens de sécurité surveillant la même porte :
- Un seul gardien est actif à la fois (celui qui a les clés)
- L'autre attend en veille
- Si le gardien actif s'évanouit, l'autre prend immédiatement les clés et continue le travail
- Les visiteurs ne remarquent presque rien car c'est la **même porte** (même stockage)

### Architecture et fonctionnement

#### Composants clés

```
┌──────────────────────────────────────────────────────────────────┐
│                    Cluster de basculement                        │
│                                                                  │
│  ┌────────────────┐                    ┌────────────────┐        │
│  │   Nœud 1       │                    │   Nœud 2       │        │
│  │  (ACTIF)       │◄──────────────────►│  (PASSIF)      │        │
│  │                │   Heartbeat /      │                │        │
│  │ SQL Server     │   Vérification     │ SQL Server     │        │
│  │ Instance       │                    │ Instance       │        │
│  └────────┬───────┘                    └────────┬───────┘        │
│           │                                     │                │
│           │    ┌──────────────────────────┐     │                │
│           └───►│  Stockage partagé (SAN)  │◄────┘                │
│                │                          │                      │
│                │  ┌────────────────────┐  │                      │
│                │  │ Fichiers de données│  │                      │
│                │  │ (.MDF, .LDF)       │  │                      │
│                │  └────────────────────┘  │                      │
│                └──────────────────────────┘                      │
│                                                                  │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │              IP Virtuelle / Nom de cluster                  │ │
│  │              SQLCLUSTER\INSTANCE1                           │ │
│  └─────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
                             ▲
                             │
                             │ Les applications se connectent ici
                             │
                      ┌──────┴───────┐
                      │ Applications │
                      └──────────────┘
```

#### Principe de fonctionnement

**1. État normal**
- Un seul nœud est actif (possède les ressources)
- Cet instance SQL Server a accès au stockage partagé
- Les autres nœuds sont en veille (passifs)
- Le cluster surveille la santé du nœud actif via "heartbeat" (battement de cœur)

**2. Détection de panne**
- Le nœud actif ne répond plus (panne matérielle, crash)
- Le cluster détecte l'absence de heartbeat
- Un vote automatique détermine quel nœud passif devient actif

**3. Basculement automatique**
- Le nœud passif prend le contrôle du stockage partagé
- L'instance SQL Server démarre sur le nouveau nœud
- Les fichiers de base de données sont déjà là (stockage partagé)
- L'IP virtuelle et le nom basculent vers le nouveau nœud
- **Aucune perte de données** : même fichiers de données

**4. Reconnexion des applications**
- Les applications utilisent le nom du cluster (ex: `SQLCLUSTER\INSTANCE1`)
- Ce nom pointe toujours vers le nœud actif
- Après le basculement, les connexions se reconnectent automatiquement

### Caractéristiques importantes

#### Stockage partagé obligatoire

C'est la **différence fondamentale** avec AlwaysOn :
- **Cluster** : Un seul ensemble de fichiers de base de données partagé entre les nœuds
- **AlwaysOn** : Chaque nœud a sa propre copie des fichiers

Le stockage partagé peut être :
- **SAN** (Storage Area Network) : Stockage réseau haute performance
- **SMB 3.0** : Partage de fichiers Windows avancé
- **Espaces de stockage direct** (Storage Spaces Direct) : Stockage défini par logiciel

#### Un seul nœud actif à la fois

Contrairement à AlwaysOn où plusieurs réplicas peuvent servir des lectures, **un seul nœud dans le cluster peut utiliser les bases de données à un moment donné**. Les autres nœuds sont complètement passifs.

#### Basculement rapide

Le basculement est très rapide car il n'y a pas de copie de données :

```
t=0    : Le nœud actif plante
t=5s   : Détection de la panne (absence de heartbeat)
t=10s  : Vote et élection du nouveau nœud actif
t=30s  : Démarrage de l'instance SQL Server sur le nouveau nœud
t=45s  : Récupération des bases de données (REDO des transactions)
t=60s  : Système opérationnel

➡️ Durée typique : 30 secondes à 2 minutes
```

#### Zéro perte de données

Puisque les fichiers de base de données sont partagés et qu'aucune réplication n'est nécessaire, **il n'y a aucune perte de données** (RPO = 0).

### Basculement et retour arrière

#### Basculement automatique
Le basculement est automatique en cas de :
- Panne matérielle du nœud actif
- Crash de l'instance SQL Server
- Perte de connectivité réseau du nœud actif

#### Basculement manuel (planifié)
Un administrateur peut également forcer un basculement pour :
- Maintenance planifiée
- Mise à jour de Windows ou SQL Server
- Test de la haute disponibilité

```powershell
# Commande PowerShell pour basculer manuellement
Move-ClusterGroup -Name "SQL Server (INSTANCE1)" -Node "Noeud2"
```

#### Retour arrière (Failback)
Après avoir résolu le problème sur le nœud d'origine, vous pouvez le remettre en production :
```powershell
Move-ClusterGroup -Name "SQL Server (INSTANCE1)" -Node "Noeud1"
```

### Avantages du Failover Clustering

| Avantage | Explication |
|----------|-------------|
| **Aucune perte de données** | RPO = 0 (même stockage) |
| **Basculement automatique** | Pas d'intervention humaine nécessaire |
| **Basculement rapide** | 30 secondes à 2 minutes (RTO faible) |
| **Transparence applicative** | Les applications se reconnectent automatiquement au nom du cluster |
| **Protection au niveau instance** | Toutes les bases de données basculent ensemble |
| **Disponible dans Standard Edition** | Oui, limité à 2 nœuds — et ce, depuis bien avant SQL Server 2016 |

### Inconvénients du Failover Clustering

| Inconvénient | Explication |
|--------------|-------------|
| **Coût du stockage partagé** | SAN ou infrastructure similaire onéreuse |
| **Complexité d'infrastructure** | Configuration Windows Clustering requise |
| **Pas de reprise après sinistre** | Tous les nœuds doivent être proches (même datacenter généralement) |
| **Point de défaillance unique** | Le stockage partagé est un SPOF (Single Point Of Failure) |
| **Pas de lecture sur secondaire** | Les nœuds passifs ne servent à rien (gaspillage de ressources) |
| **Nécessite Windows Server** | Pas disponible sur Linux (alternatives: Pacemaker, mais différent) |

### Cas d'usage du Failover Clustering

**Quand utiliser un Cluster de basculement :**

1. **Haute disponibilité locale**
   - Protection contre les pannes matérielles dans le même datacenter
   - RTO très faible requis (< 2 minutes)

2. **Pas de perte de données acceptable**
   - RPO = 0 obligatoire
   - Budget pour stockage partagé disponible

3. **Migration simplifiée**
   - Basculer facilement pour maintenance sans temps d'arrêt

4. **Toutes les bases doivent basculer ensemble**
   - Applications avec plusieurs bases interdépendantes

5. **Besoin de protéger tout le serveur**
   - Jobs SQL Agent, Linked Servers, etc. basculent automatiquement

**Exemple concret :**
Une application financière critique dans un datacenter avec un SAN existant, nécessitant zéro perte de données et un temps de reprise de moins de 2 minutes pour se conformer aux exigences réglementaires.

## 3. Comparaison des technologies HA/DR

### Tableau comparatif

| Critère | AlwaysOn AG | Log Shipping | Failover Clustering |
|---------|-------------|--------------|---------------------|
| **Perte de données (RPO)** | 0 (synchrone) ou quelques secondes (asynchrone) | Minutes à heures | 0 |
| **Temps de basculement (RTO)** | 30s-2min (auto) ou manuel | 15-30 min (manuel) | 30s-2min (auto) |
| **Basculement automatique** | Oui (si synchrone) | Non | Oui |
| **Lecture sur secondaire** | Oui | Oui (mode STANDBY) | Non |
| **Nombre de secondaires** | Jusqu'à 8 | Illimité | Dépend du cluster (généralement 2-4) |
| **Édition SQL Server** | Enterprise (ou Standard limité) | Web, Standard, Enterprise (pas Express) | Standard et Enterprise |
| **Stockage partagé requis** | Non | Non | Oui |
| **Distance géographique** | Possible (asynchrone) | Excellente | Limitée (même datacenter généralement) |
| **Niveau de protection** | Base de données | Base de données | Instance (toutes les bases) |
| **Complexité** | Élevée | Moyenne | Élevée |
| **Coût** | Élevé (licence) | Faible | Élevé (infrastructure) |

### Schéma de décision

```
┌─────────────────────────────────────────────────────────────────┐
│         Besoin de Haute Disponibilité (HA) ou                   │
│         Reprise après Sinistre (DR) ?                           │
└────────────────────────┬────────────────────────────────────────┘
                         │
         ┌───────────────┴───────────────┐
         │                               │
    HA (Local)                      DR (Distant)
         │                               │
         │                               │
    ┌────▼─────┐                   ┌─────▼────┐
    │ Budget   │                   │ RPO ?    │
    │ pour SAN?│                   │          │
    └────┬─────┘                   └─────┬────┘
         │                               │
    ┌────┴────┐                    ┌─────┴──────┐
    │         │                    │            │
   Oui       Non                  0        >15 minutes
    │         │                    │            │
    ▼         ▼                    ▼            ▼
Failover   AlwaysOn          AlwaysOn          Log
Cluster      AG              AG (async)        Shipping
```

### Combinaisons possibles

Ces technologies peuvent être **combinées** pour une protection maximale :

#### Exemple 1 : Cluster + Log Shipping
```
┌──────────────────────────────────┐
│  Datacenter Paris                │
│  ┌────────────────────────────┐  │
│  │  Failover Cluster          │  │
│  │  (HA locale)               │  │
│  │                            │  │
│  │  Nœud1 ◄─► Nœud2           │  │
│  │     │         │            │  │
│  │     └────┬────┘            │  │
│  │         SAN                │  │
│  └──────────┬─────────────────┘  │
└─────────────┼────────────────────┘
              │ Log Shipping
              │ (DR distant)
              ↓
┌─────────────┴────────────────────┐
│  Datacenter Lyon                 │
│  ┌────────────────────────────┐  │
│  │  Serveur Standalone        │  │
│  │  (Secondaire Log Shipping) │  │
│  └────────────────────────────┘  │
└──────────────────────────────────┘
```

**Bénéfices :**
- HA locale avec basculement rapide (Cluster)
- DR distant en cas de catastrophe majeure (Log Shipping)

```

          │

```

**Bénéfices :**
- HA locale avec zéro perte de données (synchrone)
- DR distant avec perte minimale (asynchrone)
- Déchargement de lecture possible sur les secondaires

## 4. Terminologie récapitulative

| Terme | Définition |
|-------|------------|
| **Log Shipping** | Technique basée sur la copie et restauration automatique des journaux de transactions |
| **Failover Clustering** | Plusieurs serveurs partageant le même stockage, un seul actif à la fois |
| **SAN (Storage Area Network)** | Réseau de stockage haute performance partagé entre serveurs |
| **Heartbeat** | Signal envoyé régulièrement pour vérifier qu'un nœud est vivant |
| **Nœud** | Un serveur individuel dans un cluster |
| **SPOF (Single Point Of Failure)** | Point de défaillance unique qui peut faire tomber tout le système |
| **RPO (Recovery Point Objective)** | Perte de données maximale acceptable |
| **RTO (Recovery Time Objective)** | Temps d'indisponibilité maximal acceptable |
| **HA (High Availability)** | Haute disponibilité - minimiser les temps d'arrêt |
| **DR (Disaster Recovery)** | Reprise après sinistre - protéger contre les catastrophes majeures |

## 5. Évolution historique des technologies

Pour comprendre pourquoi ces technologies coexistent, voici un aperçu historique :

```
SQL Server 7.0 (1998)
  └─> Log Shipping introduit (basique)

SQL Server 2000 (2000)
  └─> Failover Clustering amélioré

SQL Server 2005 (2005)
  └─> Database Mirroring introduit (prédécesseur d'AlwaysOn)

SQL Server 2008/2008 R2 (2008-2010)
  └─> Améliorations du Mirroring

SQL Server 2012 (2012) ★
  └─> AlwaysOn Availability Groups introduit
      (révolution de la haute disponibilité)

SQL Server 2016 (2016)
  └─> Basic Availability Groups disponibles dans Standard Edition
      (le Failover Clustering est, lui, présent dans Standard —
       limité à 2 nœuds — depuis bien plus longtemps)

SQL Server 2017 (2017)
  └─> AlwaysOn sur Linux (sans WSFC)

SQL Server 2019+ (2019-présent)
  └─> Améliorations continues, support Kubernetes
```

**Pourquoi les anciennes technologies restent pertinentes :**
- **Coût** : Log Shipping fonctionne avec les éditions Web, Standard et Enterprise
- **Simplicité** : Plus facile à comprendre et maintenir pour certaines équipes
- **Infrastructure existante** : Entreprises ayant déjà investi dans un SAN pour le clustering
- **Compatibilité** : Certaines versions/éditions ne supportent pas AlwaysOn

## Conclusion

Le choix de la technologie de haute disponibilité dépend de nombreux facteurs :

### Choisir **Log Shipping** si :
- ✅ Budget limité (Standard ou Web Edition)
- ✅ Tolérance à une perte de données de plusieurs minutes
- ✅ Basculement manuel acceptable
- ✅ Besoin de plusieurs copies de la base
- ✅ Distances géographiques importantes avec connexion limitée

### Choisir **Failover Clustering** si :
- ✅ Infrastructure SAN déjà en place
- ✅ Besoin de RPO = 0 (aucune perte)
- ✅ RTO très faible requis (< 2 minutes)
- ✅ Basculement automatique nécessaire
- ✅ HA locale uniquement (même datacenter)

### Choisir **AlwaysOn AG** si :
- ✅ Budget pour Enterprise Edition (ou Standard avec limitations)
- ✅ Besoin de lecture sur secondaires
- ✅ RPO très faible (0 en synchrone)
- ✅ Flexibilité (HA + DR combinés)
- ✅ Solution moderne et évolutive

### Approche hybride :
Combinez plusieurs technologies pour une protection en profondeur :
- **Clustering** pour HA locale rapide
- **Log Shipping** ou **AlwaysOn asynchrone** pour DR distant
- **Sauvegardes** régulières (toujours indispensables !)

---

**Pour aller plus loin :**
- Consultez la documentation officielle Microsoft pour les détails techniques
- Travaillez avec votre équipe infrastructure pour évaluer les besoins réels
- Considérez les solutions cloud (Azure SQL) qui gèrent beaucoup de ces aspects automatiquement

**Rappel important :** Ces technologies protègent contre les pannes techniques, mais **n'éliminent pas le besoin de sauvegardes régulières** pour se protéger contre les erreurs humaines, corruptions de données, ou attaques malveillantes.
