# 7.6.2 Éviter les fonctions dans le WHERE

## Introduction

Dans la section précédente (7.6.1), nous avons découvert le concept de SARGability. Une des règles les plus importantes pour maintenir la SARGability est d'**éviter d'appliquer des fonctions sur les colonnes indexées dans la clause WHERE**.

Cette section approfondit ce principe crucial et vous montre comment transformer vos requêtes pour éliminer les fonctions problématiques.

## Pourquoi les fonctions posent problème

### Le processus sans fonction

Quand vous écrivez une condition simple comme `WHERE CustomerID = 123` :

```
1. SQL Server consulte l'index sur CustomerID
2. Il trouve directement la ligne avec CustomerID = 123
3. Il lit uniquement cette ligne
4. Temps : quelques millisecondes
```

### Le processus avec fonction

Quand vous écrivez `WHERE UPPER(CustomerName) = 'DUPONT'` :

```
1. SQL Server ne peut PAS utiliser l'index directement
2. Il doit lire TOUTES les lignes une par une
3. Pour chaque ligne :
   - Lire CustomerName
   - Appliquer UPPER() sur cette valeur
   - Comparer avec 'DUPONT'
4. Temps : plusieurs secondes (sur une grande table)
```

### Analogie : La recherche dans un dictionnaire

**Sans fonction (optimal)** :
```
Vous cherchez le mot "Chat" dans un dictionnaire
→ Vous ouvrez directement à la lettre C
→ Vous trouvez le mot en quelques secondes
```

**Avec fonction (problématique)** :
```
Vous cherchez tous les mots dont la version INVERSÉE commence par "tah"
→ Le dictionnaire est organisé alphabétiquement normalement
→ Vous devez lire CHAQUE mot
→ Inverser chaque mot
→ Vérifier s'il commence par "tah"
→ Cela prend des heures !
```

## Impact quantitatif

### Comparaison réelle

**Table de 1 million de lignes avec index sur OrderDate :**

```sql
-- ❌ Avec fonction : YEAR(OrderDate) = 2024
Temps d'exécution : 3.2 secondes
Lectures logiques : 45,000 pages
Plan d'exécution : Table Scan (95% du coût)

-- ✅ Sans fonction : OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'
Temps d'exécution : 0.005 secondes (5 millisecondes)
Lectures logiques : 150 pages
Plan d'exécution : Index Seek (2% du coût)

→ Amélioration de 640x en vitesse
→ Réduction de 99.7% des lectures disque
```

## Catégories de fonctions problématiques

### 1. Fonctions de dates

Les fonctions de dates sont parmi les plus couramment utilisées de manière problématique.

#### ❌ Problème : YEAR(), MONTH(), DAY()

```sql
-- Trouver les commandes de 2024
SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;

-- Trouver les commandes de novembre
SELECT * FROM Orders
WHERE MONTH(OrderDate) = 11;

-- Trouver les commandes du 15
SELECT * FROM Orders
WHERE DAY(OrderDate) = 15;
```

**Pourquoi c'est mauvais :**
- YEAR(), MONTH(), DAY() sont appelés pour CHAQUE ligne
- L'index sur OrderDate ne peut pas être utilisé
- Performance catastrophique sur les grandes tables

#### ✅ Solution : Utiliser des plages de dates

```sql
-- Trouver les commandes de 2024
SELECT * FROM Orders
WHERE OrderDate >= '2024-01-01'
  AND OrderDate < '2025-01-01';

-- Trouver les commandes de novembre 2024
SELECT * FROM Orders
WHERE OrderDate >= '2024-11-01'
  AND OrderDate < '2024-12-01';

-- Trouver les commandes du 15 novembre 2024
SELECT * FROM Orders
WHERE OrderDate >= '2024-11-15'
  AND OrderDate < '2024-11-16';
```

**Avantages :**
- L'index est utilisé efficacement (Index Seek)
- Les comparaisons sont directes
- Performance optimale

#### ❌ Problème : DATEPART() et DATEADD()

```sql
-- Trouver les commandes du même jour de la semaine
SELECT * FROM Orders
WHERE DATEPART(WEEKDAY, OrderDate) = 2;  -- Lundi

-- Trouver les commandes de plus de 30 jours
SELECT * FROM Orders
WHERE DATEADD(DAY, 30, OrderDate) < GETDATE();
```

#### ✅ Solution : Réorganiser la logique

```sql
-- Trouver les lundis (plus complexe, envisager une colonne calculée)
-- Option 1 : Colonne calculée
ALTER TABLE Orders
ADD DayOfWeek AS DATEPART(WEEKDAY, OrderDate) PERSISTED;

CREATE INDEX IX_Orders_DayOfWeek ON Orders(DayOfWeek);

SELECT * FROM Orders
WHERE DayOfWeek = 2;

-- Option 2 : Pour une utilisation ponctuelle, calculer les dates précises
-- (Calculer les lundis du mois en cours dans l'application)

-- Trouver les commandes de plus de 30 jours (reformuler)
DECLARE @CutoffDate DATE = DATEADD(DAY, -30, GETDATE());
SELECT * FROM Orders
WHERE OrderDate < @CutoffDate;
```

#### ❌ Problème : CAST() et CONVERT() sur les dates

```sql
-- Comparer uniquement la partie date
SELECT * FROM Orders
WHERE CAST(OrderDate AS DATE) = '2024-11-18';

-- Convertir pour comparer
SELECT * FROM Orders
WHERE CONVERT(VARCHAR(10), OrderDate, 120) = '2024-11-18';
```

#### ✅ Solution : Plages sans conversion

```sql
-- Comparer la date complète avec une plage
DECLARE @TargetDate DATE = '2024-11-18';
SELECT * FROM Orders
WHERE OrderDate >= @TargetDate
  AND OrderDate < DATEADD(DAY, 1, @TargetDate);

-- Alternative : Si OrderDate est déjà de type DATE
SELECT * FROM Orders
WHERE OrderDate = '2024-11-18';
```

#### ❌ Problème : DATEDIFF()

```sql
-- Commandes des 30 derniers jours
SELECT * FROM Orders
WHERE DATEDIFF(DAY, OrderDate, GETDATE()) <= 30;

-- Commandes de cette année
SELECT * FROM Orders
WHERE DATEDIFF(YEAR, OrderDate, GETDATE()) = 0;
```

#### ✅ Solution : Inverser la logique

```sql
-- Commandes des 30 derniers jours
SELECT * FROM Orders
WHERE OrderDate >= DATEADD(DAY, -30, GETDATE());

-- Commandes de cette année
DECLARE @StartOfYear DATE = DATEFROMPARTS(YEAR(GETDATE()), 1, 1);
DECLARE @StartOfNextYear DATE = DATEADD(YEAR, 1, @StartOfYear);
SELECT * FROM Orders
WHERE OrderDate >= @StartOfYear
  AND OrderDate < @StartOfNextYear;
```

### 2. Fonctions de chaînes de caractères

#### ❌ Problème : UPPER() et LOWER()

```sql
-- Recherche insensible à la casse
SELECT * FROM Customers
WHERE UPPER(CustomerName) = 'MARTIN';

SELECT * FROM Customers
WHERE LOWER(Email) = 'john@example.com';
```

**Impact :**
- Fonction appliquée sur toutes les lignes
- Index inutilisable
- Très lent sur des millions de lignes

#### ✅ Solution : Utiliser COLLATE ou colonnes calculées

```sql
-- Solution 1 : COLLATE (Case Insensitive)
SELECT * FROM Customers
WHERE CustomerName = 'Martin' COLLATE Latin1_General_CI_AS;
-- CI = Case Insensitive, AS = Accent Sensitive

-- Solution 2 : Configurer la base avec collation CI par défaut
-- Lors de la création de la base

-- Solution 3 : Colonne calculée (pour recherches fréquentes)
ALTER TABLE Customers
ADD CustomerNameUpper AS UPPER(CustomerName) PERSISTED;

CREATE INDEX IX_Customers_NameUpper ON Customers(CustomerNameUpper);

SELECT * FROM Customers
WHERE CustomerNameUpper = 'MARTIN';
```

#### ❌ Problème : SUBSTRING()

```sql
-- Extraire les 3 premiers caractères
SELECT * FROM Products
WHERE SUBSTRING(ProductCode, 1, 3) = 'ABC';

-- Extraire à partir du milieu
SELECT * FROM Products
WHERE SUBSTRING(ProductCode, 4, 2) = '12';
```

#### ✅ Solution : Selon le contexte

```sql
-- Pour les préfixes : Utiliser LIKE
SELECT * FROM Products
WHERE ProductCode LIKE 'ABC%';

-- Pour les suffixes : Plus difficile, envisager une colonne calculée
ALTER TABLE Products
ADD ProductPrefix AS SUBSTRING(ProductCode, 1, 3) PERSISTED;

CREATE INDEX IX_Products_Prefix ON Products(ProductPrefix);

SELECT * FROM Products
WHERE ProductPrefix = 'ABC';

-- Pour extractions au milieu : Repenser le modèle de données
-- Peut-être séparer les codes en plusieurs colonnes
```

#### ❌ Problème : LTRIM(), RTRIM(), TRIM()

```sql
-- Supprimer les espaces avant comparaison
SELECT * FROM Products
WHERE LTRIM(RTRIM(ProductCode)) = 'ABC123';

-- Avec TRIM() (SQL Server 2017+)
SELECT * FROM Products
WHERE TRIM(ProductCode) = 'ABC123';
```

#### ✅ Solution : Nettoyer à la source

```sql
-- Option 1 : Nettoyer les données à l'insertion
CREATE TRIGGER trg_CleanProductCode
ON Products
AFTER INSERT, UPDATE
AS
BEGIN
    UPDATE p
    SET ProductCode = LTRIM(RTRIM(i.ProductCode))
    FROM Products p
    INNER JOIN inserted i ON p.ProductID = i.ProductID
    WHERE p.ProductCode <> LTRIM(RTRIM(i.ProductCode));
END;

-- Option 2 : Colonne calculée
ALTER TABLE Products
ADD ProductCodeClean AS LTRIM(RTRIM(ProductCode)) PERSISTED;

CREATE INDEX IX_Products_CodeClean ON Products(ProductCodeClean);

SELECT * FROM Products
WHERE ProductCodeClean = 'ABC123';

-- Option 3 : Contrainte CHECK pour prévenir
ALTER TABLE Products
ADD CONSTRAINT CK_ProductCode_NoSpaces
CHECK (ProductCode = LTRIM(RTRIM(ProductCode)));
```

#### ❌ Problème : LEN() et DATALENGTH()

```sql
-- Trouver les noms de plus de 10 caractères
SELECT * FROM Customers
WHERE LEN(CustomerName) > 10;

-- Trouver les codes de longueur spécifique
SELECT * FROM Products
WHERE LEN(ProductCode) = 8;
```

#### ✅ Solution : Colonne calculée

```sql
-- Si cette recherche est fréquente
ALTER TABLE Customers
ADD NameLength AS LEN(CustomerName) PERSISTED;

CREATE INDEX IX_Customers_NameLength ON Customers(NameLength);

SELECT * FROM Customers
WHERE NameLength > 10;

-- Alternative : Envisager une contrainte de longueur fixe
-- Si tous les codes doivent faire 8 caractères
ALTER TABLE Products
ADD CONSTRAINT CK_ProductCode_Length
CHECK (LEN(ProductCode) = 8);
```

#### ❌ Problème : LEFT(), RIGHT()

```sql
-- Premiers caractères
SELECT * FROM Customers
WHERE LEFT(CustomerName, 3) = 'Mar';

-- Derniers caractères
SELECT * FROM Customers
WHERE RIGHT(Phone, 4) = '1234';
```

#### ✅ Solution : Alternatives

```sql
-- Pour LEFT() : Utiliser LIKE
SELECT * FROM Customers
WHERE CustomerName LIKE 'Mar%';

-- Pour RIGHT() : Plus complexe
-- Option 1 : Colonne calculée (si recherche fréquente)
ALTER TABLE Customers
ADD PhoneLast4 AS RIGHT(Phone, 4) PERSISTED;

CREATE INDEX IX_Customers_PhoneLast4 ON Customers(PhoneLast4);

SELECT * FROM Customers
WHERE PhoneLast4 = '1234';

-- Option 2 : Repenser la structure (numéro court séparé)
```

#### ❌ Problème : REPLACE() et autres transformations

```sql
-- Remplacer avant comparaison
SELECT * FROM Products
WHERE REPLACE(ProductName, '-', '') = 'ProductA123';

-- Concaténation
SELECT * FROM Employees
WHERE FirstName + ' ' + LastName = 'John Doe';
```

#### ✅ Solution : Stocker la version transformée

```sql
-- Colonne calculée pour le nom sans tiret
ALTER TABLE Products
ADD ProductNameNoDash AS REPLACE(ProductName, '-', '') PERSISTED;

CREATE INDEX IX_Products_NameNoDash ON Products(ProductNameNoDash);

-- Colonne calculée pour le nom complet
ALTER TABLE Employees
ADD FullName AS FirstName + ' ' + LastName PERSISTED;

CREATE INDEX IX_Employees_FullName ON Employees(FullName);

SELECT * FROM Employees
WHERE FullName = 'John Doe';
```

### 3. Fonctions mathématiques et arithmétiques

#### ❌ Problème : Opérations arithmétiques

```sql
-- Calcul dans le WHERE
SELECT * FROM Products
WHERE Price * 1.20 > 100;  -- Prix TTC

SELECT * FROM Employees
WHERE Salary * 12 > 60000;  -- Salaire annuel

SELECT * FROM Orders
WHERE Quantity * UnitPrice > 1000;  -- Montant total
```

#### ✅ Solution : Inverser le calcul

```sql
-- Déplacer le calcul côté constante
SELECT * FROM Products
WHERE Price > 100 / 1.20;  -- = 83.33

SELECT * FROM Employees
WHERE Salary > 60000 / 12;  -- = 5000

-- Pour des calculs complexes : Colonne calculée
ALTER TABLE Orders
ADD TotalAmount AS Quantity * UnitPrice PERSISTED;

CREATE INDEX IX_Orders_TotalAmount ON Orders(TotalAmount);

SELECT * FROM Orders
WHERE TotalAmount > 1000;
```

#### ❌ Problème : ABS(), POWER(), SQRT()

```sql
-- Valeur absolue
SELECT * FROM Transactions
WHERE ABS(Amount) > 1000;

-- Puissance
SELECT * FROM Measurements
WHERE POWER(Value, 2) > 100;

-- Racine carrée
SELECT * FROM Statistics
WHERE SQRT(Variance) > 10;
```

#### ✅ Solution : Reformuler ou colonne calculée

```sql
-- Valeur absolue : Reformuler avec OR
SELECT * FROM Transactions
WHERE Amount > 1000 OR Amount < -1000;

-- Pour des calculs fréquents : Colonne calculée
ALTER TABLE Measurements
ADD ValueSquared AS POWER(Value, 2) PERSISTED;

CREATE INDEX IX_Measurements_ValueSquared ON Measurements(ValueSquared);

SELECT * FROM Measurements
WHERE ValueSquared > 100;
```

#### ❌ Problème : ROUND(), CEILING(), FLOOR()

```sql
-- Arrondi
SELECT * FROM Prices
WHERE ROUND(Price, 0) = 100;

-- Arrondi supérieur
SELECT * FROM Prices
WHERE CEILING(Price) > 99;
```

#### ✅ Solution : Plages précises

```sql
-- Au lieu d'arrondir, utiliser des plages
SELECT * FROM Prices
WHERE Price >= 99.5 AND Price < 100.5;  -- ROUND(Price, 0) = 100

-- Pour CEILING
SELECT * FROM Prices
WHERE Price > 99;  -- CEILING(Price) > 99 équivaut à Price > 99
```

### 4. Fonctions de conversion

#### ❌ Problème : CAST() et CONVERT()

```sql
-- Conversion de type
SELECT * FROM Orders
WHERE CAST(CustomerID AS VARCHAR(10)) = '12345';

-- Conversion de date
SELECT * FROM Orders
WHERE CAST(OrderDate AS DATE) = '2024-11-18';

-- Conversion pour comparaison
SELECT * FROM Products
WHERE CAST(Price AS INT) > 100;
```

#### ✅ Solution : Utiliser le type correct

```sql
-- Pas de conversion nécessaire si les types correspondent
SELECT * FROM Orders
WHERE CustomerID = 12345;  -- INT directement

-- Plage pour les dates
DECLARE @TargetDate DATE = '2024-11-18';
SELECT * FROM Orders
WHERE OrderDate >= @TargetDate
  AND OrderDate < DATEADD(DAY, 1, @TargetDate);

-- Pour les prix : Comparer avec décimal
SELECT * FROM Products
WHERE Price > 100.0;  -- Pas besoin de CAST
```

#### ❌ Problème : STR() et FORMAT()

```sql
-- Formatage pour comparaison
SELECT * FROM Orders
WHERE STR(OrderID, 10) = '      1234';

-- FORMAT (SQL Server 2012+)
SELECT * FROM Orders
WHERE FORMAT(OrderDate, 'yyyy-MM') = '2024-11';
```

#### ✅ Solution : Éviter le formatage

```sql
-- Comparer directement sans formatage
SELECT * FROM Orders
WHERE OrderID = 1234;

-- Pour les dates formatées : Plages
SELECT * FROM Orders
WHERE OrderDate >= '2024-11-01'
  AND OrderDate < '2024-12-01';
```

### 5. Fonctions d'agrégation imbriquées

#### ❌ Problème rare mais possible

```sql
-- Comparer avec un agrégat (généralement dans un HAVING, pas WHERE)
-- Si dans WHERE (nécessite une sous-requête), éviter les fonctions
SELECT CustomerID, AVG(OrderAmount) as AvgAmount
FROM Orders
GROUP BY CustomerID
HAVING SUM(CASE WHEN YEAR(OrderDate) = 2024 THEN 1 ELSE 0 END) > 10;
```

#### ✅ Solution

```sql
-- Déplacer la condition avant l'agrégation quand possible
SELECT CustomerID, AVG(OrderAmount) as AvgAmount
FROM Orders
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'
GROUP BY CustomerID
HAVING COUNT(*) > 10;
```

## Techniques avancées de réécriture

### Technique 1 : Pré-calcul dans une CTE ou variable

```sql
-- ❌ Calcul répété
SELECT * FROM Orders
WHERE DATEDIFF(DAY, OrderDate, GETDATE()) <= 30
   OR DATEDIFF(DAY, ShipDate, GETDATE()) <= 30;

-- ✅ Calcul une seule fois
DECLARE @CutoffDate DATE = DATEADD(DAY, -30, GETDATE());

SELECT * FROM Orders
WHERE OrderDate >= @CutoffDate
   OR ShipDate >= @CutoffDate;
```

### Technique 2 : Colonnes calculées persistées

```sql
-- Configuration optimale pour recherches fréquentes
ALTER TABLE Customers
ADD SearchName AS UPPER(LTRIM(RTRIM(CustomerName))) PERSISTED;

CREATE INDEX IX_Customers_SearchName ON Customers(SearchName);

-- Index sur expression (alternative)
CREATE INDEX IX_Customers_NameUpper
ON Customers(UPPER(CustomerName));

-- Note : L'index sur expression n'est pas aussi performant
-- qu'une colonne calculée persistée
```

### Technique 3 : Index filtrés pour conditions complexes

```sql
-- Si vous recherchez souvent une condition spécifique
-- Ex: Commandes actives (Status = 'Active')

-- ❌ Avec fonction
WHERE ISNULL(Status, 'Active') = 'Active'

-- ✅ Avec index filtré
CREATE INDEX IX_Orders_Active
ON Orders(OrderDate, CustomerID)
WHERE Status = 'Active' OR Status IS NULL;

-- Puis requête simple
SELECT * FROM Orders
WHERE (Status = 'Active' OR Status IS NULL)
  AND OrderDate >= '2024-01-01';
```

### Technique 4 : Vues indexées

Pour des transformations très fréquentes :

```sql
-- Créer une vue avec les transformations
CREATE VIEW vw_ProductsSearchable
WITH SCHEMABINDING
AS
SELECT
    ProductID,
    UPPER(ProductName) AS ProductNameUpper,
    SUBSTRING(ProductCode, 1, 3) AS ProductPrefix,
    Price * 1.20 AS PriceWithTax
FROM dbo.Products;
GO

-- Créer un index clustered sur la vue
CREATE UNIQUE CLUSTERED INDEX IX_vw_ProductsSearchable
ON vw_ProductsSearchable(ProductID);

-- Créer des index additionnels
CREATE INDEX IX_vw_ProductsSearchable_NameUpper
ON vw_ProductsSearchable(ProductNameUpper);

-- Utiliser la vue
SELECT * FROM vw_ProductsSearchable
WHERE ProductNameUpper = 'LAPTOP'
  AND PriceWithTax > 1000;
```

**Avantages :**
- Les calculs sont stockés physiquement
- Mises à jour automatiques
- Performance optimale

**Inconvénients :**
- Complexité accrue
- Espace disque supplémentaire
- Maintenance plus lourde

## Cas particuliers et compromis

### Cas 1 : Full-Text Search pour les textes

Pour les recherches textuelles complexes :

```sql
-- ❌ Très lent
SELECT * FROM Articles
WHERE UPPER(Content) LIKE '%PERFORMANCE%';

-- ✅ Full-Text Index
CREATE FULLTEXT INDEX ON Articles(Content)
KEY INDEX PK_Articles;

-- Utiliser CONTAINS
SELECT * FROM Articles
WHERE CONTAINS(Content, 'performance');
```

### Cas 2 : Quand la fonction est inévitable

Si vous ne pouvez vraiment pas éviter une fonction :

**1. Minimiser l'impact :**
```sql
-- Filtrer d'abord avec des critères SARGable
SELECT * FROM Orders
WHERE OrderDate >= '2024-01-01'  -- SARGable : réduit les lignes
  AND OrderDate < '2025-01-01'
  AND DATEPART(WEEKDAY, OrderDate) = 2;  -- Non-SARGable : sur peu de lignes
```

**2. Créer une colonne calculée :**
```sql
ALTER TABLE Orders
ADD OrderWeekday AS DATEPART(WEEKDAY, OrderDate) PERSISTED;

CREATE INDEX IX_Orders_Weekday ON Orders(OrderWeekday);
```

**3. Accepter la performance réduite :**
Pour des rapports exécutés rarement, c'est acceptable.

### Cas 3 : Recherches avec paramètres dynamiques

```sql
-- Éviter les constructions dynamiques avec fonctions
CREATE PROCEDURE sp_SearchProducts
    @SearchType VARCHAR(20),
    @SearchValue VARCHAR(100)
AS
BEGIN
    -- ❌ Mauvaise approche
    IF @SearchType = 'UPPERCASE'
        SELECT * FROM Products WHERE UPPER(ProductName) = @SearchValue;

    -- ✅ Meilleure approche : Colonnes calculées
    ALTER TABLE Products
    ADD ProductNameUpper AS UPPER(ProductName) PERSISTED;

    IF @SearchType = 'UPPERCASE'
        SELECT * FROM Products WHERE ProductNameUpper = @SearchValue;
    ELSE IF @SearchType = 'NORMAL'
        SELECT * FROM Products WHERE ProductName = @SearchValue;
END;
```

## Outils de détection

### 1. Identifier les fonctions dans les requêtes existantes

```sql
-- Requête pour trouver les fonctions courantes dans Query Store
SELECT
    qt.query_sql_text,
    rs.avg_duration / 1000.0 AS avg_duration_ms,
    rs.avg_logical_io_reads
FROM sys.query_store_query_text qt
INNER JOIN sys.query_store_query q ON qt.query_text_id = q.query_text_id
INNER JOIN sys.query_store_plan p ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
WHERE qt.query_sql_text LIKE '%YEAR(%'
   OR qt.query_sql_text LIKE '%MONTH(%'
   OR qt.query_sql_text LIKE '%UPPER(%'
   OR qt.query_sql_text LIKE '%LOWER(%'
   OR qt.query_sql_text LIKE '%SUBSTRING(%'
   OR qt.query_sql_text LIKE '%CAST(%'
ORDER BY rs.avg_logical_io_reads DESC;
```

### 2. Analyser les plans d'exécution

Cherchez ces indicateurs :

```
[Table Scan] ou [Index Scan]
    Predicate: [fonction](colonne) = valeur
    ↓
    Problème détecté !
```

vs

```
[Index Seek]
    Seek Predicate: colonne = valeur
    ↓
    Bon !
```

### 3. Script de diagnostic

```sql
-- Créer une table de suivi des performances
CREATE TABLE PerformanceBaseline (
    QueryID INT IDENTITY PRIMARY KEY,
    QueryText NVARCHAR(MAX),
    HasFunctionInWhere BIT,
    AvgDurationMs FLOAT,
    AvgLogicalReads BIGINT,
    ExecutionDate DATETIME2 DEFAULT GETDATE()
);

-- Peupler avec les requêtes actuelles
INSERT INTO PerformanceBaseline (QueryText, HasFunctionInWhere, AvgDurationMs, AvgLogicalReads)
SELECT
    qt.query_sql_text,
    CASE
        WHEN qt.query_sql_text LIKE '%WHERE%[A-Z]%(%' THEN 1
        ELSE 0
    END,
    rs.avg_duration / 1000.0,
    rs.avg_logical_io_reads
FROM sys.query_store_query_text qt
INNER JOIN sys.query_store_query q ON qt.query_text_id = q.query_text_id
INNER JOIN sys.query_store_plan p ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
WHERE qt.query_sql_text LIKE '%WHERE%';

-- Identifier les cibles d'optimisation
SELECT TOP 20
    QueryText,
    AvgDurationMs,
    AvgLogicalReads
FROM PerformanceBaseline
WHERE HasFunctionInWhere = 1
ORDER BY AvgDurationMs DESC;
```

## Méthodologie d'optimisation

### Étape 1 : Audit des requêtes

```sql
-- Lister toutes les requêtes avec fonctions dans WHERE
SELECT DISTINCT
    OBJECT_NAME(object_id) AS ObjectName,
    definition
FROM sys.sql_modules
WHERE definition LIKE '%WHERE%YEAR(%'
   OR definition LIKE '%WHERE%MONTH(%'
   OR definition LIKE '%WHERE%UPPER(%'
   OR definition LIKE '%WHERE%CAST(%';
```

### Étape 2 : Prioriser

Critères de priorisation :
1. **Fréquence d'exécution** : Requêtes exécutées 1000x/jour
2. **Durée** : Requêtes prenant >1 seconde
3. **Impact utilisateur** : Pages critiques de l'application
4. **Volume de données** : Tables avec >1M de lignes

### Étape 3 : Planifier la correction

```
Pour chaque requête identifiée :

1. Analyser le contexte
   - Pourquoi la fonction est-elle utilisée ?
   - Y a-t-il une alternative SARGable ?

2. Choisir la stratégie
   - Réécriture simple
   - Colonne calculée
   - Vue indexée
   - Full-Text Search

3. Tester en développement
   - Vérifier le plan d'exécution
   - Mesurer les performances (avant/après)
   - Valider les résultats (même données)

4. Déployer progressivement
   - Test
   - Pré-production
   - Production (hors heures de pointe)

5. Monitorer
   - Query Store pour suivre l'amélioration
   - Alertes pour détecter les régressions
```

### Étape 4 : Documenter

```sql
-- Exemple de documentation
/*
Optimisation : Requête sp_GetMonthlyOrders
Date : 2024-11-18
Auteur : Jean Dupont

AVANT :
WHERE MONTH(OrderDate) = @Month AND YEAR(OrderDate) = @Year
- Durée moyenne : 2.5 secondes
- Lectures logiques : 45,000 pages
- Plan : Table Scan

APRÈS :
WHERE OrderDate >= @StartDate AND OrderDate < @EndDate
- Durée moyenne : 0.008 secondes
- Lectures logiques : 120 pages
- Plan : Index Seek

Amélioration : 312x plus rapide
*/
```

## Checklist pratique

Avant de finaliser une requête, vérifiez :

**✅ Checklist "Pas de fonctions sur colonnes indexées"**

- [ ] Pas de YEAR(), MONTH(), DAY() dans WHERE
- [ ] Pas de UPPER(), LOWER() dans WHERE
- [ ] Pas de CAST() ou CONVERT() sur colonnes indexées
- [ ] Pas de SUBSTRING(), LEFT(), RIGHT() dans WHERE
- [ ] Pas de calculs arithmétiques sur colonnes indexées
- [ ] Pas de DATEDIFF(), DATEADD() sur colonnes
- [ ] Utilisation de plages pour les dates (>= et <)
- [ ] Types de données correspondants (pas de conversion implicite)
- [ ] Plan d'exécution montre "Index Seek" (pas "Scan")
- [ ] Statistiques I/O acceptables (<1000 reads pour queries fréquentes)

## Exemples de refactoring complets

### Exemple 1 : Rapport de ventes mensuel

```sql
-- ❌ AVANT : Non-optimal
CREATE PROCEDURE sp_MonthlySalesReport_SLOW
    @Year INT,
    @Month INT
AS
BEGIN
    SELECT
        CustomerID,
        COUNT(*) AS OrderCount,
        SUM(TotalAmount) AS TotalSales
    FROM Orders
    WHERE YEAR(OrderDate) = @Year
      AND MONTH(OrderDate) = @Month
    GROUP BY CustomerID
    ORDER BY TotalSales DESC;
END;

-- Performance : 3.2 secondes sur 1M de lignes

-- ✅ APRÈS : Optimisé
CREATE PROCEDURE sp_MonthlySalesReport_FAST
    @Year INT,
    @Month INT
AS
BEGIN
    -- Calculer les bornes une seule fois
    DECLARE @StartDate DATE = DATEFROMPARTS(@Year, @Month, 1);
    DECLARE @EndDate DATE = DATEADD(MONTH, 1, @StartDate);

    SELECT
        CustomerID,
        COUNT(*) AS OrderCount,
        SUM(TotalAmount) AS TotalSales
    FROM Orders
    WHERE OrderDate >= @StartDate
      AND OrderDate < @EndDate
    GROUP BY CustomerID
    ORDER BY TotalSales DESC;
END;

-- Performance : 0.01 secondes sur 1M de lignes
-- Amélioration : 320x plus rapide
```

CREATE PROCEDURE sp_SearchCustomers_SLOW

ALTER TABLE Customers
ADD CustomerNameUpper AS UPPER(CustomerName) PERSISTED;

CREATE INDEX IX_Customers_NameUpper ON Customers(CustomerNameUpper);

-- Étape 3 : Procédure optimisée

    @SearchTerm VARCHAR(100)
AS

    -- Pour recherche exacte ou préfixe
    IF @SearchTerm NOT LIKE '%[%_]%'  -- Pas de wildcards
    BEGIN

        FROM Customers
        WHERE CustomerNameUpper LIKE @SearchTermUpper + '%'
           OR EmailUpper LIKE @SearchTermUpper + '%';

        SELECT CustomerID, CustomerName, Email, Phone
        FROM Customers
        WHERE CONTAINS((CustomerName, Email), @SearchTerm);
    END

### Exemple 3 : Dashboard de KPIs

```sql
-- ❌ AVANT : Calculs répétés dans WHERE
CREATE PROCEDURE sp_DashboardKPIs_SLOW
AS
BEGIN
    -- Commandes aujourd'hui
    SELECT COUNT(*) AS OrdersToday
    FROM Orders
    WHERE CAST(OrderDate AS DATE) = CAST(GETDATE() AS DATE);

    -- Commandes ce mois
    SELECT COUNT(*) AS OrdersThisMonth
    FROM Orders
    WHERE MONTH(OrderDate) = MONTH(GETDATE())
      AND YEAR(OrderDate) = YEAR(GETDATE());

    -- Commandes 30 derniers jours
    SELECT COUNT(*) AS Orders30Days
    FROM Orders
    WHERE DATEDIFF(DAY, OrderDate, GETDATE()) <= 30;
END;

-- Performance : 9 secondes (3 scans de table)

-- ✅ APRÈS : Calculs une fois, requête optimisée
CREATE PROCEDURE sp_DashboardKPIs_FAST
AS
BEGIN
    -- Pré-calculer toutes les dates
    DECLARE @Now DATETIME2 = GETDATE();
    DECLARE @Today DATE = CAST(@Now AS DATE);
    DECLARE @Tomorrow DATE = DATEADD(DAY, 1, @Today);
    DECLARE @StartOfMonth DATE = DATEFROMPARTS(YEAR(@Now), MONTH(@Now), 1);
    DECLARE @StartOfNextMonth DATE = DATEADD(MONTH, 1, @StartOfMonth);
    DECLARE @ThirtyDaysAgo DATE = DATEADD(DAY, -30, @Today);

    -- Une seule lecture de la table
    SELECT
        SUM(CASE WHEN OrderDate >= @Today AND OrderDate < @Tomorrow THEN 1 ELSE 0 END) AS OrdersToday,
        SUM(CASE WHEN OrderDate >= @StartOfMonth AND OrderDate < @StartOfNextMonth THEN 1 ELSE 0 END) AS OrdersThisMonth,
        SUM(CASE WHEN OrderDate >= @ThirtyDaysAgo THEN 1 ELSE 0 END) AS Orders30Days
    FROM Orders
    WHERE OrderDate >= @ThirtyDaysAgo;  -- Filtre SARGable global
END;

-- Performance : 0.3 secondes (1 scan optimisé avec index)
-- Amélioration : 30x plus rapide
```

## Résumé

Éviter les fonctions dans la clause WHERE est une des optimisations les plus impactantes que vous puissiez faire.

**Principes fondamentaux :**

1. **Les fonctions empêchent l'utilisation des index**
   - Elles forcent SQL Server à lire toutes les lignes
   - Performance catastrophique sur grandes tables

2. **Alternatives systématiques existent**
   - Plages de dates au lieu de YEAR()/MONTH()
   - COLLATE au lieu de UPPER()/LOWER()
   - Inverser les calculs arithmétiques
   - Colonnes calculées pour transformations fréquentes

3. **Impact mesurable**
   - Gains de 10x à 1000x en performance
   - Réduction drastique des I/O
   - Meilleure scalabilité

4. **Méthodologie**
   - Audit des requêtes existantes
   - Priorisation par impact
   - Test et validation
   - Documentation

**Règle d'or :** Si vous voyez une fonction sur une colonne dans WHERE, demandez-vous "Puis-je réorganiser cette requête pour isoler la colonne ?"

---

**Points clés à retenir :**

- ✅ Fonctions sur colonnes = Non-SARGable = Lent
- ✅ Utiliser des plages pour les dates (`>= AND <`)
- ✅ Utiliser COLLATE pour insensibilité à la casse
- ✅ Inverser les calculs (côté constante, pas colonne)
- ✅ Colonnes calculées pour transformations fréquentes
- ✅ Index filtrés pour conditions spécifiques
- ✅ Full-Text Search pour recherches textuelles complexes
- ✅ Toujours tester et comparer les performances
- ✅ Documenter les optimisations
- ✅ Monitorer avec Query Store

**Mantra de l'optimisation :** "La colonne indexée doit être nue et seule dans le WHERE."
