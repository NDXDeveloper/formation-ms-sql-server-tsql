# 8.7.3 Cas d'usage, mode batch et limites

## Introduction

Cette dernière sous-section sur le columnstore est tournée vers la **pratique** : à quoi sert-il vraiment, comment fonctionne le **mode batch** qui lui donne sa vitesse, et quelles **limites** garder en tête pour ne pas se tromper d'outil.

---

## Le mode batch (batch mode execution)

Le **mode batch** est, avec la compression, la grande raison de la vitesse du columnstore.

### Le mode ligne classique (row mode)

Dans l'exécution traditionnelle, les opérateurs du plan (filtre, agrégation, jointure) traitent **une ligne à la fois**. Pour agréger 200 millions de lignes, le moteur fait 200 millions de passages — avec un coût processeur par ligne (appels de fonction, vérifications) qui s'accumule.

### Le mode batch

Avec le columnstore, le moteur traite les lignes par **lots (*batches*) d'environ 900 lignes** à la fois :

```
   Mode ligne :   ligne → ligne → ligne → ...   (200 M de fois)
   Mode batch :   [lot de ~900] → [lot de ~900] → ...   (≈ 220 000 fois)
```

Les bénéfices :
- Le coût processeur par ligne **s'effondre** (un traitement amorti sur 900 lignes).
- Meilleure utilisation des **caches CPU** et des instructions vectorielles.
- Idéal pour les **agrégations** et **jointures** sur de gros volumes.

> 💡 **Batch mode on rowstore** : depuis SQL Server 2019, le mode batch peut aussi s'appliquer à des tables **rowstore** classiques (sans columnstore), lorsque l'optimiseur estime que la requête est analytique. Une raison de plus de migrer vers une version récente.

---

## Cas d'usage typiques

✅ **Entrepôts de données (data warehouse)**
Les **tables de faits** (ventes, transactions, événements) de plusieurs dizaines ou centaines de millions de lignes sont le terrain de jeu idéal du CCI.

✅ **Reporting et tableaux de bord**
Les requêtes d'agrégation qui alimentent les rapports (CA par mois/région/produit) passent de minutes à secondes.

✅ **Données IoT et journaux (logs)**
De gros volumes append-only (capteurs, télémétrie, logs applicatifs) que l'on analyse ensuite : compression massive + analytique rapide.

✅ **HTAP (analytique temps réel sur OLTP)**
Un NCCI sur une table transactionnelle permet de produire des analyses en direct sans ETL ni base séparée.

---

## Quand NE PAS utiliser le columnstore

❌ **Petites tables** (quelques milliers/dizaines de milliers de lignes) : le gain est nul. Un rowgroup n'est efficace qu'à partir de centaines de milliers de lignes ; en deçà, tout reste dans le delta store.

❌ **Charges OLTP pures** : recherches d'une seule ligne (`WHERE CommandeID = 4521`), mises à jour unitaires fréquentes. Le rowstore avec index B-tree (voir §7.1) reste roi.

❌ **Tables très étroites** (2-3 colonnes) : l'avantage « ne lire que les colonnes utiles » disparaît.

❌ **Mises à jour massives et fréquentes ligne par ligne** : génèrent beaucoup de lignes supprimées et de fragmentation.

---

## Limites et points d'attention

- **Un seul index cluster par table** : un CCI exclut un index cluster rowstore (et inversement). On peut toutefois ajouter des index **non-cluster rowstore** sur une table CCI (depuis SQL 2016) pour accélérer les recherches ponctuelles.
- **Tailles de rowgroup** : un rowgroup vise ~1 048 576 lignes. La pression mémoire ou des lots trop petits produisent des rowgroups **tronqués**, moins efficaces.
- **Types de données** : les anciens types `text`/`ntext`/`image` (dépréciés) ne sont pas pris en charge ; utilisez `varchar(max)`/`nvarchar(max)` (supportés depuis SQL 2017).
- **Maintenance** : surveiller la fragmentation et les `deleted_rows` (voir §8.7.2), reconstruire au besoin.

---

## Synergie avec le partitionnement

Sur les très grandes tables de faits, on combine souvent le columnstore avec le **partitionnement de table** (par exemple, une partition par mois) :

- On peut **basculer** (`SWITCH`) une partition entière de façon quasi instantanée pour archiver ou charger des données.
- L'**élimination de partition** s'ajoute à l'élimination de segments pour des requêtes encore plus ciblées.
- On reconstruit/maintient l'index **partition par partition**, sans toucher au reste.

## Exemple : convertir une table et observer le mode batch

```sql
-- Une table de faits volumineuse, au départ en rowstore : on la passe en columnstore
CREATE CLUSTERED COLUMNSTORE INDEX CCI_FaitVentes ON FaitVentes;

-- Requête analytique typique
SELECT RegionID, SUM(Montant) AS CA
FROM FaitVentes
WHERE DateVente >= '2024-01-01'
GROUP BY RegionID;
```

Activez « Inclure le plan d'exécution réel » dans SSMS (voir §7.3) et observez l'opérateur **Columnstore Index Scan**. Dans ses propriétés, la mention **Actual Execution Mode = Batch** confirme que le moteur traite les lignes par paquets de ~900 : c'est là que se gagne le facteur 10× à 100×. Si vous voyez `Row` au lieu de `Batch`, vérifiez la version de SQL Server et la présence effective d'un index columnstore.

## Bonnes pratiques en résumé

- 📦 Charger par **gros lots** (≥ 100 000 lignes, idéalement ≥ 1 million) pour aller directement en rowgroups compressés.
- 📊 Réserver le columnstore aux **grandes tables analytiques**.
- 🔧 **Surveiller** l'état des rowgroups et reconstruire quand la fragmentation grimpe.
- 🧩 Pour l'**HTAP**, préférer un **NCCI** sur la table OLTP plutôt que de dupliquer les données ailleurs.
- 🗓️ Sur de très grands historiques, combiner avec le **partitionnement**.

---

## Questions fréquentes

**Q : Columnstore et index B-tree classiques sont-ils incompatibles ?**
R : Non. Une table avec CCI peut recevoir des index **non-cluster rowstore** pour les recherches ponctuelles. C'est même recommandé en HTAP.

**Q : Le columnstore remplace-t-il un cube SSAS / un entrepôt dédié ?**
R : Pour beaucoup de besoins analytiques « relationnels », un CCI bien conçu suffit et évite une couche supplémentaire. Les cubes/modèles tabulaires gardent leur intérêt pour des besoins BI spécifiques.

**Q : Dois-je activer quelque chose pour le mode batch ?**
R : Non, l'optimiseur le choisit automatiquement quand c'est pertinent (présence d'un columnstore, ou rowstore en SQL 2019+ pour des requêtes analytiques).

---

## Résumé

- Le **mode batch** traite ~900 lignes à la fois : il fait s'effondrer le coût processeur des agrégations et jointures massives.
- Cas d'usage : **entrepôts de données**, **reporting**, **IoT/logs**, **HTAP**.
- À éviter sur les **petites tables**, l'**OLTP pur**, les tables très étroites.
- Limites : un seul index cluster, gestion des rowgroups, anciens types non supportés.
- Combiné au **partitionnement**, le columnstore excelle sur les très grands historiques.
