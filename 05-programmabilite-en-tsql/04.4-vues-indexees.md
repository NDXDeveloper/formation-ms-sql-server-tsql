# 5.4.4 Vues Indexées - Concepts

## Introduction

Les **vues indexées** (également appelées **vues matérialisées** ou *indexed views* / *materialized views* en anglais) sont un type spécial de vue qui permet de surmonter certaines limitations de performance des vues standards.

C'est un concept avancé mais très puissant lorsqu'il est utilisé correctement. Dans cette section, nous allons comprendre ce que sont les vues indexées, comment elles fonctionnent, et quand les utiliser.

---

## 1. Rappel : Le Problème avec les Vues Standards

### 1.1 Les vues standards ne stockent pas de données

Comme nous l'avons vu précédemment, une vue standard est simplement une **requête enregistrée**.

```sql
-- Vue standard
CREATE VIEW VueStatistiquesVentes
AS
    SELECT
        ClientID,
        COUNT(*) AS NombreCommandes,
        SUM(MontantTotal) AS TotalAchats,
        AVG(MontantTotal) AS MoyenneCommande
    FROM Commandes
    GROUP BY ClientID;

-- Chaque fois qu'on interroge la vue :
SELECT * FROM VueStatistiquesVentes;
```

**Ce qui se passe à chaque interrogation :**
1. SQL Server lit la définition de la vue
2. Parcourt **toute** la table `Commandes`
3. Effectue les calculs (`COUNT`, `SUM`, `AVG`)
4. Applique le `GROUP BY`
5. Retourne les résultats

**Problème :** Si la table `Commandes` contient **10 millions de lignes**, cette opération peut prendre plusieurs secondes à chaque exécution.

**Analogie :** C'est comme recalculer la moyenne de vos notes à chaque fois que quelqu'un vous demande votre moyenne générale, même si vous n'avez pas eu de nouvelle note.

---

## 2. Qu'est-ce qu'une Vue Indexée ?

### 2.1 Définition

Une **vue indexée** est une vue dont les résultats sont **physiquement stockés sur le disque**, exactement comme une table.

**Différences clés :**

| Caractéristique | Vue Standard | Vue Indexée |
|----------------|--------------|-------------|
| Stockage des données | ❌ Non | ✅ Oui (sur disque) |
| Recalcul à chaque requête | ✅ Oui | ❌ Non (données pré-calculées) |
| Création d'index | ❌ Impossible | ✅ Possible |
| Maintenance automatique | ❌ N/A | ✅ Oui (mise à jour auto) |
| Restrictions | ⚠️ Peu | ⚠️⚠️⚠️ Beaucoup |
| Performance lecture | ⚠️ Dépend | ✅ Très rapide |
| Performance écriture | ✅ Pas d'impact | ⚠️ Impact (mise à jour de la vue) |

### 2.2 Analogie simple

**Vue standard :** Un raccourci sur votre bureau qui ouvre un programme quand vous cliquez dessus.

**Vue indexée :** Une copie complète du fichier sur votre bureau. Vous n'avez plus besoin de chercher le fichier original, tout est déjà là.

**Avantage :** Accès ultra-rapide car les données sont déjà là.

**Inconvénient :** Si le fichier original change, vous devez mettre à jour la copie (coût de maintenance).

---

## 3. Comment Créer une Vue Indexée

La création d'une vue indexée se fait en **deux étapes** :

### Étape 1 : Créer la vue avec SCHEMABINDING

```sql
-- Étape 1 : Créer la vue avec SCHEMABINDING
CREATE VIEW VueStatistiquesVentesIndexee
WITH SCHEMABINDING  -- OBLIGATOIRE pour pouvoir indexer
AS
    SELECT
        ClientID,
        COUNT_BIG(*) AS NombreCommandes,  -- COUNT_BIG obligatoire (pas COUNT)
        SUM(MontantTotal) AS TotalAchats,
        SUM(MontantTotal * Quantite) AS TotalQuantitatif
    FROM dbo.Commandes  -- Le schéma (dbo.) est OBLIGATOIRE
    GROUP BY ClientID;
```

**Points importants :**
- `WITH SCHEMABINDING` : Lie la vue aux tables sous-jacentes (empêche leur modification)
- `COUNT_BIG(*)` : Obligatoire au lieu de `COUNT(*)` pour l'indexation
- `dbo.Commandes` : Le nom de schéma est obligatoire (pas juste `Commandes`)

### Étape 2 : Créer un index clustered unique

```sql
-- Étape 2 : Créer un index clustered UNIQUE sur la vue
CREATE UNIQUE CLUSTERED INDEX IX_VueStatistiquesVentes_ClientID
ON VueStatistiquesVentesIndexee(ClientID);
```

**Explication :**
- **UNIQUE** : L'index doit être unique (garantit qu'il n'y a pas de doublons sur ClientID)
- **CLUSTERED** : Le premier index doit être un index clustered
- Une fois cet index créé, **les données sont physiquement stockées** sur le disque

---

### 3.1 Que se passe-t-il après la création ?

Après la création de l'index clustered :

1. **SQL Server calcule les résultats** de la vue (comme si vous l'interrogiez)
2. **Stocke physiquement** ces résultats sur le disque
3. **Met à jour automatiquement** ces résultats quand les tables sous-jacentes changent

```sql
-- Maintenant, quand vous interrogez la vue :
SELECT * FROM VueStatistiquesVentesIndexee;
```

**Ce qui se passe :**
- SQL Server lit directement les données **pré-calculées** depuis le disque
- Pas de recalcul, pas de parcours de millions de lignes
- **Performance ultra-rapide** (comme interroger une table avec un bon index)

---

## 4. Avantages des Vues Indexées

### 4.1 Performance spectaculaire en lecture

Les vues indexées peuvent améliorer drastiquement les performances pour les requêtes complexes.

#### Exemple de comparaison

**Scénario :** Table `Commandes` avec 10 millions de lignes

```sql
-- Sans vue indexée (vue standard)
SELECT ClientID, SUM(MontantTotal) AS Total
FROM Commandes
GROUP BY ClientID;
-- Temps : 8 secondes (balayage complet de 10M lignes)

-- Avec vue indexée
SELECT ClientID, TotalAchats
FROM VueStatistiquesVentesIndexee;
-- Temps : 0.1 seconde (lecture directe des données pré-agrégées)
```

**Gain de performance :** Jusqu'à **80 fois plus rapide** dans certains cas !

### 4.2 Agrégations pré-calculées

Les calculs coûteux (SUM, AVG, COUNT) sont effectués une seule fois et stockés.

```sql
-- Ces agrégations sont déjà calculées et stockées
CREATE VIEW VueRapportVentes
WITH SCHEMABINDING
AS
    SELECT
        YEAR(DateCommande) AS Annee,
        MONTH(DateCommande) AS Mois,
        COUNT_BIG(*) AS NombreVentes,
        SUM(MontantTotal) AS ChiffreAffaires,
        AVG(MontantTotal) AS PanierMoyen
    FROM dbo.Commandes
    GROUP BY YEAR(DateCommande), MONTH(DateCommande);

-- Créer l'index
CREATE UNIQUE CLUSTERED INDEX IX_RapportVentes
ON VueRapportVentes(Annee, Mois);
```

**Bénéfice :** Les rapports mensuels sont instantanés car tout est déjà calculé.

### 4.3 Réduction de la charge sur les tables principales

Les requêtes analytiques n'interrogent plus la table principale, réduisant la contention.

```sql
-- Les utilisateurs interrogent la vue indexée
SELECT * FROM VueStatistiquesVentesIndexee
WHERE TotalAchats > 10000;

-- Au lieu de bloquer la table Commandes avec des agrégations lourdes
-- (Moins de locks, moins de blocages)
```

## 5. Restrictions et Contraintes

⚠️ **ATTENTION :** Les vues indexées ont des **restrictions très strictes**. Beaucoup de requêtes ne peuvent pas être transformées en vues indexées.

### 5.1 WITH SCHEMABINDING obligatoire

```sql
-- ❌ Sans SCHEMABINDING, impossible de créer un index
CREATE VIEW VueSansSchema
AS
    SELECT ClientID, Nom
    FROM Clients;

CREATE INDEX IX_Test ON VueSansSchema(ClientID);  -- ERREUR
```

**Conséquence de SCHEMABINDING :**
- Vous ne pouvez plus modifier la structure des tables sous-jacentes sans supprimer d'abord la vue
- Impossible de supprimer une colonne utilisée dans la vue

```sql
-- Vue avec SCHEMABINDING
CREATE VIEW VueClientsLiee
WITH SCHEMABINDING
AS
    SELECT ClientID, Nom, Email
    FROM dbo.Clients;

-- ❌ ERREUR : Impossible de supprimer la colonne Email
ALTER TABLE Clients DROP COLUMN Email;
-- Message : "Cannot drop column 'Email' because it is being used by object 'VueClientsLiee'"
```

### 5.2 COUNT_BIG(*) au lieu de COUNT(*)

```sql
-- ❌ ERREUR : COUNT(*) n'est pas autorisé
CREATE VIEW VueTest1
WITH SCHEMABINDING
AS
    SELECT
        ClientID,
        COUNT(*) AS Nombre  -- ERREUR
    FROM dbo.Commandes
    GROUP BY ClientID;

-- ✅ CORRECT : COUNT_BIG(*) est obligatoire
CREATE VIEW VueTest2
WITH SCHEMABINDING
AS
    SELECT
        ClientID,
        COUNT_BIG(*) AS Nombre  -- OK
    FROM dbo.Commandes
    GROUP BY ClientID;
```

**Raison :** `COUNT_BIG` retourne un `BIGINT` (8 octets), ce qui évite les dépassements sur de très grandes tables.

### 5.3 Pas de LEFT/RIGHT/FULL OUTER JOIN

Les vues indexées ne peuvent contenir que des **INNER JOIN** ou **CROSS JOIN**.

```sql
-- ❌ ERREUR : LEFT JOIN interdit
CREATE VIEW VueAvecLeftJoin
WITH SCHEMABINDING
AS
    SELECT
        c.ClientID,
        c.Nom,
        COUNT_BIG(co.CommandeID) AS NbCommandes
    FROM dbo.Clients c
    LEFT JOIN dbo.Commandes co ON c.ClientID = co.ClientID  -- ERREUR
    GROUP BY c.ClientID, c.Nom;

-- ✅ CORRECT : INNER JOIN autorisé
CREATE VIEW VueAvecInnerJoin
WITH SCHEMABINDING
AS
    SELECT
        c.ClientID,
        c.Nom,
        COUNT_BIG(co.CommandeID) AS NbCommandes
    FROM dbo.Clients c
    INNER JOIN dbo.Commandes co ON c.ClientID = co.ClientID  -- OK
    GROUP BY c.ClientID, c.Nom;
```

### 5.4 Pas de sous-requêtes

```sql
-- ❌ ERREUR : Sous-requêtes interdites
CREATE VIEW VueAvecSousRequete
WITH SCHEMABINDING
AS
    SELECT
        ClientID,
        Nom,
        (SELECT COUNT(*) FROM dbo.Commandes WHERE ClientID = c.ClientID) AS NbCmd
    FROM dbo.Clients c;  -- ERREUR
```

### 5.5 Pas de fonctions non déterministes

Les fonctions qui retournent des résultats différents à chaque exécution sont interdites.

```sql
-- ❌ ERREUR : GETDATE() est non déterministe
CREATE VIEW VueAvecDate
WITH SCHEMABINDING
AS
    SELECT
        CommandeID,
        DateCommande,
        DATEDIFF(DAY, DateCommande, GETDATE()) AS JoursEcoules  -- ERREUR
    FROM dbo.Commandes;

-- ✅ CORRECT : Expression déterministe
CREATE VIEW VueAvecDateFixe
WITH SCHEMABINDING
AS
    SELECT
        CommandeID,
        DateCommande,
        YEAR(DateCommande) AS Annee  -- OK (déterministe)
    FROM dbo.Commandes;
```

**Fonctions interdites :**
- `GETDATE()`, `GETUTCDATE()`, `SYSDATETIME()`
- `NEWID()` (génération de GUID)
- `RAND()` (nombres aléatoires)
- Fonctions définies par l'utilisateur (UDF) non déterministes

### 5.6 GROUP BY : Toutes les colonnes non agrégées doivent être dans le GROUP BY

```sql
-- ❌ ERREUR : Nom n'est pas dans le GROUP BY
CREATE VIEW VueErreurGroupBy
WITH SCHEMABINDING
AS
    SELECT
        ClientID,
        Nom,  -- Pas dans GROUP BY
        COUNT_BIG(*) AS NbCommandes
    FROM dbo.Commandes
    GROUP BY ClientID;  -- ERREUR

-- ✅ CORRECT
CREATE VIEW VueCorrectGroupBy
WITH SCHEMABINDING
AS
    SELECT
        ClientID,
        COUNT_BIG(*) AS NbCommandes
    FROM dbo.Commandes
    GROUP BY ClientID;
```

### 5.7 Pas de DISTINCT (sauf cas spécifiques)

```sql
-- ❌ ERREUR : DISTINCT généralement interdit
CREATE VIEW VueAvecDistinct
WITH SCHEMABINDING
AS
    SELECT DISTINCT
        Ville
    FROM dbo.Clients;  -- ERREUR dans la plupart des cas
```

### 5.8 Autres restrictions importantes

| Interdit | Raison |
|----------|--------|
| `SELECT *` | Vous devez spécifier explicitement les colonnes |
| `UNION`, `EXCEPT`, `INTERSECT` | Opérateurs d'ensemble interdits |
| `TOP`, `OFFSET-FETCH` | Limitation de lignes interdite |
| `ORDER BY` | Sauf avec TOP (mais TOP est interdit...) |
| Tables dérivées | Sous-requêtes dans FROM interdites |
| CTE (WITH) | Expressions de table communes interdites |
| `HAVING` sans agrégation | Doit avoir au moins une fonction d'agrégation |
| Types de données non précis | FLOAT, REAL, TEXT, NTEXT, IMAGE interdits dans les index |

## 6. Maintenance et Coûts

### 6.1 Maintenance automatique

**Avantage :** SQL Server maintient automatiquement la vue indexée à jour.

```sql
-- Quand vous faites :
INSERT INTO Commandes (ClientID, MontantTotal, DateCommande)
VALUES (5, 1500, '2024-11-18');

-- SQL Server met automatiquement à jour :
-- - La table Commandes (évidemment)
-- - TOUTES les vues indexées qui dépendent de cette table
```

**Processus de mise à jour :**
1. L'INSERT dans `Commandes` est effectué
2. SQL Server identifie toutes les vues indexées affectées
3. Recalcule les agrégations nécessaires
4. Met à jour les données stockées dans les vues indexées

### 6.2 Coût des opérations d'écriture

**ATTENTION :** Les vues indexées ralentissent les opérations INSERT, UPDATE, DELETE.

#### Exemple de l'impact

```sql
-- Sans vue indexée
INSERT INTO Commandes (ClientID, MontantTotal, DateCommande)
VALUES (5, 1500, '2024-11-18');
-- Temps : 2 ms

-- Avec 3 vues indexées sur la table Commandes
INSERT INTO Commandes (ClientID, MontantTotal, DateCommande)
VALUES (5, 1500, '2024-11-18');
-- Temps : 15 ms (7.5x plus lent !)
```

**Pourquoi ?**
- Chaque vue indexée doit être mise à jour
- Les agrégations doivent être recalculées
- Les index de la vue doivent être maintenus

**Règle d'or :** Plus vous avez de vues indexées sur une table, plus les écritures sont lentes.

### 6.3 Espace disque

Les vues indexées consomment de l'espace disque, exactement comme une table.

```sql
-- Voir l'espace utilisé par une vue indexée
EXEC sp_spaceused 'VueStatistiquesVentesIndexee';
```

**Exemple :**
- Table `Commandes` : 10 millions de lignes = 5 GB
- Vue indexée agrégée par client : 100 000 clients = 50 MB

**Impact :** Généralement acceptable car les vues agrégées sont beaucoup plus petites que les tables sources.

## 7. Quand Utiliser les Vues Indexées ?

### 7.1 Cas d'usage idéaux ✅

#### 1. Agrégations coûteuses fréquemment consultées

```sql
-- Rapport de ventes consulté 1000 fois par jour
CREATE VIEW VueRapportVentesMensuel
WITH SCHEMABINDING
AS
    SELECT
        YEAR(DateCommande) AS Annee,
        MONTH(DateCommande) AS Mois,
        COUNT_BIG(*) AS NombreVentes,
        SUM(MontantTotal) AS CA
    FROM dbo.Commandes
    GROUP BY YEAR(DateCommande), MONTH(DateCommande);

CREATE UNIQUE CLUSTERED INDEX IX_RapportMensuel
ON VueRapportVentesMensuel(Annee, Mois);
```

**Bénéfice :** Les 1000 consultations quotidiennes sont ultra-rapides et ne chargent pas la base.

#### 2. Jointures complexes pour reporting

```sql
-- Dashboard avec jointures complexes
CREATE VIEW VueDashboardVentes
WITH SCHEMABINDING
AS
    SELECT
        c.ClientID,
        c.NomEntreprise,
        r.RegionNom,
        COUNT_BIG(co.CommandeID) AS NbCommandes,
        SUM(co.MontantTotal) AS CA
    FROM dbo.Clients c
    INNER JOIN dbo.Regions r ON c.RegionID = r.RegionID
    INNER JOIN dbo.Commandes co ON c.ClientID = co.ClientID
    GROUP BY c.ClientID, c.NomEntreprise, r.RegionNom;
```

#### 3. Tables volumineuses avec agrégations

- Table avec des millions/milliards de lignes
- Requêtes analytiques fréquentes
- Écriture relativement peu fréquente (ex : entrepôt de données)

#### 4. Data warehousing

Les vues indexées sont particulièrement adaptées aux **entrepôts de données** (data warehouses) :
- Lectures très fréquentes
- Écritures en batch (une fois par jour par exemple)
- Agrégations complexes
- Performance critique

---

### 7.2 Quand NE PAS utiliser les vues indexées ❌

#### 1. Tables avec écritures fréquentes (OLTP)

```sql
-- ❌ MAUVAIS : Table de commandes avec 10 000 INSERT/sec
-- La vue indexée ralentirait drastiquement les insertions
```

**Raison :** Chaque écriture doit mettre à jour toutes les vues indexées.

#### 2. Vues complexes qui ne respectent pas les restrictions

```sql
-- ❌ Impossible d'indexer : LEFT JOIN, sous-requêtes, GETDATE()
CREATE VIEW VueComplexe
AS
    SELECT
        c.ClientID,
        (SELECT COUNT(*) FROM Commandes WHERE ClientID = c.ClientID) AS NbCmd,
        DATEDIFF(DAY, c.DateInscription, GETDATE()) AS AncienneteJours
    FROM Clients c
    LEFT JOIN Adresses a ON c.ClientID = a.ClientID;
```

#### 3. Données qui changent constamment

- Tables de logs
- Données en temps réel (capteurs, IoT)
- Tables avec updates massifs fréquents

#### 4. Faible gain de performance attendu

Si la requête est déjà rapide (<100 ms), le coût de maintenance d'une vue indexée n'en vaut probablement pas la peine.

## 8. Utilisation Transparente des Vues Indexées

### 8.1 Optimiseur de requêtes automatique

**Fonctionnalité puissante :** SQL Server peut utiliser automatiquement une vue indexée même si vous ne l'interrogez pas directement !

```sql
-- Vue indexée créée
CREATE VIEW VueStatistiquesClients
WITH SCHEMABINDING
AS
    SELECT
        ClientID,
        COUNT_BIG(*) AS NbCommandes,
        SUM(MontantTotal) AS TotalAchats
    FROM dbo.Commandes
    GROUP BY ClientID;

CREATE UNIQUE CLUSTERED INDEX IX_Stats ON VueStatistiquesClients(ClientID);

-- Vous exécutez cette requête (sans mentionner la vue)
SELECT
    ClientID,
    COUNT(*) AS NbCommandes
FROM Commandes
GROUP BY ClientID;
```

**Ce qui se passe :**
- L'optimiseur détecte que la vue indexée `VueStatistiquesClients` contient les données nécessaires
- Il utilise **automatiquement** la vue indexée au lieu de la table
- Votre requête devient ultra-rapide **sans modification**

**Note :** Cette fonctionnalité est disponible dans les éditions Enterprise et Developer de SQL Server.

### 8.2 Forcer l'utilisation d'une vue indexée

Vous pouvez forcer SQL Server à utiliser une vue indexée avec le hint `NOEXPAND`.

```sql
-- Forcer l'utilisation de la vue indexée
SELECT ClientID, TotalAchats
FROM VueStatistiquesClients WITH (NOEXPAND)
WHERE TotalAchats > 10000;
```

## 9. Créer des Index Supplémentaires

Après avoir créé l'index clustered, vous pouvez créer des **index non-clustered** supplémentaires sur la vue.

```sql
-- Index clustered (déjà créé)
CREATE UNIQUE CLUSTERED INDEX IX_VueStats_ClientID
ON VueStatistiquesVentesIndexee(ClientID);

-- Index non-clustered supplémentaire
CREATE NONCLUSTERED INDEX IX_VueStats_TotalAchats
ON VueStatistiquesVentesIndexee(TotalAchats);

-- Maintenant cette requête utilise l'index non-clustered
SELECT ClientID, TotalAchats
FROM VueStatistiquesVentesIndexee
WHERE TotalAchats > 50000;  -- Très rapide grâce à l'index
```

## 10. Exemple Complet : Système d'Analyse de Ventes

### Scénario

Vous avez une table `Commandes` avec 50 millions de lignes et vous devez générer des rapports de ventes toutes les heures.

### Étape 1 : Créer la vue indexée

```sql
-- Vue pour les statistiques de ventes par produit
CREATE VIEW VueAnalyseVentesProduits
WITH SCHEMABINDING
AS
    SELECT
        p.ProduitID,
        p.NomProduit,
        p.CategorieID,
        COUNT_BIG(*) AS NombreVentes,
        SUM(dc.Quantite) AS QuantiteTotale,
        SUM(dc.Quantite * dc.PrixUnitaire) AS ChiffreAffaires,
        AVG(dc.PrixUnitaire) AS PrixMoyen
    FROM dbo.Produits p
    INNER JOIN dbo.DetailsCommande dc ON p.ProduitID = dc.ProduitID
    INNER JOIN dbo.Commandes c ON dc.CommandeID = c.CommandeID
    WHERE c.Statut = 'Validée'
    GROUP BY p.ProduitID, p.NomProduit, p.CategorieID;

-- Créer l'index clustered unique
CREATE UNIQUE CLUSTERED INDEX IX_AnalyseVentesProduits
ON VueAnalyseVentesProduits(ProduitID);

-- Index supplémentaire pour les requêtes par catégorie
CREATE NONCLUSTERED INDEX IX_AnalyseVentes_Categorie
ON VueAnalyseVentesProduits(CategorieID)
INCLUDE (ChiffreAffaires, QuantiteTotale);
```

### Étape 2 : Utilisation

```sql
-- Top 10 des produits les plus vendus (ultra-rapide)
SELECT TOP 10
    NomProduit,
    QuantiteTotale,
    ChiffreAffaires
FROM VueAnalyseVentesProduits
ORDER BY QuantiteTotale DESC;

-- Analyse par catégorie (utilise l'index non-clustered)
SELECT
    CategorieID,
    SUM(ChiffreAffaires) AS CATotalCategorie,
    AVG(PrixMoyen) AS PrixMoyenCategorie
FROM VueAnalyseVentesProduits
GROUP BY CategorieID;
```

**Résultat :**
- Requêtes qui prenaient 30 secondes → maintenant 0.1 seconde
- Pas de surcharge sur la table `Commandes`
- Rapports générés instantanément

## 11. Surveillance et Maintenance

### 11.1 Vérifier l'existence d'une vue indexée

```sql
-- Lister toutes les vues indexées
SELECT
    OBJECT_NAME(object_id) AS VueNom,
    name AS IndexNom,
    type_desc AS TypeIndex
FROM sys.indexes
WHERE object_id IN (
    SELECT object_id
    FROM sys.views
)
AND index_id > 0;  -- index_id > 0 signifie qu'il y a un index
```

### 11.2 Voir l'utilisation d'une vue indexée

```sql
-- Statistiques d'utilisation
SELECT
    OBJECT_NAME(s.object_id) AS VueNom,
    i.name AS IndexNom,
    s.user_seeks AS Recherches,
    s.user_scans AS Balayages,
    s.user_lookups AS Consultations,
    s.user_updates AS MisesAJour
FROM sys.dm_db_index_usage_stats s
INNER JOIN sys.indexes i ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE OBJECT_NAME(s.object_id) = 'VueStatistiquesVentesIndexee';
```

### 11.3 Supprimer une vue indexée

```sql
-- Supprimer d'abord les index non-clustered
DROP INDEX IX_VueStats_TotalAchats ON VueStatistiquesVentesIndexee;

-- Supprimer l'index clustered
DROP INDEX IX_VueStats_ClientID ON VueStatistiquesVentesIndexee;

-- Maintenant supprimer la vue
DROP VIEW VueStatistiquesVentesIndexee;
```

## 13. Alternatives aux Vues Indexées

Si les restrictions sont trop contraignantes, considérez ces alternatives :

### 13.1 Tables de cache / Tables d'agrégation

```sql
-- Créer une table physique
CREATE TABLE CacheStatistiquesVentes (
    ClientID INT PRIMARY KEY,
    NombreCommandes INT,
    TotalAchats DECIMAL(10,2),
    DerniereMiseAJour DATETIME DEFAULT GETDATE()
);

-- Procédure de rafraîchissement (exécutée périodiquement)
CREATE PROCEDURE SpRefreshCacheVentes
AS
BEGIN
    TRUNCATE TABLE CacheStatistiquesVentes;

    INSERT INTO CacheStatistiquesVentes (ClientID, NombreCommandes, TotalAchats)
    SELECT
        ClientID,
        COUNT(*),
        SUM(MontantTotal)
    FROM Commandes
    GROUP BY ClientID;
END;
```

**Avantages :**
- Aucune restriction sur la requête
- Contrôle total sur le moment du rafraîchissement
- Pas d'impact sur les écritures (sauf lors du refresh)

**Inconvénients :**
- Données potentiellement obsolètes
- Rafraîchissement manuel (via job)

### 13.2 Columnstore Index

Pour les entrepôts de données, les index columnstore sont souvent plus appropriés.

```sql
-- Index columnstore sur une table
CREATE NONCLUSTERED COLUMNSTORE INDEX IX_Commandes_Columnstore
ON Commandes (DateCommande, ClientID, MontantTotal, Quantite);
```

**Avantages :**
- Compression excellente
- Performance exceptionnelle pour les agrégations
- Moins de restrictions que les vues indexées

## Résumé

### 🎯 Points Clés

**Qu'est-ce qu'une vue indexée ?**
- Vue dont les résultats sont **physiquement stockés** sur le disque
- Permet des performances exceptionnelles en lecture
- Maintenue automatiquement par SQL Server

**Création en 2 étapes :**
1. `CREATE VIEW ... WITH SCHEMABINDING`
2. `CREATE UNIQUE CLUSTERED INDEX`

**⚠️ Restrictions importantes :**
- `WITH SCHEMABINDING` obligatoire
- `COUNT_BIG(*)` au lieu de `COUNT(*)`
- Pas de `LEFT/RIGHT/FULL JOIN`
- Pas de sous-requêtes
- Pas de fonctions non déterministes
- Beaucoup d'autres limitations

**✅ Utiliser quand :**
- Agrégations coûteuses consultées fréquemment
- Tables volumineuses avec peu d'écritures
- Data warehousing / reporting
- Gain de performance significatif attendu

**❌ Éviter quand :**
- Tables OLTP avec écritures fréquentes
- Requêtes complexes qui ne respectent pas les restrictions
- Gain de performance marginal

**💰 Coûts :**
- Ralentissement des opérations d'écriture
- Consommation d'espace disque
- Complexité de maintenance

Les vues indexées sont un **outil puissant mais spécialisé**. Utilisez-les judicieusement pour les cas où le gain de performance en lecture justifie le coût de maintenance en écriture.
