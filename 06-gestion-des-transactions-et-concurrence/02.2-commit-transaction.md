# 6.2.2 COMMIT TRANSACTION

## Introduction

Dans la section précédente, nous avons appris à démarrer une transaction avec `BEGIN TRANSACTION`. Maintenant, nous allons découvrir comment **valider** et **rendre permanentes** les modifications effectuées dans une transaction grâce à la commande `COMMIT TRANSACTION`.

`COMMIT` est l'une des deux façons de terminer une transaction (l'autre étant `ROLLBACK`). C'est le moment décisif où vous dites à SQL Server : "Tout s'est bien passé, enregistre définitivement toutes ces modifications."

## Qu'est-ce que COMMIT TRANSACTION ?

`COMMIT TRANSACTION` (ou simplement `COMMIT`) est une commande T-SQL qui **valide** une transaction en rendant **permanentes** toutes les modifications effectuées depuis le `BEGIN TRANSACTION`.

Une fois le COMMIT exécuté :
- ✅ Les modifications sont **définitivement écrites** dans la base de données
- ✅ Les modifications deviennent **visibles** pour tous les autres utilisateurs
- ✅ Les **verrous** posés par la transaction sont **libérés**
- ✅ La transaction est **terminée**

### Analogie : Signer le Contrat

Imaginez que vous achetez une voiture :

```
Phase 1 : Négociation (BEGIN TRANSACTION)
├─► Vous discutez du prix
├─► Vous essayez la voiture
├─► Vous vérifiez les papiers
└─► Tout est encore modifiable/annulable

Phase 2 : Signature (COMMIT TRANSACTION)
├─► Vous signez le contrat de vente ✍️
├─► Le paiement est effectué
├─► Les clés vous sont remises
└─► C'EST DÉFINITIF, la voiture est à vous !
```

Le `COMMIT` est comme la signature du contrat : à partir de ce moment, c'est officiel et permanent.

---

## Syntaxe de COMMIT TRANSACTION

### Forme Simple (La Plus Courante)

```sql
COMMIT TRANSACTION;
-- ou simplement :
COMMIT;
-- ou en abrégé :
COMMIT TRAN;
```

Ces trois formes sont équivalentes et interchangeables. La forme `COMMIT;` est la plus concise et la plus utilisée.

### Forme avec Nom (Optionnel)

```sql
COMMIT TRANSACTION nom_transaction;
-- ou :
COMMIT TRAN nom_transaction;
```

Le nom doit correspondre au nom donné lors du `BEGIN TRANSACTION`. Cependant, **le nom est ignoré** lors du COMMIT (il sert principalement à la lisibilité du code et au débogage).

### Quelle Forme Utiliser ?

Pour la clarté et la simplicité, la plupart des développeurs utilisent simplement :

```sql
BEGIN TRANSACTION;
    -- Opérations...
COMMIT;
```

## Ce qui Se Passe Lors d'un COMMIT

Quand vous exécutez `COMMIT TRANSACTION`, SQL Server effectue plusieurs opérations importantes en arrière-plan :

### 1. Écriture dans le Journal de Transactions

Toutes les modifications sont définitivement **écrites dans le journal de transactions** (Transaction Log) sur le disque.

```
Mémoire RAM                    Disque Dur
┌──────────────┐               ┌─────────────────┐
│ Modifications│   COMMIT      │ Transaction Log │
│ temporaires  │──────────────►│   📝 Écrit      │
└──────────────┘               └─────────────────┘
                                      │
                                      ▼
                               ┌─────────────────┐
                               │ Fichiers de     │
                               │ données         │
                               │   💾 Écrit      │
                               └─────────────────┘
```

### 2. Libération des Verrous

SQL Server **libère tous les verrous** qui avaient été posés pendant la transaction. Les autres utilisateurs qui attendaient peuvent maintenant accéder aux ressources.

```
Pendant la Transaction :
┌──────────────────┐
│ Transaction A    │──► 🔒 Verrou sur Table Comptes
└──────────────────┘
         │
         │ Autres utilisateurs : ⏳ EN ATTENTE
         │
         ▼
       COMMIT
         │
         ▼
┌──────────────────┐
│ Verrous libérés  │──► ✅ Table Comptes accessible
└──────────────────┘
         │
         │ Autres utilisateurs : ✓ PEUVENT ACCÉDER
```

### 3. Visibilité des Données

Les modifications deviennent **visibles** pour tous les autres utilisateurs connectés à la base de données.

```
Avant COMMIT :
├─► Transaction A voit ses modifications ✓
└─► Autres utilisateurs NE voient PAS les modifications ✗

Après COMMIT :
└─► TOUS les utilisateurs voient les modifications ✓
```

### 4. Décrémentation de @@TRANCOUNT

Le compteur `@@TRANCOUNT` est décrémenté de 1. Si le compteur atteint 0, la transaction est réellement validée.

```sql
SELECT @@TRANCOUNT; -- 0

BEGIN TRANSACTION;
SELECT @@TRANCOUNT; -- 1

    -- Opérations...

COMMIT TRANSACTION;
SELECT @@TRANCOUNT; -- 0 (transaction terminée)
```

## Exemples Détaillés

### Exemple 1 : Transaction Simple avec COMMIT

Voici l'exemple le plus basique d'une transaction validée :

```sql
-- Démarrer la transaction
BEGIN TRANSACTION;

    -- Ajouter un nouveau client
    INSERT INTO Clients (ClientID, Nom, Email, DateInscription)
    VALUES (1001, 'Sophie Martin', 'sophie.martin@example.com', GETDATE());

    -- Ajouter son adresse
    INSERT INTO Adresses (ClientID, Rue, Ville, CodePostal)
    VALUES (1001, '15 Avenue des Champs', 'Paris', '75008');

-- Valider la transaction (rendre permanent)
COMMIT;

PRINT '✓ Client créé avec succès !';
```

**Ce qui se passe :**
1. `BEGIN TRANSACTION` : La transaction commence, SQL Server pose des verrous
2. Les deux `INSERT` : Les données sont ajoutées en mémoire (temporairement)
3. `COMMIT` : Les données sont écrites sur le disque, les verrous sont libérés
4. Les autres utilisateurs voient maintenant le nouveau client

### Exemple 2 : Transaction avec Vérification avant COMMIT

Souvent, vous voulez vérifier que tout s'est bien passé avant de valider :

```sql
BEGIN TRANSACTION;

    -- Débiter un compte
    UPDATE Comptes
    SET Solde = Solde - 500
    WHERE NumeroCompte = 'A123';

    -- Vérifier que la mise à jour a bien eu lieu
    IF @@ROWCOUNT = 0
    BEGIN
        -- Le compte n'existe pas
        ROLLBACK;
        PRINT '✗ Erreur : Compte inexistant, transaction annulée.';
        RETURN; -- Sortir du script
    END

    -- Créditer un autre compte
    UPDATE Comptes
    SET Solde = Solde + 500
    WHERE NumeroCompte = 'B456';

    -- Vérifier que la mise à jour a bien eu lieu
    IF @@ROWCOUNT = 0
    BEGIN
        -- Le compte destinataire n'existe pas
        ROLLBACK;
        PRINT '✗ Erreur : Compte destinataire inexistant, transaction annulée.';
        RETURN;
    END

    -- Vérifier qu''aucun compte n''est en négatif
    IF EXISTS (SELECT 1 FROM Comptes WHERE Solde < 0)
    BEGIN
        ROLLBACK;
        PRINT '✗ Erreur : Solde insuffisant, transaction annulée.';
        RETURN;
    END

    -- Si on arrive ici, tout est OK
    COMMIT;
    PRINT '✓ Transfert effectué avec succès !';

```

**Analyse :**
- On effectue des vérifications après chaque opération
- Si une vérification échoue → `ROLLBACK` (annulation)
- Si toutes les vérifications passent → `COMMIT` (validation)

### Exemple 3 : Transaction avec TRY...CATCH

La meilleure pratique est d'utiliser TRY...CATCH pour gérer les erreurs automatiquement :

```sql
BEGIN TRANSACTION;

BEGIN TRY
    -- Opération 1 : Créer une commande
    INSERT INTO Commandes (ClientID, DateCommande, Statut, Total)
    VALUES (123, GETDATE(), 'En cours', 0);

    DECLARE @CommandeID INT = SCOPE_IDENTITY();
    DECLARE @Total DECIMAL(10,2) = 0;

    -- Opération 2 : Ajouter des articles
    INSERT INTO LignesCommande (CommandeID, ProduitID, Quantite, PrixUnitaire)
    VALUES
        (@CommandeID, 456, 2, 49.99),
        (@CommandeID, 789, 1, 99.99);

    -- Calculer le total
    SET @Total = (2 * 49.99) + (1 * 99.99);

    -- Opération 3 : Mettre à jour le total de la commande
    UPDATE Commandes
    SET Total = @Total
    WHERE CommandeID = @CommandeID;

    -- Opération 4 : Mettre à jour le stock
    UPDATE Produits
    SET StockDisponible = StockDisponible - 2
    WHERE ProduitID = 456;

    UPDATE Produits
    SET StockDisponible = StockDisponible - 1
    WHERE ProduitID = 789;

    -- Si tout s'est bien passé, VALIDER
    COMMIT;
    PRINT '✓ Commande ' + CAST(@CommandeID AS VARCHAR) + ' créée avec succès !';

END TRY
BEGIN CATCH
    -- En cas d'erreur, ANNULER
    ROLLBACK;

    -- Afficher l'erreur
    PRINT '✗ Erreur lors de la création de la commande :';
    PRINT '   Code erreur : ' + CAST(ERROR_NUMBER() AS VARCHAR);
    PRINT '   Message : ' + ERROR_MESSAGE();
    PRINT '   Transaction annulée.';
END CATCH;
```

**Avantages de cette approche :**
- ✅ Gestion automatique des erreurs
- ✅ Code plus propre et lisible
- ✅ Garantie que la transaction sera annulée en cas d'erreur
- ✅ Informations détaillées sur l'erreur

### Exemple 4 : Transaction Complexe avec Plusieurs Validations

Voici un exemple plus réaliste de traitement de commande avec plusieurs validations métier :

```sql
BEGIN TRANSACTION;

BEGIN TRY
    -- Variables
    DECLARE @ClientID INT = 123;
    DECLARE @ProduitID INT = 456;
    DECLARE @Quantite INT = 5;
    DECLARE @StockActuel INT;
    DECLARE @CreditClient DECIMAL(10,2);
    DECLARE @PrixTotal DECIMAL(10,2);

    -- 1. Vérifier le stock disponible
    SELECT @StockActuel = StockDisponible
    FROM Produits
    WHERE ProduitID = @ProduitID;

    IF @StockActuel < @Quantite
    BEGIN
        RAISERROR('Stock insuffisant. Disponible: %d, Demandé: %d', 16, 1, @StockActuel, @Quantite);
    END

    -- 2. Calculer le prix total
    SELECT @PrixTotal = Prix * @Quantite
    FROM Produits
    WHERE ProduitID = @ProduitID;

    -- 3. Vérifier le crédit du client
    SELECT @CreditClient = LimiteCredit - EncoursCreditActuel
    FROM Clients
    WHERE ClientID = @ClientID;

    IF @CreditClient < @PrixTotal
    BEGIN
        RAISERROR('Crédit insuffisant. Disponible: %.2f, Nécessaire: %.2f', 16, 1, @CreditClient, @PrixTotal);
    END

    -- 4. Toutes les vérifications sont OK, on procède

    -- Créer la commande
    INSERT INTO Commandes (ClientID, DateCommande, Total, Statut)
    VALUES (@ClientID, GETDATE(), @PrixTotal, 'Confirmée');

    DECLARE @CommandeID INT = SCOPE_IDENTITY();

    -- Ajouter les lignes de commande
    INSERT INTO LignesCommande (CommandeID, ProduitID, Quantite, PrixUnitaire, Montant)
    SELECT @CommandeID, @ProduitID, @Quantite, Prix, @PrixTotal
    FROM Produits
    WHERE ProduitID = @ProduitID;

    -- Mettre à jour le stock
    UPDATE Produits
    SET StockDisponible = StockDisponible - @Quantite
    WHERE ProduitID = @ProduitID;

    -- Mettre à jour l'encours crédit du client
    UPDATE Clients
    SET EncoursCreditActuel = EncoursCreditActuel + @PrixTotal
    WHERE ClientID = @ClientID;

    -- Enregistrer dans l'historique
    INSERT INTO HistoriqueCommandes (CommandeID, Action, DateAction)
    VALUES (@CommandeID, 'Commande créée', GETDATE());

    -- TOUT EST OK : VALIDER
    COMMIT;

    PRINT '✓ Commande ' + CAST(@CommandeID AS VARCHAR) + ' créée et validée avec succès !';
    PRINT '  Total : ' + CAST(@PrixTotal AS VARCHAR) + ' €';

END TRY
BEGIN CATCH
    -- UNE ERREUR S'EST PRODUITE : ANNULER
    ROLLBACK;

    PRINT '✗ Impossible de créer la commande :';
    PRINT '  ' + ERROR_MESSAGE();

END CATCH;
```

**Points clés de cet exemple :**
1. On effectue toutes les **vérifications métier** d'abord
2. Si une vérification échoue, on lève une erreur avec `RAISERROR`
3. Si tout est OK, on effectue toutes les modifications
4. On `COMMIT` seulement si TOUT a réussi
5. En cas d'erreur, le `CATCH` fait un `ROLLBACK` automatique

## COMMIT et les Transactions Imbriquées

Quand vous avez des transactions imbriquées, `COMMIT` se comporte différemment :

```sql
SELECT @@TRANCOUNT; -- 0

BEGIN TRANSACTION; -- Transaction niveau 1
SELECT @@TRANCOUNT; -- 1

    UPDATE Table1 SET Colonne = 'A';

    BEGIN TRANSACTION; -- Transaction niveau 2 (imbriquée)
    SELECT @@TRANCOUNT; -- 2

        UPDATE Table2 SET Colonne = 'B';

    COMMIT; -- Décrémente seulement @@TRANCOUNT
    SELECT @@TRANCOUNT; -- 1 (toujours en transaction !)

    UPDATE Table3 SET Colonne = 'C';

COMMIT; -- C'est ce COMMIT qui valide réellement tout
SELECT @@TRANCOUNT; -- 0 (transaction terminée)
```

**Important à comprendre :**
- Seul le **dernier COMMIT** (celui qui ramène `@@TRANCOUNT` à 0) **valide réellement** les données
- Les COMMIT intermédiaires ne font que **décrémenter** le compteur
- Si un ROLLBACK survient à n'importe quel niveau, **TOUT** est annulé

### Illustration Visuelle

```
@@TRANCOUNT:  0 ──► 1 ──────► 2 ──► 1 ───────────────► 0
                │             │     │                  │
              BEGIN         BEGIN COMMIT            COMMIT
              TRAN          TRAN                      │
                │             │     │                 │
                │             │     │                 ▼
                │             │     │           ✅ VALIDATION
                │             │     │              RÉELLE
                │             │     │
                ▼             ▼     ▼
              Modif 1      Modif 2  Modif 3
```

## COMMIT vs COMMIT avec Nom

Bien que vous puissiez nommer votre COMMIT, cela n'a **aucun effet** sur le comportement :

```sql
BEGIN TRANSACTION MaTransaction;

    UPDATE Produits SET Prix = Prix * 1.1;

-- Ces deux lignes sont IDENTIQUES en comportement :
COMMIT TRANSACTION MaTransaction;
-- ou simplement :
COMMIT;
```

Le nom dans `COMMIT TRANSACTION MaTransaction` est **ignoré** par SQL Server. Il sert uniquement à :
- Rendre le code plus lisible
- Apparier visuellement BEGIN et COMMIT
- Faciliter le débogage

**Recommandation** : Utilisez simplement `COMMIT;` pour plus de simplicité.

## Bonnes Pratiques avec COMMIT

### ✅ Validez Dès que Possible

Plus une transaction reste ouverte longtemps, plus elle bloque les autres utilisateurs.

**Mauvais exemple** :
```sql
BEGIN TRANSACTION;
    UPDATE Produits SET Prix = Prix * 1.1;

    -- Traitement long qui ne nécessite pas la transaction
    DECLARE @i INT = 0;
    WHILE @i < 1000000
    BEGIN
        SET @i = @i + 1;
    END

COMMIT; -- Les verrous ont été maintenus inutilement
```

**Bon exemple** :
```sql
-- Traitement long AVANT la transaction
DECLARE @i INT = 0;
WHILE @i < 1000000
BEGIN
    SET @i = @i + 1;
END

-- Transaction courte
BEGIN TRANSACTION;
    UPDATE Produits SET Prix = Prix * 1.1;
COMMIT; -- Verrous libérés rapidement
```

### ✅ Un Seul Chemin de COMMIT

Il est plus clair d'avoir un seul point de COMMIT à la fin :

**Moins clair** :
```sql
BEGIN TRANSACTION;
    IF @Condition = 1
    BEGIN
        UPDATE Table1 ...;
        COMMIT; -- COMMIT ici
    END
    ELSE
    BEGIN
        UPDATE Table2 ...;
        COMMIT; -- COMMIT là
    END
```

**Plus clair** :
```sql
BEGIN TRANSACTION;
BEGIN TRY
    IF @Condition = 1
        UPDATE Table1 ...;
    ELSE
        UPDATE Table2 ...;

    -- Un seul COMMIT à la fin
    COMMIT;
END TRY
BEGIN CATCH
    ROLLBACK;
    THROW;
END CATCH;
```

### ✅ Vérifiez @@TRANCOUNT avant COMMIT

Dans les procédures stockées complexes, vérifiez qu'une transaction est bien active :

```sql
-- Vérifier qu'une transaction est en cours
IF @@TRANCOUNT > 0
BEGIN
    COMMIT;
    PRINT 'Transaction validée.';
END
ELSE
BEGIN
    PRINT 'Aucune transaction à valider.';
END
```

### ✅ Documentez Pourquoi Vous Validez

Ajoutez des commentaires expliquant ce qui a été accompli :

```sql
BEGIN TRANSACTION;
    -- Opérations...

-- COMMIT car :
-- - Toutes les validations métier ont réussi
-- - Le stock a été mis à jour correctement
-- - La commande et ses lignes sont cohérentes
COMMIT;
```

### ✅ Loggez les Validations Importantes

Pour les opérations critiques, enregistrez dans une table d'audit :

```sql
BEGIN TRANSACTION;
BEGIN TRY
    -- Opérations critiques...
    UPDATE CompteBancaire SET Solde = Solde - 10000;

    -- Enregistrer dans l'audit
    INSERT INTO AuditOperations (TypeOperation, Montant, DateOperation, Utilisateur)
    VALUES ('Retrait', 10000, GETDATE(), SYSTEM_USER);

    COMMIT;

END TRY
BEGIN CATCH
    ROLLBACK;
    THROW;
END CATCH;
```

## Erreurs Courantes avec COMMIT

### ❌ Erreur 1 : COMMIT sans BEGIN TRANSACTION

```sql
-- Aucune transaction en cours
UPDATE Produits SET Prix = Prix * 1.1;
COMMIT; -- ⚠️ Pas d'erreur, mais inutile
```

**Ce qui se passe** : L'UPDATE est déjà auto-validé. Le COMMIT ne fait rien (mais ne cause pas d'erreur).

### ❌ Erreur 2 : Oublier le COMMIT

```sql
BEGIN TRANSACTION;
    UPDATE Produits SET Prix = Prix * 1.1;
-- ⚠️ OUBLI : Pas de COMMIT ni de ROLLBACK
```

**Conséquence** :
- La transaction reste ouverte
- Les verrous restent actifs
- Les autres utilisateurs sont bloqués
- Risque de timeout et de problèmes de performance graves

### ❌ Erreur 3 : COMMIT après une Erreur Non Gérée

```sql
BEGIN TRANSACTION;
    UPDATE Table1 SET Colonne = 'A';
    UPDATE Table2 SET Colonne = 'B'; -- Cette ligne échoue (erreur SQL)
    -- Le script continue quand même !
    UPDATE Table3 SET Colonne = 'C';
COMMIT; -- ⚠️ On valide même si une erreur s'est produite
```

**Solution** : Toujours utiliser TRY...CATCH

### ❌ Erreur 4 : COMMIT Conditionnel Mal Géré

```sql
BEGIN TRANSACTION;
    UPDATE Table1 ...;

    IF @Erreur = 1
        ROLLBACK;
    -- ⚠️ Si @Erreur = 1, la transaction est annulée
    -- mais le script continue !

    UPDATE Table2 ...; -- Cette ligne s'exécute en auto-commit
COMMIT; -- ⚠️ Erreur : pas de transaction active
```

**Solution** : Utiliser RETURN après ROLLBACK

```sql
BEGIN TRANSACTION;
    UPDATE Table1 ...;

    IF @Erreur = 1
    BEGIN
        ROLLBACK;
        RETURN; -- ✓ Sortir du script
    END

    UPDATE Table2 ...;
COMMIT;
```

## COMMIT et Performance

### Impact Positif : Libération des Verrous

Dès que vous faites COMMIT, les verrous sont libérés, permettant aux autres utilisateurs de continuer leur travail.

```
Temps ──────────────────────────────►
        │
BEGIN   │  ← Verrous posés 🔒
TRAN    │
        │  Utilisateur B attend ⏳
        │  Utilisateur C attend ⏳
        │
Opérations...
        │
COMMIT  │  ← Verrous libérés ✅
        │
        │  Utilisateur B continue ▶
        │  Utilisateur C continue ▶
```

### Impact sur le Disque

COMMIT force l'écriture du journal de transactions sur le disque, ce qui prend du temps :

```
Opération       Temps relatif
─────────────────────────────
UPDATE (RAM)    ⚡ Très rapide
INSERT (RAM)    ⚡ Très rapide
DELETE (RAM)    ⚡ Très rapide
COMMIT (Disque) 🐌 Plus lent (I/O disque)
```

**Conseil** : Regroupez plusieurs opérations dans une transaction plutôt que de faire de multiples petites transactions.

**Moins efficace** :
```sql
-- 1000 transactions séparées = 1000 écritures disque
DECLARE @i INT = 1;
WHILE @i <= 1000
BEGIN
    BEGIN TRANSACTION;
        INSERT INTO MaTable VALUES (@i);
    COMMIT; -- Écriture disque à chaque fois 💾
    SET @i = @i + 1;
END
```

**Plus efficace** :
```sql
-- 1 seule transaction = 1 écriture disque
BEGIN TRANSACTION;
    DECLARE @i INT = 1;
    WHILE @i <= 1000
    BEGIN
        INSERT INTO MaTable VALUES (@i);
        SET @i = @i + 1;
    END
COMMIT; -- Une seule écriture disque 💾
```

## Résumé : BEGIN TRANSACTION + COMMIT = Transaction Complète

```sql
-- Structure de base d'une transaction réussie
BEGIN TRANSACTION;                    -- 1️⃣ Démarrage

    -- Vos opérations SQL ici
    INSERT INTO ...                   -- 2️⃣ Modifications
    UPDATE ...                        --
    DELETE ...                        --

COMMIT;                               -- 3️⃣ Validation

-- À ce stade :
-- ✅ Toutes les modifications sont permanentes
-- ✅ Les verrous sont libérés
-- ✅ Les autres utilisateurs voient les changements
-- ✅ Impossible d'annuler (sauf restauration de backup)
```

## Points Clés à Retenir

### ✓ COMMIT rend les modifications permanentes

Une fois validées, les modifications ne peuvent plus être annulées (sauf restauration de sauvegarde).

### ✓ COMMIT libère tous les verrous

Les autres utilisateurs peuvent immédiatement accéder aux ressources.

### ✓ COMMIT écrit sur le disque

C'est l'opération qui garantit la durabilité (le "D" de ACID).

### ✓ Toujours utiliser COMMIT ou ROLLBACK

Chaque BEGIN TRANSACTION doit se terminer par l'un ou l'autre.

### ✓ COMMIT dans TRY, ROLLBACK dans CATCH

C'est le pattern le plus sûr pour gérer les transactions.

### ✓ Les transactions imbriquées nécessitent plusieurs COMMIT

Seul le dernier COMMIT (@@TRANCOUNT = 0) valide réellement.

### ✓ Gardez les transactions courtes

Plus vite vous faites COMMIT, moins vous bloquez les autres.

### ✓ Le nom dans COMMIT est ignoré

`COMMIT TRANSACTION MaTransaction;` équivaut à `COMMIT;`

---

## Conclusion

`COMMIT TRANSACTION` est la commande qui scelle le sort de vos modifications. C'est le moment décisif où vous dites : "J'ai vérifié, tout est correct, rendez ces changements permanents."

**La règle d'or** : Toute transaction commencée avec `BEGIN TRANSACTION` doit se terminer soit par un `COMMIT` (tout va bien), soit par un `ROLLBACK` (quelque chose s'est mal passé). Ne laissez jamais une transaction ouverte.

Dans la prochaine section, nous découvrirons le pendant de COMMIT : la commande `ROLLBACK TRANSACTION`, qui permet d'annuler une transaction en cas d'erreur.
