# 5.7.4 Triggers INSTEAD OF

## Introduction : Une différence fondamentale

Jusqu'à présent, nous avons vu les triggers **AFTER** (ou FOR) qui s'exécutent **après** que l'opération DML ait été effectuée. Les triggers **INSTEAD OF** fonctionnent de manière radicalement différente :

**Ils interceptent l'opération AVANT qu'elle ne soit exécutée et la remplacent complètement.**

### Analogie pour comprendre

Imaginez deux types de gardiens de sécurité :

**Trigger AFTER** (gardien qui agit après) :
- Laisse entrer le visiteur dans le bâtiment
- Puis enregistre son passage dans un registre
- "Après votre entrée, je note votre passage"

**Trigger INSTEAD OF** (gardien qui intercepte) :
- Intercepte le visiteur AVANT qu'il n'entre
- Décide quoi faire : le laisser entrer, le rediriger ailleurs, ou le refuser
- Doit gérer l'entrée lui-même
- "Au lieu de vous laisser entrer directement, je vais gérer votre entrée moi-même"

## Comparaison AFTER vs INSTEAD OF

### Trigger AFTER

```
1. Utilisateur exécute INSERT INTO Table VALUES (...)
2. SQL Server EFFECTUE l'insertion dans la table ✅
3. Le trigger AFTER s'exécute
4. Le trigger peut consulter les données insérées (INSERTED)
5. Le trigger peut annuler avec ROLLBACK si nécessaire
```

### Trigger INSTEAD OF

```
1. Utilisateur exécute INSERT INTO Table VALUES (...)
2. SQL Server INTERCEPTE la commande 🛑
3. Le trigger INSTEAD OF s'exécute
4. Le trigger DOIT coder lui-même l'insertion (ou ne rien faire)
5. SQL Server ne fait RIEN d'autre automatiquement
```

### Différence visuelle

```sql
-- Avec un trigger AFTER
INSERT INTO Clients (Nom, Prenom) VALUES ('Dupont', 'Jean');
-- SQL Server insère réellement dans Clients
-- Puis le trigger fait ses opérations supplémentaires

-- Avec un trigger INSTEAD OF
INSERT INTO Clients (Nom, Prenom) VALUES ('Dupont', 'Jean');
-- SQL Server NE fait PAS l'insertion
-- Le trigger doit tout gérer lui-même
```

## Syntaxe de base

```sql
CREATE TRIGGER nom_du_trigger
ON nom_de_la_table_ou_vue
INSTEAD OF {INSERT | UPDATE | DELETE}
AS
BEGIN
    -- Votre logique ici
    -- VOUS devez effectuer l'opération vous-même si vous le souhaitez
END;
```

**Point crucial** : Contrairement à AFTER, un trigger INSTEAD OF ne peut réagir qu'à **UN SEUL type d'opération** (INSERT, UPDATE ou DELETE, mais pas plusieurs à la fois).

## Cas d'usage 1 : Rendre une vue modifiable

### Le problème avec les vues complexes

Les vues basées sur plusieurs tables ou avec des agrégations ne sont généralement **pas modifiables** directement :

```sql
-- Création d'une vue qui joint deux tables
CREATE VIEW vue_Clients_Adresses AS
SELECT
    c.ClientID,
    c.Nom,
    c.Prenom,
    a.Ville,
    a.CodePostal
FROM Clients c
INNER JOIN Adresses a ON c.AdresseID = a.AdresseID;

-- Tentative d'insertion dans la vue
INSERT INTO vue_Clients_Adresses (Nom, Prenom, Ville, CodePostal)
VALUES ('Dupont', 'Jean', 'Paris', '75001');
-- ❌ ERREUR : Cannot insert into view - it's based on multiple tables
```

### Solution : INSTEAD OF pour gérer l'insertion

```sql
CREATE TRIGGER trg_vue_Clients_Adresses_Insert
ON vue_Clients_Adresses
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- Étape 1 : Insérer dans la table Adresses
    INSERT INTO Adresses (Ville, CodePostal)
    SELECT DISTINCT Ville, CodePostal
    FROM INSERTED;

    -- Étape 2 : Récupérer l'ID de l'adresse créée
    DECLARE @AdresseID INT = SCOPE_IDENTITY();

    -- Étape 3 : Insérer dans la table Clients avec l'AdresseID
    INSERT INTO Clients (Nom, Prenom, AdresseID)
    SELECT Nom, Prenom, @AdresseID
    FROM INSERTED;
END;
```

**Ce qui se passe maintenant** :

```
1. Utilisateur : INSERT INTO vue_Clients_Adresses (...)
2. SQL Server intercepte la commande
3. Le trigger s'exécute et :
   a. Crée l'adresse dans la table Adresses
   b. Crée le client dans la table Clients
4. L'utilisateur voit son INSERT réussir, sans savoir que deux tables ont été modifiées !
```

> ⚠️ **Limite de cet exemple : il ne fonctionne correctement que pour UNE seule ligne !** `SCOPE_IDENTITY()` ne renvoie que le **dernier** identifiant généré. Si `INSERTED` contient plusieurs lignes (insertion multiple), l'étape 1 crée plusieurs adresses, mais l'étape 3 associe **tous** les clients à la **même** (dernière) `@AdresseID` — un bug classique du raisonnement « une ligne à la fois », justement déconseillé dans tout ce chapitre.
>
> Gérer proprement un `INSTEAD OF INSERT` multi-lignes **avec génération d'identité** est l'un des cas les plus délicats : il faut faire correspondre chaque ligne source à l'identité créée, typiquement avec `MERGE ... OUTPUT inserted.AdresseID, source.<clé>` pour construire une table de correspondance, puis insérer les clients à partir de cette correspondance. C'est un sujet avancé ; retenez ici que l'exemple ci-dessus est **volontairement simplifié** et **mono-ligne**.

### Exemple complet avec UPDATE sur une vue

```sql
CREATE TRIGGER trg_vue_Clients_Adresses_Update
ON vue_Clients_Adresses
INSTEAD OF UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Mise à jour de la table Clients si Nom ou Prenom a changé
    IF UPDATE(Nom) OR UPDATE(Prenom)
    BEGIN
        UPDATE c
        SET
            c.Nom = i.Nom,
            c.Prenom = i.Prenom
        FROM Clients c
        INNER JOIN INSERTED i ON c.ClientID = i.ClientID;
    END

    -- Mise à jour de la table Adresses si Ville ou CodePostal a changé
    IF UPDATE(Ville) OR UPDATE(CodePostal)
    BEGIN
        UPDATE a
        SET
            a.Ville = i.Ville,
            a.CodePostal = i.CodePostal
        FROM Adresses a
        INNER JOIN Clients c ON a.AdresseID = c.AdresseID
        INNER JOIN INSERTED i ON c.ClientID = i.ClientID;
    END
END;
```

## Cas d'usage 2 : Validation et contrôle total

### Validation avec rejet sélectif

Avec INSTEAD OF, vous pouvez décider d'accepter certaines lignes et d'en rejeter d'autres :

```sql
CREATE TRIGGER trg_Commandes_Validation_Insert
ON Commandes
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- Vérifie la validité des données
    IF EXISTS (
        SELECT 1 FROM INSERTED
        WHERE Montant < 0 OR Montant > 100000
    )
    BEGIN
        RAISERROR('Montant invalide : doit être entre 0 et 100000', 16, 1);
        ROLLBACK TRANSACTION;
        RETURN;
    END

    -- Si validation OK, effectue l'insertion
    INSERT INTO Commandes (ClientID, Montant, DateCommande, Statut)
    SELECT
        ClientID,
        Montant,
        DateCommande,
        'En attente'  -- Force un statut par défaut
    FROM INSERTED;
END;
```

### Modification des données avant insertion

Un trigger INSTEAD OF peut **modifier les données** avant de les insérer :

```sql
CREATE TRIGGER trg_Clients_Normalize_Insert
ON Clients
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- Normalise et insère les données
    INSERT INTO Clients (Nom, Prenom, Email, DateInscription)
    SELECT
        UPPER(Nom),                    -- Nom en majuscules
        -- ⚠️ INITCAP() n'existe PAS en T-SQL (c'est une fonction Oracle/PostgreSQL).
        -- On reconstruit « Première lettre majuscule, reste minuscule » à la main :
        UPPER(LEFT(Prenom, 1)) + LOWER(SUBSTRING(Prenom, 2, LEN(Prenom))),
        LOWER(Email),                  -- Email en minuscules
        GETDATE()                      -- Force la date actuelle
    FROM INSERTED;
END;
```

**Ce qui se passe** :

```sql
-- L'utilisateur écrit :
INSERT INTO Clients (Nom, Prenom, Email)
VALUES ('dupont', 'jean', 'JEAN@EMAIL.COM');

-- Mais grâce au trigger INSTEAD OF, ce qui est réellement inséré :
-- Nom: 'DUPONT', Prenom: 'Jean', Email: 'jean@email.com', DateInscription: '2024-11-18'
```

## Cas d'usage 3 : Redirection de données (Partitionnement logique)

### Archivage automatique basé sur des règles

```sql
-- Table principale pour les commandes actives
CREATE TABLE Commandes_Actives (
    CommandeID INT PRIMARY KEY,
    ClientID INT,
    Montant DECIMAL(10,2),
    DateCommande DATE,
    Statut VARCHAR(20)
);

-- Table d'archives pour les anciennes commandes
CREATE TABLE Commandes_Archives (
    CommandeID INT PRIMARY KEY,
    ClientID INT,
    Montant DECIMAL(10,2),
    DateCommande DATE,
    Statut VARCHAR(20)
);

-- Vue unifiée
CREATE VIEW vue_Toutes_Commandes AS
SELECT * FROM Commandes_Actives
UNION ALL
SELECT * FROM Commandes_Archives;

-- Trigger INSTEAD OF pour rediriger automatiquement
CREATE TRIGGER trg_vue_Toutes_Commandes_Insert
ON vue_Toutes_Commandes
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- Insère dans Commandes_Actives si la commande est récente
    INSERT INTO Commandes_Actives (CommandeID, ClientID, Montant, DateCommande, Statut)
    SELECT CommandeID, ClientID, Montant, DateCommande, Statut
    FROM INSERTED
    WHERE DateCommande >= DATEADD(YEAR, -1, GETDATE());

    -- Insère dans Commandes_Archives si la commande est ancienne
    INSERT INTO Commandes_Archives (CommandeID, ClientID, Montant, DateCommande, Statut)
    SELECT CommandeID, ClientID, Montant, DateCommande, Statut
    FROM INSERTED
    WHERE DateCommande < DATEADD(YEAR, -1, GETDATE());
END;
```

**Avantage** : L'utilisateur insère dans une seule vue, mais les données sont automatiquement routées vers la bonne table selon leur date !

## Cas d'usage 4 : Soft Delete (Suppression logique)

Au lieu de supprimer réellement les données, on les marque comme supprimées :

```sql
-- Table avec une colonne pour le soft delete
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Nom VARCHAR(50),
    Prenom VARCHAR(50),
    EstSupprime BIT DEFAULT 0,
    DateSuppression DATETIME NULL
);

-- Vue qui cache les clients supprimés
CREATE VIEW vue_Clients_Actifs AS
SELECT ClientID, Nom, Prenom
FROM Clients
WHERE EstSupprime = 0;

-- Trigger INSTEAD OF DELETE pour faire un soft delete
CREATE TRIGGER trg_Clients_SoftDelete
ON vue_Clients_Actifs
INSTEAD OF DELETE
AS
BEGIN
    SET NOCOUNT ON;

    -- Au lieu de supprimer, on marque comme supprimé
    UPDATE c
    SET
        EstSupprime = 1,
        DateSuppression = GETDATE()
    FROM Clients c
    INNER JOIN DELETED d ON c.ClientID = d.ClientID;

    -- Les données ne sont pas vraiment supprimées !
END;
```

**Utilisation** :

```sql
-- L'utilisateur exécute une suppression normale
DELETE FROM vue_Clients_Actifs WHERE ClientID = 1;

-- Mais en réalité, aucune ligne n'est supprimée
-- La colonne EstSupprime est juste passée à 1

-- Pour vraiment supprimer (accès admin uniquement) :
DELETE FROM Clients WHERE ClientID = 1;
```

## INSTEAD OF sur les tables vs sur les vues

### Sur les tables

```sql
CREATE TRIGGER trg_Produits_Instead
ON Produits  -- Table physique
INSTEAD OF INSERT
AS
BEGIN
    -- Vous DEVEZ coder l'insertion
    INSERT INTO Produits (Nom, Prix)
    SELECT Nom, Prix FROM INSERTED;
END;
```

**⚠️ Attention** : Si vous oubliez de coder l'insertion, RIEN ne sera inséré !

### Sur les vues (usage principal)

```sql
CREATE TRIGGER trg_vue_Instead
ON vue_Produits  -- Vue
INSTEAD OF INSERT
AS
BEGIN
    -- Gère l'insertion dans les tables sous-jacentes
END;
```

**Usage recommandé** : Les triggers INSTEAD OF sont principalement conçus pour les **vues**, pas pour les tables.

## Limitations importantes

### Limitation 1 : Un seul trigger INSTEAD OF par type d'opération

Sur une table ou vue, vous ne pouvez avoir qu'**un seul** trigger INSTEAD OF pour chaque opération :

```sql
-- Premier trigger INSTEAD OF INSERT
CREATE TRIGGER trg_First_Insert ON MaTable INSTEAD OF INSERT
AS BEGIN ... END;

-- Tentative de créer un second trigger INSTEAD OF INSERT
CREATE TRIGGER trg_Second_Insert ON MaTable INSTEAD OF INSERT
AS BEGIN ... END;
-- ❌ ERREUR : Cannot create multiple INSTEAD OF triggers of the same type
```

### Limitation 2 : AFTER est interdit sur les vues

Les triggers **AFTER ne sont pas autorisés sur les vues**, quelle que soit la situation. Sur une vue, **seuls** les triggers `INSTEAD OF` existent :

```sql
-- Sur une vue
CREATE TRIGGER trg_Instead ON MaVue INSTEAD OF INSERT
AS BEGIN ... END;   -- ✅ OK

CREATE TRIGGER trg_After ON MaVue AFTER INSERT
AS BEGIN ... END;   -- ❌ ERREUR : un trigger AFTER ne peut pas être créé sur une vue
```

Sur une **table**, en revanche, on peut tout à fait avoir à la fois un `INSTEAD OF` et un `AFTER` pour la même opération :
- le trigger `INSTEAD OF` s'exécute d'abord et **remplace** l'opération initiale ;
- s'il réalise effectivement l'`INSERT` (ou `UPDATE`/`DELETE`) sur la table, **cette** opération déclenche alors le trigger `AFTER`.

Autrement dit, contrairement à une idée reçue, le `AFTER` **peut** bien se déclencher sur une table dotée d'un `INSTEAD OF` — à la condition que ce dernier effectue réellement l'opération.

### Limitation 3 : Ne fonctionne pas avec les contraintes CASCADE

Si vous avez des contraintes FOREIGN KEY avec CASCADE, les triggers INSTEAD OF ne les interceptent pas :

```sql
-- Table parent avec trigger INSTEAD OF
CREATE TRIGGER trg_Parent_Instead ON TableParent INSTEAD OF DELETE
AS BEGIN
    PRINT 'Trigger INSTEAD OF sur parent';
END;

-- Si vous supprimez un parent et que la contrainte a ON DELETE CASCADE,
-- les enfants sont supprimés directement par le moteur,
-- SANS passer par un éventuel trigger INSTEAD OF sur la table enfant
```

## Responsabilité du développeur

### Vous devez TOUT gérer

Avec INSTEAD OF, SQL Server ne fait **rien automatiquement**. Vous devez :

1. ✅ Gérer l'insertion/modification/suppression vous-même
2. ✅ Respecter les contraintes (PRIMARY KEY, FOREIGN KEY, etc.)
3. ✅ Gérer les colonnes avec DEFAULT
4. ✅ Gérer les colonnes IDENTITY
5. ✅ Gérer les colonnes calculées

### Exemple : Gérer une colonne IDENTITY

```sql
CREATE TABLE Produits (
    ProduitID INT IDENTITY(1,1) PRIMARY KEY,  -- Colonne auto-incrémentée
    Nom VARCHAR(50),
    Prix DECIMAL(10,2)
);

CREATE TRIGGER trg_Produits_Instead
ON Produits
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- ❌ ERREUR : On ne peut pas insérer dans une colonne IDENTITY
    INSERT INTO Produits (ProduitID, Nom, Prix)
    SELECT ProduitID, Nom, Prix FROM INSERTED;

    -- ✅ CORRECT : On laisse IDENTITY générer l'ID
    INSERT INTO Produits (Nom, Prix)
    SELECT Nom, Prix FROM INSERTED;
END;
```

### Exemple : Gérer les valeurs DEFAULT

```sql
CREATE TABLE Commandes (
    CommandeID INT IDENTITY(1,1) PRIMARY KEY,
    ClientID INT,
    Montant DECIMAL(10,2),
    DateCommande DATE DEFAULT GETDATE(),  -- Valeur par défaut
    Statut VARCHAR(20) DEFAULT 'En attente'
);

CREATE TRIGGER trg_Commandes_Instead
ON Commandes
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- VOUS devez gérer les valeurs par défaut !
    INSERT INTO Commandes (ClientID, Montant, DateCommande, Statut)
    SELECT
        ClientID,
        Montant,
        ISNULL(DateCommande, GETDATE()),      -- Applique le DEFAULT
        ISNULL(Statut, 'En attente')          -- Applique le DEFAULT
    FROM INSERTED;
END;
```

## Pièges et erreurs courantes

### Piège 1 : Oublier de coder l'opération

```sql
-- ❌ PIÈGE : L'opération n'est jamais effectuée !
CREATE TRIGGER trg_Validation_Only
ON Commandes
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- Validation
    IF EXISTS (SELECT 1 FROM INSERTED WHERE Montant < 0)
    BEGIN
        RAISERROR('Montant négatif', 16, 1);
        ROLLBACK;
        RETURN;
    END

    -- 💥 OUPS ! On a oublié de faire l'insertion
    -- Les données ne seront JAMAIS insérées !
END;

-- ✅ CORRECT : N'oubliez pas l'insertion
CREATE TRIGGER trg_Validation_Complete
ON Commandes
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    IF EXISTS (SELECT 1 FROM INSERTED WHERE Montant < 0)
    BEGIN
        RAISERROR('Montant négatif', 16, 1);
        ROLLBACK;
        RETURN;
    END

    -- Effectue l'insertion
    INSERT INTO Commandes (ClientID, Montant, DateCommande)
    SELECT ClientID, Montant, DateCommande
    FROM INSERTED;
END;
```

### Piège 2 : Croire qu'un INSTEAD OF se rappelle lui-même

```sql
CREATE TRIGGER trg_Reinsertion
ON MaTable
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO MaTable (Colonne1)
    SELECT Colonne1 FROM INSERTED;
END;
```

On pourrait croire que cet `INSERT INTO MaTable`, exécuté **à l'intérieur** du trigger, va re-déclencher le même `INSTEAD OF` et provoquer une boucle infinie. **Ce n'est pas le cas.**

**Comportement réel :** un trigger `INSTEAD OF` n'est **jamais** rappelé récursivement par une opération qu'il effectue lui-même sur **sa propre table**. L'`INSERT` interne s'exécute **directement** sur la table, comme s'il n'y avait pas de trigger. Cette règle est d'ailleurs **indispensable** : sans elle, tout `INSTEAD OF INSERT` qui réalise réellement l'insertion bouclerait — ce qui rendrait ce type de trigger inutilisable. L'exemple ci-dessus fonctionne donc correctement et insère bien les lignes.

> ⚠️ **Ne désactivez surtout pas le trigger depuis l'intérieur du trigger** avec `ALTER TABLE … DISABLE TRIGGER` : c'est inutile (il n'y a pas de récursion) **et dangereux** — `DISABLE TRIGGER` est une opération globale qui affecte **toutes** les sessions, pas seulement la vôtre.
>
> **Nuance :** une récursion d'`INSTEAD OF` peut tout de même survenir de façon **indirecte** — par exemple si le trigger modifie une *autre* table dont un trigger `AFTER` revient modifier la table de départ. Mais la simple ré-insertion directe, elle, ne boucle pas.

### Piège 3 : Performances avec plusieurs lignes

```sql
-- ❌ MAUVAISE PERFORMANCE : Utilise un curseur
CREATE TRIGGER trg_Slow_Instead
ON Clients
INSTEAD OF INSERT
AS
BEGIN
    DECLARE @Nom VARCHAR(50), @Prenom VARCHAR(50);

    DECLARE curseur CURSOR FOR SELECT Nom, Prenom FROM INSERTED;
    OPEN curseur;
    FETCH NEXT FROM curseur INTO @Nom, @Prenom;

    WHILE @@FETCH_STATUS = 0
    BEGIN
        -- Traite ligne par ligne (LENT !)
        INSERT INTO Clients (Nom, Prenom) VALUES (@Nom, @Prenom);
        FETCH NEXT FROM curseur INTO @Nom, @Prenom;
    END;

    CLOSE curseur;
    DEALLOCATE curseur;
END;

-- ✅ BONNE PERFORMANCE : Opération ensembliste
CREATE TRIGGER trg_Fast_Instead
ON Clients
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- Insère toutes les lignes en une seule opération
    INSERT INTO Clients (Nom, Prenom)
    SELECT Nom, Prenom FROM INSERTED;
END;
```

## Comparaison : Quand utiliser AFTER vs INSTEAD OF ?

### Utilisez AFTER quand :

- ✅ Vous voulez **compléter** l'opération par des actions supplémentaires
- ✅ L'opération standard convient, vous voulez juste ajouter de l'audit, des validations
- ✅ Vous travaillez avec des tables normales (pas des vues complexes)
- ✅ Vous voulez que SQL Server gère automatiquement les contraintes, DEFAULT, IDENTITY

**Exemple** : Enregistrer un audit après chaque modification

### Utilisez INSTEAD OF quand :

- ✅ Vous voulez **remplacer** complètement l'opération
- ✅ Vous devez rendre une vue complexe modifiable
- ✅ Vous voulez rediriger les données vers différentes tables
- ✅ Vous voulez implémenter un soft delete
- ✅ Vous voulez transformer les données avant insertion

**Exemple** : Gérer l'insertion dans plusieurs tables via une vue

### Tableau de comparaison

| Critère | AFTER | INSTEAD OF |
|---------|-------|------------|
| **Moment d'exécution** | Après l'opération | À la place de l'opération |
| **Opération automatique** | Oui, SQL Server le fait | Non, vous devez tout coder |
| **Peut annuler** | Oui, avec ROLLBACK | N'a pas besoin (ne fait rien si on veut annuler) |
| **Nombre par type** | Multiple autorisé | Un seul par type |
| **Usage principal** | Tables physiques | Vues (mais possible sur tables) |
| **Complexité** | Plus simple | Plus complexe |
| **Contrôle** | Moins de contrôle | Contrôle total |

## Bonnes pratiques

### 1. Documentez abondamment

Les triggers INSTEAD OF sont complexes. Documentez-les très clairement :

```sql
/*
================================================================
TRIGGER: trg_vue_Clients_Adresses_Insert
TYPE: INSTEAD OF INSERT
CIBLE: vue_Clients_Adresses (vue joignant Clients et Adresses)
AUTEUR: Jean Dupont
DATE: 2024-11-18

OBJECTIF:
    Permet l'insertion dans une vue complexe en gérant
    automatiquement l'insertion dans les tables sous-jacentes.

LOGIQUE:
    1. Insère d'abord dans la table Adresses
    2. Récupère l'AdresseID généré
    3. Insère ensuite dans la table Clients avec cet AdresseID

TABLES MODIFIÉES:
    - Adresses (INSERT)
    - Clients (INSERT)

DÉPENDANCES:
    - Table Clients doit avoir une colonne AdresseID
    - Table Adresses doit avoir une clé primaire AdresseID

IMPORTANT:
    Ce trigger REMPLACE complètement l'opération INSERT.
    Si ce trigger est désactivé, les insertions dans la vue
    échoueront avec une erreur.
================================================================
*/
CREATE TRIGGER trg_vue_Clients_Adresses_Insert
...
```

### 2. Gérez tous les cas limites

```sql
CREATE TRIGGER trg_Robust_Instead
ON MaTable
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRY
        -- Vérification : Y a-t-il des données à insérer ?
        IF NOT EXISTS (SELECT 1 FROM INSERTED)
            RETURN;

        -- Votre logique d'insertion
        INSERT INTO MaTable (Col1, Col2)
        SELECT Col1, Col2 FROM INSERTED;

    END TRY
    BEGIN CATCH
        -- Gestion d'erreur propre
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;

        DECLARE @ErrorMessage NVARCHAR(4000) = ERROR_MESSAGE();
        RAISERROR(@ErrorMessage, 16, 1);
    END CATCH
END;
```

### 3. Testez avec plusieurs lignes

Toujours tester vos triggers INSTEAD OF avec des insertions multiples :

```sql
-- Test unitaire : une ligne
INSERT INTO MaVue (Col1) VALUES ('Test1');

-- Test important : plusieurs lignes
INSERT INTO MaVue (Col1)
VALUES ('Test1'), ('Test2'), ('Test3');

-- Test limite : beaucoup de lignes
INSERT INTO MaVue (Col1)
SELECT 'Test' + CAST(n AS VARCHAR)
FROM (SELECT TOP 1000 ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS n
      FROM sys.objects) t;
```

### 4. Utilisez SET NOCOUNT ON

Toujours commencer par `SET NOCOUNT ON` pour éviter la pollution des messages :

```sql
CREATE TRIGGER trg_Example
ON MaTable
INSTEAD OF INSERT
AS
BEGIN
    SET NOCOUNT ON;  -- ✅ Recommandé

    -- Votre code
END;
```

## Résumé

### Points clés à retenir

1. **INSTEAD OF = Remplacement** : Le trigger remplace complètement l'opération
2. **Vous devez tout coder** : SQL Server ne fait rien automatiquement
3. **Principal usage : Vues** : Rendre des vues complexes modifiables
4. **Un seul par type** : Un seul INSTEAD OF INSERT, un seul INSTEAD OF UPDATE, etc.
5. **Responsabilité élevée** : Gérer DEFAULT, IDENTITY, contraintes
6. **Plus complexe** : Nécessite plus de code et de tests qu'un trigger AFTER

### Cas d'usage principaux

✅ **Utilisez INSTEAD OF pour** :
1. Rendre des vues multi-tables modifiables
2. Implémenter le soft delete (suppression logique)
3. Rediriger les données vers différentes tables (partitionnement)
4. Transformer/normaliser les données avant insertion
5. Contrôle total sur l'opération

❌ **N'utilisez PAS INSTEAD OF pour** :
1. Simple audit (utilisez AFTER)
2. Validation simple (utilisez des contraintes CHECK ou un trigger AFTER)
3. Quand un trigger AFTER suffit
4. Si vous n'êtes pas prêt à gérer toute la complexité

### Règle de décision

```
Ai-je besoin de REMPLACER complètement l'opération ?
    ├─ Non → Utilisez AFTER
    └─ Oui → Utilisez INSTEAD OF
        └─ Êtes-vous prêt à coder toute la logique ?
            ├─ Non → Reconsidérez votre approche
            └─ Oui → INSTEAD OF est le bon choix
```

## Conclusion

Les triggers INSTEAD OF sont des outils **puissants mais exigeants**. Ils donnent un contrôle total sur les opérations DML, mais avec ce pouvoir vient une grande responsabilité. Utilisez-les principalement pour rendre des vues complexes modifiables, et assurez-vous de bien comprendre toutes les implications avant de les implémenter.

**Conseil final** : Commencez toujours par vous demander si un trigger AFTER ne suffirait pas. N'utilisez INSTEAD OF que quand c'est vraiment nécessaire !
