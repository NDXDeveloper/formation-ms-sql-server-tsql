# 8.6.2 Azure SQL Managed Instance vs. Single Database (Concepts et limitations)

## Introduction

Dans la section précédente, nous avons vu la différence entre IaaS (VM) et PaaS. Nous avons découvert qu'Azure SQL Database est une solution PaaS, mais il existe en réalité **deux saveurs principales de PaaS** pour SQL Server dans Azure :

1. **Azure SQL Database** (aussi appelé "Single Database")
2. **Azure SQL Managed Instance**

Ces deux services sont tous les deux PaaS (Microsoft gère l'infrastructure), mais ils offrent des **niveaux de compatibilité et de fonctionnalités différents** par rapport à SQL Server "classique".

Cette section vous aide à comprendre ces différences et à choisir l'option la plus adaptée à vos besoins.

## Vue d'ensemble du spectre PaaS Azure SQL

### Analogie : Les niveaux d'automatisation automobile

Pour comprendre ces différences, pensez à l'évolution de l'automobile :

**IaaS (VM) = Voiture manuelle classique**
- Contrôle total (boîte manuelle, embrayage)
- Vous gérez tout (entretien, révisions)
- Maximum de personnalisation

**Managed Instance = Voiture automatique haut de gamme**
- Conduite automatisée mais vous gardez le contrôle
- Beaucoup de fonctionnalités (régulateur, aide au stationnement)
- Entretien inclus dans le forfait

**SQL Database = Transport en commun intelligent**
- Vous montez, vous descendez
- Tout est géré pour vous
- Plus simple mais moins personnalisable

## Azure SQL Managed Instance

### Concept fondamental

**Azure SQL Managed Instance** est une **instance complète de SQL Server** dans le cloud, gérée par Microsoft. C'est le **meilleur compromis** entre IaaS et PaaS classique.

### Qu'est-ce qu'une "instance" ?

Rappel : Une **instance SQL Server** est un service SQL Server complet qui peut héberger plusieurs bases de données. Sur un serveur physique ou une VM, vous pouvez installer plusieurs instances.

**Managed Instance reproduit ce concept dans le cloud :**
- Vous obtenez une instance SQL Server complète
- Elle peut héberger plusieurs bases de données
- Vous avez accès à des fonctionnalités au niveau instance (pas seulement base de données)

### Caractéristiques principales de Managed Instance

#### 1. Compatibilité quasi-totale avec SQL Server

**~99% de compatibilité** avec SQL Server on-premises (Enterprise Edition)

**Fonctionnalités disponibles :**
- ✅ **SQL Agent** : Jobs complets, scheduling, alertes
- ✅ **Linked Servers** : Connexions vers d'autres Managed Instances ou SQL Servers
- ✅ **Cross-database queries** : Requêtes entre bases de la même instance
- ✅ **Service Broker** : Messaging asynchrone
- ✅ **Database Mail** : Envoi d'emails depuis SQL Server
- ✅ **CLR** : Code .NET dans SQL Server
- ✅ **Distributed Transactions** : Transactions distribuées (avec limitations)
- ✅ **Replication** : Réplication transactionnelle (comme éditeur)
- ✅ **Change Data Capture (CDC)**
- ✅ **Change Tracking**
- ✅ **TempDB** : Configuration personnalisable

**Exemple de code qui fonctionne sur Managed Instance :**

```sql
-- ✅ Cross-database query (fonctionne sur Managed Instance)
SELECT
    c.CustomerName,
    COUNT(o.OrderId) AS OrderCount
FROM Database1.dbo.Customers c
LEFT JOIN Database2.dbo.Orders o ON c.CustomerId = o.CustomerId
GROUP BY c.CustomerName;

-- ✅ Linked Server (fonctionne sur Managed Instance)
SELECT *
FROM [LinkedMI].[Database1].[dbo].[Products]
WHERE Price > 100;

-- ✅ SQL Agent Job (via T-SQL)
EXEC msdb.dbo.sp_add_job
    @job_name = N'DailyBackupJob';
```

#### 2. Isolation réseau (VNet)

Managed Instance est déployé dans un **Réseau Virtuel Azure (VNet)**, ce qui offre :
- ✅ **Isolation réseau complète**
- ✅ **Connectivité privée** depuis votre réseau d'entreprise (VPN, ExpressRoute)
- ✅ **Pas d'accès Internet public par défaut** (plus sécurisé)
- ✅ **Intégration avec architecture Azure** (VMs, App Services, etc.)

```
┌──────────────────────────────────────────────────────────┐
│           Réseau d'entreprise (On-Premise)               │
│                                                          │
│   ┌──────────────┐                                       │
│   │ Applications │                                       │
│   │   internes   │                                       │
│   └──────┬───────┘                                       │
│          │                                               │
│          │ VPN / ExpressRoute (connexion privée)         │
└──────────┼───────────────────────────────────────────────┘
           │
           ↓
┌──────────┼───────────────────────────────────────────────┐
│          │      Azure VNet (Réseau Virtuel)              │
│          │                                               │
│          ↓                                               │
│   ┌──────────────────┐      ┌──────────────────┐         │
│   │  Managed Instance│      │   App Service    │         │
│   │                  │◄─────┤   (Web App)      │         │
│   └──────────────────┘      └──────────────────┘         │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

#### 3. Migration facilitée

Managed Instance est **conçu pour les migrations "lift and shift"** :
- Minimal ou aucun changement de code nécessaire
- Compatible avec Database Migration Service
- Possibilité de restaurer des sauvegardes (.bak) directement

**Processus de migration typique :**
```
1. Évaluer la compatibilité (Data Migration Assistant)
2. Créer Managed Instance dans Azure
3. Restaurer les sauvegardes ou utiliser Migration Service
4. Reconfigurer les applications (chaînes de connexion)
5. Basculer en production
```

#### 4. Haute disponibilité intégrée

Comme Azure SQL Database, Managed Instance inclut :
- **99,99% de SLA** (disponibilité)
- **AlwaysOn Availability Groups** configuré automatiquement
- **Basculement transparent** en cas de panne
- **Sauvegardes automatiques** avec restauration à un instant T

### Limitations de Managed Instance

Malgré sa haute compatibilité, certaines fonctionnalités ne sont **pas disponibles** :

| Fonctionnalité | Disponible ? | Alternative |
|----------------|--------------|-------------|
| **FILESTREAM / FileTable** | ❌ Non | Stockage Blob Azure |
| **SQL Server Audit vers fichier local** | ❌ Non | Audit vers Azure Storage |
| **Accès au système de fichiers** | ❌ Limité | Stockage Blob pour fichiers |
| **SSIS natif** | ❌ Non | Azure Data Factory avec SSIS Runtime |
| **SSRS natif** | ❌ Non | Power BI Report Server (VM) ou Power BI Service |
| **SSAS natif** | ❌ Non | Azure Analysis Services |
| **Polybase** | ❌ Non | Alternatives avec Data Factory |
| **R/Python (Machine Learning Services)** | ❌ Non | Azure Machine Learning |

### Cas d'usage typiques de Managed Instance

**Quand choisir Managed Instance :**

1. **Migration d'applications existantes complexes**
   - Applications avec Linked Servers
   - Cross-database queries essentielles
   - SQL Agent jobs complexes
   - Migration minimale de code souhaitée

2. **Besoins de compatibilité élevée**
   - Applications qui utilisent Service Broker
   - Besoin de Database Mail
   - CLR assemblies personnalisés

3. **Exigences réseau strictes**
   - Connexion privée requise (pas d'exposition Internet)
   - Intégration VNet avec architecture Azure
   - Connectivité avec on-premise via VPN/ExpressRoute

4. **Consolidation de plusieurs bases**
   - Plusieurs bases sur une même instance
   - Économies d'échelle
   - Gestion centralisée au niveau instance

**Exemple concret :**
Une entreprise migre son ERP développé sur SQL Server 2016 avec 15 bases de données interconnectées, utilisant des cross-database queries, 50 jobs SQL Agent, et nécessitant une connexion privée depuis le datacenter on-premise via ExpressRoute.

### Tarification de Managed Instance

**Modèle de coût :**
- Facturation au **vCore** (processeur virtuel)
- Choix entre 4-80 vCores
- Stockage facturé séparément (jusqu'à 8 To par instance)
- Option "license included" ou "Azure Hybrid Benefit" (BYOL)

**Fourchette de prix indicative :**
- Managed Instance 8 vCores : ~800-1000 €/mois
- Managed Instance 16 vCores : ~1600-2000 €/mois

**Important :** Managed Instance est généralement **plus cher** que SQL Database, mais moins cher que IaaS quand on compte le temps d'administration.

## Azure SQL Database (Single Database)

### Concept fondamental

**Azure SQL Database** (Single Database) est un **service de base de données unique**, où chaque base de données est **isolée** et **indépendante**. C'est l'option PaaS la plus **simple** et la plus **moderne**.

### Caractéristiques principales de SQL Database

#### 1. Simplicité maximale

**Philosophie :** Une base de données = Un service isolé
- Pas de concept d'instance
- Pas de gestion multi-bases
- Focus sur **une seule base de données**

**Création ultra-simple :**
```
1. Créer une base dans le portail Azure (3 clics)
2. Choisir la taille (DTU ou vCore)
3. Obtenir la chaîne de connexion
4. C'est prêt !
```

#### 2. Scalabilité dynamique

**Caractéristique unique :** Vous pouvez **changer la taille** de votre base en quelques secondes :
- Passer de 2 vCores à 8 vCores en un clic
- Aucun temps d'arrêt (quelques secondes de reconnexion)
- Ajuster selon la charge

**Exemple d'usage :**
```
Lundi-Vendredi 9h-18h : 8 vCores (charge élevée)
Soirs et weekends     : 2 vCores (charge faible)
➡️ Économies substantielles
```

#### 3. Modèles de tarification flexibles

**Deux modèles :**

**A. Modèle DTU (Database Transaction Unit)**
- Unité combinant CPU, RAM, I/O
- Simple à comprendre : Basic, Standard (S0-S12), Premium (P1-P15)
- Bon pour débuter

**B. Modèle vCore**
- Choix précis de CPU et RAM
- Plus flexible et prévisible
- Recommandé pour la production

**Options de calcul :**
- **Provisionné** : Ressources réservées 24/7
- **Serverless** : Facturation à la seconde d'utilisation, pause automatique

#### 4. Fonctionnalités cloud-natives avancées

Azure SQL Database offre des fonctionnalités **uniques** absentes de SQL Server classique :

**Elastic Pools (Pools élastiques) :**
- Partager des ressources entre plusieurs bases de données
- Optimisation des coûts pour applications multi-tenant

```
┌──────────────────────────────────────────────────┐
│         Elastic Pool (200 DTU partagés)          │
│                                                  │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐           │
│  │  DB 1   │  │  DB 2   │  │  DB 3   │           │

│  └─────────┘  └─────────┘  └─────────┘           │
│                                                  │
│  Total utilisé : 200 DTU                         │
│  Coût : Pool de 200 DTU (moins cher que 3×100)   │
└──────────────────────────────────────────────────┘
```

**Geo-Replication active :**
- Réplication asynchrone vers d'autres régions Azure
- Configuration en quelques clics
- Lecture possible sur les secondaires

**Automatic Tuning (Ajustement automatique) :**
- Recommandations d'index automatiques
- Création/suppression d'index autonome
- Optimisation des plans d'exécution

**Query Performance Insight :**
- Interface graphique pour identifier les requêtes lentes
- Recommandations d'optimisation

### Limitations de SQL Database

Comparé à SQL Server complet et Managed Instance, SQL Database a des **limitations importantes** :

#### Limitations fonctionnelles majeures

| Fonctionnalité | Disponible ? | Impact |
|----------------|--------------|--------|
| **Cross-database queries** | ❌ Non | Impossible de faire SELECT entre deux bases |
| **Linked Servers** | ❌ Non | Pas de connexion à d'autres serveurs SQL |
| **SQL Agent (jobs)** | ⚠️ Limité | Uniquement via Elastic Jobs (complexe) |
| **Service Broker** | ❌ Non | Pas de messaging asynchrone natif |
| **Database Mail** | ❌ Non | Utiliser Logic Apps ou Azure Functions |
| **CLR** | ⚠️ Limité | Fonctionnalités CLR restreintes |
| **Distributed Transactions** | ❌ Non | Transactions limitées à une seule base |
| **FILESTREAM** | ❌ Non | Utiliser Blob Storage |
| **Replication** | ⚠️ Limité | Peut être abonné seulement |

#### Exemple de code qui NE fonctionne PAS

```sql
-- ❌ Cross-database query (NE FONCTIONNE PAS sur SQL Database)
SELECT
    c.CustomerName,
    COUNT(o.OrderId) AS OrderCount
FROM Database1.dbo.Customers c  -- ❌ Erreur : Database1 inaccessible
LEFT JOIN Database2.dbo.Orders o ON c.CustomerId = o.CustomerId
GROUP BY c.CustomerName;

-- ❌ Linked Server (NE FONCTIONNE PAS)
SELECT *
FROM [LinkedServer].[Database1].[dbo].[Products];  -- ❌ Erreur

-- ❌ SQL Agent Job classique (NE FONCTIONNE PAS)
EXEC msdb.dbo.sp_add_job   -- ❌ msdb n'existe pas
    @job_name = N'DailyJob';
```

#### Solutions de contournement

**Pour cross-database queries :**
```sql
-- ✅ Utiliser Elastic Query (configuration requise)
-- Ou restructurer pour avoir tout dans une seule base
```

**Pour Linked Servers :**
```sql
-- ✅ Utiliser Elastic Query pour connexions entre Azure SQL DB
-- ✅ Utiliser des API REST pour autres sources
-- ✅ Utiliser Azure Data Factory pour ETL
```

**Pour SQL Agent jobs :**
```
✅ Elastic Jobs (pour tâches récurrentes sur plusieurs bases)
✅ Azure Automation (scripts PowerShell planifiés)
✅ Azure Functions (déclenchées par timer)
✅ Logic Apps (workflows planifiés)
```

### Cas d'usage typiques de SQL Database

**Quand choisir SQL Database (Single Database) :**

1. **Nouvelle application cloud-native**
   - Application web moderne (API REST)
   - Application mobile backend
   - Microservices
   - Une base de données suffit

2. **Simplicité et agilité**
   - Équipe DevOps sans administrateur DBA
   - Déploiement rapide (développement, test, production)
   - Pas de complexité inutile

3. **Scalabilité dynamique requise**
   - Charge variable (pics et creux)
   - Besoin d'ajuster les ressources fréquemment
   - Environnements éphémères (test, staging)

4. **Applications SaaS multi-tenant**
   - Une base par client (isolation)
   - Elastic Pools pour optimisation des coûts
   - Gestion indépendante par client

5. **Pas de dépendances inter-bases**
   - L'application utilise une seule base
   - Pas besoin de requêtes entre bases
   - Architecture microservices (une base par service)

**Exemple concret :**
Une startup développe une API REST pour une application mobile de gestion de tâches. Chaque requête API interroge une seule base de données. Besoin de scalabilité pour suivre la croissance. Équipe de 3 développeurs sans DBA.

### Tarification de SQL Database

**Plus flexible et souvent moins cher** que Managed Instance pour des bases individuelles.

**Modèle DTU (exemple) :**
- Basic (5 DTU) : ~5 €/mois
- Standard S3 (100 DTU) : ~75 €/mois
- Premium P2 (250 DTU) : ~450 €/mois

**Modèle vCore (exemple) :**
- 2 vCores : ~200-350 €/mois
- 4 vCores : ~400-700 €/mois

**Serverless (facturation à l'usage) :**
- Pause automatique après inactivité
- Facturation à la seconde d'utilisation
- Idéal pour dev/test ou charge intermittente

### Scénarios de migration

#### Scénario 1 : ERP complexe

**Contexte :**
- Application ERP avec 12 bases interconnectées
- 80 jobs SQL Agent (exports, calculs, maintenance)
- Cross-database queries intensives
- Linked Server vers un système externe
- Service Broker pour communication asynchrone

**Choix recommandé : ✅ Managed Instance**

**Raison :**
- Toutes les fonctionnalités nécessaires disponibles
- Migration avec modifications minimales
- Une seule instance pour toutes les bases

**Migration :**
```
1. Créer Managed Instance (4-6 heures)
2. Restaurer toutes les bases (.bak)
3. Migrer les jobs SQL Agent
4. Reconfigurer Linked Server
5. Tester et basculer
```

#### Scénario 2 : API REST moderne

**Contexte :**
- API REST ASP.NET Core
- Une seule base de données
- Pas de jobs complexes (Azure Functions pour tâches planifiées)
- Charge variable (pics lors des campagnes marketing)
- Équipe de développeurs sans DBA

**Choix recommandé : ✅ SQL Database (Single DB)**

**Raison :**
- Simplicité maximale
- Scalabilité instantanée pour gérer les pics
- Coût optimisé (serverless ou scaling dynamique)
- Pas besoin de fonctionnalités avancées

**Migration :**
```
1. Créer Azure SQL Database (5 minutes)
2. Exporter/importer le schéma (SSDT ou scripts)
3. Migrer les données (BCP, Azure Data Factory)
4. Modifier chaîne de connexion
5. Déployer et tester
```

#### Scénario 3 : Application hybride

**Contexte :**
- Application avec 3 modules distincts
- Module 1 : ERP (plusieurs bases, cross-database)
- Module 2 : CRM (base unique, simple)
- Module 3 : Portail web (base unique, pics de charge)

**Choix recommandé : ✅ Combinaison**

**Architecture recommandée :**
```
Module 1 (ERP)      →  Managed Instance
Module 2 (CRM)      →  SQL Database
Module 3 (Portail)  →  SQL Database (Serverless)
```

**Raison :**
- Chaque composant utilise le service le plus adapté
- Optimisation des coûts
- Simplicité là où c'est possible, puissance là où c'est nécessaire

## Évolution et chemins de migration

### Peut-on migrer de SQL Database vers Managed Instance ?

**Oui, mais avec effort :**
- Export/Import des données
- Recréation des objets
- Tests complets nécessaires

**Stratégie recommandée :**
Choisir le bon service dès le départ en évaluant bien les besoins.

### Peut-on migrer de Managed Instance vers SQL Database ?

**Possible si l'application n'utilise pas les fonctionnalités spécifiques à MI :**
- Pas de cross-database queries
- Pas de SQL Agent jobs critiques
- Pas de Linked Servers

**Scénario typique :**
Commencer avec MI pour migration rapide, puis refactoriser progressivement vers SQL Database pour optimiser les coûts.

## Recommandations par type d'organisation

### Startup / PME

**Recommandation : SQL Database**
- Coûts maîtrisés
- Simplicité de gestion
- Scalabilité pour la croissance
- Pas besoin de DBA

**Exception :** Si migration d'une application existante complexe → Managed Instance

### Grande entreprise avec applications existantes

**Recommandation : Managed Instance**
- Migration facilitée des applications existantes
- Compatibilité maximale
- Connexion privée avec datacenter on-premise
- Support des architectures complexes

**Complément :** SQL Database pour nouvelles applications cloud-natives

### Éditeur de logiciel SaaS

**Recommandation : SQL Database avec Elastic Pools**
- Une base par client (isolation parfaite)
- Partage des ressources (optimisation des coûts)
- Scalabilité par client
- Gestion automatisée

### Environnements de développement/test

**Recommandation : SQL Database Serverless**
- Pause automatique quand inutilisé
- Facturation à la seconde
- Économies importantes
- Création/suppression rapide

## Conclusion

Le choix entre **Azure SQL Managed Instance** et **Azure SQL Database** dépend principalement de :

### Choisir Managed Instance si vous avez besoin de :
1. **Compatibilité maximale** avec SQL Server on-premises
2. **Fonctionnalités au niveau instance** (SQL Agent complet, Linked Servers, cross-database queries)
3. **Migration rapide** d'applications existantes sans refactoring
4. **Plusieurs bases interconnectées** sur une même instance
5. **Isolation réseau stricte** avec VNet

### Choisir SQL Database si vous voulez :
1. **Simplicité maximale** sans complexité inutile
2. **Scalabilité dynamique** avec ajustement en secondes
3. **Coûts optimisés** et flexibilité tarifaire (serverless, pools élastiques)
4. **Applications cloud-natives** modernes
5. **Bases de données indépendantes** sans interactions entre elles

### Points clés à retenir :

| Aspect | Managed Instance | SQL Database |
|--------|------------------|--------------|
| **Philosophie** | Compatibilité maximale | Simplicité et modernité |
| **Migration** | Facile (lift-and-shift) | Peut nécessiter modifications |
| **Gestion** | Instance multi-bases | Base de données unique |
| **Coût** | Plus élevé mais consolidation | Optimisé et flexible |
| **Réseau** | VNet obligatoire | Accès public/privé |
| **Cible** | Migration on-premise | Applications cloud-natives |

**Conseil final :**
Si vous hésitez, commencez par évaluer :
1. Avez-vous besoin de cross-database queries ? → MI
2. Utilisez-vous des Linked Servers ? → MI
3. Des jobs SQL Agent complexes ? → MI
4. Sinon → SQL Database (plus simple et souvent moins cher)

N'oubliez pas : vous pouvez aussi **utiliser les deux** dans la même architecture, chaque composant utilisant le service le plus adapté à ses besoins spécifiques.
