# 6.3.1 Problématiques de concurrence (Dirty Reads, Non-Repeatable Reads, Phantom Reads)

## Introduction

Dans un système de gestion de base de données comme SQL Server, plusieurs utilisateurs ou applications peuvent accéder simultanément aux mêmes données. C'est ce qu'on appelle la **concurrence**. Si cette concurrence n'est pas gérée correctement, elle peut entraîner des anomalies de lecture qui compromettent la cohérence des données.

Imaginez une salle de classe où plusieurs étudiants lisent et modifient le même document en même temps sans coordination : ils risquent de lire des informations obsolètes ou contradictoires. C'est exactement ce qui peut se produire dans une base de données.

Dans cette section, nous allons explorer les trois principales **problématiques de concurrence** qui peuvent survenir lors de transactions simultanées :

1. **Dirty Reads** (Lectures sales)
2. **Non-Repeatable Reads** (Lectures non répétables)
3. **Phantom Reads** (Lectures fantômes)

---

## 1. Dirty Reads (Lectures sales)

### Qu'est-ce qu'une Dirty Read ?

Une **Dirty Read** se produit lorsqu'une transaction lit des données qui ont été modifiées par une autre transaction, mais qui n'ont **pas encore été validées** (committed). Si cette deuxième transaction est annulée (rollback), les données lues deviennent invalides.

### Analogie simple

Imaginez que vous consultez le prix d'un produit sur un site e-commerce. Au même moment, un employé est en train de modifier ce prix dans la base de données. Vous voyez le nouveau prix (par exemple 50€ au lieu de 100€), mais l'employé se rend compte de son erreur et annule sa modification. Le prix que vous avez vu (50€) n'a jamais vraiment existé officiellement : c'était une "lecture sale".

### Exemple technique

**Situation :**
- **Transaction A** modifie le salaire d'un employé de 3000€ à 3500€
- **Transaction B** lit ce salaire pendant que Transaction A est encore en cours
- **Transaction A** est finalement annulée (ROLLBACK)

**Résultat :** Transaction B a lu un salaire de 3500€ qui n'a jamais été officiellement validé. Cette valeur est considérée comme "sale" car elle provient d'une transaction non terminée.

```sql
-- Transaction A
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
-- La transaction n'est pas encore validée

-- Transaction B (lecture simultanée)
SELECT Salaire FROM Employes WHERE EmployeID = 1;
-- Résultat : 3500 (lecture sale !)

-- Transaction A annule sa modification
ROLLBACK;
-- Le salaire réel est toujours 3000, mais Transaction B a lu 3500
```

### Pourquoi est-ce un problème ?

Transaction B a pris une décision basée sur des données incorrectes. Par exemple, si elle calculait une moyenne de salaires pour établir un budget, ce budget serait faux.

## 2. Non-Repeatable Reads (Lectures non répétables)

### Qu'est-ce qu'une Non-Repeatable Read ?

Une **Non-Repeatable Read** survient lorsqu'une transaction lit la même donnée deux fois et obtient des résultats différents parce qu'une autre transaction a modifié et **validé** cette donnée entre les deux lectures.

### Analogie simple

Vous consultez votre compte bancaire le matin et voyez un solde de 1000€. Vous continuez à travailler sur votre budget sans fermer l'application. Quelques minutes plus tard, vous consultez à nouveau le même solde dans la même session, et vous voyez maintenant 500€ parce que votre conjoint vient d'effectuer un retrait. La lecture n'est "pas répétable" : la même requête donne des résultats différents.

### Exemple technique

**Situation :**
- **Transaction A** lit le prix d'un article (100€)
- **Transaction B** modifie ce prix à 120€ et valide (COMMIT)
- **Transaction A** relit le même prix et trouve maintenant 120€

**Résultat :** Dans la même transaction, la même requête a donné deux résultats différents.

```sql
-- Transaction A
BEGIN TRANSACTION;
SELECT Prix FROM Produits WHERE ProduitID = 10;
-- Résultat : 100€

-- Transaction B (modification simultanée)
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 120 WHERE ProduitID = 10;
COMMIT;
-- La modification est validée

-- Transaction A relit le prix
SELECT Prix FROM Produits WHERE ProduitID = 10;
-- Résultat : 120€ (lecture non répétable !)
COMMIT;
```

### Pourquoi est-ce un problème ?

Si Transaction A fait des calculs ou des comparaisons basés sur le prix initial (100€), ses résultats peuvent être incohérents. Par exemple, elle pourrait calculer une remise sur 100€ alors que le prix réel est maintenant 120€.

---

## 3. Phantom Reads (Lectures fantômes)

### Qu'est-ce qu'une Phantom Read ?

Une **Phantom Read** se produit lorsqu'une transaction exécute la même requête deux fois et obtient un nombre différent de lignes parce qu'une autre transaction a **inséré ou supprimé** des lignes correspondant aux critères de recherche entre les deux lectures.

### Analogie simple

Vous comptez le nombre d'étudiants présents dans une salle de classe : il y en a 20. Pendant que vous préparez la liste des présents, 3 nouveaux étudiants arrivent. Quand vous recomptez pour vérifier, vous trouvez maintenant 23 étudiants. Ces 3 étudiants sont des "fantômes" : ils n'étaient pas là lors de votre première lecture, mais apparaissent lors de la seconde.

### Exemple technique

**Situation :**
- **Transaction A** compte le nombre d'employés ayant un salaire > 3000€ (résultat : 5 employés)
- **Transaction B** insère un nouvel employé avec un salaire de 3500€ et valide
- **Transaction A** refait le même comptage et trouve maintenant 6 employés

**Résultat :** Une nouvelle ligne "fantôme" est apparue entre les deux lectures.

```sql
-- Transaction A
BEGIN TRANSACTION;
SELECT COUNT(*) FROM Employes WHERE Salaire > 3000;
-- Résultat : 5 employés

-- Transaction B (insertion simultanée)
BEGIN TRANSACTION;
INSERT INTO Employes (Nom, Salaire) VALUES ('Dupont', 3500);
COMMIT;
-- Le nouvel employé est validé

-- Transaction A refait le comptage
SELECT COUNT(*) FROM Employes WHERE Salaire > 3000;
-- Résultat : 6 employés (lecture fantôme !)
COMMIT;
```

### Pourquoi est-ce un problème ?

Si Transaction A génère un rapport basé sur le premier comptage (5 employés), puis effectue des calculs basés sur le second comptage (6 employés), les résultats seront incohérents. Par exemple, un calcul de budget pourrait être faussé.

---

## Différences entre les trois problématiques

| Problématique | Type de modification | Validation (COMMIT) | Impact |
|---------------|---------------------|---------------------|--------|
| **Dirty Read** | UPDATE/DELETE | **Non validée** | Lecture de données temporaires qui peuvent être annulées |
| **Non-Repeatable Read** | UPDATE/DELETE | **Validée** | Même requête donne des valeurs différentes |
| **Phantom Read** | INSERT/DELETE | **Validée** | Même requête donne un nombre de lignes différent |

---

## Pourquoi ces problématiques sont-elles importantes ?

Ces anomalies de concurrence peuvent entraîner :

1. **Des incohérences dans les rapports** : Les statistiques et les analyses peuvent être faussées
2. **Des erreurs de calcul** : Les opérations financières ou commerciales peuvent être incorrectes
3. **Des décisions erronées** : Les utilisateurs peuvent prendre des décisions basées sur des données incorrectes
4. **Une perte de confiance** : Les utilisateurs peuvent douter de la fiabilité du système

---

## Comment SQL Server gère-t-il ces problématiques ?

SQL Server propose différents **niveaux d'isolation des transactions** qui permettent de contrôler quel type d'anomalie est autorisé ou bloqué. Ces niveaux offrent un compromis entre :

- **La cohérence des données** (éviter les anomalies)
- **Les performances** (permettre plus de concurrence)

Plus un niveau d'isolation est strict, plus il garantit la cohérence des données, mais au prix d'une réduction des performances (car plus de verrous sont utilisés).

Les différents niveaux d'isolation seront abordés dans les sections suivantes (6.4.1 à 6.4.6).

---

## Résumé

- **Dirty Read** : Lecture de données non validées qui peuvent être annulées
- **Non-Repeatable Read** : Une même donnée change de valeur entre deux lectures dans la même transaction
- **Phantom Read** : De nouvelles lignes apparaissent (ou disparaissent) entre deux lectures dans la même transaction

Ces trois problématiques sont des anomalies classiques de concurrence dans les bases de données. Comprendre ces concepts est essentiel pour choisir le bon niveau d'isolation et garantir l'intégrité des données dans vos applications.
