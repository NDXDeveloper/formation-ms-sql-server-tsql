# 7.8.5 Restauration à un instant T (Point-in-Time Recovery)

## Introduction

Voici **le scénario qui justifie tout l'effort du modèle `FULL`**. Il est 14h32. Un développeur, persuadé de travailler sur l'environnement de test, exécute sur la **production** :

```sql
DELETE FROM Commandes;   -- ❌ sans clause WHERE !
```

50 000 commandes viennent de disparaître. La sauvegarde complète date de cette nuit (02h00) ; restaurer simplement cette complète ferait perdre **toute la journée** de travail des équipes.

La **restauration à un instant T** (*Point-in-Time Recovery*, ou PITR) permet de faire infiniment mieux : restaurer la base **exactement à 14h31**, juste **avant** la commande fatale. On ne perd alors qu'une seule minute de données.

> 🧠 C'est la fonctionnalité qui transforme la sauvegarde d'une simple « photo de la nuit dernière » en une véritable **machine à remonter le temps**.

---

## Le prérequis absolu

La restauration à un instant T n'est possible que si **deux conditions** sont réunies :

1. La base est en modèle de récupération **`FULL`** (ou `BULK_LOGGED` hors opérations en bloc) — voir §7.8.1.
2. Vous disposez d'une **chaîne de sauvegardes de journal ininterrompue** couvrant l'instant cible — voir §7.8.2.

> ⚠️ Sans sauvegardes de journal, **pas de PITR possible**. C'est la raison d'être de tout l'effort des sous-sections précédentes : ces sauvegardes de journal régulières que l'on planifie « au cas où », c'est *exactement* ce cas-là.

---

## La clause STOPAT

On effectue une séquence de restauration **normale** (comme au §7.8.4), mais sur la **sauvegarde de journal qui contient l'instant cible**, on ajoute la clause `STOPAT` :

```sql
-- 1) Complète, en attente
RESTORE DATABASE Boutique
FROM DISK = 'C:\Backups\Boutique_FULL_0200.bak'
WITH NORECOVERY, REPLACE;

-- 2) Journaux antérieurs à l'incident, appliqués entièrement
RESTORE LOG Boutique
FROM DISK = 'C:\Backups\Boutique_LOG_1400.trn'
WITH NORECOVERY;

-- 3) Journal contenant 14h32 : on s'arrête à 14h31:00 et on ouvre la base
RESTORE LOG Boutique
FROM DISK = 'C:\Backups\Boutique_LOG_1430.trn'
WITH STOPAT = '2026-05-31T14:31:00', RECOVERY;
```

Résultat : la base est restaurée dans l'état où elle se trouvait à **14h31:00**, soit **avant** le `DELETE` de 14h32. Les 50 000 commandes sont de retour. 🎉

> 💡 **Astuce** : vous pouvez aussi mettre `STOPAT` (avec `NORECOVERY`) sur les journaux intermédiaires ; SQL Server ignorera simplement les transactions postérieures à l'instant cible. L'important est de ne pas **dépasser** l'instant voulu avec un `RECOVERY` final.

> ⚠️ Si l'instant `STOPAT` se situe **avant** le début du journal en cours de restauration, SQL Server le signale : il faut alors appliquer un journal **antérieur**. À l'inverse, s'il est postérieur, le journal est appliqué en entier.

---

## La stratégie recommandée : récupérer dans une base de copie

En pratique, on évite souvent d'écraser directement la production. La démarche la plus sûre :

```
1. Restaurer à l'instant T dans une base de COPIE (Boutique_Recover)
2. Vérifier que les données récupérées sont correctes
3. Réinjecter uniquement les données manquantes dans la production
```

### Étape 1 — restaurer dans une copie

```sql
RESTORE DATABASE Boutique_Recover
FROM DISK = 'C:\Backups\Boutique_FULL_0200.bak'
WITH MOVE 'Boutique'     TO 'D:\Data\Boutique_Recover.mdf',
     MOVE 'Boutique_log' TO 'D:\Data\Boutique_Recover_log.ldf',
     NORECOVERY;

RESTORE LOG Boutique_Recover
FROM DISK = 'C:\Backups\Boutique_LOG_1430.trn'
WITH STOPAT = '2026-05-31T14:31:00', RECOVERY;
```

### Étape 3 — réinjecter les lignes manquantes

```sql
INSERT INTO Boutique.dbo.Commandes
SELECT c.*
FROM Boutique_Recover.dbo.Commandes AS c
WHERE NOT EXISTS (
    SELECT 1 FROM Boutique.dbo.Commandes AS b
    WHERE b.CommandeID = c.CommandeID
);
```

> ✅ **Avantage majeur** : cette approche ne met **pas** la production hors ligne et ne risque pas d'écraser des données légitimes saisies *après* l'incident (les nouvelles commandes de 14h33, par exemple).

---

## STOPATMARK et STOPBEFOREMARK (transactions marquées)

Au lieu d'un horaire, on peut s'arrêter sur une **transaction nommée** (*marked transaction*). On marque d'abord une transaction importante :

```sql
BEGIN TRANSACTION AvantMigration WITH MARK 'Avant migration des tarifs';
    -- ... opérations sensibles ...
COMMIT TRANSACTION AvantMigration;
```

On pourra ensuite restaurer **jusqu'à** cette marque (incluse) ou **juste avant** :

```sql
-- Restaurer en incluant la transaction marquée
RESTORE LOG Boutique FROM DISK = '...' WITH STOPATMARK = 'Avant migration des tarifs', RECOVERY;

-- Restaurer juste AVANT la transaction marquée
RESTORE LOG Boutique FROM DISK = '...' WITH STOPBEFOREMARK = 'Avant migration des tarifs', RECOVERY;
```

C'est précieux **avant une opération risquée** (migration, déploiement, mise à jour de masse) : on dispose d'un point de retour **nommé**, bien plus parlant et fiable qu'un horodatage approximatif.

---

## Comment connaître l'instant exact de l'incident ?

Pour cibler `STOPAT` au plus juste, plusieurs pistes :
- Les **logs applicatifs** (heure de l'erreur signalée par les utilisateurs).
- Le **journal d'erreurs SQL Server**, les traces et *Extended Events*.
- L'audit SQL Server, s'il est activé.
- L'inspection du contenu d'une sauvegarde de journal avec des outils tiers.

En pratique, on procède souvent par **approche itérative** : on restaure dans une copie avec un `STOPAT` estimé, on vérifie si les données fautives sont présentes ou non, et on ajuste l'horodatage jusqu'à tomber juste.

---

## Alternatives et compléments modernes

Le PITR par sauvegardes de journal reste la méthode universelle, mais d'autres mécanismes peuvent **compléter** la protection :

- Les **tables temporelles** (*system-versioned tables*, voir §8.3) conservent automatiquement l'historique des versions de lignes : on peut retrouver l'état passé d'une table avec `FOR SYSTEM_TIME AS OF`, sans restauration.
- Sur **Azure SQL Database**, le PITR est **intégré et automatique** : on choisit une date/heure dans le portail, sans gérer soi-même les sauvegardes (voir §8.6).

Ces mécanismes ne remplacent pas les sauvegardes, mais offrent des recours plus rapides pour certains scénarios.

---

## Limites à connaître

- Le PITR ne fonctionne pas en modèle `SIMPLE`.
- En `BULK_LOGGED`, on ne peut pas s'arrêter à un instant **situé à l'intérieur** d'un intervalle contenant une opération en bloc.
- La précision dépend de la **granularité du journal** : on peut viser la seconde, mais pas « juste avant la 3ᵉ ligne du DELETE » au sein d'une même transaction (une transaction est atomique : tout ou rien).

---

## Questions fréquentes

**Q : Le DELETE était dans une transaction validée. Puis-je restaurer "au milieu" ?**
R : Non. Une transaction est atomique. `STOPAT` s'arrête à une frontière de transaction : juste avant ou juste après. Visez l'instant **avant** le `BEGIN`/l'exécution du `DELETE`.

**Q : Et si je n'ai pas de sauvegarde de journal couvrant 14h31 ?**
R : Alors le PITR à 14h31 est impossible : vous ne pourrez restaurer qu'à la dernière sauvegarde disponible avant l'incident (par ex. 14h00 si un log existe à cette heure). D'où l'importance de la **fréquence** des log backups (= votre RPO).

**Q : Puis-je faire un PITR sur Azure SQL Database ?**
R : Oui, et c'est même plus simple : la plateforme gère les sauvegardes ; vous choisissez l'instant cible dans le portail/CLI.

---

## Résumé

- La **restauration à un instant T** (PITR) permet de remonter à une **date/heure précise**, idéalement **juste avant** une erreur.
- Elle exige le modèle **`FULL`** et une **chaîne de journaux complète** couvrant l'instant cible.
- On utilise `RESTORE LOG ... WITH STOPAT = 'AAAA-MM-JJThh:mm:ss'` sur le journal contenant l'instant.
- `STOPATMARK` / `STOPBEFOREMARK` permettent de s'arrêter sur une **transaction marquée** — idéal avant une opération risquée.
- En pratique, restaurez dans une **base de copie** puis réinjectez les données manquantes : plus sûr pour la production.
- Les **tables temporelles** (§8.3) et le PITR intégré d'**Azure SQL** complètent ce dispositif.

Nous maîtrisons la mécanique. Reste à transformer tout cela en une **stratégie cohérente** : à quelle fréquence sauvegarder, combien de temps conserver, et comment garantir que tout fonctionnera le jour J.
