# 5.7.3 Les tables virtuelles INSERTED et DELETED

## Introduction : Qu'est-ce qu'une table virtuelle ?

Lorsqu'un trigger s'exécute, il a besoin d'accéder aux données qui ont été modifiées. SQL Server fournit deux **tables virtuelles** spéciales pour cela :

- **INSERTED** : Contient les nouvelles données
- **DELETED** : Contient les anciennes données

### Pourquoi "virtuelles" ?

Ces tables sont appelées "virtuelles" parce qu'elles :
- ✅ N'existent que **temporairement** pendant l'exécution du trigger
- ✅ **Ne sont pas stockées** physiquement sur le disque
- ✅ **Disparaissent** automatiquement à la fin du trigger
- ✅ Ont **automatiquement la même structure** que la table qui a déclenché le trigger

### Analogie pour comprendre

Imaginez que vous modifiez un document Word :
- **DELETED** serait comme le texte que vous avez sélectionné pour le supprimer (avant de presser Suppr)
- **INSERTED** serait comme le nouveau texte que vous tapez pour le remplacer

Ces informations existent temporairement dans la mémoire de l'ordinateur pendant l'opération, mais ne sont pas sauvegardées de manière permanente.

## Vue d'ensemble : Quel contenu dans quelle table ?

Voici un tableau récapitulatif qui montre quelles tables contiennent des données selon l'opération :

| Opération | Contenu de INSERTED | Contenu de DELETED |
|-----------|---------------------|-------------------|
| **INSERT** | ✅ Les nouvelles lignes ajoutées | ❌ Vide (aucune ligne) |
| **UPDATE** | ✅ Les lignes avec les NOUVELLES valeurs | ✅ Les lignes avec les ANCIENNES valeurs |
| **DELETE** | ❌ Vide (aucune ligne) | ✅ Les lignes supprimées |

### Mémo visuel

```
INSERT :   [DELETED: vide]  →  [Table]  →  [INSERTED: nouvelles données]

UPDATE :   [DELETED: avant] →  [Table]  →  [INSERTED: après]

DELETE :   [DELETED: données supprimées]  →  [Table]  →  [INSERTED: vide]
```

## Structure des tables INSERTED et DELETED

### Même structure que la table source

Les tables INSERTED et DELETED ont **exactement les mêmes colonnes** que la table qui déclenche le trigger.

**Exemple** :

```sql
-- Si votre table Clients est définie comme ceci :
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Nom VARCHAR(50),
    Prenom VARCHAR(50),
    Email VARCHAR(100),
    DateInscription DATE
);

-- Alors INSERTED et DELETED auront aussi ces colonnes :
-- ClientID, Nom, Prenom, Email, DateInscription
```

### Accès aux colonnes

Vous accédez aux colonnes comme vous le feriez avec n'importe quelle table :

```sql
SELECT ClientID, Nom, Email FROM INSERTED;
SELECT ClientID, Nom, Email FROM DELETED;
```

## INSERTED dans un trigger AFTER INSERT

### Ce que contient INSERTED

Après une opération INSERT, INSERTED contient **toutes les lignes qui viennent d'être ajoutées** à la table.

### Exemple : Audit des nouveaux clients

```sql
CREATE TRIGGER trg_Clients_Audit_Insert
ON Clients
AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;

    -- INSERTED contient tous les nouveaux clients
    INSERT INTO Audit_Clients (ClientID, Nom, Prenom, Action, DateAction)
    SELECT
        ClientID,
        Nom,
        Prenom,
        'NOUVEAU CLIENT',
        GETDATE()
    FROM INSERTED;  -- On lit directement dans INSERTED
END;
```

**Ce qui se passe** :

```
1. Utilisateur exécute :
   INSERT INTO Clients (Nom, Prenom, Email)
   VALUES ('Dupont', 'Jean', 'jean@email.com');

2. La ligne est ajoutée à la table Clients

3. Le trigger s'exécute et INSERTED contient :
   ClientID | Nom    | Prenom | Email           | DateInscription
   ---------|--------|--------|-----------------|----------------
   1        | Dupont | Jean   | jean@email.com  | 2024-11-18

4. Le trigger copie ces informations dans Audit_Clients
```

### DELETED est vide

```sql
CREATE TRIGGER trg_Exemple_Insert
ON Clients
AFTER INSERT
AS
BEGIN
    SELECT COUNT(*) AS NombreDansInserted FROM INSERTED;  -- Retourne 1 (ou plus)
    SELECT COUNT(*) AS NombreDansDeleted FROM DELETED;    -- Retourne 0 (toujours vide)
END;
```

## DELETED dans un trigger AFTER DELETE

### Ce que contient DELETED

Après une opération DELETE, DELETED contient **toutes les lignes qui viennent d'être supprimées** de la table.

### Exemple : Archivage automatique

```sql
CREATE TRIGGER trg_Clients_Archive_Delete
ON Clients
AFTER DELETE
AS
BEGIN
    SET NOCOUNT ON;

    -- DELETED contient les clients qui viennent d'être supprimés
    INSERT INTO Clients_Archives (
        ClientID,
        Nom,
        Prenom,
        Email,
        DateSuppression
    )
    SELECT
        ClientID,
        Nom,
        Prenom,
        Email,
        GETDATE()
    FROM DELETED;  -- On récupère les données supprimées
END;
```

**Ce qui se passe** :

```
1. Utilisateur exécute :
   DELETE FROM Clients WHERE ClientID = 1;

2. La ligne est supprimée de la table Clients

3. Le trigger s'exécute et DELETED contient :
   ClientID | Nom    | Prenom | Email           | DateInscription
   ---------|--------|--------|-----------------|----------------
   1        | Dupont | Jean   | jean@email.com  | 2024-01-15

4. Le trigger sauvegarde ces informations dans Clients_Archives
```

### Exemple : Empêcher la suppression

```sql
CREATE TRIGGER trg_Clients_Prevent_Delete
ON Clients
AFTER DELETE
AS
BEGIN
    SET NOCOUNT ON;

    -- Vérifie si les clients supprimés ont des commandes
    IF EXISTS (
        SELECT 1
        FROM DELETED d
        INNER JOIN Commandes c ON d.ClientID = c.ClientID
    )
    BEGIN
        RAISERROR('Impossible de supprimer un client avec des commandes', 16, 1);
        ROLLBACK TRANSACTION;
    END
END;
```

### INSERTED est vide

```sql
CREATE TRIGGER trg_Exemple_Delete
ON Clients
AFTER DELETE
AS
BEGIN
    SELECT COUNT(*) AS NombreDansDeleted FROM DELETED;   -- Retourne 1 (ou plus)
    SELECT COUNT(*) AS NombreDansInserted FROM INSERTED; -- Retourne 0 (toujours vide)
END;
```

## INSERTED et DELETED dans un trigger AFTER UPDATE

### Les deux tables contiennent des données

Lors d'un UPDATE, les choses deviennent plus intéressantes car **les deux tables contiennent des données** :

- **DELETED** : Les valeurs **AVANT** la modification
- **INSERTED** : Les valeurs **APRÈS** la modification

### Visualisation d'un UPDATE

```sql
-- État initial de la table Clients :
ClientID | Nom    | Prenom | Salaire
---------|--------|--------|--------
1        | Dupont | Jean   | 30000

-- L'utilisateur exécute :
UPDATE Clients SET Salaire = 35000 WHERE ClientID = 1;

-- Pendant le trigger :

-- DELETED contient les ANCIENNES valeurs :
ClientID | Nom    | Prenom | Salaire
---------|--------|--------|--------
1        | Dupont | Jean   | 30000    ← Ancien salaire

-- INSERTED contient les NOUVELLES valeurs :
ClientID | Nom    | Prenom | Salaire
---------|--------|--------|--------
1        | Dupont | Jean   | 35000    ← Nouveau salaire
```

### Exemple : Audit des modifications de salaire

```sql
CREATE TRIGGER trg_Employes_Audit_Salaire
ON Employes
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Compare les anciennes et nouvelles valeurs
    INSERT INTO Audit_Salaires (
        EmployeID,
        AncienSalaire,
        NouveauSalaire,
        Augmentation,
        DateModification,
        Utilisateur
    )
    SELECT
        i.EmployeID,
        d.Salaire AS AncienSalaire,      -- De DELETED
        i.Salaire AS NouveauSalaire,     -- De INSERTED
        i.Salaire - d.Salaire AS Augmentation,
        GETDATE(),
        SYSTEM_USER
    FROM INSERTED i
    INNER JOIN DELETED d ON i.EmployeID = d.EmployeID
    WHERE i.Salaire != d.Salaire;  -- Seulement si le salaire a vraiment changé
END;
```

### Jointure INSERTED et DELETED

Pour comparer les anciennes et nouvelles valeurs, vous devez **joindre INSERTED et DELETED** sur la clé primaire :

```sql
SELECT
    i.EmployeID,
    d.Nom AS AncienNom,
    i.Nom AS NouveauNom,
    d.Email AS AncienEmail,
    i.Email AS NouveauEmail
FROM INSERTED i
INNER JOIN DELETED d ON i.EmployeID = d.EmployeID;
```

### Exemple : Détecter quelles colonnes ont changé

```sql
CREATE TRIGGER trg_Clients_Detect_Changes
ON Clients
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Enregistre quelles colonnes ont été modifiées
    INSERT INTO Audit_Modifications (ClientID, ColonneModifiee, DateModif)
    SELECT
        i.ClientID,
        CASE
            WHEN i.Nom != d.Nom THEN 'Nom'
            WHEN i.Prenom != d.Prenom THEN 'Prenom'
            WHEN i.Email != d.Email THEN 'Email'
            WHEN i.Telephone != d.Telephone THEN 'Telephone'
        END,
        GETDATE()
    FROM INSERTED i
    INNER JOIN DELETED d ON i.ClientID = d.ClientID
    WHERE
        i.Nom != d.Nom
        OR i.Prenom != d.Prenom
        OR i.Email != d.Email
        OR i.Telephone != d.Telephone;
END;
```

## La fonction UPDATE() pour détecter les colonnes modifiées

### Qu'est-ce que UPDATE() ?

`UPDATE(nom_colonne)` est une fonction spéciale utilisable uniquement dans les triggers qui indique si une colonne a été **mentionnée** dans l'instruction UPDATE.

### Syntaxe

```sql
IF UPDATE(NomColonne)
BEGIN
    -- Cette colonne a été mentionnée dans l'UPDATE
END
```

### Exemple : Réagir seulement aux modifications de salaire

```sql
CREATE TRIGGER trg_Employes_Only_Salaire
ON Employes
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- N'agit que si la colonne Salaire a été modifiée
    IF UPDATE(Salaire)
    BEGIN
        INSERT INTO Audit_Salaires (EmployeID, NouveauSalaire, DateModif)
        SELECT EmployeID, Salaire, GETDATE()
        FROM INSERTED;
    END

    -- Si d'autres colonnes sont modifiées, le trigger ne fait rien
END;
```

### Différence importante : UPDATE() vs comparaison de valeurs

⚠️ **ATTENTION** : `UPDATE(Salaire)` retourne TRUE si la colonne est **mentionnée** dans l'UPDATE, même si la valeur n'a pas changé !

```sql
-- Cet UPDATE mentionne Salaire, donc UPDATE(Salaire) = TRUE
UPDATE Employes SET Salaire = Salaire WHERE EmployeID = 1;
-- Même si la valeur reste identique !

-- Pour vérifier si la valeur a VRAIMENT changé :
IF UPDATE(Salaire)
BEGIN
    -- Vérifier que la valeur est différente
    IF EXISTS (
        SELECT 1
        FROM INSERTED i
        INNER JOIN DELETED d ON i.EmployeID = d.EmployeID
        WHERE i.Salaire != d.Salaire
    )
    BEGIN
        -- Ici, le salaire a VRAIMENT changé
    END
END
```

### Vérifier plusieurs colonnes

```sql
CREATE TRIGGER trg_Employes_Infos_Sensibles
ON Employes
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Réagit si le salaire OU le poste a été modifié
    IF UPDATE(Salaire) OR UPDATE(Poste)
    BEGIN
        INSERT INTO Audit_Modifications (
            EmployeID,
            Message,
            DateModif
        )
        SELECT
            EmployeID,
            'Modification d''information sensible',
            GETDATE()
        FROM INSERTED;
    END
END;
```

## Gestion des valeurs NULL

### Problème avec la comparaison directe

```sql
-- ⚠️ ATTENTION : Ceci ne fonctionne pas correctement avec les NULL
WHERE i.Email != d.Email

-- Si l'ancien Email était NULL et le nouveau aussi NULL,
-- NULL != NULL retourne UNKNOWN (pas TRUE ni FALSE)
```

### Solution : Utiliser des comparaisons sécurisées

```sql
-- ✅ Méthode 1 : Utiliser ISNULL
WHERE ISNULL(i.Email, '') != ISNULL(d.Email, '')

-- ✅ Méthode 2 : Utiliser une comparaison explicite
WHERE (i.Email != d.Email)
   OR (i.Email IS NULL AND d.Email IS NOT NULL)
   OR (i.Email IS NOT NULL AND d.Email IS NULL)

-- ✅ Méthode 3 (SQL Server 2022+) : Utiliser IS DISTINCT FROM
WHERE i.Email IS DISTINCT FROM d.Email
```

### Exemple complet avec gestion des NULL

```sql
CREATE TRIGGER trg_Clients_Update_Email
ON Clients
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    IF UPDATE(Email)
    BEGIN
        -- Enregistre les changements d'email, en gérant les NULL
        INSERT INTO Audit_Email (
            ClientID,
            AncienEmail,
            NouveauEmail,
            DateModif
        )
        SELECT
            i.ClientID,
            ISNULL(d.Email, '(vide)'),
            ISNULL(i.Email, '(vide)'),
            GETDATE()
        FROM INSERTED i
        INNER JOIN DELETED d ON i.ClientID = d.ClientID
        WHERE ISNULL(i.Email, '') != ISNULL(d.Email, '');
    END
END;
```

## Opérations en masse : Plusieurs lignes dans INSERTED/DELETED

### Concept fondamental

Les tables INSERTED et DELETED peuvent contenir **plusieurs lignes** si l'opération DML affecte plusieurs lignes en une seule instruction.

### Exemple visuel

```sql
-- Modification de 3 employés en une seule instruction
UPDATE Employes
SET Salaire = Salaire * 1.10
WHERE Departement = 'Ventes';
-- Suppose que 3 employés sont dans le département Ventes

-- DELETED contient :
EmployeID | Nom    | Salaire | Departement
----------|--------|---------|------------
1         | Dupont | 30000   | Ventes
2         | Martin | 32000   | Ventes
3         | Durand | 28000   | Ventes

-- INSERTED contient :
EmployeID | Nom    | Salaire | Departement
----------|--------|---------|------------
1         | Dupont | 33000   | Ventes      ← Salaire augmenté de 10%
2         | Martin | 35200   | Ventes
3         | Durand | 30800   | Ventes

-- Le trigger s'exécute UNE SEULE FOIS avec ces 3 lignes dans chaque table
```

### Erreur courante : Traiter comme une seule ligne

```sql
-- ❌ MAUVAISE PRATIQUE : Suppose qu'il n'y a qu'une seule ligne
CREATE TRIGGER trg_Mauvais_Exemple
ON Employes
AFTER UPDATE
AS
BEGIN
    DECLARE @EmployeID INT;
    DECLARE @NouveauSalaire DECIMAL(10,2);

    -- Ceci ne récupère qu'UNE ligne, même s'il y en a plusieurs !
    SELECT @EmployeID = EmployeID, @NouveauSalaire = Salaire
    FROM INSERTED;

    -- Le reste du code ne traite qu'un seul employé
    -- Les autres sont ignorés ! 💥
END;
```

### Bonne pratique : Traitement ensembliste

```sql
-- ✅ BONNE PRATIQUE : Traite toutes les lignes en une seule opération
CREATE TRIGGER trg_Bon_Exemple
ON Employes
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Traite TOUTES les lignes en une seule instruction
    INSERT INTO Audit_Salaires (EmployeID, AncienSalaire, NouveauSalaire, DateModif)
    SELECT
        i.EmployeID,
        d.Salaire,
        i.Salaire,
        GETDATE()
    FROM INSERTED i
    INNER JOIN DELETED d ON i.EmployeID = d.EmployeID
    WHERE i.Salaire != d.Salaire;

    -- Aucune boucle nécessaire, SQL Server traite tout d'un coup
END;
```

## Techniques avancées avec INSERTED et DELETED

### Compter le nombre de lignes affectées

```sql
CREATE TRIGGER trg_Count_Rows
ON Clients
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @InsertedCount INT = (SELECT COUNT(*) FROM INSERTED);
    DECLARE @DeletedCount INT = (SELECT COUNT(*) FROM DELETED);

    -- Enregistre des statistiques
    INSERT INTO Statistiques_Operations (
        TableName,
        OperationType,
        RowCount,
        DateOperation
    )
    VALUES (
        'Clients',
        CASE
            WHEN @InsertedCount > 0 AND @DeletedCount = 0 THEN 'INSERT'
            WHEN @InsertedCount > 0 AND @DeletedCount > 0 THEN 'UPDATE'
            WHEN @InsertedCount = 0 AND @DeletedCount > 0 THEN 'DELETE'
        END,
        COALESCE(@InsertedCount, @DeletedCount),
        GETDATE()
    );
END;
```

### Récupérer des valeurs agrégées

```sql
CREATE TRIGGER trg_Stats_Salaires
ON Employes
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    IF UPDATE(Salaire)
    BEGIN
        -- Calcule des statistiques sur les changements de salaire
        INSERT INTO Stats_Augmentations (
            NombreEmployes,
            AugmentationMoyenne,
            AugmentationTotale,
            DateCalcul
        )
        SELECT
            COUNT(*),
            AVG(i.Salaire - d.Salaire),
            SUM(i.Salaire - d.Salaire),
            GETDATE()
        FROM INSERTED i
        INNER JOIN DELETED d ON i.EmployeID = d.EmployeID
        WHERE i.Salaire != d.Salaire;
    END
END;
```

### Vérifications conditionnelles complexes

```sql
CREATE TRIGGER trg_Validation_Complexe
ON Employes
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Empêche de réduire le salaire d'un manager
    IF EXISTS (
        SELECT 1
        FROM INSERTED i
        INNER JOIN DELETED d ON i.EmployeID = d.EmployeID
        WHERE i.Salaire < d.Salaire  -- Salaire réduit
          AND i.EstManager = 1        -- C'est un manager
    )
    BEGIN
        RAISERROR('Impossible de réduire le salaire d''un manager', 16, 1);
        ROLLBACK TRANSACTION;
    END

    -- Empêche d'augmenter un salaire de plus de 20% en une fois
    IF EXISTS (
        SELECT 1
        FROM INSERTED i
        INNER JOIN DELETED d ON i.EmployeID = d.EmployeID
        WHERE i.Salaire > d.Salaire * 1.20
    )
    BEGIN
        RAISERROR('Augmentation supérieure à 20% non autorisée', 16, 1);
        ROLLBACK TRANSACTION;
    END
END;
```

## Débogage : Voir le contenu des tables virtuelles

### Technique de débogage temporaire

Pendant le développement, vous pouvez vouloir voir ce que contiennent INSERTED et DELETED :

```sql
CREATE TRIGGER trg_Debug_Exemple
ON Clients
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Pour le débogage uniquement : affiche le contenu
    SELECT 'INSERTED' AS Source, * FROM INSERTED;
    SELECT 'DELETED' AS Source, * FROM DELETED;

    -- Votre code normal ici
    -- ...
END;
```

**⚠️ IMPORTANT** : Retirez ces SELECT de débogage en production ! Ils peuvent perturber les applications clientes.

### Enregistrer dans une table de log

Méthode plus propre pour le débogage :

```sql
CREATE TRIGGER trg_Debug_Proper
ON Clients
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Enregistre dans une table de log.
    -- ⚠️ On ne peut PAS écrire CAST(INSERTED.* AS VARCHAR(MAX)) : « .* » n'est pas castable.
    -- On sérialise donc les colonnes voulues, par exemple avec CONCAT (qui gère les NULL).
    INSERT INTO Debug_Trigger_Log (TriggerName, TableSource, Content, LogDate)
    SELECT
        'trg_Debug_Proper',
        'INSERTED',
        CONCAT('ClientID=', ClientID, '; Nom=', Nom, '; Email=', Email),
        GETDATE()
    FROM INSERTED;

    -- Même chose pour DELETED
    INSERT INTO Debug_Trigger_Log (TriggerName, TableSource, Content, LogDate)
    SELECT
        'trg_Debug_Proper',
        'DELETED',
        CONCAT('ClientID=', ClientID, '; Nom=', Nom, '; Email=', Email),
        GETDATE()
    FROM DELETED;

    -- Astuce : pour sérialiser TOUTES les colonnes d'un coup, on peut aussi utiliser
    -- (SELECT * FROM INSERTED FOR XML AUTO, ELEMENTS) dans une colonne XML ou NVARCHAR(MAX).
END;
```

## Limitations et pièges

### Limitation 1 : Ne pas pouvoir modifier INSERTED et DELETED

```sql
-- ❌ IMPOSSIBLE : On ne peut pas modifier ces tables
UPDATE INSERTED SET Nom = 'Nouveau nom';  -- ERREUR !
DELETE FROM DELETED WHERE ClientID = 1;   -- ERREUR !
```

Ces tables sont en **lecture seule**. Vous pouvez seulement les consulter.

### Limitation 2 : Disponibilité limitée

INSERTED et DELETED n'existent que **pendant l'exécution du trigger**. Vous ne pouvez pas y accéder en dehors.

```sql
-- ❌ IMPOSSIBLE en dehors d'un trigger
SELECT * FROM INSERTED;  -- ERREUR : Invalid object name 'INSERTED'
```

### Piège 3 : Oublier la jointure dans les UPDATE

```sql
-- ❌ ERREUR FRÉQUENTE : Oublie la jointure
CREATE TRIGGER trg_Oubli_Jointure
ON Employes
AFTER UPDATE
AS
BEGIN
    INSERT INTO Audit (EmployeID, AncienSalaire, NouveauSalaire)
    SELECT
        EmployeID,
        (SELECT Salaire FROM DELETED),      -- ⚠️ Retourne UNE valeur ou NULL
        (SELECT Salaire FROM INSERTED)      -- Même problème
    FROM INSERTED;
END;

-- ✅ CORRECT : Avec jointure
CREATE TRIGGER trg_Avec_Jointure
ON Employes
AFTER UPDATE
AS
BEGIN
    INSERT INTO Audit (EmployeID, AncienSalaire, NouveauSalaire)
    SELECT
        i.EmployeID,
        d.Salaire,  -- Correctement associé ligne par ligne
        i.Salaire
    FROM INSERTED i
    INNER JOIN DELETED d ON i.EmployeID = d.EmployeID;
END;
```

## Récapitulatif

### Tableau récapitulatif complet

| Opération | INSERTED | DELETED | Usage typique |
|-----------|----------|---------|---------------|
| **INSERT** | ✅ Nouvelles lignes | ❌ Vide | Audit des créations, validation des nouvelles données |
| **UPDATE** | ✅ Valeurs APRÈS | ✅ Valeurs AVANT | Comparaison avant/après, audit des modifications |
| **DELETE** | ❌ Vide | ✅ Lignes supprimées | Archivage, validation avant suppression |

### Points clés à retenir

1. **Tables temporaires** : INSERTED et DELETED existent uniquement pendant l'exécution du trigger
2. **Structure identique** : Elles ont les mêmes colonnes que la table source
3. **Lecture seule** : Vous pouvez les consulter mais pas les modifier
4. **Peuvent contenir plusieurs lignes** : Toujours écrire du code qui gère plusieurs lignes
5. **UPDATE() est différent** : La fonction UPDATE() détecte les colonnes mentionnées, pas forcément modifiées
6. **Attention aux NULL** : Utiliser ISNULL ou des comparaisons explicites pour éviter les bugs
7. **Jointure obligatoire pour UPDATE** : Joindre INSERTED et DELETED sur la clé primaire pour comparer

### Meilleures pratiques

✅ **Faire** :
- Toujours utiliser des opérations ensemblistes (SELECT, INSERT, UPDATE avec FROM)
- Joindre INSERTED et DELETED sur la clé primaire dans les triggers UPDATE
- Gérer correctement les valeurs NULL dans les comparaisons
- Tester avec plusieurs lignes, pas seulement une

❌ **Ne pas faire** :
- Utiliser des variables scalaires qui ne récupèrent qu'une ligne
- Oublier que ces tables peuvent contenir plusieurs lignes
- Essayer de modifier INSERTED ou DELETED
- Comparer directement des colonnes qui peuvent contenir NULL

## Conclusion

Les tables virtuelles INSERTED et DELETED sont le **cœur du système de triggers** en SQL Server. Bien les comprendre est essentiel pour :
- Écrire des triggers corrects et performants
- Éviter les bugs subtils liés aux opérations en masse
- Implémenter correctement l'audit et la validation des données

La règle d'or : **Pensez toujours "ensemble de lignes", jamais "une ligne à la fois"** !
