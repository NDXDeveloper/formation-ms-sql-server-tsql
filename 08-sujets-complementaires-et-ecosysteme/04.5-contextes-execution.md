# 8.4.5 Contextes d'exécution (EXECUTE AS)

## Introduction

Imaginez que vous êtes un **acteur de théâtre**. Normalement, vous jouez votre propre rôle avec votre propre personnalité. Mais parfois, vous devez **incarner un autre personnage** et agir comme si vous étiez cette autre personne. Pendant que vous jouez ce rôle, vous avez les caractéristiques, les connaissances et les capacités de ce personnage, pas les vôtres.

Dans SQL Server, **EXECUTE AS** fonctionne de la même manière : vous pouvez temporairement **"devenir" un autre utilisateur** et exécuter du code avec **ses permissions** au lieu des vôtres.

**Analogie visuelle** :

```
Vous êtes "Jean" (développeur)          Vous devenez temporairement "Admin"
   avec permissions limitées              avec permissions étendues
           ↓                                          ↓
    ┌─────────────┐                           ┌─────────────┐
    │    Jean     │  ──EXECUTE AS Admin──→    │    Admin    │
    │  (Dev)      │                           │  (DBA)      │
    │ Permissions:│                           │ Permissions:│
    │  - SELECT   │                           │  - TOUT !   │
    │  - INSERT   │                           │  - CREATE   │
    └─────────────┘                           │  - DROP     │
                                              │  - ALTER    │
                                              └─────────────┘
                          ↓
                    Vous exécutez du code
                   avec les droits Admin
                          ↓
                      REVERT
                          ↓
                  Retour à "Jean"
```

## Qu'est-ce que EXECUTE AS ?

**EXECUTE AS** est une commande SQL qui permet de **changer le contexte d'exécution** - c'est-à-dire "qui vous êtes" du point de vue de SQL Server.

### Le contexte d'exécution, c'est quoi ?

Le **contexte d'exécution** détermine :
- 🎭 **Quelle identité** SQL Server voit quand vous exécutez du code
- 🔑 **Quelles permissions** sont utilisées pour vérifier les accès
- 📝 **Quel nom** apparaît dans les logs d'audit
- 🏠 **Quel schéma par défaut** est utilisé

Par défaut, vous exécutez toujours dans **votre propre contexte** (avec vos permissions). `EXECUTE AS` permet de basculer temporairement dans le contexte d'un autre utilisateur.

## Pourquoi utiliser EXECUTE AS ?

### Cas d'usage 1 : Tester les permissions

Vous avez configuré des permissions pour un rôle et voulez vérifier qu'elles fonctionnent correctement **sans avoir à vous déconnecter et reconnecter** avec un autre compte.

```sql
-- Vous êtes Admin, vous voulez tester les permissions de Jean
EXECUTE AS USER = 'Jean';

-- Maintenant vous "êtes" Jean, testez ses permissions
SELECT * FROM dbo.Clients;  -- Fonctionne si Jean a SELECT
DELETE FROM dbo.Clients WHERE ClientID = 1;  -- Échoue si Jean n'a pas DELETE

-- Revenir à votre identité
REVERT;
```

**Avantage** : Pas besoin de créer une session de test séparée !

### Cas d'usage 2 : Procédures stockées avec permissions élevées

Une application a besoin d'effectuer une opération qui nécessite des permissions élevées, mais vous ne voulez pas donner ces permissions directement à l'application.

```sql
-- L'application n'a pas le droit de supprimer directement
-- Mais elle peut appeler cette procédure qui s'exécute avec les droits du propriétaire

CREATE PROCEDURE dbo.SupprimerClientInactif
    @ClientID INT
WITH EXECUTE AS OWNER  -- S'exécute avec les droits du propriétaire (dbo)
AS
BEGIN
    -- Validations métier
    IF NOT EXISTS (
        SELECT 1 FROM dbo.Clients
        WHERE ClientID = @ClientID
        AND DerniereActivite < DATEADD(YEAR, -3, GETDATE())
    )
    BEGIN
        THROW 50001, 'Client non éligible à la suppression', 1;
    END

    -- Suppression (avec les droits du propriétaire)
    DELETE FROM dbo.Clients WHERE ClientID = @ClientID;
END;
GO

-- L'application peut exécuter la procédure
GRANT EXECUTE ON dbo.SupprimerClientInactif TO AppWeb;

-- Mais n'a PAS de droit DELETE direct sur la table
-- (pas de GRANT DELETE sur dbo.Clients)
```

**Avantage** : Contrôle fin et logique métier centralisée !

### Cas d'usage 3 : Débogage et audit

Un administrateur veut voir exactement ce qu'un utilisateur peut faire pour comprendre un problème de permissions.

```sql
-- Admin veut comprendre pourquoi Analyste ne peut pas accéder aux rapports

-- Se mettre dans la peau de l'Analyste
EXECUTE AS USER = 'Analyste';

-- Voir quelles permissions il a réellement
SELECT * FROM fn_my_permissions(NULL, 'DATABASE');

-- Tester l'accès problématique
SELECT * FROM dbo.RapportsConfidentiels;  -- Échouera avec le message d'erreur exact

-- Revenir au contexte Admin
REVERT;
```

### Cas d'usage 4 : Développement et migration

Créer des objets dans un schéma dont vous n'êtes pas le propriétaire.

```sql
-- Vous êtes AdminDB, mais voulez créer une table dans le schéma RH
-- (dont le propriétaire est le user 'RH_Owner')

EXECUTE AS USER = 'RH_Owner';

CREATE TABLE RH.NouvelleTable (
    ID INT PRIMARY KEY,
    Nom NVARCHAR(100)
);
-- La table est créée avec RH_Owner comme propriétaire

REVERT;
```

## Les différentes formes de EXECUTE AS

Il existe plusieurs variantes d'EXECUTE AS, chacune avec un usage spécifique.

### 1. EXECUTE AS USER (au niveau base de données)

Basculer vers un **utilisateur** de la base de données.

```sql
-- Syntaxe
EXECUTE AS USER = 'NomUtilisateur';

-- Exemple
EXECUTE AS USER = 'Jean';
SELECT USER_NAME();  -- Retourne 'Jean'
REVERT;
```

**Utilisation** : Tester les permissions au niveau base de données.

### 2. EXECUTE AS LOGIN (au niveau serveur)

Basculer vers un **login** au niveau du serveur.

```sql
-- Syntaxe
EXECUTE AS LOGIN = 'NomLogin';

-- Exemple
EXECUTE AS LOGIN = 'AppLogin';
-- Maintenant vous pouvez accéder aux bases auxquelles AppLogin a accès
SELECT * FROM sys.databases WHERE name = 'MaBase';
REVERT;
```

**Utilisation** : Tester les permissions au niveau serveur (moins courant).

### 3. EXECUTE AS CALLER (dans une procédure)

La procédure s'exécute avec les permissions de **celui qui l'appelle**.

```sql
CREATE PROCEDURE dbo.ConsulterClients
WITH EXECUTE AS CALLER  -- Par défaut (peut être omis)
AS
BEGIN
    -- S'exécute avec les droits de l'appelant
    SELECT * FROM dbo.Clients;
END;
```

**Comportement** :
- Si Jean appelle la procédure, elle s'exécute avec les permissions de Jean
- Si Marie appelle la procédure, elle s'exécute avec les permissions de Marie

C'est le **comportement par défaut** si vous ne spécifiez rien.

### 4. EXECUTE AS OWNER (dans une procédure)

La procédure s'exécute avec les permissions du **propriétaire** de la procédure.

```sql
CREATE PROCEDURE dbo.CreerAudit
WITH EXECUTE AS OWNER  -- S'exécute avec les droits du propriétaire (dbo)
AS
BEGIN
    -- Même si l'appelant n'a pas de droits sur AuditLog,
    -- cette instruction fonctionne car elle s'exécute avec les droits de dbo
    INSERT INTO dbo.AuditLog (DateEvent, Details)
    VALUES (GETDATE(), 'Audit créé');
END;
```

**Avantage** : L'utilisateur n'a pas besoin de permissions sur les tables internes.

### 5. EXECUTE AS SELF (dans une procédure)

La procédure s'exécute avec les permissions de **celui qui l'a créée**.

```sql
-- Jean crée une procédure
CREATE PROCEDURE dbo.RapportSpecial
WITH EXECUTE AS SELF  -- S'exécute avec les droits de Jean (créateur)
AS
BEGIN
    SELECT * FROM dbo.DonneesSensibles;
END;
```

**Particularité** : Même si Jean est supprimé ou perd ses permissions, la procédure continue de fonctionner avec les permissions qu'il avait au moment de la création.

### 6. EXECUTE AS 'NomUtilisateur' (dans une procédure)

La procédure s'exécute avec les permissions d'un **utilisateur spécifique**.

```sql
CREATE PROCEDURE dbo.ProcedurePrivilegiee
WITH EXECUTE AS 'Admin'  -- S'exécute toujours avec les droits d'Admin
AS
BEGIN
    -- Code avec permissions Admin
    ALTER TABLE dbo.Produits ADD NouvelleColonne INT;
END;
```

**Attention** : Nécessite que le créateur de la procédure ait la permission `IMPERSONATE` sur cet utilisateur.

## REVERT : Revenir au contexte original

Après avoir utilisé `EXECUTE AS`, vous devez **revenir** à votre contexte original avec `REVERT`.

### Syntaxe simple

```sql
-- Changer de contexte
EXECUTE AS USER = 'Jean';

-- Faire des opérations en tant que Jean
SELECT USER_NAME();  -- Retourne 'Jean'

-- Revenir à votre contexte original
REVERT;

SELECT USER_NAME();  -- Retourne votre nom original
```

### REVERT peut être appelé plusieurs fois

Si vous empilez plusieurs `EXECUTE AS`, `REVERT` revient d'un niveau à la fois.

```sql
SELECT USER_NAME();  -- Admin (contexte initial)

EXECUTE AS USER = 'Jean';
SELECT USER_NAME();  -- Jean

EXECUTE AS USER = 'Marie';
SELECT USER_NAME();  -- Marie

REVERT;
SELECT USER_NAME();  -- Jean (retour d'un niveau)

REVERT;
SELECT USER_NAME();  -- Admin (retour au contexte initial)
```

**Analogie** : C'est comme une **pile d'assiettes**. Vous empilez les contextes, et REVERT retire le contexte du dessus.

```
┌─────────────┐
│   Marie     │  ← REVERT retire ce niveau
├─────────────┤
│    Jean     │  ← REVERT retire ensuite ce niveau
├─────────────┤
│   Admin     │  ← Contexte initial
└─────────────┘
```

### ⚠️ N'oubliez jamais REVERT !

Si vous oubliez `REVERT`, vous resterez dans le contexte changé, ce qui peut causer des problèmes inattendus.

```sql
-- Bonne pratique : Toujours utiliser dans un bloc TRY/CATCH
BEGIN TRY
    EXECUTE AS USER = 'Jean';

    -- Vos opérations ici
    SELECT * FROM dbo.Clients;

    REVERT;  -- Toujours appelé en cas de succès
END TRY
BEGIN CATCH
    -- Même en cas d'erreur, on revient au contexte original
    IF EXISTS (SELECT 1 FROM sys.dm_exec_sessions WHERE session_id = @@SPID AND original_login_name != login_name)
        REVERT;

    -- Gérer l'erreur
    THROW;
END CATCH;
```

## Vérifier le contexte actuel

Comment savoir dans quel contexte vous êtes actuellement ?

### Fonctions utiles

```sql
-- Nom de l'utilisateur actuel (contexte d'exécution)
SELECT USER_NAME() AS ContexteActuel;

-- Login original (qui s'est vraiment connecté)
SELECT ORIGINAL_LOGIN() AS LoginOriginal;

-- Login actuel (peut être différent après EXECUTE AS LOGIN)
SELECT SYSTEM_USER AS LoginActuel;

-- Tout voir en une fois
SELECT
    USER_NAME() AS ContexteUser,
    SYSTEM_USER AS LoginActuel,
    ORIGINAL_LOGIN() AS LoginOriginal;
```

### Exemple de différence

```sql
-- Vous êtes connecté comme AdminDB
SELECT USER_NAME();        -- AdminDB
SELECT ORIGINAL_LOGIN();   -- AdminDB

-- Vous changez de contexte
EXECUTE AS USER = 'Jean';

SELECT USER_NAME();        -- Jean (contexte actuel)
SELECT ORIGINAL_LOGIN();   -- AdminDB (connexion réelle)

REVERT;
```

## Le concept d'Ownership Chaining (chaînage de propriété)

C'est un concept très important lié à EXECUTE AS.

### Qu'est-ce que l'Ownership Chaining ?

Quand plusieurs objets SQL (tables, vues, procédures) appartiennent au **même propriétaire**, SQL Server "enchaîne" les permissions : il ne vérifie les permissions que sur le **premier objet**, pas sur les objets dépendants.

### Exemple sans Ownership Chaining (problème)

```sql
-- Propriétaires différents
CREATE TABLE RH.Salaires (...);  -- Propriétaire : RH_Owner
GO

-- Créer une vue sur cette table (propriétaire différent)
CREATE VIEW dbo.VueSalairesPublics  -- Propriétaire : dbo
AS
SELECT EmployeID, Salaire FROM RH.Salaires WHERE Salaire < 50000;
GO

-- Donner accès à la vue
GRANT SELECT ON dbo.VueSalairesPublics TO Analyste;

-- L'Analyste essaie d'utiliser la vue
-- ❌ ERREUR : "SELECT permission denied on object 'Salaires'"
-- Car la chaîne de propriété est brisée (propriétaires différents)
```

**Problème** : SQL Server vérifie les permissions sur **chaque objet** de la chaîne, car les propriétaires sont différents.

### Exemple avec Ownership Chaining (fonctionne)

```sql
-- Même propriétaire (dbo) pour tout
CREATE TABLE dbo.Salaires (...);  -- Propriétaire : dbo
GO

CREATE VIEW dbo.VueSalairesPublics  -- Propriétaire : dbo
AS
SELECT EmployeID, Salaire FROM dbo.Salaires WHERE Salaire < 50000;
GO

-- Donner accès à la vue
GRANT SELECT ON dbo.VueSalairesPublics TO Analyste;

-- L'Analyste utilise la vue
-- ✅ FONCTIONNE !
-- SQL Server vérifie seulement la permission sur la VUE, pas sur la table
```

**Avantage** : L'Analyste peut utiliser la vue **sans avoir besoin de permissions sur la table sous-jacente**.

### Solution avec EXECUTE AS pour briser la chaîne intentionnellement

```sql
-- Si vous voulez créer une vue avec un propriétaire différent
-- mais que cela fonctionne quand même

CREATE VIEW RH.VueSalairesLimites
WITH EXECUTE AS OWNER
AS
SELECT EmployeID, Salaire
FROM dbo.Salaires  -- Propriétaire différent, mais EXECUTE AS OWNER contourne
WHERE Salaire < 50000;
GO

-- Maintenant cela fonctionne même avec des propriétaires différents
GRANT SELECT ON RH.VueSalairesLimites TO Analyste;
```

## Exemples pratiques complets

### Exemple 1 : Procédure d'audit sécurisée

```sql
-- Table d'audit (accès restreint)
CREATE TABLE dbo.AuditLog (
    AuditID INT IDENTITY(1,1) PRIMARY KEY,
    DateEvent DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    UserName NVARCHAR(128) NOT NULL,
    Action NVARCHAR(255) NOT NULL,
    Details NVARCHAR(MAX)
);
GO

-- Personne ne peut lire ou écrire directement dans AuditLog
-- (aucun GRANT)

-- Procédure pour enregistrer un audit
CREATE PROCEDURE dbo.EnregistrerAudit
    @Action NVARCHAR(255),
    @Details NVARCHAR(MAX) = NULL
WITH EXECUTE AS OWNER  -- S'exécute avec les droits de dbo
AS
BEGIN
    -- Enregistrer qui appelle réellement la procédure
    INSERT INTO dbo.AuditLog (UserName, Action, Details)
    VALUES (ORIGINAL_LOGIN(), @Action, @Details);
END;
GO

-- Tout le monde peut appeler cette procédure
GRANT EXECUTE ON dbo.EnregistrerAudit TO PUBLIC;

-- Utilisation par n'importe quel user
EXEC dbo.EnregistrerAudit
    @Action = 'Consultation rapport',
    @Details = 'Rapport Q3 2024';

-- L'utilisateur ne peut PAS :
-- - Modifier les logs existants
-- - Supprimer des logs
-- - Insérer directement dans AuditLog
-- Il peut SEULEMENT appeler la procédure qui valide et enregistre
```

**Avantages** :
- ✅ Logs d'audit protégés contre la falsification
- ✅ Logique centralisée et contrôlée
- ✅ Utilisateurs n'ont pas de permissions directes sur la table

### Exemple 2 : Gestion de compte utilisateur

```sql
-- Application web qui gère les utilisateurs
-- L'application ne doit PAS avoir db_owner, mais doit créer des users

CREATE PROCEDURE dbo.CreerUtilisateurApplication
    @NomUtilisateur NVARCHAR(128),
    @MotDePasse NVARCHAR(128)
WITH EXECUTE AS OWNER  -- S'exécute avec droits administratifs
AS
BEGIN
    -- Validations métier
    IF LEN(@MotDePasse) < 8
        THROW 50001, 'Le mot de passe doit contenir au moins 8 caractères', 1;

    IF EXISTS (SELECT 1 FROM sys.database_principals WHERE name = @NomUtilisateur)
        THROW 50002, 'Cet utilisateur existe déjà', 1;

    -- Création du login et user (nécessite des droits élevés)
    DECLARE @SQL NVARCHAR(MAX);

    SET @SQL = 'CREATE LOGIN ' + QUOTENAME(@NomUtilisateur) +
               ' WITH PASSWORD = ' + QUOTENAME(@MotDePasse, '''');
    EXEC sp_executesql @SQL;

    SET @SQL = 'CREATE USER ' + QUOTENAME(@NomUtilisateur) +
               ' FOR LOGIN ' + QUOTENAME(@NomUtilisateur);
    EXEC sp_executesql @SQL;

    -- Ajouter au rôle utilisateur standard
    SET @SQL = 'ALTER ROLE RoleUtilisateursApp ADD MEMBER ' + QUOTENAME(@NomUtilisateur);
    EXEC sp_executesql @SQL;

    -- Audit
    EXEC dbo.EnregistrerAudit
        @Action = 'Création utilisateur',
        @Details = @NomUtilisateur;
END;
GO

-- L'application peut créer des users via la procédure
GRANT EXECUTE ON dbo.CreerUtilisateurApplication TO AppWeb;

-- Mais AppWeb n'a PAS les droits CREATE LOGIN ni CREATE USER directement
```

### Exemple 3 : Tester les permissions avant déploiement

```sql
-- Script de validation des permissions avant déploiement en production

-- Créer un user de test
CREATE USER TestAnalyste WITHOUT LOGIN;
ALTER ROLE RoleAnalystes ADD MEMBER TestAnalyste;

-- Tester les permissions de ce rôle
PRINT '=== Test des permissions du rôle Analystes ===';

EXECUTE AS USER = 'TestAnalyste';

-- Test 1 : Lecture des ventes (doit fonctionner)
BEGIN TRY
    SELECT TOP 1 * FROM dbo.Ventes;
    PRINT '✓ Test 1 : SELECT sur Ventes OK';
END TRY
BEGIN CATCH
    PRINT '✗ Test 1 : SELECT sur Ventes ÉCHEC - ' + ERROR_MESSAGE();
END CATCH;

-- Test 2 : Lecture des salaires (doit échouer)
BEGIN TRY
    SELECT TOP 1 * FROM dbo.Salaires;
    PRINT '✗ Test 2 : SELECT sur Salaires OK (ne devrait pas fonctionner!)';
END TRY
BEGIN CATCH
    PRINT '✓ Test 2 : SELECT sur Salaires bloqué comme prévu';
END CATCH;

-- Test 3 : Modification des données (doit échouer)
BEGIN TRY
    UPDATE dbo.Ventes SET Montant = 0 WHERE VenteID = 1;
    PRINT '✗ Test 3 : UPDATE sur Ventes OK (ne devrait pas fonctionner!)';
    ROLLBACK;  -- Annuler si ça a fonctionné
END TRY
BEGIN CATCH
    PRINT '✓ Test 3 : UPDATE sur Ventes bloqué comme prévu';
END CATCH;

REVERT;

-- Nettoyage
DROP USER TestAnalyste;

PRINT '=== Tests terminés ===';
```

### Exemple 4 : Procédure avec impersonation dynamique

```sql
-- Procédure qui change de contexte en fonction d'un paramètre
-- (Cas d'usage avancé : simulation de différents niveaux d'accès)

CREATE PROCEDURE dbo.SimulerAccesUtilisateur
    @NomUtilisateur NVARCHAR(128),
    @RequeteTest NVARCHAR(MAX)
AS
BEGIN
    SET NOCOUNT ON;

    -- Vérifier que l'utilisateur existe
    IF NOT EXISTS (SELECT 1 FROM sys.database_principals WHERE name = @NomUtilisateur)
    BEGIN
        PRINT 'Utilisateur introuvable : ' + @NomUtilisateur;
        RETURN;
    END

    PRINT '=== Simulation pour : ' + @NomUtilisateur + ' ===';
    PRINT 'Requête testée : ' + @RequeteTest;
    PRINT '';

    -- Afficher les rôles de l'utilisateur
    PRINT 'Rôles :';
    EXECUTE AS USER = @NomUtilisateur;

    SELECT r.name AS RoleName
    FROM sys.database_role_members rm
    JOIN sys.database_principals r ON rm.role_principal_id = r.principal_id
    JOIN sys.database_principals m ON rm.member_principal_id = m.principal_id
    WHERE m.name = @NomUtilisateur;

    -- Exécuter la requête test
    PRINT '';
    PRINT 'Résultat de la requête :';

    BEGIN TRY
        EXEC sp_executesql @RequeteTest;
        PRINT '✓ Requête exécutée avec succès';
    END TRY
    BEGIN CATCH
        PRINT '✗ Erreur : ' + ERROR_MESSAGE();
    END CATCH;

    REVERT;

    PRINT '=== Fin de la simulation ===';
END;
GO

-- Utilisation
EXEC dbo.SimulerAccesUtilisateur
    @NomUtilisateur = 'Analyste',
    @RequeteTest = 'SELECT COUNT(*) FROM dbo.Ventes';
```

## Permissions nécessaires pour utiliser EXECUTE AS

Pour utiliser `EXECUTE AS`, vous avez besoin de permissions spécifiques.

### IMPERSONATE : La permission clé

Pour vous "faire passer" pour un autre utilisateur, vous avez besoin de la permission **IMPERSONATE**.

```sql
-- Donner à Admin1 le droit de se faire passer pour Jean
GRANT IMPERSONATE ON USER::Jean TO Admin1;

-- Maintenant Admin1 peut faire :
EXECUTE AS USER = 'Jean';
-- ... opérations ...
REVERT;
```

### Au niveau serveur (pour EXECUTE AS LOGIN)

```sql
-- Donner le droit d'emprunter l'identité d'un login au niveau serveur
GRANT IMPERSONATE ON LOGIN::AppLogin TO AdminServeur;

-- AdminServeur peut maintenant faire :
EXECUTE AS LOGIN = 'AppLogin';
-- ... opérations ...
REVERT;
```

### Permission implicite pour les admins

Les membres de **db_owner** et **sysadmin** ont automatiquement le droit IMPERSONATE sur tous les users/logins.

```sql
-- Si vous êtes db_owner, vous pouvez vous faire passer pour n'importe qui
ALTER ROLE db_owner ADD MEMBER SuperUser;

-- SuperUser peut maintenant faire :
EXECUTE AS USER = 'N_importe_qui';
```

## Risques de sécurité et bonnes pratiques

### ⚠️ Risque 1 : Escalade de privilèges

Un utilisateur avec IMPERSONATE peut obtenir des permissions qu'il n'est pas censé avoir.

```sql
-- ❌ DANGEREUX : Donner IMPERSONATE sur un admin
GRANT IMPERSONATE ON USER::Admin TO UtilisateurNormal;

-- UtilisateurNormal peut maintenant devenir Admin !
EXECUTE AS USER = 'Admin';
-- Il peut faire N'IMPORTE QUOI !
```

**Bonne pratique** : Ne donnez IMPERSONATE qu'aux utilisateurs de confiance, et seulement sur des comptes avec permissions limitées.

### ⚠️ Risque 2 : Oubli de REVERT

```sql
-- Code problématique
EXECUTE AS USER = 'UtilisateurLimite';
SELECT * FROM dbo.TableOuverte;
-- Oubli de REVERT !

-- Tout le code qui suit s'exécute avec les permissions limitées
-- Ce qui peut causer des erreurs inattendues
```

**Bonne pratique** : Toujours utiliser TRY/CATCH et s'assurer que REVERT est appelé.

```sql
BEGIN TRY
    EXECUTE AS USER = 'UtilisateurLimite';
    -- Opérations
    REVERT;
END TRY
BEGIN CATCH
    -- Même en cas d'erreur, revenir au contexte original
    REVERT;
    THROW;
END CATCH;
```

### ⚠️ Risque 3 : Utilisation abusive dans les procédures

```sql
-- ❌ MAUVAIS : Donner trop de pouvoir
CREATE PROCEDURE dbo.FaireNimporteQuoi
WITH EXECUTE AS OWNER  -- Le propriétaire est dbo = tous les droits !
AS
BEGIN
    -- Accepte n'importe quelle commande SQL !
    DECLARE @SQL NVARCHAR(MAX) = ?;
    EXEC sp_executesql @SQL;  -- TRÈS DANGEREUX !
END;
```

**Bonne pratique** : Dans les procédures avec EXECUTE AS OWNER, n'exécutez que du code strictement validé et contrôlé.

```sql
-- ✅ BON : Logique strictement contrôlée
CREATE PROCEDURE dbo.SupprimerClientInactif
    @ClientID INT
WITH EXECUTE AS OWNER
AS
BEGIN
    -- Validation stricte
    IF @ClientID IS NULL OR @ClientID <= 0
        THROW 50001, 'ClientID invalide', 1;

    IF NOT EXISTS (
        SELECT 1 FROM dbo.Clients
        WHERE ClientID = @ClientID
        AND DerniereActivite < DATEADD(YEAR, -3, GETDATE())
    )
        THROW 50002, 'Client non éligible', 1;

    -- Action contrôlée (pas de SQL dynamique)
    DELETE FROM dbo.Clients WHERE ClientID = @ClientID;
END;
```

### ✅ Bonne pratique 1 : Principe du moindre privilège

```sql
-- ✅ BON : User dédié avec permissions minimales
CREATE USER AutomationUser WITHOUT LOGIN;
GRANT SELECT, INSERT ON dbo.LogTable TO AutomationUser;

-- Procédure qui s'exécute avec ce user limité
CREATE PROCEDURE dbo.EnregistrerLog
WITH EXECUTE AS 'AutomationUser'  -- Permissions minimales
AS
BEGIN
    INSERT INTO dbo.LogTable (Message) VALUES ('Log créé');
END;
```

### ✅ Bonne pratique 2 : Auditer l'utilisation de IMPERSONATE

```sql
-- Créer un trigger pour auditer les changements de contexte
-- (au niveau base de données avec Extended Events ou audit SQL Server)

-- Lister qui a IMPERSONATE
SELECT
    USER_NAME(grantee_principal_id) AS QuiPeut,
    USER_NAME(major_id) AS SurQui,
    permission_name,
    state_desc
FROM
    sys.database_permissions
WHERE
    permission_name = 'IMPERSONATE'
ORDER BY
    QuiPeut;
```

## Limitations et considérations

### 1. EXECUTE AS ne fonctionne pas entre bases de données

```sql
-- Dans la base DB1
EXECUTE AS USER = 'User1';

-- Tentative d'accès à DB2
USE DB2;  -- ❌ Le contexte est perdu !

-- Solution : Utiliser EXECUTE AS LOGIN (niveau serveur)
EXECUTE AS LOGIN = 'LoginUser';
USE DB2;  -- ✅ Fonctionne
```

### 2. Certaines opérations nécessitent le contexte original

Certaines commandes système nécessitent votre identité réelle, pas le contexte d'impersonation.

```sql
EXECUTE AS USER = 'Jean';

-- Ces commandes utilisent votre identité réelle, pas Jean
BACKUP DATABASE MaBase TO DISK = 'C:\backup.bak';
RESTORE DATABASE MaBase FROM DISK = 'C:\backup.bak';

REVERT;
```

### 3. Impact sur les connexions externes

Les connexions liées (linked servers) et certaines fonctionnalités avancées peuvent ne pas respecter EXECUTE AS.

## Diagnostic et dépannage

### Problème 1 : "Cannot execute as the user, because it does not exist"

```sql
-- ❌ Erreur
EXECUTE AS USER = 'UtilisateurInexistant';
```

**Solution** : Vérifier que le user existe dans la base de données actuelle.
```sql
-- Lister tous les users
SELECT name FROM sys.database_principals WHERE type IN ('S', 'U');
```

### Problème 2 : "The current security context cannot be reverted"

```sql
-- Contexte trop profondément imbriqué ou corrompu
```

**Solution** : Fermez la connexion et reconnectez-vous. Dans une procédure, assurez-vous que REVERT est toujours appelé.

### Problème 3 : "User does not have permission to impersonate"

```sql
-- ❌ Erreur : Pas de permission IMPERSONATE
EXECUTE AS USER = 'Admin';
```

**Solution** : Vérifier les permissions IMPERSONATE.
```sql
-- Qui peut impersonner qui ?
SELECT
    USER_NAME(grantor_principal_id) AS Accordeur,
    USER_NAME(grantee_principal_id) AS QuiPeut,
    USER_NAME(major_id) AS ImpersonnerQui,
    state_desc
FROM
    sys.database_permissions
WHERE
    permission_name = 'IMPERSONATE';
```

## Résumé comparatif des clauses

| Clause | Contexte d'exécution | Usage typique |
|--------|----------------------|---------------|
| **EXECUTE AS USER = 'X'** | User X dans la base actuelle | Tests de permissions |
| **EXECUTE AS LOGIN = 'X'** | Login X au niveau serveur | Tests multi-bases |
| **EXECUTE AS CALLER** | Appelant de la procédure | Comportement par défaut |
| **EXECUTE AS OWNER** | Propriétaire de la procédure | Élévation de privilèges contrôlée |
| **EXECUTE AS SELF** | Créateur de la procédure | Permissions fixes |
| **EXECUTE AS 'UserName'** | User spécifique nommé | Contexte spécialisé |

## Conclusion

**EXECUTE AS** est un outil puissant pour :
- ✅ **Tester les permissions** sans changer de session
- ✅ **Créer des procédures sécurisées** avec élévation contrôlée de privilèges
- ✅ **Implémenter le principe du moindre privilège**
- ✅ **Déboguer les problèmes de permissions**

**Points essentiels à retenir** :

1. 🎭 **EXECUTE AS** = Changer temporairement d'identité
2. ⏮️ **REVERT** = Revenir à l'identité originale (toujours utiliser !)
3. 🔐 **Nécessite IMPERSONATE** pour changer d'identité
4. ⚠️ **Risque de sécurité** si mal utilisé (escalade de privilèges)
5. 🏢 **Dans les procédures** : CALLER (défaut), OWNER, SELF, ou user spécifique
6. 🔗 **Ownership chaining** : Permissions "enchaînées" si même propriétaire

**Bonnes pratiques** :
- Toujours utiliser TRY/CATCH avec REVERT
- Donner IMPERSONATE avec parcimonie
- Documenter les procédures avec EXECUTE AS
- Auditer l'utilisation de IMPERSONATE
- Principe du moindre privilège dans les procédures

Avec EXECUTE AS, vous avez un contrôle très fin sur les permissions et la sécurité de votre base de données SQL Server !

---

**Points clés à retenir** :
- EXECUTE AS = Changer temporairement de contexte d'exécution
- REVERT = Revenir au contexte original (obligatoire !)
- Syntaxe : `EXECUTE AS USER = 'nom'` ou `EXECUTE AS LOGIN = 'nom'`
- Dans les procédures : CALLER, OWNER, SELF, ou user spécifique
- Nécessite la permission IMPERSONATE
- Ownership chaining = Permissions enchaînées si même propriétaire
- Risques : Escalade de privilèges, oubli de REVERT
- Utilité principale : Tests de permissions et procédures sécurisées
- Toujours documenter et auditer l'utilisation
