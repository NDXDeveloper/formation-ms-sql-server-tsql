# 7.2.2 Index filtrés (WHERE ...)

## Introduction

Dans les sections précédentes, nous avons vu :
- Les index simples sur une colonne (7.1)
- Les index composites sur plusieurs colonnes (7.2.1)

Mais tous ces index ont un point commun : ils indexent **toutes** les lignes de la table. Que se passe-t-il si vous ne vous intéressez qu'à un **sous-ensemble** des données ?

C'est là qu'interviennent les **index filtrés** (filtered indexes).

### Exemple motivant

Imaginons une table `Commandes` avec 10 millions de lignes :

```sql
SELECT * FROM Commandes;

-- Distribution des données :
-- 9 500 000 lignes avec Statut = 'Livrée'
-- 300 000 lignes avec Statut = 'Annulée'
-- 200 000 lignes avec Statut = 'En cours'  ← Celles qui nous intéressent
```

**Question** : Vos requêtes portent principalement sur les commandes "En cours". Pourquoi indexer **10 millions** de lignes alors que vous n'interrogez que **200 000** ?

**Réponse** : Les **index filtrés** permettent de créer un index sur seulement les lignes qui vous intéressent !

## Qu'est-ce qu'un Index Filtré ?

### Définition

Un **index filtré** est un index qui ne contient qu'un **sous-ensemble des lignes** d'une table, défini par une condition WHERE.

```sql
-- Syntaxe
CREATE INDEX nom_index
ON nom_table (colonnes)
WHERE condition;  -- ← La clause WHERE filtre les lignes indexées
```

**Caractéristiques** :
- ✅ Indexe seulement les lignes qui satisfont la condition WHERE
- ✅ Plus petit qu'un index complet
- ✅ Plus rapide à maintenir
- ✅ Peut être clustered ou non-clustered (généralement non-clustered)
- ✅ Peut être unique

### L'analogie du fichier d'archive

Imaginez un **bureau** avec des documents :

**Sans index filtré** : Vous classez **tous** les documents dans un classeur indexé
- 10 000 documents au total
- 9 500 documents archivés (anciens, rarement consultés)
- 500 documents actifs (consultés quotidiennement)
- Votre index contient les 10 000 documents
- Lourd, encombrant, mise à jour longue

**Avec index filtré** : Vous créez un classeur indexé **uniquement pour les documents actifs**
- Index ne contient que 500 documents
- Léger, rapide à consulter
- Rapide à mettre à jour (seulement 500 documents)
- Les documents archivés ne sont pas indexés (vous les cherchez rarement)

**C'est exactement ce que font les index filtrés !**

## Création d'Index Filtrés

### Syntaxe de base

```sql
CREATE INDEX nom_index
ON nom_table (colonnes)
WHERE condition_de_filtrage;
```

### Exemple 1 : Filtrer sur un statut

```sql
-- Table Commandes
CREATE TABLE Commandes (
    CommandeID INT IDENTITY(1,1) PRIMARY KEY,
    ClientID INT,
    DateCommande DATE,
    Statut NVARCHAR(20),  -- 'En cours', 'Livrée', 'Annulée'
    MontantTotal DECIMAL(10,2)
);

-- Index filtré : Uniquement les commandes "En cours"
CREATE INDEX IX_Commandes_EnCours_Client
ON Commandes (ClientID, DateCommande)
WHERE Statut = 'En cours';
```

**Visualisation** :

```
Table Commandes (10 millions de lignes)
┌───────────┬──────────┬──────────────┬──────────┬─────────┐
│CommandeID │ ClientID │ DateCommande │ Statut   │ Montant │
├───────────┼──────────┼──────────────┼──────────┼─────────┤
│ 1         │ 100      │ 2023-01-10   │ Livrée   │ 150.00  │ ← Non indexé
│ 2         │ 101      │ 2024-10-15   │ En cours │ 200.00  │ ← Indexé ✓
│ 3         │ 102      │ 2023-05-20   │ Annulée  │ 75.00   │ ← Non indexé
│ 4         │ 100      │ 2024-11-01   │ En cours │ 300.00  │ ← Indexé ✓
│ 5         │ 103      │ 2024-11-10   │ En cours │ 120.00  │ ← Indexé ✓
│ ...       │ ...      │ ...          │ ...      │ ...     │
└───────────┴──────────┴──────────────┴──────────┴─────────┘

Index IX_Commandes_EnCours_Client (200 000 lignes seulement)
┌──────────┬──────────────┬───────────┐
│ ClientID │ DateCommande │CommandeID │
├──────────┼──────────────┼───────────┤
│ 100      │ 2024-11-01   │ 4         │ ← Seulement "En cours"
│ 101      │ 2024-10-15   │ 2         │
│ 103      │ 2024-11-10   │ 5         │
│ ...      │ ...          │ ...       │
└──────────┴──────────────┴───────────┘

Taille : 2% de la table (200 000 / 10 000 000)
```

**Utilisation** :

```sql
-- ✅ Utilise l'index filtré (requête correspond au filtre)
SELECT * FROM Commandes
WHERE Statut = 'En cours' AND ClientID = 100;
-- Index Seek : Très rapide

-- ❌ N'utilise PAS l'index filtré (requête ne correspond pas au filtre)
SELECT * FROM Commandes
WHERE Statut = 'Livrée' AND ClientID = 100;
-- Table Scan ou autre index
```

### Exemple 2 : Filtrer sur les valeurs non-NULL

**Cas d'usage très courant** : Une colonne optionnelle avec beaucoup de NULL.

```sql
-- Table Clients
CREATE TABLE Clients (
    ClientID INT IDENTITY(1,1) PRIMARY KEY,
    Nom NVARCHAR(100),
    Email NVARCHAR(255),
    Telephone NVARCHAR(20)  -- Optionnel : 70% de NULL
);

-- Index filtré : Uniquement les clients avec téléphone
CREATE INDEX IX_Clients_Telephone
ON Clients (Telephone)
WHERE Telephone IS NOT NULL;
```

**Avantages** :
- ✅ Beaucoup plus petit (30% de la table au lieu de 100%)
- ✅ Permet plusieurs NULL (nous avons vu ce problème avec les index uniques)
- ✅ Performances optimisées pour les recherches réelles

**Utilisation** :

```sql
-- ✅ Utilise l'index filtré
SELECT * FROM Clients WHERE Telephone = '0612345678';
-- Index Seek rapide

-- ❌ N'utilise pas l'index filtré (recherche sur NULL)
SELECT * FROM Clients WHERE Telephone IS NULL;
-- Table Scan (normal, les NULL ne sont pas indexés)
```

### Exemple 3 : Index unique filtré

Nous avons vu ce cas dans la section 7.1.4, le voici en détail :

```sql
-- Table Utilisateurs
CREATE TABLE Utilisateurs (
    UtilisateurID INT IDENTITY(1,1) PRIMARY KEY,
    Username NVARCHAR(50),
    Email NVARCHAR(255),  -- Peut être NULL (inscription incomplète)
    EmailVerifie BIT DEFAULT 0
);

-- Index UNIQUE filtré : Email unique seulement si non-NULL
CREATE UNIQUE INDEX IX_Utilisateurs_Email
ON Utilisateurs (Email)
WHERE Email IS NOT NULL;
```

**Effet** :

```sql
-- ✅ Insertion réussie
INSERT INTO Utilisateurs (Username, Email)
VALUES ('user1', 'user1@email.com');

-- ✅ Insertion réussie (Email NULL)
INSERT INTO Utilisateurs (Username, Email)
VALUES ('user2', NULL);

-- ✅ Insertion réussie (encore un NULL, c'est autorisé !)
INSERT INTO Utilisateurs (Username, Email)
VALUES ('user3', NULL);

-- ✅ Insertion réussie (encore un NULL)
INSERT INTO Utilisateurs (Username, Email)
VALUES ('user4', NULL);

-- ❌ ERREUR : Violation (email déjà existant)
INSERT INTO Utilisateurs (Username, Email)
VALUES ('user5', 'user1@email.com');
```

**Bénéfice** : Vous pouvez avoir **plusieurs NULL** tout en garantissant l'unicité des valeurs non-NULL.

### Exemple 4 : Filtrer sur une plage de dates

```sql
-- Table Logs avec des millions de lignes anciennes
CREATE TABLE Logs (
    LogID INT IDENTITY(1,1) PRIMARY KEY,
    DateLog DATETIME2,
    TypeLog NVARCHAR(20),
    Message NVARCHAR(MAX)
);

-- Index filtré : Uniquement les logs des 30 derniers jours
CREATE INDEX IX_Logs_Recent_Type
ON Logs (TypeLog, DateLog)
WHERE DateLog >= DATEADD(day, -30, GETDATE());
```

**Problème** : La condition utilise `GETDATE()` qui change chaque jour !

**Solution** : Utilisez une date fixe ou ne filtrez pas sur une fonction :

```sql
-- ✅ MIEUX : Date fixe
CREATE INDEX IX_Logs_Recent_Type
ON Logs (TypeLog, DateLog)
WHERE DateLog >= '2024-01-01';

-- Ou sans filtre sur date, mais c'est moins optimisé
CREATE INDEX IX_Logs_Type_Date
ON Logs (TypeLog, DateLog);
```

**Note** : SQL Server a des restrictions sur les fonctions dans les index filtrés (voir section limitations).

## Pourquoi Utiliser des Index Filtrés ?

### Avantage 1 : 💾 Économie d'espace disque

Un index filtré est **beaucoup plus petit** qu'un index complet.

**Exemple** :

```
Table Produits : 1 million de produits
- 950 000 produits : Actif = 0 (archivés)
- 50 000 produits : Actif = 1 (en vente)

Index complet sur (CategorieID, Prix) :
- Indexe 1 000 000 lignes
- Taille : ~50 MB

Index filtré WHERE Actif = 1 :
- Indexe 50 000 lignes
- Taille : ~2.5 MB

Économie : 95% d'espace disque !
```

### Avantage 2 : ⚡ Performances améliorées

Un index plus petit est :
- Plus rapide à parcourir (moins de données à lire)
- Plus facilement conservé en mémoire (cache)
- Plus rapide pour SQL Server à analyser

**Benchmark** :

| Index | Taille | Temps de recherche | Mémoire |
|-------|--------|-------------------|---------|
| Complet (1M lignes) | 50 MB | 10 ms | Cache partiel |
| Filtré (50K lignes) | 2.5 MB | 1 ms | Tout en cache |

**Gain** : 10x plus rapide !

### Avantage 3 : 🔧 Maintenance réduite

Quand vous modifiez une ligne, SQL Server doit mettre à jour les index.

**Avec index complet** :
```sql
-- Changement de statut : Livrée → Archivée
UPDATE Commandes SET Statut = 'Archivée' WHERE CommandeID = 12345;

-- SQL Server doit :
-- 1. Mettre à jour la table
-- 2. Mettre à jour TOUS les index (même ceux qui n'indexent pas Statut)
```

**Avec index filtré sur "En cours"** :
```sql
-- Changement de statut : Livrée → Archivée
UPDATE Commandes SET Statut = 'Archivée' WHERE CommandeID = 12345;

-- SQL Server :
-- 1. Vérifie : Cette ligne est-elle dans l'index filtré ? Non (Statut = 'Livrée')
-- 2. L'index filtré n'est PAS modifié !
-- Gain de performance sur l'UPDATE
```

**Impact** :
- Moins d'écritures sur le disque
- UPDATE/DELETE plus rapides
- Moins de fragmentation d'index

### Avantage 4 : 🎯 Précision des statistiques

SQL Server maintient des **statistiques** sur les index pour optimiser les requêtes.

**Avec index complet** :
- Statistiques mélangent les données actives et archivées
- L'optimiseur peut faire de mauvais choix

**Avec index filtré** :
- Statistiques précises sur les données actives uniquement
- L'optimiseur fait de meilleurs choix

### Avantage 5 : 💰 Coût réduit

Plus petit = moins cher :
- Moins d'espace de stockage (SSD coûteux)
- Moins de mémoire RAM nécessaire
- Moins de CPU pour la maintenance
- Sauvegardes plus rapides

**Exemple en production** :
- Index complet : 100 GB
- Index filtré : 5 GB
- Économie : $500/mois en stockage cloud

## Cas d'Usage Typiques

### Cas 1 : Colonnes avec beaucoup de NULL

**Scénario** : Colonne optionnelle avec 80% de NULL.

```sql
-- Table Clients : 1 million de lignes
-- Colonne Telephone : 80% NULL, 20% avec valeur

-- ❌ SANS index filtré
CREATE INDEX IX_Clients_Telephone ON Clients (Telephone);
-- Indexe 1 000 000 lignes, dont 800 000 NULL (inutiles)

-- ✅ AVEC index filtré
CREATE INDEX IX_Clients_Telephone
ON Clients (Telephone)
WHERE Telephone IS NOT NULL;
-- Indexe seulement 200 000 lignes
-- 80% plus petit, 5x plus rapide
```

### Cas 2 : Données actives vs archivées

**Scénario** : Table avec données anciennes rarement consultées.

```sql
-- Table Commandes
-- 95% des requêtes portent sur les 6 derniers mois
-- 5% sur l'historique complet

-- Index filtré pour les requêtes fréquentes
CREATE INDEX IX_Commandes_Recentes_Client
ON Commandes (ClientID, DateCommande)
WHERE DateCommande >= '2024-06-01';  -- 6 derniers mois

-- Pour l'historique complet, Table Scan acceptable (rare)
```

### Cas 3 : Statuts spécifiques

**Scénario** : Vous interrogez souvent un statut particulier.

```sql
-- Table Tickets de support
-- 90% des requêtes : tickets "Ouverts" ou "En cours"
-- 10% des requêtes : tous les tickets

-- Index filtré pour les requêtes fréquentes
CREATE INDEX IX_Tickets_Actifs_DateCreation
ON Tickets (DateCreation DESC, Priorite)
WHERE Statut IN ('Ouvert', 'En cours');

-- Statistiques :
-- Table : 1 000 000 tickets
-- Statut 'Fermé' : 950 000 (95%)
-- Statut 'Ouvert' ou 'En cours' : 50 000 (5%)
-- Index filtré : 20x plus petit !
```

### Cas 4 : Index unique avec NULL

**Scénario** : Garantir l'unicité sauf pour NULL.

```sql
-- Table Employes
-- NumeroSecuriteSociale : obligatoire pour employés permanents
--                        : NULL pour stagiaires, consultants

CREATE UNIQUE INDEX IX_Employes_NumeroSecu
ON Employes (NumeroSecuriteSociale)
WHERE NumeroSecuriteSociale IS NOT NULL;

-- Résultat :
-- ✅ Plusieurs employés peuvent avoir NULL
-- ✅ Les numéros non-NULL sont uniques
```

### Cas 5 : Lignes "importantes" seulement

**Scénario** : Indexer seulement les lignes qui passent un seuil.

```sql
-- Table Transactions
-- 99% des transactions : < 100€
-- 1% des transactions : >= 100€ (nécessitent validation)

-- Index filtré pour les transactions importantes
CREATE INDEX IX_Transactions_Importantes
ON Transactions (ClientID, DateTransaction, Montant)
WHERE Montant >= 100;

-- Requête fréquente (validations à faire)
SELECT * FROM Transactions
WHERE Montant >= 100 AND Statut = 'En attente';
-- Utilise l'index filtré : très rapide
```

### Cas 6 : Type de client spécifique

**Scénario** : Plusieurs types de clients, mais vous interrogez surtout un type.

```sql
-- Table Clients
-- TypeClient : 'Particulier' (90%), 'Entreprise' (8%), 'Administration' (2%)
-- Requêtes : 80% sur 'Entreprise', 20% sur tous

-- Index filtré pour les entreprises
CREATE INDEX IX_Clients_Entreprise_Nom
ON Clients (Nom, Ville, DateInscription)
WHERE TypeClient = 'Entreprise';

-- Beaucoup plus petit et plus rapide que :
CREATE INDEX IX_Clients_Type_Nom
ON Clients (TypeClient, Nom, Ville, DateInscription);
```

## Conditions Autorisées dans WHERE

SQL Server impose des **restrictions** sur les expressions dans la clause WHERE d'un index filtré.

### ✅ Conditions autorisées

#### 1. Comparaisons simples

```sql
-- Égalité
WHERE Statut = 'Actif'
WHERE TypeClient = 'Entreprise'

-- Inégalité
WHERE Montant > 100
WHERE Quantite >= 10
WHERE Prix < 1000

-- Combinaisons avec AND
WHERE Statut = 'Actif' AND TypeClient = 'Entreprise'
WHERE Montant >= 100 AND Montant <= 10000
```

#### 2. IS NULL / IS NOT NULL

```sql
WHERE Email IS NOT NULL
WHERE Telephone IS NULL
WHERE DateFin IS NOT NULL
```

#### 3. IN avec liste de valeurs

```sql
WHERE Statut IN ('Actif', 'Suspendu')
WHERE TypeLog IN ('ERROR', 'FATAL', 'CRITICAL')
WHERE CodePays IN ('FR', 'BE', 'CH', 'LU')
```

#### 4. Plages avec `>=` et `<=` (et non `BETWEEN`)

Les bornes de plage s'expriment avec les inégalités. ⚠️ Le mot-clé `BETWEEN`, lui, n'est **pas** accepté dans le prédicat d'un index filtré (erreur de syntaxe) — il faut écrire l'équivalent :

```sql
-- ❌ Refusé : WHERE Prix BETWEEN 10 AND 100
-- ✅ Équivalent accepté :
WHERE Prix >= 10 AND Prix <= 100
WHERE DateCommande >= '2024-01-01' AND DateCommande < '2025-01-01'
```

#### 5. Combinaisons avec AND

```sql
WHERE Actif = 1 AND DateFin IS NULL
WHERE TypeClient = 'Entreprise' AND Chiffre >= 50000
WHERE Statut IN ('Ouvert', 'En cours') AND Priorite >= 3
```

### ❌ Conditions interdites

#### 1. OR (interdit)

```sql
-- ❌ ERREUR
WHERE Statut = 'Actif' OR Statut = 'Suspendu'

-- ✅ SOLUTION : Utilisez IN
WHERE Statut IN ('Actif', 'Suspendu')
```

#### 2. Fonctions sur les colonnes

```sql
-- ❌ ERREUR
WHERE UPPER(Nom) = 'DUPONT'
WHERE YEAR(DateCommande) = 2024
WHERE LEN(Nom) > 10

-- ✅ SOLUTION : colonne calculée PERSISTED, indexée SANS filtre
-- ⚠️ Une colonne calculée ne peut PAS apparaître dans le WHERE d'un index filtré :
--    on l'indexe donc avec un index NON filtré, et on place la condition dans la requête.
ALTER TABLE Clients ADD NomUpper AS UPPER(Nom) PERSISTED;
CREATE INDEX IX_Clients_NomUpper ON Clients (NomUpper);
-- Puis : SELECT ... FROM Clients WHERE NomUpper = 'DUPONT';  → utilise l'index
```

#### 3. Fonctions non déterministes

```sql
-- ❌ ERREUR : GETDATE() change chaque jour
WHERE DateCommande >= DATEADD(day, -30, GETDATE())
WHERE DateCreation >= GETDATE()

-- ✅ SOLUTION : Utilisez une date fixe
WHERE DateCommande >= '2024-01-01'

-- Ou un index sans filtre avec la fonction dans la requête
CREATE INDEX IX_Logs_Date ON Logs (DateLog);
-- Puis : SELECT * FROM Logs WHERE DateLog >= DATEADD(day, -30, GETDATE());
```

#### 4. Sous-requêtes

```sql
-- ❌ ERREUR
WHERE ClientID IN (SELECT ClientID FROM ClientsVIP)
WHERE Montant > (SELECT AVG(Montant) FROM Commandes)
```

#### 5. LIKE (interdit)

```sql
-- ❌ ERREUR : l'opérateur LIKE n'est pas autorisé dans le prédicat d'un index filtré
CREATE INDEX IX_x ON Clients (Email) WHERE Nom LIKE 'Dup%';
-- → "Incorrect syntax near 'LIKE'."
-- Un index filtré se définit sur des conditions discrètes (=, IN, IS [NOT] NULL,
-- inégalités), pas sur un motif texte.
```

### Tableau récapitulatif

| Expression | Autorisée | Exemple |
|------------|-----------|---------|
| `=`, `!=`, `<>`, `>`, `<`, `>=`, `<=` | ✅ Oui | `WHERE Statut = 'Actif'` |
| `IS NULL`, `IS NOT NULL` | ✅ Oui | `WHERE Email IS NOT NULL` |
| `IN (liste)` | ✅ Oui | `WHERE Type IN ('A', 'B')` |
| `AND` | ✅ Oui | `WHERE A = 1 AND B = 2` |
| `BETWEEN` | ❌ Non | Remplacez par `>= … AND <= …` |
| `LIKE` | ❌ Non | Non autorisé (filtrez sur `=`, `IN`, `IS [NOT] NULL`) |
| `OR` | ❌ Non | Utilisez `IN` à la place |
| Fonctions sur colonnes | ❌ Non | Utilisez colonnes calculées |
| `GETDATE()`, `NEWID()` | ❌ Non | Fonctions non déterministes |
| Sous-requêtes | ❌ Non | Non supportées |

## Comparaison : Index Complet vs Index Filtré

### Scénario concret : Table Commandes

```sql
-- Table : 10 millions de commandes
-- Distribution :
--   9 500 000 'Livrée' (95%)
--     300 000 'Annulée' (3%)
--     200 000 'En cours' (2%)

-- Requête fréquente (80% du trafic)
SELECT * FROM Commandes
WHERE Statut = 'En cours' AND ClientID = 12345;
```

### Option 1 : Index complet

```sql
CREATE INDEX IX_Commandes_Statut_Client
ON Commandes (Statut, ClientID);
```

**Caractéristiques** :
- Taille : ~500 MB
- Indexe 10 000 000 lignes
- Mise à jour sur CHAQUE modification
- Performance : Bonne

### Option 2 : Index filtré

```sql
CREATE INDEX IX_Commandes_EnCours_Client
ON Commandes (ClientID, DateCommande)
WHERE Statut = 'En cours';
```

**Caractéristiques** :
- Taille : ~10 MB (50x plus petit !)
- Indexe 200 000 lignes seulement
- Mise à jour uniquement si Statut = 'En cours'
- Performance : Excellente (pour les commandes en cours)

### Tableau comparatif

| Aspect | Index Complet | Index Filtré |
|--------|---------------|--------------|
| **Taille** | 500 MB | 10 MB |
| **Lignes indexées** | 10 000 000 | 200 000 |
| **Mémoire utilisée** | Élevée | Faible |
| **Vitesse de recherche** | Bonne | Excellente |
| **Coût UPDATE/DELETE** | Élevé (toujours) | Faible (si hors filtre) |
| **Coût INSERT** | Élevé | Faible (si hors filtre) |
| **Polyvalence** | Toutes les requêtes | Requêtes matchant le filtre |
| **Statistiques** | Globales | Ciblées |

### Quand choisir quoi ?

**Choisissez un index filtré si** :
- ✅ Vous interrogez souvent un sous-ensemble spécifique (< 20% des lignes)
- ✅ La colonne filtrée a peu de valeurs distinctes (statut, type, booléen)
- ✅ Vous voulez économiser de l'espace
- ✅ La table a beaucoup d'UPDATE/DELETE

**Choisissez un index complet si** :
- ✅ Vous interrogez toutes les valeurs de manière égale
- ✅ Vos requêtes sont très variées (pas de pattern dominant)
- ✅ La colonne filtrée a beaucoup de valeurs distinctes
- ✅ Simplicité > Optimisation

## Limitations et Pièges

### Limitation 1 : La requête doit correspondre au filtre

**Point crucial** : SQL Server n'utilise l'index filtré que si la requête **inclut le filtre** de l'index.

```sql
-- Index filtré
CREATE INDEX IX_Produits_Actifs
ON Produits (Nom, Prix)
WHERE Actif = 1;

-- ✅ Utilise l'index filtré
SELECT * FROM Produits WHERE Actif = 1 AND Nom LIKE 'Laptop%';

-- ❌ N'utilise PAS l'index filtré
SELECT * FROM Produits WHERE Nom LIKE 'Laptop%';
-- Même si les résultats sont des produits actifs, SQL Server ne le sait pas
```

**Solution** : Ajoutez toujours la condition du filtre dans vos requêtes.

### Limitation 2 : Pas d'expression NI de colonne calculée dans le filtre

Le prédicat d'un index filtré n'accepte que des comparaisons simples sur des **colonnes de base**. Il ne peut contenir **ni une expression** (`Nom + ' ' + Prenom`), **ni une colonne calculée** — même persistée. C'est une restriction documentée de SQL Server (*« the filter predicate […] can't reference a computed column »*).

```sql
-- ❌ ERREUR : expression dans le filtre
CREATE INDEX IX_Clients_NomComplet
ON Clients (Email)
WHERE Nom + ' ' + Prenom = 'Jean Dupont';

-- ❌ ERREUR AUSSI : une colonne calculée est interdite dans le prédicat filtré
ALTER TABLE Clients ADD NomComplet AS Nom + ' ' + Prenom PERSISTED;
CREATE INDEX IX_Clients_NomComplet
ON Clients (Email)
WHERE NomComplet = 'Jean Dupont';   -- refusé : NomComplet est une colonne calculée
```

**Solution** : indexer la colonne calculée persistée avec un index **non filtré**, puis placer la condition dans la requête (elle utilisera l'index) :

```sql
ALTER TABLE Clients ADD NomComplet AS Nom + ' ' + Prenom PERSISTED;
CREATE INDEX IX_Clients_NomComplet ON Clients (NomComplet);

-- La requête tire alors parti de l'index :
SELECT * FROM Clients WHERE NomComplet = 'Jean Dupont';
```

### Limitation 3 : Pas de OR

```sql
-- ❌ ERREUR
CREATE INDEX IX_Commandes_ActifOuEnCours
ON Commandes (ClientID)
WHERE Statut = 'Actif' OR Statut = 'En cours';

-- ✅ SOLUTION : Utilisez IN
CREATE INDEX IX_Commandes_ActifEnCours
ON Commandes (ClientID)
WHERE Statut IN ('Actif', 'En cours');
```

### Limitation 4 : Maintenance manuelle parfois nécessaire

Si votre filtre utilise une date fixe :

```sql
CREATE INDEX IX_Logs_2024
ON Logs (TypeLog, Message)
WHERE DateLog >= '2024-01-01';
```

**Problème** : En 2025, vous devrez créer un nouvel index pour 2025.

**Solutions** :
1. Index sans filtre (accepter une taille plus grande)
2. Partitionnement de table (avancé)
3. Recréer l'index périodiquement (maintenance)

### Limitation 5 : Ne convient pas aux tables petites

Si votre table a 1 000 lignes, un index filtré n'apporte pas grand-chose.

**Règle** : Index filtrés utiles si :
- Table > 100 000 lignes
- Filtre réduit à < 20% des lignes

## Stratégies d'Utilisation

### Stratégie 1 : Combiner index filtré et index complet

```sql
-- Index filtré pour les requêtes fréquentes (80%)
CREATE INDEX IX_Commandes_EnCours_Client
ON Commandes (ClientID, DateCommande)
WHERE Statut = 'En cours';

-- Index complet pour les autres cas (20%)
CREATE INDEX IX_Commandes_Statut_Client
ON Commandes (Statut, ClientID, DateCommande);
```

**Avantage** : Optimisez les deux types de requêtes.

### Stratégie 2 : Plusieurs index filtrés

```sql
-- Un index filtré par statut important
CREATE INDEX IX_Tickets_Ouverts
ON Tickets (Priorite, DateCreation)
WHERE Statut = 'Ouvert';

CREATE INDEX IX_Tickets_EnCours
ON Tickets (TechnicienID, DateModification)
WHERE Statut = 'En cours';

CREATE INDEX IX_Tickets_Urgent
ON Tickets (ClientID, DateCreation)
WHERE Priorite = 'Urgent';
```

**Avantage** : Optimisation ciblée pour chaque cas d'usage.

**Attention** : Coût de maintenance plus élevé.

### Stratégie 3 : Index filtré sur données récentes

```sql
-- Table volumineuse avec historique
-- 99% des requêtes sur les 3 derniers mois

-- Index filtré pour les données récentes
CREATE INDEX IX_Transactions_Recentes
ON Transactions (ClientID, DateTransaction, Montant)
WHERE DateTransaction >= '2024-09-01';

-- Recréez l'index tous les trimestres pour avancer la date
```

**Avantage** : Performances optimales sur les données chaudes.

### Stratégie 4 : Index unique filtré pour gérer NULL

```sql
-- Garantir l'unicité en ignorant les NULL
CREATE UNIQUE INDEX IX_Employes_Badge
ON Employes (NumeroBadge)
WHERE NumeroBadge IS NOT NULL;

-- Résultat :
-- - Plusieurs NULL autorisés
-- - Valeurs non-NULL uniques
```

#### 1. Identifiez les requêtes sur sous-ensembles

```sql
-- Analysez vos requêtes fréquentes

```

#### 2. Utilisez des filtres simples

```sql
WHERE Statut IN ('Ouvert', 'En cours')
WHERE Email IS NOT NULL

-- ❌ ÉVITER : Trop complexe
WHERE (Actif = 1 AND Type = 'A') OR (Actif = 0 AND Type = 'B')
```

#### 3. Documentez le filtre

```sql
-- ✅ BON : Commentaire expliquant l'intention
-- Index filtré pour les commandes actives (2% de la table)
-- 90% des requêtes portent sur ces données
CREATE INDEX IX_Commandes_Actives_Client
ON Commandes (ClientID, DateCommande)
```

#### 4. Surveillez l'utilisation

```sql
-- Vérifiez que l'index est utilisé
SELECT
    i.name,
    s.user_seeks,
    s.user_scans,
    s.user_updates
FROM sys.dm_db_index_usage_stats s
INNER JOIN sys.indexes i ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE s.database_id = DB_ID() AND OBJECT_NAME(s.object_id) = 'Commandes';
```

#### 5. Incluez le filtre dans vos requêtes

```sql
-- Index filtré
CREATE INDEX IX_Produits_Actifs ON Produits (Nom) WHERE Actif = 1;

-- ✅ BON : Inclut le filtre
SELECT * FROM Produits WHERE Actif = 1 AND Nom LIKE 'Laptop%';

-- ❌ MAUVAIS : Oubli du filtre
SELECT * FROM Produits WHERE Nom LIKE 'Laptop%';
```

### ❌ À ÉVITER

#### 1. N'utilisez pas de filtres avec fonctions non déterministes

```sql
-- ❌ ERREUR

WHERE DateLog >= DATEADD(day, -30, GETDATE());
```

#### 2. Ne filtrez pas sur des colonnes très sélectives

```sql
-- ❌ INUTILE : ID est unique, le filtre ne réduit rien
CREATE INDEX IX_Clients_ID ON Clients (Nom)
WHERE ClientID > 1000;
```

#### 3. N'abusez pas des index filtrés

```sql
-- ❌ TROP : 10 index filtrés différents
-- Maintenance coûteuse, gains marginaux
```

#### 4. Ne créez pas d'index filtré sur petites tables

```sql
-- Table de 500 lignes
-- ❌ INUTILE : Index filtré n'apporte rien
```

## Exemple Complet : Système de Ticketing

**Contexte** : Application de support technique avec 5 millions de tickets.

### Données

```sql
CREATE TABLE Tickets (
    TicketID INT IDENTITY(1,1) PRIMARY KEY,
    ClientID INT NOT NULL,
    TechnicienID INT,  -- NULL si non assigné
    Statut NVARCHAR(20) NOT NULL,  -- 'Ouvert', 'En cours', 'Résolu', 'Fermé'
    Priorite NVARCHAR(20) NOT NULL,  -- 'Basse', 'Normale', 'Haute', 'Urgente'
    DateCreation DATETIME2 NOT NULL,
    DateResolution DATETIME2,
    Sujet NVARCHAR(200) NOT NULL
);

-- Distribution :
-- 4 700 000 tickets Fermés (94%)
--   200 000 tickets Résolus (4%)
--    80 000 tickets En cours (1.6%)
--    20 000 tickets Ouverts (0.4%)
```

### Requêtes fréquentes

```sql
-- Requête 1 (50%) : Tickets ouverts à assigner
SELECT * FROM Tickets
WHERE Statut = 'Ouvert'
ORDER BY Priorite DESC, DateCreation;

-- Requête 2 (30%) : Tickets d'un technicien
SELECT * FROM Tickets
WHERE TechnicienID = 123 AND Statut IN ('Ouvert', 'En cours');

-- Requête 3 (15%) : Tickets urgents non résolus
SELECT * FROM Tickets
WHERE Priorite = 'Urgente' AND Statut IN ('Ouvert', 'En cours');

-- Requête 4 (5%) : Recherche dans l'historique complet
SELECT * FROM Tickets
WHERE ClientID = 456;
```

### Stratégie d'indexation

```sql
-- Index filtré 1 : Tickets actifs (80% des requêtes)
CREATE INDEX IX_Tickets_Actifs_Priorite
ON Tickets (Priorite DESC, DateCreation, TechnicienID)
WHERE Statut IN ('Ouvert', 'En cours');
-- Taille : 5 MB (au lieu de 250 MB pour index complet)
-- Couvre requêtes 1, 2, 3

-- Index filtré 2 : Tickets non assignés
CREATE INDEX IX_Tickets_NonAssignes
ON Tickets (Priorite DESC, DateCreation)
WHERE Statut = 'Ouvert' AND TechnicienID IS NULL;
-- Taille : 1 MB
-- Optimise l'écran d'assignation

-- Index 3 : Pour recherches client (historique complet)
CREATE INDEX IX_Tickets_Client
ON Tickets (ClientID, DateCreation DESC);
-- Index normal (pas filtré) pour requête 4
```

### Résultats

| Aspect | Avant (index complets) | Après (index filtrés) |
|--------|------------------------|----------------------|
| **Espace total** | 800 MB | 120 MB |
| **Économie** | - | 85% |
| **Temps requête 1** | 50 ms | 5 ms |
| **Temps requête 2** | 30 ms | 3 ms |
| **Temps requête 3** | 40 ms | 4 ms |
| **Temps UPDATE** | 20 ms | 8 ms |

**Gains** :
- ✅ Performances 10x meilleures
- ✅ 85% d'économie d'espace
- ✅ UPDATE 2.5x plus rapides

## Résumé et Points Clés

### 🎯 Concepts essentiels

1. **Index filtré = Index sur un sous-ensemble de lignes**
   - Défini par une clause WHERE
   - Ne contient que les lignes satisfaisant la condition

2. **Avantages multiples**
   - 💾 Beaucoup plus petit (économie d'espace)
   - ⚡ Plus rapide (moins de données à parcourir)
   - 🔧 Maintenance réduite (mises à jour seulement si dans le filtre)
   - 🎯 Statistiques plus précises

3. **Cas d'usage principaux**
   - Colonnes avec beaucoup de NULL
   - Données actives vs archivées (95%/5%)
   - Statuts spécifiques (Ouvert, En cours)
   - Index unique avec NULL multiples

4. **Restrictions importantes**
   - Pas de OR (utilisez IN)
   - Pas de fonctions sur colonnes
   - Pas de fonctions non déterministes (GETDATE)
   - La requête doit inclure le filtre

5. **Quand utiliser**
   - Table > 100 000 lignes
   - Sous-ensemble < 20% de la table
   - Requêtes fréquentes sur ce sous-ensemble

### ✅ Checklist de décision

Créez un index filtré si :

- [ ] Vos requêtes portent principalement sur un sous-ensemble (< 20%)
- [ ] Ce sous-ensemble est identifiable par une condition simple
- [ ] La table est volumineuse (> 100 000 lignes)
- [ ] Vous voulez économiser de l'espace disque
- [ ] Vous voulez améliorer les performances UPDATE/DELETE

### 📋 Syntaxes à retenir

```sql
-- Index filtré basique
CREATE INDEX IX_Table_Colonne
ON Table (Colonne)
WHERE Condition = 'Valeur';

-- Index filtré avec NULL
CREATE INDEX IX_Table_Colonne
ON Table (Colonne)
WHERE Colonne IS NOT NULL;

-- Index unique filtré
CREATE UNIQUE INDEX IX_Table_Colonne
ON Table (Colonne)
WHERE Colonne IS NOT NULL;

-- Index filtré composite
CREATE INDEX IX_Table_Multi
ON Table (Col1, Col2, Col3)
WHERE Statut IN ('Actif', 'Suspendu');
```

## Conclusion

Les **index filtrés** sont un outil puissant mais souvent sous-utilisé. Ils permettent d'optimiser drastiquement les performances tout en réduisant les coûts de stockage et de maintenance.

**La règle d'or** :
> Si 80% de vos requêtes portent sur 20% de vos données, utilisez un index filtré sur ces 20%.

Les index filtrés brillent particulièrement dans les scénarios où vous avez :
- Des données actives vs archivées
- Des colonnes optionnelles (beaucoup de NULL)
- Des statuts spécifiques fréquemment interrogés
- Des volumes importants avec patterns d'accès bien définis
