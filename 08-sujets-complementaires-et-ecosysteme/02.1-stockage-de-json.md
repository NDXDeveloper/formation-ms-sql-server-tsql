# 8.2.1 Stockage de JSON (dans NVARCHAR)

## Introduction

**JSON** (JavaScript Object Notation) est devenu le format de données le plus populaire pour les échanges d'informations sur le web, notamment avec les APIs REST. Si vous avez déjà travaillé avec des applications web modernes, des APIs ou des services cloud, vous avez probablement rencontré du JSON.

SQL Server, à partir de la version **2016**, offre un support natif pour travailler avec des données JSON. Cependant, contrairement au XML qui dispose de son propre type de données (`XML`), JSON est stocké sous forme de **texte dans des colonnes NVARCHAR**.

Dans cette section, nous allons comprendre comment et pourquoi stocker du JSON dans SQL Server.

## Qu'est-ce que le JSON ?

### Définition

**JSON** (JavaScript Object Notation) est un format léger d'échange de données. Il est :
- **Facile à lire** pour les humains
- **Facile à parser** pour les machines
- **Indépendant du langage** (bien qu'issu de JavaScript)
- **Compact** (moins verbeux que XML)

### Structure de base du JSON

Le JSON utilise deux structures principales :

#### 1. Les objets (paires clé-valeur)

Un **objet** est délimité par des accolades `{}` et contient des paires clé-valeur :

```json
{
    "nom": "Dupont",
    "prenom": "Jean",
    "age": 30
}
```

**Caractéristiques** :
- Les **clés** sont toujours entre guillemets doubles
- Les clés et valeurs sont séparées par `:`
- Les paires sont séparées par des virgules `,`

#### 2. Les tableaux (listes de valeurs)

Un **tableau** est délimité par des crochets `[]` et contient une liste de valeurs :

```json
["Paris", "Lyon", "Marseille"]
```

Ou un tableau d'objets :

```json
[
    {"nom": "Dupont", "age": 30},
    {"nom": "Martin", "age": 25}
]
```

### Types de données JSON

JSON supporte plusieurs types de valeurs :

| Type | Exemple | Description |
|------|---------|-------------|
| **Chaîne** | `"Bonjour"` | Texte entre guillemets doubles |
| **Nombre** | `42`, `3.14`, `-10` | Entiers ou décimaux (pas de guillemets) |
| **Booléen** | `true`, `false` | Valeurs logiques (minuscules, pas de guillemets) |
| **null** | `null` | Absence de valeur (pas de guillemets) |
| **Objet** | `{"clé": "valeur"}` | Collection de paires clé-valeur |
| **Tableau** | `[1, 2, 3]` | Liste ordonnée de valeurs |

### Exemple complet

Voici un exemple JSON représentant une commande :

```json
{
    "commandeID": 12345,
    "date": "2024-11-18",
    "client": {
        "nom": "Dupont",
        "email": "dupont@example.com",
        "adresse": {
            "rue": "10 rue de la Paix",
            "ville": "Paris",
            "codePostal": "75001"
        }
    },
    "articles": [
        {
            "code": "A001",
            "nom": "Ordinateur portable",
            "quantite": 2,
            "prix": 899.99
        },
        {
            "code": "A002",
            "nom": "Souris sans fil",
            "quantite": 3,
            "prix": 29.99
        }
    ],
    "total": 1889.95,
    "livraison": {
        "methode": "Standard",
        "frais": 0,
        "gratuite": true
    }
}
```

**Observations** :
- Structure hiérarchique (imbrication d'objets)
- Tableau d'articles
- Différents types de données (nombres, chaînes, booléens)
- Facilement compréhensible

## JSON vs XML : Rappel

Nous avons vu le XML dans la section 8.1. Voici une comparaison visuelle :

**Même données en XML** :
```xml
<Personne>
    <Nom>Dupont</Nom>
    <Prenom>Jean</Prenom>
    <Age>30</Age>
    <Actif>true</Actif>
</Personne>
```

**Même données en JSON** :
```json
{
    "nom": "Dupont",
    "prenom": "Jean",
    "age": 30,
    "actif": true
}
```

**Différences clés** :

| Aspect | XML | JSON |
|--------|-----|------|
| **Verbosité** | Plus verbeux (balises fermantes) | Plus compact |
| **Types** | Tout est texte | Types natifs (nombre, booléen) |
| **Parsing** | Plus lourd | Plus rapide |
| **Commentaires** | `<!-- commentaire -->` | Non supportés officiellement |
| **Attributs** | Oui (`<elem attr="val">`) | Non (seulement clé-valeur) |
| **Usage web moderne** | Moins courant (legacy) | Standard de facto pour APIs |

## Pourquoi SQL Server stocke JSON dans NVARCHAR ?

### Pas de type JSON natif

**Important** : Historiquement (de SQL Server 2016 à 2022) et contrairement au type de données `XML`, SQL Server **n'avait pas de type `JSON` dédié**.

Le JSON est alors stocké comme du **texte simple** dans des colonnes de type `NVARCHAR` (ou `VARCHAR`), manipulé par des fonctions spécialisées.

> 🆕 **Évolution récente** : un véritable type de données **`json`** (stockage binaire optimisé, lectures et mises à jour ciblées plus rapides) a depuis été introduit — en **disponibilité générale (GA) sur Azure SQL Database / Managed Instance**, et **en préversion dans SQL Server 2025**. Si vous ciblez SQL Server 2016 à 2022 (le cas le plus fréquent on-premises), l'approche **`NVARCHAR` présentée dans cette section reste la référence** — et toutes les fonctions JSON décrites par la suite (`ISJSON`, `JSON_VALUE`, `OPENJSON`, `FOR JSON`…) s'appliquent dans les deux cas.

### Raisons de ce choix

Microsoft a fait ce choix pour plusieurs raisons :

1. **Flexibilité** : JSON est intrinsèquement flexible et peut évoluer facilement
2. **Compatibilité** : Facilite l'échange avec d'autres systèmes
3. **Performance** : Le parsing JSON en texte est très rapide
4. **Standard** : JSON est déjà un format texte standard
5. **Simplicité** : Pas besoin d'un type de données complexe comme pour XML

### NVARCHAR vs VARCHAR

**Recommandation** : Utilisez **NVARCHAR** pour stocker du JSON.

**Pourquoi NVARCHAR ?**
- Supporte **Unicode** (tous les caractères internationaux)
- Les fonctions JSON de SQL Server requièrent NVARCHAR
- Évite les problèmes d'encodage

**Taille recommandée** :
- `NVARCHAR(MAX)` : Pour du JSON de taille variable ou potentiellement large
- `NVARCHAR(4000)` : Si vous êtes certain que le JSON ne dépassera pas cette taille

```sql
-- Recommandé pour la plupart des cas
CREATE TABLE Documents (
    DocID INT PRIMARY KEY,
    ContenuJSON NVARCHAR(MAX)
);

-- Si vous avez des contraintes de taille connues
CREATE TABLE Parametres (
    ParamID INT PRIMARY KEY,
    ConfigJSON NVARCHAR(4000)
);
```

## Création de tables avec colonnes JSON

### Syntaxe de base

Créer une table avec une colonne JSON est exactement comme créer n'importe quelle autre colonne :

```sql
CREATE TABLE Produits (
    ProduitID INT PRIMARY KEY IDENTITY(1,1),
    Nom NVARCHAR(100) NOT NULL,
    Prix DECIMAL(10,2) NOT NULL,
    DetailsJSON NVARCHAR(MAX)  -- Colonne pour stocker JSON
);
```

**Note** : Il n'y a aucune syntaxe spéciale. C'est simplement une colonne NVARCHAR.

### Exemple avec plusieurs colonnes JSON

Une table peut avoir plusieurs colonnes JSON si nécessaire :

```sql
CREATE TABLE Commandes (
    CommandeID INT PRIMARY KEY IDENTITY(1,1),
    DateCommande DATETIME DEFAULT GETDATE(),
    ClientID INT NOT NULL,

    -- Données relationnelles classiques
    Statut NVARCHAR(50) NOT NULL,

    -- Données JSON pour flexibilité
    ArticlesJSON NVARCHAR(MAX),      -- Liste des articles
    AdresseLivraisonJSON NVARCHAR(MAX), -- Adresse complète
    MetadonneesJSON NVARCHAR(MAX)    -- Informations supplémentaires
);
```

### Contrainte CHECK pour valider le JSON

Bien que SQL Server ne dispose pas d'un type JSON natif, vous pouvez ajouter une **contrainte CHECK** pour garantir que le contenu est du JSON valide :

```sql
CREATE TABLE Documents (
    DocID INT PRIMARY KEY IDENTITY(1,1),
    ContenuJSON NVARCHAR(MAX),

    -- Contrainte pour valider que c'est du JSON valide
    CONSTRAINT CK_ValidJSON CHECK (ISJSON(ContenuJSON) = 1)
);
```

**Explication** :
- `ISJSON()` est une fonction qui retourne `1` si le texte est du JSON valide, `0` sinon
- La contrainte CHECK rejette toute insertion/mise à jour avec du JSON invalide

**Exemple qui sera rejeté** :

```sql
-- Ceci provoquera une ERREUR car le JSON est invalide
INSERT INTO Documents (ContenuJSON)
VALUES ('{nom: "test"}');  -- Erreur : les clés doivent être entre guillemets
```

**Exemple qui sera accepté** :

```sql
-- Ceci sera accepté car le JSON est valide
INSERT INTO Documents (ContenuJSON)
VALUES ('{"nom": "test"}');  -- OK : JSON valide
```

## Insertion de données JSON

### Méthode 1 : Insertion directe de chaînes JSON

La méthode la plus simple est d'insérer le JSON comme une chaîne de caractères :

```sql
INSERT INTO Produits (Nom, Prix, DetailsJSON)
VALUES (
    'Ordinateur portable',
    899.99,
    '{"marque": "Dell", "processeur": "Intel i7", "ram": "16GB", "stockage": "512GB SSD"}'
);
```

### Méthode 2 : JSON multiligne avec des apostrophes doubles

Pour du JSON complexe, utilisez des guillemets simples autour et doublez les apostrophes internes :

```sql
INSERT INTO Produits (Nom, Prix, DetailsJSON)
VALUES (
    'Smartphone',
    599.99,
    '{
        "marque": "Samsung",
        "modele": "Galaxy S23",
        "caracteristiques": {
            "ecran": "6.1 pouces",
            "camera": "50MP",
            "batterie": "3900mAh"
        },
        "couleurs": ["Noir", "Blanc", "Vert"]
    }'
);
```

**Note** : Le JSON peut s'étendre sur plusieurs lignes pour plus de lisibilité.

### Méthode 3 : Utiliser des variables

Pour des insertions depuis une application, utilisez des variables :

```sql
DECLARE @jsonData NVARCHAR(MAX) = N'{
    "marque": "Apple",
    "modele": "iPhone 15",
    "prix": 999,
    "disponible": true
}';

INSERT INTO Produits (Nom, Prix, DetailsJSON)
VALUES ('iPhone 15', 999.00, @jsonData);
```

**Important** : Notez le préfixe `N` devant la chaîne pour indiquer qu'il s'agit d'Unicode (NVARCHAR).

### Méthode 4 : JSON depuis une application externe

Dans une application (C#, Python, JavaScript, etc.), vous générez le JSON et l'envoyez comme paramètre :

**Exemple conceptuel en C#** :
```csharp
var produit = new {
    marque = "Sony",
    modele = "PlayStation 5",
    stockage = "825GB"
};

string json = JsonSerializer.Serialize(produit);
// json = {"marque":"Sony","modele":"PlayStation 5","stockage":"825GB"}

// Puis insérer dans SQL Server via une requête paramétrée
```

## Lecture de données JSON

### Sélection simple

Lire une colonne JSON est aussi simple que de lire n'importe quelle autre colonne :

```sql
SELECT ProduitID, Nom, Prix, DetailsJSON
FROM Produits;
```

**Résultat** :
```
ProduitID | Nom                  | Prix   | DetailsJSON
----------|----------------------|--------|--------------------------------------------------
1         | Ordinateur portable  | 899.99 | {"marque": "Dell", "processeur": "Intel i7"...}
2         | Smartphone           | 599.99 | {"marque": "Samsung", "modele": "Galaxy S23"...}
```

Le JSON est retourné **comme du texte**. Pour extraire des valeurs spécifiques, vous utiliserez les fonctions JSON (vues dans la section 8.2.2).

## Mise à jour de données JSON

### Remplacement complet

Pour remplacer entièrement le contenu JSON :

```sql
UPDATE Produits
SET DetailsJSON = '{"marque": "HP", "processeur": "AMD Ryzen 7", "ram": "32GB"}'
WHERE ProduitID = 1;
```

### Mise à jour partielle avec JSON_MODIFY

Pour modifier seulement une partie du JSON sans tout réécrire, utilisez `JSON_MODIFY()` (vue en détail dans la section 8.2.2) :

```sql
-- Exemple de mise à jour partielle (aperçu)
UPDATE Produits
SET DetailsJSON = JSON_MODIFY(DetailsJSON, '$.ram', '32GB')
WHERE ProduitID = 1;
```

## Cas d'usage du stockage JSON

### 1. Données semi-structurées

Stockez des données dont la structure peut varier d'un enregistrement à l'autre :

```sql
-- Table pour des événements système variés
CREATE TABLE Logs (
    LogID INT PRIMARY KEY IDENTITY(1,1),
    TypeEvenement NVARCHAR(50),
    Horodatage DATETIME DEFAULT GETDATE(),
    DonneesJSON NVARCHAR(MAX)  -- Structure variable selon le type
);

-- Différents types d'événements avec des structures différentes
INSERT INTO Logs (TypeEvenement, DonneesJSON) VALUES
('Connexion', '{"utilisateur": "admin", "ip": "192.168.1.10", "succes": true}'),
('Erreur', '{"code": 500, "message": "Erreur serveur", "trace": "...", "url": "/api/produits"}'),
('Achat', '{"montant": 150.50, "articles": 3, "paiement": "carte", "promo": "NOEL2024"}');
```

### 2. Intégration avec des APIs externes

Stocker les réponses d'APIs directement :

```sql
CREATE TABLE ReponsesAPI (
    ReponseID INT PRIMARY KEY IDENTITY(1,1),
    API NVARCHAR(100),
    DateAppel DATETIME DEFAULT GETDATE(),
    ReponseJSON NVARCHAR(MAX)
);

-- Stocker une réponse d'API météo
INSERT INTO ReponsesAPI (API, ReponseJSON) VALUES
('OpenWeatherMap', '{
    "temperature": 22.5,
    "humidite": 65,
    "conditions": "Nuageux",
    "vent": {"vitesse": 15, "direction": "NO"}
}');
```

### 3. Préférences utilisateurs et configurations

Stocker des configurations flexibles :

```sql
CREATE TABLE Utilisateurs (
    UtilisateurID INT PRIMARY KEY IDENTITY(1,1),
    Email NVARCHAR(100) NOT NULL,
    DateCreation DATETIME DEFAULT GETDATE(),
    PreferencesJSON NVARCHAR(MAX)
);

INSERT INTO Utilisateurs (Email, PreferencesJSON) VALUES
('jean@example.com', '{
    "theme": "sombre",
    "langue": "fr",
    "notifications": {
        "email": true,
        "push": false,
        "frequence": "quotidien"
    },
    "affichage": {
        "lignesParPage": 25,
        "compactMode": true
    }
}');
```

### 4. Historique et audit

Capturer l'état complet d'un objet à un moment donné :

```sql
CREATE TABLE HistoriqueModifications (
    HistoID INT PRIMARY KEY IDENTITY(1,1),
    TableNom NVARCHAR(100),
    EnregistrementID INT,
    DateModification DATETIME DEFAULT GETDATE(),
    UtilisateurID INT,
    AnciennesValeursJSON NVARCHAR(MAX),
    NouvellesValeursJSON NVARCHAR(MAX)
);

-- Enregistrer une modification
INSERT INTO HistoriqueModifications
(TableNom, EnregistrementID, UtilisateurID, AnciennesValeursJSON, NouvellesValeursJSON)
VALUES
('Produits', 123, 5,
 '{"nom": "Laptop", "prix": 899.99, "stock": 10}',
 '{"nom": "Laptop Pro", "prix": 999.99, "stock": 8}');
```

### 5. Métadonnées extensibles

Ajouter des informations supplémentaires sans modifier le schéma :

```sql
CREATE TABLE Documents (
    DocumentID INT PRIMARY KEY IDENTITY(1,1),
    Titre NVARCHAR(200),
    DateCreation DATETIME DEFAULT GETDATE(),
    CheminFichier NVARCHAR(500),
    MetadonneesJSON NVARCHAR(MAX)  -- Métadonnées extensibles
);

INSERT INTO Documents (Titre, CheminFichier, MetadonneesJSON) VALUES
('Rapport Q3 2024', '/docs/rapport_q3_2024.pdf', '{
    "auteur": "Marie Dupont",
    "departement": "Finance",
    "tags": ["rapport", "trimestriel", "finance"],
    "taille_octets": 2458624,
    "pages": 45,
    "confidentiel": true,
    "version": "1.2"
}');
```

## Avantages du stockage JSON dans NVARCHAR

### Flexibilité

1. **Pas de schéma rigide** : Vous pouvez ajouter ou supprimer des propriétés sans modifier la structure de la table
2. **Structure variable** : Chaque ligne peut avoir une structure JSON différente
3. **Évolution simple** : Ajout de nouveaux champs sans migration de base de données

### Performance

1. **Insertion rapide** : Pas de parsing complexe à l'insertion (c'est du texte)
2. **Stockage efficace** : NVARCHAR(MAX) utilise l'espace nécessaire seulement
3. **Compatible avec compression** : SQL Server peut compresser efficacement le texte JSON

### Interopérabilité

1. **Standard universel** : JSON est supporté par tous les langages et plateformes
2. **APIs REST** : Format natif pour les échanges web
3. **Pas de conversion** : Envoyer/recevoir directement le JSON sans transformation

## Inconvénients et limitations

### Validation limitée

1. **Pas de typage fort** : Tout est texte, les types JSON ne sont pas validés par SQL Server
2. **Pas de contraintes** : Impossible d'appliquer des contraintes sur des propriétés JSON spécifiques (sauf avec CHECK complexes)
3. **Erreurs silencieuses** : Un typo dans une clé JSON ne provoque pas d'erreur

### Performance des requêtes

1. **Pas d'index direct** : On ne peut pas créer d'index directement sur des propriétés JSON (solutions de contournement existent)
2. **Parsing à chaque requête** : Extraire des valeurs nécessite de parser le JSON à chaque fois
3. **Pas optimisé pour agrégations** : Les calculs sur des données JSON sont plus lents que sur des colonnes relationnelles

### Normalisation

1. **Redondance** : Le JSON encourage la duplication de données
2. **Cohérence** : Plus difficile de garantir la cohérence référentielle
3. **Maintenance** : Plus complexe de faire des mises à jour globales

## Quand utiliser JSON vs colonnes relationnelles ?

### Utilisez des colonnes JSON pour :

- ✅ Données semi-structurées avec structure variable
- ✅ Intégration avec des APIs externes
- ✅ Configurations et préférences utilisateurs
- ✅ Métadonnées extensibles
- ✅ Prototypage rapide
- ✅ Logs et événements avec structures diverses
- ✅ Données reçues d'autres systèmes en JSON

### Utilisez des colonnes relationnelles pour :

- ✅ Données avec structure fixe et connue
- ✅ Champs sur lesquels vous devez faire des recherches fréquentes
- ✅ Données nécessitant des contraintes d'intégrité strictes
- ✅ Agrégations et calculs fréquents
- ✅ Relations entre entités (clés étrangères)
- ✅ Données critiques pour l'application
- ✅ Performances maximales requises

### Approche hybride (recommandée)

**Le meilleur des deux mondes** : combinez colonnes relationnelles et JSON !

```sql
CREATE TABLE Produits (
    -- Colonnes relationnelles pour données structurées critiques
    ProduitID INT PRIMARY KEY IDENTITY(1,1),
    Nom NVARCHAR(200) NOT NULL,
    Categorie NVARCHAR(100) NOT NULL,
    Prix DECIMAL(10,2) NOT NULL,
    Stock INT NOT NULL,
    Actif BIT DEFAULT 1,

    -- Colonne JSON pour données flexibles/secondaires
    CaracteristiquesJSON NVARCHAR(MAX),

    -- Contrainte de validation JSON
    CONSTRAINT CK_CaracteristiquesValides CHECK (
        CaracteristiquesJSON IS NULL OR
        ISJSON(CaracteristiquesJSON) = 1
    )
);
```

**Avantages de cette approche** :
- **Performance** : Recherches rapides sur colonnes indexées (Nom, Categorie, Prix)
- **Flexibilité** : Caractéristiques variables selon le type de produit dans JSON
- **Intégrité** : Contraintes et clés étrangères sur colonnes relationnelles
- **Évolutivité** : Ajout de nouvelles caractéristiques sans migration

**Exemple d'insertion** :

```sql
INSERT INTO Produits (Nom, Categorie, Prix, Stock, CaracteristiquesJSON)
VALUES
-- Ordinateur portable
('Dell XPS 15', 'Informatique', 1299.99, 5, '{
    "marque": "Dell",
    "processeur": "Intel i7-13700H",
    "ram": "16GB",
    "ecran": "15.6 pouces FHD+",
    "gpu": "NVIDIA RTX 4050",
    "poids": "1.8kg"
}'),

-- Smartphone (différentes caractéristiques)
('iPhone 15 Pro', 'Téléphonie', 1199.00, 12, '{
    "marque": "Apple",
    "couleurs": ["Titane naturel", "Titane bleu", "Titane blanc", "Titane noir"],
    "capacites": ["128GB", "256GB", "512GB", "1TB"],
    "camera": "48MP principal + 12MP ultra grand-angle + 12MP téléobjectif",
    "5G": true,
    "certification": "IP68"
}'),

-- Livre (encore différentes caractéristiques)
('Clean Code', 'Livres', 39.99, 20, '{
    "auteur": "Robert C. Martin",
    "editeur": "Prentice Hall",
```

## Bonnes pratiques

### 1. Validation systématique

Toujours ajouter une contrainte CHECK pour valider le JSON :

```sql
CONSTRAINT CK_JSON_Valide CHECK (ISJSON(MaColonneJSON) = 1)
```

### 2. NULL vs chaîne vide vs objet vide

Soyez cohérent dans votre gestion des valeurs absentes :

```sql
-- Choisissez UNE approche et tenez-vous-y :

-- Option 1 : NULL (recommandé)
INSERT INTO Table VALUES (NULL);

-- Option 2 : Objet JSON vide
INSERT INTO Table VALUES ('{}');

-- Option 3 : Tableau JSON vide (si applicable)
INSERT INTO Table VALUES ('[]');

-- À ÉVITER : Chaîne vide (ce n'est pas du JSON valide)
INSERT INTO Table VALUES ('');
```

**Recommandation** : Utilisez `NULL` pour "pas de données" et `{}` ou `[]` pour "structure vide mais présente".

### 3. Formatage et lisibilité

Pour des données stockées à long terme, considérez un formatage lisible :

```sql
-- JSON compact (économise l'espace)
'{"nom":"Dupont","age":30,"ville":"Paris"}'

-- JSON formaté (plus lisible, mais plus volumineux)
'{
    "nom": "Dupont",
    "age": 30,
    "ville": "Paris"
}'
```

**Pour la production** : Le JSON compact est généralement préféré pour économiser l'espace.

### 4. Documentation

Documentez la structure JSON attendue dans vos tables :

```sql
-- Mauvais : Pas de documentation
CREATE TABLE Config (
    ConfigJSON NVARCHAR(MAX)
);

-- Bon : Documentation claire
CREATE TABLE Config (
    ConfigID INT PRIMARY KEY,

    -- Structure JSON attendue :
    -- {
    --   "serveur": "localhost",
    --   "port": 1433,
    --   "timeout": 30,
    --   "ssl": true,
    --   "options": {...}
    -- }
    ConfigJSON NVARCHAR(MAX),

    CONSTRAINT CK_Config_JSON CHECK (ISJSON(ConfigJSON) = 1)
);
```

### 5. Gestion de la taille

Surveillez la taille de vos données JSON :

```sql
-- Vérifier la taille moyenne des données JSON
SELECT
    AVG(LEN(ConfigJSON)) AS TailleMoyenne,
    MAX(LEN(ConfigJSON)) AS TailleMaximale,
    MIN(LEN(ConfigJSON)) AS TailleMinimale
FROM Config
WHERE ConfigJSON IS NOT NULL;
```

Si les tailles dépassent régulièrement 8000 caractères, `NVARCHAR(MAX)` est approprié. Sinon, une taille fixe peut être plus performante.

### 6. Nommage des colonnes

Adoptez une convention de nommage claire :

```sql
-- Bonnes pratiques de nommage
CREATE TABLE MaTable (
    DetailsJSON NVARCHAR(MAX),      -- Suffixe JSON
    MetadonneesJSON NVARCHAR(MAX),  -- Suffixe JSON
    ConfigJSON NVARCHAR(MAX)        -- Suffixe JSON
);
```

Le suffixe `JSON` rend immédiatement évident que la colonne contient du JSON.

## Comparaison : JSON vs XML dans SQL Server

| Aspect | JSON (NVARCHAR) | XML (type XML) |
|--------|-----------------|----------------|
| **Type de données** | NVARCHAR (texte) | XML (type natif) |
| **Validation** | Via ISJSON() dans CHECK | Automatique |
| **Parsing** | Fonctions JSON_* | Méthodes XQuery |
| **Index** | Index calculés/colonnes | Index XML natifs |
| **Performance extraction** | Rapide | Moyenne |
| **Verbosité** | Compact | Plus verbeux |
| **Popularité web** | Très élevée | Décroissante |
| **Cas d'usage moderne** | APIs REST, web apps | Legacy, documents |

**Recommandation générale** : Pour de nouveaux projets, privilégiez JSON sauf si vous avez des besoins spécifiques XML (conformité, validation XSD stricte, etc.).

## Résumé

### Points clés à retenir

1. **Stockage** : JSON est stocké comme texte dans des colonnes `NVARCHAR` (de préférence `NVARCHAR(MAX)`)

2. **Stockage en NVARCHAR** : de SQL Server 2016 à 2022, pas de type `JSON` dédié — stockage en `NVARCHAR` (un type `json` natif existe depuis, en GA sur Azure SQL et en préversion dans SQL Server 2025)

3. **Validation** : Utilisez `ISJSON()` dans une contrainte CHECK pour garantir la validité du JSON

4. **Flexibilité** : Idéal pour données semi-structurées et structures variables

5. **Approche hybride** : Combinez colonnes relationnelles (pour données structurées critiques) et JSON (pour données flexibles)

6. **Limitations** : Moins performant que des colonnes relationnelles pour recherches et agrégations

### Syntaxe minimale

```sql
-- Créer une table avec JSON
CREATE TABLE MaTable (
    ID INT PRIMARY KEY,
    DonneesJSON NVARCHAR(MAX),
    CONSTRAINT CK_JSON CHECK (ISJSON(DonneesJSON) = 1)
);

-- Insérer du JSON
INSERT INTO MaTable (ID, DonneesJSON)
VALUES (1, '{"nom": "valeur", "nombre": 42}');

-- Sélectionner du JSON
SELECT ID, DonneesJSON
FROM MaTable;
```
