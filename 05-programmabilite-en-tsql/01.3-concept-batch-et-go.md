# 5.1.3 Le concept de "Batch" et le séparateur GO

## Introduction

Lorsque vous écrivez du code T-SQL, vous ne travaillez pas toujours avec une seule instruction isolée. Vous écrivez souvent des **scripts** contenant plusieurs instructions. Pour comprendre comment SQL Server traite ces scripts, il est essentiel de comprendre le concept de **batch** (lot d'instructions) et le rôle du séparateur **GO**.

Dans cette section, nous allons découvrir comment SQL Server organise et exécute votre code en lots distincts.

---

## 1. Qu'est-ce qu'un Batch ?

### Définition

Un **batch** (ou **lot**) est un ensemble d'une ou plusieurs instructions T-SQL qui sont **envoyées ensemble** à SQL Server et **exécutées comme une unité**.

Pensez à un batch comme à un "paquet" d'instructions que SQL Server :
1. **Compile** (prépare) en une seule fois
2. **Exécute** séquentiellement

### Exemple simple

```sql
-- Ceci est un seul batch contenant 3 instructions
DECLARE @Message VARCHAR(50);
SET @Message = 'Bonjour tout le monde';
SELECT @Message AS Message;
```

Dans cet exemple, les trois instructions forment un seul batch qui est compilé et exécuté ensemble.

---

## 2. Le séparateur GO

### Qu'est-ce que GO ?

**GO** est un séparateur de batch utilisé dans les outils clients comme **SQL Server Management Studio (SSMS)** et **Azure Data Studio**. Il indique la **fin d'un batch** et le **début d'un nouveau**.

### Points importants à comprendre

1. **GO n'est PAS une instruction T-SQL**
   - GO n'est pas une commande SQL
   - C'est une commande reconnue uniquement par les outils clients (SSMS, Azure Data Studio, sqlcmd)
   - SQL Server lui-même ne connaît pas GO

2. **GO sépare les batches**
   - Tout ce qui est avant GO = Batch 1
   - Tout ce qui est après GO = Batch 2

3. **GO provoque l'envoi du batch à SQL Server**
   - Quand l'outil client rencontre GO, il envoie tout le code précédent à SQL Server
   - Puis il attend la fin de l'exécution avant d'envoyer le batch suivant

### Syntaxe

```sql
-- Batch 1
Instruction1;
Instruction2;
GO

-- Batch 2
Instruction3;
Instruction4;
GO
```

---

## 3. Pourquoi utiliser GO ?

### Raison 1 : Certaines instructions doivent être seules dans un batch

Certaines instructions T-SQL **doivent être la première instruction** d'un batch. Elles ne peuvent pas être mélangées avec d'autres.

**Exemples d'instructions nécessitant GO :**
- `CREATE DATABASE`
- `CREATE PROCEDURE`
- `CREATE FUNCTION`
- `CREATE VIEW`
- `CREATE TRIGGER`
- `ALTER DATABASE`

#### Exemple INCORRECT (génère une erreur)

```sql
-- ERREUR : CREATE PROCEDURE doit être la première instruction d'un batch
SELECT * FROM Employes;
CREATE PROCEDURE AfficherEmployes
AS
BEGIN
    SELECT * FROM Employes;
END
```

**Message d'erreur :**
```
'CREATE PROCEDURE' must be the first statement in a query batch.
```

#### Exemple CORRECT

```sql
-- Batch 1
SELECT * FROM Employes;
GO

-- Batch 2 (CREATE PROCEDURE est maintenant la première instruction)
CREATE PROCEDURE AfficherEmployes
AS
BEGIN
    SELECT * FROM Employes;
END
GO
```

### Raison 2 : Réinitialiser la portée des variables

Les variables locales sont **limitées au batch** dans lequel elles sont déclarées. GO crée une nouvelle portée.

```sql
-- Batch 1
DECLARE @Message VARCHAR(50);
SET @Message = 'Bonjour';
SELECT @Message AS Batch1;
GO

-- Batch 2
SELECT @Message AS Batch2; -- ERREUR ! La variable n'existe plus
```

**Erreur :**
```
Must declare the scalar variable "@Message".
```

### Raison 3 : Forcer l'exécution séquentielle

GO force SQL Server à **terminer complètement** un batch avant de passer au suivant.

```sql
-- Créer une table
CREATE TABLE TestTable (ID INT);
GO

-- Maintenant on peut l'utiliser (dans un nouveau batch)
INSERT INTO TestTable (ID) VALUES (1);
GO
```

## 4. Portée des variables et GO

### Les variables locales ne traversent PAS GO

C'est l'un des aspects les plus importants à comprendre.

#### Exemple 1 : Variable qui ne traverse pas GO

```sql
DECLARE @Compteur INT;
SET @Compteur = 10;
SELECT @Compteur AS Valeur; -- Affiche 10
GO

-- Nouveau batch : la variable n'existe plus
SELECT @Compteur AS Valeur; -- ERREUR !
```

#### Exemple 2 : Redéclaration nécessaire

```sql
-- Batch 1
DECLARE @Nom VARCHAR(50);
SET @Nom = 'Martin';
SELECT @Nom AS Batch1;
GO

-- Batch 2 : Il faut redéclarer la variable
DECLARE @Nom VARCHAR(50);
SET @Nom = 'Dupont';
SELECT @Nom AS Batch2;
GO
```

### Les objets de base de données persistent

Contrairement aux variables, les **objets de base de données** (tables, procédures, etc.) créés dans un batch restent disponibles dans les batches suivants.

```sql
-- Batch 1 : Créer une table
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Nom VARCHAR(50)
);
GO

-- Batch 2 : Utiliser la table créée précédemment
INSERT INTO Clients (ClientID, Nom) VALUES (1, 'Dupont');
SELECT * FROM Clients;
GO
```

## 5. GO avec un compteur

### Répéter un batch

GO accepte un **argument numérique** qui indique combien de fois le batch doit être **répété**.

#### Syntaxe

```sql
Instructions;
GO n  -- Où n est le nombre de répétitions
```

#### Exemple 1 : Insérer plusieurs lignes

```sql
-- Créer une table de test
CREATE TABLE Compteur (
    ID INT IDENTITY(1,1),
    DateCreation DATETIME DEFAULT GETDATE()
);
GO

-- Insérer 5 lignes en une seule commande
INSERT INTO Compteur DEFAULT VALUES;
GO 5

-- Vérifier le résultat
SELECT * FROM Compteur;
```

**Résultat :**
```
ID  DateCreation
--  -------------------
1   2024-01-15 10:23:45
2   2024-01-15 10:23:45
3   2024-01-15 10:23:45
4   2024-01-15 10:23:45
5   2024-01-15 10:23:45
```

#### Exemple 2 : Tests de performance

```sql
-- Exécuter une requête 10 fois pour tester la performance
SELECT COUNT(*) FROM Employes WHERE Departement = 'IT';
GO 10
```

#### ⚠️ Attention avec les variables

Les variables sont redéclarées à **chaque itération** :

```sql
DECLARE @Compteur INT = 1;
PRINT 'Valeur : ' + CAST(@Compteur AS VARCHAR);
SET @Compteur = @Compteur + 1;
GO 3
```

**Résultat :**
```
Valeur : 1
Valeur : 1
Valeur : 1
```

La variable est réinitialisée à 1 à chaque itération, elle ne s'incrémente pas !

## 6. Règles et limitations des batches

### Règle 1 : Certaines instructions doivent être isolées

Les instructions suivantes doivent être la **première instruction** d'un batch :

- `CREATE DATABASE`
- `CREATE DEFAULT`
- `CREATE FUNCTION`
- `CREATE PROCEDURE`
- `CREATE RULE`
- `CREATE SCHEMA`
- `CREATE TRIGGER`
- `CREATE VIEW`

### Règle 2 : Les erreurs de compilation arrêtent le batch

Si une **erreur de syntaxe** se produit dans un batch, **aucune instruction du batch** n'est exécutée.

```sql
-- Ce batch ne s'exécutera PAS du tout
INSERT INTO Employes (Nom) VALUES ('Martin');
SELCT * FROM Employes;  -- Erreur de syntaxe (SELCT au lieu de SELECT)
UPDATE Employes SET Salaire = 3000 WHERE Nom = 'Martin';
```

Aucune des trois instructions ne sera exécutée car la syntaxe est incorrecte.

### Règle 3 : Les erreurs d'exécution peuvent être partielles

Si une **erreur d'exécution** (pas de syntaxe) se produit, les instructions **avant l'erreur** sont exécutées, mais pas celles après.

```sql
-- Batch avec erreur d'exécution
INSERT INTO Employes (Nom) VALUES ('Martin');    -- Exécuté
INSERT INTO Employes (Nom) VALUES ('Dupont');    -- Exécuté
INSERT INTO Employes (Nom) VALUES (NULL);        -- ERREUR (si NOT NULL)
INSERT INTO Employes (Nom) VALUES ('Bernard');   -- PAS exécuté
```

### Règle 4 : ALTER TABLE avec contraintes

Certaines modifications de colonnes nécessitent GO :

```sql
-- Ajouter une colonne
ALTER TABLE Employes
ADD Email VARCHAR(100);
GO

-- Maintenant on peut ajouter une contrainte sur cette colonne
ALTER TABLE Employes
ADD CONSTRAINT CHK_Email CHECK (Email LIKE '%@%');
GO
```

## 7. Exemples pratiques

### Exemple 1 : Script de création de base de données

```sql
-- Créer la base de données
CREATE DATABASE MaBoutique;
GO

-- Utiliser la base de données
USE MaBoutique;
GO

-- Créer une table
CREATE TABLE Produits (
    ProduitID INT PRIMARY KEY IDENTITY(1,1),
    Nom VARCHAR(100) NOT NULL,
    Prix DECIMAL(10,2) NOT NULL
);
GO

-- Insérer des données
INSERT INTO Produits (Nom, Prix)
VALUES
    ('Ordinateur', 999.99),
    ('Souris', 19.99),
    ('Clavier', 49.99);
GO

-- Afficher les données
SELECT * FROM Produits;
GO
```

### Exemple 2 : Création de procédure stockée

```sql
-- S'assurer qu'on est dans la bonne base
USE MaBoutique;
GO

-- Créer une procédure (doit être la première instruction du batch)
CREATE PROCEDURE AjouterProduit
    @Nom VARCHAR(100),
    @Prix DECIMAL(10,2)
AS
BEGIN
    INSERT INTO Produits (Nom, Prix)
    VALUES (@Nom, @Prix);

    SELECT @@ROWCOUNT AS LignesInserees;
END
GO

-- Exécuter la procédure
EXEC AjouterProduit @Nom = 'Écran', @Prix = 299.99;
GO
```

### Exemple 3 : Script de maintenance

```sql
-- Désactiver les contraintes de clé étrangère
ALTER TABLE Commandes NOCHECK CONSTRAINT ALL;
GO

-- Nettoyer les données
DELETE FROM Commandes WHERE DateCommande < '2020-01-01';
GO

-- Réactiver les contraintes
ALTER TABLE Commandes CHECK CONSTRAINT ALL;
GO

-- Afficher le nombre de lignes restantes
SELECT COUNT(*) AS TotalCommandes FROM Commandes;
GO
```

### Exemple 4 : Gestion conditionnelle

```sql
-- Vérifier si une table existe et la supprimer
IF OBJECT_ID('TempData', 'U') IS NOT NULL
    DROP TABLE TempData;
GO

-- Créer la nouvelle table
CREATE TABLE TempData (
    ID INT,
    Valeur VARCHAR(50)
);
GO

-- Insérer des données de test
INSERT INTO TempData (ID, Valeur) VALUES (1, 'Test');
GO 10  -- Insérer 10 fois
```

## 8. GO dans différents outils

### SQL Server Management Studio (SSMS)

- GO est **reconnu et traité** par SSMS
- Vous pouvez exécuter plusieurs batches à la fois (F5)
- Vous pouvez exécuter un batch spécifique en le sélectionnant

### Azure Data Studio

- Fonctionne de la même manière que SSMS
- GO sépare les batches visuellement

### sqlcmd (Ligne de commande)

- GO est une commande **sqlcmd**
- Utilisée pour séparer les batches dans les scripts

### Applications .NET / C#

- **GO n'existe PAS** dans les applications
- Vous devez **diviser manuellement** vos scripts en batches séparés
- Chaque batch doit être exécuté séparément

```csharp
// C# : GO n'est pas reconnu, il faut diviser manuellement
string batch1 = "CREATE TABLE Test (ID INT);";
string batch2 = "INSERT INTO Test VALUES (1);";

command.CommandText = batch1;
command.ExecuteNonQuery();

command.CommandText = batch2;
command.ExecuteNonQuery();
```

## 9. Bonnes pratiques

### ✅ À FAIRE

1. **Utiliser GO** après les instructions CREATE PROCEDURE, CREATE VIEW, etc.
2. **Utiliser GO** pour séparer logiquement les sections de votre script
3. **Utiliser GO** lors de modifications de schéma (ALTER TABLE)
4. **Commenter vos batches** pour expliquer leur rôle
5. **Tester vos scripts batch par batch** pour identifier les erreurs

### ❌ À ÉVITER

1. **Ne pas essayer d'utiliser une variable après GO** (elle n'existera plus)
2. **Ne pas supposer que GO fonctionne dans les applications** (.NET, Java, etc.)
3. **Ne pas abuser de GO** là où ce n'est pas nécessaire (alourdit le code)
4. **Ne pas oublier GO** après CREATE PROCEDURE (erreur courante)
5. **Ne pas mélanger CREATE PROCEDURE avec d'autres instructions** sans GO

## 10. Alternatives et solutions

### Conserver des valeurs entre batches

Si vous devez conserver des valeurs entre batches, utilisez des **tables temporaires** au lieu de variables :

```sql
-- Batch 1 : Créer et remplir une table temporaire
CREATE TABLE #MesValeurs (
    ID INT,
    Valeur VARCHAR(50)
);

INSERT INTO #MesValeurs VALUES (1, 'Données persistantes');
GO

-- Batch 2 : Les tables temporaires persistent !
SELECT * FROM #MesValeurs;
GO

-- Batch 3 : Nettoyer
DROP TABLE #MesValeurs;
GO
```

### Utiliser SQLCMD variables (avancé)

Dans sqlcmd et SSMS, vous pouvez utiliser des variables SQLCMD qui **traversent** GO :

```sql
:SETVAR NomBase "MaBoutique"
GO

USE $(NomBase);
GO

SELECT DB_NAME() AS BaseCourante;
GO
```

## 11. Débogage et résolution de problèmes

### Problème 1 : Variable non définie

**Symptôme :**
```
Must declare the scalar variable "@MaVariable"
```

**Cause :** La variable a été déclarée dans un batch précédent (avant un GO)

**Solution :** Redéclarez la variable dans le batch courant

### Problème 2 : CREATE PROCEDURE doit être seul

**Symptôme :**
```
'CREATE PROCEDURE' must be the first statement in a query batch
```

**Cause :** Il y a d'autres instructions avant CREATE PROCEDURE dans le même batch

**Solution :** Ajoutez GO avant CREATE PROCEDURE

### Problème 3 : Objet introuvable

**Symptôme :**
```
Invalid object name 'MaTable'
```

**Cause :** Vous essayez d'utiliser une table dans le même batch où vous la créez

**Solution :** Ajoutez GO après CREATE TABLE

---

## Résumé

- Un **batch** est un groupe d'instructions T-SQL compilées et exécutées ensemble
- **GO** est un séparateur de batch reconnu par les outils clients (SSMS, Azure Data Studio, sqlcmd)
- **GO n'est pas une instruction T-SQL**, c'est une commande d'outil
- Les **variables locales ne traversent PAS GO** - leur portée est limitée au batch
- Certaines instructions (CREATE PROCEDURE, CREATE VIEW, etc.) **doivent être seules** dans un batch
- **GO n** exécute un batch **n fois**
- Les **objets de base de données** (tables, procédures) persistent entre les batches
- GO provoque une **séparation nette** : le batch précédent est entièrement exécuté avant le suivant

Comprendre le concept de batch et le rôle de GO est essentiel pour écrire des scripts T-SQL robustes et éviter des erreurs courantes.
