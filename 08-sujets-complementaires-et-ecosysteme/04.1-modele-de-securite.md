# 8.4.1 Modèle de sécurité (Logins, Users, Rôles, Schémas)

## Introduction

Imaginez SQL Server comme un **immeuble de bureaux sécurisé**. Pour accéder aux bureaux et travailler, vous avez besoin de plusieurs niveaux d'autorisation :

1. 🏢 **Un badge pour entrer dans l'immeuble** (Login)
2. 🚪 **Une clé pour accéder à un bureau spécifique** (User)
3. 👥 **Un rôle professionnel qui définit vos responsabilités** (Role)
4. 📁 **Des armoires organisées où ranger vos documents** (Schema)

Le modèle de sécurité SQL Server fonctionne exactement de la même manière ! Cette section vous expliquera comment SQL Server contrôle **qui peut se connecter** et **ce qu'ils peuvent faire** avec vos données.

## Pourquoi la sécurité est-elle importante ?

Dans un environnement professionnel, tous les utilisateurs n'ont pas besoin (ni ne devraient avoir) accès à toutes les données :

- 📊 Un **analyste marketing** doit lire les données de ventes, mais pas modifier les salaires
- 💰 Un **comptable** doit accéder aux données financières, mais pas aux données RH
- 👨‍💼 Un **manager** doit voir les rapports, mais pas supprimer des données
- 🔧 Un **développeur** doit créer des tables en développement, mais pas en production
- 🛡️ Un **administrateur** doit gérer le serveur, mais même lui ne devrait pas tout pouvoir faire sans raison

Le modèle de sécurité SQL Server permet de mettre en place ces restrictions de manière granulaire et efficace.

## Vue d'ensemble du modèle de sécurité

SQL Server utilise un **modèle de sécurité à plusieurs niveaux** :

```
┌────────────────────────────────────────────────────────────┐
│                    NIVEAU SERVEUR                          │
│  "Qui peut se connecter au serveur SQL Server ?"           │
│                                                            │
│  ┌──────────────┐         ┌──────────────┐                 │
│  │   LOGIN      │────────→│  RÔLE SERVEUR│                 │
│  │  (Badge)     │         │  (sysadmin,  │                 │
│  │              │         │   etc.)      │                 │
│  └──────────────┘         └──────────────┘                 │
└──────────────────────┬─────────────────────────────────────┘
                       │
                       ↓ Mappage (Correspondance)
┌──────────────────────┴─────────────────────────────────────┐
│              NIVEAU BASE DE DONNÉES                        │
│  "Que peut faire l'utilisateur dans cette base ?"          │
│                                                            │
│  ┌──────────────┐         ┌──────────────┐                 │
│  │     USER     │────────→│   RÔLE DB    │                 │
│  │  (Clé bureau)│         │ (db_owner,   │                 │
│  │              │         │  db_reader)  │                 │
│  └──────────────┘         └──────────────┘                 │
│         │                                                  │
│         ↓                                                  │
│  ┌──────────────┐         ┌──────────────┐                 │
│  │    SCHEMA    │────────→│   OBJETS     │                 │
│  │  (Armoire)   │         │  (Tables,    │                 │
│  │              │         │   Vues, SP)  │                 │
│  └──────────────┘         └──────────────┘                 │
└────────────────────────────────────────────────────────────┘
```

## 1. Les Logins (Connexions) - Niveau Serveur

### Qu'est-ce qu'un Login ?

Un **Login** est une **identité au niveau du serveur SQL Server**. C'est votre badge d'accès qui vous permet d'entrer dans le serveur.

**Analogie** : C'est comme votre compte Windows qui vous permet de démarrer votre ordinateur. Sans Login, vous ne pouvez même pas vous connecter à SQL Server.

### Types de Logins

SQL Server propose deux types principaux d'authentification :

#### 1. Authentification Windows (recommandée)

Utilise votre compte Windows (Active Directory) pour vous connecter à SQL Server.

**Avantages** :
- ✅ Pas besoin de mot de passe supplémentaire (Single Sign-On)
- ✅ Gestion centralisée via Active Directory
- ✅ Politique de mot de passe Windows appliquée
- ✅ Plus sécurisé (pas de mot de passe stocké dans les chaînes de connexion)

**Exemple de création** :
```sql
-- Créer un Login basé sur un compte Windows
CREATE LOGIN [DOMAINE\JeanDupont] FROM WINDOWS;

-- Créer un Login basé sur un groupe Windows (recommandé)
CREATE LOGIN [DOMAINE\Groupe_Developpeurs] FROM WINDOWS;
```

💡 **Bonne pratique** : Utilisez des groupes Windows plutôt que des comptes individuels. Ainsi, vous gérez les membres dans Active Directory, pas dans SQL Server.

#### 2. Authentification SQL Server

Utilise un nom d'utilisateur et un mot de passe gérés directement par SQL Server.

**Avantages** :
- ✅ Fonctionne sans Active Directory
- ✅ Utile pour les connexions d'applications ou les environnements Linux

**Inconvénients** :
- ❌ Moins sécurisé (mot de passe stocké dans SQL Server)
- ❌ Gestion manuelle des mots de passe

**Exemple de création** :
```sql
-- Créer un Login SQL Server avec mot de passe
CREATE LOGIN AppUtilisateur
WITH PASSWORD = 'P@ssw0rd123!',
     CHECK_POLICY = ON,           -- Applique la politique de mot de passe Windows
     CHECK_EXPIRATION = ON;       -- Le mot de passe expire selon la politique

-- Modifier le mot de passe d'un Login
ALTER LOGIN AppUtilisateur
WITH PASSWORD = 'NouveauP@ss2024!';
```

⚠️ **Sécurité** : Si vous utilisez l'authentification SQL, toujours :
- Utiliser des mots de passe forts et complexes
- Activer `CHECK_POLICY` et `CHECK_EXPIRATION`
- Ne jamais stocker le mot de passe en clair dans votre code

### Gérer les Logins

```sql
-- Lister tous les Logins du serveur
SELECT
    name AS LoginName,
    type_desc AS Type,  -- WINDOWS_LOGIN ou SQL_LOGIN
    create_date AS DateCreation,
    is_disabled AS EstDesactive
FROM
    sys.server_principals
WHERE
    type IN ('S', 'U', 'G')  -- S=SQL Login, U=Windows User, G=Windows Group
ORDER BY
    name;

-- Désactiver un Login (sans le supprimer)
ALTER LOGIN AppUtilisateur DISABLE;

-- Réactiver un Login
ALTER LOGIN AppUtilisateur ENABLE;

-- Supprimer un Login
DROP LOGIN AppUtilisateur;
```

⚠️ **Attention** : Supprimer un Login ne supprime pas automatiquement les Users associés dans les bases de données. Cela peut créer des "orphelins".

## 2. Les Users (Utilisateurs) - Niveau Base de Données

### Qu'est-ce qu'un User ?

Un **User** est une **identité au niveau d'une base de données spécifique**. C'est la clé qui vous donne accès à un bureau spécifique dans l'immeuble.

**Point crucial** : Un Login vous connecte au **serveur**, un User vous donne des droits dans une **base de données**. Ce sont deux entités distinctes mais liées.

### Relation Login ↔ User

```
┌──────────────┐           ┌──────────────┐
│    LOGIN     │           │  Base: Ventes│
│  JeanDupont  │──mappé──→ │  USER: Jean  │
│ (Niveau      │  vers     │  (Niveau DB) │
│  Serveur)    │           │              │
└──────────────┘           └──────────────┘
                           ┌──────────────┐
                           │  Base: RH    │
                    mappé→ │  USER: Jean  │
                    vers   │  (Niveau DB) │
                           └──────────────┘
```

Un même Login peut être mappé à un User différent dans chaque base de données.

### Créer un User

```sql
-- Se placer dans la base de données concernée
USE MaBaseDeDonnees;
GO

-- Créer un User mappé à un Login Windows existant
CREATE USER Jean FOR LOGIN [DOMAINE\JeanDupont];

-- Créer un User mappé à un Login SQL existant
CREATE USER AppUser FOR LOGIN AppUtilisateur;

-- Créer un User sans Login (utilisé pour des cas particuliers)
CREATE USER UserSansLogin WITHOUT LOGIN;
```

💡 **Convention** : Par simplicité, donnez souvent le même nom au User et au Login (ex: Login `AppUtilisateur` → User `AppUtilisateur`).

### Users spéciaux

Chaque base de données contient des Users système :

| User | Description |
|------|-------------|
| **dbo** | Database Owner - Propriétaire de la base (user par défaut pour les membres de db_owner) |
| **guest** | Compte invité (généralement désactivé pour des raisons de sécurité) |
| **INFORMATION_SCHEMA** | User système pour les vues du schéma d'information |
| **sys** | User système pour les objets système |

### Gérer les Users

```sql
-- Lister tous les Users d'une base de données
USE MaBaseDeDonnees;
GO

SELECT
    name AS UserName,
    type_desc AS Type,
    create_date AS DateCreation,
    authentication_type_desc AS TypeAuthentification
FROM
    sys.database_principals
WHERE
    type IN ('S', 'U', 'G')  -- S=SQL User, U=Windows User, G=Windows Group
ORDER BY
    name;

-- Supprimer un User
DROP USER Jean;
```

### Le problème des "Orphelin Users"

Quand vous supprimez un Login ou restaurez une base depuis un autre serveur, vous pouvez vous retrouver avec des Users "orphelins" (Users sans Login correspondant).

**Diagnostiquer les orphelins** :
```sql
-- Trouver les Users orphelins
USE MaBaseDeDonnees;
GO

SELECT
    dp.name AS UserName,
    dp.type_desc AS Type,
    dp.create_date
FROM
    sys.database_principals dp
    LEFT JOIN sys.server_principals sp ON dp.sid = sp.sid
WHERE
    dp.type IN ('S', 'U')
    AND sp.sid IS NULL
    AND dp.name NOT IN ('dbo', 'guest', 'INFORMATION_SCHEMA', 'sys');
```

**Réparer un orphelin** :
```sql
-- Relier le User orphelin à un Login existant
ALTER USER Jean WITH LOGIN = [DOMAINE\JeanDupont];
```

## 3. Les Rôles - Regroupement de permissions

### Qu'est-ce qu'un Rôle ?

Un **Rôle** est un **ensemble de permissions** que vous pouvez attribuer à plusieurs Users. Au lieu de donner des permissions individuellement à chaque User, vous les ajoutez à un Rôle.

**Analogie** : C'est comme un poste de travail dans une entreprise. Un "Comptable" a certaines responsabilités, un "Manager" en a d'autres. Quand vous embauchez quelqu'un comme Comptable, il hérite automatiquement de toutes les permissions liées à ce rôle.

### Avantages des Rôles

- ✅ **Simplicité** : Gérer les permissions en un seul endroit
- ✅ **Cohérence** : Tous les membres d'un rôle ont les mêmes droits
- ✅ **Maintenance** : Facile d'ajouter/retirer des users d'un rôle
- ✅ **Audit** : Facile de voir qui a quelles permissions

### Rôles Serveur (Server Roles)

Les **Rôles Serveur** s'appliquent au niveau du serveur SQL Server entier.

#### Rôles serveur prédéfinis

| Rôle | Permissions |
|------|-------------|
| **sysadmin** | 🔴 Contrôle total du serveur (équivalent d'administrateur) |
| **serveradmin** | Configure les options du serveur, arrête/redémarre le serveur |
| **securityadmin** | Gère les logins et leurs permissions (⚠️ Quasi-équivalent de sysadmin) |
| **processadmin** | Termine les processus en cours |
| **setupadmin** | Ajoute et supprime des serveurs liés |
| **bulkadmin** | Exécute BULK INSERT |
| **diskadmin** | Gère les fichiers de disque |
| **dbcreator** | Crée, modifie, supprime, et restaure des bases de données |
| **public** | Rôle par défaut pour tous les logins (permissions minimales) |

⚠️ **Attention** : Les rôles `sysadmin` et `securityadmin` sont très puissants. Utilisez-les avec parcimonie !

**Gérer les rôles serveur** :
```sql
-- Ajouter un Login à un rôle serveur
ALTER SERVER ROLE dbcreator ADD MEMBER [DOMAINE\JeanDupont];

-- Retirer un Login d'un rôle serveur
ALTER SERVER ROLE dbcreator DROP MEMBER [DOMAINE\JeanDupont];

-- Lister les membres d'un rôle serveur
SELECT
    r.name AS RoleName,
    m.name AS MemberName
FROM
    sys.server_role_members rm
    JOIN sys.server_principals r ON rm.role_principal_id = r.principal_id
    JOIN sys.server_principals m ON rm.member_principal_id = m.principal_id
ORDER BY
    r.name, m.name;
```

### Rôles de Base de Données (Database Roles)

Les **Rôles de Base de Données** s'appliquent à une base de données spécifique.

#### Rôles de base de données prédéfinis

| Rôle | Permissions |
|------|-------------|
| **db_owner** | 🔴 Contrôle total de la base de données |
| **db_datareader** | ✅ Peut lire toutes les données (SELECT sur toutes les tables) |
| **db_datawriter** | ✅ Peut modifier toutes les données (INSERT, UPDATE, DELETE) |
| **db_ddladmin** | Peut créer, modifier, supprimer des objets (DDL) |
| **db_backupoperator** | Peut sauvegarder la base de données |
| **db_securityadmin** | Gère les permissions et les rôles de la base |
| **db_accessadmin** | Ajoute ou supprime des users |
| **db_denydatareader** | 🚫 Interdit explicitement la lecture des données |
| **db_denydatawriter** | 🚫 Interdit explicitement l'écriture des données |

💡 **Cas d'usage courants** :
- **Analyste** : `db_datareader` (lecture seule)
- **Application** : `db_datareader` + `db_datawriter` (lecture/écriture)
- **Développeur** : `db_ddladmin` + `db_datareader` + `db_datawriter` (en développement)
- **Administrateur** : `db_owner` (contrôle total)

**Gérer les rôles de base de données** :
```sql
USE MaBaseDeDonnees;
GO

-- Ajouter un User à un rôle de base de données
ALTER ROLE db_datareader ADD MEMBER Jean;

-- Ajouter un User à plusieurs rôles
ALTER ROLE db_datareader ADD MEMBER Jean;
ALTER ROLE db_datawriter ADD MEMBER Jean;

-- Retirer un User d'un rôle
ALTER ROLE db_datareader DROP MEMBER Jean;

-- Lister les membres d'un rôle
SELECT
    r.name AS RoleName,
    m.name AS MemberName
FROM
    sys.database_role_members rm
    JOIN sys.database_principals r ON rm.role_principal_id = r.principal_id
    JOIN sys.database_principals m ON rm.member_principal_id = m.member_principal_id
WHERE
    r.type = 'R'  -- R = Role
ORDER BY
    r.name, m.name;
```

### Rôles personnalisés (Custom Roles)

Vous pouvez créer vos propres rôles pour des besoins spécifiques.

```sql
USE MaBaseDeDonnees;
GO

-- Créer un rôle personnalisé
CREATE ROLE RoleComptabilite;

-- Donner des permissions spécifiques au rôle
GRANT SELECT, INSERT, UPDATE ON dbo.Factures TO RoleComptabilite;
GRANT SELECT ON dbo.Clients TO RoleComptabilite;
GRANT EXECUTE ON dbo.CalculerTotalFacture TO RoleComptabilite;

-- Ajouter des users au rôle
ALTER ROLE RoleComptabilite ADD MEMBER Marie;
ALTER ROLE RoleComptabilite ADD MEMBER Pierre;

-- Maintenant Marie et Pierre ont les mêmes permissions !
```

**Avantage** : Si vous devez modifier les permissions, vous ne changez qu'un seul endroit (le rôle), et tous les membres en bénéficient automatiquement.

## 4. Les Schémas - Organisation logique

### Qu'est-ce qu'un Schéma ?

Un **Schéma** est un **conteneur logique** pour organiser les objets de base de données (tables, vues, procédures stockées, etc.).

**Analogie** : Pensez aux schémas comme des **classeurs** ou des **dossiers** dans lesquels vous rangez vos documents. Au lieu d'avoir toutes vos tables en vrac, vous les organisez par thème.

### Pourquoi utiliser des Schémas ?

#### 1. Organisation logique

```
Base de données : EntrepriseDB
│
├── Schema: Ventes
│   ├── Tables: Commandes, Factures, Produits
│   ├── Vues: VueVentesParRegion
│   └── Procédures: CreerCommande, CalculerCA
│
├── Schema: RH
│   ├── Tables: Employes, Salaires, Conges
│   ├── Vues: VueEmployesActifs
│   └── Procédures: AjouterEmploye
│
└── Schema: Comptabilite
    ├── Tables: Comptes, Transactions, Budgets
    └── Vues: VueBilanAnnuel
```

#### 2. Gestion de la sécurité

Vous pouvez donner des permissions sur un schéma entier plutôt que table par table.

```sql
-- Donner accès à TOUTES les tables du schéma Ventes
GRANT SELECT ON SCHEMA::Ventes TO UtilisateurVentes;

-- Plus simple que :
-- GRANT SELECT ON Ventes.Commandes TO UtilisateurVentes;
-- GRANT SELECT ON Ventes.Factures TO UtilisateurVentes;
-- GRANT SELECT ON Ventes.Produits TO UtilisateurVentes;
-- ... (et ainsi de suite pour chaque table)
```

#### 3. Éviter les conflits de noms

Deux tables peuvent avoir le même nom si elles sont dans des schémas différents :

```sql
-- Ces deux tables peuvent coexister :
CREATE TABLE Ventes.Produits (...);
CREATE TABLE Achats.Produits (...);

-- Référence explicite dans les requêtes :
SELECT * FROM Ventes.Produits;
SELECT * FROM Achats.Produits;
```

### Le schéma par défaut : dbo

Par défaut, tous les objets sont créés dans le schéma **dbo** (Database Owner).

```sql
-- Ces deux requêtes sont équivalentes :
CREATE TABLE MaTable (...);
CREATE TABLE dbo.MaTable (...);

-- Si aucun schéma n'est spécifié, SQL Server utilise dbo
```

### Créer et gérer des Schémas

```sql
USE MaBaseDeDonnees;
GO

-- Créer un nouveau schéma
CREATE SCHEMA Ventes;

-- Créer un schéma avec un propriétaire spécifique
CREATE SCHEMA Ventes AUTHORIZATION Jean;

-- Créer une table dans un schéma spécifique
CREATE TABLE Ventes.Commandes (
    CommandeID INT PRIMARY KEY,
    DateCommande DATE,
    MontantTotal DECIMAL(10,2)
);

-- Déplacer une table d'un schéma à un autre
ALTER SCHEMA Comptabilite TRANSFER dbo.Factures;
-- La table dbo.Factures devient Comptabilite.Factures

-- Supprimer un schéma (doit être vide)
DROP SCHEMA Ventes;
```

### Schéma par défaut d'un User

Chaque User a un schéma par défaut (généralement `dbo`).

```sql
-- Créer un User avec un schéma par défaut spécifique
CREATE USER Jean FOR LOGIN [DOMAINE\JeanDupont]
WITH DEFAULT_SCHEMA = Ventes;

-- Modifier le schéma par défaut d'un User existant
ALTER USER Jean WITH DEFAULT_SCHEMA = Comptabilite;
```

💡 **Utilité** : Quand Jean crée des objets sans spécifier de schéma, ils sont créés dans son schéma par défaut.

### Lister les Schémas

```sql
-- Voir tous les schémas de la base de données
SELECT
    name AS SchemaName,
    USER_NAME(principal_id) AS Owner,
    schema_id
FROM
    sys.schemas
ORDER BY
    name;

-- Voir les objets d'un schéma spécifique
SELECT
    SCHEMA_NAME(schema_id) AS SchemaName,
    name AS ObjectName,
    type_desc AS ObjectType
FROM
    sys.objects
WHERE
    SCHEMA_NAME(schema_id) = 'Ventes'
ORDER BY
    type_desc, name;
```

## Comment tout cela fonctionne ensemble

Mettons tout en pratique avec un scénario complet.

### Scénario : Nouvelle application de ventes

Vous développez une application de ventes et devez configurer la sécurité.

#### Étape 1 : Créer les Logins (niveau serveur)

```sql
-- Login pour l'application
CREATE LOGIN AppVentes
WITH PASSWORD = 'AppP@ssw0rd2024!',
     CHECK_POLICY = ON;

-- Login pour les analystes (groupe Windows)
CREATE LOGIN [DOMAINE\Groupe_Analystes] FROM WINDOWS;

-- Login pour les managers (groupe Windows)
CREATE LOGIN [DOMAINE\Groupe_Managers] FROM WINDOWS;
```

#### Étape 2 : Créer la base de données et les schémas

```sql
-- Créer la base de données
CREATE DATABASE VentesDB;
GO

USE VentesDB;
GO

-- Créer les schémas
CREATE SCHEMA Ventes;
CREATE SCHEMA Rapports;
CREATE SCHEMA Administration;
```

#### Étape 3 : Créer des objets dans les schémas

```sql
-- Tables dans le schéma Ventes
CREATE TABLE Ventes.Commandes (
    CommandeID INT PRIMARY KEY IDENTITY,
    ClientID INT NOT NULL,
    DateCommande DATE NOT NULL,
    MontantTotal DECIMAL(10,2) NOT NULL
);

CREATE TABLE Ventes.LignesCommande (
    LigneID INT PRIMARY KEY IDENTITY,
    CommandeID INT NOT NULL,
    ProduitID INT NOT NULL,
    Quantite INT NOT NULL,
    PrixUnitaire DECIMAL(10,2) NOT NULL
);

-- Vue dans le schéma Rapports
CREATE VIEW Rapports.VueCAParMois AS
SELECT
    YEAR(DateCommande) AS Annee,
    MONTH(DateCommande) AS Mois,
    SUM(MontantTotal) AS ChiffreAffaires
FROM
    Ventes.Commandes
GROUP BY
    YEAR(DateCommande), MONTH(DateCommande);
```

#### Étape 4 : Créer les Users (niveau base de données)

```sql
-- User pour l'application
CREATE USER AppVentesUser FOR LOGIN AppVentes
WITH DEFAULT_SCHEMA = Ventes;

-- User pour les analystes
CREATE USER AnalystesUser FOR LOGIN [DOMAINE\Groupe_Analystes]
WITH DEFAULT_SCHEMA = Rapports;

-- User pour les managers
CREATE USER ManagersUser FOR LOGIN [DOMAINE\Groupe_Managers]
WITH DEFAULT_SCHEMA = Rapports;
```

#### Étape 5 : Créer des rôles personnalisés

```sql
-- Rôle pour l'application (lecture/écriture sur Ventes)
CREATE ROLE RoleApplication;
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::Ventes TO RoleApplication;

-- Rôle pour les analystes (lecture seule partout)
CREATE ROLE RoleAnalystes;
GRANT SELECT ON SCHEMA::Ventes TO RoleAnalystes;
GRANT SELECT ON SCHEMA::Rapports TO RoleAnalystes;

-- Rôle pour les managers (lecture sur tout + vues spéciales)
CREATE ROLE RoleManagers;
GRANT SELECT ON SCHEMA::Ventes TO RoleManagers;
GRANT SELECT ON SCHEMA::Rapports TO RoleManagers;
GRANT SELECT ON SCHEMA::Administration TO RoleManagers;
```

#### Étape 6 : Assigner les Users aux Rôles

```sql
-- Assigner l'application à son rôle
ALTER ROLE RoleApplication ADD MEMBER AppVentesUser;

-- Assigner les analystes à leur rôle
ALTER ROLE RoleAnalystes ADD MEMBER AnalystesUser;

-- Assigner les managers à leur rôle
ALTER ROLE RoleManagers ADD MEMBER ManagersUser;
```

### Résultat final

```
┌─────────────────────────────────────────────────────────────┐
│                      SERVEUR SQL                            │
├─────────────────────────────────────────────────────────────┤
│ LOGINS:                                                     │
│  • AppVentes (SQL Login)                                    │
│  • DOMAINE\Groupe_Analystes (Windows Group)                 │
│  • DOMAINE\Groupe_Managers (Windows Group)                  │
└───────────────────────┬─────────────────────────────────────┘
                        │
                        ↓ Mappés vers
┌───────────────────────┴─────────────────────────────────────┐
│                   BASE: VentesDB                            │
├─────────────────────────────────────────────────────────────┤
│ USERS:                      RÔLES:                          │
│  • AppVentesUser       →    • RoleApplication               │
│  • AnalystesUser       →    • RoleAnalystes                 │
│  • ManagersUser        →    • RoleManagers                  │
│                                                             │
│ SCHÉMAS:                    OBJETS:                         │
│  • Ventes              →    • Commandes, LignesCommande     │
│  • Rapports            →    • VueCAParMois                  │
│  • Administration      →    • (tables admin)                │
└─────────────────────────────────────────────────────────────┘
```

**Permissions résultantes** :

| Qui | Peut faire quoi |
|-----|-----------------|
| **AppVentesUser** | Lire/écrire dans le schéma Ventes (gérer les commandes) |
| **AnalystesUser** | Lire dans Ventes et Rapports (analyser les données) |
| **ManagersUser** | Lire partout (superviser l'activité) |

## Principe du moindre privilège

**Règle d'or de la sécurité** : Donnez uniquement les permissions **strictement nécessaires**.

### ❌ Mauvaise pratique

```sql
-- Donner tous les droits par facilité
ALTER ROLE db_owner ADD MEMBER Jean;
```

**Problèmes** :
- Jean peut tout faire, y compris supprimer toutes les données
- Si son compte est compromis, l'attaquant a un contrôle total
- Difficile d'auditer les actions (trop de permissions)

### ✅ Bonne pratique

```sql
-- Donner uniquement ce qui est nécessaire
CREATE ROLE RoleJean;
GRANT SELECT ON dbo.Clients TO RoleJean;
GRANT SELECT ON dbo.Commandes TO RoleJean;
GRANT EXECUTE ON dbo.CreerRapport TO RoleJean;
ALTER ROLE RoleJean ADD MEMBER Jean;
```

**Avantages** :
- Jean peut faire son travail, pas plus
- Limitation des dégâts en cas de compromission
- Audit plus précis

## Bonnes pratiques de sécurité

### 1. Utilisez l'authentification Windows quand possible

```sql
-- ✅ Préférez ceci
CREATE LOGIN [DOMAINE\Groupe_Developpeurs] FROM WINDOWS;

-- ❌ Plutôt que cela
CREATE LOGIN Developpeur1 WITH PASSWORD = '...';
CREATE LOGIN Developpeur2 WITH PASSWORD = '...';
CREATE LOGIN Developpeur3 WITH PASSWORD = '...';
```

### 2. Utilisez des groupes, pas des comptes individuels

Gérez les membres dans Active Directory, pas dans SQL Server.

### 3. Utilisez des rôles personnalisés

```sql
-- ✅ Créez des rôles métier
CREATE ROLE RoleVentes;
CREATE ROLE RoleComptabilite;
CREATE ROLE RoleRH;

-- Puis assignez les permissions appropriées
GRANT SELECT ON SCHEMA::Ventes TO RoleVentes;
-- etc.
```

### 4. Organisez avec des schémas

```sql
-- ✅ Structurez votre base
CREATE SCHEMA Ventes;
CREATE SCHEMA Achats;
CREATE SCHEMA RH;
CREATE SCHEMA Comptabilite;
```

### 5. Désactivez le compte sa (sysadmin)

Le compte `sa` est une cible privilégiée des attaquants.

```sql
-- Désactiver le compte sa
ALTER LOGIN sa DISABLE;

-- Créer des comptes administrateurs nominatifs
CREATE LOGIN [DOMAINE\AdminSQL_Jean] FROM WINDOWS;
ALTER SERVER ROLE sysadmin ADD MEMBER [DOMAINE\AdminSQL_Jean];
```

### 6. Auditez régulièrement

```sql
-- Qui a des permissions sysadmin ?
SELECT
    m.name AS MemberName,
    m.type_desc AS Type
FROM
    sys.server_role_members rm
    JOIN sys.server_principals r ON rm.role_principal_id = r.principal_id
    JOIN sys.server_principals m ON rm.member_principal_id = m.principal_id
WHERE
    r.name = 'sysadmin';

-- Qui a db_owner sur cette base ?
USE MaBaseDeDonnees;
GO

SELECT
    m.name AS MemberName
FROM
    sys.database_role_members rm
    JOIN sys.database_principals r ON rm.role_principal_id = r.principal_id
    JOIN sys.database_principals m ON rm.member_principal_id = m.member_principal_id
WHERE
    r.name = 'db_owner';
```

### 7. Documentez votre modèle de sécurité

Créez un document expliquant :
- Quels rôles existent
- Quelles permissions chaque rôle a
- Qui doit être dans quel rôle
- Procédure pour demander des accès

## Dépannage courant

### Problème 1 : "Cannot open database requested by the login"

**Cause** : Le Login existe, mais il n'a pas de User mappé dans la base de données.

**Solution** :
```sql
USE MaBaseDeDonnees;
GO
CREATE USER MonUser FOR LOGIN MonLogin;
```

### Problème 2 : "The server principal already exists"

**Cause** : Vous essayez de créer un Login qui existe déjà.

**Solution** :
```sql
-- Vérifier si le Login existe
IF NOT EXISTS (SELECT * FROM sys.server_principals WHERE name = 'MonLogin')
BEGIN
    CREATE LOGIN MonLogin WITH PASSWORD = 'P@ss!';
END
```

### Problème 3 : "Cannot drop the user because it owns a schema"

**Cause** : Le User possède un schéma.

**Solution** :
```sql
-- Changer le propriétaire du schéma
ALTER AUTHORIZATION ON SCHEMA::MonSchema TO dbo;

-- Puis supprimer le User
DROP USER MonUser;
```

### Problème 4 : User orphelin après restauration

**Symptôme** : Le Login existe, le User existe, mais ils ne sont pas liés.

**Solution** :
```sql
-- Relier le User orphelin au Login
USE MaBaseDeDonnees;
GO
ALTER USER MonUser WITH LOGIN = MonLogin;
```

## Conclusion

Le modèle de sécurité SQL Server peut sembler complexe au premier abord, mais il est en réalité très logique :

1. 🏢 **Login** : Qui peut entrer dans le serveur ?
2. 🚪 **User** : Qui peut accéder à cette base de données ?
3. 👥 **Rôle** : Quel est le poste/fonction de cette personne ?
4. 📁 **Schéma** : Comment organiser les objets de manière logique ?

En comprenant ces quatre concepts et leur hiérarchie, vous pouvez créer un système de sécurité robuste, facile à maintenir et conforme au principe du moindre privilège.

**N'oubliez jamais** : La sécurité n'est pas une option, c'est une nécessité. Prenez le temps de bien configurer vos permissions dès le départ plutôt que de tout donner à tout le monde "pour simplifier". Votre futur vous remerciera !

---

**Points clés à retenir** :
- **Login** = Accès au serveur (niveau instance)
- **User** = Accès à une base de données (niveau DB)
- **Rôle** = Groupe de permissions réutilisable
- **Schéma** = Conteneur logique pour organiser les objets
- Utilisez l'authentification Windows quand possible
- Appliquez le principe du moindre privilège
- Créez des rôles personnalisés pour votre métier
- Organisez avec des schémas pour faciliter la gestion
- Un Login peut être mappé à plusieurs Users (un par base)
- Les permissions s'héritent : User → Rôle → Schéma → Objet
