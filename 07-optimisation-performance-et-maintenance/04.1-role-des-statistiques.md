# 7.4.1 Rôle des statistiques pour l'optimiseur de requêtes

## Introduction

Vous vous souvenez de l'optimiseur de requêtes dont nous avons parlé dans les sections précédentes ? Ce composant intelligent de SQL Server qui choisit le meilleur plan d'exécution pour vos requêtes ? Eh bien, il ne peut pas faire son travail correctement sans une information cruciale : **les statistiques**.

Les **statistiques** sont comme les yeux de l'optimiseur. Sans elles, il est aveugle et doit deviner. Avec de bonnes statistiques, il peut prendre des décisions éclairées et choisir le meilleur chemin pour exécuter vos requêtes.

Dans cette section, nous allons comprendre ce que sont les statistiques, pourquoi elles sont essentielles, et comment elles influencent les performances de vos requêtes.

## Qu'est-ce que les statistiques ?

### Définition simple

Les **statistiques** sont des informations que SQL Server collecte et maintient sur le **contenu et la distribution** des données dans vos tables et vos index.

Plus précisément, les statistiques contiennent :
- Le **nombre total de lignes** dans une table
- Le **nombre de valeurs distinctes** dans une colonne
- La **distribution des valeurs** (quelles valeurs sont fréquentes, lesquelles sont rares)
- Des **échantillons de données** représentatifs
- La **densité** des données (à quel point les valeurs sont uniques ou répétées)

### Analogie : Le recensement

Imaginez que vous dirigez une entreprise de livraison et que vous devez planifier vos itinéraires :

**Sans statistiques (données du recensement) :**
- Vous ne savez pas combien d'habitants il y a dans chaque quartier
- Vous ne savez pas quelles rues sont les plus fréquentées
- Vous devez deviner où envoyer vos livreurs
- Résultat : Planification inefficace, temps perdu

**Avec des statistiques :**
- Vous connaissez la population de chaque quartier
- Vous savez quelles zones ont le plus de clients potentiels
- Vous pouvez optimiser vos itinéraires en fonction des données réelles
- Résultat : Livraisons efficaces, économie de temps et d'argent

C'est exactement le même principe pour SQL Server. Les statistiques lui permettent de **planifier intelligemment** l'exécution des requêtes.

## Pourquoi l'optimiseur a-t-il besoin de statistiques ?

### Le défi de l'estimation

Rappelez-vous : l'optimiseur de requêtes doit choisir parmi plusieurs plans d'exécution possibles. Pour faire ce choix, il doit **estimer** le coût de chaque option.

Mais comment estimer le coût sans savoir :
- Combien de lignes seront traitées ?
- Combien de lectures disque seront nécessaires ?
- Quelle quantité de mémoire sera utilisée ?

C'est là que les statistiques entrent en jeu !

### Exemple concret

Prenons cette requête simple :

```sql
SELECT *
FROM Clients
WHERE Ville = 'Paris';
```

L'optimiseur doit choisir entre deux stratégies :

#### Option 1 : Table Scan (parcours complet)
- Lire toutes les lignes de la table
- Filtrer celles qui correspondent à 'Paris'
- Coût : Proportionnel au nombre total de lignes dans la table

#### Option 2 : Index Seek (recherche ciblée)
- Utiliser un index sur la colonne Ville
- Aller directement aux lignes où Ville = 'Paris'
- Coût : Proportionnel au nombre de lignes à Paris + coût de parcours de l'index

**Question cruciale :** Quelle option est la meilleure ?

**La réponse dépend de :**
- Combien de clients habitent à Paris ?
- Combien de clients au total ?
- Quelle proportion cela représente-t-il ?

### Trois scénarios différents

#### Scénario A : Peu de clients à Paris (1%)

```
Table Clients : 1 000 000 lignes
Clients à Paris : 10 000 lignes (1%)
```

**Meilleure stratégie :** Index Seek
- Index Seek : Lit ~10 000 lignes → Rapide ⚡
- Table Scan : Lit 1 000 000 lignes → Lent 🐌

**Comment l'optimiseur le sait ?** Grâce aux statistiques qui lui disent : "Paris = 1% des données"

#### Scénario B : Beaucoup de clients à Paris (80%)

```
Table Clients : 1 000 000 lignes
Clients à Paris : 800 000 lignes (80%)
```

**Meilleure stratégie :** Table Scan
- Index Seek : Lit ~800 000 lignes + coût de l'index → Coûteux 💰
- Table Scan : Lit 1 000 000 lignes en une seule passe → Plus efficace ⚡

**Comment l'optimiseur le sait ?** Les statistiques lui disent : "Paris = 80% des données, autant tout lire"

#### Scénario C : Statistiques obsolètes (PROBLÈME !)

```
Table Clients : 1 000 000 lignes
Clients à Paris : 800 000 lignes (80% en réalité)

MAIS les statistiques disent : 10 000 lignes (1% - information obsolète)
```

**Ce qui se passe :**
- L'optimiseur croit qu'il n'y a que 1% de clients à Paris
- Il choisit Index Seek
- En réalité, il doit traiter 80% des données
- Résultat : Performance catastrophique ! 🔥

**Voilà pourquoi les statistiques doivent être à jour !**

## Ce que contiennent les statistiques

### 1. L'histogramme

L'élément principal des statistiques est **l'histogramme**. C'est une représentation de la distribution des valeurs dans une colonne.

#### Analogie : L'histogramme des âges

Imaginez un histogramme de la population par tranche d'âge :

```
0-10 ans   : ████████ (8%)
11-20 ans  : ██████████ (10%)
21-30 ans  : ████████████████ (16%)
31-40 ans  : ██████████████ (14%)
41-50 ans  : ████████████ (12%)
51-60 ans  : ██████████ (10%)
61-70 ans  : ████████ (8%)
71-80 ans  : ████ (4%)
81+ ans    : ██ (2%)
```

Cet histogramme vous dit :
- Quelle tranche d'âge est la plus représentée (21-30 ans)
- Les valeurs extrêmes sont rares (81+ ans)
- Comment les données sont distribuées

#### Dans SQL Server

SQL Server crée des histogrammes similaires pour vos colonnes :

```
Valeur Ville    | Nombre de lignes | Pourcentage
----------------|------------------|-------------
'Lyon'          | 50 000          | 5%
'Marseille'     | 80 000          | 8%
'Paris'         | 800 000         | 80%
'Toulouse'      | 30 000          | 3%
'Autres'        | 40 000          | 4%
```

Avec ces informations, l'optimiseur sait :
- Paris est **très fréquent** (80%)
- Toulouse est **rare** (3%)
- Il doit adapter sa stratégie en fonction

### 2. La densité

La **densité** mesure à quel point une colonne a des valeurs uniques.

#### Formule simple

```
Densité = 1 / (Nombre de valeurs distinctes)
```

#### Exemples

**Colonne avec peu de valeurs distinctes (faible cardinalité) :**
```sql
Colonne : Genre (Homme, Femme)
Valeurs distinctes : 2
Densité : 1/2 = 0.5 (50%)
```

Interprétation : Chaque valeur représente en moyenne 50% des données.

**Colonne avec beaucoup de valeurs distinctes (haute cardinalité) :**
```sql
Colonne : Email (unique pour chaque client)
Valeurs distinctes : 1 000 000
Densité : 1/1 000 000 = 0.000001 (0.0001%)
```

Interprétation : Chaque valeur est quasi unique.

#### Pourquoi c'est important ?

L'optimiseur utilise la densité pour estimer combien de lignes seront retournées :

**Requête sur colonne à faible densité :**
```sql
SELECT * FROM Clients WHERE Genre = 'Homme';
```
L'optimiseur sait que ~50% des lignes seront retournées → Table Scan probablement meilleur

**Requête sur colonne à haute densité :**
```sql
SELECT * FROM Clients WHERE Email = 'jean.dupont@email.com';
```
L'optimiseur sait qu'une seule ligne sera retournée → Index Seek optimal

### 3. Le nombre total de lignes

Les statistiques enregistrent le **nombre total de lignes** dans la table au moment où elles ont été créées ou mises à jour.

C'est une information fondamentale que l'optimiseur utilise dans tous ses calculs.

### 4. La date de dernière mise à jour

Les statistiques gardent trace de **quand** elles ont été mises à jour pour la dernière fois.

Si cette date est ancienne et que la table a beaucoup changé, c'est un signal que les statistiques sont probablement obsolètes.

## Comment l'optimiseur utilise les statistiques

### Le processus de décision

Voici le cheminement de l'optimiseur lorsqu'il analyse une requête :

#### Étape 1 : Analyser la requête

```sql
SELECT Nom, Prenom
FROM Clients
WHERE Ville = 'Lyon'
  AND Age > 30;
```

L'optimiseur identifie :
- Table concernée : Clients
- Colonnes de filtrage : Ville, Age
- Colonnes à retourner : Nom, Prenom

#### Étape 2 : Consulter les statistiques

L'optimiseur regarde les statistiques pour :

**Statistiques sur Ville :**
- Combien de valeurs distinctes ? (ex: 100 villes différentes)
- Quelle est la fréquence de 'Lyon' ? (ex: 5% des clients)

**Statistiques sur Age :**
- Distribution des âges ?
- Combien de personnes ont plus de 30 ans ? (ex: 60% des clients)

#### Étape 3 : Estimer la sélectivité

L'optimiseur calcule **combien de lignes** vont correspondre aux critères :

```
Nombre total de clients : 1 000 000

Estimation :
- Clients à Lyon : 1 000 000 × 5% = 50 000
- Clients > 30 ans : 1 000 000 × 60% = 600 000
- Clients à Lyon ET > 30 ans : 1 000 000 × 5% × 60% = 30 000
  (en supposant l'indépendance des conditions)
```

Résultat : L'optimiseur estime que **30 000 lignes** seront retournées.

#### Étape 4 : Évaluer les options

Avec cette estimation, l'optimiseur peut comparer les stratégies :

**Option A : Index sur Ville + Filter sur Age**
- Index Seek sur Ville → 50 000 lignes
- Filter en mémoire (Age > 30) → 30 000 lignes finales
- Coût estimé : Moyen

**Option B : Index sur Age + Filter sur Ville**
- Index Seek sur Age → 600 000 lignes
- Filter en mémoire (Ville = 'Lyon') → 30 000 lignes finales
- Coût estimé : Élevé (beaucoup de lignes à filtrer)

**Option C : Index composite (Ville, Age)**
- Index Seek direct sur les deux conditions → 30 000 lignes
- Coût estimé : Faible ⚡

**Option D : Table Scan**
- Lire toute la table → 1 000 000 lignes
- Filtrer → 30 000 lignes finales
- Coût estimé : Élevé

#### Étape 5 : Choisir le meilleur plan

L'optimiseur calcule le coût détaillé de chaque option et choisit :
- **Si l'index composite (Ville, Age) existe :** Option C
- **Sinon, si index sur Ville existe :** Option A
- **Sinon :** Probablement Table Scan (Option D)

**Tout cela est possible grâce aux statistiques !**

## L'impact de statistiques inexactes

### Scénario problématique

Imaginez que vos statistiques sont obsolètes :

**Situation réelle :**
```
Table Commandes : 10 000 000 lignes
Commandes du dernier mois : 9 500 000 lignes (95%)
```

**Ce que disent les statistiques obsolètes :**
```
Commandes du dernier mois : 100 000 lignes (1%)
```

**Requête :**
```sql
SELECT *
FROM Commandes
WHERE DateCommande >= '2024-11-01';
```

### Ce qui se passe (avec statistiques obsolètes)

1. **L'optimiseur consulte les statistiques**
   - Les stats disent : "Seulement 1% des commandes du dernier mois"
   - Estimation : 100 000 lignes

2. **L'optimiseur choisit un plan**
   - Il pense traiter peu de lignes
   - Il choisit : **Nested Loops** avec Index Seek
   - Il alloue peu de mémoire

3. **La requête s'exécute**
   - En réalité : 9 500 000 lignes à traiter !
   - Le plan choisi est complètement inadapté
   - Débordement mémoire possible
   - Performance catastrophique 🔥

### Les conséquences

Des statistiques obsolètes peuvent causer :

#### 1. Mauvais choix de plan d'exécution
- L'optimiseur choisit une stratégie inadaptée
- Nested Loops au lieu de Hash Match
- Index Seek au lieu de Table Scan (ou vice versa)

#### 2. Mauvaise allocation de mémoire
- Trop peu de mémoire allouée
- Débordement vers TempDB (spill to disk)
- Performance dégradée de 10× à 100×

#### 3. Parallélisme inadapté
- Trop ou pas assez de threads parallèles
- Overhead de coordination inutile
- Perte de performance

#### 4. Estimations en cascade
- Une mauvaise estimation au début
- Affecte toutes les étapes suivantes
- Plan globalement sous-optimal

## Quand SQL Server crée-t-il des statistiques ?

### Création automatique

SQL Server est intelligent : il crée automatiquement des statistiques dans plusieurs situations.

#### 1. Lors de la création d'un index

Chaque fois que vous créez un index, SQL Server crée automatiquement des statistiques pour cet index :

```sql
CREATE INDEX IX_Clients_Ville ON Clients(Ville);
```

➡️ SQL Server crée automatiquement des statistiques sur la colonne `Ville`

#### 2. Sur les colonnes utilisées dans les prédicats

Si vous activez l'option `AUTO_CREATE_STATISTICS` (activée par défaut), SQL Server créera automatiquement des statistiques sur les colonnes utilisées dans les clauses WHERE, JOIN, etc.

**Exemple :**
```sql
-- Première exécution de cette requête
SELECT * FROM Clients WHERE Email = 'test@email.com';
```

Si aucun index ni statistiques n'existent sur `Email`, SQL Server :
1. Détecte que la colonne est utilisée dans un prédicat
2. Crée automatiquement des statistiques sur `Email`
3. Utilise ces statistiques pour les exécutions suivantes

#### 3. Sur les colonnes d'index composites

Lors de la création d'un index composite, des statistiques multi-colonnes sont créées :

```sql
CREATE INDEX IX_Clients_Ville_Age ON Clients(Ville, Age);
```

➡️ Crée des statistiques qui comprennent la **corrélation** entre Ville et Age

### Mise à jour automatique

Par défaut, SQL Server met à jour automatiquement les statistiques (option `AUTO_UPDATE_STATISTICS`) quand :

#### Seuil de mise à jour

Le seuil dépend de la taille de la table :

**Pour les petites tables (< 500 lignes) :**
- Mise à jour après **500 modifications** (INSERT, UPDATE, DELETE)

**Pour les tables moyennes et grandes (≥ 500 lignes) :**
- Mise à jour après **500 + 20% du nombre de lignes** ont été modifiées

**Exemple :**
```
Table de 10 000 lignes :
Seuil = 500 + (20% × 10 000) = 500 + 2 000 = 2 500 modifications

Table de 1 000 000 lignes :
Seuil = 500 + (20% × 1 000 000) = 500 + 200 000 = 200 500 modifications
```

#### Problème avec les grandes tables

Sur les très grandes tables (millions ou milliards de lignes), le seuil de 20% peut être **énorme** :

```
Table de 10 000 000 lignes :
Seuil = 2 000 500 modifications avant mise à jour !
```

Cela signifie que les statistiques peuvent rester obsolètes très longtemps si les modifications sont progressives.

**Solution :** SQL Server 2016+ a introduit un seuil dynamique plus intelligent qui s'adapte mieux aux grandes tables.

## L'importance de statistiques à jour

### Analogie : La carte routière

Imaginez que vous utilisez une carte routière pour planifier un voyage :

**Carte à jour (bonnes statistiques) :**
- ✅ Nouvelles routes construites sont indiquées
- ✅ Routes fermées sont marquées
- ✅ Temps de trajet réalistes
- ✅ Navigation efficace

**Carte obsolète (statistiques périmées) :**
- ❌ Nouvelles autoroutes manquantes
- ❌ Routes désormais fermées encore affichées
- ❌ Temps de trajet incorrects
- ❌ Détours inutiles, retards

### Dans SQL Server

**Statistiques à jour :**
- ✅ L'optimiseur connaît la vraie distribution des données
- ✅ Estimations précises du nombre de lignes
- ✅ Bon choix d'opérateurs (Seek, Scan, Join)
- ✅ Allocation mémoire appropriée
- ✅ Performance optimale ⚡

**Statistiques obsolètes :**
- ❌ L'optimiseur travaille avec des informations erronées
- ❌ Estimations très éloignées de la réalité
- ❌ Mauvais choix d'opérateurs
- ❌ Débordements mémoire, timeouts
- ❌ Performance dégradée 🐌

## Signes que vos statistiques sont obsolètes

### 1. Dans les plans d'exécution

Quand vous analysez un plan d'exécution réel, surveillez :

**Écart important entre estimations et réalité :**
```
Opérateur : Index Seek
Estimated Rows : 100
Actual Rows : 500 000

Ratio : 5 000 (!)  ← PROBLÈME !
```

Si vous voyez un ratio de ×10 ou plus, c'est un signal d'alarme.

### 2. Requêtes soudainement lentes

Une requête qui était rapide devient soudainement lente, sans changement apparent :
- Peut-être que les données ont beaucoup changé
- Les statistiques n'ont pas été mises à jour
- Le plan choisi n'est plus adapté

### 3. Plans d'exécution qui changent fréquemment

Si le même requête utilise des plans différents à chaque exécution, c'est souvent dû à :
- Statistiques mises à jour entre deux exécutions
- Ou pire : statistiques obsolètes avec parameter sniffing (concept avancé)

### 4. Avertissements dans le plan

SQL Server peut afficher des avertissements dans le plan :
- ⚠️ "Statistics not available" (statistiques non disponibles)
- ⚠️ Large estimation variance (grande variance d'estimation)

## Comment les statistiques influencent vos index

### L'index parfait... ignoré !

Vous pouvez créer l'index parfait, mais si les statistiques sont obsolètes, SQL Server peut **ne pas l'utiliser** :

**Situation :**
```sql
-- Vous créez un index
CREATE INDEX IX_Produits_Categorie ON Produits(Categorie);

-- Requête
SELECT * FROM Produits WHERE Categorie = 'Électronique';
```

**Si les statistiques sont obsolètes :**
- Les stats disent : "Électronique = 90% des produits" (ancienne info)
- L'optimiseur pense : "90%, autant faire un Table Scan"
- Résultat : Votre index est ignoré ! ❌

**Si les statistiques sont à jour :**
- Les stats disent : "Électronique = 5% des produits" (info actuelle)
- L'optimiseur pense : "5%, parfait pour un Index Seek"
- Résultat : Votre index est utilisé ! ✅

**Moral :** Un index sans bonnes statistiques est comme une Ferrari sans essence.

## Les statistiques multi-colonnes

### Au-delà d'une seule colonne

SQL Server peut créer des statistiques sur **plusieurs colonnes à la fois**. C'est particulièrement utile quand les colonnes sont **corrélées**.

### Exemple de corrélation

Imaginez une table de ventes :

```sql
CREATE TABLE Ventes (
    VenteID INT,
    Pays VARCHAR(50),
    Ville VARCHAR(50),
    Montant DECIMAL(10,2)
);
```

**Corrélation évidente :**
- Si Pays = 'France', alors Ville peut être 'Paris', 'Lyon', 'Marseille'
- Si Pays = 'Espagne', alors Ville peut être 'Madrid', 'Barcelone'
- Paris n'existe pas en Espagne dans cette table !

### Problème sans statistiques multi-colonnes

```sql
SELECT *
FROM Ventes
WHERE Pays = 'France'
  AND Ville = 'Madrid';  -- Impossible !
```

**Avec seulement des statistiques séparées :**
- Stats sur Pays : France = 40% des lignes
- Stats sur Ville : Madrid = 15% des lignes
- SQL Server estime : 40% × 15% = 6% des lignes

**En réalité :**
- Résultat : 0 lignes (Madrid n'est pas en France !)

L'estimation est complètement fausse car SQL Server suppose que Pays et Ville sont **indépendants**.

### Solution : Statistiques multi-colonnes

Avec un index composite ou des statistiques multi-colonnes :

```sql
CREATE INDEX IX_Ventes_Pays_Ville ON Ventes(Pays, Ville);
```

SQL Server comprend maintenant la **corrélation** :
- France + Paris = 25% des lignes
- France + Lyon = 10% des lignes
- France + Madrid = 0% des lignes ✅

L'estimation devient précise !

## Conclusion

Les statistiques sont le **fondement** de l'optimisation des requêtes dans SQL Server. Elles permettent à l'optimiseur de :

1. **Estimer** combien de lignes seront traitées
2. **Choisir** les meilleurs opérateurs (Seek vs Scan, type de jointure)
3. **Allouer** la mémoire appropriée
4. **Décider** si le parallélisme est justifié

Sans statistiques, ou avec des statistiques obsolètes, même le meilleur code SQL et les meilleurs index ne peuvent pas fonctionner de manière optimale.

### Récapitulatif des points clés

**Ce que sont les statistiques :**
- Des informations sur la distribution des données
- Nombre de lignes, valeurs distinctes, histogrammes
- Créées automatiquement par SQL Server

**Pourquoi elles sont essentielles :**
- L'optimiseur s'appuie sur elles pour prendre des décisions
- Des statistiques précises = des plans d'exécution optimaux
- Des statistiques obsolètes = des performances catastrophiques

**Comment les maintenir :**
- SQL Server les met à jour automatiquement (mais pas toujours assez vite)
- Vous pouvez les mettre à jour manuellement si nécessaire
- Surveillez les écarts entre estimations et réalité dans les plans

**L'impact sur vos requêtes :**
- Choix d'opérateurs (Seek, Scan, type de jointure)
- Utilisation ou non des index
- Allocation mémoire
- Performance globale

Dans les sections suivantes, nous verrons **comment créer, mettre à jour et analyser les statistiques** de manière pratique pour garantir que votre base de données fonctionne toujours de manière optimale.

---

**Points à retenir :**
- Les statistiques sont les "yeux" de l'optimiseur de requêtes
- Elles contiennent des informations sur la distribution des données (histogrammes, densité, nombre de lignes)
- L'optimiseur utilise les statistiques pour estimer le nombre de lignes et choisir le meilleur plan
- Des statistiques obsolètes peuvent causer des pertes de performance de 10× à 100× ou plus
- SQL Server crée et met à jour les statistiques automatiquement, mais pas toujours assez rapidement
- Surveillez les écarts entre "Estimated Rows" et "Actual Rows" dans les plans d'exécution
- Un bon index avec de mauvaises statistiques peut être ignoré par SQL Server
