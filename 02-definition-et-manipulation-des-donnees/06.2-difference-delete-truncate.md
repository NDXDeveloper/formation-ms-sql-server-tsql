# 2.6.2 Différence entre DELETE et TRUNCATE

## Introduction

Lorsqu'on souhaite supprimer des données d'une table, SQL Server propose deux commandes principales : **DELETE** et **TRUNCATE**. À première vue, elles peuvent sembler similaires puisqu'elles suppriment toutes deux des lignes, mais en réalité, elles fonctionnent de manière **très différente** et ont des cas d'usage distincts.

Comprendre ces différences est essentiel pour choisir le bon outil selon votre situation. Utiliser TRUNCATE quand DELETE est nécessaire (ou inversement) peut causer des problèmes majeurs ou des pertes de données.

Dans cette section, nous allons explorer en détail les différences entre ces deux commandes, leurs avantages et inconvénients respectifs, et apprendre quand utiliser l'une plutôt que l'autre.

---

## Qu'est-ce que TRUNCATE ?

### Définition

**TRUNCATE TABLE** est une commande DDL (Data Definition Language) qui **vide complètement une table** en supprimant toutes ses lignes de manière extrêmement rapide et efficace.

**Syntaxe :**
```sql
TRUNCATE TABLE nom_table;
```

**Caractéristiques principales :**
- Supprime **TOUTES** les lignes de la table (pas de clause WHERE possible)
- Très rapide, même sur des tables volumineuses
- Réinitialise les compteurs IDENTITY à leur valeur de départ
- Utilise peu de ressources (minimal logging)
- Ne peut pas être utilisée si la table a des contraintes de clé étrangère

### Analogie du monde réel

Imaginez que vous vouliez vider votre garage :

**DELETE (avec WHERE) :**
- Vous sortez les objets un par un selon des critères
- "Je garde les outils, je jette seulement les vieux cartons"
- Travail précis mais peut être long

**DELETE (sans WHERE) :**
- Vous sortez tous les objets un par un
- Vous videz tout mais c'est méthodique
- Long et enregistre chaque objet sorti

**TRUNCATE :**
- Vous utilisez un camion pour tout vider d'un coup
- Rapide et efficace
- Mais c'est tout ou rien, pas de tri possible

## DELETE vs TRUNCATE : Les différences fondamentales

### Tableau comparatif rapide

| Aspect | DELETE | TRUNCATE |
|--------|--------|----------|
| **Type** | DML (Data Manipulation Language) | DDL (Data Definition Language) |
| **Clause WHERE** | ✅ Possible (sélectif) | ❌ Impossible (tout ou rien) |
| **Vitesse** | ⚠️ Plus lent | ✅ Très rapide |
| **Logging** | ⚠️ Chaque ligne enregistrée | ✅ Minimal |
| **IDENTITY** | ⚠️ Conserve la valeur actuelle | ✅ Réinitialise à la valeur de départ |
| **Triggers** | ✅ Déclenche les triggers DELETE | ❌ Ne déclenche PAS les triggers |
| **Transactions** | ✅ Peut être annulé (ROLLBACK) | ✅ Peut être annulé (ROLLBACK) |
| **Contraintes FK** | ✅ Fonctionne si table enfant | ❌ Erreur si table référencée |
| **Permissions** | ⚠️ Requiert DELETE | ⚠️ Requiert ALTER TABLE |
| **Espace disque** | ⚠️ Libéré progressivement | ✅ Libéré immédiatement |

## Différence 1 : Clause WHERE

### DELETE : Suppression sélective possible

```sql
-- DELETE peut avoir une clause WHERE
DELETE FROM Clients
WHERE EstActif = 0;  -- Supprime seulement les clients inactifs

DELETE FROM Logs
WHERE DateLog < DATEADD(DAY, -90, GETDATE());  -- Supprime les logs > 90 jours

DELETE FROM Produits
WHERE Stock = 0 AND DateAjout < '2020-01-01';  -- Suppression conditionnelle
```

**Avantage :** Contrôle précis sur ce qui est supprimé.

### TRUNCATE : Tout ou rien

```sql
-- TRUNCATE supprime TOUJOURS toute la table
TRUNCATE TABLE Logs;  -- Supprime TOUS les logs

-- ❌ ERREUR : TRUNCATE ne peut pas avoir de WHERE
TRUNCATE TABLE Logs WHERE DateLog < '2023-01-01';
-- Msg 156: Incorrect syntax near the keyword 'WHERE'.
```

**Limitation :** Impossible de filtrer, c'est tout ou rien.

### Exemple comparatif

```sql
-- Table de 1 million de lignes
CREATE TABLE Transactions (
    TransactionID INT,
    DateTransaction DATE,
    Montant DECIMAL(10, 2),
    Statut NVARCHAR(20)
);

-- Scénario 1 : Supprimer les transactions de 2023
-- Seule option : DELETE
DELETE FROM Transactions
WHERE YEAR(DateTransaction) = 2023;
-- Résultat : 250 000 lignes supprimées, 750 000 conservées

-- Scénario 2 : Vider complètement la table
-- Option A : DELETE (plus lent)
DELETE FROM Transactions;  -- Supprime 1 million de lignes une par une

-- Option B : TRUNCATE (plus rapide)
TRUNCATE TABLE Transactions;  -- Vide la table instantanément
```

**Règle :** Si vous avez besoin d'un WHERE, vous DEVEZ utiliser DELETE.

## Différence 2 : Performance et vitesse

### DELETE : Plus lent (enregistrement complet)

```sql
-- DELETE sur une grosse table : LENT
DELETE FROM LogsSysteme;  -- 10 millions de lignes
-- Peut prendre plusieurs heures !
-- Chaque suppression est enregistrée dans le log de transaction
```

**Pourquoi DELETE est lent :**
1. Chaque ligne est lue
2. Chaque suppression est enregistrée dans le log de transaction
3. Les index sont mis à jour pour chaque ligne
4. Les triggers DELETE sont exécutés pour chaque ligne (ou lot)
5. Les verrous sont maintenus pendant toute l'opération

### TRUNCATE : Très rapide (minimal logging)

```sql
-- TRUNCATE sur la même table : RAPIDE
TRUNCATE TABLE LogsSysteme;  -- 10 millions de lignes
-- Quelques secondes seulement !
-- Enregistre seulement la désallocation des pages de données
```

**Pourquoi TRUNCATE est rapide :**
1. Ne lit pas chaque ligne individuellement
2. Désalloue simplement les pages de données
3. Minimal logging (enregistre seulement la désallocation)
4. Pas d'exécution de triggers
5. Opération globale sur la structure

### Comparaison de performance réelle

```sql
-- Test sur une table de 5 millions de lignes

-- DELETE : ~45 minutes
DECLARE @Start DATETIME = GETDATE();
DELETE FROM TableTest;
SELECT DATEDIFF(SECOND, @Start, GETDATE()) AS SecondesDelete;
-- Résultat : 2700 secondes (45 minutes)

-- Recréer la table et les données pour le test suivant

-- TRUNCATE : ~3 secondes
DECLARE @Start DATETIME = GETDATE();
TRUNCATE TABLE TableTest;
SELECT DATEDIFF(SECOND, @Start, GETDATE()) AS SecondesTruncate;
-- Résultat : 3 secondes
```

**Gain de performance : 900x plus rapide !**

## Différence 3 : Réinitialisation IDENTITY

### DELETE : Conserve le compteur IDENTITY

```sql
-- Créer une table avec IDENTITY
CREATE TABLE Commandes (
    CommandeID INT IDENTITY(1,1) PRIMARY KEY,
    DateCommande DATE
);

-- Insérer quelques lignes
INSERT INTO Commandes (DateCommande) VALUES ('2024-01-01');
INSERT INTO Commandes (DateCommande) VALUES ('2024-01-02');
INSERT INTO Commandes (DateCommande) VALUES ('2024-01-03');

SELECT * FROM Commandes;
/*
CommandeID | DateCommande
-----------|-------------
1          | 2024-01-01
2          | 2024-01-02
3          | 2024-01-03
*/

-- Supprimer avec DELETE
DELETE FROM Commandes;

-- Insérer une nouvelle ligne
INSERT INTO Commandes (DateCommande) VALUES ('2024-01-04');

SELECT * FROM Commandes;
/*
CommandeID | DateCommande
-----------|-------------
4          | 2024-01-04    ← Commence à 4, pas à 1 !
*/
```

**Comportement :** DELETE conserve le compteur IDENTITY (continue à 4).

### TRUNCATE : Réinitialise le compteur IDENTITY

```sql
-- Même table avec des données
INSERT INTO Commandes (DateCommande) VALUES ('2024-01-05');
INSERT INTO Commandes (DateCommande) VALUES ('2024-01-06');

SELECT * FROM Commandes;
/*
CommandeID | DateCommande
-----------|-------------
4          | 2024-01-04
5          | 2024-01-05
6          | 2024-01-06
*/

-- Vider avec TRUNCATE
TRUNCATE TABLE Commandes;

-- Insérer une nouvelle ligne
INSERT INTO Commandes (DateCommande) VALUES ('2024-01-07');

SELECT * FROM Commandes;
/*
CommandeID | DateCommande
-----------|-------------
1          | 2024-01-07    ← Repart à 1 !
*/
```

**Comportement :** TRUNCATE réinitialise le compteur IDENTITY à sa valeur de départ.

### Quand c'est important

```sql
-- Scénario : Table temporaire réutilisée
CREATE TABLE #TempCalculations (
    ID INT IDENTITY(1,1),
    Resultat DECIMAL(10, 2)
);

-- Processus 1
INSERT INTO #TempCalculations (Resultat) VALUES (100), (200), (300);
-- IDs : 1, 2, 3

-- Nettoyer pour le processus suivant
DELETE FROM #TempCalculations;  -- Les IDs continuent

-- Processus 2
INSERT INTO #TempCalculations (Resultat) VALUES (400), (500);
-- IDs : 4, 5  ← Commence à 4, pas idéal

-- Meilleure approche avec TRUNCATE
TRUNCATE TABLE #TempCalculations;

-- Processus 3
INSERT INTO #TempCalculations (Resultat) VALUES (600), (700);
-- IDs : 1, 2  ← Repart à 1, comme prévu
```

## Différence 4 : Triggers

### DELETE : Déclenche les triggers

```sql
-- Créer un trigger sur DELETE
CREATE TRIGGER TR_Clients_Delete
ON Clients
AFTER DELETE
AS
BEGIN
    -- Archiver les clients supprimés
    INSERT INTO ClientsArchive (ClientID, Nom, DateSuppression)
    SELECT ClientID, Nom, GETDATE()
    FROM DELETED;

    PRINT 'Trigger exécuté : ' + CAST(@@ROWCOUNT AS VARCHAR) + ' clients archivés';
END;

-- Supprimer avec DELETE
DELETE FROM Clients WHERE ClientID = 1;
-- Sortie : "Trigger exécuté : 1 clients archivés"
-- Le trigger s'exécute et archive le client
```

### TRUNCATE : Ne déclenche PAS les triggers

```sql
-- Vider avec TRUNCATE
TRUNCATE TABLE Clients;
-- Aucune sortie du trigger
-- Les clients sont supprimés SANS archivage !
```

**Attention :** Si vous avez des triggers DELETE importants (archivage, audit, etc.), vous DEVEZ utiliser DELETE, pas TRUNCATE.

## Différence 5 : Contraintes de clé étrangère

### DELETE : Fonctionne avec les contraintes

```sql
-- Tables parent-enfant
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Nom NVARCHAR(100)
);

CREATE TABLE Commandes (
    CommandeID INT PRIMARY KEY,
    ClientID INT FOREIGN KEY REFERENCES Clients(ClientID),
    DateCommande DATE
);

-- Insérer des données
INSERT INTO Clients VALUES (1, N'Marie'), (2, N'Pierre');
INSERT INTO Commandes VALUES (1, 1, '2024-01-01'), (2, 2, '2024-01-02');

-- ✅ DELETE fonctionne si on respecte l'ordre
DELETE FROM Commandes;  -- D'abord les enfants
DELETE FROM Clients;    -- Puis les parents
-- Succès !
```

### TRUNCATE : Bloqué par les contraintes

```sql
-- Réinsérer les données
INSERT INTO Clients VALUES (1, N'Marie'), (2, N'Pierre');
INSERT INTO Commandes VALUES (1, 1, '2024-01-01'), (2, 2, '2024-01-02');

-- ❌ TRUNCATE échoue si la table est référencée
TRUNCATE TABLE Clients;
/*
Msg 4712: Cannot truncate table 'Clients' because it is being referenced
by a FOREIGN KEY constraint.
*/

-- ✅ Mais fonctionne sur la table enfant
TRUNCATE TABLE Commandes;  -- Succès
```

**Règle :** TRUNCATE ne peut pas être utilisé sur une table référencée par une clé étrangère, même si la table enfant est vide.

### Contournement (si vraiment nécessaire)

```sql
-- Si vous devez absolument utiliser TRUNCATE sur une table parent

-- Option 1 : Désactiver temporairement les contraintes (DANGEREUX !)
ALTER TABLE Commandes NOCHECK CONSTRAINT ALL;
TRUNCATE TABLE Clients;
ALTER TABLE Commandes CHECK CONSTRAINT ALL;

-- Option 2 : Supprimer et recréer les contraintes (complexe)
-- Option 3 : Utiliser DELETE à la place (recommandé)
DELETE FROM Clients;
```

**Recommandation :** Utilisez DELETE si vous avez des contraintes de clé étrangère.

## Différence 6 : Logging et espace de transaction

### DELETE : Logging complet

```sql
-- DELETE enregistre chaque ligne dans le log de transaction
DELETE FROM TableVolumineuse;  -- 10 millions de lignes

-- Impact :
-- - Log de transaction devient énorme
-- - Risque de saturation de l'espace disque du log
-- - Récupération possible ligne par ligne en cas de ROLLBACK
```

**Conséquence :** Le log de transaction peut devenir très volumineux.

### TRUNCATE : Minimal logging

```sql
-- TRUNCATE enregistre seulement la désallocation des pages
TRUNCATE TABLE TableVolumineuse;  -- 10 millions de lignes

-- Impact :
-- - Log de transaction reste petit
-- - Espace disque économisé
-- - Récupération en bloc (tout ou rien) en cas de ROLLBACK
```

**Avantage :** Beaucoup moins d'espace utilisé dans le log de transaction.

---

## Différence 7 : Espace disque libéré

### DELETE : Espace libéré progressivement

```sql
-- DELETE ne libère pas immédiatement tout l'espace
DELETE FROM GrosseTable;

-- L'espace reste alloué à la table
-- Pour libérer l'espace :
ALTER TABLE GrosseTable REBUILD;
-- ou
DBCC SHRINKFILE(fichier_donnees);
```

### TRUNCATE : Espace libéré immédiatement

```sql
-- TRUNCATE libère l'espace immédiatement
TRUNCATE TABLE GrosseTable;

-- L'espace est immédiatement disponible pour d'autres tables
-- Pas besoin de REBUILD ou SHRINK
```

## Quand utiliser DELETE ?

### Utilisez DELETE quand :

#### 1. Vous avez besoin d'une clause WHERE

```sql
-- ✅ DELETE : suppression sélective
DELETE FROM Logs
WHERE DateLog < DATEADD(DAY, -90, GETDATE());

DELETE FROM Clients
WHERE EstActif = 0 AND DerniereConnexion < '2023-01-01';
```

#### 2. La table a des contraintes de clé étrangère

```sql
-- ✅ DELETE : fonctionne avec les FK
DELETE FROM Commandes WHERE ClientID = 1;
DELETE FROM Clients WHERE ClientID = 1;
```

#### 3. Vous avez des triggers importants

```sql
-- ✅ DELETE : déclenche les triggers pour archivage
DELETE FROM Produits WHERE EstObsolete = 1;
-- Les triggers archivent les produits supprimés
```

#### 4. Vous voulez conserver la valeur IDENTITY

```sql
-- ✅ DELETE : garde le compteur IDENTITY
DELETE FROM SessionsTemporaires;
-- Le prochain ID sera 1001 (si c'était à 1000)
```

#### 5. Vous êtes dans une transaction complexe

```sql
-- ✅ DELETE : s'intègre bien dans les transactions complexes
BEGIN TRANSACTION;
    DELETE FROM LignesCommande WHERE CommandeID = 123;
    DELETE FROM Commandes WHERE CommandeID = 123;
    UPDATE Clients SET NombreCommandes = NombreCommandes - 1;
COMMIT;
```

---

## Quand utiliser TRUNCATE ?

### Utilisez TRUNCATE quand :

#### 1. Vous voulez vider complètement la table

```sql
-- ✅ TRUNCATE : vider une table de logs
TRUNCATE TABLE LogsDebug;

-- ✅ TRUNCATE : réinitialiser une table de cache
TRUNCATE TABLE CacheTemporaire;
```

#### 2. Performance critique (grosse table)

```sql
-- ✅ TRUNCATE : très rapide sur grosse table
TRUNCATE TABLE HistoriqueNavigation;  -- 100 millions de lignes en 2 secondes
```

#### 3. Vous voulez réinitialiser IDENTITY

```sql
-- ✅ TRUNCATE : repart à 1
TRUNCATE TABLE TempCalculations;
INSERT INTO TempCalculations (Valeur) VALUES (100);
-- ID = 1 (repart du début)
```

#### 4. La table n'a PAS de contraintes FK

```sql
-- ✅ TRUNCATE : table indépendante
TRUNCATE TABLE StatistiquesJournalieres;
```

#### 5. Pas de triggers à exécuter

```sql
-- ✅ TRUNCATE : pas besoin d'archivage
TRUNCATE TABLE SessionsExpirees;
```

## Exemples pratiques comparés

### Exemple 1 : Nettoyage de logs

```sql
-- Scénario A : Supprimer les logs de plus de 30 jours
-- → Seule option : DELETE (besoin de WHERE)
DELETE FROM Logs
WHERE DateLog < DATEADD(DAY, -30, GETDATE());

-- Scénario B : Vider complètement les logs de debug
-- → Meilleure option : TRUNCATE (plus rapide)
TRUNCATE TABLE LogsDebug;
```

### Exemple 2 : Réinitialisation de table temporaire

```sql
-- Table de calculs temporaires sans dépendances
CREATE TABLE #TempResults (
    ID INT IDENTITY(1,1),
    Calcul DECIMAL(18, 2)
);

-- Processus 1
INSERT INTO #TempResults (Calcul) VALUES (100), (200), (300);

-- Nettoyer pour réutiliser
-- ❌ Mauvais choix : DELETE (IDs continuent)
DELETE FROM #TempResults;

-- ✅ Bon choix : TRUNCATE (IDs repartent à 1)
TRUNCATE TABLE #TempResults;

-- Processus 2
INSERT INTO #TempResults (Calcul) VALUES (400), (500);
-- IDs : 1, 2 (comme souhaité)
```

### Exemple 3 : Table avec clés étrangères

```sql
-- Tables liées
CREATE TABLE Categories (
    CategorieID INT PRIMARY KEY,
    Nom NVARCHAR(100)
);

CREATE TABLE Produits (
    ProduitID INT PRIMARY KEY,
    CategorieID INT FOREIGN KEY REFERENCES Categories(CategorieID),
    Nom NVARCHAR(200)
);

-- ❌ TRUNCATE échoue sur Categories (référencée par FK)
TRUNCATE TABLE Categories;
-- Erreur : Cannot truncate table 'Categories'...

-- ✅ DELETE fonctionne (si on respecte l'ordre)
DELETE FROM Produits;    -- D'abord les enfants
DELETE FROM Categories;  -- Puis les parents
```

### Exemple 4 : Table avec trigger d'archivage

```sql
-- Trigger qui archive les suppressions
CREATE TRIGGER TR_Clients_Archive
ON Clients
AFTER DELETE
AS
BEGIN
    INSERT INTO ClientsArchive
    SELECT *, GETDATE() FROM DELETED;
END;

-- ❌ TRUNCATE ignore le trigger (pas d'archivage)
TRUNCATE TABLE Clients;
-- Les clients sont supprimés SANS archivage !

-- ✅ DELETE déclenche le trigger (archivage)
DELETE FROM Clients;
-- Les clients sont archivés avant suppression
```

## Pièges courants et erreurs

### Piège 1 : Utiliser TRUNCATE avec WHERE

```sql
-- ❌ Erreur de syntaxe
TRUNCATE TABLE Logs WHERE DateLog < '2023-01-01';
-- Msg 156: Incorrect syntax near the keyword 'WHERE'.

-- ✅ Solution : utiliser DELETE
DELETE FROM Logs WHERE DateLog < '2023-01-01';
```

### Piège 2 : TRUNCATE sur table référencée

```sql
-- ❌ Erreur même si la table enfant est vide
TRUNCATE TABLE Clients;  -- Référencée par Commandes
-- Msg 4712: Cannot truncate table 'Clients'...

-- ✅ Solution 1 : utiliser DELETE
DELETE FROM Clients;

-- ✅ Solution 2 : vider d'abord les enfants avec TRUNCATE
TRUNCATE TABLE Commandes;
DELETE FROM Clients;  -- Puis DELETE sur parent
```

### Piège 3 : Oublier la réinitialisation IDENTITY

```sql
-- Problème : vous voulez que les IDs repartent à 1
CREATE TABLE Temp (ID INT IDENTITY(1,1), Valeur INT);

INSERT INTO Temp VALUES (100), (200), (300);
-- IDs : 1, 2, 3

-- ❌ DELETE conserve le compteur
DELETE FROM Temp;
INSERT INTO Temp VALUES (400);
-- ID : 4 (au lieu de 1)

-- ✅ TRUNCATE réinitialise
TRUNCATE TABLE Temp;
INSERT INTO Temp VALUES (400);
-- ID : 1 (comme souhaité)

-- ✅ Alternative : réinitialiser manuellement avec DELETE
DELETE FROM Temp;
DBCC CHECKIDENT ('Temp', RESEED, 0);
INSERT INTO Temp VALUES (400);
-- ID : 1
```

### Piège 4 : Performance sur petite table

```sql
-- Sur une petite table (< 1000 lignes), la différence est négligeable
CREATE TABLE PetiteTable (ID INT, Valeur INT);
INSERT INTO PetiteTable SELECT TOP 100 n, n*2 FROM Nombres;

-- DELETE : ~0.01 seconde
DELETE FROM PetiteTable;

-- TRUNCATE : ~0.01 seconde
TRUNCATE TABLE PetiteTable;

-- La différence n'est significative qu'à partir de milliers/millions de lignes
```

### Piège 5 : Oublier les triggers

```sql
-- Vous avez un trigger d'audit
CREATE TRIGGER TR_Produits_Audit
ON Produits
AFTER DELETE
AS
BEGIN
    INSERT INTO AuditLog (Action, DateAction)
    VALUES ('Suppression produit', GETDATE());
END;

-- ❌ TRUNCATE ignore le trigger
TRUNCATE TABLE Produits;
-- Aucun enregistrement dans AuditLog !

-- ✅ DELETE déclenche le trigger
DELETE FROM Produits;
-- Enregistrement dans AuditLog
```

## Permissions requises

### DELETE : Permission DELETE

```sql
-- Pour exécuter DELETE, besoin de :
GRANT DELETE ON Clients TO MonUtilisateur;
```

### TRUNCATE : Permission ALTER TABLE

```sql
-- Pour exécuter TRUNCATE, besoin de :
GRANT ALTER ON Clients TO MonUtilisateur;

-- ALTER est une permission plus élevée que DELETE
-- TRUNCATE est considéré comme une opération DDL
```

**Impact :** Un utilisateur avec permission DELETE ne peut pas forcément faire TRUNCATE.

---

## Transactions et ROLLBACK

### Les deux peuvent être annulés

```sql
-- DELETE dans une transaction
BEGIN TRANSACTION;
    DELETE FROM Clients;
    -- Vérifier...
    ROLLBACK;  -- ✅ Annulé

-- TRUNCATE dans une transaction
BEGIN TRANSACTION;
    TRUNCATE TABLE Clients;
    -- Vérifier...
    ROLLBACK;  -- ✅ Annulé aussi
```

**Important :** Même si TRUNCATE est DDL, il peut être annulé dans SQL Server (contrairement à d'autres SGBD).

## Tableau de décision rapide

| Critère | Utilisez DELETE | Utilisez TRUNCATE |
|---------|-----------------|-------------------|
| **Besoin de WHERE** | ✅ Oui | ❌ Non |
| **Table volumineuse (> 1M lignes)** | ❌ Non | ✅ Oui |
| **Table avec FK** | ✅ Oui | ❌ Non |
| **Triggers importants** | ✅ Oui | ❌ Non |
| **Réinitialiser IDENTITY** | ❌ Non* | ✅ Oui |
| **Permissions limitées (DELETE uniquement)** | ✅ Oui | ❌ Non |
| **Audit/Archivage requis** | ✅ Oui | ❌ Non |
| **Performance critique** | ❌ Non | ✅ Oui |
| **Table temporaire** | ❌ Non | ✅ Oui |

*Sauf si vous utilisez DBCC CHECKIDENT après DELETE

## Recommandations et bonnes pratiques

### Règle générale

```
Si vous avez UN DOUTE, utilisez DELETE.
TRUNCATE seulement si vous êtes CERTAIN que :
- Vous voulez tout supprimer
- Pas de contraintes FK
- Pas de triggers importants
- Réinitialiser IDENTITY est OK
```

### Checklist avant TRUNCATE

Avant d'utiliser TRUNCATE, vérifiez :

- [ ] Je veux vraiment supprimer **TOUTES** les lignes
- [ ] La table n'est **PAS** référencée par une clé étrangère
- [ ] Il n'y a **PAS** de triggers DELETE importants
- [ ] Réinitialiser IDENTITY est acceptable
- [ ] J'ai les permissions ALTER TABLE
- [ ] J'ai testé en développement d'abord
- [ ] J'ai une sauvegarde récente

### Pour les débutants

**Recommandation simple :**
- Utilisez **DELETE** par défaut
- Utilisez **TRUNCATE** uniquement pour vider des tables temporaires ou de cache
- En cas de doute, demandez à un collègue expérimenté

## Exemples de scénarios complets

### Scénario 1 : Nettoyage quotidien de logs

```sql
-- Table de logs avec millions de lignes par jour
-- Besoin : garder 30 jours, supprimer le reste

-- ❌ Mauvais choix : TRUNCATE (perd tout)
TRUNCATE TABLE Logs;

-- ✅ Bon choix : DELETE (garde les 30 derniers jours)
DELETE FROM Logs
WHERE DateLog < DATEADD(DAY, -30, GETDATE());
```

### Scénario 2 : Réinitialisation de table de test

```sql
-- Table de test sans dépendances
-- Besoin : vider entre chaque test, IDs à 1

-- ❌ Mauvais choix : DELETE (IDs continuent)
DELETE FROM TableTest;

-- ✅ Bon choix : TRUNCATE (IDs repartent à 1)
TRUNCATE TABLE TableTest;
```

### Scénario 3 : Purge avec archivage

```sql
-- Besoin : archiver puis supprimer les vieilles commandes

-- ✅ Utiliser DELETE avec trigger ou processus manuel
-- Option 1 : Trigger automatique
CREATE TRIGGER TR_Commandes_Archive
ON Commandes AFTER DELETE
AS
BEGIN
    INSERT INTO CommandesArchive
    SELECT *, GETDATE() FROM DELETED;
END;

DELETE FROM Commandes WHERE DateCommande < '2020-01-01';

-- Option 2 : Archivage manuel
INSERT INTO CommandesArchive
SELECT *, GETDATE() FROM Commandes
WHERE DateCommande < '2020-01-01';

DELETE FROM Commandes WHERE DateCommande < '2020-01-01';

-- ❌ TRUNCATE ne convient PAS (pas d'archivage)
```

### Scénario 4 : Tables liées parent-enfant

```sql
-- Besoin : vider complètement une base de test

-- ❌ TRUNCATE échoue sur les parents
TRUNCATE TABLE Clients;  -- Erreur FK

-- ✅ Solution mixte : TRUNCATE enfants, DELETE parents
TRUNCATE TABLE Commandes;    -- Rapide
TRUNCATE TABLE Factures;     -- Rapide
DELETE FROM Clients;          -- Nécessaire (a des FK vers elle)
```

---

## Points clés à retenir

✅ **DELETE** : Flexible, sélectif, compatible avec tout, mais plus lent

✅ **TRUNCATE** : Très rapide, mais tout ou rien et limitations importantes

✅ **WHERE obligatoire ?** → DELETE uniquement

✅ **Grosse table à vider entièrement ?** → TRUNCATE si pas de FK

✅ **Contraintes FK ?** → DELETE uniquement

✅ **Triggers importants ?** → DELETE uniquement

✅ **Réinitialiser IDENTITY ?** → TRUNCATE automatiquement, DELETE avec DBCC CHECKIDENT

✅ **Les deux peuvent être annulés** avec ROLLBACK

⚠️ **En cas de doute** → Utilisez DELETE (plus sûr)

## Conclusion

**DELETE** et **TRUNCATE** sont deux outils différents pour deux besoins différents :

**DELETE :**
- ✅ Outil universel et flexible
- ✅ Fonctionne dans tous les cas
- ⚠️ Plus lent sur grosses tables
- 💡 Utilisez par défaut

**TRUNCATE :**
- ✅ Ultra-rapide pour vider une table
- ✅ Réinitialise automatiquement IDENTITY
- ⚠️ Nombreuses limitations (pas de WHERE, pas de FK, pas de triggers)
- 💡 Utilisez pour des cas spécifiques uniquement

**Règle d'or :**
> Si vous hésitez entre DELETE et TRUNCATE, choisissez DELETE.
> TRUNCATE uniquement quand vous êtes certain que c'est approprié.

Dans la plupart des cas d'usage quotidien, **DELETE** sera votre choix par défaut car il offre flexibilité et sécurité. Réservez **TRUNCATE** aux situations où vous avez vraiment besoin de performance et où vous pouvez accepter ses limitations.
