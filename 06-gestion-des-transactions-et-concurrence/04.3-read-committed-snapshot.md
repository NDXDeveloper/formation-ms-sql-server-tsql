# 6.4.3 READ COMMITTED SNAPSHOT (RCSI)

## Introduction

Nous avons vu que **READ COMMITTED** (le niveau par défaut) bloque les dirty reads en utilisant des verrous, ce qui peut créer des situations de blocage où les lecteurs doivent attendre les écrivains. **READ COMMITTED SNAPSHOT (RCSI)** est une variante moderne qui offre les **mêmes garanties** de cohérence, mais en utilisant une approche complètement différente : le **versioning de lignes** (row versioning).

Cette approche permet aux **lecteurs de ne jamais être bloqués** par les écrivains, améliorant considérablement les performances dans les environnements à forte concurrence.

---

## Qu'est-ce que READ COMMITTED SNAPSHOT ?

### Définition

**READ COMMITTED SNAPSHOT (RCSI)** est une variante de READ COMMITTED qui garantit qu'une transaction ne lit **que des données validées**, mais au lieu d'utiliser des verrous, elle utilise le **versioning de lignes** stocké dans **tempdb** pour fournir aux lecteurs une vue cohérente des données.

### Caractéristiques principales

| Caractéristique | RCSI |
|-----------------|------|
| **Dirty Reads** | ❌ Bloquées |
| **Non-Repeatable Reads** | ✅ Autorisées |
| **Phantom Reads** | ✅ Autorisées |
| **Verrous de lecture** | ❌ Aucun |
| **Mécanisme** | Versioning de lignes (tempdb) |
| **Blocage en lecture** | ❌ Jamais |
| **Performances lecture** | ⭐⭐⭐⭐⭐ Excellentes |
| **Overhead tempdb** | ⚠️ Modéré |
| **Configuration** | Au niveau de la **base de données** |

### Analogie : La photographie

Imaginez une bibliothèque où :
- Quand quelqu'un consulte un livre (lecture), on lui donne une **photographie** du livre tel qu'il était à ce moment-là
- Pendant qu'il regarde la photo, d'autres personnes peuvent **modifier le livre original** sans le bloquer
- Le lecteur voit toujours la version "figée" dans sa photo, même si le livre original change
- Quand il a terminé, la photo est détruite

C'est exactement ainsi que fonctionne RCSI : SQL Server crée des "photographies" (versions) des données pour les lecteurs, permettant aux écrivains de modifier les originaux sans blocage.

## Différence fondamentale avec READ COMMITTED classique

### READ COMMITTED classique (par défaut)

**Mécanisme : Verrous**

```
Transaction A (écriture)           Transaction B (lecture)
────────────────────────────────────────────────────────
BEGIN TRANSACTION
UPDATE Produits
SET Prix = 150
WHERE ProduitID = 1
-- Verrou exclusif placé
                                   SELECT Prix FROM Produits
                                   WHERE ProduitID = 1
                                   -- BLOQUÉE ! Doit attendre A
COMMIT
-- Verrou libéré
                                   -- Maintenant peut lire : 150
```

**Résultat :** Le lecteur est **bloqué** pendant que l'écrivain travaille.

### READ COMMITTED SNAPSHOT (RCSI)

**Mécanisme : Versioning**

```
Transaction A (écriture)           Transaction B (lecture RCSI)
────────────────────────────────────────────────────────
BEGIN TRANSACTION
UPDATE Produits
SET Prix = 150
WHERE ProduitID = 1
-- Version originale (100)
-- copiée dans tempdb
-- Nouvelle version (150)
-- dans la table principale
                                   SELECT Prix FROM Produits
                                   WHERE ProduitID = 1
                                   -- Lit la version de tempdb : 100
                                   -- PAS DE BLOCAGE !
COMMIT
-- Version de tempdb supprimée
```

**Résultat :** Le lecteur n'est **jamais bloqué** et lit la dernière version **validée**.

## Le concept de versioning de lignes (Row Versioning)

### Comment ça fonctionne

Quand RCSI est activé, voici ce qui se passe lors d'une modification :

**1. Avant la modification**
```
Table Produits (données principales)
┌──────────┬────────┬────────┐
│ ProduitID│  Nom   │  Prix  │
├──────────┼────────┼────────┤
│    1     │ Laptop │  100   │
└──────────┴────────┴────────┘
```

**2. Transaction commence à modifier**
```sql
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
```

**3. Version créée dans tempdb**
```
Table Produits (nouvelle version)
┌──────────┬────────┬────────┐
│ ProduitID│  Nom   │  Prix  │
├──────────┼────────┼────────┤
│    1     │ Laptop │  150   │ ← Nouvelle version (non validée)
└──────────┴────────┴────────┘

tempdb (version store)
┌──────────┬────────┬────────┬──────────┐
│ ProduitID│  Nom   │  Prix  │ Version  │
├──────────┼────────┼────────┼──────────┤
│    1     │ Laptop │  100   │ Timestamp│ ← Ancienne version (validée)
└──────────┴────────┴────────┴──────────┘
```

**4. Lecture pendant la modification**
```sql
-- Transaction de lecture
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Résultat : 100 (lu depuis tempdb, version validée)
```

**5. Après COMMIT**
```sql
COMMIT;
```

La version dans tempdb est supprimée car elle n'est plus nécessaire.

### Qui utilise quelle version ?

| Qui ? | Quelle version ? |
|-------|------------------|
| **Lecteurs** (SELECT) | Version dans **tempdb** (dernière version validée) |
| **Écrivains** (UPDATE/INSERT/DELETE) | Version dans la **table principale** (version actuelle) |

## Avantages de RCSI

### 1. Pas de blocage en lecture

**Le principal avantage :** Les lecteurs ne sont **jamais bloqués** par les écrivains.

```sql
-- Transaction A modifie 100 000 lignes (très lent)
BEGIN TRANSACTION;
UPDATE Produits SET Prix = Prix * 1.1;  -- Prend 30 secondes

-- Transaction B peut lire immédiatement (pas d'attente)
SELECT * FROM Produits WHERE Categorie = 'Electronique';
-- Résultat : Lit les anciennes valeurs depuis tempdb
-- PAS DE BLOCAGE, pas d'attente
```

### 2. Amélioration des performances en lecture

Dans les environnements avec **beaucoup de lectures** et **peu d'écritures**, RCSI améliore significativement les performances.

**Scénario typique : Site e-commerce**
- 1000 clients consultent le catalogue (lectures)
- 5 employés mettent à jour les stocks (écritures)

**Avec READ COMMITTED classique :**
```
Les 1000 clients peuvent être bloqués par les 5 mises à jour
→ Temps de réponse lent
→ Mauvaise expérience utilisateur
```

**Avec RCSI :**
```
Les 1000 clients lisent sans attendre
→ Temps de réponse rapide
→ Bonne expérience utilisateur
```

### 3. Réduction des deadlocks

Moins de verrous = moins de risque de deadlock (interblocage).

### 4. Comportement similaire à READ COMMITTED

RCSI offre les **mêmes garanties** que READ COMMITTED :
- ❌ Pas de dirty reads
- ✅ Non-repeatable reads autorisés
- ✅ Phantom reads autorisés

**Avantage :** Pas besoin de changer la logique applicative !

---

## Inconvénients de RCSI

### 1. Utilisation de tempdb

**Le coût :** Les anciennes versions sont stockées dans **tempdb**, ce qui peut :
- Augmenter la taille de tempdb
- Créer plus d'I/O (lectures/écritures disque)
- Nécessiter plus d'espace disque

```
Sans RCSI : tempdb = 1 GB
Avec RCSI (site e-commerce actif) : tempdb = 5-10 GB
```

### 2. Overhead sur les écritures

Chaque modification (UPDATE/DELETE) doit :
1. Copier l'ancienne version dans tempdb
2. Effectuer la modification
3. Maintenir le lien entre les versions

**Impact :** Les écritures peuvent être légèrement plus lentes (5-10%).

### 3. Cleanup des versions

SQL Server doit périodiquement **nettoyer** les anciennes versions dans tempdb quand elles ne sont plus nécessaires. Ce processus consomme des ressources.

### 4. Transactions longues problématiques

Si une transaction de **lecture longue** reste ouverte, SQL Server doit conserver les anciennes versions dans tempdb pour cette transaction, ce qui peut faire grossir tempdb de manière excessive.

```sql
-- ❌ PROBLÉMATIQUE
BEGIN TRANSACTION;

SELECT * FROM GrosseTable;  -- 10 millions de lignes

-- L'utilisateur part déjeuner pendant 2 heures
-- SQL Server doit conserver toutes les versions pendant 2 heures !
-- tempdb peut exploser

COMMIT;
```

## Activation de RCSI

### Important : Configuration au niveau de la base de données

RCSI n'est **pas un niveau d'isolation** que vous définissez au niveau de la transaction. C'est une **option de base de données** qui change le comportement de READ COMMITTED.

### Activer RCSI

```sql
-- Activer RCSI pour la base de données
ALTER DATABASE VotreBaseDeDonnees
SET READ_COMMITTED_SNAPSHOT ON;
```

**⚠️ Important :** Cette opération nécessite :
- Aucune autre connexion active sur la base (mode exclusif temporaire)
- Peut prendre du temps selon la taille de la base

### Vérifier si RCSI est activé

```sql
-- Vérifier l'état de RCSI
SELECT
    name,
    is_read_committed_snapshot_on
FROM sys.databases
WHERE name = 'VotreBaseDeDonnees';
```

### Désactiver RCSI

```sql
-- Désactiver RCSI (revenir au comportement par défaut)
ALTER DATABASE VotreBaseDeDonnees
SET READ_COMMITTED_SNAPSHOT OFF;
```

---

## Utilisation de RCSI

### Transparence pour l'application

Une fois RCSI activé, **aucun changement de code n'est nécessaire** !

```sql
-- Votre code reste identique
BEGIN TRANSACTION;

SELECT * FROM Produits WHERE Categorie = 'Electronique';

COMMIT;

-- Mais maintenant :
-- - Pas de verrous de lecture
-- - Utilise le versioning
-- - Pas de blocage
```

### Le niveau d'isolation est toujours READ COMMITTED

```sql
-- Vérifier le niveau d'isolation
SELECT
    CASE transaction_isolation_level
        WHEN 2 THEN 'ReadCommitted'
    END AS IsolationLevel
FROM sys.dm_exec_sessions
WHERE session_id = @@SPID;

-- Résultat : ReadCommitted
-- Mais le comportement est celui de RCSI (avec versioning)
```

## Comparaison détaillée

### RCSI vs READ COMMITTED classique

| Aspect | READ COMMITTED classique | RCSI |
|--------|-------------------------|------|
| **Mécanisme** | Verrous | Versioning (tempdb) |
| **Blocage lecture** | ✅ Possible | ❌ Jamais |
| **Dirty Reads** | ❌ Bloquées | ❌ Bloquées |
| **Non-Rep. Reads** | ✅ Autorisées | ✅ Autorisées |
| **Phantom Reads** | ✅ Autorisées | ✅ Autorisées |
| **Overhead tempdb** | ❌ Aucun | ✅ Modéré |
| **Performances lecture** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **Performances écriture** | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **Activation** | Par défaut | Option de base |

### RCSI vs SNAPSHOT (aperçu)

| Aspect | RCSI | SNAPSHOT |
|--------|------|----------|
| **Type** | Variante de READ COMMITTED | Niveau d'isolation distinct |
| **Non-Rep. Reads** | ✅ Autorisées | ❌ Bloquées |
| **Vue cohérente** | À chaque requête | Toute la transaction |
| **Usage** | Plus courant | Cas spécifiques |

## Exemple pratique complet

### Scénario : Système de gestion de stocks

**Problème avec READ COMMITTED classique :**

```sql
-- Transaction A : Inventaire (très long, 5 minutes)
BEGIN TRANSACTION;
UPDATE Produits
SET DerniereVerification = GETDATE()
WHERE Categorie = 'Electronique';  -- 100 000 produits
-- Prend 5 minutes

COMMIT;

-- Transaction B : Client consulte le catalogue
SELECT * FROM Produits WHERE Categorie = 'Electronique';
-- BLOQUÉE pendant 5 minutes !
-- Le client attend... et part
```

**Solution avec RCSI :**

```sql
-- 1. Activer RCSI (une fois, par l'administrateur)
ALTER DATABASE BoutiqueEnLigne
SET READ_COMMITTED_SNAPSHOT ON;

-- 2. Transaction A : Inventaire (toujours long)
BEGIN TRANSACTION;
UPDATE Produits
SET DerniereVerification = GETDATE()
WHERE Categorie = 'Electronique';  -- 100 000 produits
-- Prend toujours 5 minutes

COMMIT;

-- 3. Transaction B : Client consulte le catalogue
SELECT * FROM Produits WHERE Categorie = 'Electronique';
-- AUCUN BLOCAGE !
-- Lit les anciennes versions depuis tempdb
-- Résultat immédiat (< 1 seconde)
-- Le client est content
```

### Détail du comportement

```sql
-- ===== État initial =====
Table Produits
┌──────────┬─────────────┬──────────────────────┐
│ ProduitID│     Nom     │ DerniereVerification │
├──────────┼─────────────┼──────────────────────┤
│    1     │ Laptop      │ 2025-01-01 10:00     │
│    2     │ Smartphone  │ 2025-01-01 10:00     │
└──────────┴─────────────┴──────────────────────┘

-- ===== Transaction A commence l'UPDATE =====
BEGIN TRANSACTION;
UPDATE Produits SET DerniereVerification = GETDATE();
-- Anciennes versions copiées dans tempdb

tempdb (version store)
┌──────────┬─────────────┬──────────────────────┐
│ ProduitID│     Nom     │ DerniereVerification │
├──────────┼─────────────┼──────────────────────┤
│    1     │ Laptop      │ 2025-01-01 10:00     │ ← Ancienne version
│    2     │ Smartphone  │ 2025-01-01 10:00     │ ← Ancienne version
└──────────┴─────────────┴──────────────────────┘

Table Produits (en cours de modification)
┌──────────┬─────────────┬──────────────────────┐
│ ProduitID│     Nom     │ DerniereVerification │
├──────────┼─────────────┼──────────────────────┤
│    1     │ Laptop      │ 2025-01-15 14:30     │ ← Nouvelle version
│    2     │ Smartphone  │ 2025-01-15 14:30     │ ← Nouvelle version
└──────────┴─────────────┴──────────────────────┘

-- ===== Transaction B lit pendant l'UPDATE =====
SELECT * FROM Produits;
-- Lit depuis tempdb : voit 2025-01-01 10:00
-- Pas de blocage, résultat immédiat

-- ===== Transaction A fait COMMIT =====
COMMIT;
-- Versions dans tempdb supprimées (plus nécessaires)
```

## Surveillance de RCSI

### Vérifier l'utilisation de tempdb

```sql
-- Voir la taille du version store dans tempdb
SELECT
    SUM(version_store_reserved_page_count) * 8 / 1024 AS VersionStoreMB
FROM sys.dm_db_file_space_usage;
```

### Identifier les transactions problématiques

```sql
-- Trouver les transactions qui gardent des versions anciennes
SELECT
    session_id,
    transaction_id,
    elapsed_time_seconds
FROM sys.dm_tran_active_snapshot_database_transactions
ORDER BY elapsed_time_seconds DESC;
```

### Espace du version store par base de données

```sql
-- Voir l'espace réservé par le version store, base par base
SELECT
    DB_NAME(database_id) AS DatabaseName,
    reserved_page_count,
    reserved_space_kb / 1024 AS ReservedSpaceMB
FROM sys.dm_tran_version_store_space_usage
ORDER BY reserved_space_kb DESC;
```

## Quand utiliser RCSI ?

### Cas d'usage idéaux ✅

**1. Applications avec beaucoup de lectures et peu d'écritures**
```
Exemple : Site e-commerce
- 95% de lectures (consultations de produits)
- 5% d'écritures (mises à jour de stocks)
→ RCSI est PARFAIT
```

**2. Environnements avec problèmes de blocage**
```
Symptôme : Les utilisateurs se plaignent de lenteurs
Diagnostic : Beaucoup de blocages lecture/écriture
Solution : Activer RCSI
```

**3. Applications web et mobile**
```
Caractéristiques :
- Nombreux utilisateurs simultanés (concurrence élevée)
- Lectures fréquentes (listes, détails, recherches)
- Écritures occasionnelles (commandes, mises à jour)
→ RCSI améliore l'expérience utilisateur
```

**4. Systèmes de reporting avec données en temps réel**
```
Besoin : Rapports basés sur des données quasi actuelles
Problème : Les rapports bloquent les opérations transactionnelles
Solution : RCSI permet les rapports sans blocage
```

### Cas où réfléchir à deux fois ⚠️

**1. Applications avec beaucoup d'écritures**
```
Exemple : Système de trading haute fréquence
- 80% d'écritures (ordres, transactions)
- 20% de lectures
→ L'overhead de RCSI peut être problématique
```

**2. tempdb déjà surchargé**
```
Situation : tempdb est déjà proche de ses limites
Risque : RCSI va augmenter encore la charge
Solution : Optimiser tempdb d'abord ou éviter RCSI
```

**3. Transactions de lecture très longues**
```
Problème : Certaines requêtes prennent des heures
Risque : tempdb va exploser en taille
Solution : Optimiser ces requêtes d'abord
```

**4. Espace disque limité**
```
Contrainte : Serveur avec peu d'espace disque
Risque : tempdb peut grossir de manière importante
Solution : Provisionner plus d'espace ou éviter RCSI
```

## Migration vers RCSI

### Étapes recommandées

**1. Évaluation**
```sql
-- Analyser les patterns de concurrence actuels
SELECT
    blocking_session_id,
    COUNT(*) AS BlockingCount
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0
GROUP BY blocking_session_id
ORDER BY BlockingCount DESC;
```

**2. Test dans un environnement de développement**
```sql
-- Activer RCSI dans la base de test
ALTER DATABASE TestDB
SET READ_COMMITTED_SNAPSHOT ON;

-- Exécuter les tests de charge
-- Surveiller tempdb
```

**3. Surveillance de tempdb**
```sql
-- Vérifier que tempdb peut gérer la charge
SELECT
    SUM(version_store_reserved_page_count) * 8 / 1024 AS VersionStoreMB,
    SUM(unallocated_extent_page_count) * 8 / 1024 AS FreeSpaceMB
FROM sys.dm_db_file_space_usage;
```

**4. Activation en production**
```sql
-- Planifier pendant une fenêtre de maintenance
-- (nécessite un accès exclusif temporaire)
ALTER DATABASE ProdDB
SET READ_COMMITTED_SNAPSHOT ON;
```

**5. Surveillance post-activation**
```sql
-- Surveiller pendant au moins 1 semaine
-- - Taille de tempdb
-- - Performances des requêtes
-- - Blocages (devraient diminuer)
```

## Bonnes pratiques

### 1. Dimensionner tempdb correctement

```sql
-- tempdb devrait avoir :
-- - Plusieurs fichiers (1 par cœur CPU, max 8)
-- - Taille initiale suffisante (au moins 20% de la base principale)
-- - Croissance automatique raisonnable (512 MB ou 10%)

ALTER DATABASE tempdb
MODIFY FILE (NAME = tempdev, SIZE = 10240MB, FILEGROWTH = 512MB);
```

### 2. Éviter les transactions de lecture longues

```sql
-- ❌ MAUVAIS
BEGIN TRANSACTION;
SELECT * FROM GrosseTable;  -- Prend 10 minutes
-- Traitement long...
COMMIT;

-- ✅ BON
-- Pas de transaction pour les lectures simples
SELECT * FROM GrosseTable;
-- Ou transactions courtes
```

### 3. Monitorer régulièrement

```sql
-- Créer une alerte si tempdb dépasse un seuil
-- Exemple : Alerte si version store > 5 GB

IF (SELECT SUM(version_store_reserved_page_count) * 8 / 1024
    FROM sys.dm_db_file_space_usage) > 5120
BEGIN
    RAISERROR('tempdb version store trop grand !', 16, 1);
END
```

### 4. Combiner avec l'optimisation des index

```sql
-- RCSI améliore les lectures, mais des index appropriés restent essentiels
CREATE INDEX IX_Produits_Categorie ON Produits(Categorie);

-- RCSI + Bons index = Performance maximale
```

## Résumé

### Points clés

| Aspect | Description |
|--------|-------------|
| **Type** | Variante de READ COMMITTED utilisant le versioning |
| **Activation** | Au niveau de la **base de données** (pas de la transaction) |
| **Mécanisme** | Versions des lignes stockées dans **tempdb** |
| **Dirty Reads** | ❌ Bloquées (comme READ COMMITTED) |
| **Non-Repeatable Reads** | ✅ Autorisées |
| **Phantom Reads** | ✅ Autorisées |
| **Blocage en lecture** | ❌ Jamais |
| **Overhead** | Sur tempdb et écritures |
| **Performances lecture** | ⭐⭐⭐⭐⭐ Excellentes |

### Quand l'utiliser

✅ **OUI** pour :
- Applications avec lectures fréquentes (sites web, mobile)
- Environnements avec problèmes de blocage
- Besoin d'améliorer l'expérience utilisateur (temps de réponse)
- Architecture lecture intensive (e-commerce, portails)

❌ **NON** si :
- Beaucoup d'écritures et peu de lectures
- tempdb déjà surchargé
- Espace disque très limité
- Transactions de lecture extrêmement longues

### L'essentiel à retenir

1. RCSI utilise le **versioning** au lieu des verrous
2. Les **lecteurs ne sont jamais bloqués** par les écrivains
3. Nécessite de l'**espace dans tempdb**
4. S'active au niveau de la **base de données**, pas de la transaction
5. **Transparence** : aucun changement de code nécessaire
6. Offre les **mêmes garanties** que READ COMMITTED classique
7. Idéal pour les applications **lecture intensive**
8. Nécessite une **surveillance de tempdb**

### Commande d'activation

```sql
-- Une seule commande pour transformer votre base !
ALTER DATABASE VotreBaseDeDonnees
SET READ_COMMITTED_SNAPSHOT ON;
```
