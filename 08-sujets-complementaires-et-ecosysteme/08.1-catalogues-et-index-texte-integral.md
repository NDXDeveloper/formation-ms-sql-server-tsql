# 8.8.1 Catalogues et index de texte intégral

## Introduction

Pour utiliser la recherche plein texte, il faut d'abord mettre en place deux objets : un **catalogue de texte intégral** (le conteneur) et un **index de texte intégral** (la structure de recherche sur une table). Cette sous-section détaille leur création, leurs options importantes, et leur maintenance.

---

## Prérequis

Avant de commencer :

1. Le composant **Full-Text Search** doit être installé sur l'instance (voir annexe A). On peut le vérifier :

```sql
SELECT SERVERPROPERTY('IsFullTextInstalled') AS FullTextInstalle;  -- 1 = oui
```

2. La table à indexer doit posséder un **index unique, à colonne unique, non nullable** — typiquement sa **clé primaire**. C'est cet index qui sert à identifier les lignes dans l'index de texte intégral (le *KEY INDEX*).

---

## Étape 1 : créer un catalogue de texte intégral

Le **catalogue** est un conteneur logique qui regroupe un ou plusieurs index de texte intégral.

```sql
CREATE FULLTEXT CATALOG ftCatalogue AS DEFAULT;
```

L'option `AS DEFAULT` en fait le catalogue par défaut de la base (on n'aura plus besoin de le nommer à chaque création d'index).

---

## Étape 2 : créer un index de texte intégral

Prenons une table d'articles :

```sql
CREATE TABLE Articles (
    ArticleID  INT IDENTITY PRIMARY KEY,   -- index unique → servira de KEY INDEX
    Titre      NVARCHAR(200),
    Contenu    NVARCHAR(MAX),
    Langue     NVARCHAR(20)
);
```

On crée l'index de texte intégral sur les colonnes textuelles :

```sql
CREATE FULLTEXT INDEX ON Articles
(
    Titre   LANGUAGE 'French',
    Contenu LANGUAGE 'French'
)
KEY INDEX PK__Articles      -- l'index unique de la table (ici la PK)
ON ftCatalogue
WITH CHANGE_TRACKING = AUTO; -- l'index se met à jour automatiquement
```

### Les options importantes

| Option | Rôle |
|--------|------|
| `KEY INDEX` | Nomme l'index unique qui identifie les lignes (obligatoire) |
| `LANGUAGE` | Langue d'analyse (découpage des mots, racinisation, mots vides) |
| `CHANGE_TRACKING = AUTO` | L'index se met à jour **automatiquement** quand les données changent |
| `CHANGE_TRACKING = MANUAL` | Mise à jour déclenchée manuellement (`ALTER FULLTEXT INDEX ... START UPDATE POPULATION`) |
| `CHANGE_TRACKING = OFF, NO POPULATION` | Aucune mise à jour automatique (peuplement explicite) |

> 💡 **Choisir la bonne langue** est crucial : c'est elle qui détermine la racinisation (« courir »/« course ») et les mots vides. Une colonne `LANGUAGE 'French'` ne traitera pas correctement du contenu anglais.

---

## Indexer des documents binaires (PDF, Word…)

Si vos documents sont stockés en `VARBINARY(MAX)`, ajoutez une colonne indiquant leur **type** (extension), et déclarez-la avec `TYPE COLUMN` :

```sql
CREATE TABLE Documents (
    DocID     INT IDENTITY PRIMARY KEY,
    Fichier   VARBINARY(MAX),
    Extension NVARCHAR(10)        -- '.pdf', '.docx', ...
);

CREATE FULLTEXT INDEX ON Documents
(
    Fichier TYPE COLUMN Extension LANGUAGE 'French'
)
KEY INDEX PK__Documents
ON ftCatalogue
WITH CHANGE_TRACKING = AUTO;
```

SQL Server utilise alors un **iFilter** correspondant à l'extension pour extraire le texte du document avant de l'indexer. (Le filtre PDF doit parfois être installé séparément.)

---

## Le peuplement (population) de l'index

Lorsqu'un index est créé, SQL Server doit le **peupler** : analyser tout le texte existant. Sur de gros volumes, cela prend du temps et se fait **en arrière-plan**.

On suit l'état du peuplement :

```sql
SELECT
    OBJECT_NAME(object_id) AS Tbl,
    FULLTEXTCATALOGPROPERTY('ftCatalogue', 'PopulateStatus') AS Statut
FROM sys.fulltext_indexes;
```

Avec `CHANGE_TRACKING = AUTO`, les modifications ultérieures (INSERT/UPDATE/DELETE) sont répercutées automatiquement, sans intervention.

---

## Mots vides (stoplist) et thésaurus

### Stoplist (mots vides)

Une **stoplist** définit les mots ignorés à l'indexation (« le », « la », « de », « and »…). SQL Server fournit une stoplist système, et l'on peut en créer une personnalisée :

```sql
CREATE FULLTEXT STOPLIST maStoplist;
ALTER FULLTEXT STOPLIST maStoplist ADD 'svp' LANGUAGE 'French';
```

### Thésaurus (synonymes)

Le **thésaurus** (un fichier XML par langue, configurable sur le serveur) permet de déclarer des **synonymes** : une recherche sur « PC » trouvera aussi « ordinateur ». Il s'active dans les requêtes via `FORMSOF(THESAURUS, ...)` (voir §8.8.2).

---

## Maintenance et surveillance

- Avec `CHANGE_TRACKING = AUTO`, la maintenance est minimale.
- On peut **réorganiser** ou **reconstruire** un catalogue si nécessaire :

```sql
ALTER FULLTEXT CATALOG ftCatalogue REORGANIZE;
```

- Vues utiles : `sys.fulltext_catalogs`, `sys.fulltext_indexes`, et la fonction `sys.dm_fts_index_population` pour suivre les peuplements en cours.

---

## Exemple complet de mise en place

```sql
-- 1) Vérifier que Full-Text est installé
SELECT SERVERPROPERTY('IsFullTextInstalled');

-- 2) Créer le catalogue
CREATE FULLTEXT CATALOG ftCatalogue AS DEFAULT;

-- 3) Créer l'index de texte intégral sur la table Articles
CREATE FULLTEXT INDEX ON Articles (Titre, Contenu)
KEY INDEX PK__Articles
ON ftCatalogue
WITH CHANGE_TRACKING = AUTO;

-- 4) (le peuplement démarre automatiquement ; vérifier son avancement)
SELECT FULLTEXTCATALOGPROPERTY('ftCatalogue', 'PopulateStatus');
```

Une fois l'index peuplé, la table est prête à être interrogée avec `CONTAINS` et `FREETEXT`.

---

## Résumé

- La FTS repose sur un **catalogue** (conteneur) et un **index de texte intégral** (un par table).
- L'index nécessite un **index unique** sur la table (le `KEY INDEX`, souvent la PK).
- On précise la **langue** (racinisation, mots vides) et le mode de mise à jour (`CHANGE_TRACKING = AUTO` recommandé).
- On peut indexer des **documents binaires** (`TYPE COLUMN` + iFilters).
- **Stoplist** (mots vides) et **thésaurus** (synonymes) affinent la qualité de la recherche.
- Le composant Full-Text doit être **installé** sur l'instance.

Place maintenant aux requêtes : comment interroger réellement cet index avec `CONTAINS` et `FREETEXT`.
