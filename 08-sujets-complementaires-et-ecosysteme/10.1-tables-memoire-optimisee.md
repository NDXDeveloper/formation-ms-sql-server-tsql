# 8.10.1 Tables à mémoire optimisée et concurrence optimiste (MVCC)

## Introduction

Le cœur d'In-Memory OLTP, ce sont les **tables à mémoire optimisée**. Elles diffèrent profondément des tables classiques : elles vivent en **RAM**, n'utilisent **ni verrous ni latches**, et reposent sur un modèle de concurrence **optimiste et multi-version** (MVCC). Cette sous-section explique comment les créer et, surtout, comment fonctionne ce modèle qui change la façon de penser les transactions.

---

## Créer une table à mémoire optimisée

### Étape 1 : un groupe de fichiers dédié

Une base doit disposer d'un **groupe de fichiers** spécial `MEMORY_OPTIMIZED_DATA`, qui stockera les fichiers de points de contrôle assurant la durabilité :

```sql
ALTER DATABASE Boutique
ADD FILEGROUP fg_memoire CONTAINS MEMORY_OPTIMIZED_DATA;

ALTER DATABASE Boutique
ADD FILE (NAME = 'memoire', FILENAME = 'D:\Data\Boutique_memoire')
TO FILEGROUP fg_memoire;
```

### Étape 2 : la table

```sql
CREATE TABLE Commandes_MO (
    CommandeID  INT NOT NULL
        PRIMARY KEY NONCLUSTERED HASH WITH (BUCKET_COUNT = 1000000),
    ClientID    INT NOT NULL,
    DateCommande DATETIME2 NOT NULL,
    Montant     DECIMAL(12,2) NOT NULL,
    INDEX ix_client NONCLUSTERED (ClientID)
)
WITH (MEMORY_OPTIMIZED = ON, DURABILITY = SCHEMA_AND_DATA);
```

Les deux options de la clause `WITH` sont essentielles : `MEMORY_OPTIMIZED = ON` et `DURABILITY`.

---

## Le choix crucial : la durabilité (DURABILITY)

| Valeur | Comportement | Cas d'usage |
|--------|--------------|-------------|
| `SCHEMA_AND_DATA` | **Structure + données** survivent au redémarrage (durable, par défaut) | Données métier persistantes |
| `SCHEMA_ONLY` | Seule la **structure** survit ; **les données sont perdues** au redémarrage | Tables temporaires, sessions, staging |

> 💡 `SCHEMA_ONLY` est extrêmement rapide (aucune écriture dans le journal pour la durabilité), mais réservé aux données que l'on peut **perdre** sans conséquence : tables de session, files temporaires, zone de transit ETL.

```sql
-- Exemple : table de sessions, ultra-rapide, non durable
CREATE TABLE Sessions_MO (
    SessionID UNIQUEIDENTIFIER NOT NULL
        PRIMARY KEY NONCLUSTERED HASH WITH (BUCKET_COUNT = 500000),
    Donnees   NVARCHAR(4000)
)
WITH (MEMORY_OPTIMIZED = ON, DURABILITY = SCHEMA_ONLY);
```

---

## Les index en mémoire

Les tables à mémoire optimisée ont leurs propres types d'index, **entièrement en mémoire** (jamais écrits sur disque ; ils sont reconstruits au démarrage) :

### Index HASH

Optimisé pour les recherches d'**égalité** (`WHERE CommandeID = 4521`). Il nécessite un `BUCKET_COUNT` (nombre de « casiers ») :

```sql
PRIMARY KEY NONCLUSTERED HASH WITH (BUCKET_COUNT = 1000000)
```

> ⚠️ **Régler le BUCKET_COUNT** : visez environ **1 à 2 fois le nombre de valeurs distinctes** attendues. Trop bas → collisions (chaînes longues, lenteur). Trop haut → mémoire gaspillée. C'est le réglage le plus important d'un index hash.

### Index NONCLUSTERED (range)

Optimisé pour les recherches de **plage** et le **tri** (`WHERE DateCommande BETWEEN ...`, `ORDER BY`). C'est le choix par défaut si l'on ne sait pas :

```sql
INDEX ix_date NONCLUSTERED (DateCommande)
```

> 💡 En cas de doute, préférez un index **NONCLUSTERED range** : il gère à la fois l'égalité et les plages, sans réglage de bucket.

## Le modèle de concurrence : optimiste et multi-version (MVCC)

C'est ici que tout change par rapport aux tables classiques (chapitre 6).

### Pas de verrous, mais des versions

Une table à mémoire optimisée n'utilise **aucun verrou ni latch**. À la place, chaque modification crée une **nouvelle version** de la ligne, horodatée. Plusieurs versions d'une même ligne coexistent ; chaque transaction voit la version **cohérente** correspondant à son instant de démarrage.

> 🧠 **Analogie** : au lieu de se disputer l'accès à un seul cahier (verrou), chaque transaction reçoit une **photocopie figée** du cahier au moment où elle commence. Personne n'attend personne.

### Optimiste : on valide à la fin

Le modèle est **optimiste** : on suppose que les conflits sont rares. Les transactions travaillent **sans bloquer**, et c'est **au moment du `COMMIT`** que SQL Server vérifie si deux transactions ont modifié les mêmes données de façon incompatible.

- Pas de conflit → la transaction est validée.
- Conflit détecté → la transaction **échoue** (erreurs du type **41302**, 41305, 41325…) et doit être **réessayée**.

⚠️ **Conséquence pour le développeur** : votre code applicatif doit prévoir une **logique de nouvelle tentative** (*retry*) autour des transactions sur tables à mémoire optimisée :

```sql
-- Pseudo-logique de retry (à implémenter côté application ou en T-SQL)
-- 1. Tenter la transaction
-- 2. Si erreur 41302/41305/41325 (conflit) → attendre un instant, réessayer
-- 3. Après N échecs → abandonner et signaler
```

### Niveaux d'isolation

Les transactions sur tables à mémoire optimisée utilisent des niveaux d'isolation **fondés sur les versions** : `SNAPSHOT`, `REPEATABLE READ` ou `SERIALIZABLE` (voir §6.4). Le niveau `READ COMMITTED` classique des transactions explicites multi-instructions n'est pas applicable de la même manière ; on indique souvent l'indication `WITH (SNAPSHOT)` :

```sql
SELECT * FROM Commandes_MO WITH (SNAPSHOT) WHERE ClientID = 42;
```

## Accès : interprété ou natif

On peut accéder à une table à mémoire optimisée de deux façons :
1. Depuis du **T-SQL classique interprété** (*interop*) — pratique, compatible avec presque tout.
2. Depuis une **procédure compilée nativement** — performances maximales (voir §8.10.2).

Les deux accès cohabitent ; on commence souvent en interop, puis on « native-compile » les procédures critiques.

---

## Bonnes pratiques

- ✅ Choisir `DURABILITY` selon le besoin : `SCHEMA_AND_DATA` (persistant) vs `SCHEMA_ONLY` (jetable, ultra-rapide).
- ✅ Dimensionner soigneusement le **`BUCKET_COUNT`** des index hash.
- ✅ En cas de doute sur le type d'index, choisir **NONCLUSTERED range**.
- ✅ Implémenter une **logique de retry** pour gérer les conflits optimistes.
- ✅ Prévoir la **mémoire** : toute la table réside en RAM (surveiller la consommation).

---

## Questions fréquentes

**Q : Comment dimensionner le `BUCKET_COUNT` d'un index hash ?**
R : Visez environ **1 à 2 fois** le nombre de valeurs distinctes attendues. Trop bas → collisions ; trop haut → mémoire gaspillée.

**Q : HASH ou NONCLUSTERED, lequel choisir ?**
R : En cas de doute, **NONCLUSTERED range** : il gère égalité, plages et tri, sans réglage de bucket. Le HASH n'a d'intérêt que pour des recherches d'égalité très fréquentes.

**Q : Que se passe-t-il quand deux transactions entrent en conflit ?**
R : La transaction perdante **échoue** au `COMMIT` (erreurs 41302, 41305, 41325…). L'application doit la **réessayer** : c'est le prix du modèle optimiste, sans blocage.

---

## Résumé

- Une **table à mémoire optimisée** réside en **RAM** et n'utilise **ni verrou ni latch**.
- `DURABILITY` = `SCHEMA_AND_DATA` (données durables) ou `SCHEMA_ONLY` (données jetables, ultra-rapide).
- Index spécifiques : **HASH** (égalité, régler `BUCKET_COUNT`) et **NONCLUSTERED range** (plages/tri).
- La concurrence est **optimiste et multi-version** : pas d'attente, mais conflits détectés au `COMMIT` → prévoir un **retry**.
- Isolation fondée sur les versions (`SNAPSHOT`, `REPEATABLE READ`, `SERIALIZABLE`).

Voyons maintenant le second pilier qui décuple encore les performances : les procédures stockées compilées nativement.
