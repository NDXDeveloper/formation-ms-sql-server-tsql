# 4.4.2 UNION ALL (Conservation des doublons)

## Introduction

L'opérateur **UNION ALL** est très similaire à UNION, mais avec une différence fondamentale : il **conserve tous les doublons** au lieu de les éliminer. C'est souvent l'opérateur préféré quand on sait qu'il n'y a pas de doublons ou quand les doublons sont acceptables, car il offre de **meilleures performances**.

### Analogie simple

Imaginez que vous empilez deux paquets de cartes :
- **Avec UNION** : Vous empilez les cartes, puis vous cherchez et retirez tous les doublons (processus long)
- **Avec UNION ALL** : Vous empilez simplement les cartes sans vérifier les doublons (processus rapide)

Si vous avez deux listes :
- **Liste A** : Alice, Bob, Charlie, Alice
- **Liste B** : Bob, David, Eve

Avec `UNION ALL`, vous obtenez :
- **Résultat** : Alice, Bob, Charlie, Alice, Bob, David, Eve

Notez que :
- Alice apparaît **2 fois** (comme dans Liste A)
- Bob apparaît **2 fois** (une fois de chaque liste)
- **Tous les doublons sont conservés**

## Qu'est-ce que UNION ALL ?

### Définition

`UNION ALL` est un opérateur qui :
1. Combine les lignes de deux requêtes SELECT ou plus
2. **Conserve TOUS les doublons**
3. **Ne trie pas** les résultats (contrairement à UNION)
4. Est généralement **plus rapide** que UNION

### Syntaxe de base

```sql
SELECT colonnes
FROM table1
WHERE conditions1

UNION ALL

SELECT colonnes
FROM table2
WHERE conditions2;
```

**Différence clé avec UNION :**
- `UNION` → Élimine les doublons
- `UNION ALL` → Conserve les doublons

## La différence fondamentale : UNION vs UNION ALL

### Comparaison visuelle

**Données sources :**
```
Table1:           Table2:
- Alice           - Bob
- Bob             - Charlie
- Bob             - Alice
```

**Avec UNION (élimine doublons) :**
```sql
SELECT Nom FROM Table1
UNION
SELECT Nom FROM Table2;
```
**Résultat :** 3 lignes uniques
```
Alice    (1 fois, même si présent dans les 2 tables)
Bob      (1 fois, même si présent 2 fois dans Table1 et 1 fois dans Table2)
Charlie  (1 fois)
```

**Avec UNION ALL (conserve doublons) :**
```sql
SELECT Nom FROM Table1
UNION ALL
SELECT Nom FROM Table2;
```
**Résultat :** 6 lignes (toutes les lignes combinées)
```
Alice    (de Table1)
Bob      (de Table1, première occurrence)
Bob      (de Table1, deuxième occurrence)
Bob      (de Table2)
Charlie  (de Table2)
Alice    (de Table2)
```

### Tableau comparatif

| Aspect | UNION | UNION ALL |
|--------|-------|-----------|
| **Doublons** | ❌ Éliminés | ✅ Conservés |
| **Tri** | ✅ Tri automatique | ❌ Pas de tri |
| **Performance** | ⚠️ Plus lent | ✅ Plus rapide |
| **Nombre de lignes** | ≤ somme des lignes sources | = somme exacte des lignes sources |
| **Usage CPU** | ⚠️ Plus élevé | ✅ Plus faible |
| **Usage mémoire** | ⚠️ Plus élevé | ✅ Plus faible |

## Exemples de base

### Exemple 1 : Combiner des ventes de deux mois

```sql
SELECT VenteID, Vendeur, Montant
FROM VentesJanvier

UNION ALL

SELECT VenteID, Vendeur, Montant
FROM VentesFevrier

ORDER BY VenteID;
```

**Résultat :**
| VenteID | Vendeur | Montant |
|---------|---------|---------|
| 1 | Alice | 1000 |
| 2 | Bob | 1500 |
| 3 | Alice | 1200 |
| 4 | Bob | 2000 |
| 5 | Charlie | 800 |
| 6 | Alice | 1100 |

**Observations :**
- **6 lignes** au total (3 + 3)
- Alice apparaît **3 fois** (2 fois en janvier, 1 fois en février)
- Bob apparaît **2 fois** (1 fois en janvier, 1 fois en février)
- Tous les doublons de noms sont **conservés**
- L'ordre final dépend du `ORDER BY` (ici par VenteID)

### Exemple 2 : Comparaison UNION vs UNION ALL

Voyons la différence concrète entre les deux opérateurs.

**Avec UNION (élimine les doublons) :**
```sql
SELECT Vendeur FROM VentesJanvier
UNION
SELECT Vendeur FROM VentesFevrier;
```

**Résultat :** 3 lignes uniques
| Vendeur |
|---------|
| Alice |
| Bob |
| Charlie |

**Avec UNION ALL (conserve les doublons) :**
```sql
SELECT Vendeur FROM VentesJanvier
UNION ALL
SELECT Vendeur FROM VentesFevrier;
```

**Résultat :** 6 lignes
| Vendeur |
|---------|
| Alice |
| Bob |
| Alice |
| Bob |
| Charlie |
| Alice |

**Différence :**
- UNION : 3 vendeurs uniques
- UNION ALL : 6 entrées (une par vente)

## Processus d'exécution de UNION ALL

### Étapes d'exécution

**UNION (avec élimination des doublons) :**
```
SELECT 1 → Résultats → ┐
                       ├→ Combiner → Trier → Comparer → Éliminer doublons → Résultat
SELECT 2 → Résultats → ┘
```

**UNION ALL (simple combinaison) :**
```
SELECT 1 → Résultats → ┐
                       ├→ Combiner → Résultat
SELECT 2 → Résultats → ┘
```

**UNION ALL est plus rapide car :**
- ❌ Pas de tri nécessaire
- ❌ Pas de comparaison des lignes
- ❌ Pas de détection de doublons
- ✅ Simple concaténation des résultats

### Exemple de mesure de performance

Imaginons une requête sur de grandes tables :

```sql
-- UNION (plus lent)
SELECT ClientID, NomClient FROM Clients1  -- 100,000 lignes
UNION
SELECT ClientID, NomClient FROM Clients2; -- 100,000 lignes

-- Temps estimé : 5 secondes (tri + élimination doublons)
```

```sql
-- UNION ALL (plus rapide)
SELECT ClientID, NomClient FROM Clients1  -- 100,000 lignes
UNION ALL
SELECT ClientID, NomClient FROM Clients2; -- 100,000 lignes

-- Temps estimé : 1 seconde (simple combinaison)
```

**Différence de performance :** UNION ALL peut être **5 à 10 fois plus rapide** sur de gros volumes !

## Cas d'usage de UNION ALL

### 1. Combiner des données partitionnées par période

C'est le cas d'usage le plus courant : combiner des données réparties par mois, année, trimestre, etc.

```sql
-- Combiner les ventes de tous les mois de l'année
SELECT VenteID, Vendeur, Montant, 'Janvier' AS Mois
FROM VentesJanvier

UNION ALL

SELECT VenteID, Vendeur, Montant, 'Février'
FROM VentesFevrier

UNION ALL

SELECT VenteID, Vendeur, Montant, 'Mars'
FROM VentesMars

-- ... jusqu'à Décembre

ORDER BY Mois, VenteID;
```

**Pourquoi UNION ALL ?**
- Chaque vente a un `VenteID` unique
- Il n'y a **aucun risque de doublon** entre les mois
- UNION ALL est donc **plus rapide** sans inconvénient

### 2. Consolider des données de sources différentes

```sql
-- Toutes les transactions de la journée
SELECT
    TransactionID,
    'Vente en magasin' AS Type,
    Montant,
    DateHeure
FROM VentesMagasin
WHERE CAST(DateHeure AS DATE) = '2024-01-15'

UNION ALL

SELECT
    TransactionID,
    'Vente en ligne' AS Type,
    Montant,
    DateHeure
FROM VentesEnLigne
WHERE CAST(DateHeure AS DATE) = '2024-01-15'

UNION ALL

SELECT
    TransactionID,
    'Remboursement' AS Type,
    -Montant AS Montant,  -- Négatif pour les remboursements
    DateHeure
FROM Remboursements
WHERE CAST(DateHeure AS DATE) = '2024-01-15'

ORDER BY DateHeure;
```

| Alice | 1000 | Détail | 1 |

### 4. Combiner des données historiques et actuelles

```sql
-- Vue complète : données archivées + données actuelles
SELECT
    CommandeID,
    ClientID,
    DateCommande,
    Montant,
    'Archive' AS Source
FROM CommandesArchivees

UNION ALL

SELECT
    CommandeID,
    ClientID,
    DateCommande,
    Montant,
    'Actuel' AS Source
FROM CommandesActuelles

```

**Pourquoi UNION ALL ?**
- Les archives et les données actuelles sont **distinctes par nature**
- Pas de risque qu'une même commande soit dans les deux tables
- Performance optimale

## Quand utiliser UNION vs UNION ALL ?

### Arbre de décision

```
Avez-vous besoin d'éliminer les doublons ?
│
├─ OUI → Y a-t-il vraiment des doublons possibles ?
│         │
│         ├─ OUI → Utilisez UNION
│         │
│         └─ NON → Utilisez UNION ALL (même résultat, plus rapide)
│
└─ NON → Utilisez UNION ALL
```

### Guide de choix détaillé

✅ **Utilisez UNION ALL quand :**

1. **Vous savez qu'il n'y a pas de doublons possibles**
   ```sql
   -- IDs uniques, pas de doublon possible
   SELECT CommandeID, Montant FROM Commandes2023
   UNION ALL
   SELECT CommandeID, Montant FROM Commandes2024;
   ```

2. **Les doublons sont acceptables ou souhaités**
   ```sql
   -- On veut compter toutes les occurrences
   SELECT Produit FROM VentesJanvier
   UNION ALL
   SELECT Produit FROM VentesFevrier;
   -- Chaque vente doit être comptée
   ```

3. **La performance est critique**
   ```sql
   -- Gros volumes de données
   SELECT * FROM LogsServeur1  -- 1 million de lignes
   UNION ALL
   SELECT * FROM LogsServeur2  -- 1 million de lignes
   -- UNION ALL sera 5-10x plus rapide
   ```

4. **Vous consolidez des partitions disjointes**
   ```sql
   -- Données partitionnées par région (mutuellement exclusives)
   SELECT * FROM VentesEurope
   UNION ALL
   SELECT * FROM VentesAsie
   UNION ALL
   SELECT * FROM VentesAmeriques;
   ```

⚠️ **Utilisez UNION quand :**

1. **Vous devez absolument éliminer les doublons**
   ```sql
   -- Liste unique de clients ayant acheté en ligne OU en magasin
   SELECT ClientID FROM VentesEnLigne
   UNION
   SELECT ClientID FROM VentesMagasin;
   ```

2. **Les sources peuvent avoir des données qui se chevauchent**
   ```sql
   -- Listes avec potentiellement les mêmes personnes
   SELECT Email FROM NewsletterA
   UNION
   SELECT Email FROM NewsletterB;
   ```

3. **L'intégrité des données prime sur la performance**
   ```sql
   -- Rapport où chaque ligne doit être unique
   SELECT Produit, Categorie FROM Source1
   UNION
   SELECT Produit, Categorie FROM Source2;
   ```

### Tableau de décision pratique

| Situation | UNION | UNION ALL |
|-----------|-------|-----------|
| Tables partitionnées par temps (année, mois) | ❌ | ✅ |
| Données avec IDs uniques | ❌ | ✅ |
| Liste d'emails pour mailing | ✅ | ❌ |
| Logs d'événements | ❌ | ✅ |
| Liste de produits uniques | ✅ | ❌ |
| Consolidation multi-régions (disjointes) | ❌ | ✅ |
| Rapports avec totaux et détails | ❌ | ✅ |
| Fusion de listes client | ✅ | ❌ |
| Données archivées + actuelles | ❌ | ✅ |
| Performance critique, gros volumes | ❌ | ✅ |

| Utilisation CPU | 45% | 8% | **5.6x moins** |
| Lectures logiques | 15,000 | 2,000 | **7.5x moins** |
| Utilisation mémoire | 25 MB | 5 MB | **5x moins** |

### Plan d'exécution

**UNION (plus complexe) :**
```
Concatenation
  ├─ Sort (pour éliminer doublons) ← Coûteux !
  │   └─ Table Scan Table1
  └─ Sort (pour éliminer doublons) ← Coûteux !
      └─ Table Scan Table2
```

**UNION ALL (simple) :**
```
Concatenation  ← Simple et rapide !
  ├─ Table Scan Table1
  └─ Table Scan Table2
```

## Règles et contraintes

### Mêmes règles que UNION

UNION ALL suit les **mêmes règles** que UNION concernant :

1. **Même nombre de colonnes**
   ```sql
   -- ❌ ERREUR
   SELECT Col1, Col2 FROM Table1
   UNION ALL
   SELECT Col1 FROM Table2;  -- Pas le même nombre de colonnes !
   ```

2. **Types de données compatibles**
   ```sql
   -- ❌ ERREUR
   SELECT NomClient, ClientID FROM Table1  -- VARCHAR, INT
   UNION ALL
   SELECT NomClient, Ville FROM Table2;    -- VARCHAR, VARCHAR
   ```

3. **Noms de colonnes du premier SELECT**
   ```sql
   SELECT Nom AS Client, Age
   FROM Table1
   UNION ALL
   SELECT Prenom AS Personne, Annees  -- Ces noms sont ignorés
   FROM Table2;
   -- Résultat : colonnes nommées "Client" et "Age"
   ```

4. **ORDER BY uniquement à la fin**
   ```sql
   -- ✅ CORRECT
   SELECT Nom FROM Table1
   UNION ALL
   SELECT Nom FROM Table2
   ORDER BY Nom;  -- Tri final
   ```

### Différence avec UNION : Pas de tri automatique

```sql
-- UNION ALL ne trie PAS automatiquement
SELECT 'Charlie' AS Nom
UNION ALL
SELECT 'Alice'
UNION ALL
SELECT 'Bob';
```

**Résultat (ordre d'insertion) :**
| Nom |
|---------|
| Charlie |
| Alice |
| Bob |

Si vous voulez un tri, ajoutez explicitement `ORDER BY` :

```sql
SELECT 'Charlie' AS Nom
UNION ALL
SELECT 'Alice'
UNION ALL
SELECT 'Bob'
ORDER BY Nom;  -- Tri explicite
```

**Résultat (trié) :**
| Nom |
|---------|
| Alice |
| Bob |
| Charlie |

## Optimisations spécifiques à UNION ALL

### 1. Utiliser des index sur les colonnes filtrées

```sql
-- Créer des index pour améliorer les filtres
CREATE INDEX IDX_Ventes_Date ON VentesJanvier(DateVente);
CREATE INDEX IDX_Ventes_Date ON VentesFevrier(DateVente);

-- Requête optimisée
SELECT VenteID, Montant
FROM VentesJanvier
WHERE DateVente >= '2024-01-15'

UNION ALL

SELECT VenteID, Montant
FROM VentesFevrier
WHERE DateVente >= '2024-02-15';
```

### 2. Filtrer avant de combiner

Réduisez le nombre de lignes **avant** le UNION ALL.

```sql
-- ❌ Moins efficace : Filtre après UNION ALL
SELECT * FROM (
    SELECT VenteID, Vendeur, Montant FROM VentesJanvier
    UNION ALL
    SELECT VenteID, Vendeur, Montant FROM VentesFevrier
) AS Toutes
WHERE Montant > 1000;

-- ✅ Plus efficace : Filtre avant UNION ALL
SELECT VenteID, Vendeur, Montant
FROM VentesJanvier
WHERE Montant > 1000

UNION ALL

SELECT VenteID, Vendeur, Montant
FROM VentesFevrier
WHERE Montant > 1000;
```

### 3. Utiliser des vues partitionnées

Pour de grandes tables historiques, créez une vue partitionnée :

```sql
CREATE VIEW VueToutesLesVentes AS
SELECT * FROM Ventes2020
UNION ALL
SELECT * FROM Ventes2021
UNION ALL
SELECT * FROM Ventes2022
UNION ALL
SELECT * FROM Ventes2023
UNION ALL
SELECT * FROM Ventes2024;

-- SQL Server peut optimiser en n'accédant qu'aux partitions nécessaires
SELECT * FROM VueToutesLesVentes
WHERE DateVente >= '2024-01-01';
-- Accède uniquement à Ventes2024 !
```

## Pièges courants à éviter

### Piège 1 : Utiliser UNION par habitude

```sql
-- ❌ UNION inutile si pas de doublons possibles
SELECT CommandeID, Montant FROM Commandes2023
UNION  -- Élimine des doublons qui n'existent pas !
SELECT CommandeID, Montant FROM Commandes2024;

-- ✅ UNION ALL est plus approprié
SELECT CommandeID, Montant FROM Commandes2023
UNION ALL  -- Plus rapide, même résultat
SELECT CommandeID, Montant FROM Commandes2024;
```

### Piège 2 : Oublier que UNION ALL ne trie pas

```sql
-- ⚠️ L'ordre n'est pas garanti
SELECT Nom FROM Employes2023
UNION ALL
SELECT Nom FROM Employes2024;
-- L'ordre dépend de l'ordre physique des tables

-- ✅ Spécifier l'ordre explicitement si nécessaire
SELECT Nom FROM Employes2023
UNION ALL
SELECT Nom FROM Employes2024
ORDER BY Nom;
```

### Piège 3 : Supposer que UNION ALL est toujours meilleur

```sql
-- ⚠️ Cas où UNION est nécessaire
SELECT Email FROM Clients
UNION ALL  -- Mauvais choix ici !
SELECT Email FROM Prospects;
-- Peut créer des doublons d'emails indésirables

-- ✅ UNION élimine les doublons d'emails
SELECT Email FROM Clients
UNION
SELECT Email FROM Prospects;
```

### Piège 4 : Ne pas documenter le choix

```sql
-- ❌ Pas clair pourquoi UNION ALL
SELECT * FROM Table1
UNION ALL
SELECT * FROM Table2;

-- ✅ Documenter le raisonnement
-- Utilisation de UNION ALL car :
-- 1. Les deux tables sont partitionnées par année (pas de chevauchement)
-- 2. Chaque ligne doit être comptée individuellement
-- 3. Performance critique (millions de lignes)
SELECT * FROM Ventes2023
UNION ALL
SELECT * FROM Ventes2024;
```

```sql
    SELECT Col1, Col2 FROM Table2

    SELECT Col1, Col2 FROM Table1
    UNION ALL

-- Si les deux comptages sont identiques, utilisez UNION ALL !
```

### 4. Utiliser des CTE pour plus de clarté

```sql
-- ✅ Structure claire avec CTE
WITH
    VentesQ1 AS (
        SELECT * FROM VentesJanvier
        UNION ALL
        SELECT * FROM VentesFevrier
        UNION ALL
        SELECT * FROM VentesMars
    ),
    VentesQ2 AS (
        SELECT * FROM VentesAvril
        UNION ALL
        SELECT * FROM VentesMai
        UNION ALL
        SELECT * FROM VentesJuin
    )
SELECT * FROM VentesQ1
UNION ALL
SELECT * FROM VentesQ2
ORDER BY DateVente;
```

## Cas d'usage avancé : Vues partitionnées

### Créer une vue avec UNION ALL

Pour gérer de grandes tables historiques, une approche courante est de les partitionner par période et de créer une vue consolidée.

```sql
-- Vue consolidée de toutes les années
CREATE VIEW VueToutesLesCommandes AS
SELECT
    CommandeID,
    ClientID,
    DateCommande,
    Montant,
    2020 AS Annee
FROM Commandes2020

UNION ALL

SELECT
    CommandeID,
    ClientID,
    DateCommande,
    Montant,
    2021
FROM Commandes2021

UNION ALL

SELECT
    CommandeID,
    ClientID,
    DateCommande,
    Montant,
    2022
FROM Commandes2022

UNION ALL

SELECT
    CommandeID,
    ClientID,
    DateCommande,
    Montant,
    2023
FROM Commandes2023

UNION ALL

SELECT
    CommandeID,
    ClientID,
    DateCommande,
    Montant,
    2024
FROM Commandes2024;
```

**Utilisation de la vue :**
```sql
-- SQL Server peut optimiser et n'accéder qu'à la table 2024
SELECT *
FROM VueToutesLesCommandes
WHERE Annee = 2024;

-- Analyse sur plusieurs années
SELECT
    Annee,
    COUNT(*) AS NombreCommandes,
    SUM(Montant) AS TotalVentes
FROM VueToutesLesCommandes
WHERE Annee BETWEEN 2022 AND 2024
GROUP BY Annee;
```

**Avantages :**
- ✅ Interface unique pour accéder à toutes les données
- ✅ SQL Server optimise et n'accède qu'aux tables nécessaires
- ✅ Facilite l'ajout de nouvelles années
- ✅ Simplifie les requêtes des applications

## Résumé

L'opérateur **UNION ALL** combine les résultats de plusieurs requêtes SELECT en **conservant tous les doublons**.

### Syntaxe clé

```sql
SELECT colonnes FROM table1
UNION ALL
SELECT colonnes FROM table2;
```

### Caractéristiques essentielles

✅ **Avantages :**
- **Conserve tous les doublons**
- **Pas de tri** (pas de surcoût)
- **Performance optimale** (5-10x plus rapide que UNION)
- **Utilisation mémoire réduite**
- Idéal pour les gros volumes

❌ **Inconvénients :**
- Ne supprime pas les doublons (si nécessaire)
- Pas de tri automatique

### Différences clés : UNION vs UNION ALL

| Aspect | UNION | UNION ALL |
|--------|-------|-----------|
| Doublons | Éliminés | Conservés |
| Tri | Automatique | Aucun |
| Performance | Plus lent | Plus rapide |
| Usage | Quand doublons indésirables | Quand doublons OK ou impossibles |

### Quand utiliser UNION ALL ?

✅ **UNION ALL est préférable quand :**
- Données partitionnées (par temps, région, etc.)
- IDs uniques garantis entre les sources
- Doublons acceptables ou souhaités
- Performance critique
- Gros volumes de données
- Consolidation de logs ou d'événements

⚠️ **Utiliser UNION si :**
- Vous devez éliminer les doublons
- Les sources peuvent se chevaucher
- L'intégrité prime sur la performance

### Règles importantes

1. **Mêmes règles que UNION** : nombre de colonnes, types compatibles
2. **Performance** : Toujours considérer UNION ALL d'abord
3. **Documentation** : Expliquer le choix de UNION vs UNION ALL
4. **Test** : Vérifier s'il y a réellement des doublons

### Conseil principal

**Par défaut, utilisez UNION ALL** sauf si vous avez une raison spécifique de vouloir éliminer les doublons. C'est plus performant et exprime clairement votre intention de conserver toutes les lignes.
