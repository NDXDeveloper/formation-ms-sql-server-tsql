# 7.8.4 RESTORE et séquence de restauration

## Introduction

Sauvegarder, c'est bien. **Restaurer correctement, c'est l'objectif réel.** Cette sous-section explique le mécanisme central de toute restauration SQL Server : la notion de **`NORECOVERY` / `RECOVERY`**, et l'ordre précis dans lequel on rejoue les sauvegardes — la **séquence de restauration**.

> 🧠 C'est probablement la sous-section la plus importante de toute la section : le jour d'un incident, c'est ce savoir-faire — et lui seul — qui sauvera vos données.

---

## L'idée clé : restaurer = empiler des sauvegardes dans l'ordre

Restaurer une base avec précision, c'est comme **reconstituer un film à partir d'une photo, puis d'un résumé, puis de l'enregistrement complet** :

1. On part de la **photo complète** (sauvegarde complète).
2. On applique éventuellement le **résumé des changements** (différentielle).
3. On rejoue ensuite **action par action** (sauvegardes de journal) jusqu'au moment voulu.

Entre chaque étape, la base doit rester **« en attente »** de recevoir d'autres sauvegardes. C'est tout le rôle de l'option `NORECOVERY`.

---

## NORECOVERY vs RECOVERY : LA notion à maîtriser

Quand vous restaurez une sauvegarde, vous devez indiquer à SQL Server s'il y a **encore d'autres sauvegardes à appliquer ensuite** :

| Option | Signification | État de la base après |
|--------|---------------|------------------------|
| `WITH NORECOVERY` | « Ce n'est pas fini, garde la base en attente » | `RESTORING` (inutilisable) |
| `WITH RECOVERY` | « C'est terminé, ouvre la base » | En ligne (utilisable) |
| `WITH STANDBY = ...` | « En attente, mais lisible en lecture seule » | Lecture seule |

> 🧠 **Règle d'or** : on utilise `NORECOVERY` pour **toutes les sauvegardes sauf la dernière**, et `RECOVERY` (qui est la valeur par défaut) **uniquement pour la toute dernière** sauvegarde de la séquence.

### Pourquoi cette mécanique ?

Quand SQL Server termine une restauration avec `RECOVERY`, il effectue une phase de **récupération** (*recovery*) : il rejoue (REDO) les transactions validées et annule (UNDO) les transactions non validées, pour rendre la base **cohérente et ouvrable**. Une fois cette phase faite, **on ne peut plus appliquer de journaux**.

⚠️ C'est pourquoi `RECOVERY` appliqué **trop tôt** est l'erreur la plus coûteuse : si vous ouvrez la base après la complète alors qu'il restait des journaux à appliquer, vous devez **tout recommencer** depuis le début.

---

## Une séquence de restauration complète

Scénario : restaurer la base `Boutique` jusqu'au mercredi 11h, à partir de la complète du dimanche, de la différentielle de mercredi matin, puis des journaux de la matinée.

```sql
-- 1) Sauvegarde COMPLÈTE — on garde la base en attente
RESTORE DATABASE Boutique
FROM DISK = 'C:\Backups\Boutique_FULL_dimanche.bak'
WITH NORECOVERY, REPLACE;

-- 2) Dernière DIFFÉRENTIELLE — toujours en attente
RESTORE DATABASE Boutique
FROM DISK = 'C:\Backups\Boutique_DIFF_mercredi.bak'
WITH NORECOVERY;

-- 3) Les sauvegardes de JOURNAL, dans l'ordre chronologique — toujours en attente
RESTORE LOG Boutique
FROM DISK = 'C:\Backups\Boutique_LOG_mercredi_0900.trn'
WITH NORECOVERY;

RESTORE LOG Boutique
FROM DISK = 'C:\Backups\Boutique_LOG_mercredi_1000.trn'
WITH NORECOVERY;

-- 4) DERNIÈRE sauvegarde de journal — on ouvre enfin la base
RESTORE LOG Boutique
FROM DISK = 'C:\Backups\Boutique_LOG_mercredi_1100.trn'
WITH RECOVERY;
```

Visuellement :

```
RESTORE DATABASE (FULL)   WITH NORECOVERY   ┐
RESTORE DATABASE (DIFF)   WITH NORECOVERY   │  base en état RESTORING
RESTORE LOG  (09h)        WITH NORECOVERY   │  (inutilisable, en attente)
RESTORE LOG  (10h)        WITH NORECOVERY   │
RESTORE LOG  (11h)        WITH RECOVERY     ┘──▶ base EN LIGNE ✅
```

---

## L'option REPLACE

`WITH REPLACE` autorise SQL Server à **écraser une base existante**. Sans elle, SQL Server refuse par sécurité d'écraser une base qui ne correspond pas exactement à la sauvegarde (protection contre les écrasements accidentels, par exemple restaurer la sauvegarde d'une *autre* base par-dessus la vôtre).

À n'utiliser **qu'en connaissance de cause** : vous confirmez vouloir remplacer la base cible par le contenu de la sauvegarde.

---

## Restaurer ailleurs ou sous un autre nom : l'option MOVE

Cas très fréquent : restaurer une sauvegarde de production sur un **autre serveur** ou un poste de développement, où les chemins de fichiers diffèrent. On utilise `MOVE` pour rediriger chaque fichier :

```sql
RESTORE DATABASE Boutique_Test
FROM DISK = 'C:\Backups\Boutique_FULL_dimanche.bak'
WITH
    MOVE 'Boutique'     TO 'D:\Data\Boutique_Test.mdf',
    MOVE 'Boutique_log' TO 'D:\Data\Boutique_Test_log.ldf',
    RECOVERY, REPLACE;
```

> 💡 Les **noms logiques** (`'Boutique'`, `'Boutique_log'`) s'obtiennent avec `RESTORE FILELISTONLY` (voir §7.8.3). Ne confondez pas le nom **logique** (interne à SQL Server) et le **chemin physique** sur le disque.

## Suivre l'avancement d'une restauration

Une grosse restauration peut durer longtemps. On suit sa progression ainsi :

```sql
SELECT
    r.command,
    r.percent_complete,
    DATEADD(SECOND, r.estimated_completion_time / 1000, GETDATE()) AS FinEstimee
FROM sys.dm_exec_requests r
WHERE r.command IN ('RESTORE DATABASE', 'RESTORE LOG', 'BACKUP DATABASE');
```

(L'option `STATS = 10` affiche aussi la progression en pourcentage dans le message.)

---

## L'état RESTORING et l'option STANDBY

Tant qu'une base est restaurée `WITH NORECOVERY`, elle apparaît dans SSMS avec la mention **« (Restoring...) »** et n'est **pas accessible**.

Si vous voulez **consulter** la base entre deux applications de journaux (par exemple pour vérifier où vous en êtes dans la récupération), utilisez `STANDBY` au lieu de `NORECOVERY` : la base devient **lisible en lecture seule**, tout en pouvant recevoir d'autres journaux ensuite.

```sql
RESTORE LOG Boutique
FROM DISK = 'C:\Backups\Boutique_LOG_mercredi_0900.trn'
WITH STANDBY = 'C:\Backups\Boutique_standby.bak';
```

C'est le mécanisme utilisé par le *log shipping* pour offrir un réplica en lecture seule (voir §8.5).

## Scénario complet : récupération après sinistre

Mettons bout à bout ce que nous savons. Le serveur a un problème, mais le fichier journal est intact :

```sql
-- ÉTAPE 0 (cruciale) : capturer les dernières transactions non sauvegardées
BACKUP LOG Boutique
TO DISK = 'C:\Backups\Boutique_tail.trn'
WITH NO_TRUNCATE;

-- ÉTAPE 1 : restaurer la dernière complète
RESTORE DATABASE Boutique FROM DISK = 'C:\Backups\Boutique_FULL.bak'
WITH NORECOVERY, REPLACE;

-- ÉTAPE 2 : la dernière différentielle
RESTORE DATABASE Boutique FROM DISK = 'C:\Backups\Boutique_DIFF.bak'
WITH NORECOVERY;

-- ÉTAPE 3 : tous les journaux, dans l'ordre, y compris le tail-log en dernier
RESTORE LOG Boutique FROM DISK = 'C:\Backups\Boutique_LOG_1.trn' WITH NORECOVERY;
RESTORE LOG Boutique FROM DISK = 'C:\Backups\Boutique_LOG_2.trn' WITH NORECOVERY;
RESTORE LOG Boutique FROM DISK = 'C:\Backups\Boutique_tail.trn'  WITH RECOVERY;
```

➡️ Résultat : **zéro perte de données**, jusqu'à la dernière transaction.

## Restaurer les bases système

Les bases système se restaurent différemment :
- **`master`** : nécessite de démarrer l'instance en mode mono-utilisateur (`-m`). C'est une procédure d'administration particulière.
- **`msdb`** : se restaure comme une base utilisateur, mais on perd jobs et historique si elle n'est pas à jour.
- **`tempdb`** : ne se sauvegarde pas — elle est recréée à chaque démarrage de l'instance.

Retenez surtout que `master` mérite une procédure de restauration documentée à part.

---

## Erreurs fréquentes à éviter

| Erreur | Conséquence | Remède |
|--------|-------------|--------|
| `RECOVERY` appliqué trop tôt | Impossible d'appliquer les journaux suivants | Tout recommencer depuis la complète |
| Journaux appliqués dans le désordre | Erreur « LSN trop récent/ancien » | Respecter l'ordre chronologique |
| Chaîne de journaux incomplète | Restauration bloquée à un maillon | S'assurer d'avoir tous les `.trn` |
| Oubli de `MOVE` sur un autre serveur | Erreur « chemin introuvable » | Utiliser `MOVE` avec les bons chemins |
| Oubli du tail-log backup | Perte des dernières transactions | Toujours commencer par le tail-log |

## Questions fréquentes

**Q : Comment annuler une restauration laissée en NORECOVERY ?**
R : `RESTORE DATABASE MaBase WITH RECOVERY;` force la sortie de l'état RESTORING (mais sans appliquer d'autres journaux).

**Q : Peut-on restaurer une sauvegarde d'une version plus récente de SQL Server sur une version plus ancienne ?**
R : Non. On peut restaurer d'une version ancienne vers une plus récente (la base est alors « migrée »), jamais l'inverse.

**Q : Une restauration verrouille-t-elle la base pour les utilisateurs ?**
R : Oui, la base est hors ligne pendant la restauration. D'où l'intérêt de restaurer dans une **copie** quand on veut juste récupérer quelques données (voir §7.8.5).

---

## Résumé

- La restauration consiste à **empiler** les sauvegardes dans l'ordre : complète → différentielle → journaux.
- `WITH NORECOVERY` garde la base **en attente** ; `WITH RECOVERY` (dernière étape) **ouvre** la base ; `STANDBY` permet une lecture seule intermédiaire.
- `REPLACE` autorise l'écrasement ; `MOVE` redirige les fichiers vers d'autres chemins/noms.
- Face à un sinistre : **commencer par le tail-log backup** (`NO_TRUNCATE`), puis restaurer dans l'ordre.
- Respecter **l'ordre** et la **complétude** de la chaîne est impératif.
