# 7.5.3 Forcer un plan d'exécution

## Qu'est-ce que le forçage d'un plan ?

**Forcer un plan d'exécution** signifie dire à SQL Server : "Pour cette requête spécifique, utilise toujours ce plan précis, peu importe les circonstances."

### Analogie simple

Imaginez que vous utilisez un GPS pour aller au travail. Normalement, le GPS calcule automatiquement le meilleur itinéraire chaque jour en fonction du trafic. Mais parfois, il vous propose un chemin qui semble bon sur le papier mais qui est en réalité terrible (travaux, routes étroites, etc.).

**Forcer un plan**, c'est comme dire au GPS : "Je sais que tu penses que cette route est meilleure, mais fais-moi confiance, prends toujours l'autoroute A13. Arrête d'essayer de me faire passer par les petites routes."

## Pourquoi forcer un plan ?

### Le problème : L'optimiseur n'a pas toujours raison

SQL Server dispose d'un composant appelé **l'optimiseur de requêtes** qui choisit automatiquement le meilleur plan d'exécution. Dans 99% des cas, il fait un excellent travail. Mais parfois :

1. **Les statistiques sont trompeuses**
   - L'optimiseur pense qu'une table contient peu de données alors qu'elle en contient beaucoup
   - Il choisit un plan inadapté basé sur des informations incorrectes

2. **Le Parameter Sniffing**
   - L'optimiseur crée un plan basé sur la première valeur de paramètre qu'il voit
   - Ce plan peut être mauvais pour d'autres valeurs de paramètres

3. **Changements d'environnement**
   - Une mise à jour de SQL Server
   - Un changement du niveau de compatibilité
   - Ces changements peuvent amener l'optimiseur à choisir de moins bons plans

### La solution : Le forçage temporaire

Au lieu de passer des heures à comprendre pourquoi l'optimiseur fait un mauvais choix, vous pouvez **temporairement** forcer l'utilisation du bon plan que vous aviez identifié précédemment.

**Important :** Le forçage d'un plan est une solution à court terme, pas une solution permanente. Vous devez toujours chercher à comprendre et corriger la cause racine.

## Comment forcer un plan d'exécution

### Méthode 1 : Via SSMS (la plus simple)

C'est la méthode recommandée pour les débutants car elle est visuelle et intuitive.

#### Étape 1 : Identifier le bon plan

1. Ouvrez le rapport **Regressed Queries** dans Query Store
2. Identifiez une requête qui a régressé
3. Dans le panneau inférieur, vous voyez les différents plans disponibles
4. Identifiez le plan avec les meilleures performances (durée plus courte)

**Exemple de ce que vous voyez :**
```
Plan ID: 1 - Avg Duration: 50 ms   ← Le bon plan
Plan ID: 2 - Avg Duration: 2500 ms ← Le mauvais plan (actuellement utilisé)
```

#### Étape 2 : Forcer le plan

1. **Clic droit** sur le bon plan (Plan ID: 1 dans notre exemple)
2. Sélectionnez **"Force Plan"** dans le menu contextuel
3. Une boîte de dialogue de confirmation apparaît
4. Cliquez sur **"Yes"**

C'est tout ! SQL Server utilisera maintenant toujours ce plan pour cette requête.

#### Vérification

Dans la liste des plans, vous verrez :
- Une **icône de cadenas** ou une **coche** à côté du plan forcé
- La colonne "Force" indiquera "Yes"

### Méthode 2 : Via T-SQL

Si vous préférez le code ou si vous devez automatiser le processus :

#### Syntaxe de base

```sql
EXEC sp_query_store_force_plan
    @query_id = <ID_de_la_requête>,
    @plan_id = <ID_du_plan>;
```

#### Exemple complet

```sql
-- Étape 1 : Identifier la requête et le plan
-- Disons que nous voulons forcer le plan 1 pour la requête 123

-- Étape 2 : Forcer le plan
EXEC sp_query_store_force_plan
    @query_id = 123,
    @plan_id = 1;

-- Message de confirmation :
-- Plan 1 for query 123 forced successfully.
```

#### Script d'aide pour trouver les IDs

Si vous ne connaissez pas les IDs, utilisez cette requête :

```sql
-- Trouver une requête spécifique et ses plans
SELECT
    q.query_id,
    qt.query_sql_text,
    p.plan_id,
    p.is_forced_plan,
    rs.avg_duration / 1000.0 AS avg_duration_ms,
    rs.count_executions,
    rs.last_execution_time
FROM sys.query_store_query q
INNER JOIN sys.query_store_query_text qt
    ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan p
    ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats rs
    ON p.plan_id = rs.plan_id
WHERE qt.query_sql_text LIKE '%SELECT%FROM Customers%'  -- Adaptez cette recherche
ORDER BY q.query_id, rs.avg_duration;
```

**Lecture des résultats :**
```
query_id | query_sql_text      | plan_id | is_forced_plan | avg_duration_ms
---------|---------------------|---------|----------------|----------------
123      | SELECT * FROM...   | 1       | 0              | 50
123      | SELECT * FROM...   | 2       | 0              | 2500
```

Vous voyez que le plan 1 est le meilleur. Forcez-le avec :
```sql
EXEC sp_query_store_force_plan @query_id = 123, @plan_id = 1;
```

## Ce qui se passe après le forçage

### Comportement de SQL Server

Une fois un plan forcé :

1. **Pour cette requête spécifique**
   - SQL Server utilisera **toujours** le plan forcé
   - Même si l'optimiseur pense avoir trouvé un meilleur plan
   - Même après un redémarrage du serveur

2. **L'optimiseur est contourné**
   - Il ne cherchera plus à optimiser cette requête
   - Il utilisera directement le plan forcé du cache ou du Query Store

3. **Persistance**
   - Le forçage est stocké dans la base de données
   - Il persiste tant que vous ne le retirez pas manuellement

### Exemple de scénario

**Avant le forçage :**
```
9:00 AM - SQL Server utilise Plan 1 (rapide: 50 ms)
10:00 AM - Les statistiques sont mises à jour
10:01 AM - SQL Server bascule sur Plan 2 (lent: 2500 ms)
10:02 AM - Les utilisateurs se plaignent de lenteur
```

**Après le forçage du Plan 1 :**
```
10:05 AM - Vous forcez Plan 1
10:06 AM - SQL Server utilise Plan 1 (rapide: 50 ms)
11:00 AM - Mise à jour des statistiques → SQL Server continue d'utiliser Plan 1
12:00 PM - Redémarrage du serveur → SQL Server utilise toujours Plan 1
```

## Vérifier les plans forcés

### Via SSMS

1. Dans Query Store, ouvrez le rapport **"Queries With Forced Plans"**
2. Vous voyez toutes les requêtes qui ont un plan forcé
3. Pour chaque requête :
   - Le plan forcé
   - Depuis quand il est forcé
   - Les statistiques de performance

### Via T-SQL

```sql
-- Liste de tous les plans forcés dans la base de données actuelle
SELECT
    q.query_id,
    qt.query_sql_text,
    p.plan_id,
    p.is_forced_plan,
    p.force_failure_count,
    p.last_force_failure_reason_desc,
    rs.avg_duration / 1000.0 AS avg_duration_ms,
    rs.last_execution_time
FROM sys.query_store_query q
INNER JOIN sys.query_store_query_text qt
    ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan p
    ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats rs
    ON p.plan_id = rs.plan_id
WHERE p.is_forced_plan = 1
ORDER BY q.query_id;
```

**Colonnes importantes :**
- `is_forced_plan` : 1 si le plan est forcé
- `force_failure_count` : Nombre d'échecs de forçage
- `last_force_failure_reason_desc` : Raison du dernier échec

## Retirer le forçage d'un plan

### Pourquoi retirer un plan forcé ?

Le forçage est une solution temporaire. Vous devez le retirer quand :

1. **La cause racine est corrigée**
   - Statistiques mises à jour correctement
   - Index manquant créé
   - Requête optimisée

2. **Le plan forcé devient obsolète**
   - Les données ont beaucoup changé
   - Le plan forcé n'est plus optimal

3. **Pour tester des améliorations**
   - Vous voulez voir si l'optimiseur choisit maintenant un meilleur plan
   - Après une mise à jour de SQL Server

### Méthode 1 : Via SSMS

1. Ouvrez le rapport **"Queries With Forced Plans"**
2. Sélectionnez la requête concernée
3. **Clic droit** sur le plan forcé
4. Sélectionnez **"Unforce Plan"**
5. Confirmez

### Méthode 2 : Via T-SQL

```sql
-- Retirer le forçage d'un plan spécifique
EXEC sp_query_store_unforce_plan
    @query_id = 123,
    @plan_id = 1;

-- Message de confirmation :
-- Plan 1 for query 123 unforced successfully.
```

### Retirer tous les plans forcés (avec prudence)

```sql
-- ⚠️ Attention : Cela retire TOUS les plans forcés de la base de données
DECLARE @query_id INT;
DECLARE @plan_id INT;

DECLARE plan_cursor CURSOR FOR
    SELECT query_id, plan_id
    FROM sys.query_store_plan
    WHERE is_forced_plan = 1;

OPEN plan_cursor;
FETCH NEXT FROM plan_cursor INTO @query_id, @plan_id;

WHILE @@FETCH_STATUS = 0
BEGIN
    EXEC sp_query_store_unforce_plan @query_id, @plan_id;
    PRINT 'Plan ' + CAST(@plan_id AS VARCHAR) + ' for query '
          + CAST(@query_id AS VARCHAR) + ' unforced.';
    FETCH NEXT FROM plan_cursor INTO @query_id, @plan_id;
END

CLOSE plan_cursor;
DEALLOCATE plan_cursor;
```

## Échecs de forçage de plan

### Qu'est-ce qu'un échec de forçage ?

Parfois, SQL Server ne peut pas utiliser le plan forcé. Cela s'appelle un **échec de forçage** (force failure).

### Causes courantes

#### 1. Changements de schéma

**Exemple :**
```sql
-- Le plan forcé utilisait cet index
CREATE INDEX IX_Customers_Name ON Customers(CustomerName);

-- Puis quelqu'un supprime l'index
DROP INDEX IX_Customers_Name ON Customers;

-- → Le plan forcé ne peut plus être utilisé (il dépendait de cet index)
```

#### 2. Index manquants

Le plan forcé référence un index qui n'existe plus ou qui n'existe pas dans un environnement différent (test → production).

#### 3. Objets modifiés

```sql
-- Le plan forcé utilisait cette colonne
ALTER TABLE Orders DROP COLUMN OrderPriority;

-- → Le plan ne peut plus être exécuté
```

#### 4. Statistiques très obsolètes

Dans de rares cas, si les statistiques sont extrêmement différentes, SQL Server peut abandonner le plan forcé.

### Détecter les échecs

```sql
-- Trouver les plans forcés qui échouent
SELECT
    q.query_id,
    qt.query_sql_text,
    p.plan_id,
    p.force_failure_count,
    p.last_force_failure_reason,
    p.last_force_failure_reason_desc
FROM sys.query_store_query q
INNER JOIN sys.query_store_query_text qt
    ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan p
    ON q.query_id = p.query_id
WHERE p.is_forced_plan = 1
    AND p.force_failure_count > 0
ORDER BY p.force_failure_count DESC;
```

**Raisons possibles :**
```
1 - GENERAL_FAILURE : Erreur générale
2 - SCHEMA_CHANGED : Le schéma a changé
3 - NO_TRUSTED_STATISTICS : Statistiques non fiables
4 - COMPILATION_ERROR : Erreur de compilation
```

### Résoudre un échec

1. **Identifier la cause** avec la requête ci-dessus
2. **Corriger le problème** :
   - Recréer l'index manquant
   - Restaurer la colonne supprimée
   - Mettre à jour les statistiques
3. **Retester** : Le forçage devrait à nouveau fonctionner

Si le problème persiste :
```sql
-- Retirer le forçage et chercher une autre solution
EXEC sp_query_store_unforce_plan @query_id = 123, @plan_id = 1;
```

## Bonnes pratiques

### 1. Forcer avec parcimonie

Le forçage de plan est puissant mais doit être utilisé avec prudence :

✅ **À faire :**
- Forcer un plan pour une régression critique en production
- Forcer temporairement en attendant une vraie correction
- Documenter pourquoi vous forcez un plan

❌ **À éviter :**
- Forcer des dizaines de plans "par précaution"
- Forcer un plan et l'oublier pendant des mois
- Forcer un plan sans comprendre pourquoi il est meilleur

### 2. Toujours chercher la cause racine

Le forçage est un **pansement**, pas un remède :

```
Problème identifié
    ↓
Forcer le bon plan (solution immédiate)
    ↓
Investiguer la cause (statistiques? index? parameter sniffing?)
    ↓
Corriger la cause
    ↓
Retirer le forçage
    ↓
Vérifier que le problème ne revient pas
```

### 3. Documenter vos décisions

Pour chaque plan forcé, documentez :

```sql
-- Exemple de documentation sous forme de commentaire
-- Date: 2025-11-18
-- Forcé par: Jean Dupont
-- Raison: Régression après mise à jour des statistiques
-- Query ID: 123, Plan ID: 1
-- Ticket: SUPPORT-4567
-- Action prévue: Analyser les statistiques et retirer le forçage sous 1 semaine

EXEC sp_query_store_force_plan @query_id = 123, @plan_id = 1;
```

Ou utilisez une table de suivi :

```sql
CREATE TABLE PlanForcingLog (
    LogID INT IDENTITY PRIMARY KEY,
    QueryID INT,
    PlanID INT,
    ForcedDate DATETIME2 DEFAULT GETDATE(),
    ForcedBy VARCHAR(100),
    Reason VARCHAR(500),
    TicketNumber VARCHAR(50),
    PlannedReviewDate DATE,
    UnforcedDate DATETIME2,
    Notes VARCHAR(1000)
);

-- Lors du forçage
INSERT INTO PlanForcingLog (QueryID, PlanID, ForcedBy, Reason, TicketNumber, PlannedReviewDate)
VALUES (123, 1, 'Jean Dupont', 'Régression après mise à jour stats', 'SUP-4567', '2025-11-25');
```

### 4. Réviser régulièrement

Planifiez une révision périodique :

```sql
-- Trouver les plans forcés depuis plus de 30 jours
SELECT
    q.query_id,
    SUBSTRING(qt.query_sql_text, 1, 100) as query_preview,
    p.plan_id,
    p.create_time as plan_created,
    DATEDIFF(day, p.create_time, GETDATE()) as days_forced
FROM sys.query_store_query q
INNER JOIN sys.query_store_query_text qt
    ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan p
    ON q.query_id = p.query_id
WHERE p.is_forced_plan = 1
    AND DATEDIFF(day, p.create_time, GETDATE()) > 30
ORDER BY days_forced DESC;
```

Posez-vous ces questions :
- La cause racine a-t-elle été corrigée ?
- Le plan forcé est-il toujours optimal ?
- Peut-on retirer le forçage en toute sécurité ?

### 5. Tester avant de retirer

Avant de retirer un forçage en production :

1. **Reproduisez dans un environnement de test**
```sql
-- En test : Retirer le forçage
EXEC sp_query_store_unforce_plan @query_id = 123, @plan_id = 1;

-- Exécuter la requête plusieurs fois avec différents paramètres
-- Vérifier les performances
```

2. **Vider le cache de plans** (pour forcer une recompilation)
```sql
-- Attention : À faire uniquement en test ou hors heures de pointe
DBCC FREEPROCCACHE;
```

3. **Surveiller pendant plusieurs heures/jours**

4. **Si tout va bien, appliquer en production**

### 6. Utiliser des alertes

Configurez des alertes pour être notifié :

- Quand un plan forcé échoue
- Quand un plan forcé est utilisé (pour suivre l'activité)
- Quand un plan est forcé depuis trop longtemps

## Scénarios d'utilisation réels

### Scénario 1 : Le Parameter Sniffing

**Problème :**
```sql
CREATE PROCEDURE GetOrdersByCountry @Country VARCHAR(50)
AS
SELECT * FROM Orders WHERE Country = @Country;
```

- Pour 'Monaco' (peu de commandes) : Plan rapide avec Index Seek
- Pour 'France' (beaucoup de commandes) : Le même plan devient très lent

**Solution :**
1. Identifier les deux plans différents dans Query Store
2. Déterminer quel plan est globalement le meilleur
3. Forcer ce plan

**Meilleure solution à long terme :**
```sql
-- Utiliser OPTION (RECOMPILE) pour une recompilation à chaque exécution
CREATE PROCEDURE GetOrdersByCountry @Country VARCHAR(50)
AS
SELECT * FROM Orders WHERE Country = @Country
OPTION (RECOMPILE);

-- Puis retirer le forçage
```

### Scénario 2 : Après une migration

**Problème :**
Vous migrez de SQL Server 2017 vers SQL Server 2022. Certaines requêtes deviennent lentes à cause du nouveau cardinality estimator.

**Solution immédiate :**
Forcer les bons plans de l'ancienne version (exportés via Query Store).

**Solution à long terme :**
```sql
-- Option 1 : Utiliser l'ancien niveau de compatibilité temporairement
ALTER DATABASE MyDatabase SET COMPATIBILITY_LEVEL = 140; -- SQL 2017

-- Option 2 : Utiliser l'ancien cardinality estimator
ALTER DATABASE SCOPED CONFIGURATION SET LEGACY_CARDINALITY_ESTIMATION = ON;

-- Puis progressivement optimiser les requêtes pour SQL 2022
-- Et retirer les plans forcés un par un
```

### Scénario 3 : Pic de charge imprévu

**Problème :**
Un événement marketing génère 10x plus de trafic que d'habitude. Certaines requêtes s'effondrent.

**Solution d'urgence :**
1. Identifier les requêtes problématiques
2. Regarder dans l'historique Query Store leur comportement habituel
3. Forcer les plans qui fonctionnaient bien avant le pic
4. Cela stabilise le système le temps du pic
5. Après le pic, analyser et optimiser correctement

## Alternatives au forçage

Avant de forcer un plan, considérez ces alternatives :

### 1. Utiliser des Query Hints

```sql
-- Au lieu de forcer le plan, ajoutez un hint dans la requête (paramétrée)
-- OPTIMIZE FOR s'applique à un PARAMÈTRE : la requête doit donc en utiliser un
DECLARE @Country VARCHAR(50) = 'France';
SELECT * FROM Orders
WHERE Country = @Country
OPTION (OPTIMIZE FOR (@Country = 'France'));  -- Optimiser pour une valeur de paramètre spécifique
```

### 2. Mettre à jour les statistiques

```sql
-- Les statistiques obsolètes causent souvent de mauvais plans
UPDATE STATISTICS Customers WITH FULLSCAN;
```

### 3. Créer des index manquants

```sql
-- Si l'ancien plan utilisait un index qui a été supprimé
CREATE INDEX IX_Orders_Country ON Orders(Country) INCLUDE (OrderDate, Amount);
```

### 4. Réecrire la requête

Parfois, une petite réécriture peut aider l'optimiseur :

```sql
-- Avant (mauvais plan)
SELECT * FROM Orders WHERE YEAR(OrderDate) = 2024;

-- Après (bon plan) - SARGable
SELECT * FROM Orders WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';
```

### 5. Utiliser des Plan Guides

Pour les requêtes que vous ne pouvez pas modifier (librairies tierces) :

```sql
-- Créer un plan guide
EXEC sp_create_plan_guide
    @name = N'GuideForThirdPartyQuery',
    @stmt = N'SELECT * FROM Orders WHERE Country = @Country',
    @type = N'SQL',
    @module_or_batch = NULL,
    @params = N'@Country VARCHAR(50)',
    @hints = N'OPTION (OPTIMIZE FOR (@Country = ''France''))';
```

## Monitoring et maintenance

### Dashboard de surveillance

```sql
-- Vue d'ensemble des plans forcés et leur santé
SELECT
    q.query_id,
    LEFT(qt.query_sql_text, 60) as query_preview,
    p.plan_id,
    p.force_failure_count,
    p.last_force_failure_reason_desc,
    DATEDIFF(day, p.create_time, GETDATE()) as days_since_forced,
    rs.count_executions as total_executions,
    rs.avg_duration / 1000.0 as avg_duration_ms,
    CASE
        WHEN p.force_failure_count > 0 THEN '⚠️ WARNING'
        WHEN DATEDIFF(day, p.create_time, GETDATE()) > 90 THEN '⚠️ REVIEW NEEDED'
        ELSE '✅ OK'
    END as status
FROM sys.query_store_query q
INNER JOIN sys.query_store_query_text qt
    ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan p
    ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats rs
    ON p.plan_id = rs.plan_id
WHERE p.is_forced_plan = 1
ORDER BY
    CASE
        WHEN p.force_failure_count > 0 THEN 1
        WHEN DATEDIFF(day, p.create_time, GETDATE()) > 90 THEN 2
        ELSE 3
    END,
    days_since_forced DESC;
```

## Résumé

Le forçage d'un plan d'exécution est une fonctionnalité puissante du Query Store qui permet de :

**Avantages :**
- ✅ Corriger rapidement une régression de performance
- ✅ Stabiliser les performances en production
- ✅ Gagner du temps pour investiguer la cause racine
- ✅ Protéger contre les changements de plan intempestifs

**Limites :**
- ⚠️ C'est une solution temporaire, pas permanente
- ⚠️ Le plan forcé peut devenir obsolète avec le temps
- ⚠️ Risque d'oublier les plans forcés
- ⚠️ Ne corrige pas la cause sous-jacente

**Processus recommandé :**
```
1. Identifier une régression avec Query Store
2. Comparer les plans (ancien vs nouveau)
3. Forcer le bon plan (solution immédiate)
4. Documenter la décision
5. Investiguer la cause racine
6. Appliquer une vraie correction
7. Retirer le forçage
8. Vérifier que tout fonctionne bien
```

**Règle d'or :** Forcez avec parcimonie, documentez systématiquement, révisez régulièrement.

---

**Points clés à retenir :**
- Le forçage de plan contourne l'optimiseur pour une requête spécifique
- Facile à faire via SSMS (clic droit → Force Plan) ou T-SQL (sp_query_store_force_plan)
- Utilisez-le comme solution d'urgence, pas comme solution permanente
- Documentez toujours pourquoi vous forcez un plan
- Révisez régulièrement vos plans forcés (surtout après 30+ jours)
- Retirez le forçage une fois la cause racine corrigée
- Surveillez les échecs de forçage (force_failure_count)
