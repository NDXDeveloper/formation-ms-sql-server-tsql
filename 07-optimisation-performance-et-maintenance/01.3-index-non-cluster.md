# 7.1.3 Index Non-Cluster (Non-Clustered) : La structure B-Tree

## Introduction

Dans les sections précédentes, nous avons vu :
- Pourquoi les index sont importants (7.1.1)
- L'index clustered qui détermine l'ordre physique de la table (7.1.2)

Maintenant, découvrons les **index non-clustered** (non-cluster), qui sont des structures **séparées** de la table et permettent d'accélérer les recherches sur **d'autres colonnes** que la clé clustered.

## Rappel : Index Clustered vs Non-Clustered

### L'analogie complète du livre

**Index Clustered = Le dictionnaire**
- Les mots (données) sont **physiquement** rangés dans l'ordre alphabétique
- Le contenu EST l'index
- Un seul ordre possible

**Index Non-Clustered = L'index à la fin d'un livre**
- Le livre a son propre ordre (chapitres 1, 2, 3...)
- À la fin, un index séparé vous dit : "Marketing : voir pages 45, 78, 132"
- L'index est une **structure séparée** qui pointe vers les pages
- Vous pouvez avoir **plusieurs index** (index des noms, index des lieux, index des concepts)

## Qu'est-ce qu'un Index Non-Clustered ?

### Définition

Un **index non-clustered** est une structure de données **séparée** de la table qui contient :
1. **Les valeurs de la ou des colonnes indexées** (triées)
2. **Un pointeur** vers l'emplacement des données dans la table

**Point important** : Contrairement à l'index clustered, un index non-clustered **ne change pas** l'ordre physique de la table. Il crée simplement une copie triée de certaines colonnes avec des pointeurs.

### Caractéristiques principales

- ✅ **Séparé de la table** : C'est une structure additionnelle
- ✅ **Multiple** : Une table peut avoir jusqu'à **999 index non-clustered** (mais n'en abusez pas !)
- ✅ **Indépendant** : N'affecte pas l'ordre physique des données
- ✅ **Coût** : Prend de l'espace disque et ralentit les INSERT/UPDATE/DELETE

```
Index IX_Clients_Email (structure séparée, triée par Email)

- Pour chaque email, il stocke le ClientID (la clé clustered) qui permet de retrouver la ligne complète

```

**Vous pouvez avoir plusieurs index non-clustered**, chacun trié sur une colonne différente !

## Comment fonctionne une recherche avec Index Non-Clustered ?

### Exemple : Recherche par Email

```sql
SELECT * FROM Clients WHERE Email = 'marie@email.com';
```

**Étape 1** : SQL Server consulte l'index non-clustered sur Email
```
Index IX_Clients_Email
┌──────────────────────┬──────────┐
│ Email                │ ClientID │
├──────────────────────┼──────────┤
│ jean@email.com       │ 3        │
│ luc@email.com        │ 1        │
│ marie@email.com      │ 8        │ ← Trouvé !
│ paul@email.com       │ 2        │
│ sophie@email.com     │ 5        │
└──────────────────────┴──────────┘
```
Résultat : ClientID = 8

**Étape 2** : SQL Server va chercher la ligne complète dans la table (via l'index clustered)
```
Table Clients (index clustered sur ClientID)
┌──────────┬─────────┬─────────┬──────────────────────┬───────┐
│ ClientID │ Nom     │ Prenom  │ Email                │ Ville │
├──────────┼─────────┼─────────┼──────────────────────┼───────┤
│ 8        │ Bernard │ Marie   │ marie@email.com      │ Paris │ ← Ligne retrouvée
└──────────┴─────────┴─────────┴──────────────────────┴───────┘
```

Cette opération en deux étapes s'appelle un **"Key Lookup"** ou **"Bookmark Lookup"**.

### Performance : Avec vs Sans Index

**Sans index non-clustered sur Email** :
- Table Scan : parcourir toutes les lignes (lent si millions de lignes)
- Exemple : 1 000 000 de lectures

**Avec index non-clustered sur Email** :
- Index Seek : trouver dans l'index (quelques lectures)
- Key Lookup : aller chercher la ligne complète (1 lecture)
- Exemple : 3-5 lectures au total

**Gain** : 1 000 000 lectures → 5 lectures = **200 000 fois plus rapide** !

## La Structure B-Tree (Balanced Tree)

Les index non-clustered utilisent la même structure que les index clustered : **le B-Tree**.

### Qu'est-ce qu'un B-Tree ?

**B-Tree** = Balanced Tree = Arbre équilibré

C'est une structure en **niveaux hiérarchiques** qui permet des recherches ultra-rapides.

### Analogie : Chercher un mot dans le dictionnaire

Imaginez chercher le mot "Ordinateur" dans un dictionnaire de 100 000 mots :

**Méthode linéaire (sans arbre)** :
- Regarder mot 1, mot 2, mot 3... jusqu'à trouver "Ordinateur"
- Jusqu'à 100 000 vérifications

**Méthode avec B-Tree (dichotomie)** :
1. Ouvrir au milieu : "M" → "Ordinateur" est après "M", aller à droite
2. Ouvrir au milieu de la partie droite : "S" → "Ordinateur" est avant "S", aller à gauche
3. Continuer... Trouvé en environ 17 étapes (log₂(100 000) ≈ 17)

C'est **exponentiel** : pour 1 million d'entrées, seulement ~20 étapes !

### Structure B-Tree d'un Index Non-Clustered

```
Structure à 3 niveaux d'un index non-clustered sur Email
(Simplifié pour la compréhension)

Niveau Racine (Root)
┌────────────────────────────────────┐
│    A-M    │    N-Z                 │
└───────┬────────────┬───────────────┘
        │            │
        │            │
┌───────▼───────┐  ┌─▼─────────────┐
│ Niveau        │  │ Niveau        │
│ Intermédiaire │  │ Intermédiaire │
├───────────────┤  ├───────────────┤
│ A-F │ G-M     │  │ N-S │ T-Z     │
└──┬───────┬────┘  └────┬──────┬───┘
   │       │            │      │
   │       │            │      │
┌──▼─────┐┌▼───────┐┌───▼───┐┌─▼─────┐
│Feuilles│ Feuilles│Feuilles│Feuilles│
│(Leaf)  │(Leaf)   │(Leaf)  │(Leaf)  │
├────────┼─────────┼────────┼────────┤
│ Email  │ Email   │ Email  │ Email  │
│ + Ptr  │ + Ptr   │ + Ptr  │ + Ptr  │
├────────┼─────────┼────────┼────────┤
│a@...→1 │g@...→4  │n@...→7 │t@...→10│
│b@...→2 │h@...→5  │o@...→8 │u@...→11│
│c@...→3 │i@...→6  │p@...→9 │v@...→12│
└────────┴─────────┴────────┴────────┘
```

### Les niveaux du B-Tree

#### 1. **Niveau Racine (Root)**
- Le sommet de l'arbre
- Contient des pointeurs vers les niveaux intermédiaires
- Toujours chargé en mémoire (très rapide)

#### 2. **Niveaux Intermédiaires (Intermediate)**
- Peuvent exister ou non selon la taille de l'index
- Permettent de naviguer vers le bon endroit
- Plus la table est grande, plus il y a de niveaux

#### 3. **Niveau Feuilles (Leaf)**
- Le niveau le plus bas
- Contient les **vraies données** de l'index :
  - Les valeurs de la colonne indexée (triées)
  - Les pointeurs vers la table (clé clustered ou RID)

### Exemple de recherche dans le B-Tree

**Recherche** : `WHERE Email = 'marie@email.com'`

```
Étape 1 - Racine :
"marie" commence par "m" → aller dans la branche A-M

Étape 2 - Intermédiaire :
"m" est dans la plage G-M → aller dans cette branche

Étape 3 - Feuilles :
Parcourir les emails commençant par "m" jusqu'à trouver "marie@email.com"
→ Trouvé ! ClientID = 8

Étape 4 - Key Lookup (si nécessaire) :
Aller dans la table principale pour récupérer toutes les colonnes
```

**Nombre de lectures** : Généralement 3-4 pour l'index + 1 pour le Key Lookup = 4-5 au total.

### Propriétés importantes du B-Tree

#### ✅ Équilibré (Balanced)
- Tous les chemins de la racine aux feuilles ont la **même longueur**
- Garantit des performances prévisibles
- Pas de "branches longues" qui ralentiraient certaines recherches

#### ✅ Ordonné (Sorted)
- Les feuilles sont triées de gauche à droite
- Permet les recherches par plage (`WHERE Ville BETWEEN 'L' AND 'P'`)
- Facilite les parcours ordonnés (`ORDER BY Ville`)

#### ✅ Efficace en espace
- Chaque nœud (page) contient plusieurs valeurs (généralement des centaines)
- Minimise le nombre de niveaux nécessaires

#### ✅ Auto-équilibrant
- Quand vous ajoutez/supprimez des données, le B-Tree se réorganise automatiquement
- Maintient l'équilibre sans intervention manuelle

## Création d'un Index Non-Clustered

### Syntaxe de base

```sql
CREATE INDEX nom_de_l_index
ON nom_table (colonne);
```

### Exemples pratiques

#### Exemple 1 : Index simple sur une colonne

```sql
-- Index sur la colonne Email
CREATE INDEX IX_Clients_Email
ON Clients (Email);
```

Utilisation :
```sql
-- Cette requête utilisera l'index
SELECT * FROM Clients WHERE Email = 'paul@email.com';
```

#### Exemple 2 : Index sur plusieurs colonnes (index composite)

```sql
-- Index sur Ville puis Nom
CREATE INDEX IX_Clients_Ville_Nom
ON Clients (Ville, Nom);
```

Utilisation :
```sql
-- Très efficace : utilise les deux colonnes de l'index
SELECT * FROM Clients WHERE Ville = 'Paris' AND Nom = 'Durand';

-- Efficace : utilise la première colonne (Ville)
SELECT * FROM Clients WHERE Ville = 'Paris';

-- PAS efficace : n'utilise pas la première colonne
SELECT * FROM Clients WHERE Nom = 'Durand';
-- L'ordre des colonnes dans l'index est crucial !
```

**Règle importante** : Pour un index composite (Ville, Nom), l'ordre compte !
- ✅ Efficace : `WHERE Ville = ...` ou `WHERE Ville = ... AND Nom = ...`
- ❌ Peu efficace : `WHERE Nom = ...` (ne peut pas utiliser l'index efficacement)

#### Exemple 3 : Index avec INCLUDE

```sql
-- Index sur Email avec colonnes incluses
CREATE INDEX IX_Clients_Email_Inc
ON Clients (Email)
INCLUDE (Nom, Prenom);
```

**Avantage** : Évite le Key Lookup !

```sql
-- Cette requête n'a PAS besoin de Key Lookup
-- Car Nom et Prenom sont dans l'index
SELECT Nom, Prenom FROM Clients WHERE Email = 'paul@email.com';
```

Sans INCLUDE :
1. Chercher dans l'index → trouver ClientID
2. Key Lookup → aller chercher Nom et Prenom dans la table

Avec INCLUDE :
1. Chercher dans l'index → trouver directement Email, Nom, Prenom
2. Pas de Key Lookup nécessaire !

**Attention** : INCLUDE augmente la taille de l'index.

## Le Concept de "Covering Index" (Index Couvrant)

### Définition

Un **covering index** (index couvrant) est un index qui contient **toutes les colonnes** nécessaires pour répondre à une requête, sans avoir besoin d'accéder à la table.

### Exemple sans Covering Index

```sql
-- Requête
SELECT Nom, Prenom FROM Clients WHERE Email = 'paul@email.com';

-- Index existant
CREATE INDEX IX_Clients_Email ON Clients (Email);

-- Opérations SQL Server :
-- 1. Index Seek sur IX_Clients_Email → trouve ClientID = 2
-- 2. Key Lookup → va chercher Nom et Prenom dans la table
-- Total : 2 opérations (Index Seek + Key Lookup)
```

### Exemple avec Covering Index

```sql
-- Requête (la même)
SELECT Nom, Prenom FROM Clients WHERE Email = 'paul@email.com';

-- Index couvrant
CREATE INDEX IX_Clients_Email_Covering
ON Clients (Email)
INCLUDE (Nom, Prenom);

-- Opérations SQL Server :
-- 1. Index Seek sur IX_Clients_Email_Covering → trouve Email, Nom, Prenom
-- Total : 1 opération (Index Seek seulement)
-- Pas de Key Lookup nécessaire !
```

### Avantages d'un Covering Index

✅ **Performance maximale** : Pas de Key Lookup, donc plus rapide
✅ **Moins de lectures** : Une seule structure à consulter
✅ **Évite la contention** : Moins de blocages sur la table principale

### Inconvénients d'un Covering Index

❌ **Taille importante** : Plus de colonnes = index plus volumineux
❌ **Maintenance coûteuse** : Les INSERT/UPDATE/DELETE sont plus lents
❌ **Espace disque** : Consomme beaucoup d'espace

**Règle d'or** : Créez des covering index uniquement pour les requêtes **très fréquentes** et **critiques**.

## Index Non-Clustered : Points vers quoi ?

### Dans une table avec Index Clustered

```
Table avec index clustered sur ClientID :

Index Non-Clustered sur Email
┌──────────────────────┬──────────────┐
│ Email                │ ClientID     │ ← Pointe vers la clé clustered
├──────────────────────┼──────────────┤
│ jean@email.com       │ 3            │
│ marie@email.com      │ 8            │
└──────────────────────┴──────────────┘
```

**Pointeur** = La clé de l'index clustered (ici, ClientID)

Pour retrouver la ligne complète :
1. Utiliser l'index non-clustered → trouver ClientID = 8
2. Utiliser l'index clustered → aller directement à ClientID = 8 dans la table

### Dans une table HEAP (sans index clustered)

```
Table HEAP (pas d'index clustered) :

Index Non-Clustered sur Email
┌──────────────────────┬──────────────┐
│ Email                │ RID          │ ← Pointe vers l'emplacement physique
├──────────────────────┼──────────────┤
│ jean@email.com       │ (1:234:5)    │
│ marie@email.com      │ (1:567:2)    │
└──────────────────────┴──────────────┘
```

**Pointeur** = RID (Row Identifier) = Adresse physique de la ligne
- Format : (FileID : PageID : SlotID)
- Exemple : (1:567:2) = Fichier 1, Page 567, Slot 2

**Problème** : Si les données bougent physiquement (rare mais possible), le RID change et l'index doit être mis à jour.

**C'est une raison de plus d'avoir un index clustered** (le pointeur est logique, pas physique).

## Quand créer un Index Non-Clustered ?

### ✅ Créez un index non-clustered quand :

#### 1. Colonne fréquemment utilisée dans WHERE

```sql
-- Recherches fréquentes sur Email
SELECT * FROM Clients WHERE Email = 'user@email.com';

-- Solution : Index non-clustered sur Email
CREATE INDEX IX_Clients_Email ON Clients (Email);
```

#### 2. Colonne utilisée dans les JOIN

```sql
-- Jointure fréquente sur ClientID
SELECT c.Nom, co.NumeroCommande
FROM Clients c
INNER JOIN Commandes co ON c.ClientID = co.ClientID;

-- Solution : Index non-clustered sur Commandes.ClientID
CREATE INDEX IX_Commandes_ClientID ON Commandes (ClientID);
```

#### 3. Colonne utilisée dans ORDER BY

```sql
-- Tri fréquent sur DateInscription
SELECT * FROM Clients ORDER BY DateInscription DESC;

-- Solution : Index non-clustered sur DateInscription
CREATE INDEX IX_Clients_DateInscription ON Clients (DateInscription DESC);
```

#### 4. Requêtes avec forte sélectivité

**Sélectivité** = Pourcentage de lignes retournées

```sql
-- Haute sélectivité : 1 ligne sur 1 million
SELECT * FROM Clients WHERE ClientID = 12345;
-- ✅ Index très utile

-- Faible sélectivité : 800 000 lignes sur 1 million
SELECT * FROM Clients WHERE Actif = 1;
-- ❌ Index peu utile (SQL Server fera un Table Scan de toute façon)
```

**Règle** : Un index est utile si la requête retourne **moins de 10-20% des lignes**.

### ❌ N'en créez PAS quand :

#### 1. Colonne avec peu de valeurs distinctes

```sql
-- Colonne Sexe : seulement 2 valeurs (M, F)
-- ❌ Mauvais candidat pour un index
CREATE INDEX IX_Clients_Sexe ON Clients (Sexe);
```

#### 2. Table très petite

```sql
-- Table de 50 lignes
-- ❌ Pas besoin d'index (Table Scan est rapide)
```

#### 3. Colonne rarement utilisée dans les requêtes

```sql
-- Si vous ne cherchez jamais par NumeroPasseport
-- ❌ Pas besoin d'index
CREATE INDEX IX_Clients_NumeroPasseport ON Clients (NumeroPasseport);
```

#### 4. Table avec beaucoup d'écritures et peu de lectures

```sql
-- Table de logs : 10 000 INSERT/seconde, 1 SELECT/jour
-- ❌ Les index ralentiraient trop les insertions
```

## Coût des Index Non-Clustered

### 💾 Espace disque

Chaque index non-clustered occupe de l'espace :

```
Table Clients : 1 Go
Index sur Email : 200 Mo
Index sur Ville : 150 Mo
Index sur DateInscription : 100 Mo

Total : 1 Go + 450 Mo = 1,45 Go

Surcoût : 45% d'espace supplémentaire
```

### ⏱️ Ralentissement des opérations d'écriture

**Sans index non-clustered** :
```sql
INSERT INTO Clients (ClientID, Nom, Email)
VALUES (100, 'Dubois', 'dubois@email.com');

-- 1 opération : insérer dans la table
```

**Avec 3 index non-clustered** :
```sql
INSERT INTO Clients (ClientID, Nom, Email)
VALUES (100, 'Dubois', 'dubois@email.com');

-- 4 opérations :
-- 1. Insérer dans la table (index clustered)
-- 2. Mettre à jour l'index sur Email
-- 3. Mettre à jour l'index sur Ville
-- 4. Mettre à jour l'index sur DateInscription

-- C'est 4 fois plus lent !
```

### 📊 Équilibre Lecture vs Écriture

| Type d'application | Ratio Lecture/Écriture | Nombre d'index recommandé |
|-------------------|------------------------|---------------------------|
| Application OLTP (transactions) | 50/50 | 2-5 index |
| Application de reporting | 95/5 | 5-15 index |
| Table de logs | 5/95 | 0-2 index |
| Datawarehouse | 99/1 | 10-30 index |

**OLTP** = Online Transaction Processing (ex : site e-commerce)
**Datawarehouse** = Entrepôt de données (ex : analyses, BI)

## Index Non-Clustered : Bonnes Pratiques

### ✅ DO (À faire)

1. **Indexez les colonnes de jointure**
```sql
CREATE INDEX IX_Commandes_ClientID ON Commandes (ClientID);
```

2. **Indexez les colonnes de recherche fréquente**
```sql
CREATE INDEX IX_Clients_Email ON Clients (Email);
```

3. **Utilisez INCLUDE pour les covering index critiques**
```sql
CREATE INDEX IX_Clients_Email_Cover
ON Clients (Email)
INCLUDE (Nom, Prenom);
```

4. **Nommez vos index clairement**
```sql
-- ✅ Bon : IX_TableName_ColumnName
CREATE INDEX IX_Clients_Email ON Clients (Email);

-- ❌ Mauvais : index1
CREATE INDEX index1 ON Clients (Email);
```

5. **Surveillez l'utilisation des index**
```sql
-- Vérifiez quels index sont utilisés
-- (Requête avancée, juste pour référence)
SELECT
    OBJECT_NAME(s.object_id) AS TableName,
    i.name AS IndexName,
    s.user_seeks + s.user_scans AS TotalReads
FROM sys.dm_db_index_usage_stats s
INNER JOIN sys.indexes i ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE s.database_id = DB_ID()
ORDER BY TotalReads DESC;
```

### ❌ DON'T (À éviter)

1. **N'indexez pas tout**
```sql
-- ❌ Trop d'index !
CREATE INDEX IX1 ON Clients (Nom);
CREATE INDEX IX2 ON Clients (Prenom);
CREATE INDEX IX3 ON Clients (Email);
CREATE INDEX IX4 ON Clients (Telephone);
CREATE INDEX IX5 ON Clients (Ville);
CREATE INDEX IX6 ON Clients (CodePostal);
CREATE INDEX IX7 ON Clients (DateInscription);
-- ... 20 index au total

-- Les INSERT/UPDATE/DELETE seront catastrophiquement lents !
```

2. **N'indexez pas les colonnes avec peu de valeurs distinctes**
```sql
-- ❌ Seulement 2 valeurs possibles (Actif : 0 ou 1)
CREATE INDEX IX_Clients_Actif ON Clients (Actif);
```

3. **Ne créez pas d'index redondants**
```sql
-- ❌ Redondant !
CREATE INDEX IX_Clients_Ville ON Clients (Ville);
CREATE INDEX IX_Clients_Ville_Nom ON Clients (Ville, Nom);

-- Le deuxième index peut déjà servir pour les recherches sur Ville seul
-- Le premier est inutile !
```

4. **Ne créez pas d'index sans analyser les performances**
```sql
-- ❌ Créer un index "au cas où"
-- Analysez d'abord les requêtes lentes avec les plans d'exécution
```

## Comparaison : Clustered vs Non-Clustered

### Tableau récapitulatif

| Caractéristique | Index Clustered | Index Non-Clustered |
|-----------------|-----------------|---------------------|
| **Nombre par table** | 1 maximum | Jusqu'à 999 |
| **Ordre physique** | Détermine l'ordre physique | N'affecte pas l'ordre |
| **Contenu** | Contient toutes les colonnes | Contient colonnes indexées + pointeur |
| **Structure** | B-Tree | B-Tree |
| **Les feuilles contiennent** | Les données elles-mêmes | Pointeurs vers la table |
| **Espace** | = Taille de la table | Additionnel |
| **Utilisation typique** | Clé primaire | Colonnes de recherche, jointure |
| **Performance recherche** | Excellente sur la clé | Très bonne (+ Key Lookup si nécessaire) |
| **Performance insertion** | Bonne (si clé croissante) | Ralentit proportionnellement au nombre d'index |

### Quand utiliser l'un ou l'autre ?

**Index Clustered** :
- Sur la clé primaire (99% des cas)
- Colonnes avec large plage de valeurs
- Colonnes fréquemment utilisées pour ORDER BY

**Index Non-Clustered** :
- Sur les colonnes de recherche fréquente
- Sur les clés étrangères
- Pour optimiser des requêtes spécifiques

## Conclusion

Les **index non-clustered** sont des outils puissants pour optimiser les performances des requêtes. Ils utilisent la structure **B-Tree** qui permet des recherches ultra-rapides, même sur des millions de lignes.

### 🎯 Points clés à retenir

1. **Structure séparée** : Les index non-clustered sont des copies triées de colonnes avec des pointeurs
2. **Multiple** : Vous pouvez avoir jusqu'à 999 index non-clustered (mais soyez raisonnables !)
3. **B-Tree** : Permet des recherches logarithmiques (très rapides)
4. **Coût** : Prennent de l'espace et ralentissent les écritures
5. **Covering Index** : Peut éliminer le Key Lookup pour des performances maximales
6. **Sélectivité** : Efficaces uniquement si la requête retourne un petit pourcentage de lignes

### ✅ Règles d'or

- Indexez les colonnes de **recherche fréquente** (WHERE, JOIN)
- Utilisez des **index composites** avec le bon ordre de colonnes
- Créez des **covering index** pour les requêtes critiques
- **Surveillez** l'utilisation réelle de vos index
- **Équilibrez** entre performances de lecture et d'écriture
