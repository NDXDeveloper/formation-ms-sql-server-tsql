# 8.4.3 DENY (Refuser explicitement)

## Introduction

Vous connaissez maintenant **GRANT**, qui permet d'**autoriser** des permissions. Mais que faire si vous voulez **interdire explicitement** quelque chose à quelqu'un ?

**Analogie simple** : Imaginez un panneau d'affichage dans un immeuble. Il y a trois types de messages possibles :

1. 🟢 **"Autorisé"** (GRANT) - "Vous pouvez accéder à la salle de réunion"
2. 🔴 **"Interdit"** (DENY) - "Vous ne pouvez PAS accéder au coffre-fort"
3. ⚪ **"Rien"** (pas de permission) - Absence d'autorisation = pas d'accès par défaut

La commande **DENY** est l'équivalent du panneau "Interdit" : elle refuse **explicitement** une permission, même si cette permission serait normalement accordée par ailleurs.

## Qu'est-ce que DENY ?

**DENY** est une commande SQL qui fait partie du **DCL (Data Control Language)**. Elle permet de **refuser explicitement** une permission à un user ou un rôle.

### La règle d'or : DENY est plus fort que GRANT

C'est le concept le plus important à comprendre :

**🔴 DENY gagne TOUJOURS sur GRANT 🟢**

Peu importe combien de GRANT vous avez, un seul DENY suffit à bloquer l'accès.

### Syntaxe de base

```sql
DENY <permission(s)>
ON <objet>
TO <principal>
[CASCADE];
```

La syntaxe est quasiment identique à GRANT, mais l'effet est inverse.

## Différence fondamentale : DENY vs Absence de GRANT

C'est crucial de bien comprendre la différence :

### Absence de GRANT (comportement par défaut)

```sql
-- Jean n'a AUCUNE permission sur la table Salaires
-- (aucun GRANT n'a été fait)

-- Résultat : Jean ne peut pas accéder aux Salaires
SELECT * FROM dbo.Salaires;  -- ❌ Échoue
```

**Mais** : Si Jean rejoint un rôle qui a accès, il y aura accès :

```sql
-- Plus tard, Jean rejoint le rôle RH
ALTER ROLE RoleRH ADD MEMBER Jean;

-- Le rôle RH a accès aux salaires
GRANT SELECT ON dbo.Salaires TO RoleRH;

-- Maintenant Jean peut accéder aux Salaires
SELECT * FROM dbo.Salaires;  -- ✅ Fonctionne
```

### DENY explicite

```sql
-- On refuse EXPLICITEMENT l'accès aux Salaires à Jean
DENY SELECT ON dbo.Salaires TO Jean;

-- Résultat : Jean ne peut pas accéder aux Salaires
SELECT * FROM dbo.Salaires;  -- ❌ Échoue
```

**Même si** Jean rejoint un rôle qui a accès, le DENY bloque :

```sql
-- Jean rejoint le rôle RH
ALTER ROLE RoleRH ADD MEMBER Jean;

-- Le rôle RH a accès aux salaires
GRANT SELECT ON dbo.Salaires TO RoleRH;

-- MAIS Jean ne peut TOUJOURS PAS accéder aux Salaires
-- Car le DENY sur Jean surpasse le GRANT sur RoleRH
SELECT * FROM dbo.Salaires;  -- ❌ Échoue quand même !
```

**Schéma visuel** :

```
Scénario 1 : Absence de GRANT
═══════════════════════════════
Jean ──┐
       ├──→ RoleRH ──GRANT SELECT──→ Salaires ✅ ACCÈS
       │    (GRANT gagne)
       └──→ Pas de permission directe

Résultat : Jean a accès via le rôle


Scénario 2 : DENY explicite
═══════════════════════════════
Jean ──┬──DENY SELECT──┐
       │               ↓
       └──→ RoleRH ──GRANT SELECT──→ Salaires ❌ REFUSÉ
            (DENY gagne sur GRANT)

Résultat : Jean n'a PAS accès, le DENY bloque tout
```

## Quand utiliser DENY ?

DENY est utile dans des situations spécifiques où vous devez **faire une exception** à une permission générale.

### Cas d'usage 1 : Exception dans un groupe

**Scénario** : Tous les managers peuvent voir les salaires, sauf un manager spécifique.

```sql
-- Tous les managers ont accès aux salaires
GRANT SELECT ON dbo.Salaires TO RoleManagers;

-- Ajouter tous les managers au rôle
ALTER ROLE RoleManagers ADD MEMBER Manager1;
ALTER ROLE RoleManagers ADD MEMBER Manager2;
ALTER ROLE RoleManagers ADD MEMBER Manager3;  -- Manager en probation

-- MAIS Manager3 est nouveau, on ne veut pas encore qu'il voie les salaires
DENY SELECT ON dbo.Salaires TO Manager3;
```

**Résultat** :
- Manager1 et Manager2 peuvent voir les salaires ✅
- Manager3 ne peut PAS voir les salaires ❌ (malgré son appartenance au rôle)

### Cas d'usage 2 : Protéger des colonnes sensibles

**Scénario** : Donner accès à une table, mais bloquer certaines colonnes sensibles.

```sql
-- Accès complet à la table Employes pour les RH
GRANT SELECT ON dbo.Employes TO RoleRH;

-- SAUF pour certaines colonnes très sensibles
DENY SELECT ON dbo.Employes (NumeroSecuriteSociale, NumeroCarteBancaire) TO RoleRH;
```

**Résultat** :
- Les RH peuvent voir toutes les colonnes ✅
- SAUF NumeroSecuriteSociale et NumeroCarteBancaire ❌

### Cas d'usage 3 : Protection contre les suppressions accidentelles

**Scénario** : Permettre de lire et modifier, mais pas de supprimer.

```sql
-- L'application peut lire et modifier les produits
GRANT SELECT, INSERT, UPDATE ON dbo.Produits TO AppUser;

-- Mais pour éviter les suppressions accidentelles, on les bloque explicitement
DENY DELETE ON dbo.Produits TO AppUser;
```

**Résultat** : Même si quelqu'un ajoute AppUser à un rôle avec DELETE, le DENY bloquera.

### Cas d'usage 4 : Audit et conformité

**Scénario** : Un auditeur doit pouvoir lire les données mais jamais les modifier.

```sql
-- L'auditeur peut tout lire
GRANT SELECT ON SCHEMA::dbo TO Auditeur;

-- Bloquer explicitement toute modification (double sécurité)
DENY INSERT, UPDATE, DELETE ON SCHEMA::dbo TO Auditeur;
```

**Résultat** : Garantie absolue que l'auditeur ne peut QUE consulter, jamais modifier.

## Exemples pratiques détaillés

### Exemple 1 : Manager temporaire avec accès limité

```sql
-- Contexte : Un manager remplace temporairement le responsable RH
-- Il doit accéder à certaines tables RH, mais pas aux salaires

-- 1. Ajouter le manager au rôle RH (qui a beaucoup de permissions)
ALTER ROLE RoleRH ADD MEMBER ManagerTemporaire;

-- Le rôle RH a accès à tout
GRANT SELECT ON SCHEMA::RH TO RoleRH;  -- Inclut la table Salaires

-- 2. Bloquer spécifiquement l'accès aux salaires
DENY SELECT ON dbo.Salaires TO ManagerTemporaire;

-- Résultat :
-- ManagerTemporaire peut voir : Employes, Conges, Postes, etc. ✅
-- ManagerTemporaire ne peut PAS voir : Salaires ❌
```

**Vérification** :
```sql
-- En tant que ManagerTemporaire
EXECUTE AS USER = 'ManagerTemporaire';

-- Ceci fonctionne
SELECT * FROM dbo.Employes;  ✅

-- Ceci échoue
SELECT * FROM dbo.Salaires;  ❌
-- Message : "The SELECT permission was denied on the object 'Salaires'"

REVERT;
```

### Exemple 2 : Protection d'une table critique

```sql
-- Contexte : La table ConfigurationSysteme est critique
-- Les développeurs doivent pouvoir lire la config, mais JAMAIS la modifier

-- 1. Créer un rôle pour les développeurs
CREATE ROLE RoleDeveloppeurs;

-- 2. Donner accès en lecture à tout le schéma
GRANT SELECT ON SCHEMA::dbo TO RoleDeveloppeurs;

-- 3. Donner aussi des droits d'écriture sur les tables de développement
GRANT INSERT, UPDATE, DELETE ON SCHEMA::Dev TO RoleDeveloppeurs;

-- 4. Mais bloquer TOUTE modification sur la table critique
DENY INSERT, UPDATE, DELETE ON dbo.ConfigurationSysteme TO RoleDeveloppeurs;

-- Résultat :
-- Les développeurs peuvent lire ConfigurationSysteme ✅
-- Ils ne peuvent PAS la modifier ❌ (même par erreur)
```

### Exemple 3 : Cascader un DENY à travers les appartenances

```sql
-- Contexte : Créer une hiérarchie de rôles avec restrictions

-- Niveau 1 : Rôle général (accès large)
CREATE ROLE RoleEmployes;
GRANT SELECT ON SCHEMA::Public TO RoleEmployes;

-- Niveau 2 : Rôle spécialisé (hérite du rôle général)
CREATE ROLE RoleSupport;
ALTER ROLE RoleEmployes ADD MEMBER RoleSupport;  -- RoleSupport hérite de RoleEmployes
GRANT INSERT, UPDATE ON dbo.Tickets TO RoleSupport;

-- Niveau 3 : User (membre du rôle spécialisé)
CREATE USER AgentSupport FOR LOGIN [DOMAINE\Agent];
ALTER ROLE RoleSupport ADD MEMBER AgentSupport;

-- Maintenant, bloquer explicitement certaines tables pour les Supports
DENY SELECT ON dbo.ComptabiliteInterne TO RoleSupport;

-- Résultat :
-- AgentSupport peut lire toutes les tables de Public ✅
-- AgentSupport peut modifier les Tickets ✅
-- AgentSupport ne peut PAS voir ComptabiliteInterne ❌
-- (même si cette table est dans le schéma Public)
```

### Exemple 4 : Protéger contre l'escalade de privilèges

```sql
-- Contexte : Empêcher un user de donner des permissions à d'autres
-- (même s'il a WITH GRANT OPTION)

-- User a la permission avec possibilité de la transmettre
GRANT SELECT ON dbo.Clients TO Superviseur WITH GRANT OPTION;

-- Mais on bloque sa capacité à donner des permissions sur des tables sensibles
DENY CONTROL ON dbo.Salaires TO Superviseur;

-- Résultat :
-- Superviseur peut donner SELECT sur Clients à d'autres ✅
-- Superviseur ne peut RIEN faire avec Salaires ❌ (ni accéder, ni donner des permissions)
```

## Ordre de priorité des permissions

Voici comment SQL Server évalue les permissions :

```
1. DENY direct sur le user          ← Priorité MAXIMALE (bloque tout)
   ↓
2. DENY sur un rôle dont le user est membre
   ↓
3. GRANT direct sur le user
   ↓
4. GRANT sur un rôle dont le user est membre
   ↓
5. Absence de permission            ← Priorité MINIMALE (refus par défaut)
```

**Exemple d'évaluation** :

```sql
-- Setup
CREATE USER Jean FOR LOGIN JeanLogin;
CREATE ROLE Role1;
CREATE ROLE Role2;

ALTER ROLE Role1 ADD MEMBER Jean;
ALTER ROLE Role2 ADD MEMBER Jean;

-- Permissions
GRANT SELECT ON dbo.Produits TO Role1;      -- #4 : GRANT via rôle
GRANT SELECT ON dbo.Produits TO Jean;       -- #3 : GRANT direct
DENY SELECT ON dbo.Produits TO Role2;       -- #2 : DENY via rôle
-- (pas de #1 : DENY direct sur Jean)

-- Résultat : Jean NE PEUT PAS accéder à Produits
-- Car le DENY sur Role2 (#2) surpasse les GRANT (#3 et #4)
```

## Types de DENY courants

### 1. DENY sur les données (DML)

```sql
-- Bloquer la lecture
DENY SELECT ON dbo.Salaires TO User;

-- Bloquer l'ajout de données
DENY INSERT ON dbo.Configuration TO User;

-- Bloquer la modification
DENY UPDATE ON dbo.PrixProduits TO User;

-- Bloquer la suppression
DENY DELETE ON dbo.HistoriqueTransactions TO User;

-- Bloquer plusieurs actions à la fois
DENY SELECT, INSERT, UPDATE, DELETE ON dbo.TableSensible TO User;
```

### 2. DENY sur la structure (DDL)

```sql
-- Bloquer la création de tables
DENY CREATE TABLE TO Developpeur;

-- Bloquer la modification de structure
DENY ALTER ON dbo.Clients TO User;

-- Bloquer la suppression d'objets
DENY DROP ON dbo.Produits TO User;
```

### 3. DENY sur les procédures

```sql
-- Bloquer l'exécution d'une procédure spécifique
DENY EXECUTE ON dbo.SupprimerToutesLesDonnees TO User;

-- Bloquer l'exécution de toutes les procédures d'un schéma
DENY EXECUTE ON SCHEMA::Administration TO Developpeur;
```

### 4. DENY au niveau schéma

```sql
-- Bloquer tout accès à un schéma entier
DENY SELECT ON SCHEMA::Comptabilite TO RoleVentes;

-- Bloquer les modifications dans un schéma
DENY INSERT, UPDATE, DELETE ON SCHEMA::Production TO RoleTest;
```

### 5. DENY au niveau colonne

```sql
-- Bloquer l'accès à des colonnes spécifiques
DENY SELECT ON dbo.Employes (Salaire, Bonus) TO ManagerJunior;

-- Bloquer la modification de colonnes spécifiques
DENY UPDATE ON dbo.Produits (PrixCoutant, MargeCommerciale) TO VendeurExterne;
```

## Vérifier les DENY actifs

### Voir tous les DENY d'un user

```sql
-- Lister tous les DENY pour Jean
SELECT
    USER_NAME(grantee_principal_id) AS UserName,
    permission_name AS Permission,
    OBJECT_NAME(major_id) AS ObjectName,
    state_desc AS State  -- 'DENY' pour les refus
FROM
    sys.database_permissions
WHERE
    USER_NAME(grantee_principal_id) = 'Jean'
    AND state_desc = 'DENY'
ORDER BY
    permission_name, ObjectName;
```

### Voir tous les DENY sur un objet

```sql
-- Qui a des DENY sur la table Salaires ?
SELECT
    USER_NAME(grantee_principal_id) AS UserName,
    permission_name AS Permission,
    state_desc AS State
FROM
    sys.database_permissions
WHERE
    major_id = OBJECT_ID('dbo.Salaires')
    AND state_desc = 'DENY'
ORDER BY
    UserName, permission_name;
```

### Voir tous les DENY de la base de données

```sql
-- Vue complète de tous les DENY
SELECT
    USER_NAME(grantee_principal_id) AS UserOrRole,
    permission_name AS Permission,
    OBJECT_SCHEMA_NAME(major_id) AS SchemaName,
    OBJECT_NAME(major_id) AS ObjectName,
    state_desc AS State
FROM
    sys.database_permissions
WHERE
    state_desc = 'DENY'
ORDER BY
    UserOrRole, permission_name;
```

## Retirer un DENY : REVOKE

Pour annuler un DENY, vous utilisez **REVOKE** (que nous verrons en détail dans la section 8.4.4).

```sql
-- Mettre en place un DENY
DENY SELECT ON dbo.Salaires TO Jean;

-- Retirer le DENY
REVOKE SELECT ON dbo.Salaires TO Jean;
```

⚠️ **Important** : REVOKE supprime le DENY, mais ne donne PAS automatiquement la permission. Après un REVOKE :
- Si Jean n'a pas de GRANT, il n'aura toujours pas accès
- Si Jean a un GRANT (direct ou via un rôle), il aura maintenant accès

## Erreurs courantes et pièges

### Piège 1 : DENY en cascade (CASCADE)

Quand vous ajoutez `CASCADE` à un DENY, cela affecte aussi ceux qui ont reçu la permission via WITH GRANT OPTION.

```sql
-- User1 a une permission avec droit de la transmettre
GRANT SELECT ON dbo.Clients TO User1 WITH GRANT OPTION;

-- User1 transmet la permission à User2
-- (User1 se connecte et exécute)
GRANT SELECT ON dbo.Clients TO User2;

-- Plus tard, on applique un DENY à User1 avec CASCADE
DENY SELECT ON dbo.Clients TO User1 CASCADE;

-- Résultat :
-- User1 perd l'accès ❌
-- User2 perd AUSSI l'accès ❌ (car il avait reçu la permission de User1)
```

### Piège 2 : DENY oublié qui bloque tout

```sql
-- Scénario : Un admin met un DENY temporaire pour des tests
DENY SELECT ON dbo.Commandes TO TestUser;

-- Tests terminés, on oublie de retirer le DENY
-- Plus tard, on ajoute TestUser au rôle de production
ALTER ROLE RoleProduction ADD MEMBER TestUser;
GRANT SELECT ON SCHEMA::dbo TO RoleProduction;

-- PROBLÈME : TestUser ne peut toujours PAS lire Commandes
-- Car le DENY oublié bloque l'accès
```

**Solution** : Toujours documenter et nettoyer les DENY temporaires.

### Piège 3 : DENY trop large

```sql
-- MAUVAIS : Bloquer tout un schéma par facilité
DENY SELECT ON SCHEMA::RH TO Stagiaire;

-- PROBLÈME : Stagiaire ne peut plus rien voir du tout dans RH
-- Même des tables non-sensibles qu'il pourrait voir

-- MIEUX : Être spécifique
DENY SELECT ON dbo.Salaires TO Stagiaire;
DENY SELECT ON dbo.EvaluationsConfidentielles TO Stagiaire;
-- Le reste du schéma RH reste accessible via les GRANT normaux
```

### Piège 4 : Confondre "pas de GRANT" et "DENY"

```sql
-- Situation 1 : Jean n'a PAS de permission (pas de GRANT)
-- Résultat : Jean ne peut pas accéder
-- Solution : GRANT pour donner l'accès

-- Situation 2 : Jean a un DENY explicite
-- Résultat : Jean ne peut pas accéder
-- Solution : REVOKE pour retirer le DENY, puis GRANT si nécessaire
```

**Comment savoir lequel ?**
```sql
-- Vérifier s'il y a un DENY
SELECT *
FROM sys.database_permissions
WHERE USER_NAME(grantee_principal_id) = 'Jean'
  AND state_desc = 'DENY';

-- Si la requête retourne des lignes : Il y a un DENY
-- Si la requête est vide : C'est juste une absence de GRANT
```

## DENY vs ne pas donner de GRANT : Quand utiliser quoi ?

### ❌ N'utilisez PAS DENY pour...

**Cas 1 : Restriction normale**
```sql
-- ❌ MAUVAIS : DENY pour une restriction normale
GRANT SELECT ON SCHEMA::Ventes TO RoleComptabilite;
DENY SELECT ON SCHEMA::RH TO RoleComptabilite;  -- Inutilement complexe

-- ✅ MIEUX : Simplement ne pas donner le GRANT
GRANT SELECT ON SCHEMA::Ventes TO RoleComptabilite;
-- Pas de GRANT sur RH = pas d'accès, c'est tout
```

**Cas 2 : Permissions granulaires simples**
```sql
-- ❌ MAUVAIS : DENY pour contrôler finement
GRANT SELECT ON SCHEMA::dbo TO User;
DENY SELECT ON dbo.Table1 TO User;
DENY SELECT ON dbo.Table2 TO User;
DENY SELECT ON dbo.Table3 TO User;

-- ✅ MIEUX : GRANT spécifique uniquement sur ce qui est nécessaire
GRANT SELECT ON dbo.Table4 TO User;
GRANT SELECT ON dbo.Table5 TO User;
```

### ✅ Utilisez DENY pour...

**Cas 1 : Exception dans un groupe**
```sql
-- ✅ BON : Bloquer un membre spécifique d'un rôle
GRANT SELECT ON dbo.Salaires TO RoleManagers;
ALTER ROLE RoleManagers ADD MEMBER Manager1;
ALTER ROLE RoleManagers ADD MEMBER Manager2;
ALTER ROLE RoleManagers ADD MEMBER ManagerStagiaire;

DENY SELECT ON dbo.Salaires TO ManagerStagiaire;  -- Exception justifiée
```

**Cas 2 : Protection contre l'escalade involontaire**
```sql
-- ✅ BON : Garantir qu'un accès ne sera JAMAIS donné
-- Même si on ajoute le user à un rôle puissant par erreur
DENY DELETE ON dbo.HistoriqueAudit TO AppWeb;
DENY DROP ON dbo.Clients TO AppWeb;
```

**Cas 3 : Conformité et audit**
```sql
-- ✅ BON : Prouver explicitement qu'une restriction existe
-- Pour les auditeurs, il est plus clair de voir un DENY
-- que de devoir chercher l'absence d'un GRANT
DENY INSERT, UPDATE, DELETE ON SCHEMA::Production TO RoleAuditeur;
```

## Bonnes pratiques DENY

### 1. Documentez TOUS vos DENY ✅

Les DENY sont moins intuitifs que les GRANT. Expliquez toujours pourquoi.

```sql
-- ✅ BON : Documentation claire
/*
DENY sur Manager3 - Table Salaires
Raison : Manager3 est en période de probation (6 mois)
Date : 2024-01-15
Créé par : AdminDB
À réviser : 2024-07-15
*/
DENY SELECT ON dbo.Salaires TO Manager3;
```

### 2. Utilisez DENY avec parcimonie ⚠️

DENY rend la gestion des permissions plus complexe. Préférez ne pas donner de GRANT.

```sql
-- ✅ Préférez la simplicité
-- Au lieu de :
GRANT SELECT ON SCHEMA::dbo TO User;
DENY SELECT ON dbo.Table1, dbo.Table2, dbo.Table3 TO User;

-- Faites plutôt :
GRANT SELECT ON dbo.Table4, dbo.Table5, dbo.Table6 TO User;
```

### 3. Soyez spécifique avec DENY 🎯

```sql
-- ❌ MAUVAIS : DENY trop large
DENY SELECT ON SCHEMA::RH TO User;

-- ✅ BON : DENY ciblé
DENY SELECT ON dbo.Salaires TO User;
DENY SELECT ON dbo.EvaluationsPersonnelles TO User;
```

### 4. Auditez régulièrement les DENY 🔍

```sql
-- Script d'audit mensuel : Lister tous les DENY
SELECT
    USER_NAME(grantee_principal_id) AS WhoIsBlocked,
    permission_name AS WhatIsBlocked,
    OBJECT_NAME(major_id) AS OnWhichObject,
    'REVOKE ' + permission_name + ' ON ' +
        ISNULL(OBJECT_NAME(major_id), 'DATABASE') + ' TO ' +
        USER_NAME(grantee_principal_id) AS CommandToRemove
FROM
    sys.database_permissions
WHERE
    state_desc = 'DENY'
ORDER BY
    WhoIsBlocked;
```

### 5. Testez l'impact avant de mettre en production ✅

```sql
-- Tester l'impact d'un DENY sur un user
EXECUTE AS USER = 'TestUser';

-- Vérifier ce qui fonctionne encore
SELECT 'Test 1' AS Test, COUNT(*) FROM dbo.Table1;  -- Doit réussir
SELECT 'Test 2' AS Test, COUNT(*) FROM dbo.Table2;  -- Doit échouer (DENY)
SELECT 'Test 3' AS Test, COUNT(*) FROM dbo.Table3;  -- Doit réussir

REVERT;
```

### 6. Créez des alertes pour les DENY critiques 🚨

```sql
-- Créer une alerte si un DENY est modifié sur des tables sensibles
-- (à implémenter avec un trigger DDL ou Extended Events)

CREATE TRIGGER trg_Alert_Deny_Changes
ON DATABASE
FOR DENY_DATABASE
AS
BEGIN
    -- Logger l'événement
    INSERT INTO dbo.AuditSecurite (DateEvent, TypeEvent, Details)
    VALUES (GETDATE(), 'DENY Applied', EVENTDATA().value('(/EVENT_INSTANCE/TSQLCommand/CommandText)[1]', 'NVARCHAR(MAX)'));

    -- Envoyer une alerte email
    -- (code de notification)
END;
```

## Comparaison : GRANT vs DENY vs Absence

| Aspect | GRANT | DENY | Absence (rien) |
|--------|-------|------|----------------|
| **Effet** | Autorise explicitement | Refuse explicitement | Refuse par défaut |
| **Priorité** | Basse | **HAUTE** | Très basse |
| **Peut être surpassé ?** | Oui (par DENY) | **Non** | Oui (par GRANT) |
| **Usage** | Donner des accès | Bloquer des exceptions | Comportement par défaut |
| **Complexité** | Simple | Complexe | Très simple |
| **Héritage** | Se cumule | Bloque tout | N/A |

## Scénario complet : Gestion d'équipe avec DENY

Mettons tout en pratique avec un exemple réaliste.

```sql
-- Contexte : Une équipe de ventes avec différents niveaux d'accès

-- 1. Créer la structure de base
CREATE ROLE RoleVentes;
CREATE USER VendeurSenior FOR LOGIN [DOMAINE\Senior];
CREATE USER VendeurJunior FOR LOGIN [DOMAINE\Junior];
CREATE USER ManagerVentes FOR LOGIN [DOMAINE\Manager];

-- 2. Tous les vendeurs ont accès aux données de ventes
GRANT SELECT ON SCHEMA::Ventes TO RoleVentes;
GRANT INSERT, UPDATE ON dbo.Commandes TO RoleVentes;

-- 3. Ajouter tout le monde au rôle
ALTER ROLE RoleVentes ADD MEMBER VendeurSenior;
ALTER ROLE RoleVentes ADD MEMBER VendeurJunior;
ALTER ROLE RoleVentes ADD MEMBER ManagerVentes;

-- 4. Exceptions avec DENY :

-- Le vendeur junior ne peut pas voir les commissions
DENY SELECT ON dbo.Commissions TO VendeurJunior;

-- Le vendeur junior ne peut pas modifier les remises importantes
DENY UPDATE ON dbo.Commandes (RemiseSpeciale, RemiseExceptionnelle) TO VendeurJunior;

-- Personne (même le manager) ne peut supprimer l'historique
DENY DELETE ON dbo.HistoriqueCommandes TO RoleVentes;

-- 5. Permissions additionnelles pour le manager (sans DENY, donc OK)
GRANT SELECT ON dbo.Commissions TO ManagerVentes;
GRANT UPDATE ON dbo.Commandes TO ManagerVentes;  -- Peut modifier toutes les colonnes
GRANT EXECUTE ON dbo.ApprouverRemise TO ManagerVentes;
```

**Résultat final** :

| User | Peut voir commandes | Peut modifier commandes | Peut voir commissions | Peut supprimer historique |
|------|---------------------|-------------------------|----------------------|---------------------------|
| VendeurSenior | ✅ | ✅ (sauf remises spéciales) | ✅ | ❌ (DENY) |
| VendeurJunior | ✅ | ✅ (sauf remises spéciales) | ❌ (DENY) | ❌ (DENY) |
| ManagerVentes | ✅ | ✅ (tout) | ✅ | ❌ (DENY) |

## Conclusion

**DENY** est un outil puissant mais à utiliser avec précaution. Voici les points essentiels :

**Règle d'or** :
🔴 **DENY surpasse toujours GRANT** 🟢

**Quand utiliser DENY** :
- ✅ Pour créer des exceptions dans des groupes de permissions
- ✅ Pour garantir qu'un accès ne sera jamais donné (protection)
- ✅ Pour la conformité et l'audit (refus explicite visible)

**Quand NE PAS utiliser DENY** :
- ❌ Pour des restrictions normales (utilisez simplement l'absence de GRANT)
- ❌ Pour remplacer une conception de permissions trop large
- ❌ Par facilité (DENY augmente la complexité)

**Bonnes pratiques** :
1. 📝 Documentez TOUS vos DENY
2. 🎯 Soyez spécifique (évitez les DENY trop larges)
3. 🔍 Auditez régulièrement
4. ⚠️ Utilisez avec parcimonie
5. ✅ Testez avant de déployer

Dans la prochaine section (8.4.4), nous verrons **REVOKE**, qui permet de retirer des permissions (qu'elles soient GRANT ou DENY).

---

**Points clés à retenir** :
- DENY = Refus explicite d'une permission
- DENY est plus fort que GRANT (toujours prioritaire)
- DENY ≠ Absence de permission (différent et plus restrictif)
- Syntaxe : `DENY permission ON objet TO principal`
- Utilisez DENY pour les exceptions, pas pour les règles normales
- Documentez et auditez tous vos DENY
- REVOKE permet de retirer un DENY
- Préférez la simplicité : n'utilisez DENY que quand c'est vraiment nécessaire
