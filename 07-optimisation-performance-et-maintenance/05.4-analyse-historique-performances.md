# 7.5.4 Analyse historique des performances

## Qu'est-ce que l'analyse historique des performances ?

L'**analyse historique des performances** consiste à examiner comment les performances de vos requêtes ont évolué au fil du temps : heures, jours, semaines, voire mois. C'est comme regarder l'historique de votre santé chez le médecin pour comprendre les tendances.

### Analogie simple

Imaginez que vous tenez un journal de votre consommation d'essence :

**Sans historique :**
```
Aujourd'hui : 8 litres/100km
→ Est-ce bien ? Est-ce mal ? Vous ne savez pas.
```

**Avec historique :**
```
Janvier : 6 litres/100km
Février : 6.5 litres/100km
Mars : 7 litres/100km
Aujourd'hui : 8 litres/100km
→ Tendance à la hausse ! Il y a un problème à investiguer.
```

Le Query Store fait la même chose pour vos requêtes SQL : il garde l'historique et vous permet d'identifier les tendances, les patterns et les anomalies.

## Pourquoi l'analyse historique est cruciale ?

### 1. Détecter les dégradations progressives

Certains problèmes ne surviennent pas brutalement mais s'installent lentement :

```
Semaine 1 : Requête moyenne = 100 ms
Semaine 2 : Requête moyenne = 150 ms
Semaine 3 : Requête moyenne = 200 ms
Semaine 4 : Requête moyenne = 300 ms ← Problème clair !
```

Sans historique, vous ne verriez que "300 ms" et ne sauriez pas que c'était 100 ms il y a un mois.

### 2. Comprendre les patterns d'utilisation

Votre application a peut-être des patterns prévisibles :

- **Pics matinaux** : Tous les jours entre 9h-10h
- **Pics hebdomadaires** : Les lundis matin
- **Pics mensuels** : Le dernier jour du mois (clôtures)
- **Saisonnalité** : Plus d'activité en décembre (commerce)

Connaître ces patterns vous aide à :
- Planifier la maintenance aux bonnes heures
- Dimensionner les ressources correctement
- Anticiper les problèmes

### 3. Valider l'impact des changements

Vous avez créé un nouvel index hier ? L'analyse historique vous montre :

```
Avant l'index : 2000 ms en moyenne
Après l'index : 200 ms en moyenne
→ Impact positif confirmé ! ✅
```

Ou au contraire :

```
Avant la modification : 100 ms
Après la modification : 500 ms
→ Régression ! Il faut revenir en arrière ❌
```

### 4. Établir une baseline

Une **baseline** (ligne de base) est votre référence "normale". Elle vous dit :
- À quelle vitesse les requêtes devraient s'exécuter normalement
- Quel est le comportement attendu
- Quand quelque chose est vraiment anormal

Sans baseline, vous ne savez pas si 500 ms est normal ou problématique pour une requête donnée.

## Les rapports historiques dans SSMS

Query Store offre plusieurs rapports prédéfinis pour l'analyse historique.

### Accéder aux rapports

1. Dans SQL Server Management Studio (SSMS)
2. Développez votre base de données
3. Développez le dossier **Query Store**
4. Vous verrez plusieurs rapports

### 1. Overall Resource Consumption (Consommation globale)

**Ce qu'il montre :**
Un graphique temporel de la consommation des ressources pour **toute la base de données**.

**Métriques disponibles :**
- Duration (Durée totale)
- CPU Time
- Logical Reads
- Logical Writes
- Physical Reads
- Execution Count (Nombre d'exécutions)

**Comment l'utiliser :**

```
Axe horizontal (X) : Le temps (par défaut, par heure)
Axe vertical (Y) : La métrique choisie
Graphique : Barres ou lignes montrant l'évolution
```

**Exemple d'interprétation :**

```
Lundi 9h : 100,000 lectures logiques
Lundi 10h : 120,000 lectures logiques
Lundi 11h : 95,000 lectures logiques
...
Mardi 9h : 500,000 lectures logiques ← Anomalie !
```

Vous voyez immédiatement que mardi matin, quelque chose d'inhabituel s'est produit.

**Configuration du rapport :**
- **Interval** : Granularité temporelle (1h, 6h, 1 jour)
- **Time Window** : Période à analyser (dernière heure, jour, semaine)
- **Metric** : La métrique à visualiser

### 2. Top Resource Consuming Queries (Requêtes les plus gourmandes)

**Ce qu'il montre :**
Les requêtes qui consomment le plus de ressources, avec leur évolution dans le temps.

**Comment l'utiliser :**

1. Le graphique supérieur montre les top requêtes (par défaut top 25)
2. Chaque barre représente une requête
3. Cliquez sur une barre pour voir son évolution historique dans le panneau inférieur

**Exemple d'analyse :**

```
Top 1 : Requête A - 35% du CPU total
Top 2 : Requête B - 20% du CPU total
Top 3 : Requête C - 15% du CPU total
```

En cliquant sur la Requête A, vous voyez son historique :
```
Semaine dernière : 10% du CPU
Cette semaine : 35% du CPU
→ Cette requête a triplé sa consommation !
```

**Utilité :**
- Identifier les "resource hogs" (gouffres à ressources)
- Prioriser les optimisations (commencer par le top 1)
- Voir si une optimisation a vraiment eu un impact

### 3. Tracked Queries (Requêtes suivies)

**Ce qu'il montre :**
Permet de suivre spécifiquement certaines requêtes que vous avez marquées.

**Comment l'utiliser :**

1. Identifiez une requête critique dans un autre rapport
2. Clic droit → **Track Query**
3. La requête apparaît maintenant dans ce rapport
4. Vous pouvez voir son évolution isolée des autres

**Cas d'usage :**
- Suivre une requête après optimisation
- Surveiller une requête critique pour le métier
- Monitorer une requête problématique en cours de correction

### 4. Queries With High Variation (Requêtes à forte variation)

**Ce qu'il montre :**
Les requêtes dont les performances varient beaucoup d'une exécution à l'autre.

**Exemple :**
```
Requête X :
- Exécution 1 : 100 ms
- Exécution 2 : 150 ms
- Exécution 3 : 5000 ms ← Énorme variation !
- Exécution 4 : 120 ms
```

**Causes fréquentes :**
- Parameter Sniffing
- Verrous et blocages aléatoires
- Problèmes de concurrence
- Données très hétérogènes

**Utilité :**
Ces requêtes sont imprévisibles et peuvent causer des timeouts aléatoires. Il faut les stabiliser.

## Analyse par périodes

### Comparer deux périodes

Une des analyses les plus puissantes : comparer "avant" vs "après".

**Exemples de comparaisons utiles :**

#### 1. Avant/Après un déploiement
```
Période de référence : Mercredi 10h-12h (avant déploiement)
Période récente : Mercredi 14h-16h (après déploiement)
```

**Ce que vous cherchez :**
- Nouvelles requêtes introduites
- Requêtes existantes plus lentes
- Augmentation du nombre d'exécutions

#### 2. Même heure, jour différent
```
Période de référence : Lundi 9h-10h (normal)
Période récente : Mardi 9h-10h (problème signalé)
```

**Ce que vous cherchez :**
- Quelles requêtes ont changé de comportement
- Quels sont les pics inhabituels

#### 3. Semaine normale vs semaine problématique
```
Période de référence : Semaine 1 (normale)
Période récente : Semaine 2 (lente)
```

**Ce que vous cherchez :**
- Tendances générales à la hausse
- Nouvelles requêtes apparues
- Croissance du volume de données

### Configuration dans SSMS

Dans la plupart des rapports :

**Section "Configure" :**
```
Metric: Duration
Statistic: Average
Time Period:
  - Recent: Last 1 day
  - History: Last 1 week
```

**Exemple d'interprétation :**

Le graphique montre deux points par requête :
- **Point gauche** (bleu) : Moyenne de la semaine dernière
- **Point droit** (rouge) : Moyenne du dernier jour

Une ligne montante = dégradation  
Une ligne descendante = amélioration  

## Requêtes T-SQL pour l'analyse historique

Pour des analyses plus personnalisées, utilisez SQL directement.

### 1. Évolution d'une requête spécifique dans le temps

```sql
-- Voir comment une requête spécifique a performé au fil du temps
DECLARE @query_id INT = 123; -- ID de votre requête

SELECT
    rs.runtime_stats_interval_id,
    rsi.start_time,
    rsi.end_time,
    rs.count_executions,
    rs.avg_duration / 1000.0 AS avg_duration_ms,
    rs.min_duration / 1000.0 AS min_duration_ms,
    rs.max_duration / 1000.0 AS max_duration_ms,
    rs.avg_cpu_time / 1000.0 AS avg_cpu_time_ms,
    rs.avg_logical_io_reads,
    rs.avg_logical_io_writes
FROM sys.query_store_runtime_stats rs
INNER JOIN sys.query_store_runtime_stats_interval rsi
    ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
INNER JOIN sys.query_store_plan p
    ON rs.plan_id = p.plan_id
WHERE p.query_id = @query_id
ORDER BY rsi.start_time;
```

**Résultat typique :**
```
start_time          | end_time            | count | avg_duration_ms
--------------------|---------------------|-------|----------------
2025-11-01 09:00:00 | 2025-11-01 10:00:00 | 150   | 100
2025-11-01 10:00:00 | 2025-11-01 11:00:00 | 180   | 105
2025-11-01 11:00:00 | 2025-11-01 12:00:00 | 200   | 110
...
2025-11-18 09:00:00 | 2025-11-18 10:00:00 | 160   | 350  ← Problème !
```

Vous voyez clairement que ce matin, la requête est 3.5x plus lente que d'habitude.

### 2. Comparer deux périodes précises

```sql
-- Comparer les performances entre deux périodes spécifiques
WITH PeriodRecent AS (
    SELECT
        p.query_id,
        AVG(rs.avg_duration) AS avg_duration,
        SUM(rs.count_executions) AS total_executions
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    INNER JOIN sys.query_store_plan p
        ON rs.plan_id = p.plan_id
    WHERE rsi.start_time >= '2025-11-18 08:00:00'
        AND rsi.end_time <= '2025-11-18 12:00:00'
    GROUP BY p.query_id
),
PeriodHistory AS (
    SELECT
        p.query_id,
        AVG(rs.avg_duration) AS avg_duration,
        SUM(rs.count_executions) AS total_executions
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    INNER JOIN sys.query_store_plan p
        ON rs.plan_id = p.plan_id
    WHERE rsi.start_time >= '2025-11-11 08:00:00'
        AND rsi.end_time <= '2025-11-11 12:00:00'
    GROUP BY p.query_id
)
SELECT
    qt.query_sql_text,
    ph.avg_duration / 1000.0 AS history_avg_ms,
    pr.avg_duration / 1000.0 AS recent_avg_ms,
    ((pr.avg_duration - ph.avg_duration) * 100.0 / ph.avg_duration) AS percent_change,
    ph.total_executions AS history_executions,
    pr.total_executions AS recent_executions,
    CASE
        WHEN pr.avg_duration > ph.avg_duration * 1.5 THEN '❌ REGRESSION'
        WHEN pr.avg_duration < ph.avg_duration * 0.8 THEN '✅ IMPROVEMENT'
        ELSE '➡️ STABLE'
    END AS status
FROM PeriodRecent pr
INNER JOIN PeriodHistory ph ON pr.query_id = ph.query_id
INNER JOIN sys.query_store_query q ON pr.query_id = q.query_id
INNER JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
WHERE ph.avg_duration > 0 -- Éviter division par zéro
ORDER BY ABS(pr.avg_duration - ph.avg_duration) DESC;
```

**Ce que cette requête fait :**
- Compare aujourd'hui 8h-12h avec la même plage il y a une semaine
- Calcule le pourcentage de changement
- Identifie les régressions (>50% plus lent)
- Identifie les améliorations (>20% plus rapide)

### 3. Identifier les tendances (régression linéaire simple)

```sql
-- Trouver les requêtes dont les performances se dégradent progressivement
WITH TimeSeriesData AS (
    SELECT
        p.query_id,
        rsi.start_time,
        rs.avg_duration / 1000.0 AS avg_duration_ms,
        ROW_NUMBER() OVER (PARTITION BY p.query_id ORDER BY rsi.start_time) AS time_index
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    INNER JOIN sys.query_store_plan p
        ON rs.plan_id = p.plan_id
    WHERE rsi.start_time >= DATEADD(day, -7, GETDATE())
        AND rs.count_executions > 10
),
Trends AS (
    SELECT
        query_id,
        MIN(avg_duration_ms) AS min_duration,
        MAX(avg_duration_ms) AS max_duration,
        AVG(avg_duration_ms) AS avg_duration,
        COUNT(*) AS sample_count,
        CASE
            WHEN MAX(avg_duration_ms) > MIN(avg_duration_ms) * 1.5
            THEN 'DEGRADING'
            WHEN MAX(avg_duration_ms) < MIN(avg_duration_ms) * 0.8
            THEN 'IMPROVING'
            ELSE 'STABLE'
        END AS trend
    FROM TimeSeriesData
    GROUP BY query_id
    HAVING COUNT(*) >= 5  -- Au moins 5 points de données
)
SELECT
    t.query_id,
    LEFT(qt.query_sql_text, 100) AS query_preview,
    t.min_duration,
    t.max_duration,
    t.avg_duration,
    ((t.max_duration - t.min_duration) / t.min_duration * 100) AS degradation_percent,
    t.trend,
    t.sample_count
FROM Trends t
INNER JOIN sys.query_store_query q ON t.query_id = q.query_id
INNER JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
WHERE t.trend = 'DEGRADING'
ORDER BY degradation_percent DESC;
```

**Ce que cette requête identifie :**
- Les requêtes dont la durée max est 50%+ plus élevée que la durée min
- Sur les 7 derniers jours
- Avec au moins 5 points de mesure

### 4. Analyser les patterns hebdomadaires

```sql
-- Voir si certains jours de la semaine sont plus problématiques
SELECT
    DATENAME(weekday, rsi.start_time) AS day_of_week,
    DATEPART(hour, rsi.start_time) AS hour_of_day,
    COUNT(DISTINCT p.query_id) AS unique_queries,
    SUM(rs.count_executions) AS total_executions,
    AVG(rs.avg_duration) / 1000.0 AS avg_duration_ms,
    SUM(rs.avg_duration * rs.count_executions) / 1000000.0 AS total_duration_seconds,
    AVG(rs.avg_cpu_time) / 1000.0 AS avg_cpu_ms,
    SUM(rs.avg_logical_io_reads * rs.count_executions) AS total_logical_reads
FROM sys.query_store_runtime_stats rs
INNER JOIN sys.query_store_runtime_stats_interval rsi
    ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
INNER JOIN sys.query_store_plan p
    ON rs.plan_id = p.plan_id
WHERE rsi.start_time >= DATEADD(day, -30, GETDATE())
GROUP BY DATENAME(weekday, rsi.start_time), DATEPART(hour, rsi.start_time)
ORDER BY
    CASE DATENAME(weekday, rsi.start_time)
        WHEN 'Monday' THEN 1
        WHEN 'Tuesday' THEN 2
        WHEN 'Wednesday' THEN 3
        WHEN 'Thursday' THEN 4
        WHEN 'Friday' THEN 5
        WHEN 'Saturday' THEN 6
        WHEN 'Sunday' THEN 7
    END,
    hour_of_day;
```

**Exemple de résultat :**
```
day_of_week | hour_of_day | total_executions | avg_duration_ms
------------|-------------|------------------|----------------
Monday      | 9           | 50,000          | 150
Monday      | 10          | 45,000          | 120
Monday      | 11          | 40,000          | 110
...
Friday      | 17          | 20,000          | 90
Saturday    | 10          | 5,000           | 80
```

**Insights possibles :**
- Les lundis matin sont les plus chargés
- Le vendredi après-midi est calme
- Les week-ends ont peu d'activité

### 5. Calculer une baseline (moyenne mobile)

```sql
-- Établir une baseline avec moyenne mobile sur 7 jours
WITH DailyStats AS (
    SELECT
        p.query_id,
        CAST(rsi.start_time AS DATE) AS execution_date,
        AVG(rs.avg_duration) / 1000.0 AS daily_avg_duration_ms,
        SUM(rs.count_executions) AS daily_executions
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    INNER JOIN sys.query_store_plan p
        ON rs.plan_id = p.plan_id
    WHERE rsi.start_time >= DATEADD(day, -30, GETDATE())
    GROUP BY p.query_id, CAST(rsi.start_time AS DATE)
),
MovingAverage AS (
    SELECT
        query_id,
        execution_date,
        daily_avg_duration_ms,
        daily_executions,
        AVG(daily_avg_duration_ms) OVER (
            PARTITION BY query_id
            ORDER BY execution_date
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) AS moving_avg_7days,
        STDEV(daily_avg_duration_ms) OVER (
            PARTITION BY query_id
            ORDER BY execution_date
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) AS moving_stdev_7days
    FROM DailyStats
)
SELECT
    ma.query_id,
    LEFT(qt.query_sql_text, 80) AS query_preview,
    ma.execution_date,
    ma.daily_avg_duration_ms,
    ma.moving_avg_7days AS baseline_avg_ms,
    ma.moving_stdev_7days AS baseline_stdev_ms,
    CASE
        WHEN ma.daily_avg_duration_ms > ma.moving_avg_7days + (2 * ma.moving_stdev_7days)
        THEN '⚠️ ANOMALY (2σ above baseline)'
        WHEN ma.daily_avg_duration_ms > ma.moving_avg_7days + ma.moving_stdev_7days
        THEN '⚡ WARNING (1σ above baseline)'
        ELSE '✅ NORMAL'
    END AS status
FROM MovingAverage ma
INNER JOIN sys.query_store_query q ON ma.query_id = q.query_id
INNER JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
WHERE ma.execution_date >= DATEADD(day, -7, GETDATE())
    AND ma.daily_executions > 100  -- Seulement les requêtes fréquentes
ORDER BY ma.execution_date DESC, ma.query_id;
```

**Ce que cette requête fait :**
- Calcule la moyenne mobile sur 7 jours pour chaque requête
- Calcule l'écart-type (mesure de variabilité)
- Identifie les jours où la performance dépasse 2 écarts-types (anomalie statistique)

**Utilité :**
Détection automatique des anomalies basée sur le comportement historique normal.

## Cas d'usage réels

### Cas 1 : Investigation d'un incident

**Situation :**
Mardi à 14h, les utilisateurs signalent que l'application est très lente. À 16h, tout est revenu à la normale.

**Analyse historique :**

```sql
-- Comparer l'incident avec une période normale
-- Période normale : Lundi 14h-16h
-- Période incident : Mardi 14h-16h

WITH NormalPeriod AS (
    SELECT p.query_id, AVG(rs.avg_duration) AS avg_dur
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    INNER JOIN sys.query_store_plan p ON rs.plan_id = p.plan_id
    WHERE rsi.start_time >= '2025-11-17 14:00'
        AND rsi.start_time < '2025-11-17 16:00'
    GROUP BY p.query_id
),
IncidentPeriod AS (
    SELECT p.query_id, AVG(rs.avg_duration) AS avg_dur
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    INNER JOIN sys.query_store_plan p ON rs.plan_id = p.plan_id
    WHERE rsi.start_time >= '2025-11-18 14:00'
        AND rsi.start_time < '2025-11-18 16:00'
    GROUP BY p.query_id
)
SELECT TOP 10
    qt.query_sql_text,
    n.avg_dur / 1000.0 AS normal_ms,
    i.avg_dur / 1000.0 AS incident_ms,
    ((i.avg_dur - n.avg_dur) / n.avg_dur * 100) AS increase_percent
FROM IncidentPeriod i
INNER JOIN NormalPeriod n ON i.query_id = n.query_id
INNER JOIN sys.query_store_query q ON i.query_id = q.query_id
INNER JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
WHERE i.avg_dur > n.avg_dur * 2  -- Au moins 2x plus lent
ORDER BY increase_percent DESC;
```

**Résultat :** Vous identifiez exactement quelles requêtes ont causé le problème pendant l'incident.

### Cas 2 : Valider une optimisation

**Situation :**
Vous avez créé un nouvel index vendredi. Est-ce que ça a aidé ?

**Analyse :**

```sql
-- Comparer avant/après la création de l'index
DECLARE @index_creation_time DATETIME2 = '2025-11-15 10:00:00';

SELECT
    'BEFORE INDEX' AS period,
    AVG(rs.avg_duration) / 1000.0 AS avg_duration_ms,
    SUM(rs.count_executions) AS total_executions,
    AVG(rs.avg_logical_io_reads) AS avg_logical_reads
FROM sys.query_store_runtime_stats rs
INNER JOIN sys.query_store_runtime_stats_interval rsi
    ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
INNER JOIN sys.query_store_plan p ON rs.plan_id = p.plan_id
WHERE p.query_id = 123  -- Votre requête optimisée
    AND rsi.start_time < @index_creation_time
    AND rsi.start_time >= DATEADD(day, -7, @index_creation_time)

UNION ALL

SELECT
    'AFTER INDEX' AS period,
    AVG(rs.avg_duration) / 1000.0 AS avg_duration_ms,
    SUM(rs.count_executions) AS total_executions,
    AVG(rs.avg_logical_io_reads) AS avg_logical_reads
FROM sys.query_store_runtime_stats rs
INNER JOIN sys.query_store_runtime_stats_interval rsi
    ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
INNER JOIN sys.query_store_plan p ON rs.plan_id = p.plan_id
WHERE p.query_id = 123
    AND rsi.start_time >= @index_creation_time
    AND rsi.start_time < DATEADD(day, 7, @index_creation_time);
```

**Résultat typique :**
```
period        | avg_duration_ms | total_executions | avg_logical_reads
--------------|-----------------|------------------|------------------
BEFORE INDEX  | 2500            | 10,000          | 50,000
AFTER INDEX   | 150             | 10,000          | 500

→ Amélioration de 94% ! Index très efficace ✅
```

### Cas 3 : Planification de capacité

**Situation :**
Votre base de données grandit. Vous devez prévoir quand mettre à niveau le serveur.

**Analyse de tendance :**

```sql
-- Évolution de la charge sur 3 mois
SELECT
    DATEPART(year, rsi.start_time) AS year,
    DATEPART(month, rsi.start_time) AS month,
    SUM(rs.count_executions) AS total_queries,
    SUM(rs.avg_duration * rs.count_executions) / 1000000.0 AS total_duration_seconds,
    AVG(rs.avg_cpu_time) / 1000.0 AS avg_cpu_ms,
    SUM(rs.avg_logical_io_reads * rs.count_executions) / 1000000.0 AS total_reads_millions
FROM sys.query_store_runtime_stats rs
INNER JOIN sys.query_store_runtime_stats_interval rsi
    ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
WHERE rsi.start_time >= DATEADD(month, -3, GETDATE())
GROUP BY DATEPART(year, rsi.start_time), DATEPART(month, rsi.start_time)
ORDER BY year, month;
```

**Résultat exemple :**
```
month     | total_queries | total_duration_seconds | total_reads_millions
----------|---------------|------------------------|---------------------
Septembre | 10,000,000   | 5,000                  | 100
Octobre   | 12,000,000   | 7,000                  | 150
Novembre  | 15,000,000   | 10,000                 | 225

→ Croissance de 50% en 2 mois
→ Projection : Besoin d'upgrade dans 3-4 mois
```

### Cas 4 : Identifier la saisonnalité

**Situation :**
Vous voulez savoir si votre application a des patterns saisonniers.

**Analyse :**

```sql
-- Comparer le même jour de la semaine et la même heure sur plusieurs semaines
WITH WeeklyPattern AS (
    SELECT
        DATENAME(weekday, rsi.start_time) AS day_of_week,
        DATEPART(hour, rsi.start_time) AS hour,
        DATEPART(week, rsi.start_time) AS week_number,
        SUM(rs.count_executions) AS executions,
        AVG(rs.avg_duration) / 1000.0 AS avg_duration_ms
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    WHERE rsi.start_time >= DATEADD(week, -8, GETDATE())
    GROUP BY
        DATENAME(weekday, rsi.start_time),
        DATEPART(hour, rsi.start_time),
        DATEPART(week, rsi.start_time)
)
SELECT
    day_of_week,
    hour,
    AVG(executions) AS avg_weekly_executions,
    STDEV(executions) AS stdev_executions,
    MIN(executions) AS min_executions,
    MAX(executions) AS max_executions,
    AVG(avg_duration_ms) AS avg_duration
FROM WeeklyPattern
GROUP BY day_of_week, hour
HAVING COUNT(*) >= 4  -- Au moins 4 semaines de données
ORDER BY
    CASE day_of_week
        WHEN 'Monday' THEN 1
        WHEN 'Tuesday' THEN 2
        WHEN 'Wednesday' THEN 3
        WHEN 'Thursday' THEN 4
        WHEN 'Friday' THEN 5
        WHEN 'Saturday' THEN 6
        WHEN 'Sunday' THEN 7
    END,
    hour;
```

**Insights :**
- Identifie les heures de pointe prévisibles
- Détecte les variations anormales
- Aide à planifier la maintenance

## Bonnes pratiques

### 1. Définir une fenêtre de rétention appropriée

```sql
-- Configurer la rétention du Query Store
ALTER DATABASE YourDatabase
SET QUERY_STORE (
    INTERVAL_LENGTH_MINUTES = 60,  -- Granularité : 1 heure
    CLEANUP_POLICY = (STALE_QUERY_THRESHOLD_DAYS = 30)  -- Garder 30 jours
);
```

**Recommandations :**
- **Production critique** : 30-90 jours de rétention
- **Développement** : 7-14 jours suffisent
- **Très haute fréquence** : Augmenter l'intervalle à 6 heures pour réduire le volume

### 2. Établir des baselines régulièrement

**Créez un processus mensuel :**

```sql
-- Script à exécuter le 1er de chaque mois
-- Sauvegarder les statistiques baseline
CREATE TABLE BaselineStatistics (
    baseline_date DATE,
    query_id INT,
    avg_duration_ms FLOAT,
    avg_cpu_ms FLOAT,
    avg_logical_reads BIGINT,
    avg_executions_per_hour INT
);

INSERT INTO BaselineStatistics
SELECT
    CAST(GETDATE() AS DATE) AS baseline_date,
    p.query_id,
    AVG(rs.avg_duration) / 1000.0,
    AVG(rs.avg_cpu_time) / 1000.0,
    AVG(rs.avg_logical_io_reads),
    AVG(rs.count_executions) AS avg_per_interval
FROM sys.query_store_runtime_stats rs
INNER JOIN sys.query_store_plan p ON rs.plan_id = p.plan_id
WHERE rs.last_execution_time >= DATEADD(day, -30, GETDATE())
GROUP BY p.query_id;
```

### 3. Automatiser les rapports

**Créez une procédure stockée pour un rapport hebdomadaire :**

```sql
CREATE PROCEDURE sp_WeeklyPerformanceReport
AS
BEGIN
    -- Top 10 requêtes les plus lentes cette semaine
    SELECT TOP 10
        LEFT(qt.query_sql_text, 100) AS query,
        AVG(rs.avg_duration) / 1000.0 AS avg_ms
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_plan p ON rs.plan_id = p.plan_id
    INNER JOIN sys.query_store_query q ON p.query_id = q.query_id
    INNER JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
    WHERE rs.last_execution_time >= DATEADD(day, -7, GETDATE())
    GROUP BY qt.query_sql_text
    ORDER BY avg_ms DESC;

    -- Tendances générales
    SELECT
        CAST(rsi.start_time AS DATE) AS date,
        SUM(rs.count_executions) AS total_executions,
        AVG(rs.avg_duration) / 1000.0 AS avg_duration_ms
    FROM sys.query_store_runtime_stats rs
    INNER JOIN sys.query_store_runtime_stats_interval rsi
        ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
    WHERE rsi.start_time >= DATEADD(day, -7, GETDATE())
    GROUP BY CAST(rsi.start_time AS DATE)
    ORDER BY date;
END;
```

Puis programmez son exécution tous les lundis avec SQL Server Agent.

### 5. Utiliser des alertes proactives

**Créez une alerte pour les dégradations :**

```sql
-- Job SQL Agent quotidien qui envoie un email si dégradation détectée
DECLARE @degraded_queries INT;

SELECT @degraded_queries = COUNT(*)
FROM (
    -- Votre requête de détection de régression ici
    -- (Voir les exemples plus haut)
) AS degraded
WHERE degradation_percent > 50;

IF @degraded_queries > 0
BEGIN
    EXEC msdb.dbo.sp_send_dbmail
        @profile_name = 'YourMailProfile',
        @recipients = 'dba@yourcompany.com',
        @subject = 'ALERT: Performance Degradation Detected',
        @body = 'X queries have degraded by more than 50%. Check Query Store.';
END;
```

## Limitations de l'analyse historique

### 1. Granularité temporelle

La granularité par défaut est de 60 minutes. Vous ne pouvez pas :
- Voir une dégradation qui a duré 5 minutes
- Analyser des variations intra-heure fines

**Solution :** Réduire `INTERVAL_LENGTH_MINUTES` à 15 ou 30 minutes (attention à l'espace disque).

### 2. Volume de données

Plus vous gardez d'historique, plus Query Store consomme d'espace :

```
Rétention 7 jours : ~50 MB
Rétention 30 jours : ~200 MB
Rétention 90 jours : ~600 MB
```

**Solution :** Équilibrer entre historique utile et espace disponible.

### 3. Requêtes ad-hoc

Les requêtes non paramétrées génèrent beaucoup de "bruit" :

```sql
SELECT * FROM Customers WHERE CustomerID = 1
SELECT * FROM Customers WHERE CustomerID = 2
...
→ Millions d'entrées différentes
```

**Solution :** Utiliser `QUERY_CAPTURE_MODE = AUTO` et encourager les requêtes paramétrées.

### 4. Corrélation causale

L'analyse historique montre **ce qui s'est passé**, mais pas toujours **pourquoi** :

```
Observation : La requête X est plus lente depuis mardi
Possible causes :
- Croissance des données ?
- Statistiques obsolètes ?
- Changement de plan ?
- Problème réseau ?
- Contention disque ?
```

**Solution :** Combiner Query Store avec d'autres outils (DMVs, Extended Events, Performance Monitor).

## Résumé

L'analyse historique des performances avec Query Store permet de :

**Capacités clés :**
- ✅ Voir l'évolution des performances dans le temps
- ✅ Détecter les dégradations progressives
- ✅ Identifier les patterns et la saisonnalité
- ✅ Comparer avant/après des changements
- ✅ Établir des baselines et détecter les anomalies
- ✅ Valider l'impact des optimisations

**Outils disponibles :**
- 📊 Rapports SSMS prédéfinis (Overall Resource, Top Queries, etc.)
- 💻 Requêtes T-SQL personnalisées
- 📈 Visualisations Excel / Power BI
- ⏰ Alertes automatisées

**Processus recommandé :**
```
1. Établir une baseline (comportement normal)
2. Surveiller régulièrement (quotidien/hebdomadaire)
3. Comparer les périodes (avant/après changements)
4. Identifier les tendances (dégradation progressive)
5. Corréler avec les événements métier
6. Documenter les observations
7. Agir sur les insights découverts
```

**Règle d'or :** L'historique est votre allié. Une semaine de données vaut mieux qu'un snapshot instantané. Un mois de données vaut mieux qu'une semaine. Collectez dès maintenant, analysez plus tard.

**Points clés à retenir :**

- Établissez des baselines pour détecter les anomalies automatiquement
