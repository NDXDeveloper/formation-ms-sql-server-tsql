# 6.4.2 READ COMMITTED (Défaut)

## Introduction

Nous avons vu dans la section précédente que READ UNCOMMITTED offre des performances maximales au prix d'une cohérence très faible (lectures sales autorisées). Le niveau d'isolation **READ COMMITTED** représente un meilleur équilibre entre performance et cohérence.

C'est le **niveau d'isolation par défaut** dans SQL Server, ce qui signifie que si vous ne spécifiez rien, c'est ce niveau qui est utilisé automatiquement. Il est conçu pour couvrir la majorité des besoins des applications tout en maintenant un bon niveau d'intégrité des données.

---

## Qu'est-ce que READ COMMITTED ?

### Définition

**READ COMMITTED** est un niveau d'isolation qui garantit qu'une transaction ne peut lire **que des données qui ont été validées** (committed) par d'autres transactions. En d'autres termes, il **bloque les Dirty Reads** (lectures sales) mais **autorise** les Non-Repeatable Reads et les Phantom Reads.

### Caractéristiques principales

| Caractéristique | READ COMMITTED |
|-----------------|----------------|
| **Dirty Reads** | ❌ Bloquées |
| **Non-Repeatable Reads** | ✅ Autorisées |
| **Phantom Reads** | ✅ Autorisées |
| **Verrous de lecture** | ⏱️ Temporaires (libérés immédiatement) |
| **Performances** | ⭐⭐⭐⭐ Très bonnes |
| **Cohérence** | ⭐⭐⭐ Bonne |
| **Usage** | Niveau **par défaut** |

### Analogie : Le livre publié

Imaginez une bibliothèque où :
- Vous ne pouvez lire **que des livres publiés** (validés par l'éditeur)
- Vous **ne pouvez pas** lire les manuscrits en cours de rédaction (données non validées)
- Si vous consultez le même livre plusieurs fois, son contenu **peut avoir changé** entre-temps (nouvelle édition publiée)
- De **nouveaux livres** peuvent apparaître sur les étagères entre vos visites

C'est exactement le comportement de READ COMMITTED : vous ne lisez que des données "officielles" (validées), mais elles peuvent changer entre deux lectures.

---

## Comment fonctionne READ COMMITTED ?

### Le principe de base

Avec READ COMMITTED :
1. **Des verrous partagés** sont placés lors des lectures (SELECT)
2. Ces verrous **empêchent** les autres transactions de modifier les données pendant la lecture
3. Les verrous sont **libérés immédiatement** après la lecture (pas conservés jusqu'à la fin de la transaction)
4. Une transaction **ne peut pas lire** des données verrouillées en mode exclusif par une autre transaction

### Schéma de fonctionnement

```
Transaction A (écriture)           Transaction B (lecture en READ COMMITTED)
────────────────────────────────────────────────────────────────────────────
BEGIN TRANSACTION

UPDATE Produits
SET Prix = 50
WHERE ProduitID = 1
-- Verrou exclusif placé
-- Données NON validées
                                   BEGIN TRANSACTION
                                   -- READ COMMITTED est le défaut

                                   SELECT Prix FROM Produits
                                   WHERE ProduitID = 1
                                   -- Transaction B est BLOQUÉE
                                   -- Elle doit attendre que A valide ou annule

COMMIT
-- Le prix est maintenant validé
-- Verrou libéré
                                   -- Transaction B peut maintenant lire
                                   -- Résultat : 50 (donnée validée)
                                   COMMIT
```

**Résultat :** Transaction B ne lit que des données validées. Pas de dirty read !

## Différence avec READ UNCOMMITTED

### Comparaison visuelle

| Aspect | READ UNCOMMITTED | READ COMMITTED |
|--------|------------------|----------------|
| **Dirty Reads** | ✅ Lit les brouillons | ❌ Lit uniquement les versions publiées |
| **Attente** | Jamais | Attend si données en modification |
| **Verrous** | Aucun | Temporaires |
| **Garantie** | Aucune | Données validées uniquement |
| **Performance** | Maximum | Très bonne |

### Exemple concret : Le prix du produit

#### Avec READ UNCOMMITTED (rappel)

```sql
-- Transaction A
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 50 WHERE ProduitID = 1;
-- Pas de COMMIT

-- Transaction B (READ UNCOMMITTED)
SELECT Prix FROM Produits WITH (NOLOCK) WHERE ProduitID = 1;
-- Résultat : 50 (donnée non validée !)

-- Transaction A
ROLLBACK;
-- La valeur 50 n'a jamais existé officiellement
```

#### Avec READ COMMITTED (défaut)

```sql
-- Transaction A
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 50 WHERE ProduitID = 1;
-- Pas de COMMIT

-- Transaction B (READ COMMITTED - défaut)
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Transaction B ATTEND...
-- Elle ne peut pas lire tant que A n'a pas validé ou annulé

-- Transaction A
ROLLBACK;

-- Transaction B continue maintenant
-- Résultat : 100 (valeur originale, validée)
```

**Avantage :** Transaction B ne voit jamais la valeur temporaire de 50.

## Les Dirty Reads sont bloqués

### Comment READ COMMITTED empêche les Dirty Reads

READ COMMITTED garantit que vous ne lisez **jamais** des données non validées.

**Mécanisme :**
1. Quand une transaction modifie des données (UPDATE, DELETE), elle place un **verrou exclusif**
2. Ce verrou empêche d'autres transactions de lire ces données
3. Les lectures **attendent** que la modification soit validée (COMMIT) ou annulée (ROLLBACK)
4. Seules les données **validées** sont lisibles

### Exemple : Le transfert bancaire

```sql
-- ===== Transaction A : Transfert de 1000€ du Compte 1 au Compte 2 =====
BEGIN TRANSACTION;

-- Étape 1 : Débiter le compte source
UPDATE Comptes SET Solde = Solde - 1000 WHERE CompteID = 1;
-- Verrou exclusif sur Compte 1

-- Pause de 10 secondes (simulation d'une opération lente)
WAITFOR DELAY '00:00:10';

-- Étape 2 : Créditer le compte destination
UPDATE Comptes SET Solde = Solde + 1000 WHERE CompteID = 2;
-- Verrou exclusif sur Compte 2

COMMIT;
```

```sql
-- ===== Transaction B : Consultation des soldes (défaut READ COMMITTED) =====
BEGIN TRANSACTION;

SELECT CompteID, Solde FROM Comptes WHERE CompteID IN (1, 2);
-- Si Transaction A est en cours :
-- Transaction B attend que les verrous soient libérés
-- Elle ne verra jamais un état incohérent

COMMIT;
```

**Résultat garanti :**
- **SOIT** Transaction B voit les soldes **avant** le transfert (les deux comptes non modifiés)
- **SOIT** Transaction B voit les soldes **après** le transfert (les deux comptes modifiés)
- **JAMAIS** un état intermédiaire (un compte débité, l'autre pas encore crédité)

### Pourquoi c'est important

Sans cette garantie, on pourrait voir des situations absurdes :
```
Compte 1 : 5000€ → 4000€ (débité)
Compte 2 : 3000€ → 3000€ (pas encore crédité)
Total : 7000€ au lieu de 8000€
→ 1000€ ont "disparu" temporairement !
```

READ COMMITTED empêche cela en **bloquant** la lecture pendant la modification.

## Les Non-Repeatable Reads sont autorisés

### Qu'est-ce qu'un Non-Repeatable Read ?

Même avec READ COMMITTED, si vous lisez la **même donnée deux fois** dans une transaction, vous pouvez obtenir des **résultats différents** car une autre transaction peut modifier et valider ces données entre vos deux lectures.

### Pourquoi ?

Les **verrous partagés** de lecture sont **libérés immédiatement** après chaque SELECT, ils ne sont pas maintenus jusqu'à la fin de la transaction.

### Exemple

```sql
-- ===== Transaction A : Consultation d'un prix =====
BEGIN TRANSACTION;

-- Première lecture
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Résultat : 100€
-- Verrou partagé placé puis immédiatement libéré

-- Pause de 5 secondes
WAITFOR DELAY '00:00:05';

-- Deuxième lecture (même requête)
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Résultat : 120€ (différent !)
-- Une autre transaction a modifié le prix entre-temps

COMMIT;
```

```sql
-- ===== Transaction B : Modification du prix (en parallèle) =====
BEGIN TRANSACTION;

UPDATE Produits SET Prix = 120 WHERE ProduitID = 1;

COMMIT;
-- Validé entre les deux lectures de Transaction A
```

### Est-ce un problème ?

**Pour la plupart des applications : NON**

La majorité des applications n'ont pas besoin que les données restent figées pendant toute la transaction. Par exemple :
- Un utilisateur consulte une liste de produits
- Les prix peuvent changer pendant qu'il navigue
- Ce n'est pas grave, il verra les prix à jour au moment du paiement

**Quand c'est un problème :**
- Rapports financiers qui nécessitent une cohérence stricte
- Analyses qui comparent des valeurs sur plusieurs lectures
- Calculs critiques basés sur plusieurs requêtes

→ Dans ces cas, utilisez un niveau d'isolation plus strict (REPEATABLE READ ou SNAPSHOT).

---

## Les Phantom Reads sont autorisés

### Qu'est-ce qu'un Phantom Read ?

De **nouvelles lignes** peuvent apparaître (ou disparaître) entre deux lectures dans la même transaction.

### Exemple

```sql
-- ===== Transaction A : Comptage des commandes =====
BEGIN TRANSACTION;

-- Premier comptage
SELECT COUNT(*) FROM Commandes WHERE DateCommande = '2025-01-15';
-- Résultat : 10 commandes

-- Pause
WAITFOR DELAY '00:00:05';

-- Deuxième comptage (même requête)
SELECT COUNT(*) FROM Commandes WHERE DateCommande = '2025-01-15';
-- Résultat : 11 commandes (une ligne "fantôme" est apparue)

COMMIT;
```

```sql
-- ===== Transaction B : Nouvelle commande (en parallèle) =====
BEGIN TRANSACTION;

INSERT INTO Commandes (DateCommande, MontantTotal)
VALUES ('2025-01-15', 150.00);

COMMIT;
-- Nouvelle ligne insérée entre les deux comptages
```

### Pourquoi READ COMMITTED permet cela

Les verrous partagés ne protègent que les **lignes existantes** au moment de la lecture. Ils ne peuvent pas empêcher l'insertion de **nouvelles lignes** qui correspondent aux critères.

## Syntaxe et utilisation

### READ COMMITTED est le défaut

```sql
-- ===== Vous n'avez rien à faire ! =====
-- Par défaut, toutes vos transactions utilisent READ COMMITTED

BEGIN TRANSACTION;

SELECT * FROM Employes;
-- Utilise automatiquement READ COMMITTED

COMMIT;
```

### Définir explicitement READ COMMITTED

```sql
-- Si vous voulez être explicite (ou revenir au défaut après avoir changé)
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

BEGIN TRANSACTION;

SELECT * FROM Produits;

COMMIT;
```

### Vérifier le niveau d'isolation actuel

```sql
-- Voir le niveau d'isolation de votre session
DBCC USEROPTIONS;

-- Ou utiliser cette requête
SELECT
    CASE transaction_isolation_level
        WHEN 0 THEN 'Unspecified'
        WHEN 1 THEN 'ReadUncommitted'
        WHEN 2 THEN 'ReadCommitted'
        WHEN 3 THEN 'Repeatable'
        WHEN 4 THEN 'Serializable'
        WHEN 5 THEN 'Snapshot'
    END AS IsolationLevel
FROM sys.dm_exec_sessions
WHERE session_id = @@SPID;
```

## Impact sur les performances

### Le comportement des verrous

#### Lors d'une lecture (SELECT)

1. **Verrou partagé** placé sur les données lues
2. La lecture s'effectue
3. **Verrou immédiatement libéré** (après la lecture)

```sql
BEGIN TRANSACTION;

SELECT * FROM Produits WHERE ProduitID = 1;
-- Verrou partagé placé
-- Lecture effectuée
-- Verrou LIBÉRÉ immédiatement (même si la transaction continue)

-- Autres opérations...
UPDATE AutreTable SET ...;

COMMIT;
```

#### Lors d'une écriture (UPDATE, INSERT, DELETE)

1. **Verrou exclusif** placé sur les données modifiées
2. La modification s'effectue
3. **Verrou maintenu jusqu'au COMMIT ou ROLLBACK**

```sql
BEGIN TRANSACTION;

UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
-- Verrou exclusif placé
-- Modification effectuée
-- Verrou MAINTENU jusqu'au COMMIT

-- Autres opérations...
-- Le verrou est toujours actif

COMMIT;
-- Verrou libéré maintenant
```

### Situations de blocage (Blocking)

#### Scénario 1 : Lecture pendant une écriture

```sql
-- Transaction A écrit
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
-- (pas de COMMIT)

-- Transaction B tente de lire
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Transaction B est BLOQUÉE
-- Elle attend que Transaction A fasse COMMIT ou ROLLBACK
```

**Durée du blocage :** Jusqu'à ce que Transaction A se termine.

#### Scénario 2 : Écriture pendant une lecture

```sql
-- Transaction A lit
BEGIN TRANSACTION;
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Verrou partagé placé puis LIBÉRÉ immédiatement

-- Transaction B tente d'écrire (immédiatement après)
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
-- Transaction B réussit ! (le verrou de lecture a été libéré)
```

**Pas de blocage :** Les verrous de lecture sont libérés immédiatement.

### Optimisation des performances

#### Bonnes pratiques

**1. Garder les transactions courtes**

```sql
-- ✅ BON : Transaction rapide
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
COMMIT;

-- ❌ MAUVAIS : Transaction longue
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
WAITFOR DELAY '00:05:00';  -- 5 minutes !
COMMIT;
```

**2. Ne pas faire d'opérations lentes dans une transaction**

```sql
-- ❌ MAUVAIS
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;

-- Appel à une API externe (très lent)
EXEC sp_EnvoyerEmailNotification;  -- Peut prendre 30 secondes

COMMIT;

-- ✅ BON
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
COMMIT;

-- Envoyer l'email APRÈS la transaction
EXEC sp_EnvoyerEmailNotification;
```

**3. Utiliser des index appropriés**

Des requêtes lentes = des verrous maintenus plus longtemps = plus de blocage.

```sql
-- Sans index : Scan de table (lent)
UPDATE Produits SET Prix = Prix * 1.1 WHERE Categorie = 'Electronique';

-- Avec index sur Categorie : Seek (rapide)
CREATE INDEX IX_Produits_Categorie ON Produits(Categorie);
```

## Cas d'usage et recommandations

### Quand utiliser READ COMMITTED (défaut) ✅

**C'est le choix par défaut pour 80-90% des applications.**

**1. Applications web standard**
```sql
-- Lecture de la liste des produits pour affichage
SELECT ProduitID, Nom, Prix, Stock
FROM Produits
WHERE Categorie = 'Informatique'
ORDER BY Nom;
```

**2. Opérations CRUD classiques**
```sql
-- Création d'une commande
BEGIN TRANSACTION;

INSERT INTO Commandes (ClientID, DateCommande, MontantTotal)
VALUES (123, GETDATE(), 299.99);

INSERT INTO CommandeLignes (CommandeID, ProduitID, Quantite, PrixUnitaire)
VALUES (SCOPE_IDENTITY(), 456, 2, 149.99);

COMMIT;
```

**3. Consultation de données en temps réel**
```sql
-- Dashboard : Commandes en cours
SELECT
    c.CommandeID,
    c.DateCommande,
    c.Statut,
    cl.Nom AS NomClient
FROM Commandes c
INNER JOIN Clients cl ON c.ClientID = cl.ClientID
WHERE c.Statut = 'En cours'
ORDER BY c.DateCommande DESC;
```

**4. Mises à jour transactionnelles**
```sql
-- Mise à jour de stock après vente
BEGIN TRANSACTION;

UPDATE Produits
SET Stock = Stock - @Quantite
WHERE ProduitID = @ProduitID
AND Stock >= @Quantite;

IF @@ROWCOUNT = 0
BEGIN
    ROLLBACK;
    RAISERROR('Stock insuffisant', 16, 1);
END
ELSE
BEGIN
    COMMIT;
END
```

### Quand considérer un autre niveau ⚠️

**Passer à READ UNCOMMITTED si :**
- Performances critiques sur des lectures non critiques
- Rapports approximatifs acceptables
- Données historiques/archivées

**Passer à REPEATABLE READ ou SNAPSHOT si :**
- Besoin de cohérence stricte entre plusieurs lectures
- Rapports financiers ou légaux
- Analyses critiques nécessitant des données figées

## Exemple pratique complet

### Scénario : Système de réservation de places de cinéma

```sql
-- ========================================
-- RÉSERVATION DE PLACES DE CINÉMA
-- Utilise READ COMMITTED (par défaut)
-- ========================================

-- 1. Le client consulte les places disponibles
SELECT
    PlaceID,
    Rangee,
    Numero,
    Statut
FROM Places
WHERE SeanceID = @SeanceID
AND Statut = 'Disponible'
ORDER BY Rangee, Numero;
-- READ COMMITTED garantit qu'on ne voit que des places réellement disponibles
-- (pas de places en cours de réservation non validée)

-- 2. Le client sélectionne une place et valide
BEGIN TRANSACTION;

-- Vérifier que la place est toujours disponible
DECLARE @CurrentStatut VARCHAR(20);
SELECT @CurrentStatut = Statut
FROM Places WITH (UPDLOCK)  -- Verrou de mise à jour pour éviter les doublons
WHERE PlaceID = @PlaceID;

IF @CurrentStatut = 'Disponible'
BEGIN
    -- Réserver la place
    UPDATE Places
    SET Statut = 'Reservee',
        ClientID = @ClientID,
        DateReservation = GETDATE()
    WHERE PlaceID = @PlaceID;

    -- Créer la réservation
    INSERT INTO Reservations (ClientID, SeanceID, PlaceID, MontantPaye)
    VALUES (@ClientID, @SeanceID, @PlaceID, 12.50);

    COMMIT;
    PRINT 'Réservation confirmée';
END
ELSE
BEGIN
    ROLLBACK;
    RAISERROR('Place déjà réservée', 16, 1);
END

-- READ COMMITTED garantit :
-- - Pas de dirty reads : On ne voit jamais de places en état temporaire
-- - Les modifications sont atomiques : La place change de statut proprement
-- - Blocage approprié : Si deux clients tentent de réserver la même place,
--   l'un attend l'autre (grâce au verrou exclusif sur UPDATE)
```

**Pourquoi READ COMMITTED est parfait ici :**
1. ✅ **Pas de dirty reads** : Les clients ne voient pas de places en réservation temporaire
2. ✅ **Performance** : Les verrous de lecture sont libérés rapidement
3. ✅ **Cohérence suffisante** : Chaque opération est atomique
4. ✅ **Blocage géré** : SQL Server gère automatiquement les conflits

## Résumé

### Points clés

| Aspect | Description |
|--------|-------------|
| **Niveau d'isolation** | Défaut de SQL Server |
| **Principe** | Lecture uniquement de données validées |
| **Dirty Reads** | ❌ Bloquées (garantie importante) |
| **Non-Repeatable Reads** | ✅ Autorisées (acceptable pour la plupart des cas) |
| **Phantom Reads** | ✅ Autorisées |
| **Verrous de lecture** | ⏱️ Temporaires (libérés immédiatement) |
| **Verrous d'écriture** | 🔒 Maintenus jusqu'au COMMIT |
| **Performance** | ⭐⭐⭐⭐ Très bonne |
| **Cohérence** | ⭐⭐⭐ Bonne |

### Quand l'utiliser

✅ **OUI** (c'est le défaut) pour :
- Applications web et mobile standard
- Opérations CRUD classiques
- Systèmes transactionnels typiques
- 80-90% des cas d'usage

⚠️ **Reconsidérer** si :
- Besoin de performances maximales sur lectures non critiques → READ UNCOMMITTED
- Besoin de cohérence stricte entre plusieurs lectures → REPEATABLE READ ou SNAPSHOT
- Rapports financiers critiques → SERIALIZABLE ou SNAPSHOT

### L'essentiel à retenir

1. READ COMMITTED est le **niveau par défaut** de SQL Server
2. Il **bloque les dirty reads** (pas de lectures de données non validées)
3. Il offre un **excellent compromis** performance/cohérence
4. Les verrous de lecture sont **libérés immédiatement**
5. Les verrous d'écriture sont **maintenus jusqu'au COMMIT**
6. C'est le **bon choix pour la majorité** des applications
7. Vous n'avez **rien à configurer** pour l'utiliser (c'est automatique)

### Comportement des verrous en résumé

```
SELECT (lecture)     : Verrou partagé → Libéré immédiatement
UPDATE/INSERT/DELETE : Verrou exclusif → Maintenu jusqu'au COMMIT
```
