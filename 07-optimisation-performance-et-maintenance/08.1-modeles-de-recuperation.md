# 7.8.1 Modèles de récupération (FULL, SIMPLE, BULK_LOGGED)

## Introduction

Avant même de parler de la commande `BACKUP`, il faut comprendre une notion qui conditionne **tout** ce que vous pourrez sauvegarder et restaurer : le **modèle de récupération** (*recovery model*) de la base de données.

Le modèle de récupération est un réglage **propre à chaque base** qui détermine **comment SQL Server gère son journal des transactions** — et donc quelles options de sauvegarde et de restauration seront à votre disposition. Choisir le mauvais modèle, c'est soit risquer de perdre des données (alors qu'on croyait être protégé), soit voir un journal saturer un disque sans comprendre pourquoi.

C'est donc le tout premier réglage à vérifier sur n'importe quelle base.

---

## Rappel essentiel : le journal des transactions

Chaque base de données SQL Server possède au moins deux fichiers :

- Le **fichier de données** (`.mdf`) : il contient les tables, les index, les données.
- Le **journal des transactions** (`.ldf`, *transaction log*) : il enregistre **toutes les modifications** avant qu'elles ne soient écrites définitivement dans le fichier de données.

> 🧠 **Analogie** : le journal des transactions est le **livre de bord** d'un navire. Avant chaque manœuvre, on note ce qu'on s'apprête à faire. Si quelque chose tourne mal, on relit le livre de bord pour reconstituer l'état exact du navire et le remettre dans une position cohérente.

### Le protocole WAL (Write-Ahead Logging)

SQL Server applique une règle fondamentale appelée **Write-Ahead Logging** : *les enregistrements du journal sont écrits sur le disque AVANT les données correspondantes.*

```
   Une transaction modifie une ligne
              │
              ▼
   1. L'enregistrement est écrit dans le JOURNAL (.ldf)   ◀── d'abord
              │
              ▼
   2. (plus tard) La donnée est écrite dans le fichier .mdf ◀── ensuite
```

Pourquoi ? Parce que si le serveur s'arrête brutalement (coupure de courant) entre les étapes 1 et 2, SQL Server pourra, au redémarrage, **rejouer** ou **annuler** les transactions à partir du journal. C'est ce mécanisme qui garantit l'**Atomicité** et la **Durabilité** des propriétés ACID (vues au chapitre 6).

Le modèle de récupération décide **pendant combien de temps** les informations de ce journal sont conservées avant que leur espace ne soit recyclé.

### Checkpoint et troncature

- Un **checkpoint** (point de contrôle) est le moment où SQL Server écrit les pages de données « sales » (modifiées en mémoire) vers le fichier `.mdf`.
- La **troncature du journal** est l'opération qui marque l'espace du journal comme **réutilisable**. Elle ne réduit pas la taille du fichier ; elle libère de l'espace **à l'intérieur** du fichier.

**C'est exactement ici que le modèle de récupération intervient** : il détermine *quand* la troncature a lieu.

---

## Les trois modèles de récupération

### 1. SIMPLE

En modèle **SIMPLE**, SQL Server **tronque automatiquement** le journal des transactions à chaque checkpoint. L'espace du journal est donc recyclé en permanence, sans intervention de votre part.

**Conséquences :**
- ✅ Gestion du journal **sans effort** : il ne grossit pas indéfiniment.
- ✅ Idéal pour les bases où l'on ne veut pas se soucier des sauvegardes de journal.
- ❌ **Impossible de sauvegarder le journal** : la commande `BACKUP LOG` est interdite.
- ❌ **Pas de restauration à un instant T** : on ne peut restaurer que jusqu'à la dernière sauvegarde complète ou différentielle.

**Quand l'utiliser ?**
- Bases de **développement** et de **test**.
- Bases dont les données peuvent être **rechargées** (entrepôts alimentés par lots nocturnes, bases de reporting reconstruites).
- Petites bases internes où perdre quelques heures de données est acceptable.

> 📌 **Exemple de raisonnement** : une base de reporting reconstruite chaque nuit à partir de l'ERP n'a pas besoin de PITR — si on la perd, on relance l'alimentation. → modèle `SIMPLE`.

### 2. FULL

En modèle **FULL** (complet), **toutes les opérations sont entièrement journalisées**, et le journal n'est tronqué **que** lorsque vous en faites une sauvegarde avec `BACKUP LOG`.

**Conséquences :**
- ✅ **Aucune perte de données** possible jusqu'à la dernière sauvegarde de journal réussie.
- ✅ **Restauration à un instant T** (*point-in-time*) possible (voir §7.8.5).
- ✅ Indispensable pour la haute disponibilité (mise en miroir, AlwaysOn).
- ⚠️ Le journal **grossit** jusqu'à ce que vous le sauvegardiez : il faut **planifier des `BACKUP LOG` réguliers**.

**Quand l'utiliser ?**
- **Toutes les bases de production** où la perte de données n'est pas acceptable.
- Dès que vous avez besoin de pouvoir « remonter le temps » à la minute près.

> ⚠️ **Piège classique** : passer une base en `FULL` *sans* programmer de sauvegardes de journal. Le journal grossit alors sans fin jusqu'à saturer le disque. En `FULL`, **sauvegarde complète et sauvegarde de journal sont indissociables**.

### 3. BULK_LOGGED

Le modèle **BULK_LOGGED** est un compromis. Il fonctionne comme `FULL`, mais les **opérations en bloc** (*bulk operations*) sont **journalisées de façon minimale** : SQL Server n'enregistre que les extensions modifiées, pas chaque ligne.

Opérations concernées par la journalisation minimale :
- `BULK INSERT` et l'utilitaire `bcp` (import massif)
- `INSERT ... SELECT` massif (sous conditions)
- `SELECT ... INTO`
- Création et reconstruction d'index (`CREATE INDEX`, `ALTER INDEX ... REBUILD`)
- Opérations sur les données de type *large* (`WRITETEXT`, `UPDATETEXT`)

**Conséquences :**
- ✅ Le journal grossit **beaucoup moins** lors de grosses opérations en masse.
- ✅ Meilleures performances pour ces opérations.
- ❌ **Pas de restauration à un instant T** *à l'intérieur* d'un intervalle contenant une opération en bloc (on ne peut restaurer qu'à la fin d'une sauvegarde de journal, pas à une seconde précise au milieu).

**Quand l'utiliser ?**
- **Temporairement**, le temps d'une grosse opération de chargement ou de reconstruction d'index, puis on **revient en `FULL`** :

```sql
ALTER DATABASE Boutique SET RECOVERY BULK_LOGGED;
-- ... chargement massif / reconstruction d'index ...
ALTER DATABASE Boutique SET RECOVERY FULL;
BACKUP LOG Boutique TO DISK = 'C:\Backups\apres_chargement.trn';  -- on referme la chaîne
```

## Tableau comparatif

| Critère | SIMPLE | FULL | BULK_LOGGED |
|---------|:------:|:----:|:-----------:|
| Sauvegarde de journal (`BACKUP LOG`) | ❌ Non | ✅ Oui | ✅ Oui |
| Restauration à un instant T | ❌ Non | ✅ Oui | ⚠️ Partielle |
| Gestion du journal | Automatique | Manuelle (log backups) | Manuelle |
| Journalisation des opérations en bloc | Minimale | Complète | Minimale |
| Risque de perte de données | Élevé | Minimal | Minimal* |
| Usage typique | Dev / test | Production | Chargements massifs |

\* *Sauf à l'intérieur d'un intervalle contenant une opération en bloc.*

## Consulter et modifier le modèle de récupération

### Voir le modèle actuel de toutes les bases

```sql
SELECT
    name                AS NomBase,
    recovery_model_desc AS ModeleRecuperation
FROM sys.databases
ORDER BY name;
```

Résultat typique :

```
NomBase      ModeleRecuperation
-----------  ------------------
master       SIMPLE
model        FULL
msdb         SIMPLE
Boutique     FULL
BoutiqueTest SIMPLE
```

### Changer le modèle de récupération

```sql
-- Passer en mode complet (production)
ALTER DATABASE Boutique SET RECOVERY FULL;

-- Passer en mode simple (développement)
ALTER DATABASE BoutiqueTest SET RECOVERY SIMPLE;

-- Passer en mode bulk-logged (temporairement)
ALTER DATABASE Boutique SET RECOVERY BULK_LOGGED;
```

> 💡 **Bon à savoir** : une nouvelle base hérite du modèle de récupération de la base système `model`. Vérifiez toujours le modèle d'une base de production — ne supposez jamais qu'il est correct par défaut.

## Le piège n°1 en entreprise : le journal qui explose

Voici le scénario le plus fréquent rencontré sur le terrain :

```
1. Une base est en modèle FULL (souvent par défaut, hérité de 'model').
2. Personne n'a programmé de BACKUP LOG.
3. Le journal (.ldf) grossit... 1 Go... 10 Go... 100 Go...
4. Le disque du journal est plein → la base passe en lecture seule ou s'arrête.
5. Panique générale en production.
```

### Diagnostiquer pourquoi le journal ne se vide pas

SQL Server vous dit **exactement** pourquoi l'espace du journal n'est pas réutilisable :

```sql
SELECT name, log_reuse_wait_desc
FROM sys.databases
WHERE name = 'Boutique';
```

Valeurs fréquentes de `log_reuse_wait_desc` :
- `LOG_BACKUP` → il faut faire un `BACKUP LOG` (cas le plus courant en `FULL`).
- `ACTIVE_TRANSACTION` → une transaction très longue n'est pas terminée.
- `NOTHING` → tout va bien, l'espace est réutilisable.

### La bonne solution selon le besoin réel

- Si vous **avez besoin** de la restauration à l'instant T → mettez en place des **sauvegardes de journal régulières** (par ex. toutes les 15 minutes). Ce sont elles qui « vident » le journal.
- Si vous **n'en avez pas besoin** (dev, données rechargeables) → passez la base en `SIMPLE`.

> ❌ **À éviter absolument** : « régler » le problème avec `DBCC SHRINKFILE` à répétition sans en comprendre la cause. Le journal regrossira aussitôt, et les *shrink* répétés provoquent une **fragmentation des VLF** (voir ci-dessous) qui dégrade les performances. Traitez la **cause** (modèle + sauvegardes), pas le symptôme.

### Aparté : les VLF (Virtual Log Files)

En interne, le fichier journal est découpé en segments appelés **VLF** (*Virtual Log Files*). Un journal qui a grossi par petits incréments successifs, ou qui a subi de nombreux *shrink/grow*, se retrouve avec des **milliers de VLF**, ce qui ralentit le démarrage de la base et les sauvegardes/restaurations. C'est une raison de plus pour dimensionner correctement le journal et éviter les *shrink* à répétition.

## Questions fréquentes

**Q : Changer de modèle de récupération nécessite-t-il d'arrêter la base ?**
R : Non, `ALTER DATABASE ... SET RECOVERY` s'applique en ligne, immédiatement.

**Q : Si je passe de FULL à SIMPLE puis je reviens à FULL, y a-t-il un effet ?**
R : Oui — passer par `SIMPLE` **casse la chaîne de sauvegardes de journal**. Au retour en `FULL`, vous devez refaire une **sauvegarde complète** (ou différentielle) pour rétablir une base de chaîne, sinon les futures sauvegardes de journal seront inutilisables.

**Q : Quel modèle pour les bases système (master, model, msdb) ?**
R : `master` et `msdb` sont en `SIMPLE` par défaut, ce qui convient. Ne les modifiez pas sans raison précise.

**Q : Le modèle BULK_LOGGED fait-il vraiment gagner du temps ?**
R : Oui, sur de très grosses opérations en masse (chargements, reconstructions d'index), il réduit fortement le volume écrit dans le journal. Mais réservez-le à ces fenêtres précises.

---

## Résumé

- Le **modèle de récupération** détermine comment le **journal des transactions** est géré, et donc vos options de sauvegarde/restauration.
- **SIMPLE** : journal tronqué automatiquement, pas de `BACKUP LOG`, pas de PITR → dev/test, données rechargeables.
- **FULL** : tout journalisé, `BACKUP LOG` requis, PITR possible → production.
- **BULK_LOGGED** : compromis **temporaire** pour les grosses opérations en masse.
- En `FULL`, **sauvegarde complète + sauvegarde de journal sont indissociables**, sinon le journal sature le disque.
- On consulte avec `sys.databases` (`recovery_model_desc`, `log_reuse_wait_desc`) et on modifie avec `ALTER DATABASE ... SET RECOVERY`.
- Ne jamais traiter un journal plein par des *shrink* répétés : traiter la cause.

Maintenant que vous savez quel modèle conditionne vos sauvegardes, découvrons les **différents types de sauvegarde** que SQL Server met à votre disposition.
