# 7.3.1 Qu'est-ce qu'un plan d'exécution ?

## Introduction

Lorsque vous écrivez une requête SQL et que vous l'exécutez, SQL Server ne se contente pas simplement de "lire" votre code et de le suivre à la lettre. En réalité, il effectue un travail complexe en coulisses pour déterminer **la meilleure façon** d'obtenir les résultats que vous demandez.

Le **plan d'exécution** (ou *execution plan* en anglais) est essentiellement **la feuille de route** que SQL Server va suivre pour exécuter votre requête. C'est comme un itinéraire GPS qui vous montre le chemin choisi pour arriver à destination.

## Analogie pour comprendre

Imaginons que vous deviez vous rendre d'un point A à un point B dans une ville. Vous pourriez :
- Prendre l'autoroute (plus rapide mais plus long en distance)
- Traverser le centre-ville (plus court mais avec des feux rouges)
- Emprunter des routes secondaires (distance moyenne, vitesse moyenne)

De la même manière, pour récupérer des données dans une base de données, SQL Server a plusieurs "chemins" possibles. Le plan d'exécution représente **le chemin choisi** parmi toutes les options disponibles.

## Le rôle de l'optimiseur de requêtes

SQL Server possède un composant intelligent appelé **l'optimiseur de requêtes** (*Query Optimizer*). Son travail consiste à :

1. **Analyser** votre requête SQL
2. **Identifier** toutes les façons possibles d'exécuter cette requête
3. **Estimer** le coût de chaque méthode (en termes de temps CPU, lectures disque, mémoire, etc.)
4. **Choisir** la méthode la plus efficace
5. **Créer** le plan d'exécution final

C'est un peu comme si vous aviez un assistant qui, avant chaque voyage, calcule automatiquement le meilleur itinéraire en tenant compte du trafic, des travaux, de la météo, etc.

## Qu'est-ce qu'un plan d'exécution contient ?

Un plan d'exécution est composé d'une série d'**opérations** (appelées **opérateurs**) que SQL Server va effectuer dans un ordre précis. Chaque opérateur représente une action spécifique, par exemple :

- **Lire des données** dans une table
- **Filtrer** les lignes selon une condition WHERE
- **Joindre** deux tables ensemble
- **Trier** les résultats
- **Agréger** des données (SUM, COUNT, etc.)

Ces opérateurs sont organisés sous forme d'un **arbre** où chaque étape dépend des étapes précédentes.

## Types de plans d'exécution

SQL Server peut vous fournir deux types principaux de plans d'exécution :

### 1. Plan d'exécution estimé (*Estimated Execution Plan*)

- C'est le plan que SQL Server **prévoit** d'utiliser
- Il est généré **avant** l'exécution de la requête
- Basé sur des **estimations** (statistiques sur les données)
- **Ne consomme pas de ressources** pour exécuter la requête
- Utile pour analyser une requête sans l'exécuter réellement

**Dans SSMS** : Vous pouvez l'afficher en cliquant sur l'icône "Display Estimated Execution Plan" ou en utilisant le raccourci `Ctrl+L`.

### 2. Plan d'exécution réel (*Actual Execution Plan*)

- C'est le plan qui a **effectivement été utilisé** lors de l'exécution
- Disponible **après** l'exécution de la requête
- Contient des **statistiques réelles** (nombre exact de lignes traitées, temps réel, etc.)
- Plus précis que le plan estimé
- Utile pour diagnostiquer les problèmes de performance réels

**Dans SSMS** : Vous pouvez l'activer en cliquant sur "Include Actual Execution Plan" ou en utilisant le raccourci `Ctrl+M`, puis en exécutant votre requête.

## Pourquoi les plans d'exécution sont-ils importants ?

Les plans d'exécution sont un outil **essentiel** pour :

### 1. Comprendre comment SQL Server traite vos requêtes

Même si votre requête SQL semble simple, SQL Server peut effectuer des opérations complexes en arrière-plan. Le plan d'exécution vous montre exactement ce qui se passe.

### 2. Identifier les problèmes de performance

Si une requête est lente, le plan d'exécution vous aide à identifier :
- Quelles opérations prennent le plus de temps
- Si SQL Server utilise (ou non) les index disponibles
- Si certaines étapes traitent beaucoup plus de données que prévu

### 3. Optimiser vos requêtes

En comprenant le plan d'exécution, vous pouvez :
- Réécrire vos requêtes de manière plus efficace
- Créer des index appropriés
- Ajuster la structure de votre base de données

### 4. Communiquer avec les DBA

Les plans d'exécution constituent un **langage universel** entre développeurs et administrateurs de bases de données (DBA). Partager un plan d'exécution permet de diagnostiquer rapidement un problème.

## Exemple simple

Prenons une requête basique :

```sql
SELECT *
FROM Clients
WHERE Ville = 'Paris';
```

Pour cette requête, SQL Server pourrait choisir entre plusieurs options :

**Option 1 : Parcours complet de la table (Table Scan)**
- Lire **toutes** les lignes de la table Clients
- Vérifier pour chaque ligne si Ville = 'Paris'
- Garder uniquement les lignes qui correspondent

**Option 2 : Utilisation d'un index (Index Seek)**
- Si un index existe sur la colonne `Ville`
- Aller directement aux lignes où Ville = 'Paris' (comme un index dans un livre)
- Beaucoup plus rapide si la table est volumineuse

Le plan d'exécution vous montrera quelle option SQL Server a choisie et pourquoi.

## Format d'affichage

Les plans d'exécution peuvent être affichés sous différents formats :

### Format graphique (le plus courant)

- Représentation visuelle avec des icônes
- Facile à lire pour les débutants
- Affiche les opérateurs sous forme de boîtes connectées
- Le flux de données va généralement **de droite à gauche** et **de haut en bas**

### Format XML

- Représentation textuelle complète
- Contient tous les détails techniques
- Peut être sauvegardé et partagé facilement
- Utile pour l'analyse programmatique

### Format texte

- Version simplifiée et lisible
- Moins de détails que le format XML
- Utile pour une analyse rapide en ligne de commande

## Concepts clés à retenir

1. **Le plan d'exécution est automatique** : SQL Server le génère pour chaque requête, que vous le visualisiez ou non.

2. **Estimation vs. Réalité** : Le plan estimé est basé sur des prévisions ; le plan réel reflète ce qui s'est vraiment passé.

3. **Le coût est relatif** : Dans les plans d'exécution, les coûts sont exprimés en pourcentage relatif. Un opérateur qui représente 80% du coût total mérite votre attention en priorité.

4. **Les plans peuvent changer** : Si les données changent, si des index sont ajoutés ou supprimés, ou si les statistiques sont mises à jour, SQL Server peut choisir un plan différent pour la même requête.

5. **Les plans sont mis en cache** : Pour éviter de recalculer le plan à chaque exécution, SQL Server met en cache les plans d'exécution et les réutilise quand possible.

## Comment accéder aux plans d'exécution dans SSMS ?

**Pour le plan estimé :**
1. Écrivez votre requête dans SSMS
2. Cliquez sur l'icône "Display Estimated Execution Plan" (ou `Ctrl+L`)
3. Le plan apparaît dans un nouvel onglet

**Pour le plan réel :**
1. Cliquez sur l'icône "Include Actual Execution Plan" (ou `Ctrl+M`)
2. Exécutez votre requête (F5)
3. Le plan apparaît dans un onglet "Execution plan" en bas de la fenêtre

## Conclusion

Le plan d'exécution est votre **fenêtre** sur le fonctionnement interne de SQL Server. Comprendre ce qu'est un plan d'exécution est la première étape vers l'optimisation de vos requêtes et la résolution des problèmes de performance.

Dans les sections suivantes, nous apprendrons à **lire** et **interpréter** les plans d'exécution de manière plus détaillée, afin de pouvoir identifier les goulots d'étranglement et améliorer les performances de nos requêtes.

---

**Points à retenir :**
- Un plan d'exécution est la stratégie choisie par SQL Server pour exécuter une requête
- L'optimiseur de requêtes choisit automatiquement le meilleur plan parmi plusieurs options
- Il existe deux types : plan estimé (avant exécution) et plan réel (après exécution)
- Les plans d'exécution sont essentiels pour comprendre et optimiser les performances
- Ils peuvent être visualisés sous forme graphique, XML ou texte dans SSMS
