# 4.3.1 Syntaxe WITH ... AS (...)

## Introduction aux CTE

Les **CTE** (Common Table Expressions), ou **Expressions de Table Communes** en français, sont une fonctionnalité de T-SQL qui permet de créer des ensembles de résultats temporaires nommés. On peut les voir comme des "tables temporaires virtuelles" qui n'existent que pendant l'exécution d'une requête.

Les CTE utilisent la syntaxe `WITH ... AS (...)` et offrent une alternative plus lisible et plus flexible aux sous-requêtes dans le `FROM` (tables dérivées).

### Analogie simple

Imaginez que vous rédigez un long document :
- **Sans CTE** : Vous écrivez tout dans un seul paragraphe géant, difficile à lire
- **Avec CTE** : Vous créez d'abord des brouillons pour chaque section, puis vous les assemblez

Les CTE permettent de créer des "brouillons" (résultats intermédiaires) avec des noms clairs, avant de les utiliser dans la requête finale.

## Syntaxe de base

### Structure simple

```sql
WITH NomDuCTE AS (
    -- Requête qui définit le CTE
    SELECT colonnes
    FROM table
    WHERE conditions
)
-- Requête principale qui utilise le CTE
SELECT *
FROM NomDuCTE
WHERE autres_conditions;
```

**Points clés :**
1. Le mot-clé `WITH` commence la définition
2. `NomDuCTE` est le nom que vous donnez au résultat temporaire
3. La requête entre parenthèses définit le contenu du CTE
4. La requête principale utilise le CTE comme s'il s'agissait d'une table normale

### Structure complète

```sql
WITH
    CTE1 AS (
        -- Premier CTE
        SELECT ...
    ),
    CTE2 AS (
        -- Deuxième CTE (peut utiliser CTE1)
        SELECT ...
        FROM CTE1
    ),
    CTE3 AS (
        -- Troisième CTE
        SELECT ...
    )
-- Requête principale
SELECT *
FROM CTE1
JOIN CTE2 ON ...
WHERE ...;
```

**Remarques importantes :**
- Vous pouvez définir **plusieurs CTE** séparés par des virgules
- Un CTE peut **référencer** les CTE définis avant lui
- Un CTE ne peut **pas** référencer les CTE définis après lui
- Le CTE n'existe que pour **cette requête**

## Premier exemple : CTE simple

### Problème
Trouver les départements où le salaire moyen dépasse 3500€.

### Sans CTE (avec table dérivée)

```sql
SELECT *
FROM (
    SELECT
        DepartementID,
        AVG(Salaire) AS SalaireMoyen
    FROM Employes
    GROUP BY DepartementID
) AS Stats
WHERE SalaireMoyen > 3500;
```

### Avec CTE (plus lisible)

```sql
WITH StatsDepartements AS (
    SELECT
        DepartementID,
        AVG(Salaire) AS SalaireMoyen
    FROM Employes
    GROUP BY DepartementID
)
SELECT *
FROM StatsDepartements
WHERE SalaireMoyen > 3500;
```

**Résultat :**
| DepartementID | SalaireMoyen |
|---------------|--------------|
| 1 | 3833.33 |

**Avantages du CTE ici :**
- Le nom `StatsDepartements` est plus descriptif qu'un alias comme `Stats`
- La logique est séparée clairement en deux parties
- Plus facile à lire et à comprendre

## Exemple avec plusieurs CTE

### Problème
Afficher chaque département avec son salaire moyen, le nombre d'employés, et son budget.

### Solution avec plusieurs CTE

```sql
WITH
    -- CTE 1 : Statistiques des salaires par département
    StatsSalaires AS (
        SELECT
            DepartementID,
            AVG(Salaire) AS SalaireMoyen,
            COUNT(*) AS NombreEmployes,
            SUM(Salaire) AS MasseSalariale
        FROM Employes
        GROUP BY DepartementID
    ),
    -- CTE 2 : Enrichir avec les informations des départements
    AnalyseComplete AS (
        SELECT
            D.NomDepartement,
            S.SalaireMoyen,
            S.NombreEmployes,
            S.MasseSalariale,
            D.Budget,
            D.Budget - S.MasseSalariale AS BudgetRestant
        FROM StatsSalaires S
        INNER JOIN Departements D ON S.DepartementID = D.DepartementID
    )
-- Requête finale
SELECT
    NomDepartement,
    NombreEmployes,
    SalaireMoyen,
    MasseSalariale,
    Budget,
    BudgetRestant,
    ROUND((MasseSalariale * 100.0 / Budget), 2) AS PourcentageBudget
FROM AnalyseComplete
ORDER BY NomDepartement;
```

**Résultat :**
| NomDepartement | NombreEmployes | SalaireMoyen | MasseSalariale | Budget | BudgetRestant | PourcentageBudget |
|----------------|----------------|--------------|----------------|--------|---------------|-------------------|
| Informatique | 3 | 3833.33 | 11500 | 150000 | 138500 | 7.67 |
| Marketing | 3 | 3500.00 | 10500 | 120000 | 109500 | 8.75 |

**Explication étape par étape :**
1. **CTE 1 (StatsSalaires)** : Calcule les statistiques salariales par département
2. **CTE 2 (AnalyseComplete)** : Joint les stats avec les infos de département et ajoute des calculs
3. **Requête finale** : Sélectionne et calcule le pourcentage du budget utilisé

**Avantages :**
- Chaque étape est clairement définie et nommée
- Facile à tester chaque CTE séparément (pour déboguer)
- La logique métier est évidente

## Comparaison : Table dérivée vs CTE

Voyons la même requête écrite des deux façons pour comprendre la différence.

### Avec table dérivée (imbriquée)

```sql
SELECT
    NomDepartement,
    SalaireMoyen,
    NombreEmployes
FROM (
    SELECT
        D.NomDepartement,
        AVG(E.Salaire) AS SalaireMoyen,
        COUNT(*) AS NombreEmployes
    FROM Employes E
    INNER JOIN Departements D ON E.DepartementID = D.DepartementID
    GROUP BY D.DepartementID, D.NomDepartement
) AS Stats
WHERE NombreEmployes >= 3
ORDER BY SalaireMoyen DESC;
```

### Avec CTE (plus clair)

```sql
WITH StatsDepartements AS (
    SELECT
        D.NomDepartement,
        AVG(E.Salaire) AS SalaireMoyen,
        COUNT(*) AS NombreEmployes
    FROM Employes E
    INNER JOIN Departements D ON E.DepartementID = D.DepartementID
    GROUP BY D.DepartementID, D.NomDepartement
)
SELECT
    NomDepartement,
    SalaireMoyen,
    NombreEmployes
FROM StatsDepartements
WHERE NombreEmployes >= 3
ORDER BY SalaireMoyen DESC;
```

**Différences clés :**
1. **Lisibilité** : Le CTE sépare clairement la définition de l'utilisation
2. **Ordre** : Avec CTE, on lit de haut en bas ; avec table dérivée, on lit de l'intérieur vers l'extérieur
3. **Nom** : `StatsDepartements` est plus descriptif qu'un simple alias `Stats`

## Réutilisation d'un CTE

Un des grands avantages des CTE est qu'ils peuvent être **référencés plusieurs fois** dans la même requête.

### Exemple : Comparer chaque vendeur à la moyenne

```sql
WITH VentesTotales AS (
    SELECT
        Vendeur,
        SUM(Montant) AS TotalVentes
    FROM Ventes
    GROUP BY Vendeur
)
SELECT
    V.Vendeur,
    V.TotalVentes,
    (SELECT AVG(TotalVentes) FROM VentesTotales) AS MoyenneGlobale,
    V.TotalVentes - (SELECT AVG(TotalVentes) FROM VentesTotales) AS EcartMoyenne
FROM VentesTotales V
ORDER BY V.TotalVentes DESC;
```

**Résultat :**
| Vendeur | TotalVentes | MoyenneGlobale | EcartMoyenne |
|---------|-------------|----------------|--------------|
| Alice | 3700 | 3250 | 450 |
| Bob | 2800 | 3250 | -450 |

**Remarque :** Le CTE `VentesTotales` est utilisé **trois fois** dans la requête :
1. Dans le `FROM`
2. Dans la première sous-requête (pour la moyenne)
3. Dans la deuxième sous-requête (pour l'écart)

**Avec une table dérivée, il faudrait :**
- Soit répéter la définition trois fois
- Soit utiliser une table temporaire

## CTE qui référencent d'autres CTE

Un CTE peut utiliser un autre CTE défini avant lui.

### Exemple : Chaîne de transformations

```sql
WITH
    -- Étape 1 : Agrégation de base
    VentesParVendeur AS (
        SELECT
            Vendeur,
            SUM(Montant) AS TotalVentes,
            COUNT(*) AS NombreVentes
        FROM Ventes
        GROUP BY Vendeur
    ),
    -- Étape 2 : Ajout de calculs (utilise VentesParVendeur)
    StatistiquesEnrichies AS (
        SELECT
            Vendeur,
            TotalVentes,
            NombreVentes,
            TotalVentes / NombreVentes AS MoyenneParVente
        FROM VentesParVendeur
    ),
    -- Étape 3 : Classification (utilise StatistiquesEnrichies)
    VendeursClasses AS (
        SELECT
            Vendeur,
            TotalVentes,
            NombreVentes,
            MoyenneParVente,
            CASE
                WHEN TotalVentes > 3000 THEN 'Excellent'
                WHEN TotalVentes > 2000 THEN 'Bon'
                ELSE 'Moyen'
            END AS Performance
        FROM StatistiquesEnrichies
    )
-- Requête finale
SELECT *
FROM VendeursClasses
ORDER BY TotalVentes DESC;
```

**Résultat :**
| Vendeur | TotalVentes | NombreVentes | MoyenneParVente | Performance |
|---------|-------------|--------------|-----------------|-------------|
| Alice | 3700 | 3 | 1233.33 | Excellent |
| Bob | 2800 | 2 | 1400.00 | Bon |

**Avantages de cette approche :**
- Chaque transformation est isolée et testable
- La logique se lit comme une histoire, étape par étape
- Facile à modifier : pour ajouter une étape, il suffit d'ajouter un CTE
- Excellent pour la maintenance et la compréhension

## Cas d'usage typiques des CTE

### 1. Simplifier les requêtes complexes

**Problème :** Trouver les employés qui gagnent plus que la moyenne de leur département ET qui ne sont pas managers.

```sql
WITH
    MoyennesParDept AS (
        SELECT
            DepartementID,
            AVG(Salaire) AS SalaireMoyen
        FROM Employes
        GROUP BY DepartementID
    ),
    EmployesNonManagers AS (
        SELECT *
        FROM Employes
        WHERE EmployeID NOT IN (
            SELECT DISTINCT ManagerID
            FROM Employes
            WHERE ManagerID IS NOT NULL
        )
    )
SELECT
    E.NomEmploye,
    E.Salaire,
    E.DepartementID,
    M.SalaireMoyen
FROM EmployesNonManagers E
INNER JOIN MoyennesParDept M ON E.DepartementID = M.DepartementID
WHERE E.Salaire > M.SalaireMoyen
ORDER BY E.Salaire DESC;
```

### 2. Calculer des rangs et filtrer

**Problème :** Trouver les 2 meilleurs vendeurs par région.

```sql
WITH VentesClassees AS (
    SELECT
        Vendeur,
        Region,
        SUM(Montant) AS TotalVentes,
        ROW_NUMBER() OVER (
            PARTITION BY Region
            ORDER BY SUM(Montant) DESC
        ) AS Rang
    FROM Ventes
    GROUP BY Vendeur, Region
)
SELECT
    Vendeur,
    Region,
    TotalVentes
FROM VentesClassees
WHERE Rang <= 2
ORDER BY Region, Rang;
```

**Note :** On ne peut pas filtrer directement sur `ROW_NUMBER()` dans un `WHERE`, d'où l'utilité du CTE.

### 3. Éviter la répétition de code

**Problème :** Calculer plusieurs pourcentages basés sur le même total.

```sql
WITH TotalGeneral AS (
    SELECT SUM(Montant) AS Total
    FROM Ventes
)
SELECT
    Vendeur,
    SUM(Montant) AS VentesVendeur,
    ROUND(SUM(Montant) * 100.0 / (SELECT Total FROM TotalGeneral), 2) AS Pourcentage,
    (SELECT Total FROM TotalGeneral) AS TotalGeneral
FROM Ventes
GROUP BY Vendeur
ORDER BY VentesVendeur DESC;
```

### 4. Créer des données de référence temporaires

**Problème :** Comparer les ventes actuelles à des objectifs définis.

```sql
WITH Objectifs AS (
    -- Définir des objectifs de manière statique
    SELECT 'Alice' AS Vendeur, 4000 AS Objectif
    UNION ALL
    SELECT 'Bob', 3000
),
VentesReelles AS (
    SELECT
        Vendeur,
        SUM(Montant) AS TotalVentes
    FROM Ventes
    GROUP BY Vendeur
)
SELECT
    O.Vendeur,
    V.TotalVentes,
    O.Objectif,
    V.TotalVentes - O.Objectif AS Ecart,
    CASE
        WHEN V.TotalVentes >= O.Objectif THEN 'Objectif atteint ✓'
        ELSE 'En dessous de l''objectif ✗'
    END AS Statut
FROM Objectifs O
LEFT JOIN VentesReelles V ON O.Vendeur = V.Vendeur;
```

**Résultat :**
| Vendeur | TotalVentes | Objectif | Ecart | Statut |
|---------|-------------|----------|-------|--------|
| Alice | 3700 | 4000 | -300 | En dessous de l'objectif ✗ |
| Bob | 2800 | 3000 | -200 | En dessous de l'objectif ✗ |

## Avantages des CTE par rapport aux autres approches

### vs Tables dérivées (sous-requêtes dans FROM)

| Aspect | CTE | Table dérivée |
|--------|-----|---------------|
| **Lisibilité** | ✅ Excellent (noms explicites, séparation claire) | ⚠️ Moyen (imbrication) |
| **Réutilisation** | ✅ Peut être référencé plusieurs fois | ❌ Doit être redéfini |
| **Ordre de lecture** | ✅ Haut en bas (naturel) | ⚠️ Intérieur vers extérieur |
| **Débogage** | ✅ Facile (tester chaque CTE séparément) | ⚠️ Plus difficile |
| **Récursivité** | ✅ Supporté | ❌ Impossible |
| **Performance** | 🟰 Identique | 🟰 Identique |

### vs Tables temporaires (#temp)

| Aspect | CTE | Table temporaire |
|--------|-----|------------------|
| **Portée** | ⚠️ Une seule requête | ✅ Toute la session |
| **Syntaxe** | ✅ Simple, intégré à la requête | ⚠️ Nécessite CREATE/DROP |
| **Index** | ❌ Impossible | ✅ Peut avoir des index |
| **Réutilisation** | ⚠️ Limitée à une requête | ✅ Multiple dans la session |
| **Overhead** | ✅ Aucun | ⚠️ Création/gestion dans tempdb |
| **Statistiques** | ⚠️ Estimées par l'optimiseur | ✅ Réelles (si créées) |

### vs Vues

| Aspect | CTE | Vue |
|--------|-----|-----|
| **Persistance** | ⚠️ Temporaire (une requête) | ✅ Permanente (stockée) |
| **Réutilisation** | ❌ Doit être redéfini | ✅ Multiple requêtes/sessions |
| **Maintenance** | ✅ Auto-contenu dans la requête | ⚠️ Objet séparé à gérer |
| **Sécurité** | 🟰 Hérite des permissions | ✅ Permissions propres |
| **Contexte** | ✅ Parfait pour logique ponctuelle | ✅ Parfait pour abstraction réutilisable |

## Bonnes pratiques

### 1. Noms descriptifs

```sql
-- ❌ Peu clair
WITH T1 AS (...), T2 AS (...)
SELECT * FROM T1 JOIN T2...

-- ✅ Descriptif
WITH VentesParVendeur AS (...), ObjectifsVendeurs AS (...)
SELECT * FROM VentesParVendeur JOIN ObjectifsVendeurs...
```

### 2. Un CTE par concept logique

```sql
-- ✅ Bon : Chaque CTE a un rôle clair
WITH
    DonneesBase AS (
        -- Extraction des données brutes
        ...
    ),
    CalculsIntermediaires AS (
        -- Transformations
        ...
    ),
    ResultatsFiltres AS (
        -- Filtrage final
        ...
    )
SELECT * FROM ResultatsFiltres;
```

### 3. Commenter les CTE complexes

```sql
WITH
    -- Calcule le total des ventes par vendeur
    -- en excluant les ventes annulées (Montant < 0)
    VentesValides AS (
        SELECT
            Vendeur,
            SUM(Montant) AS TotalVentes
        FROM Ventes
        WHERE Montant > 0
        GROUP BY Vendeur
    )
SELECT * FROM VentesValides;
```

### 4. Limiter la profondeur de chaînage

```sql
-- ⚠️ Éviter trop de CTE chaînés (difficile à suivre)
WITH A AS (...),
     B AS (SELECT * FROM A),
     C AS (SELECT * FROM B),
     D AS (SELECT * FROM C),
     E AS (SELECT * FROM D),
     F AS (SELECT * FROM E)  -- Trop profond !
SELECT * FROM F;

-- ✅ Mieux : Regrouper ou simplifier
WITH
    DonneesPreparees AS (...),  -- Étapes A+B+C combinées
    ResultatsCalcules AS (...)   -- Étapes D+E+F combinées
SELECT * FROM ResultatsCalcules;
```

### 5. Indentation cohérente

```sql
WITH
    CTE1 AS (
        SELECT
            Colonne1,
            Colonne2
        FROM Table1
        WHERE Condition
    ),
    CTE2 AS (
        SELECT
            C1.Colonne1,
            C1.Colonne2
        FROM CTE1 C1
    )
SELECT *
FROM CTE2;
```

## Limitations des CTE

### 1. Portée limitée

Un CTE n'existe que pour **une seule instruction** SQL.

```sql
-- ❌ Erreur : Le CTE n'existe plus pour la seconde requête
WITH Stats AS (SELECT ...)
SELECT * FROM Stats;  -- ✅ Fonctionne

SELECT * FROM Stats;  -- ❌ Erreur : Stats n'existe pas ici !
```

**Solution :** Redéfinir le CTE ou utiliser une vue/table temporaire.

### 2. Pas de matérialisation garantie

Les CTE ne sont pas obligatoirement "matérialisés" (stockés temporairement).

```sql
-- Le CTE peut être réévalué plusieurs fois si référencé plusieurs fois
WITH Calculs AS (
    SELECT ... -- Requête coûteuse
)
SELECT * FROM Calculs
UNION ALL
SELECT * FROM Calculs;  -- Peut recalculer au lieu de réutiliser
```

**Solution :** Pour de grosses données, utiliser une table temporaire si la performance est critique.

### 3. Pas d'index

On ne peut pas créer d'index sur un CTE.

```sql
-- ❌ Impossible
WITH Stats AS (SELECT ...)
CREATE INDEX idx ON Stats(Colonne);  -- Erreur !
```

**Solution :** Utiliser une table temporaire si vous avez besoin d'index.

### 4. Ordre de définition important

Un CTE ne peut référencer que les CTE définis **avant** lui.

```sql
-- ❌ Erreur : CTE1 référence CTE2 qui n'est pas encore défini
WITH
    CTE1 AS (SELECT * FROM CTE2),  -- Erreur !
    CTE2 AS (SELECT ...)
SELECT * FROM CTE1;

-- ✅ Correct : Inverser l'ordre
WITH
    CTE2 AS (SELECT ...),
    CTE1 AS (SELECT * FROM CTE2)  -- OK
SELECT * FROM CTE1;
```

## Résumé

Les **CTE (Common Table Expressions)** utilisent la syntaxe `WITH ... AS (...)` pour créer des résultats temporaires nommés.

### Syntaxe clé

```sql
WITH NomCTE AS (
    requête
)
SELECT * FROM NomCTE;
```

### Points essentiels

✅ **Avantages :**
- Améliore considérablement la **lisibilité**
- Permet de **nommer** les résultats intermédiaires
- Peut être **référencé plusieurs fois** dans la même requête
- Permet de **chaîner** les transformations logiquement
- Support de la **récursivité** (CTE récursifs)
- Facilite le **débogage** (tester chaque CTE séparément)

⚠️ **Limites :**
- Portée limitée à **une seule instruction**
- Pas de **matérialisation** garantie
- Pas d'**index** possible
- **Ordre** de définition important

### Quand utiliser un CTE ?

- Pour **décomposer** des requêtes complexes
- Pour **nommer** des étapes logiques
- Quand vous devez **référencer** le même résultat plusieurs fois
- Pour **améliorer la lisibilité** du code
- Pour des **transformations en chaîne**

### Quand utiliser une alternative ?

- **Table temporaire** : Résultats volumineux, utilisés dans plusieurs requêtes, besoin d'index
- **Vue** : Logique réutilisée fréquemment dans toute l'application
- **Table dérivée** : Cas très simple où le CTE serait un "overkill"

Les CTE sont un outil moderne et élégant qui rend le code T-SQL plus maintenable et compréhensible. Ils sont devenus une pratique standard dans le développement SQL moderne !
