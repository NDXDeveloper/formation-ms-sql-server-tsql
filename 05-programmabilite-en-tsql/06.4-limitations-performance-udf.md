# 5.6.4 Limitations de Performance des UDF (surtout scalaires)

## Introduction

Les **fonctions définies par l'utilisateur** (User Defined Functions - UDF) sont des outils puissants en T-SQL, mais elles peuvent causer de **graves problèmes de performance** si elles ne sont pas utilisées correctement. Parmi toutes les UDF, les **fonctions scalaires** sont particulièrement problématiques et peuvent transformer une requête rapide en cauchemar de performance.

**Analogie simple :** Imaginez que vous devez calculer le prix total de 10 000 produits. Au lieu de demander à une calculatrice ultra-rapide de tout calculer d'un coup, vous demandez à un assistant de calculer chaque prix un par un, en notant le résultat sur un papier à chaque fois. C'est exactement ce que font les fonctions scalaires : elles travaillent **ligne par ligne** au lieu de traiter les données **en ensemble**, ce qui est catastrophique pour les performances.

---

## Pourquoi les UDF scalaires sont-elles si lentes ?

### 1. Exécution ligne par ligne (Row-by-Row Processing)

Les fonctions scalaires sont exécutées **une fois pour chaque ligne** du résultat, ce qui empêche SQL Server d'utiliser son approche optimisée basée sur les ensembles.

**Exemple du problème :**

```sql
-- Supposons que nous avons une fonction scalaire simple
CREATE FUNCTION dbo.CalculerRemise
(
    @montant DECIMAL(10,2)
)
RETURNS DECIMAL(10,2)
AS
BEGIN
    DECLARE @remise DECIMAL(10,2);

    IF @montant > 1000
        SET @remise = @montant * 0.15;
    ELSE IF @montant > 500
        SET @remise = @montant * 0.10;
    ELSE
        SET @remise = @montant * 0.05;

    RETURN @remise;
END;

-- Utilisation sur une table de 100 000 commandes
SELECT
    CommandeID,
    MontantTotal,
    dbo.CalculerRemise(MontantTotal) AS Remise  -- ⚠️ APPELÉE 100 000 FOIS !
FROM Commandes;
```

**Ce qui se passe réellement :**
1. SQL Server lit la première ligne : MontantTotal = 750
2. Appelle `dbo.CalculerRemise(750)` → Résultat : 75
3. SQL Server lit la deuxième ligne : MontantTotal = 1200
4. Appelle `dbo.CalculerRemise(1200)` → Résultat : 180
5. ... **répète 99 998 fois de plus** !

C'est comme si vous deviez faire 100 000 appels téléphoniques individuels au lieu d'envoyer un email à tout le monde en même temps !

### 2. Pas d'optimisation par l'optimiseur de requêtes

L'optimiseur SQL Server ne peut pas "voir" à l'intérieur des fonctions scalaires. Il ne peut donc pas :
- Réorganiser les opérations pour plus d'efficacité
- Utiliser les index de manière optimale
- Paralléliser l'exécution
- Estimer correctement le coût de la requête

**Résultat :** Des plans d'exécution sous-optimaux et des performances dégradées.

### 3. Coût caché et non visible dans les plans d'exécution

Les plans d'exécution montrent l'appel de la fonction comme ayant un coût quasi nul (0%), ce qui est **trompeur**. Le vrai coût de l'exécution de la fonction n'apparaît pas clairement dans le plan.

**Exemple :**

```sql
-- Cette requête peut prendre 30 secondes
SELECT
    ClientID,
    dbo.CalculerStatistique(ClientID) AS Stats  -- Le plan montrera 0% de coût ici !
FROM Clients;

-- Le plan d'exécution dira : "Table Scan sur Clients : 100% du coût"
-- Mais en réalité, 99% du temps est passé dans la fonction !
```

### 4. Pas de parallélisme

SQL Server ne peut généralement pas paralléliser les requêtes qui contiennent des fonctions scalaires, ce qui signifie qu'il n'utilisera qu'un seul CPU au lieu de plusieurs.

```sql
-- Cette requête utilisera 1 seul CPU (séquentiel)
SELECT
    ProductID,
    dbo.CalculerPrix(ProductID) AS Prix
FROM Products;  -- Même avec 1 million de lignes !

-- Sans la fonction, SQL Server pourrait utiliser 8 CPUs en parallèle
SELECT
    ProductID,
    Price * 1.20 AS Prix
FROM Products;  -- Peut utiliser plusieurs CPUs
```

## Démonstration de l'impact sur les performances

### Exemple 1 : Comparaison fonction scalaire vs expression directe

```sql
-- ❌ LENT : Fonction scalaire
CREATE FUNCTION dbo.CalculerTVA
(
    @montantHT DECIMAL(10,2)
)
RETURNS DECIMAL(10,2)
AS
BEGIN
    RETURN @montantHT * 0.20;
END;

-- Utilisation
SELECT
    ProduitID,
    PrixHT,
    dbo.CalculerTVA(PrixHT) AS TVA
FROM Produits;  -- 10 secondes sur 1 million de lignes

-- ✅ RAPIDE : Expression directe
SELECT
    ProduitID,
    PrixHT,
    PrixHT * 0.20 AS TVA
FROM Produits;  -- 1 seconde sur 1 million de lignes

-- 10 fois plus rapide !
```

**Différence :** La version avec fonction scalaire peut être **10 à 100 fois plus lente** pour le même résultat !

### Exemple 2 : Fonction scalaire avec accès aux données

Le problème devient encore pire quand la fonction scalaire accède à d'autres tables :

```sql
-- ❌ TRÈS LENT : Fonction qui interroge une table
CREATE FUNCTION dbo.ObtenirNomCategorie
(
    @categorieID INT
)
RETURNS VARCHAR(100)
AS
BEGIN
    DECLARE @nom VARCHAR(100);

    SELECT @nom = NomCategorie
    FROM Categories
    WHERE CategorieID = @categorieID;

    RETURN @nom;
END;

-- Utilisation sur 100 000 produits
SELECT
    ProduitID,
    NomProduit,
    dbo.ObtenirNomCategorie(CategorieID) AS Categorie  -- ⚠️ 100 000 requêtes !
FROM Produits;
-- Temps d'exécution : 45 secondes

-- ✅ RAPIDE : JOIN direct
SELECT
    p.ProduitID,
    p.NomProduit,
    c.NomCategorie AS Categorie
FROM Produits AS p
INNER JOIN Categories AS c ON p.CategorieID = c.CategorieID;
-- Temps d'exécution : 2 secondes

-- Plus de 20 fois plus rapide !
```

**Ce qui se passe avec la fonction :**
- Pour chaque produit, SQL Server exécute une requête SELECT sur la table Categories
- Si vous avez 100 000 produits, c'est 100 000 requêtes SELECT individuelles
- Même avec des index, c'est extrêmement inefficace

**Avec le JOIN :**
- Une seule opération qui traite toutes les lignes en ensemble
- SQL Server peut optimiser avec des index
- Peut utiliser le parallélisme

### Exemple 3 : Impact cumulatif sur des requêtes complexes

```sql
-- ❌ CAUCHEMAR DE PERFORMANCE : Plusieurs fonctions scalaires
SELECT
    c.CommandeID,
    c.ClientID,
    dbo.ObtenirNomClient(c.ClientID) AS NomClient,           -- Requête 1
    dbo.ObtenirEmailClient(c.ClientID) AS EmailClient,        -- Requête 2
    dbo.CalculerRemise(c.MontantTotal) AS Remise,            -- Calcul 1
    dbo.CalculerTVA(c.MontantTotal) AS TVA,                  -- Calcul 2
    dbo.ObtenirNomProduit(c.ProduitPrincipalID) AS Produit   -- Requête 3
FROM Commandes AS c
WHERE c.DateCommande >= '2025-01-01';
-- Sur 50 000 commandes : 3-5 minutes d'exécution

-- ✅ OPTIMISÉ : JOINs et expressions directes
SELECT
    c.CommandeID,
    c.ClientID,
    cl.NomClient,
    cl.Email AS EmailClient,
    CASE
        WHEN c.MontantTotal > 1000 THEN c.MontantTotal * 0.15
        WHEN c.MontantTotal > 500 THEN c.MontantTotal * 0.10
        ELSE c.MontantTotal * 0.05
    END AS Remise,
    c.MontantTotal * 0.20 AS TVA,
    p.NomProduit AS Produit
FROM Commandes AS c
INNER JOIN Clients AS cl ON c.ClientID = cl.ClientID
LEFT JOIN Produits AS p ON c.ProduitPrincipalID = p.ProduitID
WHERE c.DateCommande >= '2025-01-01';
-- Sur 50 000 commandes : 5-10 secondes d'exécution

-- 30 à 60 fois plus rapide !
```

## Comparaison des performances : UDF vs Alternatives

| Type de fonction | Performance | Utilisation recommandée |
|-----------------|-------------|------------------------|
| **Fonction scalaire** | ❌ Très lente (x10 à x100 plus lent) | Éviter autant que possible |
| **Fonction table inline** | ✅ Excellente (similaire à une vue) | Recommandée pour ensembles de données |
| **Fonction table multi-instructions** | ⚠️ Moyenne (moins bonne qu'inline) | Uniquement si logique complexe nécessaire |
| **Expression T-SQL directe** | ✅ Excellente | Recommandée pour calculs simples |
| **JOIN** | ✅ Excellente | Recommandée pour récupérer des données |
| **CTE ou sous-requête** | ✅ Bonne à excellente | Bonne alternative aux fonctions |

## Problèmes spécifiques des fonctions scalaires

### 1. Le piège de la simplicité apparente

```sql
-- Cette fonction SEMBLE simple et inoffensive
CREATE FUNCTION dbo.ObtenirPrixTTC
(
    @prixHT DECIMAL(10,2)
)
RETURNS DECIMAL(10,2)
AS
BEGIN
    RETURN @prixHT * 1.20;
END;

-- Mais sur une grosse table, elle tue les performances
SELECT
    ProduitID,
    dbo.ObtenirPrixTTC(PrixHT) AS PrixTTC  -- LENT
FROM Produits
WHERE CategorieID = 5;
```

**Pourquoi est-ce un piège ?**
- Le code semble propre et réutilisable
- La logique est simple (juste une multiplication)
- Mais l'impact sur les performances est désastreux

**Solution :**
```sql
-- Remplacer par une expression directe
SELECT
    ProduitID,
    PrixHT * 1.20 AS PrixTTC  -- RAPIDE
FROM Produits
WHERE CategorieID = 5;

-- Ou créer une colonne calculée persistée
ALTER TABLE Produits
ADD PrixTTC AS (PrixHT * 1.20) PERSISTED;
```

### 2. Les fonctions scalaires empêchent l'utilisation des index

```sql
-- ❌ Ceci empêche l'utilisation de l'index sur DateCommande
SELECT
    CommandeID,
    DateCommande
FROM Commandes
WHERE YEAR(DateCommande) = 2025;  -- Fonction sur la colonne indexée !

-- Le problème : SQL Server doit calculer YEAR() pour CHAQUE ligne
-- avant de filtrer, donc l'index ne peut pas être utilisé efficacement

-- ✅ Ceci peut utiliser l'index
SELECT
    CommandeID,
    DateCommande
FROM Commandes
WHERE DateCommande >= '2025-01-01'
    AND DateCommande < '2026-01-01';
```

### 3. Impact sur les statistiques et l'estimation

SQL Server ne peut pas estimer correctement :
- Le nombre de lignes qui seront retournées
- Le temps d'exécution réel
- Les ressources nécessaires

**Résultat :** Plans d'exécution sous-optimaux et surprises désagréables en production.

## Solutions et alternatives aux fonctions scalaires

### Solution 1 : Expressions T-SQL directes

**Pour les calculs simples, utilisez des expressions directes :**

```sql
-- ❌ Fonction scalaire
CREATE FUNCTION dbo.CalculerPrixNet(@prix DECIMAL(10,2), @remise DECIMAL(5,2))
RETURNS DECIMAL(10,2)
AS BEGIN
    RETURN @prix * (1 - @remise / 100);
END;

SELECT dbo.CalculerPrixNet(PrixBrut, TauxRemise) FROM Produits;

-- ✅ Expression directe
SELECT PrixBrut * (1 - TauxRemise / 100.0) AS PrixNet FROM Produits;
```

### Solution 2 : Fonctions table inline

**Remplacez les fonctions scalaires par des fonctions table inline :**

```sql
-- ❌ Fonction scalaire
CREATE FUNCTION dbo.ObtenirNombreCommandes(@clientID INT)
RETURNS INT
AS BEGIN
    DECLARE @count INT;
    SELECT @count = COUNT(*) FROM Commandes WHERE ClientID = @clientID;
    RETURN @count;
END;

SELECT ClientID, dbo.ObtenirNombreCommandes(ClientID) FROM Clients;

-- ✅ Fonction table inline avec CROSS APPLY
CREATE FUNCTION dbo.ObtenirStatsClient(@clientID INT)
RETURNS TABLE AS RETURN (
    SELECT
        COUNT(*) AS NombreCommandes,
        SUM(MontantTotal) AS TotalAchats
    FROM Commandes
    WHERE ClientID = @clientID
);

SELECT
    c.ClientID,
    s.NombreCommandes,
    s.TotalAchats
FROM Clients AS c
CROSS APPLY dbo.ObtenirStatsClient(c.ClientID) AS s;
```

### Solution 3 : Colonnes calculées (Computed Columns)

**Pour les calculs toujours identiques :**

```sql
-- ❌ Fonction scalaire appelée à chaque requête
CREATE FUNCTION dbo.CalculerPrixTTC(@prixHT DECIMAL(10,2))
RETURNS DECIMAL(10,2)
AS BEGIN
    RETURN @prixHT * 1.20;
END;

-- ✅ Colonne calculée (calculée à la volée)
ALTER TABLE Produits
ADD PrixTTC AS (PrixHT * 1.20);

-- ✅ Encore mieux : Colonne calculée PERSISTÉE (stockée physiquement)
ALTER TABLE Produits
ADD PrixTTC AS (PrixHT * 1.20) PERSISTED;

-- Peut même créer un index dessus !
CREATE INDEX IX_PrixTTC ON Produits(PrixTTC);
```

### Solution 4 : JOINs au lieu de fonctions pour récupérer des données

```sql
-- ❌ Fonction scalaire
CREATE FUNCTION dbo.ObtenirNomClient(@clientID INT)
RETURNS VARCHAR(100)
AS BEGIN
    DECLARE @nom VARCHAR(100);
    SELECT @nom = NomClient FROM Clients WHERE ClientID = @clientID;
    RETURN @nom;
END;

SELECT CommandeID, dbo.ObtenirNomClient(ClientID) FROM Commandes;

-- ✅ JOIN simple
SELECT
    cmd.CommandeID,
    cl.NomClient
FROM Commandes AS cmd
INNER JOIN Clients AS cl ON cmd.ClientID = cl.ClientID;
```

### Solution 5 : Common Table Expressions (CTE)

**Pour encapsuler la logique de manière lisible :**

```sql
-- ❌ Fonction scalaire pour logique complexe
CREATE FUNCTION dbo.CategoriserClient(@clientID INT)
RETURNS VARCHAR(20)
AS BEGIN
    DECLARE @total DECIMAL(10,2);
    DECLARE @categorie VARCHAR(20);

    SELECT @total = SUM(MontantTotal)
    FROM Commandes
    WHERE ClientID = @clientID;

    IF @total > 10000 SET @categorie = 'VIP';
    ELSE IF @total > 5000 SET @categorie = 'Premium';
    ELSE SET @categorie = 'Standard';

    RETURN @categorie;
END;

SELECT ClientID, dbo.CategoriserClient(ClientID) FROM Clients;

-- ✅ CTE avec CASE
WITH StatsClients AS (
    SELECT
        ClientID,
        SUM(MontantTotal) AS TotalAchats
    FROM Commandes
    GROUP BY ClientID
)
SELECT
    c.ClientID,
    CASE
        WHEN s.TotalAchats > 10000 THEN 'VIP'
        WHEN s.TotalAchats > 5000 THEN 'Premium'
        ELSE 'Standard'
    END AS Categorie
FROM Clients AS c
LEFT JOIN StatsClients AS s ON c.ClientID = s.ClientID;
```

### Solution 6 : Vues pour encapsuler la logique

```sql
-- ❌ Fonctions scalaires multiples
SELECT
    p.ProduitID,
    dbo.CalculerPrixTTC(p.PrixHT) AS PrixTTC,
    dbo.CalculerMarge(p.PrixHT, p.PrixAchat) AS Marge,
    dbo.ObtenirNomCategorie(p.CategorieID) AS Categorie
FROM Produits AS p;

-- ✅ Vue qui encapsule la logique
CREATE VIEW dbo.VueProduitsEnrichi AS
SELECT
    p.ProduitID,
    p.NomProduit,
    p.PrixHT,
    p.PrixHT * 1.20 AS PrixTTC,
    p.PrixHT - p.PrixAchat AS Marge,
    c.NomCategorie AS Categorie
FROM Produits AS p
LEFT JOIN Categories AS c ON p.CategorieID = c.CategorieID;

-- Utilisation simple et performante
SELECT * FROM dbo.VueProduitsEnrichi WHERE PrixTTC > 50;
```

## Cas particulier : SQL Server 2019+ et le Scalar UDF Inlining

À partir de **SQL Server 2019** (niveau de compatibilité **150 ou supérieur**), Microsoft a introduit le **« Scalar UDF Inlining »**, l'une des fonctionnalités de l'*Intelligent Query Processing*. Le moteur transforme **automatiquement** de nombreuses fonctions scalaires en une expression équivalente directement intégrée à la requête : l'exécution ligne par ligne disparaît, et l'optimisation par ensembles ainsi que le parallélisme redeviennent possibles. **Cette optimisation est activée par défaut.**

### Ce que l'inlining sait gérer (contrairement à une idée reçue)

Le Scalar UDF Inlining a justement été conçu pour les fonctions « réalistes », pas seulement pour les calculs triviaux. Une fonction reste **inlinable** même si elle :

- déclare et affecte des variables (`DECLARE`, `SET`) ;
- contient des `SELECT` avec affectation de variables — **y compris en lisant d'autres tables** ;
- utilise des branchements `IF / ELSE` imbriqués ;
- appelle d'autres fonctions (imbriquées ou récursives), ou des opérateurs comme `EXISTS`, `IS NULL`.

Autrement dit, la fonction `ObtenirNomClient` qui lit la table `Clients` (vue plus haut) **peut tout à fait être inlinée** sur SQL Server 2019+. C'est précisément ce type de fonction « avec accès aux données » que l'inlining vise à accélérer.

```sql
-- Cette fonction est INLINABLE : variables + IF/ELSE + un seul RETURN, sans GETDATE/NEWID/etc.
CREATE FUNCTION dbo.CalculerRemiseInlinable(@montant DECIMAL(10,2))
RETURNS DECIMAL(10,2)
AS
BEGIN
    DECLARE @remise DECIMAL(10,2);
    IF @montant > 1000      SET @remise = @montant * 0.15;
    ELSE IF @montant > 500  SET @remise = @montant * 0.10;
    ELSE                    SET @remise = @montant * 0.05;
    RETURN @remise;
END;
```

### Ce qui EMPÊCHE l'inlining

Une fonction n'est **pas** inlinable si elle :

- appelle une fonction intrinsèque **dépendante du temps** (`GETDATE()`, `SYSDATETIME()`…) ou à **effet de bord** (`NEWID()`, `NEWSEQUENTIALID()`, `RAND()`) ;
- utilise des **variables de type table**, des **curseurs** ou du **SQL dynamique** ;
- exécute une procédure stockée (`EXEC`) ;
- contient **plusieurs** instructions `RETURN` (depuis SQL Server 2019 CU5, un seul `RETURN` est admis) ;
- est définie avec une clause `EXECUTE AS` autre que `CALLER`.

### Vérifier l'éligibilité d'une fonction et l'état du réglage

```sql
-- Une fonction donnée est-elle inlinable ? (colonne is_inlineable de sys.sql_modules)
SELECT OBJECT_NAME(object_id) AS Fonction, is_inlineable
FROM sys.sql_modules
WHERE OBJECT_NAME(object_id) = 'CalculerRemiseInlinable';
-- is_inlineable = 1 → inlinable ; 0 → non inlinable

-- État du réglage au niveau de la base (activé par défaut en compat 150+)
SELECT name, value
FROM sys.database_scoped_configurations
WHERE name = 'TSQL_SCALAR_UDF_INLINING';

-- Activer / désactiver explicitement
ALTER DATABASE SCOPED CONFIGURATION SET TSQL_SCALAR_UDF_INLINING = ON;   -- valeur par défaut
ALTER DATABASE SCOPED CONFIGURATION SET TSQL_SCALAR_UDF_INLINING = OFF;  -- pour le désactiver
```

> 💡 **Conséquence pratique :** sur SQL Server 2019+/2022, beaucoup de fonctions scalaires « classiques » ne sont plus le gouffre de performance décrit plus haut — le moteur les réécrit en coulisses. **Mais** cela ne dispense pas des bonnes pratiques : l'inlining ne couvre pas toutes les fonctions (voir la liste ci-dessus), ne s'applique pas aux versions ≤ 2017, et peut être désactivé (il l'a d'ailleurs été temporairement par défaut dans certaines mises à jour à cause de bugs). La règle reste donc : **concevoir directement avec des expressions, des JOIN ou des fonctions table inline (TVF)** plutôt que de compter sur l'inlining automatique.

## Détection des problèmes de performance liés aux UDF

### 1. Analyser les requêtes lentes

```sql
-- Trouver les requêtes qui utilisent des fonctions scalaires
SELECT
    qt.text AS RequeteSQL,
    qs.execution_count AS NombreExecutions,
    qs.total_elapsed_time / 1000000.0 AS TotalSecondes,
    qs.total_elapsed_time / qs.execution_count / 1000000.0 AS MoyenneSecondes
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS qt
WHERE qt.text LIKE '%dbo.%(%'  -- Recherche d'appels de fonctions
    AND qt.text LIKE '%SELECT%'
ORDER BY qs.total_elapsed_time DESC;
```

### 2. Identifier les fonctions scalaires dans votre base

```sql
-- Lister toutes les fonctions scalaires
SELECT
    SCHEMA_NAME(schema_id) AS SchemaName,
    name AS FunctionName,
    create_date AS DateCreation,
    modify_date AS DerniereModification
FROM sys.objects
WHERE type IN ('FN', 'IF')  -- FN = Scalar function, IF = Inline Table-Valued Function
ORDER BY name;
```

### 3. Examiner le plan d'exécution

Dans SSMS :
1. Activez "Include Actual Execution Plan" (Ctrl+M)
2. Exécutez votre requête
3. Regardez le plan d'exécution
4. **Attention** : Le coût montré pour les UDF scalaires est trompeur (souvent 0%)

## Bonnes pratiques et recommandations

### ✅ À FAIRE

1. **Préférez les expressions T-SQL directes** pour les calculs simples
   ```sql
   SELECT Prix * 1.20 AS PrixTTC  -- Au lieu de dbo.CalculerTTC(Prix)
   ```

2. **Utilisez les fonctions table inline** au lieu des scalaires
   ```sql
   SELECT * FROM dbo.ObtenirCommandes(ClientID)  -- Inline TVF
   ```

3. **Utilisez des JOINs** pour récupérer des données d'autres tables
   ```sql
   SELECT c.*, cat.Nom FROM Produits c JOIN Categories cat ON ...
   ```

4. **Créez des colonnes calculées persistées** pour les calculs fréquents
   ```sql
   ALTER TABLE Produits ADD PrixTTC AS (PrixHT * 1.20) PERSISTED;
   ```

5. **Utilisez des CTE ou sous-requêtes** pour la lisibilité
   ```sql
   WITH Stats AS (SELECT ...) SELECT * FROM Stats;
   ```

6. **Documentez les fonctions existantes** qui posent problème
   ```sql
   -- TODO: Cette fonction scalaire cause des problèmes de performance
   -- Remplacer par un JOIN ou une expression directe
   ```

### ❌ À ÉVITER

1. **Ne créez PAS de fonctions scalaires** pour des opérations simples
   ```sql
   -- ❌ NE PAS FAIRE
   CREATE FUNCTION dbo.Additionner(@a INT, @b INT)
   RETURNS INT AS BEGIN RETURN @a + @b; END;
   ```

2. **N'appelez PAS de fonctions scalaires** dans des requêtes sur de grosses tables
   ```sql
   -- ❌ ÉVITER sur des tables de plus de 1000 lignes
   SELECT dbo.MaFonction(Colonne) FROM GrosseTable;
   ```

3. **N'utilisez PAS de fonctions scalaires** qui accèdent à d'autres tables
   ```sql
   -- ❌ ÉVITER : Cause N+1 requêtes
   CREATE FUNCTION dbo.GetValue(@id INT) RETURNS VARCHAR(100)
   AS BEGIN
       DECLARE @val VARCHAR(100);
       SELECT @val = Colonne FROM AutreTable WHERE ID = @id;
       RETURN @val;
   END;
   ```

4. **N'appliquez PAS de fonctions** sur des colonnes indexées dans WHERE
   ```sql
   -- ❌ Empêche l'utilisation de l'index
   WHERE YEAR(DateCommande) = 2025

   -- ✅ Permet l'utilisation de l'index
   WHERE DateCommande >= '2025-01-01' AND DateCommande < '2026-01-01'
   ```

## Stratégie de migration : Remplacer les fonctions scalaires existantes

Si vous avez hérité d'une base de données avec beaucoup de fonctions scalaires :

### Étape 1 : Inventaire et priorisation

```sql
-- Identifier les fonctions scalaires les plus utilisées
SELECT
    o.name AS FunctionName,
    COUNT(*) AS NombreReferences
FROM sys.sql_expression_dependencies AS d
INNER JOIN sys.objects AS o ON d.referenced_id = o.object_id
WHERE o.type = 'FN'  -- Scalar function
GROUP BY o.name
ORDER BY COUNT(*) DESC;
```

### Étape 2 : Évaluer l'impact

- Commencez par les fonctions utilisées dans les requêtes les plus lentes
- Testez les performances avant/après
- Documentez les gains de performance

### Étape 3 : Remplacer progressivement

```sql
-- Exemple de migration
-- AVANT
SELECT
    ClientID,
    dbo.CalculerTotal(ClientID) AS Total
FROM Clients;

-- APRÈS (Étape 1 : Créer une fonction inline équivalente)
CREATE FUNCTION dbo.CalculerTotal_Inline(@clientID INT)
RETURNS TABLE AS RETURN (
    SELECT SUM(Montant) AS Total
    FROM Commandes
    WHERE ClientID = @clientID
);

-- APRÈS (Étape 2 : Utiliser avec APPLY)
SELECT
    c.ClientID,
    t.Total
FROM Clients AS c
CROSS APPLY dbo.CalculerTotal_Inline(c.ClientID) AS t;

-- APRÈS (Étape 3 : Remplacer complètement par un JOIN/CTE si possible)
WITH Totaux AS (
    SELECT ClientID, SUM(Montant) AS Total
    FROM Commandes
    GROUP BY ClientID
)
SELECT
    c.ClientID,
    t.Total
FROM Clients AS c
LEFT JOIN Totaux AS t ON c.ClientID = t.ClientID;
```

### Étape 4 : Tests et validation

## Résumé

Les **fonctions scalaires** en T-SQL présentent des **limitations de performance majeures** :

**Problèmes principaux :**
- ⚠️ Exécution **ligne par ligne** (pas d'optimisation par ensemble)
- ⚠️ **Pas de parallélisme** possible
- ⚠️ Coût **caché** dans les plans d'exécution
- ⚠️ Empêche l'utilisation optimale des **index**
- ⚠️ Impact **multiplicateur** sur de grosses tables

**Solutions recommandées :**
- ✅ **Expressions T-SQL directes** pour calculs simples
- ✅ **Fonctions table inline** au lieu de scalaires
- ✅ **JOINs** pour récupérer des données
- ✅ **Colonnes calculées** pour valeurs dérivées
- ✅ **CTEs et sous-requêtes** pour lisibilité
- ✅ **Vues** pour encapsuler la logique

**Règle d'or :**
> **Évitez les fonctions scalaires autant que possible, surtout sur de grosses tables !**

**Exception majeure (SQL Server 2019+) :**
- Le **Scalar UDF Inlining** (compat 150+, activé par défaut) réécrit automatiquement de **nombreuses** fonctions scalaires — y compris celles qui lisent des tables — supprimant une grande partie de la pénalité décrite ici
- Il ne couvre cependant pas tous les cas (ni les versions ≤ 2017) : mieux vaut concevoir d'emblée avec des expressions/JOIN/fonctions inline plutôt que d'en dépendre

**Impact sur les performances :**
- Une fonction scalaire peut rendre une requête **10 à 100 fois plus lente**
- Sur de gros volumes, cela peut transformer 5 secondes en 5 minutes

**En résumé :** Les fonctions scalaires semblent pratiques et élégantes, mais elles cachent un piège de performance redoutable. Privilégiez toujours les alternatives optimisées basées sur les ensembles !
