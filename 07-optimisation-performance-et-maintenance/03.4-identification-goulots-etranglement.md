# 7.3.4 Identification des goulots d'étranglement

## Introduction

Maintenant que vous savez lire un plan d'exécution et reconnaître les principaux opérateurs, il est temps d'apprendre à **identifier les goulots d'étranglement** — ces points précis qui ralentissent vos requêtes et dégradent les performances de votre application.

Un **goulot d'étranglement** (ou *bottleneck* en anglais) est un point dans le plan d'exécution où les performances se dégradent significativement, ralentissant l'ensemble de la requête. C'est comme un embouteillage sur une autoroute : même si le reste du trajet est fluide, cet unique point congestionné ralentit tout le monde.

Dans cette section, nous allons apprendre à **détecter**, **comprendre** et **prioriser** les goulots d'étranglement dans vos plans d'exécution.

## Qu'est-ce qu'un goulot d'étranglement ?

### Analogie : La chaîne de production

Imaginez une usine avec plusieurs étapes de production :
1. Découpe du bois : 100 pièces/heure
2. Ponçage : 80 pièces/heure ⚠️
3. Peinture : 120 pièces/heure
4. Assemblage : 150 pièces/heure

Même si les autres étapes sont rapides, l'usine ne peut produire que **80 pièces/heure** à cause du ponçage. Le ponçage est le **goulot d'étranglement** — c'est lui qui limite la performance globale.

### Dans SQL Server

Dans un plan d'exécution, un goulot d'étranglement est un opérateur qui :
- **Consomme** la majorité du temps et des ressources
- **Traite** un volume de données disproportionné
- **Limite** la vitesse d'exécution de toute la requête

Améliorer cet opérateur aura un **impact significatif** sur les performances globales.

## Les signes révélateurs de goulots d'étranglement

### 1. Pourcentage de coût élevé

#### Le signal le plus évident

Si un opérateur représente **plus de 50%** du coût total de la requête, c'est presque toujours un goulot d'étranglement.

**Exemple :**
```
Opérateur A : 78%  ← GOULOT D'ÉTRANGLEMENT !
Opérateur B : 12%
Opérateur C : 7%
Opérateur D : 3%
```

#### Pourquoi c'est important ?

Si vous réduisez le coût de l'Opérateur A de moitié, vous améliorerez la performance globale de la requête d'environ 39% (78% ÷ 2). C'est le meilleur retour sur investissement !

#### Règle pratique

- **> 50%** : Goulot d'étranglement majeur — priorité absolue
- **30-50%** : Goulot d'étranglement significatif — à analyser
- **< 30%** : Potentiellement optimisable, mais moins critique

### 2. Flèches très épaisses

#### Ce que cela signifie

Une **flèche épaisse** dans le plan d'exécution indique qu'un **volume important de données** transite entre deux opérateurs.

#### Analogie : Le trafic routier

Une flèche fine = une voiture isolée (fluide)
Une flèche épaisse = un flot continu de camions (congestion possible)

#### Comment l'identifier ?

Dans SSMS, survolez la flèche et regardez :
- **Nombre de lignes estimées** : Ce que SQL Server pensait
- **Nombre de lignes réelles** : Ce qui s'est vraiment passé (plan réel uniquement)

#### Signal d'alarme

Si une flèche épaisse **entre** dans un opérateur coûteux, c'est souvent le problème :
- Trop de données à traiter
- Filtrage inefficace en amont
- Index manquant

**Exemple problématique :**
```
[Hash Match: 65%] ← [FLÈCHE TRÈS ÉPAISSE: 5M lignes] ← [Table Scan: 25%]
```

Le Table Scan envoie 5 millions de lignes au Hash Match, qui doit toutes les traiter. Double problème !

### 3. Écart important entre estimation et réalité

#### Le problème des statistiques

SQL Server base ses décisions sur des **estimations**. Si ces estimations sont très éloignées de la réalité, SQL Server peut faire de mauvais choix.

#### Comment le détecter ?

Dans le plan réel, comparez :
- **Estimated Number of Rows** (nombre estimé)
- **Actual Number of Rows** (nombre réel)

#### Règle d'évaluation

| Ratio Réel/Estimé | Diagnostic |
|-------------------|------------|
| 0.9 à 1.1 | ✅ Excellent — estimation précise |
| 0.5 à 2 | ⚠️ Acceptable — petite imprécision |
| 0.1 à 10 | ❌ Problématique — grande différence |
| < 0.1 ou > 10 | 🔥 Critique — statistiques obsolètes |

#### Exemple problématique

```
Index Seek (Coût: 5%)
  Estimé : 100 lignes
  Réel : 500 000 lignes  ← PROBLÈME !
```

SQL Server pensait traiter 100 lignes et a optimisé pour cela. Mais en réalité, il traite 500 000 lignes. Le plan choisi n'est probablement pas optimal.

#### Conséquences

Cet écart peut conduire à :
- Mauvais choix d'opérateur de jointure
- Mémoire insuffisante allouée (spill to disk)
- Parallélisme mal configuré
- Plan globalement sous-optimal

#### Solution

Mettre à jour les statistiques :
```sql
UPDATE STATISTICS NomDeTable;
-- ou
UPDATE STATISTICS NomDeTable NomIndex;
```

### 4. Avertissements visuels (triangles jaunes)

#### Les avertissements de SSMS

SQL Server Management Studio affiche des **triangles jaunes** (⚠️) sur certains opérateurs pour signaler des problèmes.

#### Types d'avertissements courants

**Statistiques manquantes**
- Message : "Missing index" ou "No Join Predicate"
- Signification : SQL Server suggère qu'un index pourrait améliorer les performances
- Action : Analyser la suggestion et créer l'index si pertinent

**Conversions implicites (Implicit Conversion)**
- Message : "Type conversion in expression may affect performance"
- Signification : SQL Server doit convertir des types de données (ex: VARCHAR → NVARCHAR)
- Action : Aligner les types de données dans la structure de la base ou la requête

**Débordement mémoire (Spill to TempDB)**
- Message : "Operator used tempdb to spill data during execution"
- Signification : Pas assez de mémoire, SQL Server a dû écrire sur le disque (très lent)
- Action : Optimiser la requête pour réduire l'utilisation mémoire, ou ajouter des index

**Parallélisme excessif**
- Message : Peut indiquer trop de threads ou un coût de coordination élevé
- Signification : Le parallélisme peut parfois être contre-productif sur de petites requêtes
- Action : Analyser si le parallélisme est justifié

#### Importance

Les avertissements sont des **signaux explicites** que quelque chose ne va pas. Ne les ignorez jamais !

### 5. Opérateurs coûteux spécifiques

Certains opérateurs sont naturellement plus coûteux et méritent une attention particulière :

#### Table Scan / Clustered Index Scan sur grande table
- **Signal** : Coût > 30% sur une table > 100 000 lignes
- **Problème** : Lecture complète de la table
- **Solution** : Créer un index approprié

#### Sort (Tri)
- **Signal** : Coût > 20%
- **Problème** : Tri en mémoire coûteux, ou pire, sur disque
- **Solution** : Index ordonné, ou revoir la nécessité du ORDER BY

#### Key Lookup répété
- **Signal** : Des milliers ou millions de Key Lookups
- **Problème** : Aller-retours répétés entre index et table
- **Solution** : Index avec clause INCLUDE

#### Nested Loops avec Table Scan interne
- **Signal** : Nested Loops avec coût > 50%, table interne en Scan
- **Problème** : Chaque itération fait un parcours complet
- **Solution** : Index sur la clé de jointure de la table interne

#### Hash Match avec avertissement de mémoire
- **Signal** : Triangle jaune "Spill to TempDB"
- **Problème** : Table de hachage trop grande pour la mémoire
- **Solution** : Filtrer davantage en amont, ou créer des index pour permettre un Merge Join

## Méthodologie d'identification : L'approche en 5 étapes

### Étape 1 : Vue d'ensemble

**Regardez le plan dans son ensemble**
- Identifiez visuellement les zones "chaudes" (opérateurs en orange/rouge dans SSMS moderne)
- Repérez les flèches épaisses
- Notez les triangles jaunes

**Posez-vous la question :**
"Où mon œil est-il attiré naturellement ?"

Si un opérateur vous saute aux yeux visuellement, c'est probablement un goulot d'étranglement.

### Étape 2 : Identifier le coût le plus élevé

**Trouvez l'opérateur avec le pourcentage le plus élevé**
- Dans SSMS, survolez chaque opérateur pour voir son coût
- Commencez par le plus coûteux

**Posez-vous la question :**
"Est-ce que cet opérateur représente plus de 30% du coût total ?"

Si oui, c'est votre priorité n°1.

### Étape 3 : Comprendre pourquoi il est coûteux

**Analysez l'opérateur problématique**

Pour un **Table Scan** :
- Quelle table est scannée ?
- Quelle est sa taille ?
- Y a-t-il un WHERE ou JOIN sur cette table ?
- Existe-t-il un index sur les colonnes utilisées ?

Pour une **Jointure** :
- Quel type de jointure est utilisé (Nested Loops, Hash, Merge) ?
- Les tables ont-elles des index appropriés ?
- Le nombre de lignes est-il cohérent avec les estimations ?

Pour un **Sort** :
- Pourquoi ce tri est-il nécessaire (ORDER BY, DISTINCT, GROUP BY) ?
- Le tri pourrait-il être évité avec un index ordonné ?
- Le tri se fait-il en mémoire ou sur disque ?

**Posez-vous la question :**
"Qu'est-ce qui rend cet opérateur si lent ?"

### Étape 4 : Vérifier les estimations

**Comparez les estimations avec la réalité (plan réel)**
- Cliquez sur l'opérateur problématique
- Regardez les propriétés (F4 dans SSMS)
- Comparez "Estimated Number of Rows" et "Actual Number of Rows"

**Posez-vous la question :**
"Est-ce que SQL Server savait ce qu'il faisait ?"

Si l'écart est important (×10 ou plus), les statistiques sont probablement obsolètes.

### Étape 5 : Remonter la chaîne

**Suivez le flux de données en remontant vers la droite**
- Identifiez d'où viennent les données qui entrent dans l'opérateur problématique
- Y a-t-il un filtrage inefficace en amont ?
- Y a-t-il trop de données transmises inutilement ?

**Posez-vous la question :**
"Le problème est-il vraiment ici, ou est-il causé par une étape précédente ?"

Parfois, le goulot d'étranglement apparent est en fait la conséquence d'un problème en amont.

## Exemples pratiques d'identification

### Exemple 1 : Le Table Scan évident

**Requête :**
```sql
SELECT *
FROM Commandes
WHERE ClientID = 12345;
```

**Plan d'exécution :**
```
[SELECT: 1%] ← [Table Scan: Commandes, 99%]
                Estimé: 1 000 000 lignes
                Réel: 1 000 000 lignes
```

**Identification :**
1. ✅ **Coût élevé** : 99% du coût total
2. ✅ **Opérateur problématique** : Table Scan sur 1 million de lignes
3. ✅ **Cause** : Pas d'index sur ClientID
4. ✅ **Estimation correcte** : Les statistiques sont bonnes

**Diagnostic :** Goulot d'étranglement clair — Table Scan sur grande table.

**Solution :**
```sql
CREATE INDEX IX_Commandes_ClientID ON Commandes(ClientID);
```

**Résultat attendu :** Le Table Scan (99%) sera remplacé par un Index Seek (<5%). Gain : ~20× plus rapide ou plus.

---

### Exemple 2 : Le Nested Loops inefficace

**Requête :**
```sql
SELECT c.Nom, co.NumeroCommande
FROM Clients c
INNER JOIN Commandes co ON c.ClientID = co.ClientID
WHERE c.Ville = 'Paris';
```

**Plan d'exécution :**
```
[SELECT: 2%] ← [Nested Loops: 78%] ← [Table Scan: Commandes, 15%]
                       ↑
                [Index Seek: Clients, 5%]
                Estimé: 1000 clients à Paris
                Réel: 1000 clients
```

**Identification :**
1. ✅ **Coût élevé** : Nested Loops à 78%
2. ✅ **Flèche épaisse** : 1000 itérations
3. ✅ **Table Scan interne** : Pour chaque client, parcours complet de Commandes
4. ✅ **Estimation correcte** : 1000 clients comme prévu

**Diagnostic :** Pour chaque client de Paris (1000), SQL Server fait un Table Scan de toute la table Commandes. C'est 1000 parcours complets !

**Solution :**
```sql
CREATE INDEX IX_Commandes_ClientID ON Commandes(ClientID);
```

**Résultat attendu :** Le Nested Loops restera, mais le Table Scan interne sera remplacé par des Index Seek. Les 1000 parcours complets deviennent 1000 recherches ciblées. Gain : ~100× plus rapide.

---

### Exemple 3 : L'estimation catastrophique

**Requête :**
```sql
SELECT *
FROM Produits
WHERE DateCreation > '2024-01-01'
  AND Categorie = 'Électronique';
```

**Plan d'exécution :**
```
[SELECT: 1%] ← [Nested Loops: 85%] ← [Table Scan: Stock, 10%]
                       ↑
                [Index Seek: Produits, 4%]
                Estimé: 10 lignes          ← PROBLÈME !
                Réel: 500 000 lignes       ← PROBLÈME !
```

**Identification :**
1. ✅ **Coût élevé** : Nested Loops à 85%
2. ✅ **ÉCART ÉNORME** : Estimé 10, Réel 500 000 (ratio de 50 000 !)
3. ⚠️ **Triangle jaune** : Possible avertissement sur les statistiques

**Diagnostic :** SQL Server pensait traiter 10 lignes et a choisi Nested Loops. Mais il traite en réalité 500 000 lignes. Le plan est complètement inadapté. Hash Match ou Merge Join aurait été meilleur.

**Solution :**
```sql
-- Mettre à jour les statistiques
UPDATE STATISTICS Produits;

-- Puis ré-exécuter la requête
```

**Résultat attendu :** Avec de bonnes statistiques, SQL Server choisira probablement Hash Match ou Merge Join, beaucoup plus adaptés. Gain : ~50× à 100× plus rapide.

---

### Exemple 4 : Le Sort coûteux

**Requête :**
```sql
SELECT ClientID, Nom, Ville
FROM Clients
WHERE Ville = 'Paris'
ORDER BY Nom;
```

**Plan d'exécution :**
```
[SELECT: 1%] ← [Sort: 45%] ← [Table Scan: 54%]
                Estimé: 50 000 lignes
                Réel: 50 000 lignes
```

**Identification :**
1. ✅ **Deux goulots** : Table Scan (54%) + Sort (45%)
2. ✅ **Estimations correctes** : 50 000 lignes
3. ⚠️ **Sort coûteux** : Trier 50 000 lignes est coûteux

**Diagnostic :**
- Table Scan car pas d'index sur Ville
- Sort nécessaire pour ORDER BY Nom

**Solution optimale :**
```sql
-- Index composite : Ville + Nom
CREATE INDEX IX_Clients_Ville_Nom ON Clients(Ville, Nom);
```

**Pourquoi cette solution ?**
- L'index sur `Ville` permet un Index Seek au lieu de Table Scan
- L'index inclut `Nom` dans le bon ordre, éliminant le Sort

**Résultat attendu :** Le Table Scan (54%) devient Index Seek (<5%), et le Sort (45%) disparaît complètement. Gain : ~20× plus rapide.

---

### Exemple 5 : Le Key Lookup en cascade

**Requête :**
```sql
SELECT Nom, Prenom, Email, Telephone, Adresse
FROM Clients
WHERE Ville = 'Paris';
```

**Plan d'exécution :**
```
[SELECT: 1%] ← [Nested Loops: 65%] ← [Key Lookup: Clients, 60%]
                       ↑
                [Index Seek: IX_Clients_Ville, 5%]
                Estimé: 10 000 lignes
                Réel: 10 000 lignes
```

**Identification :**
1. ✅ **Coût élevé** : Key Lookup à 60% dans Nested Loops à 65%
2. ✅ **Répété** : 10 000 Key Lookups (un pour chaque ligne trouvée)
3. ✅ **Pattern classique** : Index Seek → Key Lookup répété

**Diagnostic :** L'index IX_Clients_Ville contient seulement `Ville`, mais la requête demande aussi `Nom, Prenom, Email, Telephone, Adresse`. SQL Server doit donc retourner à la table 10 000 fois pour récupérer ces colonnes.

**Solution :**
```sql
-- Recréer l'index avec les colonnes manquantes
DROP INDEX IX_Clients_Ville ON Clients;
CREATE INDEX IX_Clients_Ville
ON Clients(Ville)
INCLUDE (Nom, Prenom, Email, Telephone, Adresse);
```

**Résultat attendu :** Le Key Lookup (60%) disparaît. L'index contient maintenant toutes les colonnes nécessaires. Gain : ~5× à 10× plus rapide.

## Priorisation des optimisations

### Comment décider par où commencer ?

Quand vous identifiez plusieurs goulots d'étranglement, utilisez cette matrice de priorisation :

| Critère | Priorité | Points |
|---------|----------|--------|
| Coût > 50% | Haute | +10 |
| Coût 30-50% | Moyenne | +5 |
| Coût < 30% | Basse | +2 |
| Écart estimation/réalité > ×10 | Haute | +8 |
| Table Scan sur grande table | Haute | +8 |
| Triangle jaune (warning) | Moyenne | +5 |
| Sort coûteux | Moyenne | +4 |
| Key Lookup massif | Moyenne | +4 |

**Règle :** Commencez par le goulot qui a le **plus de points**.

### Exemple de priorisation

**Problèmes identifiés :**
1. Table Scan (Coût 65%, table de 2M lignes) → 10 + 8 = **18 points**
2. Sort (Coût 25%) → 2 + 4 = **6 points**
3. Key Lookup (Coût 8%, mais 50 000 répétitions) → 2 + 4 = **6 points**
4. Écart estimation (Coût 2%, mais ratio ×100) → 2 + 8 = **10 points**

**Ordre de priorité :**
1. **Table Scan (18 points)** — À traiter en premier
2. **Écart estimation (10 points)** — À traiter ensuite
3. **Sort et Key Lookup (6 points chacun)** — À traiter après

### Loi de Pareto (80/20)

Dans la plupart des cas, **20% des goulots** causent **80% des problèmes**.

Concentrez-vous sur le ou les deux goulots les plus importants. L'amélioration sera souvent spectaculaire.

## Outils d'aide à l'identification

### 1. Colorisation automatique dans SSMS

Les versions récentes de SSMS colorent automatiquement les opérateurs :
- **Rouge/Orange** → Coût très élevé
- **Jaune** → Coût moyen
- **Blanc/Gris** → Coût faible

Cherchez le rouge en premier !

### 2. La vue XML du plan

Pour une analyse détaillée, affichez le plan en XML (clic droit sur le plan → "Show Execution Plan XML").

Recherchez :
- `MissingIndexes` → SQL Server suggère des index manquants
- `Warnings` → Problèmes détectés
- `EstimateRows` vs `ActualRows` → Écarts d'estimation

### 3. Propriétés détaillées (F4)

Sélectionnez un opérateur et appuyez sur F4 pour voir toutes ses propriétés dans un panneau dédié.

Informations utiles :
- **Actual/Estimated rows** : Comparaison directe
- **Actual/Estimated CPU cost** : Coût processeur
- **Actual/Estimated I/O cost** : Coût disque
- **Warnings** : Avertissements textuels

### 4. Query Store (Magasin de requêtes)

Si votre base utilise Query Store, vous pouvez :
- Comparer les plans d'exécution dans le temps
- Identifier les régressions de performance
- Voir l'évolution des coûts

## Les pièges à éviter

### Piège 1 : Optimiser les petits pourcentages

**Erreur :** Passer du temps à optimiser un opérateur à 3% de coût.

**Réalité :** Même si vous le réduisez de 100%, vous gagnez seulement 3% de performance globale.

**Solution :** Concentrez-vous sur les opérateurs > 20-30% en priorité.

### Piège 2 : Ignorer le contexte d'exécution

**Erreur :** Un Table Scan à 80% semble terrible, mais la requête s'exécute en 5ms.

**Réalité :** Si la performance est acceptable, ce n'est peut-être pas un problème.

**Solution :** Priorisez l'optimisation des requêtes qui causent des **problèmes réels** (lenteur, timeouts, plaintes utilisateurs).

### Piège 3 : Sur-indexer

**Erreur :** Créer 10 index pour optimiser une requête ponctuelle.

**Réalité :** Trop d'index ralentissent les INSERT, UPDATE, DELETE et augmentent la taille de la base.

**Solution :** Créez des index **stratégiques** qui bénéficient à plusieurs requêtes fréquentes.

### Piège 4 : Négliger les statistiques

**Erreur :** Créer plein d'index sans mettre à jour les statistiques.

**Réalité :** Avec de mauvaises statistiques, SQL Server peut ne pas utiliser vos nouveaux index.

**Solution :** Après avoir créé des index, mettez à jour les statistiques :
```sql
UPDATE STATISTICS NomDeTable;
```

### Piège 5 : Optimiser le plan estimé

**Erreur :** Analyser uniquement le plan estimé.

**Réalité :** Le plan estimé peut être très différent du plan réel.

**Solution :** Activez **toujours** le plan réel (Ctrl+M) pour vos analyses de performance.

## Checklist d'identification des goulots

Utilisez cette checklist pour chaque requête lente :

### ☐ Vue d'ensemble
- [ ] J'ai affiché le plan d'exécution réel (pas seulement estimé)
- [ ] J'ai identifié visuellement les zones "chaudes"
- [ ] J'ai repéré les avertissements (triangles jaunes)

### ☐ Analyse des coûts
- [ ] J'ai identifié l'opérateur avec le coût le plus élevé
- [ ] J'ai vérifié si ce coût dépasse 30% du total
- [ ] J'ai listé les 2-3 opérateurs les plus coûteux

### ☐ Analyse des estimations
- [ ] J'ai comparé Estimated vs Actual pour les opérateurs coûteux
- [ ] J'ai identifié les écarts importants (ratio > 10)
- [ ] J'ai vérifié quand les statistiques ont été mises à jour pour la dernière fois

### ☐ Analyse des opérateurs
- [ ] Y a-t-il des Table Scan sur grandes tables ?
- [ ] Y a-t-il des Key Lookup répétés massivement ?
- [ ] Y a-t-il des Sort coûteux ?
- [ ] Y a-t-il des jointures inefficaces (Nested Loops sans index) ?

### ☐ Analyse du flux
- [ ] J'ai vérifié l'épaisseur des flèches
- [ ] J'ai identifié où le volume de données est réduit (filtrage efficace ?)
- [ ] J'ai remonté la chaîne pour comprendre l'origine des données

### ☐ Priorisation
- [ ] J'ai classé les problèmes par ordre de priorité
- [ ] J'ai défini une solution pour le goulot #1
- [ ] J'ai évalué l'impact potentiel de cette solution

## Conclusion

Identifier les goulots d'étranglement dans un plan d'exécution est une compétence essentielle pour tout développeur travaillant avec SQL Server. En suivant une méthodologie structurée, vous pouvez rapidement localiser les problèmes et prioriser vos efforts d'optimisation.

**Récapitulatif des signaux d'alerte :**
1. 🔥 **Coût > 50%** — Goulot majeur
2. 🔥 **Écart estimation ×10+** — Statistiques obsolètes
3. ⚠️ **Flèches très épaisses** — Volume de données excessif
4. ⚠️ **Triangles jaunes** — Avertissements explicites
5. ⚠️ **Opérateurs coûteux classiques** — Table Scan, Sort, Key Lookup massif

**La méthodologie en 5 étapes :**
1. Vue d'ensemble → Repérer visuellement
2. Identifier le coût le plus élevé → Quantifier
3. Comprendre pourquoi → Analyser
4. Vérifier les estimations → Valider
5. Remonter la chaîne → Contextualiser

**Le principe 80/20 :**
Concentrez-vous sur les 1 ou 2 goulots majeurs. Résoudre le problème principal apportera souvent des gains de performance spectaculaires (×10 ou plus).

Avec cette approche méthodique, vous êtes maintenant équipé pour diagnostiquer efficacement les problèmes de performance et apporter des améliorations significatives à vos requêtes !

---

**Points à retenir :**
- Un goulot d'étranglement représente généralement > 50% du coût total
- Les écarts importants entre estimations et réalité indiquent des statistiques obsolètes
- Utilisez toujours le plan réel, pas seulement le plan estimé
- Priorisez les optimisations selon leur impact potentiel
- La loi de Pareto s'applique : 20% des problèmes causent 80% de la lenteur
- N'oubliez pas de mettre à jour les statistiques après avoir créé des index
