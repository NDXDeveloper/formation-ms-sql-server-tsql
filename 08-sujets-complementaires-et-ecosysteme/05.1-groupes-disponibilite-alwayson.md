# 8.5.1 Théorie : Groupes de disponibilité AlwaysOn (Concepts)

## Introduction

Les Groupes de disponibilité AlwaysOn (Always On Availability Groups ou AG) sont une fonctionnalité de haute disponibilité et de reprise après sinistre introduite dans SQL Server 2012. Pour un débutant, il est important de comprendre d'abord **pourquoi** cette technologie existe avant de plonger dans les détails techniques.

## Pourquoi la haute disponibilité ?

Imaginez une entreprise dont le site web de commerce en ligne repose entièrement sur une base de données SQL Server. Si cette base de données devient indisponible (panne matérielle, corruption de disque, problème réseau), l'entreprise perd immédiatement :
- Des ventes
- La confiance des clients
- Potentiellement des milliers d'euros par minute

La haute disponibilité vise à **minimiser ou éliminer les temps d'arrêt** (downtime) en garantissant que les données restent accessibles même en cas de problème.

## Le concept de base : La redondance

Le principe fondamental des Groupes de disponibilité AlwaysOn est simple : **ne jamais avoir une seule copie de vos données**.

### Analogie simple

Pensez à une bibliothèque importante :
- **Sans redondance** : Un seul exemplaire de chaque livre. Si un incendie détruit la bibliothèque, tout est perdu.
- **Avec redondance** : Des copies identiques du catalogue dans plusieurs bâtiments différents. Si un bâtiment brûle, les autres continuent à servir les lecteurs.

C'est exactement ce que fait AlwaysOn : il maintient **plusieurs copies synchronisées** de vos bases de données sur différents serveurs SQL Server.

## Architecture conceptuelle d'un Groupe de disponibilité

### Les composants clés

#### 1. Le réplica primaire (Primary Replica)
- C'est le serveur SQL Server **actif** qui reçoit toutes les modifications (INSERT, UPDATE, DELETE)
- Les applications se connectent principalement à ce réplica
- Il est responsable d'envoyer les changements aux autres réplicas

#### 2. Les réplicas secondaires (Secondary Replicas)
- Ce sont des **copies** du réplica primaire
- Ils reçoivent continuellement les modifications depuis le primaire
- Ils peuvent servir à :
  - Prendre le relais si le primaire tombe en panne (basculement automatique)
  - Servir des requêtes en lecture seule (décharger le serveur principal)
  - Créer des sauvegardes sans impacter le serveur principal

#### 3. Le cluster Windows (WSFC - Windows Server Failover Cluster)
- C'est l'infrastructure sous-jacente qui permet aux serveurs de "se parler" et de détecter les pannes
- Il orchestre le basculement automatique en cas de problème
- À partir de SQL Server 2017 (Linux), AlwaysOn peut aussi fonctionner sans WSFC

### Représentation visuelle

```
┌─────────────────────────────────────────────────────────────┐
│                  Groupe de disponibilité                    │
│                                                             │
│  ┌────────────────┐         ┌────────────────┐              │
│  │ Serveur A      │         │ Serveur B      │              │
│  │ (Primaire)     │ ══════> │ (Secondaire)   │              │
│  │                │  Sync   │                │              │
│  │ DB: Ventes     │         │ DB: Ventes     │              │
│  └────────────────┘         └────────────────┘              │
│         │                            │                      │
│         │                            │                      │
│    Applications                Lecture seule                │
│    (Écriture/Lecture)          (Optionnel)                  │
└─────────────────────────────────────────────────────────────┘
```

## Les modes de synchronisation

Un aspect crucial des Groupes de disponibilité est **comment** les données sont copiées du primaire vers les secondaires. Il existe deux modes principaux :

### 1. Mode synchrone (Synchronous-commit)

**Comment ça fonctionne :**
1. Une transaction est validée (COMMIT) sur le primaire
2. Le primaire attend la **confirmation** du secondaire que les données ont été écrites sur son disque
3. Seulement après cette confirmation, la transaction est considérée comme terminée

**Avantages :**
- **Aucune perte de données** (RPO = 0) : Le secondaire a toujours les mêmes données que le primaire
- Idéal pour les données critiques

**Inconvénients :**
- **Léger impact sur les performances** : Chaque transaction doit attendre la confirmation du réseau
- Nécessite une connexion réseau rapide et fiable entre les serveurs

**Quand l'utiliser :**
- Quand vos données sont critiques et qu'aucune perte n'est acceptable
- Dans le même datacenter (faible latence réseau)

### 2. Mode asynchrone (Asynchronous-commit)

**Comment ça fonctionne :**
1. Une transaction est validée (COMMIT) sur le primaire
2. Le primaire envoie les modifications au secondaire mais **n'attend pas la confirmation**
3. La transaction est immédiatement considérée comme terminée

**Avantages :**
- **Performances maximales** : Pas d'attente réseau
- Fonctionne bien même avec une connexion lente ou distante

**Inconvénients :**
- **Risque de perte de données** : Si le primaire tombe en panne avant que le secondaire reçoive les dernières modifications, ces données sont perdues
- Le secondaire peut être légèrement "en retard" par rapport au primaire

**Quand l'utiliser :**
- Pour des réplicas géographiquement distants (autre ville, autre pays)
- Quand les performances sont prioritaires et qu'une petite perte de données est acceptable

### Tableau comparatif

| Critère | Synchrone | Asynchrone |
|---------|-----------|------------|
| Perte de données | Aucune (RPO = 0) | Possible (RPO > 0) |
| Performance | Impact léger | Impact minimal |
| Latence réseau requise | Faible (<5ms) | Tolère la latence |
| Basculement automatique | Oui | Non (manuel seulement) |
| Usage typique | Même datacenter | Datacenters distants |

## Le basculement (Failover)

Le basculement est le processus de **promotion d'un réplica secondaire en réplica primaire** lorsque le primaire actuel devient indisponible.

### Types de basculement

#### 1. Basculement automatique (Automatic Failover)
- **Conditions** : Mode synchrone + configuration pour le basculement automatique
- **Déclenchement** : Le cluster détecte que le primaire ne répond plus
- **Durée** : Généralement 30 secondes à 2 minutes
- **Intervention humaine** : Aucune

**Scénario typique :**
```
1. Le serveur primaire plante (panne matérielle)
2. Le cluster WSFC détecte la panne en 10-20 secondes
3. Le réplica secondaire synchrone devient automatiquement le nouveau primaire
4. Les applications se reconnectent au nouveau primaire
5. Temps d'indisponibilité total : ~1 minute
```

#### 2. Basculement manuel planifié (Manual Planned Failover)
- **Conditions** : Mode synchrone
- **Déclenchement** : Action manuelle d'un administrateur
- **Perte de données** : Aucune
- **Usage** : Maintenance planifiée, migration de serveur

**Exemple d'utilisation :**
Vous devez installer des mises à jour Windows sur le serveur primaire. Vous basculez manuellement vers le secondaire, mettez à jour le serveur, puis rebasculez.

#### 3. Basculement manuel forcé (Manual Forced Failover)
- **Conditions** : Mode asynchrone ou quand le primaire est vraiment perdu
- **Déclenchement** : Action manuelle avec option FORCE
- **Perte de données** : Possible
- **Usage** : Urgence, catastrophe

## Les rôles des réplicas secondaires

Au-delà de la simple redondance, les réplicas secondaires peuvent avoir des usages actifs :

### 1. Lecture seule (Readable Secondary)

Vous pouvez configurer un secondaire pour accepter des connexions en **lecture seule**. Cela permet de :
- Décharger le primaire des requêtes de reporting
- Exécuter des analyses lourdes sans impacter la production
- Servir des tableaux de bord en temps réel

**Exemple d'architecture :**
```
Primaire (Serveur A)
  ↓ Écritures (INSERT/UPDATE/DELETE)
  ↓
  └─> Application web

Secondaire (Serveur B) en lecture seule
  ↓ Lectures (SELECT)
  ↓
  └─> Outils de reporting / Business Intelligence
```

### 2. Sauvegardes sur secondaire

Vous pouvez configurer vos sauvegardes pour s'exécuter sur un réplica secondaire plutôt que sur le primaire, ce qui :
- Libère les ressources du serveur principal
- Réduit l'impact des sauvegardes sur les performances de production

## Concepts avancés (aperçu pour débutants)

### Listener (Écouteur)

Un **listener** est un nom DNS virtuel qui pointe toujours vers le réplica primaire actuel. Les applications se connectent au listener, pas directement aux serveurs.

**Avantage :**
Lorsqu'un basculement se produit, le listener pointe automatiquement vers le nouveau primaire. Les applications n'ont pas besoin de changer leur chaîne de connexion.

**Exemple :**
```
Chaîne de connexion : Server=AG-Listener;Database=Ventes;...

Avant basculement : AG-Listener → ServeurA (primaire)
Après basculement :  AG-Listener → ServeurB (nouveau primaire)
```

### Quorum

Le quorum est le mécanisme qui permet au cluster de décider **qui a le droit de prendre des décisions** en cas de problème réseau (split-brain). C'est un concept complexe, mais retenez simplement que :
- Le quorum nécessite une majorité de "votes" dans le cluster
- Il empêche deux serveurs de se croire primaires en même temps
- Un témoin (witness) peut être ajouté pour départager en cas d'égalité

## Limitations et considérations

### Ce qu'AlwaysOn ne fait PAS

1. **Ne remplace pas les sauvegardes** : Même avec AlwaysOn, vous devez toujours faire des sauvegardes régulières (protection contre les suppressions accidentelles, corruptions logiques, etc.)

2. **Ne protège pas contre les erreurs utilisateur** : Si quelqu'un exécute `DELETE FROM Clients WHERE 1=1` sur le primaire, cette suppression est immédiatement répliquée sur tous les secondaires.

3. **N'est pas magique** : La configuration et la surveillance nécessitent de l'expertise

### Prérequis techniques

- SQL Server Enterprise Edition (ou Standard à partir de SQL Server 2016, avec limitations)
- Windows Server avec le rôle Failover Cluster (ou Linux avec Pacemaker)
- Une connexion réseau fiable entre les serveurs
- Serveurs avec des configurations matérielles similaires

### Nombre de réplicas

Selon l'édition de SQL Server :
- **Enterprise Edition** : Jusqu'à 9 réplicas (1 primaire + 8 secondaires)
- **Standard Edition** : 2 réplicas **seulement** (1 primaire + 1 secondaire), via les *Basic Availability Groups* (depuis SQL Server 2016)

> ⚠️ Les *Basic Availability Groups* de l'édition Standard sont fortement limités : **une seule base de données** par groupe, **aucun accès en lecture** sur le secondaire et **aucune sauvegarde** sur le secondaire. Les usages « lecture seule » et « sauvegarde sur secondaire » décrits plus haut nécessitent donc l'édition Enterprise.

## Cas d'usage typiques

### 1. Protection contre les pannes (High Availability)

**Scénario :** Banque en ligne

Configuration :
- 1 primaire (datacenter principal)
- 1 secondaire synchrone (même datacenter) → Basculement automatique
- Temps d'indisponibilité cible : <1 minute

### 2. Reprise après sinistre (Disaster Recovery)

**Scénario :** E-commerce international

Configuration :
- 1 primaire (Paris)
- 1 secondaire synchrone (Paris, autre bâtiment) → HA locale
- 1 secondaire asynchrone (Londres) → Protection contre sinistre majeur

### 3. Déchargement de lecture (Read-Scale Out)

**Scénario :** Application SaaS avec beaucoup de reporting

Configuration :
- 1 primaire (applications OLTP)
- 2 secondaires lisibles (rapports et dashboards)

## Terminologie récapitulative

| Terme | Définition |
|-------|------------|
| **Réplica primaire** | Serveur actif qui accepte toutes les écritures |
| **Réplica secondaire** | Copie du primaire, peut servir en lecture seule |
| **Basculement (Failover)** | Promotion d'un secondaire en primaire |
| **Synchrone** | Mode où le primaire attend la confirmation du secondaire |
| **Asynchrone** | Mode où le primaire n'attend pas le secondaire |
| **Listener** | Nom DNS virtuel pointant vers le primaire actuel |
| **RPO (Recovery Point Objective)** | Perte de données maximale acceptable |
| **RTO (Recovery Time Objective)** | Temps d'indisponibilité maximal acceptable |

## Conclusion

Les Groupes de disponibilité AlwaysOn sont une solution puissante pour garantir que vos bases de données restent disponibles même en cas de problème. Pour un développeur ou un débutant en administration SQL Server, les concepts clés à retenir sont :

1. **Redondance** : Plusieurs copies de vos données sur différents serveurs
2. **Modes de synchronisation** : Synchrone (aucune perte) vs Asynchrone (performance)
3. **Basculement** : Automatique ou manuel, permet de continuer à fonctionner après une panne
4. **Utilisations multiples** : Haute disponibilité, reprise après sinistre, déchargement de lecture

Même si vous ne configurez jamais vous-même un Groupe de disponibilité, comprendre ces concepts vous aidera à :
- Concevoir des applications résilientes
- Comprendre les chaînes de connexion avec listeners
- Collaborer efficacement avec les administrateurs de bases de données
- Anticiper les comportements lors d'un basculement
