# 7.7.3 Le Concept de DBCC CHECKDB (Intégrité de la Base)

## Introduction

Imaginez que vous avez un coffre-fort contenant tous les documents importants de votre entreprise. Comment savez-vous que ces documents sont toujours en bon état ? Qu'ils n'ont pas été endommagés par l'humidité, déchirés, ou corrompus ? Vous devez effectuer des **vérifications régulières** pour vous assurer de leur intégrité.

C'est exactement le rôle de **DBCC CHECKDB** dans SQL Server : c'est le "médecin" de votre base de données qui effectue un bilan de santé complet pour vérifier que tout est en ordre.

---

## Qu'est-ce que l'Intégrité de la Base de Données ?

### Définition

L'**intégrité de la base de données** signifie que :
- Toutes les données sont **physiquement cohérentes** (pas de corruption sur le disque)
- Les **structures internes** (pages, index, tables) sont valides
- Les **relations logiques** entre les données sont respectées
- Les **métadonnées** (informations système) sont correctes

### Analogie : L'Intégrité d'un Livre

Prenons l'exemple d'un livre :

**Intégrité physique** :
- Les pages ne sont pas déchirées
- L'encre n'est pas effacée
- Les pages sont bien reliées

**Intégrité logique** :
- Les pages sont numérotées correctement
- La table des matières correspond au contenu
- Les références croisées pointent vers les bonnes pages
- Les chapitres se suivent dans le bon ordre

Si une page est déchirée ou si la page 50 est en fait la page 150, le livre a perdu son intégrité. De même, une base de données peut avoir des problèmes d'intégrité.

---

## Qu'est-ce que DBCC CHECKDB ?

### Définition

**DBCC CHECKDB** (Database Console Command - Check Database) est une commande système qui effectue une **vérification complète de l'intégrité** d'une base de données SQL Server.

### Que signifie DBCC ?

**DBCC** = Database Console Commands

C'est une famille de commandes de diagnostic et de maintenance pour SQL Server. `CHECKDB` est la plus importante et la plus utilisée.

### Que vérifie DBCC CHECKDB ?

DBCC CHECKDB effectue plusieurs vérifications :

1. **Intégrité structurelle des pages** :
   - Vérification des checksums (sommes de contrôle)
   - Détection de pages corrompues
   - Validation de l'en-tête de chaque page

2. **Cohérence des index** :
   - Vérification que les index pointent vers les bonnes données
   - Validation de la structure B-Tree
   - Détection de liens cassés

3. **Allocation des pages** :
   - Vérification que chaque page est correctement comptabilisée
   - Détection de pages "orphelines" (perdues)
   - Validation des structures d'allocation (GAM, SGAM, PFS, IAM)

4. **Intégrité des relations** :
   - Validation des clés étrangères (Foreign Keys)
   - Vérification des contraintes CHECK
   - Cohérence entre les tables système

5. **Catalogues système** :
   - Vérification des métadonnées SQL Server
   - Validation des définitions d'objets

---

## Pourquoi est-ce Important ?

### Les Causes de Corruption

Une base de données peut se corrompre pour plusieurs raisons :

**Problèmes matériels** :
- Défaillance du disque dur (secteurs défectueux)
- Problèmes de mémoire (RAM défectueuse)
- Contrôleur de stockage défaillant
- Panne de courant soudaine

**Problèmes logiciels** :
- Bugs dans SQL Server (très rare mais possible)
- Pilotes de stockage défectueux
- Arrêt brutal du serveur (crash)
- Problèmes avec les systèmes de virtualisation ou SAN

**Facteurs humains** :
- Suppression accidentelle de fichiers de base de données
- Manipulation incorrecte des fichiers
- Restauration incorrecte

### Les Conséquences de la Corruption

Si vous n'identifiez pas rapidement une corruption :

❌ **Perte de données** :
- Impossibilité de lire certaines tables
- Lignes manquantes ou illisibles
- Données incohérentes

❌ **Erreurs applicatives** :
- Crashes des applications
- Messages d'erreur mystérieux
- Comportements imprévisibles

❌ **Propagation de la corruption** :
- Une petite corruption peut s'étendre
- Les sauvegardes peuvent contenir la corruption

❌ **Restauration impossible** :
- Si toutes les sauvegardes sont corrompues
- Perte totale de données dans le pire des cas

### L'Importance de la Prévention

> **Principe fondamental** : Il est infiniment plus facile de **prévenir** la corruption que de la **réparer**.

C'est pourquoi DBCC CHECKDB doit être exécuté régulièrement, même si tout semble fonctionner correctement.

---

## Syntaxe et Utilisation de Base

### Syntaxe Simple

```sql
-- Vérification complète de la base de données actuelle
DBCC CHECKDB;

-- Vérification d'une base de données spécifique
DBCC CHECKDB ('NomDeLaBase');

-- Avec l'option NO_INFOMSGS (moins de messages)
DBCC CHECKDB ('NomDeLaBase') WITH NO_INFOMSGS;
```

### Exemple Complet

```sql
-- Se connecter à la base de données master
USE master;
GO

-- Vérifier la base de données "MaBase"
DBCC CHECKDB ('MaBase') WITH NO_INFOMSGS;
GO
```

### Résultat d'une Exécution Réussie

Si tout va bien, vous verrez un message similaire à :

```
CHECKDB found 0 allocation errors and 0 consistency errors in database 'MaBase'.
DBCC execution completed. If DBCC printed error messages, contact your system administrator.
```

**Traduction** :
- 0 erreurs d'allocation : Toutes les pages sont correctement comptabilisées
- 0 erreurs de cohérence : Toutes les structures sont valides
- ✅ Votre base de données est en bonne santé !

---

## Les Options de DBCC CHECKDB

DBCC CHECKDB propose plusieurs options pour personnaliser la vérification :

### WITH NO_INFOMSGS

Réduit la quantité de messages affichés (recommandé pour les scripts automatisés).

```sql
DBCC CHECKDB ('MaBase') WITH NO_INFOMSGS;
```

### WITH ALL_ERRORMSGS

Affiche **toutes** les erreurs trouvées (par défaut, limité à 200 erreurs par objet).

```sql
DBCC CHECKDB ('MaBase') WITH ALL_ERRORMSGS;
```

### WITH PHYSICAL_ONLY

Effectue uniquement des vérifications **physiques** (pas de vérifications logiques) :
- Plus rapide (environ 30-50% du temps)
- Détecte les corruptions physiques du disque
- N'examine pas la cohérence logique

```sql
DBCC CHECKDB ('MaBase') WITH PHYSICAL_ONLY;
```

**Quand l'utiliser** :
- Vérifications quotidiennes rapides
- Complément à une vérification complète hebdomadaire

### WITH EXTENDED_LOGICAL_CHECKS

Effectue des vérifications **logiques étendues** sur les colonnes calculées et les index filtrés :
- Plus lent (peut ajouter beaucoup de temps)
- Plus approfondi

```sql
DBCC CHECKDB ('MaBase') WITH EXTENDED_LOGICAL_CHECKS;
```

**Quand l'utiliser** :
- Si vous soupçonnez des problèmes subtils
- Vérifications mensuelles approfondies

### WITH ESTIMATEONLY

Estime le temps et l'espace tempdb nécessaires **sans exécuter la vérification**.

```sql
DBCC CHECKDB ('MaBase') WITH ESTIMATEONLY;
```

Résultat exemple :
```
Estimated TEMPDB space needed for CHECKALLOC (KB): 12800
Estimated TEMPDB space needed for CHECKTABLES (KB): 51200
```

## Comprendre les Résultats

### Messages de Succès

```
CHECKDB found 0 allocation errors and 0 consistency errors in database 'MaBase'.
DBCC execution completed. If DBCC printed error messages, contact your system administrator.
```

✅ **Signification** : Aucun problème détecté. Votre base de données est saine.

### Messages d'Erreur

Si DBCC CHECKDB détecte des problèmes, vous verrez des messages d'erreur détaillés :

```
Msg 8928, Level 16, State 1, Line 1
Object ID 123456789, index ID 1, partition ID 234567890, alloc unit ID 345678901 (type In-row data):
Page (1:234) could not be processed. See other errors for details.

Msg 8939, Level 16, State 98, Line 1
Table error: Object ID 123456789, index ID 1, partition ID 234567890, alloc unit ID 345678901 (type In-row data),
page (1:234). Test (IS_OFF (BUF_IOERR, pBUF->bstat)) failed. Values are 2057 and -4.
```

### Déchiffrer les Messages d'Erreur

Les messages peuvent sembler cryptiques, mais voici les éléments clés :

**Numéro de message (Msg XXXX)** :
- **8928** : Page illisible
- **8939** : Erreur d'I/O (lecture/écriture)
- **2533** : Erreur de checksum (corruption physique)
- **8976** : Table avec métadonnées manquantes

**Object ID** : Identifiant de la table concernée
```sql
-- Trouver le nom de la table
SELECT OBJECT_NAME(123456789);
```

**Page (1:234)** : Numéro de fichier (1) et numéro de page (234)

**Niveau de gravité** :
- **Level 16** : Erreur grave nécessitant une action
- **Level 24** : Erreur critique, corruption sévère

---

## Types de Corruption

### Corruption Physique (Hardware)

**Description** : Dommages au niveau du disque ou de la mémoire.

**Symptômes** :
- Erreurs de checksum (Msg 824)
- Pages illisibles (Msg 823)
- Erreurs d'I/O

**Causes** :
- Disque dur défaillant
- Mémoire (RAM) défectueuse
- Contrôleur RAID défaillant

**Exemple de message** :
```
Msg 824, Level 24, State 2, Line 1
SQL Server detected a logical consistency-based I/O error: incorrect checksum
```

### Corruption Logique (Software)

**Description** : Les données sont physiquement lisibles, mais les structures logiques sont incohérentes.

**Symptômes** :
- Index pointant vers de mauvaises pages
- Liens brisés dans les structures B-Tree
- Métadonnées incohérentes

**Causes** :
- Bugs logiciels (très rare)
- Arrêt brutal pendant une écriture
- Problèmes de transaction

**Exemple de message** :
```
Msg 8976, Level 16, State 1, Line 1
Table error: Object ID 123, index ID 1. Page (1:100) was not seen in the scan
```

## Que Faire en Cas d'Erreur ?

### Étape 1 : Ne Pas Paniquer (mais Agir Vite)

✅ **À faire immédiatement** :
1. Notez tous les messages d'erreur
2. Sauvegardez l'état actuel (même corrompu) si possible
3. Vérifiez vos sauvegardes récentes

❌ **À ne pas faire** :
- Ne continuez pas à utiliser la base normalement
- N'exécutez pas de CHECKDB avec des options de réparation sans comprendre
- Ne supprimez pas de fichiers

### Étape 2 : Évaluer la Gravité

**Corruption mineure** (quelques pages) :
- Généralement récupérable
- Perte de données limitée

**Corruption majeure** (nombreuses erreurs) :
- Peut nécessiter une restauration complète
- Perte de données potentiellement importante

### Étape 3 : Tentatives de Récupération

#### Option 1 : Restauration depuis une Sauvegarde (RECOMMANDÉ)

C'est **toujours** la meilleure option si vous avez une sauvegarde saine :

```sql
-- 1. Mettre la base en mode SINGLE_USER
ALTER DATABASE MaBase SET SINGLE_USER WITH ROLLBACK IMMEDIATE;

-- 2. Restaurer depuis la dernière sauvegarde saine
RESTORE DATABASE MaBase
FROM DISK = 'C:\Backups\MaBase_Saine.bak'
WITH REPLACE;

-- 3. Remettre en mode MULTI_USER
ALTER DATABASE MaBase SET MULTI_USER;
```

**Important** : Vérifiez que votre sauvegarde n'est pas corrompue !
```sql
RESTORE VERIFYONLY
FROM DISK = 'C:\Backups\MaBase.bak';
```

#### Option 2 : Réparation avec DBCC CHECKDB (Dernier Recours)

Si vous **n'avez pas de sauvegarde**, DBCC CHECKDB peut tenter de réparer :

```sql
-- Mode REPAIR_ALLOW_DATA_LOSS
-- ⚠️ ATTENTION : Peut entraîner une perte de données !
-- La base doit être en mode SINGLE_USER

-- 1. Passer en mode SINGLE_USER
ALTER DATABASE MaBase SET SINGLE_USER WITH ROLLBACK IMMEDIATE;

-- 2. Mettre en mode EMERGENCY (si nécessaire)
ALTER DATABASE MaBase SET EMERGENCY;

-- 3. Tenter la réparation
DBCC CHECKDB ('MaBase', REPAIR_ALLOW_DATA_LOSS);

-- 4. Remettre la base en ligne
ALTER DATABASE MaBase SET ONLINE;
ALTER DATABASE MaBase SET MULTI_USER;
```

**⚠️ AVERTISSEMENT CRUCIAL** :
- `REPAIR_ALLOW_DATA_LOSS` peut **supprimer des données** pour réparer
- Utilisez uniquement si vous n'avez **aucune autre option**
- Vous perdrez définitivement certaines données
- Faites une copie avant si possible

### Étape 4 : Identifier la Cause Racine

Après avoir résolu l'urgence, identifiez pourquoi la corruption s'est produite :

**Vérifications matérielles** :
- Vérifier les logs du système d'exploitation (Event Viewer sous Windows)
- Tester la RAM avec des outils comme MemTest86
- Vérifier l'état SMART du disque dur
- Vérifier les logs du RAID si applicable

**Vérifications logicielles** :
- Vérifier les logs SQL Server (SQL Server Error Log)
- Rechercher des arrêts inattendus
- Mettre à jour les pilotes de stockage

## Planification et Bonnes Pratiques

### Fréquence Recommandée

**Bases critiques (Production)** :
- **Vérification complète** : Hebdomadaire (ou mensuelle pour très grandes bases)
- **Vérification physique** : Quotidienne (avec `PHYSICAL_ONLY`)

**Bases moins critiques (Dev/Test)** :
- **Vérification complète** : Mensuelle
- **Vérification physique** : Hebdomadaire

**Très grandes bases (> 1 TB)** :
- Envisager des vérifications partielles plus fréquentes
- Vérification complète trimestrielle

### Automatisation avec SQL Server Agent

Créez un job SQL Server Agent pour exécuter DBCC CHECKDB automatiquement :

```sql
-- Script à exécuter dans un Job SQL Agent
USE master;
GO

DECLARE @BaseDeDonnees NVARCHAR(255) = 'MaBase';

-- Vérification complète
DBCC CHECKDB (@BaseDeDonnees) WITH NO_INFOMSGS;

-- Envoyer un email en cas d'erreur
IF @@ERROR <> 0
BEGIN
    -- Configuration d'alerte email (voir Database Mail)
    EXEC msdb.dbo.sp_send_dbmail
        @profile_name = 'MonProfilMail',
        @recipients = 'dba@entreprise.com',
        @subject = 'ALERTE : Erreur DBCC CHECKDB',
        @body = 'Des erreurs ont été détectées dans la base de données. Vérifiez immédiatement !';
END
```

### Fenêtre de Maintenance

DBCC CHECKDB est une opération **intensive** :

**Impact sur les performances** :
- Consommation élevée de CPU
- Beaucoup de lectures disque (I/O)
- Utilisation de tempdb
- Peut ralentir les requêtes utilisateurs

**Recommandation** :
- Exécutez pendant les heures creuses (nuit, week-end)
- Prévoyez une fenêtre suffisante (peut prendre plusieurs heures sur de grandes bases)

### Estimation du Temps d'Exécution

```sql
-- Estimer le temps nécessaire
DBCC CHECKDB ('MaBase') WITH ESTIMATEONLY;
```

**Facteurs influençant la durée** :
- Taille de la base de données
- Nombre d'objets (tables, index)
- Vitesse du stockage (HDD vs SSD)
- Charge du serveur

**Règle approximative** :
- Petite base (< 10 GB) : Quelques minutes
- Base moyenne (10-100 GB) : 30 minutes à 2 heures
- Grande base (100-500 GB) : 2 à 8 heures
- Très grande base (> 1 TB) : Plusieurs heures à une journée

## DBCC CHECKDB vs Autres Commandes DBCC

SQL Server propose d'autres commandes DBCC pour des vérifications plus ciblées :

### DBCC CHECKTABLE

Vérifie **une seule table** au lieu de toute la base :

```sql
DBCC CHECKTABLE ('MaTable');
```

**Avantage** : Plus rapide si vous suspectez un problème sur une table spécifique.

### DBCC CHECKALLOC

Vérifie uniquement les **structures d'allocation** :

```sql
DBCC CHECKALLOC ('MaBase');
```

**Avantage** : Plus rapide, mais ne vérifie pas le contenu des tables.

### DBCC CHECKCATALOG

Vérifie la cohérence du **catalogue système** :

```sql
DBCC CHECKCATALOG ('MaBase');
```

**Note** : CHECKDB inclut automatiquement CHECKCATALOG.

### Relation entre les Commandes

```
DBCC CHECKDB
    ├── DBCC CHECKALLOC (allocation des pages)
    ├── DBCC CHECKTABLE (pour chaque table)
    └── DBCC CHECKCATALOG (catalogue système)
```

**Conclusion** : CHECKDB est la commande "tout-en-un". Les autres sont pour des diagnostics ciblés.

## Cas Particuliers

### Bases de Données Azure SQL

Sur **Azure SQL Database** (PaaS) :
- Microsoft gère automatiquement les vérifications d'intégrité
- Vous **ne pouvez pas** exécuter DBCC CHECKDB manuellement
- Microsoft assure une haute disponibilité avec réplicas

**Implication** : Moins de contrôle, mais maintenance automatisée.

### Bases de Données Très Volumineuses (VLDB)

Pour les bases de **plusieurs TB** :

**Problème** : CHECKDB peut prendre trop de temps (> 24h).

**Solutions** :
1. **Vérifications partielles** : Diviser la vérification sur plusieurs jours
2. **PHYSICAL_ONLY** : Plus fréquent (quotidien) + complet moins fréquent (mensuel)
3. **Vérification hors ligne** : Sur une copie (snapshot) pour ne pas impacter la production

```sql
-- Créer un snapshot de base de données
CREATE DATABASE MaBase_Snapshot ON
(
    NAME = MaBase_Data,
    FILENAME = 'C:\Snapshots\MaBase_Snapshot.ss'
) AS SNAPSHOT OF MaBase;

-- Vérifier le snapshot au lieu de la base de production
DBCC CHECKDB ('MaBase_Snapshot');

-- Supprimer le snapshot après vérification
DROP DATABASE MaBase_Snapshot;
```

### Bases de Données en Disponibilité AlwaysOn

Dans un groupe de disponibilité :
- Exécutez CHECKDB sur le **réplica secondaire** (lecture seule)
- Réduit l'impact sur le réplica primaire (production)
- Le secondaire doit être en mode lecture

```sql
-- Sur le réplica secondaire
DBCC CHECKDB ('MaBase') WITH NO_INFOMSGS;
```

## Vérification de l'Intégrité des Sauvegardes

### Importance Critique

> **Principe fondamental** : Une sauvegarde non vérifiée n'est pas une sauvegarde.

Vous **devez** régulièrement vérifier que vos sauvegardes sont valides.

### RESTORE VERIFYONLY

Vérifie qu'une sauvegarde peut être restaurée :

```sql
RESTORE VERIFYONLY
FROM DISK = 'C:\Backups\MaBase.bak';
```

**Ce qu'il vérifie** :
- Le fichier de sauvegarde est lisible
- La structure de la sauvegarde est valide
- Les checksums sont corrects (si activés)

**Ce qu'il NE vérifie PAS** :
- L'intégrité logique des données dans la sauvegarde

### Stratégie Complète

```sql
-- 1. Vérifier la sauvegarde
RESTORE VERIFYONLY
FROM DISK = 'C:\Backups\MaBase.bak';

-- 2. Restaurer dans une base de test
RESTORE DATABASE MaBase_Test
FROM DISK = 'C:\Backups\MaBase.bak'
WITH MOVE 'MaBase_Data' TO 'C:\Test\MaBase_Test.mdf',
     MOVE 'MaBase_Log' TO 'C:\Test\MaBase_Test_log.ldf',
     REPLACE;

-- 3. Vérifier l'intégrité de la base restaurée
DBCC CHECKDB ('MaBase_Test') WITH NO_INFOMSGS;

-- 4. Si tout est OK, supprimer la base de test
DROP DATABASE MaBase_Test;
```

**Fréquence recommandée** : Au minimum mensuelle pour les bases critiques.

## Indicateurs de Santé de la Base

En plus de CHECKDB, surveillez ces indicateurs :

### 1. Suspect Pages

SQL Server maintient une table des pages suspectes (potentiellement corrompues) :

```sql
-- Vérifier les pages suspectes
SELECT
    database_id,
    DB_NAME(database_id) AS BaseDeDonnees,
    file_id,
    page_id,
    event_type,
    error_count,
    last_update_date
FROM
    msdb.dbo.suspect_pages
ORDER BY
    last_update_date DESC;
```

Si cette requête retourne des résultats, **agissez immédiatement** !

### 2. Logs d'Erreurs SQL Server

Vérifiez régulièrement les logs pour des messages d'erreur :

```sql
-- Lire le log d'erreurs actuel
EXEC sp_readerrorlog 0, 1, N'error';
```

Recherchez des mots-clés comme :
- "corruption"
- "I/O error"
- "checksum"
- "consistency"

### 3. Événements Windows

Consultez l'**Event Viewer** de Windows pour :
- Erreurs disque
- Erreurs mémoire
- Problèmes matériels

## Exemples de Scripts de Maintenance

### Script Complet de Vérification

```sql
USE master;
GO

-- Variables
DECLARE @BaseDeDonnees NVARCHAR(255) = 'MaBase';
DECLARE @Resultat INT;
DECLARE @Message NVARCHAR(500);

-- Date et heure de début
PRINT '========================================';
PRINT 'Début de la vérification : ' + CONVERT(VARCHAR(20), GETDATE(), 120);
PRINT 'Base de données : ' + @BaseDeDonnees;
PRINT '========================================';

-- Exécution de CHECKDB
BEGIN TRY
    DBCC CHECKDB (@BaseDeDonnees) WITH NO_INFOMSGS;
    SET @Resultat = 0;
    SET @Message = 'Vérification réussie : Aucune erreur détectée.';
END TRY
BEGIN CATCH
    SET @Resultat = ERROR_NUMBER();
    SET @Message = 'ERREUR DÉTECTÉE ! ' + ERROR_MESSAGE();
END CATCH

-- Affichage du résultat
PRINT '';
PRINT 'Résultat : ' + @Message;
PRINT 'Fin de la vérification : ' + CONVERT(VARCHAR(20), GETDATE(), 120);
PRINT '========================================';

-- Retourner le code d'erreur
IF @Resultat <> 0
BEGIN
    RAISERROR (@Message, 16, 1);
END
```

### Script Multi-Bases

```sql
USE master;
GO

-- Vérifier toutes les bases de données utilisateur
DECLARE @BaseDeDonnees NVARCHAR(255);

DECLARE db_cursor CURSOR FOR
SELECT name
FROM sys.databases
WHERE database_id > 4  -- Exclure les bases système (master, model, msdb, tempdb)
  AND state_desc = 'ONLINE'
  AND name NOT IN ('ReportServer', 'ReportServerTempDB'); -- Exclure certaines bases si nécessaire

OPEN db_cursor;
FETCH NEXT FROM db_cursor INTO @BaseDeDonnees;

WHILE @@FETCH_STATUS = 0
BEGIN
    PRINT '========================================';
    PRINT 'Vérification de : ' + @BaseDeDonnees;
    PRINT '========================================';

    BEGIN TRY
        EXEC('DBCC CHECKDB ([' + @BaseDeDonnees + ']) WITH NO_INFOMSGS');
        PRINT 'Résultat : OK';
    END TRY
    BEGIN CATCH
        PRINT 'Résultat : ERREUR - ' + ERROR_MESSAGE();
    END CATCH

    PRINT '';
    FETCH NEXT FROM db_cursor INTO @BaseDeDonnees;
END

CLOSE db_cursor;
DEALLOCATE db_cursor;
```

## Conclusion

DBCC CHECKDB est votre **gardien de l'intégrité** de la base de données :

**Principes clés à retenir** :

1. ✅ **Préventif, pas réactif** : Exécutez CHECKDB régulièrement, même si tout va bien
2. ✅ **Les sauvegardes sont vitales** : Elles sont votre plan B en cas de corruption
3. ✅ **Vérifiez vos sauvegardes** : Une sauvegarde non testée est inutile
4. ✅ **Automatisez** : Créez des jobs pour ne jamais oublier
5. ✅ **Surveillez** : Consultez les logs et les pages suspectes
6. ✅ **Agissez vite** : En cas d'erreur, chaque minute compte

**Récapitulatif de la stratégie** :
- **Quotidien** : `CHECKDB WITH PHYSICAL_ONLY` (rapide)
- **Hebdomadaire** : `CHECKDB` complet
- **Mensuel** : Vérification des sauvegardes avec restauration de test
- **Trimestriel** : `CHECKDB WITH EXTENDED_LOGICAL_CHECKS` (pour bases critiques)

L'intégrité de vos données est **précieuse et irremplaçable**. DBCC CHECKDB est l'outil qui vous permet de dormir sur vos deux oreilles en sachant que vos données sont saines et récupérables.
