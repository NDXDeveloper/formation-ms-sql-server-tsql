# 7.8.3 BACKUP DATABASE et BACKUP LOG

## Introduction

Place à la pratique ! Cette sous-section présente la **syntaxe T-SQL** concrète pour réaliser chaque type de sauvegarde, les **options indispensables** en production, et — tout aussi important — la manière de **vérifier** qu'une sauvegarde est saine et exploitable.

> 🧠 Rappel : faire une sauvegarde sans la vérifier, c'est comme signer un parachute sans avoir contrôlé qu'il est plié correctement. On ne le découvre qu'au saut.

---

## Sauvegarde complète : BACKUP DATABASE

La syntaxe de base est très lisible :

```sql
BACKUP DATABASE Boutique
TO DISK = 'C:\Backups\Boutique_FULL_20260531.bak';
```

En production, on ajoute presque toujours des **options** importantes :

```sql
BACKUP DATABASE Boutique
TO DISK = 'C:\Backups\Boutique_FULL_20260531.bak'
WITH
    INIT,            -- écrase le contenu du fichier .bak s'il existe déjà
    COMPRESSION,     -- compresse la sauvegarde (gain d'espace ET de temps)
    CHECKSUM,        -- calcule des sommes de contrôle pour détecter la corruption
    STATS = 10;      -- affiche la progression tous les 10 %
```

### Les options à connaître

| Option | Rôle |
|--------|------|
| `INIT` / `NOINIT` | `INIT` écrase le fichier ; `NOINIT` (défaut) ajoute la sauvegarde à la suite |
| `FORMAT` | Réinitialise complètement le média — **destructif**, à manier avec précaution |
| `COMPRESSION` / `NO_COMPRESSION` | Active/désactive la compression de la sauvegarde |
| `CHECKSUM` / `NO_CHECKSUM` | Vérifie l'intégrité des pages pendant la sauvegarde |
| `STATS = n` | Affiche la progression tous les *n* % |
| `COPY_ONLY` | Sauvegarde hors chaîne (voir §7.8.2) |
| `DIFFERENTIAL` | Réalise une sauvegarde différentielle |
| `EXPIREDATE` / `RETAINDAYS` | Empêche l'écrasement avant une date / un délai |
| `MIRROR TO` | Écrit simultanément une copie miroir de la sauvegarde |
| `DESCRIPTION` | Ajoute un texte descriptif dans les métadonnées |

### Zoom sur la compression

`WITH COMPRESSION` réduit souvent la taille des sauvegardes d'un facteur **3 à 5**, et **accélère** la sauvegarde (moins d'écritures disque, au prix d'un peu plus de CPU).

> ⚠️ **Édition** : la compression de sauvegarde est disponible sur **Standard, Enterprise et Developer**, mais **pas sur Express**. Sur Express, retirez simplement l'option. On peut définir la compression par défaut au niveau de l'instance via `sp_configure 'backup compression default', 1`.

### Zoom sur CHECKSUM

`WITH CHECKSUM` demande à SQL Server de vérifier les sommes de contrôle des pages **pendant** la sauvegarde et d'en calculer une pour le fichier. Couplé à `RESTORE VERIFYONLY ... WITH CHECKSUM`, cela permet de détecter une corruption **avant** d'en avoir besoin. À activer systématiquement.

---

## Sauvegarde différentielle

Même commande, avec l'option `DIFFERENTIAL` :

```sql
BACKUP DATABASE Boutique
TO DISK = 'C:\Backups\Boutique_DIFF_20260531.bak'
WITH DIFFERENTIAL, INIT, COMPRESSION, CHECKSUM, STATS = 10;
```

➡️ SQL Server sait automatiquement à quelle **complète** cette différentielle se rattache (via la carte DCM, voir §7.8.2).

---

## Sauvegarde du journal des transactions : BACKUP LOG

```sql
BACKUP LOG Boutique
TO DISK = 'C:\Backups\Boutique_LOG_20260531_1015.trn'
WITH COMPRESSION, CHECKSUM, STATS = 10;
```

> 💡 **Convention de nommage** : on utilise souvent l'extension `.bak` pour les sauvegardes de données et `.trn` pour les sauvegardes de journal (*transaction log*). C'est une convention pratique, pas une obligation technique.

⚠️ Rappel : `BACKUP LOG` n'est possible **qu'en modèle `FULL` ou `BULK_LOGGED`** (voir §7.8.1). En `SIMPLE`, la commande échoue avec une erreur explicite.

### Cas particulier vital : la sauvegarde de fin de journal (tail-log backup)

Lorsqu'un sinistre survient mais que le **fichier journal est encore intact** (par exemple, le fichier de données est corrompu mais le `.ldf` est lisible), vous pouvez capturer les **toutes dernières transactions** non encore sauvegardées : c'est la **sauvegarde de fin de journal** (*tail-log backup*).

```sql
BACKUP LOG Boutique
TO DISK = 'C:\Backups\Boutique_tail.trn'
WITH NO_TRUNCATE;   -- capture la fin du journal même si la base est endommagée
```

➡️ C'est elle qui permet de restaurer **jusqu'à la dernière seconde** avant un sinistre. C'est souvent la **première** commande à exécuter face à un incident, **avant** de commencer une restauration. Ne l'oubliez jamais.

---

## Répartir une sauvegarde sur plusieurs fichiers (striping)

Pour accélérer la sauvegarde des très grosses bases, on peut l'écrire en parallèle sur plusieurs fichiers :

```sql
BACKUP DATABASE Boutique
TO DISK = 'D:\Backups\Boutique_1.bak',
   DISK = 'E:\Backups\Boutique_2.bak',
   DISK = 'F:\Backups\Boutique_3.bak'
WITH COMPRESSION, CHECKSUM, STATS = 5;
```

⚠️ Les 3 fichiers forment **un seul jeu de sauvegarde** : il faudra **les trois** pour restaurer. Perdre un seul des fichiers rend l'ensemble inutilisable.

---

## Sauvegarde miroir (MIRROR TO)

Pour écrire **deux copies identiques** en une seule opération (par exemple une locale + une réseau) :

```sql
BACKUP DATABASE Boutique
TO DISK = 'D:\Backups\Boutique.bak'
MIRROR TO DISK = '\\NAS\Backups\Boutique.bak'
WITH FORMAT, COMPRESSION, CHECKSUM;
```

---

## Sauvegarde vers le cloud (Azure Blob Storage)

SQL Server peut sauvegarder directement vers un conteneur Azure via `TO URL` — pratique pour disposer d'une copie hors site (règle 3-2-1) :

```sql
BACKUP DATABASE Boutique
TO URL = 'https://moncompte.blob.core.windows.net/backups/Boutique_FULL.bak'
WITH COMPRESSION, CHECKSUM, STATS = 10;
```

(Nécessite au préalable une *credential* SQL Server associée au compte de stockage, via un jeton SAS.)

---

## Chiffrer les sauvegardes (backup encryption)

Les sauvegardes contiennent vos données « en clair » : un fichier `.bak` volé est aussi grave qu'une base volée. Depuis SQL Server 2014, on peut **chiffrer la sauvegarde elle-même** :

```sql
BACKUP DATABASE Boutique
TO DISK = 'C:\Backups\Boutique_chiffre.bak'
WITH
    COMPRESSION,
    ENCRYPTION (ALGORITHM = AES_256, SERVER CERTIFICATE = CertSauvegarde),
    CHECKSUM, STATS = 10;
```

> ⚠️ **Sauvegardez aussi le certificat/la clé** dans un endroit sûr et séparé : sans lui, la sauvegarde chiffrée est **irrécupérable**. Une sauvegarde chiffrée dont on a perdu la clé ne vaut rien.

## Vérifier ses sauvegardes (indispensable !)

Faire une sauvegarde ne suffit pas : il faut s'assurer qu'elle est **lisible et saine**.

### Vérifier l'intégrité d'un fichier de sauvegarde

```sql
RESTORE VERIFYONLY
FROM DISK = 'C:\Backups\Boutique_FULL_20260531.bak'
WITH CHECKSUM;
```

➡️ Ne restaure rien : vérifie seulement que la sauvegarde est complète, lisible et cohérente. À exécuter **après chaque sauvegarde**.

> ⚠️ `RESTORE VERIFYONLY` ne garantit pas à 100 % une restauration réussie — le seul test vraiment fiable reste une **restauration réelle** sur un serveur de test (voir §7.8.6).

### Lire les métadonnées d'une sauvegarde

```sql
-- Quelles sauvegardes contient ce fichier ? (type, date, taille, position...)
RESTORE HEADERONLY FROM DISK = 'C:\Backups\Boutique_FULL_20260531.bak';

-- Quels fichiers logiques/physiques composent la base sauvegardée ?
RESTORE FILELISTONLY FROM DISK = 'C:\Backups\Boutique_FULL_20260531.bak';

-- Informations sur le média de sauvegarde
RESTORE LABELONLY FROM DISK = 'C:\Backups\Boutique_FULL_20260531.bak';
```

`RESTORE FILELISTONLY` est particulièrement utile **avant** une restauration : il donne les **noms logiques** des fichiers, nécessaires pour l'option `MOVE` (voir §7.8.4).

### Consulter l'historique des sauvegardes

SQL Server conserve l'historique des sauvegardes dans la base système `msdb` :

```sql
SELECT
    bs.database_name,
    bs.backup_start_date,
    CASE bs.type
        WHEN 'D' THEN 'Complète'
        WHEN 'I' THEN 'Différentielle'
        WHEN 'L' THEN 'Journal'
        ELSE bs.type
    END AS TypeSauvegarde,
    CAST(bs.backup_size / 1048576.0 AS DECIMAL(10,2)) AS Taille_Mo,
    bmf.physical_device_name AS Fichier
FROM msdb.dbo.backupset bs
JOIN msdb.dbo.backupmediafamily bmf
    ON bs.media_set_id = bmf.media_set_id
WHERE bs.database_name = 'Boutique'
ORDER BY bs.backup_start_date DESC;
```

➡️ Très utile pour répondre à « quand a eu lieu la dernière sauvegarde de cette base ? » — une question d'audit fréquente.

## Bonnes pratiques de nommage et d'organisation

```
C:\Backups\
 ├── Boutique\
 │    ├── Boutique_FULL_20260531_020000.bak
 │    ├── Boutique_DIFF_20260603_020000.bak
 │    └── Boutique_LOG_20260603_101500.trn
```

- Un **fichier horodaté par sauvegarde** (plutôt qu'empiler avec `NOINIT`) : plus clair, plus sûr.
- Un **dossier par base**.
- Une **rétention automatisée** (suppression des vieux fichiers) — sans casser une chaîne encore utile.

---

## Pièges fréquents

- ❌ **Oublier le tail-log backup** lors d'un incident → perte des dernières transactions pourtant récupérables.
- ❌ **Sauvegarder sur le même disque que la base** → un sinistre disque emporte tout.
- ❌ **Empiler les sauvegardes avec `NOINIT`** dans un seul fichier qui grossit sans fin et devient un point de défaillance unique.
- ❌ **Activer le chiffrement sans sauvegarder la clé** → sauvegardes irrécupérables.
- ❌ **Ne jamais lancer `RESTORE VERIFYONLY`** → on découvre la corruption le jour du sinistre.

---

## Questions fréquentes

**Q : Peut-on sauvegarder une base pendant qu'elle est utilisée ?**
R : Oui ! C'est tout l'intérêt de `BACKUP`. Les utilisateurs continuent de travailler ; la sauvegarde reste cohérente sur le plan transactionnel.

**Q : `INIT` ou `NOINIT` ?**
R : Avec la pratique « un fichier par sauvegarde », `INIT` (ou un nouveau nom de fichier) est plus sain. `NOINIT` empile et complique la gestion.

**Q : Faut-il sauvegarder les bases système ?**
R : Oui — surtout `master` (configuration de l'instance) et `msdb` (jobs, historique). Ne les oubliez pas dans votre plan.

---

## Résumé

- `BACKUP DATABASE ... TO DISK` réalise une complète ; ajoutez `WITH DIFFERENTIAL` pour une différentielle.
- `BACKUP LOG ... TO DISK` sauvegarde le journal (modèle `FULL`/`BULK_LOGGED`).
- Options clés : `INIT`, `COMPRESSION` (sauf Express), `CHECKSUM`, `STATS`, `COPY_ONLY`, `ENCRYPTION`.
- En cas d'incident, pensez d'abord à la **sauvegarde de fin de journal** (`BACKUP LOG ... WITH NO_TRUNCATE`).
- On peut répartir (*striping*), faire un miroir (`MIRROR TO`), ou sauvegarder vers Azure (`TO URL`).
- **Vérifiez toujours** : `RESTORE VERIFYONLY/HEADERONLY/FILELISTONLY` et l'historique dans `msdb`.

Nous savons sauvegarder. Le plus important reste à venir : **savoir restaurer**.
