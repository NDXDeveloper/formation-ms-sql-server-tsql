# 7.2.3 Colonnes incluses (INCLUDE)

## Introduction

Dans les sections précédentes, nous avons vu :
- Les index simples et composites (7.1, 7.2.1)
- Les index filtrés pour réduire la taille (7.2.2)

Nous avons également mentionné le concept de **Key Lookup** : quand SQL Server doit faire un aller-retour entre l'index et la table pour récupérer des colonnes manquantes.

**Question** : Comment éviter ces Key Lookups coûteux tout en gardant un index efficace ?

**Réponse** : Les **colonnes incluses** avec la clause **INCLUDE**.

### Rappel : Le problème du Key Lookup

```sql
-- Index sur Email
CREATE INDEX IX_Clients_Email ON Clients (Email);

-- Requête qui demande d'autres colonnes
SELECT Nom, Prenom, Telephone FROM Clients WHERE Email = 'marie@email.com';

-- Opérations SQL Server :
-- 1. Index Seek sur IX_Clients_Email → trouve ClientID = 8
-- 2. Key Lookup : va chercher Nom, Prenom, Telephone dans la table
-- Total : 2 opérations (coûteux)
```

**Le Key Lookup ralentit la requête**, surtout si elle retourne beaucoup de lignes.

## Qu'est-ce que la Clause INCLUDE ?

### Définition

La clause **INCLUDE** permet d'ajouter des **colonnes supplémentaires** à un index non-clustered **sans les inclure dans la structure de recherche**.

```sql
-- Syntaxe
CREATE INDEX nom_index
ON nom_table (colonnes_cles)
INCLUDE (colonnes_supplementaires);
```

**Concept clé** : Les colonnes INCLUDE sont stockées **seulement au niveau feuilles** de l'index B-Tree.

### L'analogie de l'annuaire avec notes

Imaginez un **annuaire téléphonique amélioré** :

**Annuaire classique** :
```
Structure de recherche (tous les niveaux) :
    Nom, Prénom → Numéro de téléphone

Exemple :
    DUPONT, Marie → 0612345678
```

**Annuaire avec INCLUDE** (notes supplémentaires) :
```
Structure de recherche (navigation) :
    Nom, Prénom

Niveau feuilles (données complètes) :
    Nom, Prénom → Numéro + Email + Adresse

Exemple :
    DUPONT, Marie → 0612345678 + marie@email.com + 123 rue de Paris
```

**Avantages** :
- ✅ Navigation rapide (structure légère : Nom, Prénom seulement)
- ✅ Données complètes disponibles quand vous arrivez (Numéro + Email + Adresse)
- ✅ Pas besoin d'aller chercher ailleurs

**C'est exactement ce que fait INCLUDE !**

## Structure d'un Index avec INCLUDE

### Index classique (sans INCLUDE)

```sql
CREATE INDEX IX_Clients_Email ON Clients (Email);
```

**Structure B-Tree** :

```
┌─────────────────────────────────────────────┐
│             Niveau Racine                   │
│   [Pointeurs vers niveaux intermédiaires]   │
│   Contient : Email (valeurs de division)    │
└──────────────────┬──────────────────────────┘
                   │
    ┌──────────────┴──────────────┐
    │                             │
┌───▼─────────────┐    ┌──────────▼──────────┐
│ Niveau          │    │ Niveau              │
│ Intermédiaire   │    │ Intermédiaire       │
│ Contient: Email │    │ Contient: Email     │
└───┬─────────────┘    └──────────┬──────────┘
    │                             │
┌───▼─────────────┐    ┌──────────▼──────────┐
│ Niveau Feuilles │    │ Niveau Feuilles     │
│ ┌─────────────┐ │    │ ┌─────────────┐     │
│ │Email        │ │    │ │Email        │     │
│ │ClientID (→) │ │    │ │ClientID (→) │     │
│ └─────────────┘ │    │ └─────────────┘     │
└─────────────────┘    └─────────────────────┘

Tous les niveaux : Email uniquement
Feuilles : Email + ClientID (pointeur)
```

### Index avec INCLUDE

```sql
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom, Telephone);
```

**Structure B-Tree** :

```
┌─────────────────────────────────────────────┐
│             Niveau Racine                   │
│   [Pointeurs vers niveaux intermédiaires]   │
│   Contient : Email SEULEMENT                │
└──────────────────┬──────────────────────────┘
                   │
    ┌──────────────┴──────────────┐
    │                             │
┌───▼─────────────┐    ┌──────────▼──────────┐
│ Niveau          │    │ Niveau              │
│ Intermédiaire   │    │ Intermédiaire       │
│ Contient: Email │    │ Contient: Email     │
│ SEULEMENT       │    │ SEULEMENT           │
└───┬─────────────┘    └──────────┬──────────┘
    │                             │
┌───▼─────────────────────────────▼──────────┐
│           Niveau Feuilles                  │
│ ┌────────────────────────────────────────┐ │
│ │ Email                                  │ │
│ │ ClientID (→)                           │ │
│ │ Nom          ← INCLUDE                 │ │
│ │ Prenom       ← INCLUDE                 │ │
│ │ Telephone    ← INCLUDE                 │ │
│ └────────────────────────────────────────┘ │
└────────────────────────────────────────────┘

Niveaux supérieurs : Email seulement (léger)
Feuilles : Email + ClientID + Nom + Prenom + Telephone
```

**Points clés** :
1. Les niveaux supérieurs (navigation) ne contiennent que Email → **Index compact et rapide**
2. Les feuilles contiennent Email + colonnes INCLUDE → **Toutes les données nécessaires**
3. Pas besoin de Key Lookup → **Une seule opération**

## Création d'Index avec INCLUDE

### Syntaxe

```sql
-- Index avec une colonne clé et colonnes INCLUDE
CREATE INDEX nom_index
ON nom_table (colonne_cle)
INCLUDE (col1, col2, col3, ...);

-- Index composite avec colonnes INCLUDE
CREATE INDEX nom_index
ON nom_table (col_cle1, col_cle2)
INCLUDE (col_include1, col_include2, ...);

-- Index unique avec INCLUDE
CREATE UNIQUE INDEX nom_index
ON nom_table (colonne_unique)
INCLUDE (col1, col2);

-- Index filtré avec INCLUDE
CREATE INDEX nom_index
ON nom_table (colonne_cle)
INCLUDE (col1, col2)
WHERE condition;
```

### Exemple 1 : Index simple avec INCLUDE

```sql
-- Table Clients
CREATE TABLE Clients (
    ClientID INT IDENTITY(1,1) PRIMARY KEY,
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    Email NVARCHAR(255),
    Telephone NVARCHAR(20),
    Ville NVARCHAR(100),
    DateInscription DATE
);

-- Requête fréquente
SELECT Nom, Prenom, Telephone
FROM Clients
WHERE Email = 'marie@email.com';

-- ❌ SANS INCLUDE : Key Lookup nécessaire
CREATE INDEX IX_Clients_Email
ON Clients (Email);
-- Opérations : Index Seek + Key Lookup = 2 opérations

-- ✅ AVEC INCLUDE : Covering Index
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom, Telephone);
-- Opérations : Index Seek seulement = 1 opération
```

**Résultat** :

```
Sans INCLUDE (2 opérations) :
┌──────────────────────┐
│ 1. Index Seek        │
│    sur Email         │
│    → Trouve ClientID │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│ 2. Key Lookup        │
│    Cherche Nom,      │
│    Prenom, Telephone │
│    dans la table     │
└──────────────────────┘

Avec INCLUDE (1 opération) :
┌──────────────────────┐
│ 1. Index Seek        │
│    sur Email         │
│    → Trouve tout :   │
│    Email, Nom,       │
│    Prenom, Telephone │
└──────────────────────┘
```

### Exemple 2 : Index composite avec INCLUDE

```sql
-- Table Commandes
CREATE TABLE Commandes (
    CommandeID INT IDENTITY(1,1) PRIMARY KEY,
    ClientID INT,
    DateCommande DATE,
    Statut NVARCHAR(20),
    MontantTotal DECIMAL(10,2),
    Adresse NVARCHAR(500),
    Commentaire NVARCHAR(MAX)
);

-- Requête fréquente
SELECT CommandeID, DateCommande, MontantTotal, Adresse
FROM Commandes
WHERE ClientID = 123 AND Statut = 'En cours';

-- Index composite avec INCLUDE
CREATE INDEX IX_Commandes_Client_Statut
ON Commandes (ClientID, Statut)
INCLUDE (DateCommande, MontantTotal, Adresse);
```

**Pourquoi cet ordre ?** :
- **Colonnes clés** (ClientID, Statut) : Utilisées dans le WHERE → Dans la structure de recherche
- **Colonnes INCLUDE** (DateCommande, MontantTotal, Adresse) : Seulement dans le SELECT → Au niveau feuilles

### Exemple 3 : Index unique avec INCLUDE

```sql
-- Table Employes
CREATE TABLE Employes (
    EmployeID INT IDENTITY(1,1) PRIMARY KEY,
    Matricule NVARCHAR(20),
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    Email NVARCHAR(255),
    Telephone NVARCHAR(20),
    Departement NVARCHAR(50)
);

-- Index unique sur Matricule avec informations supplémentaires
CREATE UNIQUE INDEX IX_Employes_Matricule
ON Employes (Matricule)
INCLUDE (Nom, Prenom, Email, Departement);

-- Requête
SELECT Nom, Prenom, Email, Departement
FROM Employes
WHERE Matricule = 'EMP-12345';
-- Une seule opération, très rapide
```

### Exemple 4 : Index filtré avec INCLUDE

```sql
-- Table Produits
CREATE TABLE Produits (
    ProduitID INT IDENTITY(1,1) PRIMARY KEY,
    SKU NVARCHAR(50),
    Nom NVARCHAR(200),
    Prix DECIMAL(10,2),
    Stock INT,
    Actif BIT,
    Description NVARCHAR(MAX)
);

-- Index filtré sur produits actifs avec infos complètes
CREATE INDEX IX_Produits_Actifs_SKU
ON Produits (SKU)
INCLUDE (Nom, Prix, Stock, Description)
WHERE Actif = 1;

-- Requête
SELECT Nom, Prix, Stock, Description
FROM Produits
WHERE Actif = 1 AND SKU = 'LAP-2024-001';
-- Très efficace : index filtré + covering index
```

## Covering Index : Le Concept Complet

### Définition

Un **covering index** (index couvrant) est un index qui contient **toutes les colonnes** nécessaires pour exécuter une requête, sans avoir besoin d'accéder à la table.

**Il peut être créé de deux façons** :
1. En mettant toutes les colonnes dans les colonnes clés (inefficace)
2. **En utilisant INCLUDE** pour les colonnes non filtrées (recommandé)

### Exemple : Covering vs Non-Covering

```sql
-- Requête
SELECT ClientID, Nom, Email, DateInscription
FROM Clients
WHERE Ville = 'Paris';
```

#### Option 1 : Index NON-couvrant

```sql
CREATE INDEX IX_Clients_Ville
ON Clients (Ville);

-- Opérations :
-- 1. Index Seek sur Ville
-- 2. Key Lookup pour chaque ligne (Nom, Email, DateInscription)
-- Si 10 000 clients à Paris → 10 000 Key Lookups ! Très lent
```

#### Option 2 : Covering Index avec colonnes clés (MAUVAIS)

```sql
-- ❌ MAUVAIS : Toutes les colonnes dans les clés
CREATE INDEX IX_Clients_Ville_Nom_Email_Date
ON Clients (Ville, Nom, Email, DateInscription);

-- Problème : Index très large
-- Structure de navigation lourde
-- Limite de 900 octets peut être dépassée
```

#### Option 3 : Covering Index avec INCLUDE (BON)

```sql
-- ✅ BON : INCLUDE pour les colonnes non filtrées
CREATE INDEX IX_Clients_Ville
ON Clients (Ville)
INCLUDE (Nom, Email, DateInscription);

-- Avantages :
-- - Structure de navigation légère (Ville seulement)
-- - Données complètes au niveau feuilles
-- - Pas de Key Lookup
-- - Pas de limite de 900 octets pour les colonnes INCLUDE
```

### Visualisation : Index Seek vs Covering Index

```
Index NON-couvrant (avec Key Lookup) :
═══════════════════════════════════════

┌─────────────────┐     ┌─────────────────┐
│  Index Seek     │     │  Key Lookup     │
│  sur Ville      │ ──▶ │  pour chaque    │
│                 │     │  ligne trouvée  │
│  Trouve 10 000  │     │                 │
│  ClientID       │     │  10 000 lookups │
└─────────────────┘     └─────────────────┘
     1 opération            10 000 opérations

Total : 10 001 opérations


Covering Index (avec INCLUDE) :
═══════════════════════════════

┌─────────────────────────────────┐
│  Index Seek                     │
│  sur Ville                      │
│                                 │
│  Trouve directement :           │
│  - ClientID                     │
│  - Nom (INCLUDE)                │
│  - Email (INCLUDE)              │
│  - DateInscription (INCLUDE)    │
│                                 │
│  Pour les 10 000 lignes         │
└─────────────────────────────────┘
        1 opération

Total : 1 opération

Gain : 10 000x plus rapide !
```

## Avantages de la Clause INCLUDE

### 1. ✅ Évite les Key Lookups coûteux

**Sans INCLUDE** :
- Index Seek : 1 opération
- Key Lookup : n opérations (une par ligne trouvée)
- Si la requête retourne 1000 lignes → 1001 opérations

**Avec INCLUDE** :
- Index Seek : 1 opération
- Toutes les données dans l'index → 1 opération

**Gain** : Énorme pour les requêtes retournant beaucoup de lignes.

### 2. ✅ Structure d'index plus efficace

Les colonnes INCLUDE ne sont **pas dans la structure de navigation**.

**Impact** :
- Index plus compact aux niveaux supérieurs
- Recherche plus rapide (moins de données à parcourir)
- Moins de mémoire pour les niveaux de navigation

### 3. ✅ Contourne la limite de 900 octets

SQL Server limite la taille des **colonnes clés** à 900 octets (pour les index non-clustered).

**Problème avec colonnes clés** :
```sql
-- ❌ ERREUR : Dépassement de 900 octets
CREATE INDEX IX_Clients_Large
ON Clients (
    Nom NVARCHAR(200),      -- 400 octets
    Adresse NVARCHAR(500)   -- 1000 octets
);
-- Total : 1400 octets > 900 octets → ERREUR
```

**Solution avec INCLUDE** :
```sql
-- ✅ BON : INCLUDE n'a pas de limite
CREATE INDEX IX_Clients_Nom
ON Clients (Nom)
INCLUDE (Adresse);
-- Pas de limite pour les colonnes INCLUDE
```

### 4. ✅ Permet des index plus ciblés

Vous pouvez créer un index sur les colonnes **vraiment importantes** pour la recherche, et ajouter les autres en INCLUDE.

**Exemple** :
```sql
-- Recherche par Email, mais besoin de beaucoup d'infos
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom, Telephone, Adresse, Ville, CodePostal, DateNaissance);

-- Email : seule colonne dans la structure de recherche (efficace)
-- Autres : disponibles sans Key Lookup
```

### 5. ✅ Moins de fragmentation

Les colonnes INCLUDE sont au niveau feuilles seulement, donc :
- Les niveaux supérieurs restent stables
- Moins de divisions de pages (page splits)
- Moins de fragmentation

## Inconvénients et Coûts

### 1. ❌ Augmentation de la taille de l'index

Plus de colonnes = index plus volumineux.

**Exemple** :
```sql
-- Index sans INCLUDE
CREATE INDEX IX_Clients_Email ON Clients (Email);
-- Taille : 50 MB

-- Index avec INCLUDE
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom, Telephone, Adresse, Ville, CodePostal);
-- Taille : 200 MB

Augmentation : 4x
```

**Impact** :
- Plus d'espace disque
- Plus de mémoire nécessaire pour le cache
- Sauvegardes plus volumineuses

### 2. ❌ Ralentissement des écritures

Comme tout index, plus il est volumineux, plus il est coûteux à maintenir.

**INSERT/UPDATE/DELETE** :
```sql
INSERT INTO Clients (...) VALUES (...);

-- Sans INCLUDE : Met à jour index de 50 MB
-- Avec INCLUDE : Met à jour index de 200 MB
-- 4x plus de données à écrire
```

### 3. ❌ Duplication des données

Les colonnes INCLUDE sont **dupliquées** : une fois dans la table, une fois dans l'index.

**Exemple** :
```
Table Clients : 1 GB
Index avec INCLUDE (5 colonnes) : 500 MB

Total : 1.5 GB (au lieu de 1 GB sans index)
Duplication : 50%
```

### 4. ❌ Risque de sur-optimisation

Il est tentant de mettre beaucoup de colonnes en INCLUDE "au cas où".

**Problème** :
```sql
-- ❌ MAUVAIS : Trop de colonnes en INCLUDE
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Col1, Col2, Col3, Col4, Col5, Col6, Col7, Col8, Col9, Col10);

-- L'index devient énorme
-- Coût de maintenance élevé
-- Bénéfice marginal
```

**Règle** : N'incluez que les colonnes **vraiment utilisées** dans vos requêtes fréquentes.

## Quand Utiliser INCLUDE ?

### ✅ Utilisez INCLUDE quand :

#### 1. Requêtes fréquentes avec Key Lookups

**Symptôme** : Vous voyez beaucoup de Key Lookups dans les plans d'exécution.

```sql
-- Requête fréquente (1000 fois/seconde)
SELECT Nom, Prenom, Telephone
FROM Clients
WHERE Email = 'user@email.com';

-- ✅ Solution : INCLUDE
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom, Telephone);
```

#### 2. Colonnes dans SELECT mais pas dans WHERE

**Principe** : Colonnes filtrées (WHERE) → Colonnes clés ; Colonnes affichées (SELECT) → INCLUDE.

```sql
-- WHERE : ClientID, Statut → Colonnes clés
-- SELECT : DateCommande, MontantTotal → INCLUDE

CREATE INDEX IX_Commandes_Client_Statut
ON Commandes (ClientID, Statut)
INCLUDE (DateCommande, MontantTotal);
```

#### 3. Colonnes larges (NVARCHAR, TEXT, etc.)

Pour éviter la limite de 900 octets :

```sql
-- Adresse est large (1000 octets)
-- ✅ Mettez-la en INCLUDE
CREATE INDEX IX_Clients_Ville
ON Clients (Ville)
INCLUDE (Adresse);
```

#### 4. Requêtes retournant beaucoup de lignes

Plus une requête retourne de lignes, plus les Key Lookups sont coûteux.

```sql
-- Requête retournant 50 000 lignes
SELECT * FROM Produits WHERE CategorieID = 10;

-- Sans INCLUDE : 50 000 Key Lookups
-- Avec INCLUDE : 0 Key Lookup

CREATE INDEX IX_Produits_Categorie
ON Produits (CategorieID)
INCLUDE (Nom, Prix, Stock, Description);
```

#### 5. Requêtes critiques pour les performances

Pour les requêtes **ultra-fréquentes** ou **critiques** pour l'application :

```sql
-- Page d'accueil : requête exécutée 10 000 fois/minute
-- Optimisation maximale nécessaire
CREATE INDEX IX_Produits_Actifs_Categorie
ON Produits (CategorieID)
INCLUDE (Nom, Prix, ImageURL, Stock)
WHERE Actif = 1;
```

### ❌ N'utilisez PAS INCLUDE quand :

#### 1. Requête ne retourne que les colonnes clés

```sql
-- Requête
SELECT ClientID FROM Clients WHERE Email = 'user@email.com';

-- ❌ INUTILE : INCLUDE n'apporte rien
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom);

-- ✅ BON : Pas besoin d'INCLUDE
CREATE INDEX IX_Clients_Email
ON Clients (Email);
```

#### 2. Table petite (< 10 000 lignes)

Sur une petite table, les Key Lookups ne sont pas si coûteux.

```sql
-- Table avec 1 000 lignes
-- ❌ Sur-optimisation inutile
CREATE INDEX IX_PetiteTable_Col1
ON PetiteTable (Col1)
INCLUDE (Col2, Col3, Col4, Col5, Col6);
```

#### 3. Colonnes très rarement utilisées

```sql
-- Colonne "Commentaire" utilisée dans 1% des requêtes
-- ❌ INUTILE : Alourdit l'index pour 1% des cas
CREATE INDEX IX_Produits_SKU
ON Produits (SKU)
INCLUDE (Nom, Prix, Stock, Commentaire);

-- ✅ MIEUX : Sans Commentaire
CREATE INDEX IX_Produits_SKU
ON Produits (SKU)
INCLUDE (Nom, Prix, Stock);
```

#### 4. Table avec beaucoup d'écritures

Si votre table reçoit beaucoup d'INSERT/UPDATE/DELETE, limitez la taille des index.

```sql
-- Table de logs : 10 000 INSERT/seconde
-- ❌ MAUVAIS : Index énorme avec INCLUDE
CREATE INDEX IX_Logs_Type
ON Logs (TypeLog)
INCLUDE (Message, Details, StackTrace, Utilisateur, DateLog);

-- ✅ MIEUX : Index minimal
CREATE INDEX IX_Logs_Type_Date
ON Logs (TypeLog, DateLog);
```

## Stratégies d'Utilisation

### Stratégie 1 : Analyser les requêtes fréquentes

**Processus** :
1. Identifiez vos 10 requêtes les plus fréquentes
2. Pour chaque requête :
   - Colonnes dans WHERE/JOIN → Colonnes clés
   - Colonnes dans SELECT uniquement → INCLUDE
3. Créez des index covering pour ces requêtes

**Exemple** :
```sql
-- Top 3 requêtes :

-- 1. Liste des commandes d'un client (50% du trafic)
SELECT CommandeID, DateCommande, MontantTotal, Statut
FROM Commandes
WHERE ClientID = @ClientID;

CREATE INDEX IX_Commandes_Client
ON Commandes (ClientID)
INCLUDE (DateCommande, MontantTotal, Statut);

-- 2. Détails d'une commande (30% du trafic)
SELECT * FROM Commandes WHERE CommandeID = @CommandeID;
-- Déjà couvert par la PRIMARY KEY (index clustered)

-- 3. Commandes récentes (20% du trafic)
SELECT ClientID, CommandeID, MontantTotal
FROM Commandes
WHERE DateCommande >= @DateDebut
ORDER BY DateCommande DESC;

CREATE INDEX IX_Commandes_Date
ON Commandes (DateCommande DESC)
INCLUDE (ClientID, MontantTotal);
```

### Stratégie 2 : Index progressif

Commencez simple, ajoutez INCLUDE si nécessaire.

**Étapes** :
1. Créez l'index de base sans INCLUDE
2. Surveillez les performances
3. Si vous voyez des Key Lookups fréquents → Ajoutez INCLUDE
4. Recréez l'index

**Exemple** :
```sql
-- Étape 1 : Index simple
CREATE INDEX IX_Clients_Email ON Clients (Email);

-- Observation : Beaucoup de Key Lookups sur (Nom, Prenom)

-- Étape 2 : Suppression et recréation avec INCLUDE
DROP INDEX IX_Clients_Email ON Clients;
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom);
```

### Stratégie 3 : INCLUDE sélectif par requête

Créez plusieurs index avec INCLUDE différents pour différentes requêtes.

**Exemple** :
```sql
-- Requête 1 : Infos de base
SELECT Nom, Prenom FROM Clients WHERE Email = @Email;

CREATE INDEX IX_Clients_Email_Base
ON Clients (Email)
INCLUDE (Nom, Prenom);

-- Requête 2 : Infos complètes pour l'administration
SELECT Nom, Prenom, Telephone, Adresse, Ville, DateInscription
FROM Clients
WHERE Email = @Email;

CREATE INDEX IX_Clients_Email_Complet
ON Clients (Email)
INCLUDE (Nom, Prenom, Telephone, Adresse, Ville, DateInscription);

-- Attention : Redondance, évaluez le coût vs bénéfice
```

### Stratégie 4 : Combiner avec index filtrés

INCLUDE est très puissant combiné avec des index filtrés.

**Exemple** :
```sql
-- 90% des requêtes portent sur les produits actifs
-- 10% sur tous les produits

-- Index filtré avec INCLUDE pour le cas fréquent
CREATE INDEX IX_Produits_Actifs_SKU
ON Produits (SKU)
INCLUDE (Nom, Prix, Stock, Description, CategorieID)
WHERE Actif = 1;

-- Taille : Très petit (10% de la table)
-- Performance : Maximale (covering index)
-- Coût : Minimal (maintenance sur 10% seulement)
```

## Comparaison : Avec et Sans INCLUDE

### Scénario : Application e-commerce

```sql
-- Table Produits : 1 million de lignes
CREATE TABLE Produits (
    ProduitID INT PRIMARY KEY,
    SKU NVARCHAR(50),
    Nom NVARCHAR(200),
    Description NVARCHAR(MAX),
    Prix DECIMAL(10,2),
    Stock INT,
    CategorieID INT,
    MarqueID INT,
    Actif BIT
);

-- Requête fréquente (recherche produit)
SELECT ProduitID, Nom, Prix, Stock
FROM Produits
WHERE SKU = 'LAP-2024-001';
```

### Option 1 : Index sans INCLUDE

```sql
CREATE INDEX IX_Produits_SKU ON Produits (SKU);
```

**Plan d'exécution** :
```
1. Index Seek sur IX_Produits_SKU
   → Trouve ProduitID = 12345

2. Key Lookup (Clustered Index Seek)
   → Va chercher Nom, Prix, Stock dans la table

Total : 2 opérations
Lectures : ~5-7 pages
Temps : 2-3 ms
```

### Option 2 : Index avec INCLUDE

```sql
CREATE INDEX IX_Produits_SKU
ON Produits (SKU)
INCLUDE (Nom, Prix, Stock);
```

**Plan d'exécution** :
```
1. Index Seek sur IX_Produits_SKU
   → Trouve directement : ProduitID, SKU, Nom, Prix, Stock

Total : 1 opération
Lectures : ~2-3 pages
Temps : 0.5-1 ms
```

### Comparaison chiffrée

| Métrique | Sans INCLUDE | Avec INCLUDE | Différence |
|----------|--------------|--------------|------------|
| **Opérations** | 2 | 1 | 50% moins |
| **Lectures** | 5-7 pages | 2-3 pages | 60% moins |
| **Temps** | 2-3 ms | 0.5-1 ms | 70% plus rapide |
| **Taille index** | 50 MB | 150 MB | 3x plus grand |
| **Coût INSERT** | Normal | +30% | Plus coûteux |

**Conclusion** : INCLUDE améliore considérablement les lectures, mais coûte en espace et écritures.

## Limites Techniques

### 1. Nombre maximum de colonnes INCLUDE

**Limite** : Pas de limite stricte, mais pratique : 10-20 colonnes maximum.

**Recommandation** : Limitez-vous aux colonnes réellement nécessaires.

### 2. Pas de limite de taille pour INCLUDE

Contrairement aux colonnes clés (900 octets), les colonnes INCLUDE n'ont **pas de limite de taille**.

```sql
-- ✅ AUTORISÉ : Colonnes larges en INCLUDE
CREATE INDEX IX_Documents_Reference
ON Documents (Reference)
INCLUDE (
    Titre NVARCHAR(500),           -- 1000 octets
    Contenu NVARCHAR(MAX),          -- Illimité
    Metadata NVARCHAR(2000)         -- 4000 octets
);
-- Pas de limite pour INCLUDE
```

### 3. Uniquement sur index non-clustered

INCLUDE est disponible **uniquement pour les index non-clustered**.

```sql
-- ❌ ERREUR : Pas d'INCLUDE sur clustered
CREATE CLUSTERED INDEX IX_Clients_ClientID
ON Clients (ClientID)
INCLUDE (Nom, Email);
-- Erreur de syntaxe

-- ✅ BON : INCLUDE sur non-clustered
CREATE NONCLUSTERED INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, ClientID);
```

**Pourquoi ?** L'index clustered **EST** la table. Toutes les colonnes sont déjà présentes.

### 4. Les colonnes INCLUDE ne peuvent pas être utilisées dans WHERE

Les colonnes INCLUDE ne sont **pas dans la structure de recherche**.

```sql
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Ville);

-- ✅ Efficace : WHERE sur Email (colonne clé)
SELECT * FROM Clients WHERE Email = 'user@email.com';

-- ❌ INEFFICACE : WHERE sur Ville (colonne INCLUDE)
SELECT * FROM Clients WHERE Ville = 'Paris';
-- Index Scan ou Table Scan (pas optimisable)
```

**Si vous filtrez sur Ville**, mettez-la dans les colonnes clés :
```sql
CREATE INDEX IX_Clients_Ville_Email
ON Clients (Ville, Email);
```

## Bonnes Pratiques

### ✅ À FAIRE

#### 1. Identifiez les colonnes pour INCLUDE

**Règle simple** :
- Colonnes dans WHERE, JOIN, ORDER BY → **Colonnes clés**
- Colonnes dans SELECT uniquement → **INCLUDE**

```sql
-- Requête
SELECT Nom, Prenom, Telephone     -- ← INCLUDE
FROM Clients
WHERE Email = 'user@email.com'    -- ← Colonne clé
  AND Actif = 1;                  -- ← Colonne clé

-- Index optimal
CREATE INDEX IX_Clients_Email_Actif
ON Clients (Email, Actif)
INCLUDE (Nom, Prenom, Telephone);
```

#### 2. Commencez minimal, ajoutez si nécessaire

```sql
-- ✅ Démarrage minimal
CREATE INDEX IX_Clients_Email ON Clients (Email);

-- Observez les performances
-- Si beaucoup de Key Lookups, ajoutez INCLUDE

-- ✅ Ajout progressif
DROP INDEX IX_Clients_Email ON Clients;
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom);
```

#### 3. Documentez les colonnes INCLUDE

```sql
-- ✅ BON : Commentaire expliquant pourquoi
-- Index covering pour la requête de recherche client
-- Inclut Nom, Prenom, Telephone pour éviter Key Lookup
-- Utilisé par : RecherchClient API (80% du trafic)
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom, Telephone);
```

#### 4. Limitez le nombre de colonnes INCLUDE

```sql
-- ✅ BON : 3-5 colonnes les plus utilisées
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Nom, Prenom, Telephone);

-- ⚠️ ATTENTION : 10+ colonnes
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Col1, Col2, Col3, Col4, Col5, Col6, Col7, Col8, Col9, Col10);
-- Index très volumineux, évaluez le coût
```

#### 5. Combinez avec index filtrés pour optimiser

```sql
-- ✅ EXCELLENT : Index filtré + INCLUDE
CREATE INDEX IX_Commandes_EnCours
ON Commandes (ClientID, DateCommande)
INCLUDE (MontantTotal, Statut, Adresse)
WHERE Statut IN ('En cours', 'En préparation');

-- Petit, rapide, covering pour les cas fréquents
```

### ❌ À ÉVITER

#### 1. N'incluez pas toutes les colonnes

```sql
-- ❌ MAUVAIS : Toutes les colonnes en INCLUDE
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Col1, Col2, Col3, ..., Col50);

-- L'index devient aussi gros que la table !
```

#### 2. N'incluez pas les colonnes déjà dans les clés

```sql
-- ❌ REDONDANT
CREATE INDEX IX_Clients_Email_Ville
ON Clients (Email, Ville)
INCLUDE (Email, Ville);  -- Déjà dans les clés !

-- ✅ BON
CREATE INDEX IX_Clients_Email_Ville
ON Clients (Email, Ville)
INCLUDE (Nom, Prenom);
```

#### 3. N'incluez pas des colonnes rarement utilisées

```sql
-- Colonne "Commentaire" utilisée dans 0.1% des requêtes
-- ❌ MAUVAIS : Inclure quand même
CREATE INDEX IX_Produits_SKU
ON Produits (SKU)
INCLUDE (Nom, Prix, Commentaire);  -- Commentaire inutile
```

#### 4. Ne mettez pas de colonnes de filtrage en INCLUDE

```sql
-- ❌ MAUVAIS : Ville est filtrée mais en INCLUDE
CREATE INDEX IX_Clients_Email
ON Clients (Email)
INCLUDE (Ville);

-- Requête
SELECT * FROM Clients WHERE Email = '...' AND Ville = 'Paris';
-- Inefficace sur Ville

-- ✅ BON : Ville dans les clés
CREATE INDEX IX_Clients_Email_Ville
ON Clients (Email, Ville)
INCLUDE (Nom, Prenom);
```

## Exemple Complet : Système de Blog

**Contexte** : Plateforme de blogs avec millions d'articles.

### Tables

```sql
CREATE TABLE Articles (
    ArticleID INT IDENTITY(1,1) PRIMARY KEY,
    AuteurID INT NOT NULL,
    Titre NVARCHAR(500) NOT NULL,
    Resume NVARCHAR(2000),
    Contenu NVARCHAR(MAX),
    DatePublication DATETIME2 NOT NULL,
    DateModification DATETIME2,
    NombreVues INT DEFAULT 0,
    Statut NVARCHAR(20) NOT NULL,  -- 'Brouillon', 'Publié', 'Archivé'
    Tags NVARCHAR(500),
    Categorie NVARCHAR(100)
);
```

### Requêtes fréquentes

```sql
-- Requête 1 (40%) : Articles publiés d'un auteur
SELECT ArticleID, Titre, Resume, DatePublication, NombreVues
FROM Articles
WHERE AuteurID = @AuteurID AND Statut = 'Publié'
ORDER BY DatePublication DESC;

-- Requête 2 (30%) : Articles récents publiés (page d'accueil)
SELECT ArticleID, Titre, Resume, AuteurID, DatePublication, Categorie
FROM Articles
WHERE Statut = 'Publié' AND DatePublication >= DATEADD(day, -30, GETDATE())
ORDER BY DatePublication DESC;

-- Requête 3 (20%) : Recherche par titre
SELECT ArticleID, Titre, Resume, AuteurID, DatePublication
FROM Articles
WHERE Titre LIKE '%' + @Mot + '%' AND Statut = 'Publié';

-- Requête 4 (10%) : Articles d'une catégorie
SELECT ArticleID, Titre, Resume, AuteurID, DatePublication, NombreVues
FROM Articles
WHERE Categorie = @Categorie AND Statut = 'Publié'
ORDER BY NombreVues DESC;
```

### Stratégie d'indexation avec INCLUDE

```sql
-- Index 1 : Pour requête 1 (40%)
CREATE INDEX IX_Articles_Auteur_Statut_Date
ON Articles (AuteurID, Statut, DatePublication DESC)
INCLUDE (Titre, Resume, NombreVues);

-- Index 2 : Pour requête 2 (30%)
CREATE INDEX IX_Articles_Publies_Date
ON Articles (DatePublication DESC)
INCLUDE (Titre, Resume, AuteurID, Categorie)
WHERE Statut = 'Publié' AND DatePublication >= '2024-01-01';
-- Index filtré + INCLUDE : Très efficace

-- Index 3 : Pour requête 4 (10%)
CREATE INDEX IX_Articles_Categorie_Publies_Vues
ON Articles (Categorie, NombreVues DESC)
INCLUDE (Titre, Resume, AuteurID, DatePublication)
WHERE Statut = 'Publié';

-- Note : Requête 3 (recherche texte) nécessite Full-Text Search
-- Hors scope pour les index standards
```

### Résultats

| Aspect | Avant | Après | Amélioration |
|--------|-------|-------|--------------|
| **Requête 1** | 150 ms | 8 ms | 19x plus rapide |
| **Requête 2** | 500 ms | 12 ms | 42x plus rapide |
| **Requête 4** | 80 ms | 5 ms | 16x plus rapide |
| **Espace index** | 200 MB | 650 MB | 3.25x plus grand |
| **Temps INSERT** | 2 ms | 5 ms | 2.5x plus lent |

**Bilan** :
- ✅ Lectures : Drastiquement améliorées
- ⚠️ Écritures : Légèrement ralenties
- ⚠️ Espace : Augmenté mais acceptable
- ✅ Expérience utilisateur : Excellente

## Résumé et Points Clés

### 🎯 Concepts essentiels

1. **INCLUDE = Colonnes au niveau feuilles uniquement**
   - Pas dans la structure de navigation (niveaux supérieurs)
   - Disponibles quand vous arrivez au résultat

2. **Covering Index = Toutes les colonnes nécessaires dans l'index**
   - Créé efficacement avec INCLUDE
   - Évite les Key Lookups coûteux

3. **Règle de décision : WHERE vs SELECT**
   - Colonnes filtrées (WHERE, JOIN) → **Colonnes clés**
   - Colonnes affichées (SELECT) → **INCLUDE**

4. **Avantages**
   - ⚡ Performances : Élimine les Key Lookups
   - 📦 Structure efficace : Navigation légère
   - 🔧 Contourne la limite de 900 octets

5. **Coûts**
   - 💾 Index plus volumineux
   - ✍️ Écritures plus lentes
   - 📊 Duplication des données

### ✅ Checklist de décision

Utilisez INCLUDE si :

- [ ] La requête retourne des colonnes non filtrées
- [ ] Vous voyez des Key Lookups dans le plan d'exécution
- [ ] La requête est fréquente (> 100 fois/seconde)
- [ ] La requête retourne beaucoup de lignes (> 100)
- [ ] Les colonnes sont larges (> 100 octets)
- [ ] Le gain en lectures justifie le coût en espace

### 📋 Syntaxes à retenir

```sql
-- Index simple avec INCLUDE
CREATE INDEX IX_Table_Colonne
ON Table (Colonne)
INCLUDE (Col1, Col2, Col3);

-- Index composite avec INCLUDE
CREATE INDEX IX_Table_AB
ON Table (A, B)
INCLUDE (C, D, E);

-- Index unique avec INCLUDE
CREATE UNIQUE INDEX IX_Table_Unique
ON Table (Email)
INCLUDE (Nom, Prenom);

-- Index filtré avec INCLUDE
CREATE INDEX IX_Table_Actif
ON Table (DateCreation)
INCLUDE (Nom, Statut, Montant)
WHERE Actif = 1;
```

## Conclusion

La clause **INCLUDE** est un outil puissant pour créer des **covering index** performants. Elle permet d'éviter les coûteux **Key Lookups** tout en gardant une structure d'index efficace.

**La règle d'or** :
> Mettez dans les colonnes clés ce que vous filtrez (WHERE, JOIN, ORDER BY), et dans INCLUDE ce que vous affichez (SELECT).

Utilisez INCLUDE avec discernement :
- ✅ Pour les requêtes fréquentes et critiques
- ✅ Quand les Key Lookups sont nombreux
- ⚠️ En gardant un œil sur la taille de l'index
- ⚠️ En équilibrant lectures vs écritures
