# 6.3.3 L'interblocage (Deadlock) : Concept et résolution

## Introduction

Dans la section précédente, nous avons vu que le **blocage (blocking)** est un comportement normal où une transaction attend qu'une autre libère un verrou. Mais que se passe-t-il lorsque **deux transactions s'attendent mutuellement** et qu'aucune ne peut progresser ? C'est ce qu'on appelle un **interblocage** ou **deadlock**.

Un deadlock est une situation problématique qui nécessite une intervention pour être résolue. Heureusement, SQL Server est capable de détecter et de résoudre automatiquement ces situations, mais au prix de l'annulation d'une des transactions.

Dans cette section, nous allons comprendre :
- Ce qu'est un deadlock
- Comment il se produit
- Comment SQL Server le détecte et le résout
- Comment prévenir les deadlocks

---

## Qu'est-ce qu'un Deadlock (Interblocage) ?

### Définition

Un **deadlock** se produit lorsque deux transactions (ou plus) se bloquent mutuellement de manière circulaire, chacune attendant que l'autre libère un verrou. Aucune des transactions ne peut progresser car elles sont dans une impasse.

### Analogie : L'intersection bloquée

Imaginez une intersection à quatre voies où :
- Une voiture du **Nord** veut aller au Sud, mais la route est bloquée par une voiture de l'**Est**
- La voiture de l'**Est** veut aller à l'Ouest, mais la route est bloquée par une voiture du **Sud**
- La voiture du **Sud** veut aller au Nord, mais la route est bloquée par une voiture de l'**Ouest**
- La voiture de l'**Ouest** veut aller à l'Est, mais la route est bloquée par la voiture du **Nord**

Personne ne peut avancer ! C'est une impasse totale. La seule solution : demander à l'une des voitures de reculer.

### Différence entre Blocking et Deadlock

| Blocking | Deadlock |
|----------|----------|
| Une transaction attend qu'une autre finisse | Deux transactions s'attendent mutuellement |
| **Situation temporaire** : ça va se débloquer | **Situation permanente** : ça ne se débloquera jamais seul |
| Comportement **normal** | Comportement **anormal** à éviter |
| Résolution naturelle (attente) | Résolution forcée (annulation d'une transaction) |

---

## Comment se produit un Deadlock ?

Un deadlock nécessite quatre conditions simultanées (appelées les **quatre conditions de Coffman**) :

1. **Exclusion mutuelle** : Les ressources ne peuvent être utilisées que par une transaction à la fois
2. **Hold and Wait** : Une transaction garde un verrou et attend d'en obtenir un autre
3. **Pas de préemption** : Un verrou ne peut être retiré de force (il doit être libéré volontairement)
4. **Attente circulaire** : Il existe une chaîne circulaire de transactions qui s'attendent

### Scénario classique d'un Deadlock

Voici le scénario le plus courant :

**Situation initiale :**
- **Transaction A** veut modifier la Table1, puis la Table2
- **Transaction B** veut modifier la Table2, puis la Table1

**Déroulement chronologique :**

```
Temps 1 : Transaction A verrouille Table1
Temps 2 : Transaction B verrouille Table2
Temps 3 : Transaction A tente de verrouiller Table2 → BLOQUÉE (attendant Transaction B)
Temps 4 : Transaction B tente de verrouiller Table1 → BLOQUÉE (attendant Transaction A)

Résultat : DEADLOCK !
```

### Exemple concret en T-SQL

```sql
-- ===== Transaction A =====
BEGIN TRANSACTION;

-- Étape 1 : Verrouille un employé
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
-- Verrou exclusif sur EmployeID = 1

-- Petite pause (simulation)...
WAITFOR DELAY '00:00:05';

-- Étape 2 : Tente de verrouiller un département
UPDATE Departements SET Budget = 100000 WHERE DepartementID = 10;
-- Attend que Transaction B libère le département → BLOQUÉE

COMMIT;
```

```sql
-- ===== Transaction B (exécutée en parallèle) =====
BEGIN TRANSACTION;

-- Étape 1 : Verrouille un département
UPDATE Departements SET Budget = 120000 WHERE DepartementID = 10;
-- Verrou exclusif sur DepartementID = 10

-- Petite pause (simulation)...
WAITFOR DELAY '00:00:05';

-- Étape 2 : Tente de verrouiller un employé
UPDATE Employes SET Salaire = 4000 WHERE EmployeID = 1;
-- Attend que Transaction A libère l'employé → BLOQUÉE

COMMIT;
```

**Résultat :** Les deux transactions sont bloquées mutuellement. SQL Server détecte le deadlock et en annule une.

## Comment SQL Server détecte-t-il un Deadlock ?

### Le Moniteur de Deadlock (Deadlock Monitor)

SQL Server possède un processus interne appelé le **moniteur de deadlock** qui s'exécute automatiquement toutes les **5 secondes** environ.

**Son rôle :**
1. Analyser les transactions en cours
2. Identifier les chaînes d'attente circulaires
3. Détecter les situations de deadlock

### Graphe d'attente

Le moniteur construit un **graphe d'attente** (wait-for graph) :
- Les **nœuds** représentent les transactions
- Les **arêtes** représentent les dépendances (qui attend qui)

Si le graphe contient un **cycle**, c'est un deadlock !

**Exemple de graphe :**
```
Transaction A → attend → Transaction B
Transaction B → attend → Transaction A
```

Ce cycle indique un deadlock.

---

## Comment SQL Server résout-il un Deadlock ?

### Choix de la victime (Deadlock Victim)

Lorsqu'un deadlock est détecté, SQL Server doit choisir une transaction à **annuler** pour briser le cycle. Cette transaction est appelée la **victime du deadlock**.

**Critères de sélection :**
1. **Priorité** : Transaction avec la priorité la plus basse (par défaut, toutes sont égales)
2. **Coût** : Transaction qui a effectué le moins de travail (moins coûteux à annuler)

### Que se passe-t-il pour la victime ?

1. La transaction victime est **annulée** (ROLLBACK automatique)
2. Tous ses verrous sont **libérés**
3. Un **message d'erreur 1205** est renvoyé à l'application
4. Les autres transactions peuvent **continuer**

### Message d'erreur typique

```
Msg 1205, Level 13, State 51, Line 1
Transaction (Process ID 52) was deadlocked on lock resources with another process
and has been chosen as the deadlock victim. Rerun the transaction.
```

**Traduction :** "Votre transaction a été choisie comme victime d'un deadlock et a été annulée. Veuillez réessayer."

## Impact sur l'application

### Gestion de l'erreur 1205

L'application doit être capable de **gérer** cette erreur et de **réessayer** la transaction :

```sql
-- Pseudo-code (logique applicative)
DECLARE @Tentatives INT = 0;
DECLARE @MaxTentatives INT = 3;
DECLARE @Success BIT = 0;

WHILE @Tentatives < @MaxTentatives AND @Success = 0
BEGIN
    BEGIN TRY
        -- Tenter la transaction
        BEGIN TRANSACTION;
        UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
        UPDATE Departements SET Budget = 100000 WHERE DepartementID = 10;
        COMMIT;

        SET @Success = 1;
    END TRY
    BEGIN CATCH
        -- ⚠️ Une victime de deadlock est DÉJÀ annulée par SQL Server (@@TRANCOUNT = 0
        --    au moment du CATCH). On ne fait donc un ROLLBACK que s'il reste une
        --    transaction ouverte ; sinon, ce ROLLBACK lèverait l'erreur 3903
        --    (« The ROLLBACK TRANSACTION request has no corresponding BEGIN TRANSACTION »).
        IF @@TRANCOUNT > 0
            ROLLBACK;

        -- Si deadlock détecté (erreur 1205)
        IF ERROR_NUMBER() = 1205
        BEGIN
            SET @Tentatives = @Tentatives + 1;
            -- Attendre un peu avant de réessayer
            WAITFOR DELAY '00:00:01';
        END
        ELSE
        BEGIN
            -- Autre erreur, propager
            THROW;
        END
    END CATCH
END
```

## Analyse d'un Deadlock

### Le Deadlock Graph

SQL Server peut capturer un **graphe de deadlock** qui montre visuellement ce qui s'est passé.

**Activation de la capture :**

```sql
-- Activer le trace flag 1222 (informations détaillées dans le log d'erreurs)
DBCC TRACEON(1222, -1);

-- Ou activer dans les propriétés du serveur
```

Le graphe montre :
- Les transactions impliquées
- Les ressources verrouillées
- L'ordre des opérations
- La victime choisie

### Exemple de lecture d'un graphe

```
Transaction A (victimized)
  └─ Détient : Verrou sur Employes (EmployeID = 1)
  └─ Attend : Verrou sur Departements (DepartementID = 10)

Transaction B
  └─ Détient : Verrou sur Departements (DepartementID = 10)
  └─ Attend : Verrou sur Employes (EmployeID = 1)
```

**Conclusion :** Les deux transactions s'attendent mutuellement → Deadlock !

## Comment prévenir les Deadlocks ?

Les deadlocks ne peuvent jamais être complètement éliminés, mais on peut grandement réduire leur probabilité en suivant de bonnes pratiques.

### 1. Accéder aux ressources dans le même ordre

**Principe :** Si toutes les transactions accèdent aux tables dans le même ordre, elles ne peuvent pas se bloquer mutuellement.

```sql
-- ❌ MAUVAIS : Ordres différents
-- Transaction A : Employes → Departements
-- Transaction B : Departements → Employes
-- → Risque de deadlock

-- ✅ BON : Même ordre
-- Transaction A : Employes → Departements
-- Transaction B : Employes → Departements
-- → Pas de deadlock possible
```

**Exemple corrigé :**

```sql
-- ===== Transaction A =====
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;        -- D'abord Employes
UPDATE Departements SET Budget = 100000 WHERE DepartementID = 10;  -- Puis Departements
COMMIT;

-- ===== Transaction B =====
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 4000 WHERE EmployeID = 2;        -- D'abord Employes
UPDATE Departements SET Budget = 120000 WHERE DepartementID = 11;  -- Puis Departements
COMMIT;

-- Pas de deadlock : même si elles s'exécutent en parallèle, l'une attendra l'autre
```

### 2. Garder les transactions courtes

Plus une transaction dure longtemps, plus elle garde des verrous longtemps, augmentant le risque de deadlock.

```sql
-- ❌ MAUVAIS
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
-- ... 10 secondes d'attente ou de traitement ...
UPDATE Departements SET Budget = 100000 WHERE DepartementID = 10;
COMMIT;

-- ✅ BON
BEGIN TRANSACTION;
UPDATE Employes SET Salaire = 3500 WHERE EmployeID = 1;
UPDATE Departements SET Budget = 100000 WHERE DepartementID = 10;
COMMIT;  -- Transaction rapide
```

### 3. Utiliser un niveau d'isolation approprié

Les niveaux d'isolation plus élevés (comme SERIALIZABLE) gardent les verrous plus longtemps et augmentent le risque de deadlock.

```sql
-- Si possible, utiliser READ COMMITTED SNAPSHOT (RCSI)
-- qui réduit les conflits de lecture/écriture
```

### 4. Utiliser des index appropriés

Des requêtes lentes = des verrous maintenus plus longtemps = plus de risque de deadlock.

```sql
-- Sans index : Scan de table (lent, beaucoup de verrous)
UPDATE Employes SET Salaire = 3500 WHERE Nom = 'Dupont';

-- Avec index sur Nom : Seek (rapide, peu de verrous)
CREATE INDEX IX_Employes_Nom ON Employes(Nom);
```

### 5. Réduire le nombre de lignes affectées

Moins de lignes = moins de verrous = moins de risque de deadlock.

```sql
-- ❌ MAUVAIS : Verrouille toute la table
UPDATE Employes SET Salaire = Salaire * 1.1;

-- ✅ BON : Traiter par lots
DECLARE @BatchSize INT = 1000;
WHILE 1=1
BEGIN
    BEGIN TRANSACTION;
    UPDATE TOP (@BatchSize) Employes
    SET Salaire = Salaire * 1.1
    WHERE StatutMiseAJour = 0;

    IF @@ROWCOUNT = 0 BREAK;
    COMMIT;
END
```

### 6. Utiliser NOLOCK avec précaution

Le hint `WITH (NOLOCK)` permet de lire sans verrous, mais peut causer des lectures sales (Dirty Reads).

```sql
-- Si les données exactes ne sont pas critiques
SELECT * FROM Employes WITH (NOLOCK);
-- Pas de verrou partagé → réduit les conflits
```

**⚠️ Attention :** À utiliser uniquement pour des lectures non critiques (rapports, statistiques approximatives).

### 7. Définir une priorité de deadlock

On peut influencer le choix de la victime en définissant une priorité :

```sql
-- Transaction moins importante (sera choisie comme victime en priorité)
SET DEADLOCK_PRIORITY LOW;
BEGIN TRANSACTION;
-- ... opérations ...
COMMIT;

-- Transaction critique (ne sera pas choisie si possible)
SET DEADLOCK_PRIORITY HIGH;
BEGIN TRANSACTION;
-- ... opérations critiques ...
COMMIT;
```

**Valeurs possibles :** LOW (-5), NORMAL (0 - par défaut), HIGH (5)

## Stratégies de retry (Nouvelle tentative)

### Implémentation d'une logique de retry

Dans le code applicatif (C#, Java, Python, etc.), implémenter une stratégie de nouvelle tentative :

**Pseudo-code :**
```
MaxTentatives = 3
Tentative = 0

Tant que Tentative < MaxTentatives:
    Tenter:
        Exécuter la transaction
        Sortir de la boucle (succès)
    Capturer:
        Si erreur = 1205 (Deadlock):
            Tentative += 1
            Attendre un délai aléatoire (100-500ms)
            Réessayer
        Sinon:
            Lever l'erreur (autre problème)

Si Tentative = MaxTentatives:
    Enregistrer l'erreur dans les logs
    Informer l'utilisateur
```

### Délai aléatoire (Random Backoff)

Il est important d'ajouter un **délai aléatoire** entre les tentatives pour éviter que les mêmes transactions se retrouvent à nouveau en deadlock immédiatement.

## Surveillance et Diagnostic

### Événements étendus (Extended Events)

SQL Server peut capturer automatiquement les deadlocks :

```sql
-- Créer une session d'événements étendus pour capturer les deadlocks
CREATE EVENT SESSION [CaptureDeadlocks] ON SERVER
ADD EVENT sqlserver.xml_deadlock_report
ADD TARGET package0.event_file(SET filename=N'C:\Logs\Deadlocks.xel')
WITH (STARTUP_STATE=ON);

-- Démarrer la session
ALTER EVENT SESSION [CaptureDeadlocks] ON SERVER STATE = START;
```

### Requêtes système pour analyser les deadlocks

```sql
-- Voir les derniers deadlocks capturés dans le système
SELECT
    XEvent.query('(event/data[@name="xml_report"]/value/deadlock)[1]') AS DeadlockGraph
FROM
(
    SELECT CAST(target_data AS XML) AS TargetData
    FROM sys.dm_xe_session_targets AS st
    INNER JOIN sys.dm_xe_sessions AS s ON s.address = st.event_session_address
    WHERE s.name = 'system_health'
) AS Data
CROSS APPLY TargetData.nodes ('//RingBufferTarget/event') AS XEventData(XEvent)
WHERE XEvent.value('@name', 'varchar(4000)') = 'xml_deadlock_report';
```

### Utilisation de SQL Server Profiler

L'outil **SQL Server Profiler** (ancien, mais encore utilisé) peut tracer les événements de deadlock en temps réel.

## Résumé

### Qu'est-ce qu'un Deadlock ?

- **Définition** : Situation où deux transactions s'attendent mutuellement de manière circulaire
- **Nature** : Problème anormal qui nécessite une intervention
- **Résolution** : SQL Server annule automatiquement une transaction (victime)
- **Impact** : La victime reçoit l'erreur 1205 et doit être réessayée

### Conditions d'un Deadlock

1. Exclusion mutuelle
2. Hold and Wait
3. Pas de préemption
4. Attente circulaire

### Prévention

1. ✅ Accéder aux ressources **dans le même ordre**
2. ✅ Garder les transactions **courtes**
3. ✅ Utiliser des **index appropriés**
4. ✅ Réduire le nombre de **lignes affectées**
5. ✅ Choisir le bon **niveau d'isolation**
6. ✅ Implémenter une **logique de retry**

### Diagnostic

- Activer la capture des deadlocks (Trace Flag 1222, Extended Events)
- Analyser les graphes de deadlock
- Identifier les patterns récurrents
- Optimiser les transactions problématiques

### Points clés

1. Les deadlocks **ne peuvent jamais être complètement éliminés**, mais peuvent être **réduits**
2. L'application **doit gérer** l'erreur 1205 et **réessayer** la transaction
3. La **conception** de la base de données et des transactions est cruciale
4. L'**ordre d'accès aux ressources** est le facteur le plus important
5. SQL Server fournit des **outils puissants** pour analyser et comprendre les deadlocks
