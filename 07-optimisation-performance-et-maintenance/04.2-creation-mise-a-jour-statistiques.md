# 7.4.2 Création et mise à jour des statistiques

## Introduction

Dans la section précédente, nous avons compris **pourquoi** les statistiques sont essentielles pour l'optimiseur de requêtes. Maintenant, nous allons apprendre **comment** créer et maintenir ces statistiques pour garantir que SQL Server dispose toujours d'informations précises sur vos données.

La bonne nouvelle ? SQL Server fait déjà beaucoup de travail automatiquement ! Mais il est important de comprendre comment cela fonctionne et quand vous devez intervenir manuellement pour garantir des performances optimales.

## Gestion automatique vs gestion manuelle

### Le rôle de SQL Server

SQL Server adopte une approche **"mains libres"** par défaut :
- Il crée automatiquement les statistiques quand nécessaire
- Il les met à jour automatiquement quand elles deviennent obsolètes
- Vous n'avez généralement pas besoin d'intervenir

### Quand intervenir manuellement ?

Dans certaines situations, vous devrez prendre les choses en main :
- ✅ Après un chargement massif de données
- ✅ Après des modifications importantes de structure
- ✅ Pour des tables critiques avec des patterns de données spécifiques
- ✅ Quand vous détectez des problèmes de performance liés aux statistiques
- ✅ Pour des colonnes très corrélées

### Analogie : L'entretien d'une voiture

Pensez aux statistiques comme à l'entretien d'une voiture :

**Entretien automatique (SQL Server) :**
- Comme un voyant d'huile qui s'allume automatiquement
- Fonctionne bien pour 90% des situations
- Pratique et sans effort

**Entretien manuel (Vous) :**
- Comme vérifier l'huile avant un long voyage
- Nécessaire dans des situations spécifiques
- Prévention proactive plutôt que réaction

## Les options de configuration

Avant de plonger dans les commandes, comprenons les options qui contrôlent le comportement automatique de SQL Server.

### AUTO_CREATE_STATISTICS

Cette option contrôle si SQL Server crée **automatiquement** des statistiques sur les colonnes utilisées dans les prédicats.

#### Vérifier le statut actuel

```sql
-- Voir si l'option est activée pour une base de données
SELECT name, is_auto_create_stats_on
FROM sys.databases
WHERE name = 'VotreBaseDeDonnees';
```

#### Activer ou désactiver

```sql
-- Activer (recommandé - valeur par défaut)
ALTER DATABASE VotreBaseDeDonnees
SET AUTO_CREATE_STATISTICS ON;

-- Désactiver (généralement déconseillé)
ALTER DATABASE VotreBaseDeDonnees
SET AUTO_CREATE_STATISTICS OFF;
```

#### Quand SQL Server crée-t-il des statistiques automatiquement ?

Avec cette option activée, SQL Server crée des statistiques lors de la **première utilisation** d'une colonne dans :
- Une clause **WHERE**
- Une clause **JOIN**
- Une clause **GROUP BY**
- Une clause **ORDER BY** (si pas d'index)

**Exemple :**
```sql
-- Table sans index ni statistiques sur la colonne Email
SELECT * FROM Clients WHERE Email = 'test@email.com';

-- À la première exécution, SQL Server :
-- 1. Détecte que Email est utilisé dans WHERE
-- 2. Crée automatiquement des statistiques sur Email
-- 3. Utilise ces statistiques pour optimiser la requête
-- 4. Les exécutions suivantes bénéficieront de ces statistiques
```

#### Recommandation

✅ **Laissez cette option activée** dans 99% des cas. C'est un filet de sécurité précieux.

### AUTO_UPDATE_STATISTICS

Cette option contrôle si SQL Server met à jour **automatiquement** les statistiques obsolètes.

#### Vérifier le statut actuel

```sql
SELECT name, is_auto_update_stats_on
FROM sys.databases
WHERE name = 'VotreBaseDeDonnees';
```

#### Activer ou désactiver

```sql
-- Activer (recommandé - valeur par défaut)
ALTER DATABASE VotreBaseDeDonnees
SET AUTO_UPDATE_STATISTICS ON;

-- Désactiver (peut être nécessaire dans certains cas spécifiques)
ALTER DATABASE VotreBaseDeDonnees
SET AUTO_UPDATE_STATISTICS OFF;
```

#### Rappel : Quand les statistiques sont-elles considérées obsolètes ?

SQL Server utilise un **seuil de modification** pour décider quand mettre à jour :

**Tables petites (< 500 lignes) :**
- Seuil = **500 modifications**

**Tables moyennes et grandes (≥ 500 lignes) :**
- Seuil = **500 + 20% du nombre de lignes**

**Exemples :**
```
Table de 1 000 lignes :
500 + (20% × 1 000) = 500 + 200 = 700 modifications

Table de 100 000 lignes :
500 + (20% × 100 000) = 500 + 20 000 = 20 500 modifications

Table de 10 000 000 lignes :
500 + (20% × 10 000 000) = 500 + 2 000 000 = 2 000 500 modifications !
```

#### Le problème des très grandes tables

Sur les tables avec des millions ou milliards de lignes, le seuil de 20% peut être **énorme**. Les statistiques peuvent rester obsolètes longtemps.

**Solution :** SQL Server 2016+ utilise un seuil **dynamique** plus intelligent qui s'adapte mieux aux grandes tables (environ √(nombre de lignes) × 1000).

#### Recommandation

✅ **Laissez cette option activée** dans la plupart des cas. Mais soyez conscient que pour de très grandes tables avec des modifications fréquentes, vous devrez peut-être mettre à jour manuellement.

### AUTO_UPDATE_STATISTICS_ASYNC

Cette option contrôle si les mises à jour de statistiques se font de manière **asynchrone** (en arrière-plan).

#### Le problème de la mise à jour synchrone

Par défaut (mode synchrone), quand SQL Server détecte que des statistiques sont obsolètes :
1. **La requête en cours est mise en pause** ⏸️
2. SQL Server met à jour les statistiques
3. La requête reprend avec les nouvelles statistiques

Cela peut causer des **latences imprévisibles** pour l'utilisateur !

#### La solution asynchrone

Avec le mode asynchrone activé :
1. **La requête continue** avec les anciennes statistiques ✅
2. SQL Server lance une mise à jour en arrière-plan
3. Les requêtes suivantes bénéficieront des nouvelles statistiques

#### Activer le mode asynchrone

```sql
ALTER DATABASE VotreBaseDeDonnees
SET AUTO_UPDATE_STATISTICS_ASYNC ON;
```

#### Avantages et inconvénients

**Avantages :**
- ✅ Pas de latence imprévisible pour les utilisateurs
- ✅ Meilleure expérience utilisateur
- ✅ Throughput plus prévisible

**Inconvénients :**
- ⚠️ La première requête après obsolescence utilise encore les anciennes stats
- ⚠️ Peut masquer des problèmes de performance

#### Recommandation

✅ **Activez cette option** pour les environnements de production où la latence prévisible est critique (applications web, API).

❌ **Gardez le mode synchrone** en développement pour détecter rapidement les problèmes de statistiques.

## Création manuelle de statistiques

### Pourquoi créer manuellement des statistiques ?

Dans la plupart des cas, SQL Server crée automatiquement les statistiques nécessaires. Mais vous pouvez vouloir créer des statistiques manuellement pour :

1. **Colonnes corrélées** : Créer des statistiques multi-colonnes
2. **Optimisation proactive** : Avant un problème de performance
3. **Contrôle total** : Spécifier exactement quelles colonnes suivre

### Syntaxe de base : CREATE STATISTICS

```sql
CREATE STATISTICS NomStatistiques
ON NomTable (Colonne1, [Colonne2], ...)
[WITH options];
```

### Exemples pratiques

#### Exemple 1 : Statistiques sur une seule colonne

```sql
-- Créer des statistiques sur la colonne DateNaissance
CREATE STATISTICS Stats_Clients_DateNaissance
ON Clients (DateNaissance);
```

**Quand l'utiliser :**
- Colonne fréquemment utilisée dans WHERE mais sans index
- Vous voulez contrôler explicitement les statistiques

#### Exemple 2 : Statistiques multi-colonnes

```sql
-- Créer des statistiques sur Pays ET Ville (colonnes corrélées)
CREATE STATISTICS Stats_Clients_Pays_Ville
ON Clients (Pays, Ville);
```

**Quand l'utiliser :**
- Colonnes utilisées ensemble dans WHERE
- Colonnes qui ont une **corrélation** (comme Pays et Ville)
- Améliore grandement les estimations de l'optimiseur

#### Exemple 3 : Statistiques avec échantillonnage personnalisé

```sql
-- Créer des statistiques en analysant 50% des données
CREATE STATISTICS Stats_Produits_Categorie
ON Produits (Categorie)
WITH SAMPLE 50 PERCENT;
```

**Quand l'utiliser :**
- Très grande table (échantillon complet trop long)
- Besoin de statistiques rapidement
- Distribution relativement uniforme

#### Exemple 4 : Statistiques avec analyse complète

```sql
-- Créer des statistiques en analysant TOUTES les données
CREATE STATISTICS Stats_Ventes_Montant
ON Ventes (Montant)
WITH FULLSCAN;
```

**Quand l'utiliser :**
- Table critique avec distribution complexe
- Besoin de la précision maximale
- Table de taille raisonnable (pas des milliards de lignes)

### Options disponibles

#### SAMPLE

Spécifie le pourcentage ou le nombre de lignes à échantillonner :

```sql
-- Échantillon de 25%
WITH SAMPLE 25 PERCENT

-- Échantillon de 10 000 lignes
WITH SAMPLE 10000 ROWS
```

**Par défaut :** SQL Server choisit automatiquement un échantillon approprié.

#### FULLSCAN

Analyse toutes les lignes de la table (100% des données) :

```sql
WITH FULLSCAN
```

**Avantage :** Précision maximale
**Inconvénient :** Plus lent sur grandes tables

#### NORECOMPUTE

Empêche la mise à jour automatique de ces statistiques :

```sql
WITH NORECOMPUTE
```

**Quand l'utiliser :**
- Très rare ! Généralement déconseillé
- Peut être utile pour des tables en lecture seule
- Vous gérez les mises à jour manuellement

**Attention :** Les statistiques deviendront obsolètes sans mise à jour !

### Voir les statistiques existantes

```sql
-- Voir toutes les statistiques d'une table
SELECT
    s.name AS StatisticName,
    s.stats_id,
    s.auto_created,
    s.user_created,
    STUFF((
        SELECT ', ' + c.name
        FROM sys.stats_columns sc
        JOIN sys.columns c ON sc.column_id = c.column_id
            AND sc.object_id = c.object_id
        WHERE sc.object_id = s.object_id
            AND sc.stats_id = s.stats_id
        ORDER BY sc.stats_column_id
        FOR XML PATH('')
    ), 1, 2, '') AS Columns
FROM sys.stats s
WHERE s.object_id = OBJECT_ID('Clients')
ORDER BY s.name;
```

**Interprétation des colonnes :**
- **auto_created = 1** : Créée automatiquement par SQL Server
- **user_created = 1** : Créée manuellement par vous
- **auto_created = 0 AND user_created = 0** : Statistiques d'index

## Mise à jour manuelle des statistiques

### Pourquoi mettre à jour manuellement ?

Même avec AUTO_UPDATE_STATISTICS activé, vous devrez parfois mettre à jour manuellement :

1. **Après un chargement massif** : Import de millions de lignes
2. **Après des modifications importantes** : Suppressions ou updates massifs
3. **Avant une opération critique** : Requête complexe importante
4. **Tables très grandes** : Le seuil automatique est trop élevé
5. **Problème de performance détecté** : Écarts importants dans les plans

### UPDATE STATISTICS : La commande principale

#### Syntaxe de base

```sql
UPDATE STATISTICS NomTable;
```

Cette commande met à jour **toutes** les statistiques de la table.

### Exemples pratiques

#### Exemple 1 : Mettre à jour toutes les statistiques d'une table

```sql
-- Mise à jour standard de toutes les statistiques
UPDATE STATISTICS Clients;
```

**Quand l'utiliser :**
- Après un chargement de données
- Quand vous détectez un problème de performance
- Maintenance régulière

#### Exemple 2 : Mettre à jour des statistiques spécifiques

```sql
-- Mettre à jour seulement les statistiques sur Ville
UPDATE STATISTICS Clients Stats_Clients_Ville;
```

**Quand l'utiliser :**
- Vous savez quelle colonne pose problème
- Optimisation ciblée plus rapide

#### Exemple 3 : Mise à jour avec FULLSCAN

```sql
-- Mise à jour en analysant 100% des données
UPDATE STATISTICS Clients
WITH FULLSCAN;
```

**Quand l'utiliser :**
- Table critique avec distribution complexe
- Après avoir détecté des estimations très inexactes
- Besoin de précision maximale

**Attention :** Peut être long sur de très grandes tables !

#### Exemple 4 : Mise à jour avec échantillonnage personnalisé

```sql
-- Mise à jour avec un échantillon de 30%
UPDATE STATISTICS Clients
WITH SAMPLE 30 PERCENT;
```

**Quand l'utiliser :**
- Compromis entre rapidité et précision
- Grandes tables où FULLSCAN est trop long

#### Exemple 5 : Mise à jour de toutes les tables d'une base

```sql
-- Mettre à jour les statistiques de TOUTES les tables
EXEC sp_updatestats;
```

**Quand l'utiliser :**
- Maintenance générale de la base
- Après une restauration de backup
- Problèmes de performance généralisés

**Attention :** Peut prendre du temps sur des bases volumineuses !

### Options avancées

#### RESAMPLE

Utilise le même taux d'échantillonnage que lors de la dernière mise à jour :

```sql
UPDATE STATISTICS Clients
WITH RESAMPLE;
```

**Avantage :** Cohérence avec les mises à jour précédentes

#### ALL | COLUMNS | INDEX

Spécifie quel type de statistiques mettre à jour :

```sql
-- Mettre à jour TOUTES les statistiques
UPDATE STATISTICS Clients WITH FULLSCAN, ALL;

-- Mettre à jour seulement les statistiques de colonnes
UPDATE STATISTICS Clients WITH FULLSCAN, COLUMNS;

-- Mettre à jour seulement les statistiques d'index
UPDATE STATISTICS Clients WITH FULLSCAN, INDEX;
```

### Vérifier quand les statistiques ont été mises à jour

```sql
-- Voir la date de dernière mise à jour des statistiques
SELECT
    t.name AS TableName,
    s.name AS StatisticName,
    STATS_DATE(s.object_id, s.stats_id) AS LastUpdated,
    DATEDIFF(DAY, STATS_DATE(s.object_id, s.stats_id), GETDATE()) AS DaysSinceUpdate
FROM sys.stats s
JOIN sys.tables t ON s.object_id = t.object_id
WHERE t.name = 'Clients'
ORDER BY LastUpdated;
```

**Interprétation :**
- **LastUpdated récent** (< 7 jours) : Statistiques probablement à jour ✅
- **LastUpdated ancien** (> 30 jours) : Vérifier si c'est normal ⚠️
- **LastUpdated NULL** : Statistiques jamais mises à jour ! ❌

## Stratégies de mise à jour

### Stratégie 1 : Laisser faire SQL Server (Recommandé)

**Pour qui :** La plupart des tables et des applications

**Approche :**
- ✅ AUTO_CREATE_STATISTICS = ON
- ✅ AUTO_UPDATE_STATISTICS = ON
- ✅ AUTO_UPDATE_STATISTICS_ASYNC = ON (production)
- 👀 Surveiller les plans d'exécution occasionnellement

**Intervention manuelle :**
- Seulement en cas de problème détecté
- Après des opérations massives

### Stratégie 2 : Maintenance proactive

**Pour qui :** Tables critiques, environnements haute performance

**Approche :**
1. **Surveillance régulière** des dates de mise à jour
2. **Mise à jour planifiée** pendant les fenêtres de maintenance
3. **Scripts de maintenance** automatisés

**Exemple de script de maintenance :**
```sql
-- Script à exécuter la nuit ou pendant les heures creuses
-- Mettre à jour les statistiques des tables critiques

UPDATE STATISTICS Clients WITH SAMPLE 50 PERCENT;
UPDATE STATISTICS Commandes WITH SAMPLE 50 PERCENT;
UPDATE STATISTICS Produits WITH FULLSCAN;  -- Petite table
```

### Stratégie 3 : Mise à jour après chargement de données

**Pour qui :** Tables avec ETL réguliers ou imports massifs

**Approche :**
```sql
-- 1. Désactiver les mises à jour automatiques pendant l'import
ALTER INDEX ALL ON Commandes DISABLE;

-- 2. Charger les données
BULK INSERT Commandes FROM 'data.csv' ...;

-- 3. Reconstruire les index
ALTER INDEX ALL ON Commandes REBUILD;

-- 4. Mettre à jour les statistiques
UPDATE STATISTICS Commandes WITH FULLSCAN;
```

**Pourquoi :**
- Évite les mises à jour multiples pendant l'import
- Garantit des statistiques précises après l'import
- Plus efficace que de laisser faire automatiquement

### Stratégie 4 : Gestion fine par table

**Pour qui :** DBA expérimentés, bases de données complexes

**Approche :**
- Tables petites/stables : AUTO_UPDATE + vérification mensuelle
- Tables moyennes/actives : AUTO_UPDATE + vérification hebdomadaire
- Tables grandes/critiques : Mises à jour manuelles planifiées

## Les pièges à éviter

### Piège 1 : Mettre à jour trop fréquemment

**Erreur :**
```sql
-- Mettre à jour après chaque transaction !
INSERT INTO Clients (...) VALUES (...);
UPDATE STATISTICS Clients WITH FULLSCAN;  -- ❌ MAUVAIS !
```

**Problème :**
- Overhead énorme
- Ralentit considérablement les opérations
- Les statistiques n'ont pas besoin d'être parfaites en temps réel

**Solution :**
Laissez SQL Server gérer automatiquement, ou planifiez des mises à jour périodiques raisonnables.

### Piège 2 : Utiliser FULLSCAN systématiquement

**Erreur :**
```sql
-- Sur une table de 100 millions de lignes
UPDATE STATISTICS GrandeTable WITH FULLSCAN;  -- ⚠️ Peut prendre des heures !
```

**Problème :**
- Très lent sur grandes tables
- Verrouille les ressources longtemps
- Souvent inutile (un bon échantillon suffit)

**Solution :**
```sql
-- Un échantillon de 10-30% suffit généralement
UPDATE STATISTICS GrandeTable WITH SAMPLE 20 PERCENT;
```

### Piège 3 : Oublier les statistiques après index

**Erreur :**
```sql
-- Créer un index
CREATE INDEX IX_Clients_Ville ON Clients(Ville);

-- Oublier que les statistiques peuvent être obsolètes !
-- Si la table était déjà grande, l'index utilise peut-être de vieilles stats
```

**Solution :**
```sql
-- Après création d'index, mettre à jour si nécessaire
CREATE INDEX IX_Clients_Ville ON Clients(Ville);
UPDATE STATISTICS Clients IX_Clients_Ville WITH FULLSCAN;
```

### Piège 4 : Désactiver AUTO_UPDATE_STATISTICS sans plan

**Erreur :**
```sql
-- "Les mises à jour auto ralentissent mes requêtes"
ALTER DATABASE MaBase SET AUTO_UPDATE_STATISTICS OFF;  -- ❌ Dangereux !

-- Et ensuite... oublier de mettre à jour manuellement
```

**Problème :**
- Les statistiques deviennent rapidement obsolètes
- Performance qui se dégrade progressivement
- Problèmes difficiles à diagnostiquer

**Solution :**
Si vous devez désactiver AUTO_UPDATE, **mettez en place un plan de maintenance manuel rigoureux**.

### Piège 5 : Ignorer les statistiques multi-colonnes

**Erreur :**
```sql
-- Requête fréquente avec deux colonnes
SELECT * FROM Ventes
WHERE Pays = 'France' AND Ville = 'Paris';

-- Mais seulement des statistiques séparées sur Pays et Ville
-- SQL Server ne comprend pas la corrélation !
```

**Solution :**
```sql
-- Créer des statistiques multi-colonnes
CREATE STATISTICS Stats_Ventes_Pays_Ville
ON Ventes (Pays, Ville)
WITH FULLSCAN;
```

## Cas pratiques

### Cas 1 : Après un import massif

**Situation :**
Vous venez d'importer 5 millions de nouvelles commandes dans une table qui en contenait 1 million.

**Actions :**
```sql
-- 1. Vérifier l'état des statistiques
SELECT
    name,
    STATS_DATE(object_id, stats_id) AS LastUpdated
FROM sys.stats
WHERE object_id = OBJECT_ID('Commandes');

-- 2. Mettre à jour avec un bon échantillon
UPDATE STATISTICS Commandes WITH SAMPLE 30 PERCENT;

-- 3. Vérifier les plans d'exécution de vos requêtes principales
-- Activer le plan d'exécution réel et comparer Estimated vs Actual
```

### Cas 2 : Requête soudainement lente

**Situation :**
Une requête qui prenait 2 secondes prend maintenant 2 minutes.

**Diagnostic :**
```sql
-- 1. Afficher le plan d'exécution réel
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Votre requête problématique
SELECT * FROM Clients WHERE Ville = 'Lyon';

-- 2. Comparer Estimated Rows vs Actual Rows dans le plan
-- Si grand écart (×10 ou plus) → problème de statistiques !

-- 3. Vérifier la date de mise à jour
SELECT
    STATS_DATE(object_id, stats_id) AS LastUpdated
FROM sys.stats
WHERE object_id = OBJECT_ID('Clients')
    AND name LIKE '%Ville%';
```

**Solution :**
```sql
-- Si les statistiques sont obsolètes
UPDATE STATISTICS Clients WITH FULLSCAN;

-- Réexécuter la requête et vérifier l'amélioration
```

### Cas 3 : Création d'index pour optimisation

**Situation :**
Vous créez un nouvel index pour améliorer une requête lente.

**Bonnes pratiques :**
```sql
-- 1. Créer l'index
CREATE INDEX IX_Produits_Categorie_Prix
ON Produits (Categorie, Prix)
INCLUDE (Nom, Description);

-- 2. Vérifier que les statistiques sont bonnes
-- (SQL Server les crée automatiquement, mais vérifier)
SELECT
    name,
    STATS_DATE(object_id, stats_id) AS LastUpdated
FROM sys.stats
WHERE object_id = OBJECT_ID('Produits')
    AND name = 'IX_Produits_Categorie_Prix';

-- 3. Si la table est grande et a beaucoup changé récemment
UPDATE STATISTICS Produits IX_Produits_Categorie_Prix WITH FULLSCAN;

-- 4. Tester la requête avec le nouveau plan
```

### Cas 4 : Maintenance hebdomadaire

**Situation :**
Vous voulez maintenir les statistiques de vos tables critiques.

**Script de maintenance :**
```sql
-- Script à exécuter chaque week-end
USE VotreBaseDeDonnees;
GO

-- Tables critiques avec FULLSCAN (petites/moyennes)
UPDATE STATISTICS Clients WITH FULLSCAN;
UPDATE STATISTICS Produits WITH FULLSCAN;

-- Grandes tables avec échantillonnage
UPDATE STATISTICS Commandes WITH SAMPLE 25 PERCENT;
UPDATE STATISTICS LogActivites WITH SAMPLE 15 PERCENT;

-- Toutes les autres tables (mise à jour standard)
EXEC sp_updatestats;

-- Afficher un résumé
SELECT
    t.name AS TableName,
    COUNT(*) AS StatsCount,
    MIN(STATS_DATE(s.object_id, s.stats_id)) AS OldestUpdate,
    MAX(STATS_DATE(s.object_id, s.stats_id)) AS NewestUpdate
FROM sys.stats s
JOIN sys.tables t ON s.object_id = t.object_id
GROUP BY t.name
ORDER BY t.name;
```

## Surveillance et monitoring

### Requêtes utiles pour surveiller les statistiques

#### 1. Statistiques obsolètes

```sql
-- Trouver les statistiques qui n'ont pas été mises à jour depuis longtemps
SELECT
    OBJECT_NAME(s.object_id) AS TableName,
    s.name AS StatisticName,
    STATS_DATE(s.object_id, s.stats_id) AS LastUpdated,
    DATEDIFF(DAY, STATS_DATE(s.object_id, s.stats_id), GETDATE()) AS DaysOld,
    sp.rows AS RowCount
FROM sys.stats s
JOIN sys.tables t ON s.object_id = t.object_id
CROSS APPLY sys.dm_db_partition_stats sp
WHERE sp.object_id = s.object_id
    AND sp.index_id < 2  -- Table ou clustered index
    AND STATS_DATE(s.object_id, s.stats_id) < DATEADD(DAY, -30, GETDATE())
ORDER BY DaysOld DESC;
```

#### 2. Statistiques avec histogramme

```sql
-- Voir l'histogramme d'une statistique
DBCC SHOW_STATISTICS('Clients', 'Stats_Clients_Ville');
```

**Interprétation des résultats :**
- **Density** : Plus c'est proche de 0, plus les valeurs sont uniques
- **Rows** : Nombre total de lignes
- **Steps** : Les "buckets" de l'histogramme avec la distribution

#### 3. Statistiques automatiques vs manuelles

```sql
-- Distinguer les statistiques auto vs manuelles
SELECT
    OBJECT_NAME(object_id) AS TableName,
    name AS StatisticName,
    CASE
        WHEN auto_created = 1 THEN 'Auto'
        WHEN user_created = 1 THEN 'Manuelle'
        ELSE 'Index'
    END AS Type,
    STATS_DATE(object_id, stats_id) AS LastUpdated
FROM sys.stats
WHERE object_id = OBJECT_ID('Clients')
ORDER BY Type, name;
```

### ✅ À FAIRE

1. **Laisser les options automatiques activées** par défaut
   ```sql
   AUTO_CREATE_STATISTICS = ON
   AUTO_UPDATE_STATISTICS = ON
   ```

2. **Utiliser AUTO_UPDATE_STATISTICS_ASYNC en production**
   ```sql
   AUTO_UPDATE_STATISTICS_ASYNC = ON
   ```

3. **Mettre à jour manuellement après opérations massives**
   ```sql
   -- Après BULK INSERT ou modifications massives
   UPDATE STATISTICS TableConcernee WITH SAMPLE 30 PERCENT;
   ```

4. **Créer des statistiques multi-colonnes pour colonnes corrélées**
   ```sql
   CREATE STATISTICS Stats_Pays_Ville ON Ventes (Pays, Ville);
   ```

5. **Surveiller les écarts dans les plans d'exécution**
   - Comparer Estimated vs Actual Rows
   - Investiguer si ratio > 10

6. **Documenter votre stratégie de maintenance**
   - Quelles tables sont mises à jour manuellement ?
   - Quelle fréquence ?
   - Quel taux d'échantillonnage ?

### ❌ À ÉVITER

1. **Ne désactivez pas AUTO_UPDATE_STATISTICS sans raison**
   - C'est rarement nécessaire
   - Crée plus de problèmes que ça n'en résout

2. **N'utilisez pas FULLSCAN systématiquement**
   - Réservez-le aux petites tables ou cas critiques
   - Un échantillon de 20-30% suffit généralement

3. **Ne mettez pas à jour après chaque modification**
   - Overhead inutile
   - Laissez SQL Server gérer automatiquement

4. **N'oubliez pas les statistiques après création d'index**
   - Vérifiez qu'elles sont à jour
   - Surtout sur de grandes tables existantes

5. **Ne négligez pas le monitoring**
   - Vérifiez périodiquement les dates de mise à jour
   - Surveillez les plans d'exécution problématiques

## Conclusion

La gestion des statistiques est un équilibre entre **automatisation** et **intervention manuelle** :

**SQL Server fait déjà beaucoup :**
- Création automatique lors de l'utilisation
- Mise à jour automatique selon un seuil
- Dans 90% des cas, cela suffit

**Votre rôle :**
- **Surveiller** : Vérifier que les statistiques restent à jour
- **Intervenir** : Mettre à jour après opérations massives
- **Optimiser** : Créer des statistiques multi-colonnes si nécessaire
- **Planifier** : Maintenance proactive pour tables critiques

**Les clés du succès :**
1. ✅ Comprendre comment SQL Server gère les statistiques
2. ✅ Savoir quand laisser faire et quand intervenir
3. ✅ Surveiller les plans d'exécution pour détecter les problèmes
4. ✅ Avoir une stratégie de maintenance adaptée à vos besoins

Avec ces connaissances, vous pouvez maintenant garantir que votre optimiseur de requêtes dispose toujours des meilleures informations pour faire les bons choix !

---

**Points à retenir :**
- AUTO_CREATE_STATISTICS et AUTO_UPDATE_STATISTICS doivent généralement rester activés
- AUTO_UPDATE_STATISTICS_ASYNC améliore la prévisibilité en production
- UPDATE STATISTICS est votre commande principale pour les mises à jour manuelles
- FULLSCAN n'est pas toujours nécessaire ; un échantillon de 20-30% suffit souvent
- Créez des statistiques multi-colonnes pour les colonnes corrélées
- Mettez à jour les statistiques après des chargements massifs de données
- Surveillez les écarts entre Estimated et Actual Rows dans les plans d'exécution
- sp_updatestats met à jour toutes les statistiques obsolètes d'une base
