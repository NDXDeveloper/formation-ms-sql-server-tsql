# 8.5.2 Implications pour le développeur (Connection String, Basculement, Réplicas en lecture seule)

## Introduction

En tant que développeur, vous n'aurez probablement jamais à configurer un Groupe de disponibilité AlwaysOn vous-même. Cependant, **vous devez comprendre comment votre application interagit avec cette infrastructure** pour garantir qu'elle fonctionne correctement, même en cas de basculement.

Cette section couvre les aspects pratiques que tout développeur travaillant avec SQL Server et AlwaysOn doit connaître.

## 1. Les chaînes de connexion (Connection Strings)

### Comprendre le problème

Traditionnellement, une chaîne de connexion pointe vers un serveur SQL Server spécifique :

```
Server=SERVEUR-SQL-01;Database=Ventes;User Id=app_user;Password=***;
```

**Problème :** Si `SERVEUR-SQL-01` tombe en panne et qu'un basculement se produit vers `SERVEUR-SQL-02`, votre application continue de tenter de se connecter à `SERVEUR-SQL-01` et échoue.

### La solution : Le Listener

Le **Listener** est un nom réseau virtuel (DNS) qui pointe toujours vers le réplica primaire actuel. C'est comme un **standard téléphonique intelligent** qui route automatiquement les appels vers la bonne personne.

#### Exemple visuel

```
┌─────────────────────────────────────────────────────────────┐
│           Application Web                                   │
│                                                             │
│  Connection String:                                         │
│  Server=AG-Ventes-Listener;...                              │
└───────────────────┬─────────────────────────────────────────┘
                    │
                    │ DNS résout toujours vers le primaire actuel
                    ↓
┌───────────────────────────────────────────────────────────────┐
│              AG-Ventes-Listener (Virtual IP)                  │
└───────────────────┬───────────────────────────────────────────┘
                    │
        ┌───────────┴───────────┐
        ↓                       ↓
┌───────────────┐       ┌───────────────┐
│ SERVEUR-01    │       │ SERVEUR-02    │
│ (Primaire) ✓  │       │ (Secondaire)  │
└───────────────┘       └───────────────┘

Après basculement :

┌───────────────┐       ┌───────────────┐
│ SERVEUR-01    │       │ SERVEUR-02    │
│ (DOWN) ✗      │       │ (Primaire) ✓  │
└───────────────┘       └───────────────┘
                    ↑
                    │
      Le listener pointe maintenant ici automatiquement
```

### Anatomie d'une chaîne de connexion avec AlwaysOn

#### Chaîne de connexion de base

```
Server=AG-Ventes-Listener;Database=Ventes;User Id=app_user;Password=***;
```

C'est le **minimum requis** et cela fonctionne, mais ce n'est pas optimal.

#### Chaîne de connexion optimisée

```
Server=AG-Ventes-Listener;Database=Ventes;
User Id=app_user;Password=***;
ApplicationIntent=ReadWrite;
MultiSubnetFailover=True;
ConnectRetryCount=3;
ConnectRetryInterval=10;
```

Décomposons chaque paramètre :

##### 1. `ApplicationIntent`

**Valeurs possibles :**
- `ReadWrite` (défaut) : Se connecte au réplica primaire
- `ReadOnly` : Se connecte à un réplica secondaire configuré pour la lecture

**Utilisation :**
```csharp
// Connexion pour des opérations de modification (INSERT, UPDATE, DELETE)
string connexionEcriture = "Server=AG-Ventes-Listener;Database=Ventes;" +
                           "User Id=app;Password=***;" +
                           "ApplicationIntent=ReadWrite;";

// Connexion pour des rapports et lectures intensives
string connexionLecture = "Server=AG-Ventes-Listener;Database=Ventes;" +
                          "User Id=app;Password=***;" +
                          "ApplicationIntent=ReadOnly;";
```

**Important :** Avec `ApplicationIntent=ReadOnly`, le listener route automatiquement la connexion vers un secondaire lisible (si configuré).

##### 2. `MultiSubnetFailover`

**Valeur :** `True` ou `False` (défaut : `False`)

**Rôle :** Accélère la détection et la reconnexion lors d'un basculement, **surtout si vos réplicas sont sur des sous-réseaux différents**.

**Comment ça marche :**
- Lorsque `True`, le driver tente de se connecter à **toutes les adresses IP** associées au listener simultanément
- La première connexion qui réussit est utilisée
- Réduit le temps de basculement de ~30 secondes à ~5-10 secondes

**Recommandation :** **Toujours utiliser `True`** avec AlwaysOn, même si vos serveurs sont sur le même sous-réseau.

```
MultiSubnetFailover=True;
```

##### 3. `ConnectRetryCount` et `ConnectRetryInterval`

**Rôle :** Gestion automatique des reconnexions après un basculement.

- `ConnectRetryCount` : Nombre de tentatives de reconnexion (défaut : 1)
- `ConnectRetryInterval` : Délai en secondes entre les tentatives (défaut : 10)

**Exemple :**
```
ConnectRetryCount=3;
ConnectRetryInterval=10;
```

Signifie : "Si la connexion échoue, réessaye 3 fois avec 10 secondes d'intervalle."

**Scénario d'utilisation :**
```
1. Basculement en cours (t=0s)
2. Application tente de se connecter → Échec
3. Attend 10 secondes
4. Nouvelle tentative → Échec (basculement pas encore terminé)
5. Attend 10 secondes
6. Nouvelle tentative → Succès (nouveau primaire prêt)
```

## 2. Gérer le basculement dans votre code

### Comprendre ce qui se passe lors d'un basculement

Lorsqu'un basculement se produit, voici la séquence typique :

```
t=0s    : Le primaire plante
t=10s   : Le cluster détecte la panne
t=20s   : Élection d'un nouveau primaire
t=30s   : Le nouveau primaire est en ligne
t=35s   : Le listener pointe vers le nouveau primaire
```

**Impact sur votre application :**
- Les connexions actives sont **brutalement interrompues**
- Les transactions en cours sont **annulées (ROLLBACK automatique)**
- Les nouvelles tentatives de connexion échouent pendant ~30 secondes

### Stratégies de gestion des erreurs

#### 1. Retry automatique (Recommandé)

La meilleure approche est d'implémenter une **logique de retry** avec un délai exponentiel (exponential backoff).

**Exemple en C# avec Polly (bibliothèque de résilience) :**

```csharp
using Polly;
using System.Data.SqlClient;

// Définir une politique de retry
var retryPolicy = Policy
    .Handle<SqlException>(ex =>
        ex.Number == -1 ||      // Timeout
        ex.Number == -2 ||      // Connexion perdue
        ex.Number == 53 ||      // Serveur introuvable
        ex.Number == 64 ||      // Erreur réseau
        ex.Number == 233 ||     // Échec de connexion
        ex.Number == 10053 ||   // Connexion interrompue
        ex.Number == 10054 ||   // Connexion réinitialisée
        ex.Number == 40197 ||   // Basculement détecté
        ex.Number == 40540 ||   // Service interrompu
        ex.Number == 40613)     // Base de données non disponible
    .WaitAndRetry(
        retryCount: 5,
        sleepDurationProvider: retryAttempt =>
            TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)), // 2s, 4s, 8s, 16s, 32s
        onRetry: (exception, timeSpan, retryCount, context) =>
        {
            Console.WriteLine($"Tentative {retryCount} après {timeSpan.TotalSeconds}s");
        }
    );

// Utilisation
retryPolicy.Execute(() =>
{
    using (SqlConnection conn = new SqlConnection(connectionString))
    {
        conn.Open();
        // Exécuter vos commandes SQL
        SqlCommand cmd = new SqlCommand("SELECT * FROM Produits", conn);
        var reader = cmd.ExecuteReader();
        // Traiter les résultats
    }
});
```

**Sans bibliothèque externe (retry manuel) :**

```csharp
public void ExecuterAvecRetry(Action action, int maxRetries = 3)
{
    int retryCount = 0;

    while (true)
    {
        try
        {
            action();
            return; // Succès, on sort
        }
        catch (SqlException ex) when (EstErreurTransitoire(ex))
        {
            retryCount++;

            if (retryCount > maxRetries)
            {
                // On a épuisé les tentatives, on propage l'erreur
                throw;
            }

            // Attendre avant de réessayer (délai exponentiel)
            int delaiSecondes = (int)Math.Pow(2, retryCount);
            Console.WriteLine($"Erreur transitoire détectée. " +
                            $"Nouvelle tentative dans {delaiSecondes}s...");
            Thread.Sleep(TimeSpan.FromSeconds(delaiSecondes));
        }
    }
}

private bool EstErreurTransitoire(SqlException ex)
{
    // Codes d'erreur liés à la connectivité et au basculement
    int[] erreursTransitoires = { -1, -2, 53, 64, 233, 10053, 10054,
                                   40197, 40540, 40613 };
    return erreursTransitoires.Contains(ex.Number);
}

// Utilisation
ExecuterAvecRetry(() =>
{
    using (SqlConnection conn = new SqlConnection(connectionString))
    {
        conn.Open();
        // Votre code ici
    }
});
```

#### 2. Gestion des transactions

**Problème :** Si une transaction est en cours lors d'un basculement, elle est automatiquement annulée (ROLLBACK).

**Solution :** Implémenter une logique de retry **au niveau transactionnel**.

```csharp
public void ExecuterTransactionAvecRetry(Action<SqlConnection, SqlTransaction> action)
{
    int maxRetries = 3;
    int retryCount = 0;

    while (retryCount <= maxRetries)
    {
        SqlConnection conn = null;
        SqlTransaction transaction = null;

        try
        {
            conn = new SqlConnection(connectionString);
            conn.Open();
            transaction = conn.BeginTransaction();

            // Exécuter les opérations
            action(conn, transaction);

            // Valider la transaction
            transaction.Commit();
            return; // Succès
        }
        catch (SqlException ex) when (EstErreurTransitoire(ex))
        {
            // Rollback automatique en cas d'erreur
            transaction?.Rollback();

            retryCount++;
            if (retryCount > maxRetries)
                throw;

            int delai = (int)Math.Pow(2, retryCount);
            Thread.Sleep(TimeSpan.FromSeconds(delai));
        }
        finally
        {
            transaction?.Dispose();
            conn?.Dispose();
        }
    }
}

// Utilisation
ExecuterTransactionAvecRetry((conn, trans) =>
{
    var cmd1 = new SqlCommand(
        "INSERT INTO Commandes (ClientId, Total) VALUES (@ClientId, @Total); " +
        "SELECT SCOPE_IDENTITY();", conn, trans);
    cmd1.Parameters.AddWithValue("@ClientId", 123);
    cmd1.Parameters.AddWithValue("@Total", 99.99);
    int commandeId = Convert.ToInt32(cmd1.ExecuteScalar());

    var cmd2 = new SqlCommand(
        "INSERT INTO DetailCommande (CommandeId, ProduitId, Quantite) " +
        "VALUES (@CommandeId, @ProduitId, @Quantite)", conn, trans);
    cmd2.Parameters.AddWithValue("@CommandeId", commandeId);
    cmd2.Parameters.AddWithValue("@ProduitId", 456);
    cmd2.Parameters.AddWithValue("@Quantite", 2);
    cmd2.ExecuteNonQuery();
});
```

#### 3. Pooling de connexions et basculement

Les connexions mises en pool peuvent devenir **obsolètes** après un basculement (elles pointent vers l'ancien primaire).

**Solution :** Définir un timeout de connexion pool raisonnable.

```csharp
string connectionString =
    "Server=AG-Ventes-Listener;Database=Ventes;" +
    "User Id=app;Password=***;" +
    "MultiSubnetFailover=True;" +
    "Connection Timeout=30;" +          // Timeout de connexion initiale
    "Min Pool Size=0;" +                // Pas de connexions minimales
    "Max Pool Size=100;" +              // Maximum 100 connexions
    "Pooling=true;" +                   // Activer le pooling (défaut)
    "Connection Lifetime=300;";         // Recycler les connexions après 5 minutes
```

**Explication :**
- `Connection Lifetime=300` : Force les connexions du pool à être fermées et recréées après 5 minutes
- Cela garantit que les connexions obsolètes (pointant vers un ancien primaire) sont éliminées

## 3. Utilisation des réplicas en lecture seule

### Principe et avantages

Avec AlwaysOn, vous pouvez **décharger les opérations de lecture** vers des réplicas secondaires, libérant ainsi des ressources sur le primaire.

**Scénario typique :**
```
┌──────────────────────────────────────────────────────────┐
│                    Application Web                       │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  Pages "normales" (CRUD)                                 │
│  └─> Connexion ReadWrite → Réplica Primaire              │
│                                                          │
│  Pages de reporting / tableaux de bord                   │
│  └─> Connexion ReadOnly → Réplica Secondaire             │
│                                                          │
│  Export de données / analyses                            │
│  └─> Connexion ReadOnly → Réplica Secondaire             │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### Implémentation pratique

#### Architecture avec deux chaînes de connexion

```csharp
public class DatabaseConnectionFactory
{
    // Chaîne pour les opérations d'écriture et lectures critiques
    private static readonly string _connectionStringWrite =
        "Server=AG-Ventes-Listener;Database=Ventes;" +
        "User Id=app;Password=***;" +
        "ApplicationIntent=ReadWrite;" +
        "MultiSubnetFailover=True;";

    // Chaîne pour les opérations de lecture lourdes (rapports)
    private static readonly string _connectionStringRead =
        "Server=AG-Ventes-Listener;Database=Ventes;" +
        "User Id=app_readonly;Password=***;" +
        "ApplicationIntent=ReadOnly;" +
        "MultiSubnetFailover=True;";

    public static SqlConnection ObtenirConnexionEcriture()
    {
        return new SqlConnection(_connectionStringWrite);
    }

    public static SqlConnection ObtenirConnexionLecture()
    {
        return new SqlConnection(_connectionStringRead);
    }
}

// Utilisation dans un contrôleur web
public class ProduitsController : Controller
{
    // GET: Liste des produits (affichage simple)
    public IActionResult Index()
    {
        var produits = new List<Produit>();

        // Utiliser la connexion en lecture seule
        using (var conn = DatabaseConnectionFactory.ObtenirConnexionLecture())
        {
            conn.Open();
            var cmd = new SqlCommand("SELECT * FROM Produits", conn);
            var reader = cmd.ExecuteReader();

            while (reader.Read())
            {
                produits.Add(new Produit
                {
                    Id = reader.GetInt32(0),
                    Nom = reader.GetString(1),
                    Prix = reader.GetDecimal(2)
                });
            }
        }

        return View(produits);
    }

    // POST: Créer un nouveau produit
    [HttpPost]
    public IActionResult Creer(Produit produit)
    {
        // Utiliser la connexion en écriture
        using (var conn = DatabaseConnectionFactory.ObtenirConnexionEcriture())
        {
            conn.Open();
            var cmd = new SqlCommand(
                "INSERT INTO Produits (Nom, Prix) VALUES (@Nom, @Prix)", conn);
            cmd.Parameters.AddWithValue("@Nom", produit.Nom);
            cmd.Parameters.AddWithValue("@Prix", produit.Prix);
            cmd.ExecuteNonQuery();
        }

        return RedirectToAction("Index");
    }

    // GET: Rapport des ventes (requête complexe)
    public IActionResult RapportVentes()
    {
        // Utiliser la connexion en lecture seule pour ne pas impacter la production
        using (var conn = DatabaseConnectionFactory.ObtenirConnexionLecture())
        {
            conn.Open();
            var cmd = new SqlCommand(@"
                SELECT
                    p.Nom,
                    SUM(dc.Quantite) AS QuantiteTotale,
                    SUM(dc.Quantite * p.Prix) AS ChiffreAffaires
                FROM Produits p
                INNER JOIN DetailCommande dc ON p.Id = dc.ProduitId
                INNER JOIN Commandes c ON dc.CommandeId = c.Id
                WHERE c.DateCommande >= DATEADD(MONTH, -1, GETDATE())
                GROUP BY p.Nom
                ORDER BY ChiffreAffaires DESC", conn);

            // Traitement des résultats...
        }

        return View();
    }
}
```

### Attention : Latence de réplication

**Important :** Un réplica secondaire peut être **légèrement en retard** par rapport au primaire, même en mode synchrone.

**Problème potentiel :**
```
1. L'utilisateur crée un nouveau produit (écriture sur primaire)
2. Redirection vers la page de liste (lecture sur secondaire)
3. Le nouveau produit n'apparaît pas ! (la réplication n'est pas encore arrivée)
```

**Solutions :**

#### Solution 1 : Lecture sur le primaire après écriture
```csharp
[HttpPost]
public IActionResult Creer(Produit produit)
{
    using (var conn = DatabaseConnectionFactory.ObtenirConnexionEcriture())
    {
        conn.Open();
        var cmd = new SqlCommand(
            "INSERT INTO Produits (Nom, Prix) VALUES (@Nom, @Prix); " +
            "SELECT SCOPE_IDENTITY();", conn);
        cmd.Parameters.AddWithValue("@Nom", produit.Nom);
        cmd.Parameters.AddWithValue("@Prix", produit.Prix);
        int nouveauId = Convert.ToInt32(cmd.ExecuteScalar());

        // Rediriger vers une page qui lit depuis le PRIMAIRE
        return RedirectToAction("Details", new { id = nouveauId, source = "write" });
    }
}

public IActionResult Details(int id, string source = "read")
{
    // Si on vient d'une écriture, lire depuis le primaire
    var conn = (source == "write")
        ? DatabaseConnectionFactory.ObtenirConnexionEcriture()
        : DatabaseConnectionFactory.ObtenirConnexionLecture();

    using (conn)
    {
        // Lire les détails du produit
    }
}
```

#### Solution 3 : Accepter un délai court (Eventual Consistency)
Pour certaines applications, un délai de 1-2 secondes est acceptable. Dans ce cas, informez simplement l'utilisateur :

```csharp
// Après création
TempData["Message"] = "Produit créé avec succès. " +
                      "Il peut prendre quelques secondes pour apparaître dans les listes.";
```

### Quand utiliser ReadOnly vs ReadWrite

| Type d'opération | Connexion recommandée | Raison |
|------------------|----------------------|--------|
| SELECT simple pour affichage | ReadOnly | Décharge le primaire |
| INSERT, UPDATE, DELETE | ReadWrite | Obligatoire |
| SELECT après écriture immédiate | ReadWrite | Éviter les problèmes de latence |
| Rapports lourds / BI | ReadOnly | Ne pas impacter la production |
| Export de données | ReadOnly | Opération longue |
| Vérification de contrainte avant INSERT | ReadWrite | Nécessite données à jour |
| Dashboard temps réel | ReadOnly (acceptable) ou ReadWrite (préférable) | Selon tolérance au délai |

## 4. Meilleures pratiques pour les développeurs

### ✅ À FAIRE

1. **Toujours utiliser `MultiSubnetFailover=True`**
   - Même si vos serveurs sont sur le même réseau

2. **Implémenter une logique de retry robuste**
   - Avec délai exponentiel
   - Gérer les erreurs transitoires spécifiques à SQL Server

3. **Utiliser des transactions explicites pour les opérations critiques**
   - Permet de tout rejouer en cas d'échec

4. **Logger les basculements détectés**
   ```csharp
   catch (SqlException ex) when (ex.Number == 40197)
   {
       Logger.LogWarning("Basculement AlwaysOn détecté. Retry en cours...");
       // Retry
   }
   ```

5. **Tester vos applications avec des basculements simulés**
   - Demandez à votre DBA de faire un basculement manuel pendant vos tests

6. **Séparer les connexions lecture/écriture quand c'est pertinent**
   - Utilisez `ApplicationIntent=ReadOnly` pour les opérations lourdes

7. **Définir des timeouts appropriés**
   ```
   Connection Timeout=30;
   Command Timeout=60;
   ```

### ❌ À ÉVITER

1. **Ne jamais coder en dur les noms de serveurs physiques**
   ```csharp
   // ❌ MAL
   string connString = "Server=SQLPROD01;...";

   // ✅ BIEN
   string connString = "Server=AG-Ventes-Listener;...";
   ```

2. **Ne pas ignorer les exceptions de connexion**
   ```csharp
   // ❌ MAL
   try {
       conn.Open();
   } catch {
       // Ignorer l'erreur silencieusement
   }

   // ✅ BIEN
   try {
       conn.Open();
   } catch (SqlException ex) {
       Logger.LogError(ex, "Échec de connexion à la base de données");
       throw; // Ou implémenter retry
   }
   ```

3. **Ne pas supposer qu'une connexion reste valide indéfiniment**
   - Toujours ouvrir/fermer les connexions au besoin
   - Utiliser le pattern `using` en C#

4. **Ne pas utiliser `ApplicationIntent=ReadOnly` pour des données devant être absolument à jour**
   - Exemple : Vérification de stock avant achat

5. **Ne pas oublier de recycler les connexions du pool**
   - Utiliser `Connection Lifetime` dans la chaîne de connexion

## 5. Checklist de déploiement

Avant de mettre en production une application utilisant AlwaysOn, vérifiez :

- [ ] La chaîne de connexion utilise le **listener**, pas un nom de serveur physique
- [ ] `MultiSubnetFailover=True` est présent
- [ ] `ApplicationIntent` est défini selon le besoin (ReadWrite ou ReadOnly)
- [ ] Une logique de **retry** est implémentée pour les erreurs transitoires
- [ ] Les **timeouts** sont configurés (Connection, Command)
- [ ] Le **pooling** est configuré avec `Connection Lifetime`
- [ ] Les **logs** capturent les échecs de connexion et basculements
- [ ] Les **transactions** critiques peuvent être rejouées en cas d'échec
- [ ] L'application a été **testée avec un basculement simulé**
- [ ] La documentation indique quelle connexion (ReadWrite/ReadOnly) utiliser pour chaque cas

## Conclusion

En tant que développeur, travailler avec AlwaysOn nécessite principalement de :

1. **Utiliser le listener** dans vos chaînes de connexion
2. **Configurer les bons paramètres** (`MultiSubnetFailover`, `ApplicationIntent`)
3. **Gérer les erreurs** avec retry et délai exponentiel
4. **Séparer les lectures lourdes** vers les secondaires quand c'est pertinent

Ces pratiques garantissent que votre application reste **résiliente** et profite pleinement de la haute disponibilité offerte par AlwaysOn, tout en optimisant les performances grâce au déchargement de lecture.
