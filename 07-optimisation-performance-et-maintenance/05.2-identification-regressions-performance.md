# 7.5.2 Identification des régressions de performance

## Qu'est-ce qu'une régression de performance ?

Une **régression de performance** se produit lorsqu'une requête qui fonctionnait bien devient soudainement plus lente, sans que le code de la requête n'ait été modifié.

### Analogie simple

Imaginez que vous prenez le même trajet pour aller au travail chaque jour. Habituellement, cela prend 20 minutes. Un jour, sans raison apparente, le même trajet prend 45 minutes. Vous n'avez pas changé de route, vous n'avez pas conduit différemment, mais quelque chose a changé (peut-être des travaux routiers ou un changement dans les feux de circulation).

C'est exactement ce qui se passe avec une régression de performance : la requête reste la même, mais quelque chose dans l'environnement a changé.

## Pourquoi les régressions se produisent-elles ?

### Les causes courantes

#### 1. **Changement de plan d'exécution**
SQL Server peut décider d'utiliser un plan d'exécution différent pour la même requête. Ce nouveau plan peut être moins efficace.

**Pourquoi le plan change ?**
- Les statistiques sur les données ont été mises à jour
- La distribution des données a évolué
- De nouveaux index ont été créés ou supprimés
- Des paramètres différents ont été utilisés (Parameter Sniffing)

#### 2. **Évolution des données**
La table contenait 1000 lignes hier, elle en contient 1 million aujourd'hui. Le même plan d'exécution n'est plus optimal.

#### 3. **Changements d'infrastructure**
- Mise à jour de SQL Server
- Modification de la configuration du serveur
- Changement du niveau de compatibilité de la base de données

#### 4. **Concurrence accrue**
Plus d'utilisateurs utilisent simultanément la base de données, créant des contentions et des attentes.

## Comment Query Store aide à identifier les régressions

Le Query Store est l'outil idéal pour détecter les régressions car il conserve :
- **L'historique des performances** : Vous pouvez voir comment une requête performait avant
- **Les plans d'exécution** : Vous pouvez comparer l'ancien plan (rapide) avec le nouveau (lent)
- **Les métriques détaillées** : Temps d'exécution, CPU, I/O, etc.

## Le rapport "Regressed Queries" dans SSMS

### Accéder au rapport

C'est le moyen le plus simple pour identifier les régressions :

1. Dans SQL Server Management Studio (SSMS)
2. Développez votre base de données
3. Développez le dossier **Query Store**
4. Double-cliquez sur **Regressed Queries**

### Comprendre le rapport

Le rapport affiche un graphique avec deux points pour chaque requête :
- **Point de gauche** : Performance historique (période de référence)
- **Point de droite** : Performance récente (période actuelle)

#### Éléments clés du rapport

**1. L'axe des ordonnées (Y)**
Représente la métrique de performance choisie :
- Durée (Duration)
- Temps CPU
- Nombre de lectures logiques
- Nombre de lectures physiques
- Temps d'attente

**2. L'axe des abscisses (X)**
Représente les requêtes, triées par ordre de régression

**3. Les bulles**
Chaque requête est représentée par une paire de bulles reliées par une ligne :
- Plus la ligne est verticale et montante, plus la régression est importante
- La taille de la bulle peut représenter le nombre d'exécutions

### Configuration du rapport

En haut du rapport, vous pouvez ajuster :

#### **Métrique** (Metric)
Choisissez ce que vous voulez mesurer :
```
- Duration (Durée) : Le plus courant, mesure le temps total
- CPU Time : Temps processeur utilisé
- Logical Reads : Lectures en mémoire
- Logical Writes : Écritures en mémoire
- Physical Reads : Lectures sur disque (les plus coûteuses)
```

#### **Statistique** (Statistic)
Comment agréger les données :
```
- Average (Moyenne) : Recommandé pour la plupart des cas
- Total (Somme) : Utile pour voir l'impact global
- Min (Minimum) : Performance dans le meilleur cas
- Max (Maximum) : Performance dans le pire cas
- Std Dev (Écart-type) : Variabilité des performances
```

#### **Période de temps**
- **Période récente** (Recent) : Par défaut, la dernière heure
- **Période de référence** (History) : Par défaut, l'heure précédente

**Exemple de configuration :**
```
Metric: Duration
Statistic: Average
Recent: Last 1 hour
History: Last 1 day
```
Cela compare la performance moyenne de la dernière heure avec celle du jour précédent.

## Analyser une régression identifiée

### Étape 1 : Sélectionner une requête problématique

Dans le rapport, cliquez sur une requête qui montre une forte régression (ligne montante prononcée).

### Étape 2 : Examiner les détails

Une fois la requête sélectionnée, le panneau inférieur affiche :

#### **Le texte de la requête**
```sql
-- Exemple
SELECT
    c.CustomerName,
    COUNT(o.OrderID) as OrderCount
FROM Customers c
LEFT JOIN Orders o ON c.CustomerID = o.CustomerID
WHERE c.Country = 'France'
GROUP BY c.CustomerName;
```

#### **Les plans d'exécution**
Vous verrez plusieurs plans, chacun avec :
- Un identifiant (Plan ID)
- La période d'utilisation
- Les statistiques de performance

**Points à observer :**
- **Plan ID** : Chaque plan a un identifiant unique
- **Avg Duration** : Durée moyenne d'exécution
- **Execution Count** : Nombre d'exécutions
- **Rectangles colorés** : Indiquent les périodes d'utilisation de chaque plan

### Étape 3 : Comparer les plans

#### Identifier le "bon" et le "mauvais" plan

**Bon plan (ancien)** :
```
Plan ID: 1
Avg Duration: 50 ms
Period: Yesterday
```

**Mauvais plan (nouveau)** :
```
Plan ID: 2
Avg Duration: 2500 ms
Period: Today
```

#### Visualiser les plans graphiquement

1. Cliquez sur un plan dans le panneau inférieur
2. Un nouveau panneau s'ouvre avec le plan d'exécution graphique
3. Répétez pour l'autre plan

**Comparez les différences :**
- **Type d'opération** : Index Scan vs Index Seek
- **Coût estimé** : Pourcentages affichés sur les opérateurs
- **Jointures** : Nested Loop vs Hash Match vs Merge Join
- **Opérateurs coûteux** : Cherchez les opérateurs avec un coût élevé (>30%)

### Exemple concret d'analyse

**Scénario :**
Votre requête de recherche de clients était rapide (100 ms) mais prend maintenant 3 secondes.

**Analyse avec Query Store :**

1. **Ouvrir le rapport Regressed Queries**
   - Métrique : Duration
   - Statistique : Average
   - Vous voyez votre requête avec une forte dégradation

2. **Examiner les plans**
   - Ancien plan (Plan ID 1) : 100 ms
   - Nouveau plan (Plan ID 2) : 3000 ms

3. **Comparer visuellement**
   - Ancien plan : Utilise un Index Seek sur l'index IX_Customers_Country
   - Nouveau plan : Fait un Table Scan complet (parcourt toute la table)

4. **Comprendre la cause**
   - Les statistiques ont été mises à jour
   - SQL Server pense maintenant qu'il y a très peu de clients en France
   - Il a choisi un plan inefficace basé sur des statistiques incorrectes

## Requêtes T-SQL pour identifier les régressions

Si vous préférez utiliser du code SQL plutôt que l'interface graphique :

### Requête 1 : Trouver les requêtes avec plusieurs plans

```sql
-- Identifier les requêtes qui ont changé de plan récemment
SELECT
    q.query_id,
    qt.query_sql_text,
    COUNT(DISTINCT p.plan_id) as number_of_plans,
    MIN(rs.last_execution_time) as first_execution,
    MAX(rs.last_execution_time) as last_execution
FROM sys.query_store_query q
INNER JOIN sys.query_store_query_text qt
    ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan p
    ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats rs
    ON p.plan_id = rs.plan_id
WHERE rs.last_execution_time >= DATEADD(day, -7, GETDATE())
GROUP BY q.query_id, qt.query_sql_text
HAVING COUNT(DISTINCT p.plan_id) > 1
ORDER BY number_of_plans DESC;
```

**Explication :**
- Cette requête trouve toutes les requêtes qui ont utilisé plusieurs plans différents dans les 7 derniers jours
- Un nombre élevé de plans peut indiquer une instabilité

### Requête 2 : Comparer les performances entre plans

```sql
-- Comparer les performances de différents plans pour une requête spécifique
DECLARE @query_id INT = 123; -- Remplacez par votre query_id

SELECT
    p.plan_id,
    p.query_id,
    CAST(p.query_plan AS XML) as query_plan_xml,
    rs.count_executions,
    rs.avg_duration / 1000.0 as avg_duration_ms,
    rs.avg_cpu_time / 1000.0 as avg_cpu_time_ms,
    rs.avg_logical_io_reads,
    rs.last_execution_time,
    CASE
        WHEN rs.avg_duration = MIN(rs.avg_duration) OVER()
        THEN 'BEST PLAN'
        WHEN rs.avg_duration = MAX(rs.avg_duration) OVER()
        THEN 'WORST PLAN'
        ELSE 'INTERMEDIATE'
    END as plan_quality
FROM sys.query_store_plan p
INNER JOIN sys.query_store_runtime_stats rs
    ON p.plan_id = rs.plan_id
WHERE p.query_id = @query_id
ORDER BY rs.avg_duration;
```

**Explication :**
- Cette requête compare tous les plans d'une requête spécifique
- Elle identifie automatiquement le meilleur et le pire plan
- Utile pour décider quel plan forcer

### Requête 3 : Détecter les régressions automatiquement

```sql
-- Détecter les requêtes dont la performance s'est dégradée
WITH RecentStats AS (
    SELECT
        p.query_id,
        p.plan_id,
        AVG(rs.avg_duration) as recent_avg_duration,
        SUM(rs.count_executions) as recent_executions
    FROM sys.query_store_plan p
    INNER JOIN sys.query_store_runtime_stats rs
        ON p.plan_id = rs.plan_id
    WHERE rs.last_execution_time >= DATEADD(hour, -1, GETDATE())
    GROUP BY p.query_id, p.plan_id
),
HistoricalStats AS (
    SELECT
        p.query_id,
        p.plan_id,
        AVG(rs.avg_duration) as historical_avg_duration,
        SUM(rs.count_executions) as historical_executions
    FROM sys.query_store_plan p
    INNER JOIN sys.query_store_runtime_stats rs
        ON p.plan_id = rs.plan_id
    WHERE rs.last_execution_time >= DATEADD(day, -7, GETDATE())
        AND rs.last_execution_time < DATEADD(hour, -1, GETDATE())
    GROUP BY p.query_id, p.plan_id
)
SELECT
    q.query_id,
    qt.query_sql_text,
    h.historical_avg_duration / 1000.0 as old_avg_duration_ms,
    r.recent_avg_duration / 1000.0 as new_avg_duration_ms,
    ((r.recent_avg_duration - h.historical_avg_duration) * 100.0
        / h.historical_avg_duration) as regression_percent,
    r.recent_executions,
    h.historical_executions
FROM RecentStats r
INNER JOIN HistoricalStats h
    ON r.query_id = h.query_id
INNER JOIN sys.query_store_query q
    ON r.query_id = q.query_id
INNER JOIN sys.query_store_query_text qt
    ON q.query_text_id = qt.query_text_id
WHERE r.recent_avg_duration > h.historical_avg_duration * 1.5  -- 50% plus lent
    AND r.recent_executions >= 10  -- Au moins 10 exécutions récentes
ORDER BY regression_percent DESC;
```

**Explication :**
- Compare les performances de la dernière heure avec celles de la semaine précédente
- Affiche les requêtes qui sont au moins 50% plus lentes
- Calcule le pourcentage de régression
- Filtre pour ne garder que les requêtes fréquemment exécutées

## Indicateurs clés d'une régression

Lors de votre analyse, surveillez ces signaux d'alarme :

### 1. Changement brutal de durée

```
Avant : 100 ms en moyenne
Après : 5000 ms en moyenne
→ Régression de 4900% !
```

### 2. Augmentation du nombre de lectures

```
Avant : 50 lectures logiques
Après : 50 000 lectures logiques
→ Le plan fait beaucoup plus de travail
```

### 3. Passage de Seek à Scan

```
Avant : Index Seek (précis, rapide)
Après : Table Scan (balayage complet, lent)
→ L'index n'est plus utilisé
```

### 4. Changement de type de jointure

```
Avant : Nested Loop (petit volume)
Après : Hash Match (grand volume)
→ SQL Server traite plus de données que prévu
```

### 5. Opérateurs de tri coûteux

```
Nouveau plan contient : Sort (Cost: 85%)
→ Tri en mémoire ou sur disque, très coûteux
```

## Scénarios typiques et leur diagnostic

### Scénario 1 : Le pic du lundi matin

**Symptôme :**
Les requêtes sont lentes tous les lundis matin, puis redeviennent normales.

**Cause probable :**
Statistiques obsolètes après le week-end (beaucoup d'insertions/mises à jour).

**Diagnostic avec Query Store :**
```
1. Rapport Regressed Queries configuré pour "Last Monday morning"
2. Identifier les requêtes affectées
3. Vérifier si les plans ont changé
4. Planifier une mise à jour des statistiques le dimanche soir
```

### Scénario 2 : Après une mise en production

**Symptôme :**
Dès le déploiement d'une nouvelle version, certaines pages de l'application sont lentes.

**Cause probable :**
Nouvelle requête ou requête modifiée avec un plan sous-optimal.

**Diagnostic avec Query Store :**
```
1. Comparer "Before deployment" vs "After deployment"
2. Identifier les nouvelles requêtes ou celles avec des plans différents
3. Analyser les plans des requêtes modifiées
4. Optimiser ou forcer un plan si nécessaire
```

### Scénario 3 : Dégradation progressive

**Symptôme :**
L'application devient de plus en plus lente sur plusieurs jours/semaines.

**Cause probable :**
Croissance des données, fragmentation d'index, ou statistiques devenues inadaptées.

**Diagnostic avec Query Store :**
```
1. Utiliser une période longue (Last 30 days)
2. Identifier les requêtes dont le trend est à la hausse
3. Corréler avec la croissance des tables
4. Envisager un réindexage ou un ajout d'index
```

## Bonnes pratiques pour l'identification

### 1. Établir une baseline

Avant qu'un problème ne survienne, familiarisez-vous avec :
- Les requêtes les plus fréquentes
- Leur durée d'exécution normale
- Les plans d'exécution typiques

### 2. Surveiller régulièrement

Consultez le rapport Regressed Queries :
- **Quotidiennement** pour les environnements de production critiques
- **Hebdomadairement** pour les environnements moins critiques
- **Après chaque déploiement** pour valider qu'il n'y a pas de régression

### 3. Définir des seuils d'alerte

Considérez qu'une régression est significative si :
- La durée augmente de plus de **50%**
- ET la requête est exécutée au moins **10 fois par heure**
- OU la durée augmente de plus de **200%** même pour des requêtes moins fréquentes

### 4. Documenter les régressions résolues

Conservez une trace des régressions identifiées et résolues :
- Date de la régression
- Requête affectée
- Cause identifiée
- Solution appliquée
- Impact métier

Cela vous aidera à détecter des patterns récurrents.

### 5. Combiner avec d'autres outils

Le Query Store n'est pas seul :
- **Extended Events** : Pour capturer des événements en temps réel
- **Performance Monitor** : Pour les métriques système (CPU, mémoire, disque)
- **Dynamic Management Views (DMV)** : Pour les informations en temps réel
- **Query Store** : Pour l'historique et les comparaisons

## Limitations à connaître

### 1. Granularité temporelle

Les statistiques sont agrégées par intervalles (par défaut 60 minutes). Vous ne verrez pas :
- Une régression qui dure 5 minutes
- Des variations intra-heure fines

### 2. Requêtes ad-hoc

Si votre application génère beaucoup de requêtes ad-hoc (non paramétrées), le Query Store peut :
- Se remplir rapidement
- Avoir du mal à identifier les patterns

**Solution :** Utilisez le mode de capture `AUTO` pour filtrer les requêtes triviales.

### 3. Régressions complexes

Certaines régressions ne sont pas causées par un changement de plan mais par :
- Des problèmes de verrouillage/blocage
- Une charge système élevée
- Des problèmes réseau

Le Query Store ne détecte que les régressions liées aux plans d'exécution.

## Résumé

L'identification des régressions de performance avec le Query Store suit ce processus :

1. **Accéder au rapport Regressed Queries** dans SSMS
2. **Configurer la période** et la métrique appropriées
3. **Identifier les requêtes** avec une dégradation significative
4. **Analyser les plans** d'exécution (ancien vs nouveau)
5. **Comprendre la cause** du changement de plan
6. **Appliquer une solution** (optimisation, forçage de plan, mise à jour de statistiques)

Le Query Store transforme la détection des régressions d'une tâche difficile et réactive en un processus simple et proactif. Vous pouvez maintenant :
- Voir **exactement quand** une régression s'est produite
- Comprendre **pourquoi** (changement de plan)
- **Corriger rapidement** en forcant le bon plan ou en optimisant la requête

---

**Points clés à retenir :**
- Une régression = même requête, performances dégradées sans modification du code
- Le rapport Regressed Queries est votre premier outil
- Comparez toujours l'ancien plan (rapide) avec le nouveau (lent)
- Cherchez les changements : Seek→Scan, changements de jointures, opérateurs coûteux
- Établissez une baseline et surveillez régulièrement
- Le Query Store stocke l'historique, utilisez-le pour comprendre les tendances
