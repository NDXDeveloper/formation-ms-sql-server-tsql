# 8.7.1 Stockage en colonnes vs stockage en lignes

## Introduction

Pour vraiment comprendre la puissance des index columnstore, il faut regarder **comment** les données sont physiquement écrites sur le disque. C'est la différence d'organisation entre le **rowstore** (par ligne) et le **columnstore** (par colonne) qui explique tout : la compression, la vitesse, et aussi les limites.

---

## Le stockage en lignes (rowstore)

C'est le mode par défaut de SQL Server, étudié tout au long de ce cours. Les données sont stockées dans des **pages de 8 Ko**, et au sein de chaque page, les **lignes complètes** sont écrites les unes à la suite des autres.

Prenons une table `Ventes` :

| VenteID | Date | Region | Produit | Montant |
|---------|------|--------|---------|---------|
| 1 | 2026-01-01 | Nord | Stylo | 2.50 |
| 2 | 2026-01-01 | Sud | Cahier | 4.00 |
| 3 | 2026-01-02 | Nord | Stylo | 2.50 |

Sur le disque (rowstore), les valeurs sont regroupées **par ligne** :
```
[1│2026-01-01│Nord│Stylo│2.50][2│2026-01-01│Sud│Cahier│4.00][3│2026-01-02│Nord│Stylo│2.50]
└──────── ligne 1 ────────┘└──────── ligne 2 ────────┘└──────── ligne 3 ────────┘
```

➡️ **Parfait pour l'OLTP** : « donne-moi toute la vente n°2 » se traduit par la lecture d'une seule zone contiguë. Idéal pour récupérer ou modifier une ligne entière.

➡️ **Problématique pour l'analytique** : pour calculer `SUM(Montant)`, SQL Server doit lire **toutes les lignes en entier** (donc aussi `Date`, `Region`, `Produit`…) juste pour extraire une seule colonne. On lit énormément de données inutiles.

---

## Le stockage en colonnes (columnstore)

Le columnstore retourne complètement la logique : il regroupe les valeurs **par colonne**.

Sur le disque (columnstore) :
```
Colonne VenteID : [1, 2, 3, ...]
Colonne Date    : [2026-01-01, 2026-01-01, 2026-01-02, ...]
Colonne Region  : [Nord, Sud, Nord, ...]
Colonne Produit : [Stylo, Cahier, Stylo, ...]
Colonne Montant : [2.50, 4.00, 2.50, ...]
```

➡️ Pour calculer `SUM(Montant)`, SQL Server lit **uniquement** le bloc de la colonne `Montant`. Sur une table de 50 colonnes, il ignore 49 colonnes : l'économie d'entrées/sorties est gigantesque.

---

## Pourquoi la compression est si efficace par colonne

C'est l'avantage le plus spectaculaire. Une colonne contient des valeurs **du même type** et souvent **très répétitives**. SQL Server exploite cela avec plusieurs techniques :

### 1. L'encodage par dictionnaire (dictionary encoding)

La colonne `Region` ne contient que quelques valeurs distinctes (`Nord`, `Sud`, `Est`, `Ouest`). On les stocke **une seule fois** dans un dictionnaire, et la colonne ne contient plus que de petits **numéros** :

```
Dictionnaire : 0=Nord, 1=Sud, 2=Est, 3=Ouest
Colonne Region : [0, 1, 0, 2, 0, 1, 3, ...]   ← des entiers minuscules
```

### 2. L'encodage par plages (run-length encoding)

Si une valeur se répète, on stocke « la valeur **× le nombre de répétitions** » :

```
Au lieu de : Nord, Nord, Nord, Nord, Nord
On stocke  : (Nord × 5)
```

### 3. L'encodage de valeurs (value encoding)

Pour les nombres, SQL Server peut réduire l'amplitude (par exemple en retranchant une base commune) pour utiliser moins de bits.

> 🧠 **Analogie** : dans une bibliothèque, ranger les livres par **thème** (colonne) plutôt qu'au hasard permet de les décrire de façon très compacte : « rayon entier de romans policiers » prend une ligne, au lieu de décrire chaque livre individuellement.

**Résultat concret** : là où le rowstore atteint péniblement un facteur 1,5× à 2× de compression, le columnstore atteint couramment **10×**, parfois bien plus. Moins de données = moins d'I/O = requêtes plus rapides **et** stockage réduit.

---

## L'élimination de segments (rowgroup elimination)

SQL Server conserve, pour chaque segment de colonne, les **valeurs minimale et maximale**. Lors d'une requête filtrée, il peut **ignorer des segments entiers** sans les lire :

```sql
SELECT SUM(Montant) FROM Ventes WHERE Date >= '2026-01-01';
```

Si un segment contient uniquement des dates de 2024, son min/max indique « tout est < 2026-01-01 » → SQL Server **saute** ce segment sans le lire. Sur des années d'historique, cela évite de lire la quasi-totalité des données anciennes.

---

## Exemple chiffré

Imaginons une table de faits de **200 millions** de lignes, 40 colonnes, occupant **80 Go** en rowstore. Une requête `SUM(Montant) GROUP BY Region` :

| | Rowstore | Columnstore |
|---|---|---|
| Taille sur disque | ~80 Go | ~8 Go (compression 10×) |
| Données lues pour la requête | ~80 Go (toutes colonnes) | ~quelques centaines de Mo (2 colonnes, segments filtrés) |
| Mode d'exécution | Ligne par ligne | **Batch** (~900 lignes/lot) |
| Temps typique | Plusieurs minutes | Quelques secondes |

---

## La contrepartie : reconstruire une ligne coûte cher

Rien n'est gratuit. Pour récupérer **une ligne complète** (« toutes les infos de la vente n°2 »), le columnstore doit aller chercher la valeur dans **chaque** colonne séparément, puis recoller le tout. C'est l'inverse du rowstore.

➡️ C'est pourquoi le columnstore est **mauvais pour l'OLTP** (recherches d'une seule ligne, mises à jour fréquentes) et **excellent pour l'OLAP** (agrégations sur de larges volumes). Le bon outil dépend de la question posée.

---

## Pour visualiser : une démonstration

Imaginons deux versions de la même table de ventes : `Ventes_Rowstore` (classique) et `Ventes_CCI` (avec index columnstore cluster). La même requête analytique se comporte très différemment :

```sql
-- Agrégation sur des millions de lignes
SELECT Region, SUM(Montant) AS CA
FROM Ventes_Rowstore   -- doit parcourir toutes les lignes (toutes colonnes)
GROUP BY Region;

SELECT Region, SUM(Montant) AS CA
FROM Ventes_CCI        -- ne lit que les colonnes Region et Montant, en mode batch
GROUP BY Region;
```

Dans le **plan d'exécution** (voir §7.3), la version rowstore montre un *Table/Index Scan* traité ligne par ligne, tandis que la version columnstore montre un *Columnstore Index Scan* en **mode batch** : ce dernier ne touche que deux colonnes et traite les lignes par paquets, d'où un temps souvent divisé par 10 ou plus.

## Pièges courants

| Piège | Explication |
|-------|-------------|
| Comparer les deux sur une **petite table** | Sur peu de lignes, le columnstore n'a aucun avantage |
| Attendre un gain sur une requête qui lit **toutes les colonnes** | L'atout « lecture ciblée » disparaît avec `SELECT *` |
| Oublier le coût de **reconstruction de ligne** | Une requête OLTP (1 ligne, toutes colonnes) est plus lente en columnstore |

## Questions fréquentes

**Q : La compression columnstore est-elle « gratuite » ?**
R : Elle coûte un peu de CPU à l'écriture, mais réduit fortement les I/O à la lecture — excellent compromis pour l'analytique.

**Q : Puis-je mesurer le taux de compression réel ?**
R : Oui, via la vue `sys.dm_db_column_store_row_group_physical_stats` (taille et nombre de lignes par rowgroup).

**Q : Quelle différence entre « segment » et « rowgroup » ?**
R : Un **rowgroup** regroupe ~1 M de lignes ; à l'intérieur, chaque colonne forme un **segment** compressé indépendamment (détaillé en §8.7.2).

---

## Résumé

- Le **rowstore** stocke les valeurs **par ligne** : idéal pour récupérer/modifier une ligne entière (OLTP).
- Le **columnstore** stocke les valeurs **par colonne** : idéal pour agréger une colonne sur des millions de lignes (OLAP).
- La compression par colonne (**dictionnaire**, **run-length**, **value encoding**) atteint couramment **10×**.
- Ne lire **que les colonnes utiles** + **l'élimination de segments** réduisent massivement les I/O.
- Contrepartie : **reconstruire une ligne complète** est coûteux → columnstore inadapté à l'OLTP fin.

Voyons maintenant les deux façons de créer un index columnstore : *clustered* et *non-clustered*.
