# 8.10.2 Procédures stockées compilées en mode natif

## Introduction

Les tables à mémoire optimisée (§8.10.1) suppriment la contention des verrous. Mais il reste une autre source de lenteur : la façon dont SQL Server **exécute le code T-SQL**. C'est là qu'interviennent les **procédures stockées compilées nativement** (*natively compiled stored procedures*), le second pilier d'In-Memory OLTP, qui transforme votre T-SQL en **code machine**.

---

## Interprété vs compilé nativement

### Une procédure classique : interprétée

Une procédure stockée classique est, à l'exécution, **interprétée** : le moteur lit les instructions une à une et les traduit à la volée en opérations. C'est flexible, mais cela coûte des cycles processeur à chaque exécution.

### Une procédure compilée nativement

Une procédure compilée nativement est traduite **une fois** (à sa création) en **code machine** — concrètement, une **DLL** chargée par SQL Server. À l'exécution, il n'y a plus d'interprétation : le processeur exécute directement les instructions.

```
   Procédure classique :   T-SQL ──(interprété à CHAQUE exécution)──▶ résultat
   Procédure native    :   T-SQL ──(compilé UNE fois en DLL)──▶ exécutions directes
```

> 🧠 **Analogie** : l'interprété, c'est lire une recette en la traduisant d'une langue étrangère à chaque fois que vous cuisinez. Le natif, c'est avoir traduit la recette **une bonne fois pour toutes** : vous cuisinez ensuite à pleine vitesse.

Combinée aux tables à mémoire optimisée, cette compilation réduit drastiquement le nombre d'instructions CPU par transaction — d'où les gains spectaculaires sur les charges intenses.

---

## Syntaxe d'une procédure native

```sql
CREATE PROCEDURE dbo.EnregistrerCommande
    @CommandeID INT,
    @ClientID   INT,
    @Montant    DECIMAL(12,2)
WITH NATIVE_COMPILATION, SCHEMABINDING
AS
BEGIN ATOMIC WITH
(
    TRANSACTION ISOLATION LEVEL = SNAPSHOT,
    LANGUAGE = N'French'
)
    INSERT INTO dbo.Commandes_MO (CommandeID, ClientID, DateCommande, Montant)
    VALUES (@CommandeID, @ClientID, SYSDATETIME(), @Montant);
END;
```

Trois éléments sont **obligatoires** et caractéristiques :

| Élément | Rôle |
|---------|------|
| `WITH NATIVE_COMPILATION` | Demande la compilation en code machine |
| `SCHEMABINDING` | Lie la procédure aux tables (elles ne peuvent plus être modifiées sans la recréer) |
| `BEGIN ATOMIC WITH (...)` | Bloc atomique : la procédure **est** une transaction, avec isolation et langue explicites |

### Le bloc ATOMIC

Le `BEGIN ATOMIC ... END` remplace le `BEGIN TRAN`/`COMMIT` classique :
- Tout le bloc s'exécute comme **une transaction atomique** (tout ou rien).
- S'il est appelé dans une transaction existante, il s'y joint ; sinon il en démarre une.
- On doit y préciser le **niveau d'isolation** (souvent `SNAPSHOT`) et la **langue** (pour le format des dates/messages).

---

## Pourquoi c'est si rapide

- ✅ **Aucune interprétation** à l'exécution (code machine direct).
- ✅ Accès aux **tables à mémoire optimisée** par des chemins optimisés.
- ✅ Moins d'appels système, meilleur usage du **cache CPU**.
- ✅ Idéal pour les opérations **répétées des millions de fois** (la compilation est amortie instantanément).

---

## Les limites du mode natif

La contrepartie de la performance est un **sous-ensemble** du T-SQL : tout n'est pas autorisé dans une procédure native. Au fil des versions (2014 très restreint, 2016+ beaucoup plus permissif), les limites se sont réduites, mais il faut savoir que :

- Les procédures natives n'accèdent qu'à des **tables à mémoire optimisée** (pas de jointure directe avec des tables sur disque).
- Certaines constructions T-SQL restent non supportées ou limitées (curseurs, certaines fonctions, requêtes très complexes selon la version).
- Le code est **figé** par `SCHEMABINDING` : modifier une table liée impose de recréer la procédure.

> 💡 En pratique : on réserve la compilation native aux **procédures critiques, simples et très fréquentes** (insertion d'un événement, mise à jour d'un compteur…). Le reste de l'application continue d'utiliser du T-SQL classique en *interop*.

---

## Stratégie d'adoption progressive

On n'a pas besoin de tout réécrire en natif d'un coup :

```
1. Identifier le point chaud (procédure exécutée des millions de fois,
   sur une table très sollicitée) — voir §7.3 sur les plans/goulots.
2. Migrer la table concernée en table à mémoire optimisée (§8.10.1).
3. Y accéder d'abord en T-SQL interprété (interop) → déjà un gain.
4. Compiler nativement la ou les procédures critiques → gain maximal.
5. Mesurer à chaque étape.
```

---

## Exemple comparatif

```sql
-- Version classique (interprétée) : accès interop à la table mémoire
CREATE PROCEDURE dbo.IncrementerCompteur_Interop @CompteurID INT
AS
BEGIN
    UPDATE Compteurs_MO SET Valeur = Valeur + 1 WHERE CompteurID = @CompteurID;
END;

-- Version compilée nativement : performances maximales
CREATE PROCEDURE dbo.IncrementerCompteur_Natif @CompteurID INT
WITH NATIVE_COMPILATION, SCHEMABINDING
AS
BEGIN ATOMIC WITH (TRANSACTION ISOLATION LEVEL = SNAPSHOT, LANGUAGE = N'French')
    UPDATE dbo.Compteurs_MO SET Valeur = Valeur + 1 WHERE CompteurID = @CompteurID;
END;
```

Sur un compteur incrémenté des millions de fois par minute, la version native, combinée à la table à mémoire optimisée, peut diviser le temps total par un facteur considérable.

---

## Questions fréquentes

**Q : Dois-je tout compiler nativement ?**
R : Non. Réservez-le aux procédures **simples, critiques et très fréquentes**. Le reste demeure en T-SQL classique.

**Q : Puis-je joindre une table mémoire et une table disque dans une procédure native ?**
R : Non directement. Pour cela, utilisez du T-SQL interprété (interop), qui accède aux deux mondes.

**Q : La compilation native rend-elle le développement plus complexe ?**
R : Oui, un peu (sous-ensemble T-SQL, `SCHEMABINDING`). D'où l'intérêt de ne l'appliquer que là où le gain le justifie.

---

## Résumé

- Une **procédure compilée nativement** est traduite **une fois** en **code machine** (DLL), au lieu d'être interprétée à chaque exécution.
- Elle s'écrit avec `WITH NATIVE_COMPILATION, SCHEMABINDING` et un bloc **`BEGIN ATOMIC`** (transaction + isolation + langue).
- Elle n'accède qu'aux **tables à mémoire optimisée** et n'autorise qu'un **sous-ensemble** du T-SQL.
- Stratégie : migrer d'abord la table, accéder en interop, puis compiler nativement **les seules procédures critiques**.
- À réserver aux opérations **simples et massivement répétées**.
