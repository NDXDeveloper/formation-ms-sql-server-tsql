# 5.7.1 Triggers - Concepts : Quand les utiliser (et quand ne pas les utiliser)

## Introduction aux Triggers

Un **trigger** (ou déclencheur en français) est un type spécial de procédure stockée qui s'exécute **automatiquement** en réponse à certains événements dans la base de données. Contrairement aux procédures stockées classiques que vous appelez explicitement, les triggers se déclenchent "tout seuls" lorsqu'une action spécifique se produit.

### Analogie pour comprendre

Imaginez un système d'alarme dans une maison :
- Vous ne déclenchez pas manuellement l'alarme
- Elle se déclenche automatiquement quand quelqu'un ouvre une porte ou une fenêtre
- Elle réagit à un événement précis

C'est exactement ainsi que fonctionnent les triggers : ils "surveillent" les tables et réagissent automatiquement à certaines opérations.

## Types d'événements surveillés

Les triggers peuvent réagir à trois types d'opérations principales sur les tables :

1. **INSERT** - Quand de nouvelles lignes sont ajoutées
2. **UPDATE** - Quand des lignes existantes sont modifiées
3. **DELETE** - Quand des lignes sont supprimées

## Caractéristiques importantes des Triggers

### Exécution automatique et transparente

Le point le plus important à comprendre : **les triggers s'exécutent sans que personne ne les appelle explicitement**.

```sql
-- Quand vous faites ceci :
INSERT INTO Employes (Nom, Prenom, Salaire)
VALUES ('Dupont', 'Jean', 35000);

-- Si un trigger existe sur la table Employes pour l'événement INSERT,
-- il s'exécutera automatiquement APRÈS (ou AVANT selon le type) cette insertion.
-- Vous ne voyez pas son exécution, mais elle a lieu !
```

### Invisibilité pour l'utilisateur

Les triggers travaillent "dans l'ombre". Un utilisateur qui insère des données dans une table ne sait pas forcément qu'un trigger s'est exécuté en arrière-plan. Cela peut être à la fois un avantage (automatisation) et un inconvénient (complexité cachée).

### Impact sur les performances

Chaque fois qu'un trigger se déclenche, cela ajoute du temps de traitement. Si vous insérez 1000 lignes et qu'un trigger se déclenche pour chaque ligne, cela peut significativement ralentir l'opération.

## Quand UTILISER les Triggers : Cas d'usage appropriés

### 1. Audit et Traçabilité

**Scénario** : Vous voulez garder une trace de toutes les modifications apportées à des données sensibles.

**Exemple concret** : Dans une table de clients, vous voulez enregistrer qui a modifié quoi et quand.

```sql
-- Sans trigger, il faudrait que CHAQUE application/utilisateur
-- ajoute manuellement une ligne dans la table d'audit.
-- Avec un trigger, c'est automatique et garanti !

CREATE TRIGGER trg_Audit_Clients
ON Clients
AFTER UPDATE
AS
BEGIN
    INSERT INTO Audit_Clients (ClientID, Modification, DateModif, Utilisateur)
    SELECT
        ClientID,
        'Modification du client',
        GETDATE(),
        SYSTEM_USER
    FROM INSERTED;
END;
```

**Pourquoi c'est approprié** :
- ✅ Garantit que l'audit est TOUJOURS fait, même si l'application "oublie"
- ✅ Centralise la logique d'audit au niveau de la base de données
- ✅ Impossible de contourner (sauf désactivation du trigger)

### 2. Maintien de l'intégrité référentielle complexe

**Scénario** : Les contraintes FOREIGN KEY standards ne suffisent pas pour votre logique métier.

**Exemple concret** : Vous voulez empêcher la suppression d'un client qui a des commandes "en cours", mais autoriser la suppression si toutes ses commandes sont "archivées".

```sql
CREATE TRIGGER trg_Prevent_Delete_Active_Client
ON Clients
INSTEAD OF DELETE
AS
BEGIN
    IF EXISTS (
        SELECT 1
        FROM Commandes c
        INNER JOIN DELETED d ON c.ClientID = d.ClientID
        WHERE c.Statut = 'En cours'
    )
    BEGIN
        RAISERROR('Impossible de supprimer un client avec des commandes en cours.', 16, 1);
        ROLLBACK TRANSACTION;
    END
    ELSE
    BEGIN
        -- Suppression autorisée
        DELETE FROM Clients
        WHERE ClientID IN (SELECT ClientID FROM DELETED);
    END
END;
```

**Pourquoi c'est approprié** :
- ✅ Règle métier complexe difficile à implémenter avec des contraintes simples
- ✅ Garantit la cohérence des données au niveau base de données

### 3. Dénormalisation contrôlée et colonnes calculées complexes

**Scénario** : Vous avez besoin de maintenir des totaux ou des compteurs pour des raisons de performance.

**Exemple concret** : Maintenir automatiquement le nombre total de commandes d'un client.

```sql
CREATE TRIGGER trg_Update_Client_Order_Count
ON Commandes
AFTER INSERT, DELETE
AS
BEGIN
    -- Mise à jour pour les nouveaux clients (INSERT)
    UPDATE c
    SET NombreCommandes = (
        SELECT COUNT(*)
        FROM Commandes
        WHERE ClientID = c.ClientID
    )
    FROM Clients c
    WHERE c.ClientID IN (SELECT ClientID FROM INSERTED);

    -- Mise à jour pour les clients dont on a supprimé des commandes (DELETE)
    UPDATE c
    SET NombreCommandes = (
        SELECT COUNT(*)
        FROM Commandes
        WHERE ClientID = c.ClientID
    )
    FROM Clients c
    WHERE c.ClientID IN (SELECT ClientID FROM DELETED);
END;
```

**Pourquoi c'est approprié** :
- ✅ Améliore les performances des requêtes de lecture
- ✅ Maintient automatiquement la cohérence du compteur

### 4. Validation de données complexe

**Scénario** : Validation métier qui dépasse ce que peut faire une contrainte CHECK.

**Exemple concret** : S'assurer qu'un employé ne peut pas être son propre manager, ni créer de boucle hiérarchique.

```sql
CREATE TRIGGER trg_Prevent_Circular_Management
ON Employes
AFTER INSERT, UPDATE
AS
BEGIN
    IF EXISTS (
        SELECT 1
        FROM INSERTED i
        WHERE i.EmployeID = i.ManagerID
    )
    BEGIN
        RAISERROR('Un employé ne peut pas être son propre manager.', 16, 1);
        ROLLBACK TRANSACTION;
    END

    -- Vérification plus complexe pour les boucles dans la hiérarchie
    -- (simplifié pour l'exemple)
END;
```

## Quand NE PAS UTILISER les Triggers : Pièges à éviter

### 1. ❌ Logique métier applicative

**Piège** : Mettre toute la logique métier dans des triggers.

**Pourquoi c'est problématique** :
- La logique devient **invisible** et difficile à déboguer
- Les applications ne peuvent pas gérer les erreurs de manière appropriée
- Impossible de tester facilement la logique hors de la base de données
- Difficile de maintenir et documenter

**Exemple de mauvaise utilisation** :
```sql
-- MAUVAISE PRATIQUE !
CREATE TRIGGER trg_Calculate_Order_Total
ON Commandes
AFTER INSERT
AS
BEGIN
    -- Calcul du prix total, application de remises,
    -- envoi d'email de confirmation, etc.
    -- Tout ça caché dans un trigger !
END;
```

**Meilleure approche** :
- Faire les calculs dans l'application
- Utiliser des procédures stockées explicites que l'application appelle
- Garder les triggers pour des tâches simples et systématiques

### 2. ❌ Opérations longues et coûteuses

**Piège** : Effectuer des opérations lentes dans un trigger (appels externes, traitements lourds).

**Pourquoi c'est problématique** :
- **Bloque** la transaction de l'utilisateur
- Dégrade drastiquement les performances
- L'utilisateur ne comprend pas pourquoi son INSERT prend 30 secondes

**Exemple de mauvaise utilisation** :
```sql
-- MAUVAISE PRATIQUE !
CREATE TRIGGER trg_Send_Email_On_Insert
ON Clients
AFTER INSERT
AS
BEGIN
    -- Appel d'une procédure externe qui envoie un email
    -- Si le serveur d'email est lent, toute l'insertion est ralentie !
    EXEC msdb.dbo.sp_send_dbmail ...
END;
```

**Meilleure approche** :
- Insérer un enregistrement dans une table de "file d'attente"
- Avoir un processus séparé qui traite cette file de manière asynchrone

### 3. ❌ Cascade de triggers (triggers qui appellent d'autres triggers)

**Piège** : Un trigger sur la table A modifie la table B, ce qui déclenche un trigger sur B, qui modifie C, etc.

**Pourquoi c'est problématique** :
- **Très difficile à déboguer** : effet domino imprévisible
- Problèmes de performance en cascade
- Risque de boucles infinies
- Impossibilité de comprendre le flux d'exécution

**Exemple de situation à éviter** :
```sql
-- Sur la table Commandes
CREATE TRIGGER trg_Update_Stock
ON Commandes AFTER INSERT
AS BEGIN
    UPDATE Stock SET Quantite = Quantite - 1 ...
END;

-- Sur la table Stock
CREATE TRIGGER trg_Alert_Low_Stock
ON Stock AFTER UPDATE
AS BEGIN
    INSERT INTO Alertes ...
END;

-- Sur la table Alertes
CREATE TRIGGER trg_Notify_Manager
ON Alertes AFTER INSERT
AS BEGIN
    UPDATE Managers SET HasAlerts = 1 ...
END;

-- Un simple INSERT dans Commandes déclenche 3 triggers en cascade !
-- Bonne chance pour déboguer quand ça ne marche pas...
```

### 4. ❌ Pour compenser une mauvaise conception de base de données

**Piège** : Utiliser des triggers pour "réparer" un schéma de base de données mal conçu.

**Pourquoi c'est problématique** :
- Cache les problèmes structurels
- Rend la base de données plus complexe
- Ne résout pas le problème de fond

**Exemple** :
```sql
-- Si vous avez besoin d'un trigger pour maintenir constamment
-- la cohérence entre deux tables, c'est probablement que
-- votre modèle de données n'est pas bien normalisé !
```

**Meilleure approche** :
- Revoir la conception de la base de données
- Normaliser correctement
- Utiliser les bonnes contraintes d'intégrité référentielle

### 5. ❌ Opérations qui devraient être contrôlées par l'utilisateur

**Piège** : Automatiser des décisions qui devraient être prises par l'utilisateur ou l'application.

**Exemple** :
```sql
-- MAUVAISE PRATIQUE !
CREATE TRIGGER trg_Auto_Archive
ON Commandes
AFTER UPDATE
AS
BEGIN
    -- Archive automatiquement les commandes de plus de 6 mois
    -- Mais que se passe-t-il si l'utilisateur voulait juste corriger une faute de frappe ?
END;
```

## Règles d'or pour l'utilisation des Triggers

### ✅ Utilisez les triggers pour :

1. **L'audit et la traçabilité** - C'est leur usage le plus légitime
2. **Maintenir l'intégrité des données** - Quand les contraintes standards ne suffisent pas
3. **Automatiser des tâches systématiques simples** - Qui doivent TOUJOURS se produire
4. **Éviter la duplication de code** - Quand plusieurs applications accèdent à la même table

### ❌ N'utilisez PAS les triggers pour :

1. **La logique métier complexe** - Gardez-la dans l'application
2. **Les opérations longues** - Utilisez des processus asynchrones
3. **Remplacer une bonne conception** - Corrigez le schéma à la source
4. **Tout ce qui peut être fait avec des contraintes standards** - Préférez PRIMARY KEY, FOREIGN KEY, CHECK

## Principe directeur : La simplicité et la transparence

**Question à vous poser avant de créer un trigger** :

> "Si quelqu'un d'autre modifie cette table dans 6 mois, sera-t-il surpris par le comportement du trigger ? Sera-ce facile à comprendre et à maintenir ?"

Si la réponse est non, reconsidérez votre approche.

## Documentation : Une obligation morale

Si vous créez des triggers, **documentez-les abondamment** :

```sql
/*
==================================================================
TRIGGER: trg_Audit_Salaires
AUTEUR: Jean Dupont
DATE: 2024-01-15
OBJECTIF: Enregistre toute modification de salaire pour l'audit RH
DÉCLENCHÉ PAR: UPDATE sur la colonne Salaire de la table Employes
TABLES IMPACTÉES: Audit_Salaires
NOTES: Ce trigger est requis pour la conformité RGPD
==================================================================
*/
CREATE TRIGGER trg_Audit_Salaires
ON Employes
AFTER UPDATE
AS
...
```

## Conclusion

Les triggers sont des outils **puissants mais dangereux**. Comme un scalpel chirurgical, ils peuvent être extrêmement utiles dans de bonnes mains, mais peuvent causer des dégâts si utilisés sans discernement.

**Règle de sagesse** : En cas de doute, demandez-vous si vous pouvez accomplir la même chose avec :
1. Une contrainte standard (PRIMARY KEY, FOREIGN KEY, CHECK)
2. Une valeur par défaut (DEFAULT)
3. Une colonne calculée (COMPUTED COLUMN)
4. Une procédure stockée explicite

Si la réponse est oui, **n'utilisez pas de trigger**.

Les triggers devraient être votre **dernier recours**, pas votre premier choix !
