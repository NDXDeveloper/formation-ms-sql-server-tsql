# 2.1.2 Types de chaînes (CHAR, VARCHAR, NCHAR, NVARCHAR)

## Introduction

Les types de chaînes de caractères permettent de stocker du texte dans une base de données : noms, prénoms, adresses, descriptions, commentaires, etc. SQL Server propose plusieurs types de chaînes, chacun avec ses particularités et ses usages spécifiques.

Comprendre la différence entre ces types est essentiel pour optimiser l'espace de stockage et garantir que vos données textuelles sont correctement gérées, notamment pour les caractères spéciaux et internationaux.

---

## Les deux grandes questions à se poser

Avant de choisir un type de chaîne, posez-vous deux questions :

1. **La longueur du texte est-elle fixe ou variable ?**
   - Fixe → CHAR ou NCHAR
   - Variable → VARCHAR ou NVARCHAR

2. **Ai-je besoin de stocker des caractères internationaux (Unicode) ?**
   - Oui → NCHAR ou NVARCHAR (préfixe **N**)
   - Non → CHAR ou VARCHAR

---

## 1. CHAR : Chaînes de longueur fixe

### Qu'est-ce que CHAR ?

**CHAR** (ou CHARACTER) est un type de chaîne de **longueur fixe**. Cela signifie que SQL Server réserve toujours le même espace de stockage, quelle que soit la longueur réelle du texte inséré.

**Syntaxe :** `CHAR(n)`
- **n** : longueur fixe (de 1 à 8000 caractères)

**Caractéristiques :**
- **Longueur fixe** : occupe toujours n octets
- **Remplissage automatique** : si le texte est plus court, SQL Server ajoute des espaces à la fin
- **Encodage** : ASCII/ANSI (ne supporte pas tous les caractères internationaux)

### Comment fonctionne CHAR ?

Imaginons une colonne définie comme `CHAR(10)` :

```sql
CREATE TABLE Exemple (
    Code CHAR(10)
);

INSERT INTO Exemple (Code) VALUES ('ABC');
```

**Que se passe-t-il ?**
- Vous insérez 'ABC' (3 caractères)
- SQL Server stocke 'ABC       ' (3 caractères + 7 espaces)
- L'espace occupé : **toujours 10 octets**

### Quand utiliser CHAR ?

**CHAR est idéal pour :**
- ✅ Codes de pays (FR, US, UK) → `CHAR(2)`
- ✅ Codes postaux de longueur fixe → `CHAR(5)` pour les codes postaux américains
- ✅ Codes de produits standardisés → `CHAR(10)`
- ✅ Tout identifiant ou code de longueur fixe et garantie

**CHAR n'est PAS recommandé pour :**
- ❌ Noms de personnes (longueur variable)
- ❌ Adresses (longueur variable)
- ❌ Descriptions ou commentaires
- ❌ Tout texte dont la longueur varie

### Exemple pratique avec CHAR

```sql
CREATE TABLE Pays (
    PaysID INT,
    CodeISO CHAR(2),        -- FR, US, UK, etc.
    CodeISO3 CHAR(3),       -- FRA, USA, GBR, etc.
    CodePostalFormat CHAR(5) -- Pour certains formats fixes
);

INSERT INTO Pays (PaysID, CodeISO, CodeISO3, CodePostalFormat)
VALUES
    (1, 'FR', 'FRA', '75001'),
    (2, 'US', 'USA', '90210'),
    (3, 'UK', 'GBR', 'SW1A1');
```

## 2. VARCHAR : Chaînes de longueur variable

### Qu'est-ce que VARCHAR ?

**VARCHAR** (ou **VAR**iable **CHAR**acter) est un type de chaîne de **longueur variable**. SQL Server n'utilise que l'espace nécessaire pour stocker le texte réel, plus 2 octets pour enregistrer la longueur.

**Syntaxe :** `VARCHAR(n)` ou `VARCHAR(MAX)`
- **n** : longueur maximale (de 1 à 8000 caractères)
- **MAX** : jusqu'à 2 Go de données

**Caractéristiques :**
- **Longueur variable** : occupe uniquement l'espace nécessaire
- **Pas de remplissage** : pas d'espaces ajoutés automatiquement
- **Encodage** : ASCII/ANSI
- **Plus efficace** : pour les textes de longueurs variables

### Comment fonctionne VARCHAR ?

Imaginons une colonne définie comme `VARCHAR(100)` :

```sql
CREATE TABLE Exemple (
    Nom VARCHAR(100)
);

INSERT INTO Exemple (Nom)
VALUES
    ('Alice'),
    ('Jean-Philippe');
```

**Que se passe-t-il ?**
- 'Alice' occupe : 5 octets + 2 octets (longueur) = **7 octets**
- 'Jean-Philippe' occupe : 14 octets + 2 octets = **16 octets**
- L'espace occupé **varie** selon le contenu réel

### Quand utiliser VARCHAR ?

**VARCHAR est idéal pour :**
- ✅ Noms et prénoms
- ✅ Adresses
- ✅ Titres et descriptions
- ✅ Emails
- ✅ Tout texte de longueur variable

**VARCHAR(MAX) pour :**
- ✅ Textes très longs (articles, commentaires, descriptions détaillées)
- ✅ Documents textuels
- ⚠️ Attention : impact sur les performances pour les très grandes valeurs

### Exemple pratique avec VARCHAR

```sql
CREATE TABLE Clients (
    ClientID INT,
    Nom VARCHAR(100),
    Prenom VARCHAR(100),
    Email VARCHAR(255),
    Adresse VARCHAR(500),
    Commentaires VARCHAR(MAX)  -- Pour de longs textes
);

INSERT INTO Clients (ClientID, Nom, Prenom, Email, Adresse, Commentaires)
VALUES
    (1, 'Dupont', 'Marie', 'marie.dupont@email.fr', '15 rue de la Paix, 75001 Paris', 'Client fidèle depuis 2020'),
    (2, 'Li', 'Wei', 'wei.li@email.com', '42 avenue des Champs, 75008 Paris', NULL);
```

## 3. La différence entre CHAR et VARCHAR

### Comparaison visuelle

| Critère | CHAR(10) | VARCHAR(10) |
|---------|----------|-------------|
| **Stockage de 'ABC'** | 'ABC       ' (10 octets) | 'ABC' (5 octets : 3 + 2) |
| **Stockage de 'ABCDEFGHIJ'** | 'ABCDEFGHIJ' (10 octets) | 'ABCDEFGHIJ' (12 octets : 10 + 2) |
| **Espace occupé** | Toujours fixe | Variable selon le contenu |
| **Performance** | Légèrement plus rapide | Légèrement plus lent |
| **Flexibilité** | Faible | Élevée |

### Règle générale : VARCHAR est plus courant

**Dans 90% des cas, utilisez VARCHAR** car :
- Il économise de l'espace
- Il s'adapte automatiquement au contenu
- La différence de performance est négligeable dans la plupart des cas

**Utilisez CHAR uniquement** pour les données de longueur strictement fixe et garantie.

## 4. NCHAR et NVARCHAR : Support Unicode

### Qu'est-ce que l'Unicode ?

**Unicode** est un système d'encodage qui permet de représenter pratiquement tous les caractères de toutes les langues du monde : caractères accentués, alphabets cyrilliques, chinois, japonais, arabe, émojis, etc.

**Problème avec CHAR et VARCHAR :**
- Ils utilisent l'encodage ASCII/ANSI
- Limités à 256 caractères possibles
- Ne peuvent pas stocker correctement les caractères comme : 你好, Привет, مرحبا, 😀

**Solution : NCHAR et NVARCHAR**
- Le préfixe **N** signifie "National" (pour Unicode)
- Supportent l'encodage UTF-16
- Peuvent stocker tous les caractères Unicode

### NCHAR : Unicode de longueur fixe

**Syntaxe :** `NCHAR(n)`
- **n** : longueur fixe (de 1 à 4000 caractères)
- **Stockage** : 2 octets par caractère

**Exemple :**

```sql
CREATE TABLE Traductions (
    LangueCode CHAR(2),
    TexteOriginal NCHAR(50)  -- Longueur fixe Unicode
);
```

### NVARCHAR : Unicode de longueur variable

**Syntaxe :** `NVARCHAR(n)` ou `NVARCHAR(MAX)`
- **n** : longueur maximale (de 1 à 4000 caractères)
- **MAX** : jusqu'à 2 Go
- **Stockage** : 2 octets par caractère + 2 octets pour la longueur

**Exemple :**

```sql
CREATE TABLE Utilisateurs (
    UtilisateurID INT,
    Nom NVARCHAR(100),         -- Supporte tous les alphabets
    NomUtilisateur NVARCHAR(50),
    BiographieMultilingue NVARCHAR(MAX)
);

INSERT INTO Utilisateurs (UtilisateurID, Nom, NomUtilisateur, BiographieMultilingue)
VALUES
    (1, N'François', N'françois123', N'Développeur passionné 🚀'),
    (2, N'李明', N'liming', N'你好！Je parle chinois et français'),
    (3, N'Дмитрий', N'dmitry', N'Привет из России');
```

**⚠️ Important :** Notez le préfixe **N** devant les chaînes littérales : `N'texte'`

### Pourquoi le N devant les chaînes ?

Quand vous écrivez un littéral texte **sans** préfixe N, SQL Server l'interprète d'abord comme du **VARCHAR**, selon la *code page* (jeu de caractères) de la base. Les caractères **absents** de cette code page sont alors définitivement perdus et remplacés par `?`.

```sql
-- ❌ Sans N : le littéral transite par VARCHAR avant d'entrer dans la colonne
INSERT INTO Utilisateurs (Nom) VALUES ('你好');   -- stocké comme '??'

-- ✅ Avec N : le littéral est traité comme de l'Unicode dès le départ
INSERT INTO Utilisateurs (Nom) VALUES (N'你好');  -- stocké comme '你好'
```

| Littéral | Sans N | Avec N |
|----------|--------|--------|
| `'你好'` (chinois) | `??` ❌ | `你好` ✅ |
| `'Привет'` (cyrillique) | `??????` ❌ | `Привет` ✅ |
| `'François'` (accents latins) | dépend de la code page ⚠️ | `François` ✅ |

> ⚠️ **Nuance importante** — Sur une installation occidentale (code page 1252, la plus courante en Europe), les accents latins (é, à, ç…) sont **généralement préservés même sans le N**, car ils font partie de cette code page. Mais ce n'est **pas garanti** sur toutes les configurations, et cela échoue toujours pour les autres alphabets. **Règle simple et sûre : mettez toujours le N** devant un littéral destiné à une colonne `NCHAR`/`NVARCHAR`.

## 5. Comparaison complète des quatre types

### Tableau récapitulatif

| Type | Longueur | Unicode | Stockage | Utilisation typique |
|------|----------|---------|----------|---------------------|
| **CHAR(n)** | Fixe | Non | n octets | Codes fixes (ISO pays) |
| **VARCHAR(n)** | Variable | Non | Texte + 2 octets | Noms, emails (ASCII) |
| **NCHAR(n)** | Fixe | Oui | n × 2 octets | Codes Unicode fixes |
| **NVARCHAR(n)** | Variable | Oui | Texte × 2 + 2 octets | Texte international |

### Impact sur l'espace de stockage

**Exemple avec le prénom "Marie" :**

| Type | Espace occupé | Détail |
|------|---------------|--------|
| CHAR(50) | 50 octets | Toujours 50, même pour 5 caractères |
| VARCHAR(50) | 7 octets | 5 caractères + 2 octets de longueur |
| NCHAR(50) | 100 octets | 50 × 2 octets (Unicode) |
| NVARCHAR(50) | 12 octets | 5 × 2 + 2 octets de longueur |

**Exemple avec le prénom "你好" (2 caractères chinois) :**

| Type | Résultat | Explication |
|------|----------|-------------|
| CHAR(10) | ❌ Corrompu | Ne supporte pas Unicode |
| VARCHAR(10) | ❌ Corrompu | Ne supporte pas Unicode |
| NCHAR(10) | ✅ '你好        ' | 20 octets (10 × 2) |
| NVARCHAR(10) | ✅ '你好' | 6 octets (2 × 2 + 2) |

> 🔎 **Pour aller plus loin (SQL Server 2019+)** — Depuis SQL Server 2019, on peut attribuer une **collation UTF-8** (suffixe `_UTF8`) à une colonne `CHAR`/`VARCHAR`, qui devient alors capable de stocker de l'Unicode encodé en UTF-8. En UTF-8, un caractère ASCII tient sur **1 octet** (contre 2 en `NVARCHAR`/UTF-16), ce qui peut réduire la taille des textes majoritairement latins. Pour ce cours d'introduction, retenez la règle par défaut — **`NVARCHAR` pour l'international, `VARCHAR` pour l'ASCII pur** — tout en sachant que l'idée « VARCHAR ne supporte pas du tout l'Unicode » n'est plus tout à fait exacte sur les versions récentes.

## 6. Guide de choix : quel type utiliser ?

### Arbre de décision

```
Ai-je besoin de caractères internationaux (accents, autres alphabets, émojis) ?
│
├─ OUI → Unicode nécessaire
│   │
│   └─ La longueur est-elle fixe et garantie ?
│       │
│       ├─ OUI → NCHAR(n)
│       │
│       └─ NON → NVARCHAR(n) ← Le plus courant
│
└─ NON → ASCII suffit
    │
    └─ La longueur est-elle fixe et garantie ?
        │
        ├─ OUI → CHAR(n)
        │
        └─ NON → VARCHAR(n)
```

### Recommandations pratiques

**Dans le doute, utilisez NVARCHAR :**
- ✅ Supporte tous les caractères
- ✅ Longueur variable = économie d'espace
- ✅ Évite les problèmes futurs d'internationalisation
- ⚠️ Consomme 2× plus d'espace que VARCHAR pour du texte purement ASCII

**Utilisez VARCHAR si :**
- Vous êtes certain de n'avoir que des caractères ASCII (a-z, A-Z, 0-9, ponctuation de base)
- Vous voulez optimiser l'espace de stockage au maximum
- Exemple : codes internes, identifiants techniques

**Utilisez CHAR/NCHAR uniquement pour :**
- Codes de longueur strictement fixe
- Données standardisées (codes pays, etc.)

## 7. Exemples pratiques complets

### Exemple 1 : Table de produits e-commerce

```sql
CREATE TABLE Produits (
    ProduitID INT,
    SKU CHAR(10),                      -- Code produit fixe (ex: PROD000123)
    Nom NVARCHAR(200),                 -- Nom en plusieurs langues
    Description NVARCHAR(MAX),         -- Description longue et multilingue
    CodeBarre VARCHAR(13),             -- Code-barres (chiffres uniquement)
    UrlImage VARCHAR(500),             -- URL (ASCII suffit)
    Categorie NVARCHAR(100)            -- Catégorie multilingue
);

INSERT INTO Produits (ProduitID, SKU, Nom, Description, CodeBarre, UrlImage, Categorie)
VALUES
    (1, 'TECH000001', N'Ordinateur portable 15"', N'Description complète avec accents et émojis 💻', '1234567890123', 'https://cdn.example.com/img1.jpg', N'Électronique'),
    (2, 'BOOK000001', N'学习SQL Server', N'中文SQL Server教程书籍', '9876543210987', 'https://cdn.example.com/img2.jpg', N'图书');
```

### Exemple 2 : Table d'utilisateurs internationale

```sql
CREATE TABLE UtilisateursInternationaux (
    UserID INT,
    CodePays CHAR(2),                  -- Code ISO fixe
    NomUtilisateur VARCHAR(50),        -- Identifiant ASCII
    NomComplet NVARCHAR(100),          -- Nom avec accents
    Email VARCHAR(255),                -- Email (ASCII)
    Adresse NVARCHAR(500),             -- Adresse internationale
    LanguePrefere CHAR(2),             -- Code langue (EN, FR, ZH, etc.)
    Biographie NVARCHAR(MAX)           -- Texte libre multilingue
);

INSERT INTO UtilisateursInternationaux
VALUES
    (1, 'FR', 'jean_dupont', N'Jean Dupont', 'jean.dupont@email.fr', N'15 rue de la République, 75001 Paris', 'FR', N'Passionné de technologie'),
    (2, 'CN', 'wang_li', N'王丽', 'wang.li@email.com', N'北京市朝阳区建国路1号', 'ZH', N'软件工程师，喜欢编程');
```

### Exemple 3 : Gestion des accents et caractères spéciaux

```sql
-- Création de table avec différents types
CREATE TABLE TestEncodage (
    ID INT,
    TexteASCII VARCHAR(100),
    TexteUnicode NVARCHAR(100)
);

-- Insertion SANS le préfixe N : le caractère chinois est perdu
INSERT INTO TestEncodage (ID, TexteASCII, TexteUnicode)
VALUES (1, 'Bonjour', '你好 Bonjour');   -- ❌ '你好' transite par VARCHAR → '?? Bonjour'

-- Insertion AVEC le préfixe N : tout est préservé
INSERT INTO TestEncodage (ID, TexteASCII, TexteUnicode)
VALUES (2, 'Bonjour', N'你好 Bonjour');  -- ✅ '你好 Bonjour'

-- Vérification
SELECT * FROM TestEncodage;

/*
Résultat :
ID | TexteASCII | TexteUnicode
---+------------+----------------
1  | Bonjour    | ?? Bonjour       (le chinois est perdu, faute de N)
2  | Bonjour    | 你好 Bonjour      (préservé grâce au N)
*/
```

> Remarque : la colonne `TexteASCII` est en `VARCHAR` ; même avec un N, elle ne pourrait pas stocker « 你好 ». Ce sont le **type de la colonne** (`NVARCHAR`) **et** le préfixe `N` du littéral qui, ensemble, garantissent le stockage Unicode.

## 8. Règles et bonnes pratiques

### Règles de longueur

**Pour VARCHAR et NVARCHAR :**

```sql
-- ✅ Bonnes pratiques de dimensionnement
Prenom NVARCHAR(50)          -- Suffisant pour la plupart des prénoms
Nom NVARCHAR(100)            -- Noms de famille
Email VARCHAR(255)           -- Standard pour emails
MotDePasse VARCHAR(255)      -- Pour hashes (SHA-256, etc.)
Telephone VARCHAR(20)        -- Numéros internationaux
URL VARCHAR(2000)            -- URLs longues
Description NVARCHAR(MAX)    -- Textes sans limite précise

-- ❌ À éviter
Prenom NVARCHAR(10)          -- Trop court
Email VARCHAR(50)            -- Trop court pour certains emails
Description NVARCHAR(50000)  -- Utilisez MAX au lieu d'une très grande valeur
```

### Utilisation de MAX

**Quand utiliser VARCHAR(MAX) ou NVARCHAR(MAX) :**

```sql
-- ✅ Cas d'usage appropriés pour MAX
CREATE TABLE Articles (
    ArticleID INT,
    Titre NVARCHAR(200),
    Contenu NVARCHAR(MAX),      -- Articles de blog, longs textes
    Resume NVARCHAR(500)         -- Utilisez une limite si possible
);

-- ⚠️ Attention avec MAX
-- MAX peut contenir jusqu'à 2 Go, mais :
-- - Impact sur les performances
-- - Limitations dans certaines opérations (index, GROUP BY)
-- - Stockage externe (LOB) au-delà de 8000 octets
```

### Performances : VARCHAR vs NVARCHAR

**Impact sur les performances :**

1. **Taille des données :**
   - NVARCHAR occupe 2× l'espace de VARCHAR
   - Impact sur la mémoire et les I/O

2. **Comparaisons et tri :**
   - NVARCHAR légèrement plus lent pour les comparaisons
   - Différence négligeable dans la plupart des cas

3. **Index :**
   - Les index sur NVARCHAR sont plus volumineux (2 octets par caractère)
   - La **clé** d'un index est limitée à **900 octets** (index clustered) ou **1 700 octets** (index non-clustered, depuis SQL Server 2016)

**Recommandation :**
- Pour les applications internationales → **NVARCHAR** (le choix par défaut moderne)
- Pour les systèmes purement ASCII → **VARCHAR** (optimisation)

## 9. Pièges courants à éviter

### Piège 1 : Oublier le préfixe N

```sql
-- ❌ RISQUÉ : sans N, les caractères hors code page sont perdus
INSERT INTO Clients (Nom) VALUES ('Иван');   -- peut devenir '????'

-- ✅ SÛR : le N garantit le stockage Unicode dans tous les cas
INSERT INTO Clients (Nom) VALUES (N'Иван');
```

Prenez l'habitude de **toujours** préfixer par `N` les littéraux destinés à une colonne `NVARCHAR`/`NCHAR` : c'est sans risque et cela évite les mauvaises surprises avec les noms étrangers, les émojis ou les symboles spéciaux.

### Piège 2 : Utiliser CHAR pour des longueurs variables

```sql
-- ❌ ERREUR : gaspillage d'espace
CREATE TABLE Mauvais (
    Nom CHAR(100)  -- Occupera toujours 100 octets, même pour "Li"
);

-- ✅ CORRECT
CREATE TABLE Bon (
    Nom NVARCHAR(100)  -- Occupera seulement l'espace nécessaire
);
```

### Piège 3 : Longueurs insuffisantes

```sql
-- ❌ ERREUR : l'email sera tronqué
Email VARCHAR(50)  -- Trop court pour certains emails

-- ✅ CORRECT
Email VARCHAR(255)  -- Standard pour les emails
```

### Piège 4 : Confusion entre encodages

```sql
-- Table avec VARCHAR (ASCII)
CREATE TABLE Test (
    Texte VARCHAR(100)
);

-- ❌ Ceci ne fonctionnera pas correctement
INSERT INTO Test VALUES (N'你好');  -- Sera corrompu

-- ✅ Solution : utiliser NVARCHAR
ALTER TABLE Test ALTER COLUMN Texte NVARCHAR(100);
INSERT INTO Test VALUES (N'你好');  -- Maintenant correct
```

### Piège 5 : Oublier la longueur (n)

Si vous déclarez `VARCHAR`, `NVARCHAR`, `CHAR` ou `NCHAR` **sans préciser `(n)`**, la longueur par défaut n'est **pas** illimitée : elle vaut **1** dans une déclaration de colonne ou de variable !

```sql
-- ❌ PIÈGE : VARCHAR sans longueur = VARCHAR(1)
DECLARE @nom VARCHAR = 'Dupont';
SELECT @nom;            -- 'D'  (tronqué à 1 seul caractère !)

CREATE TABLE Test (Code CHAR);   -- CHAR(1) : un seul caractère

-- ✅ CORRECT : toujours préciser la longueur
DECLARE @nom VARCHAR(50) = 'Dupont';
SELECT @nom;            -- 'Dupont'
```

> 📝 **Subtilité** — Avec `CAST`/`CONVERT`, la longueur par défaut est **30** (et non 1) : `CAST(x AS VARCHAR)` revient à `CAST(x AS VARCHAR(30))`. Pour éviter toute surprise, **indiquez toujours `(n)` explicitement**.

## 10. Conversion entre types de chaînes

### Conversion explicite avec CAST ou CONVERT

```sql
-- De VARCHAR vers NVARCHAR
DECLARE @texteASCII VARCHAR(50) = 'Bonjour';
DECLARE @texteUnicode NVARCHAR(50);

SET @texteUnicode = CAST(@texteASCII AS NVARCHAR(50));
-- ou
SET @texteUnicode = CONVERT(NVARCHAR(50), @texteASCII);

-- Attention : la conversion inverse peut perdre des données
DECLARE @texteAvecAccents NVARCHAR(50) = N'François';
DECLARE @texteConverti VARCHAR(50);

SET @texteConverti = CAST(@texteAvecAccents AS VARCHAR(50));
-- Résultat possible : 'Francois' (perte des accents)
```

### Truncation (troncature)

```sql
-- Si le texte est trop long, il sera tronqué
DECLARE @longTexte VARCHAR(100) = 'Ceci est un très long texte qui dépasse la limite';
DECLARE @texteCoupe VARCHAR(20);

-- ⚠️ Ceci générera une erreur (par défaut)
SET @texteCoupe = @longTexte;  -- Erreur : chaîne tronquée

-- Solution : utiliser LEFT pour couper explicitement
SET @texteCoupe = LEFT(@longTexte, 20);  -- 'Ceci est un très lon'
```

## Points clés à retenir

✅ **NVARCHAR(n)** : le choix par défaut moderne pour la plupart des textes (supporte Unicode)

✅ **VARCHAR(n)** : pour les textes purement ASCII (emails, URLs, codes techniques)

✅ **CHAR(n) / NCHAR(n)** : uniquement pour des longueurs strictement fixes

✅ **Toujours utiliser le préfixe N** devant les chaînes Unicode : `N'texte'`

✅ **MAX** : pour les textes très longs sans limite précise (articles, commentaires)

✅ **Dimensionnement** : ne soyez pas trop restrictif, mais évitez les valeurs excessives

❌ **N'utilisez pas CHAR** pour des données de longueur variable

❌ **N'oubliez pas le N** pour les caractères accentués et internationaux

---

## Conclusion

Le choix du bon type de chaîne impacte :
- **L'intégrité des données** : Unicode vs ASCII
- **L'espace de stockage** : longueur fixe vs variable
- **Les performances** : taille des index et des requêtes
- **La compatibilité internationale** : support multilingue

**En pratique, pour les applications modernes :**
- Utilisez **NVARCHAR** par défaut (sauf pour les colonnes purement techniques)
- Dimensionnez raisonnablement (ni trop petit, ni trop grand)
- Utilisez **MAX** avec parcimonie
- N'oubliez jamais le **N** devant vos chaînes Unicode

Avec ces connaissances, vous êtes maintenant capable de choisir le type de chaîne approprié pour chaque situation et d'éviter les problèmes d'encodage courants dans SQL Server !
