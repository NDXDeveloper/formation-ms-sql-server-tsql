# 7.6.1 Le concept de SARGability (Rendre les prédicats "recherchables")

## Qu'est-ce que la SARGability ?

**SARGability** est un terme qui vient de "**S**earch **ARG**ument **ABLE**" - littéralement "capable d'être un argument de recherche". C'est la capacité d'une condition (prédicat) dans votre clause WHERE à utiliser efficacement les index pour trouver des données.

### La définition simple

Un prédicat est **SARGable** quand SQL Server peut utiliser un index pour trouver rapidement les lignes qui correspondent à la condition, plutôt que de devoir scanner toute la table.

### Analogie : La bibliothèque

Imaginez que vous cherchez un livre dans une bibliothèque :

**Recherche SARGable (avec l'index - le catalogue)** :
```
Vous demandez : "Je cherche tous les livres dont le titre commence par 'SQL'"
Bibliothécaire : "Parfait, j'utilise le catalogue alphabétique"
                  "Section S, entre 'SQL' et 'SQM'"
                  → Recherche directe et rapide
```

**Recherche non-SARGable (sans pouvoir utiliser l'index)** :
```
Vous demandez : "Je cherche tous les livres dont le titre en majuscules contient 'SQL'"
Bibliothécaire : "Je ne peux pas utiliser le catalogue pour ça"
                  "Je dois parcourir TOUS les livres un par un"
                  "Convertir chaque titre en majuscules"
                  "Puis vérifier s'il contient 'SQL'"
                  → Recherche exhaustive et lente
```

## Pourquoi la SARGability est cruciale ?

### L'impact sur les performances

La différence entre un prédicat SARGable et non-SARGable peut être **dramatique** :

```
Table avec 1 million de lignes :

Prédicat SARGable (Index Seek) :
- SQL Server consulte l'index
- Trouve directement les 100 lignes concernées
- Temps : 5 millisecondes
- Lectures : 150 pages

Prédicat non-SARGable (Table Scan) :
- SQL Server doit lire TOUTES les lignes
- Appliquer la condition sur chaque ligne
- Temps : 3 secondes
- Lectures : 50,000 pages

→ 600 fois plus lent !
```

### Index Seek vs Index Scan

**Index Seek (SARGable)** :
- Recherche ciblée dans l'index
- Ne lit que les données nécessaires
- Rapide et efficace
- Symbolisé par 📍 "pointage précis"

**Index Scan ou Table Scan (non-SARGable)** :
- Parcours complet de la table ou de l'index
- Lit toutes les données
- Lent et coûteux
- Symbolisé par 🔄 "balayage exhaustif"

## Les règles de la SARGability

Pour qu'un prédicat soit SARGable, il doit respecter ces règles fondamentales :

### Règle 1 : La colonne doit être isolée

**❌ NON-SARGable - Colonne modifiée**
```sql
WHERE YEAR(OrderDate) = 2024
```

**✅ SARGable - Colonne isolée**
```sql
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'
```

**Explication :** Dans le premier cas, SQL Server doit :
1. Lire chaque ligne
2. Appliquer la fonction YEAR() sur chaque OrderDate
3. Comparer le résultat avec 2024

Dans le second cas, SQL Server peut directement consulter l'index sur OrderDate.

### Règle 2 : Pas de fonctions sur la colonne indexée

**❌ NON-SARGable - Fonction sur la colonne**
```sql
WHERE UPPER(CustomerName) = 'DUPONT'
```

**✅ SARGable - Colonne directe**
```sql
WHERE CustomerName = 'DUPONT'
-- Ou si vraiment insensible à la casse :
WHERE CustomerName = 'DUPONT' COLLATE Latin1_General_CI_AS
```

### Règle 3 : Pas d'opérations arithmétiques sur la colonne

**❌ NON-SARGable - Opération sur la colonne**
```sql
WHERE Salary * 12 > 50000
```

**✅ SARGable - Opération déplacée**
```sql
WHERE Salary > 50000 / 12
```

### Règle 4 : Éviter les conversions implicites

**❌ NON-SARGable - Types incompatibles**
```sql
-- Si CustomerID est INT
WHERE CustomerID = '12345'  -- Chaîne de caractères
```

**✅ SARGable - Types correspondants**
```sql
WHERE CustomerID = 12345  -- Entier
```

## Les pièges courants et leurs solutions

### Piège 1 : Les fonctions de dates

#### ❌ Problème : Utilisation de fonctions

```sql
-- Trouver les commandes d'aujourd'hui
SELECT * FROM Orders
WHERE CAST(OrderDate AS DATE) = CAST(GETDATE() AS DATE);

-- Trouver les commandes de 2024
SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;

-- Trouver les commandes du mois actuel
SELECT * FROM Orders
WHERE MONTH(OrderDate) = MONTH(GETDATE())
  AND YEAR(OrderDate) = YEAR(GETDATE());
```

**Pourquoi c'est mauvais :**
- CAST(), YEAR(), MONTH() sont appliqués sur CHAQUE ligne
- L'index sur OrderDate ne peut pas être utilisé efficacement
- Table Scan garanti

#### ✅ Solution : Plages de dates

```sql
-- Trouver les commandes d'aujourd'hui
DECLARE @Today DATE = CAST(GETDATE() AS DATE);
SELECT * FROM Orders
WHERE OrderDate >= @Today
  AND OrderDate < DATEADD(DAY, 1, @Today);

-- Trouver les commandes de 2024
SELECT * FROM Orders
WHERE OrderDate >= '2024-01-01'
  AND OrderDate < '2025-01-01';

-- Trouver les commandes du mois actuel
DECLARE @StartOfMonth DATE = DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1);
DECLARE @StartOfNextMonth DATE = DATEADD(MONTH, 1, @StartOfMonth);
SELECT * FROM Orders
WHERE OrderDate >= @StartOfMonth
  AND OrderDate < @StartOfNextMonth;
```

**Pourquoi c'est mieux :**
- Les calculs sont faits UNE FOIS (sur les constantes)
- La colonne OrderDate n'est pas modifiée
- L'index peut être utilisé avec Index Seek

### Piège 2 : Les manipulations de chaînes

#### ❌ Problème : Fonctions sur la colonne

```sql
-- Recherche insensible à la casse (mauvaise approche)
SELECT * FROM Customers
WHERE UPPER(CustomerName) = 'MARTIN';

-- Recherche de sous-chaîne (mauvaise approche)
SELECT * FROM Customers
WHERE SUBSTRING(CustomerName, 1, 3) = 'MAR';

-- Suppression des espaces
SELECT * FROM Products
WHERE LTRIM(RTRIM(ProductCode)) = 'ABC123';
```

#### ✅ Solution : Techniques SARGable

```sql
-- Utiliser le collation approprié
SELECT * FROM Customers
WHERE CustomerName = 'Martin' COLLATE Latin1_General_CI_AS;  -- CI = Case Insensitive

-- Utiliser LIKE pour les préfixes
SELECT * FROM Customers
WHERE CustomerName LIKE 'MAR%';

-- Nettoyer les données à l'insertion plutôt qu'à la recherche
-- Ou créer une colonne calculée persistée et indexée
ALTER TABLE Products
ADD ProductCodeClean AS LTRIM(RTRIM(ProductCode)) PERSISTED;

CREATE INDEX IX_Products_ProductCodeClean ON Products(ProductCodeClean);

-- Puis rechercher sur la colonne nettoyée
SELECT * FROM Products
WHERE ProductCodeClean = 'ABC123';
```

### Piège 3 : LIKE avec wildcards à gauche

#### ❌ Problème : Wildcard au début

```sql
-- Recherche se terminant par 'son'
SELECT * FROM Customers
WHERE CustomerName LIKE '%son';

-- Recherche contenant 'martin'
SELECT * FROM Customers
WHERE CustomerName LIKE '%martin%';
```

**Pourquoi c'est non-SARGable :**
- SQL Server ne sait pas où commencer dans l'index
- Doit scanner toutes les valeurs
- Comme chercher "tous les mots se terminant par 'tion'" dans un dictionnaire

#### ✅ Solution partielle : Wildcard à droite

```sql
-- Recherche commençant par 'Mar'
SELECT * FROM Customers
WHERE CustomerName LIKE 'Mar%';  -- SARGable !
```

**Note :** Il n'existe pas de solution parfaitement SARGable pour les recherches avec wildcard au début. Options :
1. Full-Text Search (pour les recherches textuelles complexes)
2. Repenser le modèle de données
3. Accepter la performance réduite si c'est rare

### Piège 4 : Les calculs arithmétiques

#### ❌ Problème : Opérations sur la colonne

```sql
-- Prix avec TVA
SELECT * FROM Products
WHERE Price * 1.20 > 100;

-- Salaire annuel
SELECT * FROM Employees
WHERE Salary * 12 > 60000;

-- Remise appliquée
SELECT * FROM Orders
WHERE TotalAmount * (1 - DiscountPercent/100) > 500;
```

#### ✅ Solution : Inverser le calcul

```sql
-- Prix avec TVA
SELECT * FROM Products
WHERE Price > 100 / 1.20;  -- = 83.33

-- Salaire annuel
SELECT * FROM Employees
WHERE Salary > 60000 / 12;  -- = 5000

-- Remise appliquée
SELECT * FROM Orders
WHERE TotalAmount > 500 / (1 - DiscountPercent/100);
-- Ou mieux : créer une colonne calculée
ALTER TABLE Orders
ADD AmountAfterDiscount AS TotalAmount * (1 - DiscountPercent/100) PERSISTED;
```

### Piège 5 : Les conversions de types implicites

#### ❌ Problème : Types incompatibles

```sql
-- CustomerID est INT dans la table
SELECT * FROM Customers
WHERE CustomerID = '12345';  -- Chaîne de caractères

-- OrderDate est DATE dans la table
SELECT * FROM Orders
WHERE OrderDate = '2024-11-18 00:00:00.000';  -- DATETIME (pas DATE)

-- ProductCode est VARCHAR dans la table
SELECT * FROM Products
WHERE ProductCode = N'ABC123';  -- NVARCHAR
```

**Ce qui se passe :**
- SQL Server effectue une conversion implicite
- Si la conversion est sur la colonne, ce n'est pas SARGable
- Performances dégradées + risque d'erreurs

#### ✅ Solution : Utiliser les types exacts

```sql
-- Types correspondants
SELECT * FROM Customers
WHERE CustomerID = 12345;  -- INT

SELECT * FROM Orders
WHERE OrderDate = CAST('2024-11-18' AS DATE);  -- DATE

SELECT * FROM Products
WHERE ProductCode = 'ABC123';  -- VARCHAR
```

### Piège 6 : Les NOT, <>, et négations

#### ❌ Généralement non-SARGable

```sql
-- Opérateur NOT
SELECT * FROM Products
WHERE NOT (Category = 'Electronics');

-- Opérateur <>
SELECT * FROM Customers
WHERE Country <> 'France';

-- NOT IN (souvent problématique)
SELECT * FROM Orders
WHERE CustomerID NOT IN (SELECT CustomerID FROM BlockedCustomers);

-- IS NOT NULL (dépend du contexte)
SELECT * FROM Products
WHERE Description IS NOT NULL;
```

**Pourquoi c'est problématique :**
- Les index sont optimisés pour trouver ce qui EST, pas ce qui N'EST PAS
- SQL Server doit souvent scanner toute la table

#### ✅ Solutions alternatives

```sql
-- Reformuler positivement quand possible
SELECT * FROM Products
WHERE Category IN ('Clothing', 'Books', 'Toys');  -- Liste les catégories voulues

-- Utiliser EXISTS plutôt que NOT IN
SELECT * FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM BlockedCustomers bc
    WHERE bc.CustomerID = o.CustomerID
);

-- IS NOT NULL : Parfois nécessaire, mais considérer l'index filtré
CREATE INDEX IX_Products_Description
ON Products(Description)
WHERE Description IS NOT NULL;  -- Index filtré
```

## Les opérateurs et leur SARGability

### Tableau récapitulatif

| Opérateur | SARGable ? | Commentaire |
|-----------|------------|-------------|
| `=` | ✅ Oui | Idéal pour les index |
| `>`, `>=`, `<`, `<=` | ✅ Oui | Excellents pour les plages |
| `BETWEEN` | ✅ Oui | Équivalent à `>= AND <=` |
| `LIKE 'ABC%'` | ✅ Oui | Wildcard à droite uniquement |
| `LIKE '%ABC'` | ❌ Non | Wildcard à gauche |
| `LIKE '%ABC%'` | ❌ Non | Wildcards des deux côtés |
| `IN (liste)` | ✅ Oui | Équivalent à plusieurs `=` |
| `<>`, `!=` | ⚠️ Parfois | Rarement optimal |
| `NOT` | ⚠️ Parfois | Souvent non-SARGable |
| `NOT IN` | ❌ Généralement non | Préférer `NOT EXISTS` |
| `IS NULL` | ✅ Oui | Avec index filtré |
| `IS NOT NULL` | ⚠️ Parfois | Dépend du contexte |

### Combinaisons avec AND et OR

**AND** : Généralement SARGable
```sql
-- Les deux conditions peuvent utiliser des index
SELECT * FROM Orders
WHERE CustomerID = 123
  AND OrderDate >= '2024-01-01';
```

**OR** : Plus complexe
```sql
-- Peut être SARGable si les deux colonnes sont indexées séparément
SELECT * FROM Orders
WHERE CustomerID = 123
   OR CustomerID = 456;

-- Non-SARGable si les colonnes sont différentes sans index approprié
SELECT * FROM Orders
WHERE CustomerID = 123
   OR OrderDate >= '2024-01-01';
```

## Vérifier la SARGability : Lecture du plan d'exécution

### Index Seek vs Index Scan vs Table Scan

**Index Seek (✅ Bon signe - SARGable)** :
```
Plan d'exécution :
[Index Seek] ← Pointe précisément vers les données
Cost: 0.01%
Rows: 100
```

**Index Scan (⚠️ Signe d'alerte - Potentiellement non-SARGable)** :
```
Plan d'exécution :
[Index Scan] ← Parcourt tout l'index
Cost: 15%
Rows: 1,000,000
```

**Table Scan (❌ Problème - Non-SARGable)** :
```
Plan d'exécution :
[Table Scan] ← Parcourt toute la table
Cost: 85%
Rows: 1,000,000
```

### Exemple d'analyse

**Requête non-SARGable :**
```sql
SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;
```

**Plan d'exécution :**
```
|--Table Scan (Orders)
    Predicate: YEAR([OrderDate]) = 2024
    Estimated Rows: 1,000,000
    Actual Rows: 50,000
    Cost: 92%
```

**Analyse :**
- ❌ Table Scan = Mauvais
- ❌ Predicate avec fonction = Non-SARGable
- ❌ Lit 1M de lignes pour en retourner 50k

**Requête corrigée (SARGable) :**
```sql
SELECT * FROM Orders
WHERE OrderDate >= '2024-01-01'
  AND OrderDate < '2025-01-01';
```

**Plan d'exécution :**
```
|--Index Seek (IX_Orders_OrderDate)
    Seek Predicate: [OrderDate] >= '2024-01-01' AND [OrderDate] < '2025-01-01'
    Estimated Rows: 50,000
    Actual Rows: 50,000
    Cost: 2%
```

**Analyse :**
- ✅ Index Seek = Excellent
- ✅ Seek Predicate (pas juste Predicate) = SARGable
- ✅ Lit uniquement les 50k lignes nécessaires
- ✅ 46x moins coûteux (92% → 2%)

## Cas particuliers et nuances

### Cas 1 : Colonnes calculées persistées

Si vous DEVEZ utiliser une fonction, créez une colonne calculée :

```sql
-- Problème : Non-SARGable
SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;

-- Solution : Colonne calculée
ALTER TABLE Orders
ADD OrderYear AS YEAR(OrderDate) PERSISTED;

-- Créer un index sur la colonne calculée
CREATE INDEX IX_Orders_OrderYear ON Orders(OrderYear);

-- Maintenant SARGable
SELECT * FROM Orders
WHERE OrderYear = 2024;
```

**Avantages :**
- La fonction est calculée UNE fois (à l'insertion/mise à jour)
- Pas recalculée à chaque requête
- Peut être indexée

**Inconvénients :**
- Utilise plus d'espace disque
- Ralentit légèrement les INSERT/UPDATE

### Cas 2 : Indexer une expression → passer par une colonne calculée

⚠️ Contrairement à PostgreSQL ou Oracle, **SQL Server ne permet PAS d'indexer directement une expression** : la syntaxe `CREATE INDEX ... ON Customers(UPPER(CustomerName))` provoque une **erreur**. Il faut d'abord créer une **colonne calculée** (de préférence `PERSISTED`), puis l'indexer :

```sql
-- 1. Colonne calculée
ALTER TABLE Customers ADD CustomerNameUpper AS UPPER(CustomerName) PERSISTED;

-- 2. Index sur cette colonne
CREATE INDEX IX_Customers_UpperName ON Customers(CustomerNameUpper);

-- 3. Filtrer sur la colonne calculée (SARGable)
SELECT * FROM Customers WHERE CustomerNameUpper = 'MARTIN';
```

**Note :** une fois la colonne calculée indexée, l'optimiseur peut parfois reconnaître `WHERE UPPER(CustomerName) = 'MARTIN'` et utiliser l'index automatiquement (*expression matching*) — mais cibler directement la colonne calculée est plus fiable.

### Cas 3 : Paramétrage de requêtes

**Problème avec concaténation :**
```sql
-- Non-SARGable si @SearchTerm contient des wildcards dynamiques
DECLARE @SearchTerm VARCHAR(50) = '%Martin%';
SELECT * FROM Customers
WHERE CustomerName LIKE @SearchTerm;
```

**Meilleure approche :**
```sql
-- Distinguer les cas
IF @SearchTerm LIKE '[%_]%'  -- Contient des wildcards
BEGIN
    -- Recherche complexe (accepter la performance réduite)
    SELECT * FROM Customers
    WHERE CustomerName LIKE @SearchTerm;
END
ELSE
BEGIN
    -- Recherche simple (SARGable)
    SELECT * FROM Customers
    WHERE CustomerName LIKE @SearchTerm + '%';
END
```

## Méthodologie pour rendre une requête SARGable

### Étape 1 : Identifier les prédicats non-SARGable

```sql
-- Examiner le plan d'exécution
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Exécuter votre requête
SELECT * FROM Orders
WHERE DATEDIFF(DAY, OrderDate, GETDATE()) < 30;

-- Analyser :
-- - Y a-t-il des Table Scan ou Index Scan ?
-- - Y a-t-il des fonctions dans les prédicats ?
-- - Les estimations de lignes sont-elles correctes ?
```

### Étape 2 : Isoler la colonne

```sql
-- Avant (colonne modifiée)
WHERE DATEDIFF(DAY, OrderDate, GETDATE()) < 30

-- Après (colonne isolée)
WHERE OrderDate >= DATEADD(DAY, -30, GETDATE())
```

### Étape 3 : Simplifier les fonctions

```sql
-- Avant (fonction complexe)
WHERE SUBSTRING(ProductCode, 1, 3) = 'ABC'

-- Après (LIKE simple)
WHERE ProductCode LIKE 'ABC%'
```

### Étape 4 : Vérifier les types de données

```sql
-- Vérifier le type de la colonne
SELECT COLUMN_NAME, DATA_TYPE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Orders' AND COLUMN_NAME = 'CustomerID';

-- Utiliser le type exact dans la requête
WHERE CustomerID = 12345  -- Si INT
```

### Étape 5 : Tester et comparer

```sql
-- Comparer les statistiques
-- Version non-SARGable
SET STATISTICS TIME ON;
SELECT * FROM Orders WHERE YEAR(OrderDate) = 2024;
-- Note: CPU time, elapsed time, logical reads

-- Version SARGable
SELECT * FROM Orders WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';
-- Note: CPU time, elapsed time, logical reads

-- Comparer les résultats
```

## Bonnes pratiques générales

### 1. Toujours penser "SARGable" dès l'écriture

**Checklist mentale :**
- ✅ La colonne est-elle isolée (seule d'un côté de l'opérateur) ?
- ✅ Y a-t-il des fonctions sur la colonne indexée ?
- ✅ Les types de données correspondent-ils ?
- ✅ Le wildcard LIKE est-il à droite uniquement ?

### 2. Privilégier les plages aux fonctions

**Toujours préférer :**
```sql
WHERE OrderDate >= @StartDate AND OrderDate < @EndDate
```

**Plutôt que :**
```sql
WHERE YEAR(OrderDate) = @Year
```

### 3. Créer des colonnes calculées pour les transformations fréquentes

Si vous devez souvent chercher sur `UPPER(CustomerName)` :

```sql
ALTER TABLE Customers
ADD CustomerNameUpper AS UPPER(CustomerName) PERSISTED;

CREATE INDEX IX_Customers_NameUpper ON Customers(CustomerNameUpper);
```

### 4. Documenter les raisons des choix

```sql
-- ❌ Éviter (non-SARGable) :
-- WHERE CONVERT(VARCHAR(10), OrderDate, 120) = '2024-11-18'

-- ✅ Utiliser (SARGable) :
-- WHERE OrderDate >= '2024-11-18' AND OrderDate < '2024-11-19'
-- Raison : Permet l'utilisation de l'index IX_Orders_OrderDate
```

### 5. Utiliser des outils d'analyse

**Plan d'exécution** :
- Cherchez les mots-clés "Seek" vs "Scan"
- Attention aux icônes de warning (triangle jaune)

**Statistiques I/O** :
```sql
SET STATISTICS IO ON;
-- Comparer les "logical reads" entre versions
```

**Query Store** :
- Identifier les régressions de performance
- Comparer différents plans d'exécution

## Exceptions : Quand la non-SARGability est acceptable

### 1. Tables très petites

Pour une table de 100 lignes, la différence est négligeable :
```sql
-- Même non-SARGable, c'est acceptable
SELECT * FROM Countries
WHERE UPPER(CountryName) = 'FRANCE';
```

### 2. Requêtes exécutées rarement

Une requête de rapport mensuel peut se permettre d'être moins optimale :
```sql
-- Requête exécutée 1x par mois, acceptable
SELECT YEAR(OrderDate) AS Year, COUNT(*)
FROM Orders
GROUP BY YEAR(OrderDate);
```

### 3. Quand il n'y a pas d'alternative

Certaines recherches textuelles complexes n'ont pas de version SARGable :
```sql
-- Pas d'alternative SARGable parfaite
WHERE ProductDescription LIKE '%waterproof%'
```

**Solutions :**
- Full-Text Search
- Colonnes calculées avec mots-clés extraits
- Accepter la performance réduite

### 4. Développement et débogage

En phase de développement, la lisibilité prime parfois :
```sql
-- Plus lisible pour le débogage
WHERE CAST(OrderDate AS DATE) = @SpecificDate
```

Optimisez en production :
```sql
-- Version production
WHERE OrderDate >= @SpecificDate
  AND OrderDate < DATEADD(DAY, 1, @SpecificDate)
```

## Résumé des transformations courantes

### Dates

| ❌ Non-SARGable | ✅ SARGable |
|----------------|-------------|
| `YEAR(OrderDate) = 2024` | `OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'` |
| `MONTH(OrderDate) = 11` | `OrderDate >= '2024-11-01' AND OrderDate < '2024-12-01'` |
| `DATEPART(WEEK, OrderDate) = 46` | Utiliser une colonne calculée |
| `CAST(OrderDate AS DATE) = '2024-11-18'` | `OrderDate >= '2024-11-18' AND OrderDate < '2024-11-19'` |
| `DATEDIFF(DAY, OrderDate, GETDATE()) < 30` | `OrderDate >= DATEADD(DAY, -30, GETDATE())` |

### Chaînes

| ❌ Non-SARGable | ✅ SARGable |
|----------------|-------------|
| `UPPER(Name) = 'SMITH'` | `Name = 'Smith' COLLATE ...` ou colonne calculée |
| `SUBSTRING(Code, 1, 3) = 'ABC'` | `Code LIKE 'ABC%'` |
| `LTRIM(RTRIM(Code)) = 'X'` | Nettoyer à l'insertion ou colonne calculée |
| `LEN(Name) > 10` | Colonne calculée sur `LEN(Name)` |
| `REVERSE(Name) LIKE 'nos%'` | Colonne calculée sur `REVERSE(Name)` |

### Nombres

| ❌ Non-SARGable | ✅ SARGable |
|----------------|-------------|
| `Salary * 12 > 50000` | `Salary > 50000 / 12` |
| `Price * 1.20 > 100` | `Price > 100 / 1.20` |
| `ABS(Amount) > 1000` | `Amount > 1000 OR Amount < -1000` |
| `Quantity / 12 = 5` | `Quantity = 60` |

## Outils pour détecter les problèmes de SARGability

### 1. Plan d'exécution graphique (SSMS)

```sql
-- Activer le plan d'exécution
-- Ctrl + M dans SSMS

SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;

-- Regarder :
-- - Type d'opération : Seek vs Scan
-- - Warnings (triangles jaunes)
-- - Coût relatif
```

### 2. Statistiques I/O et TIME

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Exécuter votre requête
SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;

-- Analyser les résultats :
-- - Logical reads (nombre de pages lues)
-- - CPU time
-- - Elapsed time
```

### 3. Query Store

```sql
-- Identifier les requêtes avec beaucoup de lectures logiques
SELECT TOP 10
    qt.query_sql_text,
    rs.avg_logical_io_reads,
    rs.avg_duration / 1000.0 AS avg_duration_ms
FROM sys.query_store_runtime_stats rs
INNER JOIN sys.query_store_plan p ON rs.plan_id = p.plan_id
INNER JOIN sys.query_store_query q ON p.query_id = q.query_id
INNER JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
ORDER BY rs.avg_logical_io_reads DESC;
```

### 4. DMVs (Dynamic Management Views)

```sql
-- Trouver les requêtes avec beaucoup de scans
SELECT
    t.text AS query_text,
    s.execution_count,
    s.total_logical_reads / s.execution_count AS avg_logical_reads,
    s.total_elapsed_time / s.execution_count AS avg_elapsed_time
FROM sys.dm_exec_query_stats s
CROSS APPLY sys.dm_exec_sql_text(s.sql_handle) t
WHERE s.total_logical_reads / s.execution_count > 1000  -- Seuil ajustable
ORDER BY avg_logical_reads DESC;
```

- ⚡ Amélioration de la scalabilité
- 💰 Réduction de la charge serveur

**Principe de base :** Gardez la colonne indexée seule et non modifiée d'un côté de la comparaison.

**Règle d'or :** Si vous devez appliquer une fonction, appliquez-la sur la constante/paramètre, jamais sur la colonne.

---

**Points clés à retenir :**

- ✅ **SARGable** = Search ARGument ABLE = Utilisable par l'index
- ✅ Index Seek = Bon (SARGable)
- ✅ Index/Table Scan = Mauvais (non-SARGable)
- ✅ Isoler la colonne (pas de fonction dessus)
- ✅ Utiliser des plages pour les dates (`>=` et `<`)
- ✅ Wildcard LIKE à droite uniquement (`'ABC%'`)
- ✅ Types de données exacts (pas de conversion implicite)
- ✅ Inverser les calculs (mettre l'arithmétique côté constante)
- ✅ Créer des colonnes calculées persistées si nécessaire
- ✅ Toujours vérifier le plan d'exécution

**Réflexe à développer :** Chaque fois que vous écrivez un WHERE, demandez-vous "Est-ce SARGable ?"
