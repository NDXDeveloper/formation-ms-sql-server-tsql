# 1.4.2 Schémas (Organisation logique)

## Introduction

Vous savez maintenant ce que sont les tables, les colonnes et les lignes. Mais imaginez une grande base de données avec des centaines de tables : comment les organiser de manière logique et claire ?

C'est là qu'interviennent les **schémas** (schemas en anglais).

### Analogie : L'organisation d'une bibliothèque

Imaginez une bibliothèque municipale :

```
🏛️ BIBLIOTHÈQUE (Base de données)
│
├─ 📚 Section FICTION (Schéma "Fiction")
│   ├─ Romans policiers
│   ├─ Science-fiction
│   └─ Littérature classique
│
├─ 📖 Section NON-FICTION (Schéma "NonFiction")
│   ├─ Histoire
│   ├─ Sciences
│   └─ Biographies
│
├─ 👶 Section JEUNESSE (Schéma "Jeunesse")
│   ├─ Albums illustrés
│   ├─ Contes
│   └─ Premiers romans
│
└─ 💿 Section MULTIMEDIA (Schéma "Media")
    ├─ DVD
    ├─ CD
    └─ Magazines
```

Chaque **section** regroupe logiquement des livres similaires. De même, un **schéma** regroupe logiquement des objets de base de données similaires (tables, vues, procédures, etc.).

## Qu'est-ce qu'un schéma ?

### Définition simple

Un **schéma** est un **conteneur logique** qui permet de **regrouper et d'organiser** les objets d'une base de données.

**En termes encore plus simples :**
> Un schéma, c'est comme un **dossier** ou un **classeur** qui permet de ranger les tables (et autres objets) de manière organisée.

### Définition formelle

Un schéma est un **namespace** (espace de noms) qui :
- Regroupe des objets de base de données (tables, vues, procédures, etc.)
- Permet d'éviter les conflits de noms
- Facilite la gestion des permissions
- Améliore l'organisation logique

### Ce qu'un schéma n'est PAS

❌ **Un schéma n'est PAS** :
- Une base de données séparée
- Un fichier physique
- Une copie des données
- Une sauvegarde

✅ **Un schéma EST** :
- Une organisation **logique** (pas physique)
- Un moyen de **grouper** les objets
- Un **préfixe** pour les noms d'objets

## Pourquoi utiliser des schémas ?

### 1. Organisation et clarté

**Sans schémas (tout mélangé) :**
```
Base de données : Entreprise
├─ Clients
├─ Commandes
├─ Produits
├─ Factures
├─ Employes
├─ Salaires
├─ Departements
├─ Fournisseurs
├─ Achats
├─ Stocks
└─ ... (100+ tables en vrac)
```

**Avec schémas (organisé) :**
```
Base de données : Entreprise
│
├─ 📁 Schéma : Ventes
│   ├─ Clients
│   ├─ Commandes
│   ├─ Factures
│   └─ Produits
│
├─ 📁 Schéma : RH
│   ├─ Employes
│   ├─ Salaires
│   └─ Departements
│
└─ 📁 Schéma : Achats
    ├─ Fournisseurs
    ├─ Achats
    └─ Stocks
```

**Beaucoup plus clair, n'est-ce pas ?**

### 2. Éviter les conflits de noms

**Problème sans schémas :**
Vous voulez créer deux tables "Clients" :
- Une pour les clients externes (B2C)
- Une pour les clients professionnels (B2B)

❌ Impossible : Vous ne pouvez pas avoir deux tables avec le même nom dans la même base !

**Solution avec schémas :**
```sql
-- Table pour les clients particuliers
CREATE TABLE B2C.Clients (...);

-- Table pour les clients professionnels
CREATE TABLE B2B.Clients (...);
```

✅ Possible : Les deux tables ont le même nom (`Clients`) mais dans des schémas différents !

### 3. Gestion des permissions simplifiée

**Scénario :** Vous avez une équipe RH et une équipe Ventes.

**Sans schémas :**
```sql
-- Donner accès table par table (fastidieux)
GRANT SELECT ON Employes TO EquipeRH;
GRANT SELECT ON Salaires TO EquipeRH;
GRANT SELECT ON Departements TO EquipeRH;
GRANT SELECT ON Conges TO EquipeRH;
-- ... 20 tables plus tard...
```

**Avec schémas :**
```sql
-- Donner accès à tout un schéma d'un coup
GRANT SELECT ON SCHEMA::RH TO EquipeRH;
-- Toutes les tables du schéma RH sont accessibles !
```

**Beaucoup plus simple !**

### 4. Séparation logique des responsabilités

Les schémas permettent de séparer clairement les domaines fonctionnels :

| Schéma | Responsable | Contenu |
|--------|-------------|---------|
| `Ventes` | Équipe commerciale | Clients, Commandes, Devis |
| `RH` | Ressources humaines | Employés, Salaires, Congés |
| `Compta` | Comptabilité | Factures, Paiements, Écritures |
| `Production` | Usine | Ateliers, MachinesOutils, Production |
| `Logistique` | Supply chain | Stocks, Entrepôts, Livraisons |

Chaque équipe travaille dans **son propre espace**, sans interférer avec les autres.

## Le schéma par défaut : dbo

### Qu'est-ce que "dbo" ?

**dbo** signifie **Database Owner** (Propriétaire de la base de données).

C'est le **schéma par défaut** de SQL Server.

**Quand vous créez une table sans spécifier de schéma :**
```sql
CREATE TABLE Clients (...);
```

**SQL Server la crée automatiquement dans le schéma dbo :**
```sql
-- Équivalent à :
CREATE TABLE dbo.Clients (...);
```

### Convention de nommage complète

Le nom complet d'une table dans SQL Server suit cette structure :

```
[Serveur].[Base].[Schéma].[Table]

Exemples :
SERVEUR01.Entreprise.dbo.Clients
SERVEUR01.Entreprise.Ventes.Commandes
```

**En pratique, on utilise souvent des formes abrégées :**

| Format | Quand l'utiliser | Exemple |
|--------|------------------|---------|
| `Schéma.Table` | Le plus courant | `dbo.Clients` |
| `Table` | Quand on utilise le schéma par défaut | `Clients` |
| `Base.Schéma.Table` | Pour accéder à une autre base | `Entreprise.dbo.Clients` |
| `Serveur.Base.Schéma.Table` | Pour accéder à un autre serveur | `SERVEUR01.Entreprise.dbo.Clients` |

### Bonnes pratiques avec dbo

✅ **Utilisez dbo pour :**
- Les tables principales et communes
- Les objets système
- Les petits projets simples

❌ **Évitez dbo pour :**
- Les grands projets avec beaucoup de tables
- Quand vous voulez séparer logiquement les domaines
- Quand plusieurs équipes travaillent sur la même base

**Conseil :** Même si vous utilisez dbo, **spécifiez-le explicitement** dans vos requêtes pour la clarté :

```sql
-- Moins clair
SELECT * FROM Clients;

-- Plus clair
SELECT * FROM dbo.Clients;
```

## Créer et utiliser des schémas

### Créer un schéma

**Syntaxe de base :**
```sql
CREATE SCHEMA nom_schema;
```

**Exemples :**
```sql
-- Créer un schéma pour les ventes
CREATE SCHEMA Ventes;

-- Créer un schéma pour les ressources humaines
CREATE SCHEMA RH;

-- Créer un schéma pour la comptabilité
CREATE SCHEMA Compta;
```

**Avec spécification du propriétaire :**
```sql
CREATE SCHEMA Ventes AUTHORIZATION dbo;
```

### Créer une table dans un schéma

**Syntaxe :**
```sql
CREATE TABLE Schéma.NomTable (
    colonnes...
);
```

**Exemples :**
```sql
-- Table dans le schéma Ventes
CREATE TABLE Ventes.Clients (
    ClientID INT PRIMARY KEY,
    Nom NVARCHAR(50),
    Prenom NVARCHAR(50)
);

-- Table dans le schéma RH
CREATE TABLE RH.Employes (
    EmployeID INT PRIMARY KEY,
    Nom NVARCHAR(50),
    Salaire DECIMAL(10,2)
);

-- Table dans le schéma Compta
CREATE TABLE Compta.Factures (
    FactureID INT PRIMARY KEY,
    Montant DECIMAL(10,2),
    DateEmission DATE
);
```

### Interroger une table dans un schéma

**Toujours préfixer le nom de la table par le schéma :**

```sql
-- Lire les clients du schéma Ventes
SELECT * FROM Ventes.Clients;

-- Lire les employés du schéma RH
SELECT * FROM RH.Employes;

-- Lire les factures du schéma Compta
SELECT * FROM Compta.Factures;
```

**Sans préfixe, SQL Server utilise le schéma par défaut (dbo) :**

```sql
-- Cherche dans dbo.Clients
SELECT * FROM Clients;

-- Pour accéder à Ventes.Clients, il FAUT spécifier :
SELECT * FROM Ventes.Clients;
```

### Modifier le schéma d'une table existante

**Scénario :** Vous avez créé une table dans dbo, mais vous voulez la déplacer dans un autre schéma.

**Syntaxe :**
```sql
ALTER SCHEMA nouveau_schema TRANSFER ancien_schema.nom_table;
```

**Exemple :**
```sql
-- Déplacer la table Clients de dbo vers Ventes
ALTER SCHEMA Ventes TRANSFER dbo.Clients;

-- Maintenant, la table s'appelle Ventes.Clients
```

### Supprimer un schéma

**Attention :** Un schéma ne peut être supprimé que s'il est **vide** (aucun objet à l'intérieur).

**Syntaxe :**
```sql
DROP SCHEMA nom_schema;
```

**Exemple :**
```sql
-- D'abord, supprimer tous les objets du schéma
DROP TABLE Test.TableTemp;

-- Ensuite, supprimer le schéma
DROP SCHEMA Test;
```

## Les objets qu'un schéma peut contenir

Un schéma ne contient pas seulement des tables ! Il peut contenir tous types d'objets :

| Type d'objet | Description | Exemple |
|--------------|-------------|---------|
| **Tables** | Stockage des données | `Ventes.Clients` |
| **Vues** | Requêtes enregistrées | `Ventes.Vue_ClientsActifs` |
| **Procédures stockées** | Code réutilisable | `Ventes.AjouterCommande` |
| **Fonctions** | Calculs réutilisables | `Ventes.CalculerRemise` |
| **Index** | Optimisation | Index sur `Ventes.Clients` |
| **Triggers** | Actions automatiques | Trigger sur `Ventes.Commandes` |
| **Types définis** | Types personnalisés | `Ventes.AdresseType` |
| **Synonymes** | Alias d'objets | Synonyme dans `Ventes` |

**Exemple complet :**
```
Schéma : Ventes
├─ Tables
│   ├─ Clients
│   ├─ Commandes
│   └─ Produits
├─ Vues
│   ├─ Vue_ClientsActifs
│   └─ Vue_CommandesRecentes
├─ Procédures stockées
│   ├─ AjouterClient
│   ├─ PasserCommande
│   └─ CalculerStatistiques
└─ Fonctions
    ├─ CalculerRemise
    └─ ObtenirPrixTTC
```

## Lister les schémas et leurs objets

### Voir tous les schémas d'une base de données

```sql
SELECT
    name AS NomSchema,
    schema_id AS ID,
    SCHEMA_NAME(schema_id) AS Proprietaire
FROM
    sys.schemas
ORDER BY
    name;
```

**Résultat typique :**
```
NomSchema      | ID | Proprietaire
---------------|----|-------------
dbo            | 1  | dbo
guest          | 2  | guest
INFORMATION... | 3  | INFORMATION_SCHEMA
sys            | 4  | sys
Ventes         | 5  | dbo
RH             | 6  | dbo
Compta         | 7  | dbo
```

### Voir toutes les tables d'un schéma spécifique

```sql
SELECT
    TABLE_SCHEMA,
    TABLE_NAME
FROM
    INFORMATION_SCHEMA.TABLES
WHERE
    TABLE_SCHEMA = 'Ventes'
ORDER BY
    TABLE_NAME;
```

**Résultat :**
```
TABLE_SCHEMA | TABLE_NAME
-------------|---------------
Ventes       | Clients
Ventes       | Commandes
Ventes       | LignesCommande
Ventes       | Produits
```

### Compter les objets par schéma

```sql
SELECT
    SCHEMA_NAME(schema_id) AS Schéma,
    COUNT(*) AS NombreObjets
FROM
    sys.objects
WHERE
    type = 'U'  -- U = User Table (tables utilisateur)
GROUP BY
    schema_id
ORDER BY
    NombreObjets DESC;
```

## Permissions et sécurité avec les schémas

### Accorder des permissions sur un schéma

**Donner accès en lecture à tout un schéma :**
```sql
GRANT SELECT ON SCHEMA::Ventes TO Utilisateur_Commercial;
```

**Donner accès complet (lecture + écriture) :**
```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::Ventes TO Utilisateur_Admin;
```

**Donner tous les droits :**
```sql
GRANT ALL ON SCHEMA::Ventes TO Role_Gestionnaires;
```

### Refuser des permissions

```sql
DENY DELETE ON SCHEMA::Ventes TO Utilisateur_Stagiaire;
```

### Exemple de configuration de sécurité

**Scénario : Application ERP**

```sql
-- Créer les schémas
CREATE SCHEMA Ventes;
CREATE SCHEMA RH;
CREATE SCHEMA Compta;

-- Créer des utilisateurs/rôles
CREATE ROLE Role_Commercial;
CREATE ROLE Role_RH;
CREATE ROLE Role_Comptable;

-- Permissions pour l'équipe commerciale
GRANT SELECT, INSERT, UPDATE ON SCHEMA::Ventes TO Role_Commercial;
DENY DELETE ON SCHEMA::Ventes TO Role_Commercial;  -- Pas de suppression

-- Permissions pour l'équipe RH
GRANT SELECT, INSERT, UPDATE ON SCHEMA::RH TO Role_RH;

-- Permissions pour l'équipe comptabilité
GRANT ALL ON SCHEMA::Compta TO Role_Comptable;  -- Accès complet

-- Personne ne peut accéder aux données d'un autre service
DENY ALL ON SCHEMA::RH TO Role_Commercial;
DENY ALL ON SCHEMA::Compta TO Role_Commercial;
```

**Résultat :** Séparation claire des responsabilités et des accès.

## Bonnes pratiques

### 1. Nommage des schémas

✅ **Noms clairs et descriptifs :**
- `Ventes`, `RH`, `Compta` : ✅ Bon
- `Schema1`, `Test`, `Temp` : ❌ Mauvais

✅ **Convention cohérente :**
- Tout en PascalCase : `Ventes`, `RessourcesHumaines`
- OU tout en minuscules : `ventes`, `ressources_humaines`

✅ **Éviter les préfixes redondants :**
- ❌ `Schema_Ventes`, `Sch_RH`
- ✅ `Ventes`, `RH`

### 2. Organisation logique

✅ **Grouper par domaine fonctionnel :**
```
Ventes    → Tout ce qui concerne les ventes
RH        → Tout ce qui concerne les RH
Compta    → Tout ce qui concerne la comptabilité
```

✅ **Séparer les environnements si nécessaire :**
```
Production    → Données de production
Staging       → Données de test
Archive       → Données historiques
```

### 3. Utilisation systématique

✅ **Toujours spécifier le schéma :**
```sql
-- Bon
SELECT * FROM Ventes.Clients;

-- Moins bon (dépend du contexte)
SELECT * FROM Clients;
```

✅ **Dans les scripts de création :**
```sql
CREATE TABLE Ventes.Commandes (...);  -- ✅ Explicite
-- plutôt que
CREATE TABLE Commandes (...);         -- ❌ Ambiguë
```

### 4. Ne pas abuser des schémas

❌ **Trop de schémas = confusion :**
```
Ventes_France
Ventes_Allemagne
Ventes_Espagne
Ventes_Italie
Ventes_UK
... (20 schémas)
```

✅ **Mieux : Un seul schéma avec une colonne Pays :**
```
Schéma : Ventes
  └─ Table : Commandes
      └─ Colonne : Pays
```

### 5. Documentation

✅ **Documenter la raison d'être de chaque schéma :**

```sql
-- Schéma Ventes : Gère toutes les données commerciales
-- Propriétaire : Équipe Commerciale
-- Dernière modification : 2024-11-16
CREATE SCHEMA Ventes;
```

## Schémas vs Bases de données : Quelle différence ?

### Comparaison

| Aspect | Base de données | Schéma |
|--------|-----------------|--------|
| **Niveau** | Conteneur physique | Conteneur logique |
| **Séparation** | Complète (fichiers séparés) | Logique (même fichier) |
| **Requêtes** | Jointures possibles mais plus lentes | Jointures rapides |
| **Permissions** | Au niveau base | Au niveau schéma |
| **Sauvegarde** | Par base | Tout ensemble |
| **Complexité** | Plus complexe | Plus simple |

### Quand utiliser une base de données séparée ?

✅ **Utilisez une base de données séparée quand :**
- Séparation totale nécessaire (clients complètement distincts)
- Sauvegardes indépendantes requises
- Sécurité maximale (isolation physique)
- Grandes quantités de données

### Quand utiliser des schémas ?

✅ **Utilisez des schémas quand :**
- Organisation logique dans un même projet
- Besoin de faire des jointures entre domaines
- Gestion des permissions par domaine
- Éviter de multiplier les bases

## Cas pratique complet

### Scénario

Vous gérez une base de données pour une **librairie en ligne**.

### Sans schémas (approche simple)

```sql
CREATE DATABASE Librairie;
GO

USE Librairie;
GO

-- Toutes les tables dans dbo
CREATE TABLE dbo.Clients (...);
CREATE TABLE dbo.Livres (...);
CREATE TABLE dbo.Commandes (...);
CREATE TABLE dbo.Auteurs (...);
CREATE TABLE dbo.Editeurs (...);
CREATE TABLE dbo.Avis (...);
CREATE TABLE dbo.Stocks (...);
CREATE TABLE dbo.Fournisseurs (...);
CREATE TABLE dbo.Achats (...);
CREATE TABLE dbo.Employes (...);
CREATE TABLE dbo.Salaires (...);
-- ... 50 tables mélangées
```

### Avec schémas (approche organisée)

```sql
CREATE DATABASE Librairie;
GO

USE Librairie;
GO

-- Créer les schémas
CREATE SCHEMA Catalogue;  -- Livres, auteurs, éditeurs
CREATE SCHEMA Ventes;     -- Clients, commandes, avis
CREATE SCHEMA Stock;      -- Stocks, entrepôts
CREATE SCHEMA Achats;     -- Fournisseurs, achats
CREATE SCHEMA RH;         -- Employés, salaires
GO

-- Tables du catalogue
CREATE TABLE Catalogue.Livres (
    LivreID INT PRIMARY KEY,
    Titre NVARCHAR(200),
    ISBN VARCHAR(13),
    Prix DECIMAL(10,2)
);

CREATE TABLE Catalogue.Auteurs (
    AuteurID INT PRIMARY KEY,
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100)
);

CREATE TABLE Catalogue.Editeurs (
    EditeurID INT PRIMARY KEY,
    Nom NVARCHAR(100)
);

-- Tables des ventes
CREATE TABLE Ventes.Clients (
    ClientID INT PRIMARY KEY,
    Nom NVARCHAR(50),
    Email NVARCHAR(100)
);

CREATE TABLE Ventes.Commandes (
    CommandeID INT PRIMARY KEY,
    ClientID INT,
    DateCommande DATETIME
);

CREATE TABLE Ventes.Avis (
    AvisID INT PRIMARY KEY,
    LivreID INT,
    ClientID INT,
    Note INT,
    Commentaire NVARCHAR(500)
);

-- Tables du stock
CREATE TABLE Stock.Stocks (
    StockID INT PRIMARY KEY,
    LivreID INT,
    Entrepot NVARCHAR(50),
    Quantite INT
);

-- Tables des achats
CREATE TABLE Achats.Fournisseurs (
    FournisseurID INT PRIMARY KEY,
    Nom NVARCHAR(100)
);

-- Tables RH
CREATE TABLE RH.Employes (
    EmployeID INT PRIMARY KEY,
    Nom NVARCHAR(50),
    Poste NVARCHAR(50)
);
```

```
Base : Librairie
│
├─ 📚 Catalogue
│   ├─ Livres
│   ├─ Auteurs
│   └─ Editeurs
│
├─ 🛒 Ventes

    └─ Employes
```

**Beaucoup plus organisé et maintenable !**

## Résumé

### Points clés à retenir

| Concept | Définition |
|---------|------------|
| **Schéma** | Conteneur logique pour organiser les objets d'une base de données |
| **dbo** | Schéma par défaut de SQL Server (Database Owner) |
| **Namespace** | Permet d'éviter les conflits de noms |
| **Organisation** | Groupe les objets par domaine fonctionnel |
| **Permissions** | Facilite la gestion des droits d'accès |

### Analogies récapitulatives

```
Schéma = Dossier dans un classeur
Schéma = Section dans une bibliothèque
Schéma = Département dans une entreprise
Schéma = Rayon dans un supermarché
```

### Syntaxe essentielle

```sql
-- Créer un schéma
CREATE SCHEMA Ventes;

-- Créer une table dans un schéma
CREATE TABLE Ventes.Clients (...);

-- Interroger une table d'un schéma
SELECT * FROM Ventes.Clients;

-- Donner des permissions sur un schéma
GRANT SELECT ON SCHEMA::Ventes TO Utilisateur;

-- Déplacer une table vers un autre schéma
ALTER SCHEMA Ventes TRANSFER dbo.Clients;
```

### Hiérarchie complète

```
Serveur
  └─ Base de données
      └─ Schéma
          └─ Table
              ├─ Colonnes
              └─ Lignes
```

### Quand utiliser des schémas ?

✅ **Utilisez des schémas pour :**
- Organiser logiquement une grande base de données
- Séparer les domaines fonctionnels
- Faciliter la gestion des permissions
- Éviter les conflits de noms
- Clarifier la structure pour les développeurs

❌ **Pas nécessaire pour :**
- Très petits projets (< 10 tables)
- Prototypes rapides
- Bases de données temporaires
- Quand dbo suffit amplement
