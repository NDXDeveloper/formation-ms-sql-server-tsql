# 3.5.3 Ordre logique d'exécution (FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY)

## Introduction

Lorsque vous écrivez une requête SQL, vous utilisez un certain ordre d'écriture : vous commencez généralement par `SELECT`, puis `FROM`, `WHERE`, etc. Cependant, **SQL n'exécute pas votre requête dans cet ordre !**

Comprendre l'**ordre logique d'exécution** est crucial car :
- Cela explique pourquoi certaines requêtes génèrent des erreurs
- Cela vous aide à comprendre quand utiliser `WHERE` vs `HAVING`
- Cela clarifie pourquoi certains alias fonctionnent à certains endroits et pas à d'autres
- Cela vous permet d'écrire des requêtes plus efficaces

## L'ordre d'écriture vs l'ordre d'exécution

### Ordre d'écriture (syntaxe)

Voici comment nous **écrivons** une requête SQL :

```sql
SELECT      -- 1. On écrit d'abord ce qu'on veut voir
FROM        -- 2. Puis d'où viennent les données
WHERE       -- 3. Puis comment filtrer
GROUP BY    -- 4. Puis comment regrouper
HAVING      -- 5. Puis comment filtrer les groupes
ORDER BY    -- 6. Enfin, comment trier
```

### Ordre logique d'exécution

Mais voici comment SQL **exécute** réellement la requête :

```
1. FROM         ← SQL commence ici
2. WHERE        ← Puis filtre les lignes
3. GROUP BY     ← Puis crée les groupes
4. HAVING       ← Puis filtre les groupes
5. SELECT       ← Puis détermine les colonnes à afficher
6. ORDER BY     ← Enfin, trie les résultats
```

**Cette différence est fondamentale !** C'est elle qui explique la plupart des règles et restrictions que vous rencontrez en SQL.

## Détail de chaque étape

Prenons une requête complète comme exemple et voyons ce qui se passe à chaque étape :

```sql
SELECT
    Categorie,
    COUNT(*) AS NombreProduits,
    AVG(Prix) AS PrixMoyen
FROM Produits
WHERE Prix > 50
GROUP BY Categorie
HAVING COUNT(*) >= 3
ORDER BY PrixMoyen DESC;
```

Table de départ `Produits` :

| ProduitID | NomProduit | Categorie | Prix |
|-----------|------------|-----------|------|
| 1 | Laptop | Informatique | 899 |
| 2 | Souris | Informatique | 25 |
| 3 | Chaise | Mobilier | 150 |
| 4 | Bureau | Mobilier | 300 |
| 5 | Clavier | Informatique | 45 |
| 6 | Lampe | Mobilier | 75 |
| 7 | Écran | Informatique | 250 |
| 8 | Étagère | Mobilier | 120 |

### Étape 1 : FROM

SQL identifie et charge la table source.

```sql
FROM Produits
```

**Résultat après cette étape :** Toutes les lignes de la table `Produits` sont disponibles.

**8 lignes** sont chargées en mémoire.

---

### Étape 2 : WHERE

SQL filtre les lignes individuelles selon le critère spécifié.

```sql
WHERE Prix > 50
```

**Lignes conservées :**

| ProduitID | NomProduit | Categorie | Prix |
|-----------|------------|-----------|------|
| 1 | Laptop | Informatique | 899 |
| 3 | Chaise | Mobilier | 150 |
| 4 | Bureau | Mobilier | 300 |
| 6 | Lampe | Mobilier | 75 |
| 7 | Écran | Informatique | 250 |
| 8 | Étagère | Mobilier | 120 |

**Lignes éliminées :**
- Souris (25 ≤ 50)
- Clavier (45 ≤ 50)

**6 lignes** passent à l'étape suivante.

---

### Étape 3 : GROUP BY

SQL regroupe les lignes restantes selon la colonne spécifiée.

```sql
GROUP BY Categorie
```

**Groupes créés :**

**Groupe "Informatique" :**
- Laptop (899)
- Écran (250)

**Groupe "Mobilier" :**
- Chaise (150)
- Bureau (300)
- Lampe (75)
- Étagère (120)

**2 groupes** sont créés.

---

### Étape 4 : HAVING

SQL filtre les groupes selon les critères d'agrégation.

```sql
HAVING COUNT(*) >= 3
```

**Calcul pour chaque groupe :**
- **Informatique** : COUNT(*) = 2 ❌ (éliminé car 2 < 3)
- **Mobilier** : COUNT(*) = 4 ✅ (conservé car 4 ≥ 3)

**Groupe conservé :**

**Groupe "Mobilier" :**
- Chaise (150)
- Bureau (300)
- Lampe (75)
- Étagère (120)

**1 groupe** passe à l'étape suivante.

---

### Étape 5 : SELECT

SQL détermine les colonnes à afficher et calcule les agrégations.

```sql
SELECT
    Categorie,
    COUNT(*) AS NombreProduits,
    AVG(Prix) AS PrixMoyen
```

**Calculs pour le groupe "Mobilier" :**
- `Categorie` = "Mobilier"
- `COUNT(*)` = 4
- `AVG(Prix)` = (150 + 300 + 75 + 120) / 4 = 161.25

**Résultat intermédiaire :**

| Categorie | NombreProduits | PrixMoyen |
|-----------|----------------|-----------|
| Mobilier | 4 | 161.25 |

**C'est à ce moment que les alias sont créés !** (`NombreProduits`, `PrixMoyen`)

---

### Étape 6 : ORDER BY

SQL trie les résultats selon le critère spécifié.

```sql
ORDER BY PrixMoyen DESC
```

Dans notre cas, il n'y a qu'une seule ligne, donc le tri ne change rien.

**Résultat final :**

| Categorie | NombreProduits | PrixMoyen |
|-----------|----------------|-----------|
| Mobilier | 4 | 161.25 |

---

## Implications pratiques de cet ordre

### 1. Pourquoi on ne peut pas utiliser les alias dans WHERE

❌ **Cette requête génère une erreur :**
```sql
SELECT
    Nom,
    Prix * 1.2 AS PrixTTC
FROM Produits
WHERE PrixTTC > 100;  -- ERREUR : PrixTTC n'existe pas encore
```

**Explication :** L'alias `PrixTTC` est créé à l'étape 5 (`SELECT`), mais `WHERE` s'exécute à l'étape 2, **avant** que l'alias n'existe.

✅ **Solution :**
```sql
SELECT
    Nom,
    Prix * 1.2 AS PrixTTC
FROM Produits
WHERE Prix * 1.2 > 100;  -- Répéter l'expression
```

ou

✅ **Solution avec sous-requête :**
```sql
SELECT *
FROM (
    SELECT
        Nom,
        Prix * 1.2 AS PrixTTC
    FROM Produits
) AS Temp
WHERE PrixTTC > 100;  -- Maintenant l'alias existe
```

---

### 2. Pourquoi on peut utiliser les alias dans ORDER BY

✅ **Cette requête fonctionne :**
```sql
SELECT
    Nom,
    Prix * 1.2 AS PrixTTC
FROM Produits
ORDER BY PrixTTC DESC;  -- Fonctionne !
```

**Explication :** `ORDER BY` s'exécute à l'étape 6, **après** que `SELECT` (étape 5) ait créé l'alias. L'alias existe donc au moment de son utilisation.

---

### 3. Pourquoi WHERE ne peut pas utiliser les fonctions d'agrégation

❌ **Cette requête génère une erreur :**
```sql
SELECT Categorie, COUNT(*) AS NombreProduits
FROM Produits
WHERE COUNT(*) > 5;  -- ERREUR
GROUP BY Categorie;
```

**Explication :**
- `WHERE` s'exécute à l'étape 2
- `GROUP BY` (et donc les agrégations) s'exécute à l'étape 3
- À l'étape 2, les groupes n'existent pas encore, donc `COUNT(*)` n'a aucun sens

✅ **Solution : utiliser HAVING :**
```sql
SELECT Categorie, COUNT(*) AS NombreProduits
FROM Produits
GROUP BY Categorie
HAVING COUNT(*) > 5;  -- Correct
```

---

### 4. Pourquoi on ne peut pas grouper par un alias

❌ **Cette requête peut générer une erreur :**
```sql
SELECT
    YEAR(DateVente) AS Annee,
    SUM(Montant) AS Total
FROM Ventes
GROUP BY Annee;  -- ERREUR (sur la plupart des SGBD)
```

**Explication :** `GROUP BY` s'exécute à l'étape 3, mais l'alias `Annee` n'est créé qu'à l'étape 5.

✅ **Solution :**
```sql
SELECT
    YEAR(DateVente) AS Annee,
    SUM(Montant) AS Total
FROM Ventes
GROUP BY YEAR(DateVente);  -- Répéter l'expression
```

**Note :** Certains SGBD comme PostgreSQL acceptent les alias dans `GROUP BY` par commodité, mais ce n'est pas standard SQL. SQL Server ne l'accepte pas.

---

### 5. Ordre d'évaluation des filtres : WHERE puis HAVING

```sql
SELECT
    Categorie,
    AVG(Prix) AS PrixMoyen
FROM Produits
WHERE Stock > 0        -- Filtrage AVANT regroupement
GROUP BY Categorie
HAVING AVG(Prix) > 100; -- Filtrage APRÈS regroupement
```

**Étapes :**
1. `FROM` : Charge `Produits`
2. `WHERE` : Ne garde que les produits en stock
3. `GROUP BY` : Regroupe les produits restants par catégorie
4. `HAVING` : Ne garde que les catégories avec prix moyen > 100

**Règle importante :** Utilisez `WHERE` dès que possible (pour filtrer avant le regroupement) car c'est plus efficace !

## Cas d'étude complets

### Cas 1 : Analyse des ventes par région

```sql
SELECT
    Region,
    YEAR(DateVente) AS Annee,
    COUNT(*) AS NombreVentes,
    SUM(Montant) AS ChiffreAffaires,
    AVG(Montant) AS PanierMoyen
FROM Ventes
WHERE Statut = 'Finalisée'
  AND DateVente >= '2024-01-01'
GROUP BY Region, YEAR(DateVente)
HAVING SUM(Montant) > 50000
ORDER BY ChiffreAffaires DESC;
```

**Ordre d'exécution :**

1. **FROM** : Charge la table `Ventes`

2. **WHERE** : Filtre les ventes
   - Statut = 'Finalisée'
   - Date >= 2024-01-01

3. **GROUP BY** : Crée des groupes pour chaque combinaison (Region, Année)
   - Ex : (Paris, 2024), (Lyon, 2024), (Paris, 2025), etc.

4. **HAVING** : Ne garde que les groupes avec CA > 50000

5. **SELECT** : Calcule les colonnes
   - Crée les alias `Annee`, `NombreVentes`, `ChiffreAffaires`, `PanierMoyen`
   - Calcule `COUNT(*)`, `SUM(Montant)`, `AVG(Montant)`

6. **ORDER BY** : Trie par chiffre d'affaires décroissant

---

### Cas 2 : Identification des clients VIP

```sql
SELECT
    ClientID,
    COUNT(DISTINCT CommandeID) AS NombreCommandes,
    SUM(Montant) AS TotalDepense,
    MAX(DateCommande) AS DerniereCommande,
    DATEDIFF(DAY, MAX(DateCommande), GETDATE()) AS JoursDepuisDernierAchat
FROM Commandes
WHERE YEAR(DateCommande) >= 2023
  AND Statut IN ('Livrée', 'En cours')
GROUP BY ClientID
HAVING COUNT(DISTINCT CommandeID) >= 10
   AND SUM(Montant) >= 5000
ORDER BY TotalDepense DESC;
```

**Ordre d'exécution :**

1. **FROM** : Charge `Commandes`

2. **WHERE** : Filtre
   - Commandes depuis 2023
   - Statut = 'Livrée' ou 'En cours'

3. **GROUP BY** : Crée un groupe par `ClientID`

4. **HAVING** : Ne garde que les clients avec
   - Au moins 10 commandes distinctes **ET**
   - Total dépensé ≥ 5000

5. **SELECT** : Calcule toutes les colonnes et agrégations
   - Les alias sont créés ici

6. **ORDER BY** : Trie par dépense totale décroissante

## Mnémotechnique pour retenir l'ordre

Voici quelques moyens mnémotechniques pour retenir l'ordre d'exécution :

### Méthode 1 : La phrase

**"France Where Groupe Have Selectionné Organisation"**

- **F**ROM
- **W**HERE
- **G**ROUP BY
- **H**AVING
- **S**ELECT
- **O**RDER BY

### Méthode 2 : L'histoire

Imaginez que vous organisez une fête :

1. **FROM** : Vous choisissez **d'où** viennent les invités (la table)
2. **WHERE** : Vous **filtrez** qui peut venir (âge, VIP, etc.)
3. **GROUP BY** : Vous **regroupez** les invités (par table, par centre d'intérêt)
4. **HAVING** : Vous **éliminez** les groupes trop petits ou trop grands
5. **SELECT** : Vous **décidez** quelles informations afficher sur les cartons
6. **ORDER BY** : Vous **triez** les cartons par ordre alphabétique

### Méthode 3 : Le processus de recrutement

1. **FROM** : On cherche des candidats (source de données)
2. **WHERE** : On filtre les CV (qualifications de base)
3. **GROUP BY** : On regroupe par département souhaité
4. **HAVING** : On ne garde que les départements avec assez de candidats
5. **SELECT** : On choisit les informations à présenter
6. **ORDER BY** : On classe par score

## Questions fréquentes

### Q1 : Pourquoi SQL n'exécute-t-il pas dans l'ordre d'écriture ?

**Réponse :** C'est une question de logique et d'efficacité. SQL doit d'abord savoir **d'où** viennent les données (`FROM`), puis les **filtrer** (`WHERE`) avant de pouvoir les **regrouper** (`GROUP BY`). Ce n'est qu'après toutes ces opérations qu'il peut déterminer ce qui doit être **affiché** (`SELECT`).

### Q2 : Est-ce que tous les SGBD respectent strictement cet ordre ?

**Réponse :** Oui, l'ordre logique est le même pour tous les SGBD relationnels (SQL Server, MySQL, PostgreSQL, Oracle, etc.). C'est une partie fondamentale du standard SQL. Cependant, certains SGBD peuvent offrir des extensions (comme accepter les alias dans `GROUP BY`), mais ce n'est pas portable.

### Q3 : L'optimiseur de requêtes peut-il changer cet ordre ?

**Réponse :** L'optimiseur peut changer l'**ordre physique** d'exécution pour des raisons de performance, mais le **résultat final** sera toujours comme si l'ordre logique avait été respecté. Par exemple, il peut décider d'utiliser un index pour filtrer avant de charger toute la table, mais le résultat sera identique.

### Q4 : Pourquoi ORDER BY est-il en dernier ?

**Réponse :** Parce que le tri ne peut s'effectuer que sur le résultat final. Si on triait avant de filtrer ou de regrouper, il faudrait retrier après chaque opération, ce qui serait inefficace.

## Résumé

L'ordre logique d'exécution est :

```
1. FROM       → Identifier la source de données
2. WHERE      → Filtrer les lignes individuelles
3. GROUP BY   → Créer les groupes
4. HAVING     → Filtrer les groupes
5. SELECT     → Déterminer les colonnes à afficher
6. ORDER BY   → Trier le résultat final
```

**Conséquences importantes :**
- Les alias créés dans `SELECT` ne sont utilisables que dans `ORDER BY`
- `WHERE` ne peut pas utiliser d'agrégations (utilisez `HAVING`)
- `WHERE` filtre avant le regroupement, `HAVING` après
- Toujours utiliser les noms de colonnes originaux dans `WHERE`, `GROUP BY`, et `HAVING`

**Comprendre cet ordre vous aide à :**
- Écrire des requêtes correctes du premier coup
- Déboguer les erreurs plus facilement
- Optimiser vos requêtes (en filtrant tôt avec `WHERE`)
- Comprendre les messages d'erreur du SGBD
