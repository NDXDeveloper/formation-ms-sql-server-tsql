# 8.4.2 GRANT (Autoriser)

## Introduction

Maintenant que vous comprenez le modèle de sécurité SQL Server (Logins, Users, Rôles, Schémas), il est temps d'apprendre à **donner des permissions** concrètes. C'est exactement le rôle de la commande **GRANT**.

**Analogie simple** : Imaginez que vous êtes le gardien d'un musée. Vous avez les clés de toutes les salles. La commande GRANT, c'est comme **remettre une clé** à quelqu'un pour lui permettre d'accéder à une salle spécifique. Vous décidez :
- 🚪 **À quelle salle** il peut accéder (quelle table, quelle vue, quelle procédure)
- 🔑 **Ce qu'il peut y faire** (regarder, modifier, supprimer)
- 👤 **À qui** vous donnez cette clé (quel user, quel rôle)

## Qu'est-ce que GRANT ?

**GRANT** est une commande SQL qui fait partie du **DCL (Data Control Language)** - le langage de contrôle des données. Elle permet d'**accorder des permissions** à un user ou un rôle.

### Syntaxe de base

```sql
GRANT <permission(s)>
ON <objet>
TO <principal>
[WITH GRANT OPTION];
```

Décomposons chaque élément :

| Élément | Signification | Exemples |
|---------|---------------|----------|
| **permission(s)** | Ce que vous autorisez | SELECT, INSERT, UPDATE, DELETE, EXECUTE |
| **objet** | Sur quoi porte la permission | Table, Vue, Procédure, Schéma, Base |
| **principal** | À qui vous donnez la permission | User, Rôle |
| **WITH GRANT OPTION** | Permet au destinataire de transmettre cette permission à d'autres (optionnel) | |

## Les différents types de permissions

SQL Server propose de nombreuses permissions. Voici les plus courantes, classées par catégorie :

### 1. Permissions sur les données (DML)

Ces permissions contrôlent ce qu'on peut faire avec les **données** dans les tables et vues.

| Permission | Permet de | Exemple d'utilisation |
|------------|-----------|----------------------|
| **SELECT** | Lire les données | Analyste qui consulte les rapports |
| **INSERT** | Ajouter de nouvelles lignes | Application qui enregistre des commandes |
| **UPDATE** | Modifier des lignes existantes | Utilisateur qui met à jour un profil |
| **DELETE** | Supprimer des lignes | Administrateur qui nettoie des données obsolètes |

**Exemple complet** :
```sql
-- Permettre à Jean de lire la table Clients
GRANT SELECT ON dbo.Clients TO Jean;

-- Permettre à l'application d'ajouter et modifier des commandes
GRANT INSERT, UPDATE ON dbo.Commandes TO AppUser;

-- Permettre au rôle RH de tout faire sur la table Employes
GRANT SELECT, INSERT, UPDATE, DELETE ON dbo.Employes TO RoleRH;
```

### 2. Permissions sur la structure (DDL)

Ces permissions contrôlent ce qu'on peut faire avec la **structure** de la base de données.

| Permission | Permet de | Exemple d'utilisation |
|------------|-----------|----------------------|
| **CREATE TABLE** | Créer des tables | Développeur en environnement de test |
| **ALTER** | Modifier la structure d'objets | DBA qui ajoute une colonne |
| **DROP** | Supprimer des objets | Administrateur qui nettoie |
| **VIEW DEFINITION** | Voir le code source | Développeur qui analyse du code |

**Exemple complet** :
```sql
-- Permettre à un développeur de créer des tables
GRANT CREATE TABLE TO Developpeur;

-- Permettre de modifier la structure d'une table spécifique
GRANT ALTER ON dbo.Produits TO AdminDB;

-- Permettre de voir le code d'une procédure stockée sans l'exécuter
GRANT VIEW DEFINITION ON dbo.CalculerCA TO Auditeur;
```

### 3. Permissions sur les procédures et fonctions

| Permission | Permet de | Exemple d'utilisation |
|------------|-----------|----------------------|
| **EXECUTE** | Exécuter une procédure ou fonction | Application qui appelle une procédure métier |

**Exemple complet** :
```sql
-- Permettre à l'application d'exécuter une procédure stockée
GRANT EXECUTE ON dbo.CreerCommande TO AppUser;

-- Permettre l'exécution de toutes les procédures d'un schéma
GRANT EXECUTE ON SCHEMA::Ventes TO RoleVentes;
```

### 4. Permissions au niveau base de données

| Permission | Permet de | Exemple d'utilisation |
|------------|-----------|----------------------|
| **CONNECT** | Se connecter à la base | Accès de base à la base de données |
| **CREATE TABLE** | Créer des tables | Développeur |
| **CREATE VIEW** | Créer des vues | Analyste avancé |
| **CREATE PROCEDURE** | Créer des procédures | Développeur |
| **BACKUP DATABASE** | Sauvegarder la base | Administrateur de sauvegarde |

**Exemple complet** :
```sql
-- Permettre à un user de se connecter à la base
GRANT CONNECT TO UtilisateurExterne;

-- Permettre à un développeur de créer des objets
GRANT CREATE TABLE, CREATE VIEW, CREATE PROCEDURE TO Developpeur;
```

## Niveaux de granularité des permissions

Les permissions peuvent être accordées à différents **niveaux de granularité**. Plus vous descendez dans la hiérarchie, plus vous êtes précis.

### 1. Niveau Serveur (le plus large)

```sql
-- Permettre de créer des bases de données sur tout le serveur
GRANT CREATE DATABASE TO [DOMAINE\Developpeurs];

-- Permettre de voir les métadonnées du serveur
GRANT VIEW ANY DATABASE TO [DOMAINE\Auditeurs];
```

⚠️ **Attention** : Les permissions au niveau serveur sont très puissantes. Utilisez-les avec parcimonie.

### 2. Niveau Base de données

```sql
USE MaBaseDeDonnees;
GO

-- Permettre de créer des tables dans cette base
GRANT CREATE TABLE TO Developpeur;

-- Permettre de sauvegarder cette base
GRANT BACKUP DATABASE TO AdminBackup;
```

### 3. Niveau Schéma (pratique pour les groupes d'objets)

```sql
-- Permettre de lire TOUTES les tables du schéma Ventes
GRANT SELECT ON SCHEMA::Ventes TO AnalysteVentes;

-- Permettre de tout faire dans le schéma Test
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::Test TO Developpeur;

-- Permettre d'exécuter TOUTES les procédures du schéma Rapports
GRANT EXECUTE ON SCHEMA::Rapports TO RoleRapports;
```

💡 **Avantage** : Quand vous ajoutez une nouvelle table au schéma Ventes, les permissions s'appliquent automatiquement ! Pas besoin de refaire un GRANT.

### 4. Niveau Objet (table, vue, procédure spécifique)

```sql
-- Permettre de lire UNE table spécifique
GRANT SELECT ON dbo.Clients TO Analyste;

-- Permettre de modifier UNE table spécifique
GRANT UPDATE ON dbo.Produits TO GestionnaireProduits;

-- Permettre d'exécuter UNE procédure spécifique
GRANT EXECUTE ON dbo.CalculerRemise TO AppCommerce;
```

### 5. Niveau Colonne (le plus précis)

Le plus granulaire : vous pouvez donner accès à certaines colonnes d'une table, mais pas à d'autres.

```sql
-- Permettre de lire SEULEMENT certaines colonnes
GRANT SELECT ON dbo.Employes (EmployeID, Nom, Prenom, Departement) TO ManagerDepartement;
-- Le manager ne peut PAS voir la colonne Salaire

-- Permettre de modifier SEULEMENT certaines colonnes
GRANT UPDATE ON dbo.Employes (Telephone, Email) TO EmployeStandard;
-- L'employé peut mettre à jour ses coordonnées, mais pas son salaire
```

💡 **Cas d'usage** : Très utile pour protéger les données sensibles (salaires, numéros de sécurité sociale, etc.) tout en permettant l'accès aux autres informations.

## Exemples pratiques par scénario

### Scénario 1 : Analyste en lecture seule

**Besoin** : Un analyste doit pouvoir consulter les données de vente, mais pas les modifier.

```sql
-- Créer un rôle pour les analystes
CREATE ROLE RoleAnalystes;

-- Donner accès en lecture à toutes les tables de ventes
GRANT SELECT ON SCHEMA::Ventes TO RoleAnalystes;

-- Donner accès aux vues de rapports
GRANT SELECT ON SCHEMA::Rapports TO RoleAnalystes;

-- Ajouter l'analyste au rôle
ALTER ROLE RoleAnalystes ADD MEMBER Marie;
```

**Résultat** : Marie peut faire des `SELECT` partout dans Ventes et Rapports, mais ne peut pas faire d'`INSERT`, `UPDATE` ou `DELETE`.

### Scénario 2 : Application web

**Besoin** : Une application web doit gérer les commandes (créer, lire, modifier) mais ne doit jamais pouvoir supprimer.

```sql
-- Créer le user pour l'application
CREATE USER AppWeb FOR LOGIN AppWebLogin;

-- Permettre de lire et écrire dans les tables nécessaires
GRANT SELECT, INSERT, UPDATE ON dbo.Commandes TO AppWeb;
GRANT SELECT, INSERT, UPDATE ON dbo.LignesCommande TO AppWeb;
GRANT SELECT ON dbo.Produits TO AppWeb;  -- Lecture seule des produits
GRANT SELECT ON dbo.Clients TO AppWeb;   -- Lecture seule des clients

-- Permettre d'exécuter les procédures métier
GRANT EXECUTE ON dbo.CreerCommande TO AppWeb;
GRANT EXECUTE ON dbo.CalculerTotal TO AppWeb;
```

**Résultat** : L'application peut gérer les commandes, mais ne peut **jamais** supprimer de données (pas de permission DELETE).

### Scénario 3 : Développeur en environnement de test

**Besoin** : Un développeur doit pouvoir tout faire dans le schéma Test, mais rien dans Production.

```sql
-- Permissions complètes sur le schéma Test
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::Test TO Developpeur;
GRANT EXECUTE ON SCHEMA::Test TO Developpeur;
GRANT ALTER ON SCHEMA::Test TO Developpeur;

-- Création de nouveaux objets dans Test
GRANT CREATE TABLE TO Developpeur;
GRANT CREATE VIEW TO Developpeur;
GRANT CREATE PROCEDURE TO Developpeur;
```

**Résultat** : Le développeur peut créer, modifier, supprimer tout ce qu'il veut dans Test, mais n'a aucun accès à Production.

### Scénario 4 : Manager avec accès partiel aux données RH

**Besoin** : Un manager doit voir les informations de ses employés, mais pas leurs salaires.

```sql
-- Créer une vue qui cache les colonnes sensibles
CREATE VIEW dbo.VueEmployesPublic AS
SELECT
    EmployeID,
    Nom,
    Prenom,
    Departement,
    Poste,
    DateEmbauche,
    Email,
    Telephone
    -- Salaire, NumeroSecuriteSociale sont EXCLUS
FROM
    dbo.Employes;

-- Donner accès à la vue seulement
GRANT SELECT ON dbo.VueEmployesPublic TO Manager;

-- Le manager ne peut PAS accéder directement à la table
-- (il n'a pas de GRANT sur dbo.Employes)
```

**Alternative avec permissions au niveau colonne** :
```sql
-- Donner accès seulement aux colonnes non-sensibles
GRANT SELECT ON dbo.Employes
    (EmployeID, Nom, Prenom, Departement, Poste, DateEmbauche, Email, Telephone)
    TO Manager;
```

### Scénario 5 : Utilisateur avec droit de délégation

**Besoin** : Un administrateur de données doit pouvoir donner des permissions SELECT à d'autres utilisateurs.

```sql
-- Donner la permission SELECT avec le droit de la transmettre
GRANT SELECT ON dbo.Produits TO AdminDonnees WITH GRANT OPTION;
```

**Résultat** : AdminDonnees peut maintenant exécuter :
```sql
-- AdminDonnees peut à son tour donner cette permission
GRANT SELECT ON dbo.Produits TO Analyste1;
GRANT SELECT ON dbo.Produits TO Analyste2;
```

⚠️ **Attention** : `WITH GRANT OPTION` est puissant mais dangereux. Utilisez-le avec précaution car vous perdez le contrôle direct de qui reçoit la permission.

## Accorder des permissions à des rôles (recommandé)

**Bonne pratique** : Accordez les permissions aux **rôles**, puis ajoutez les users aux rôles. Ne donnez pas les permissions directement aux users individuels.

### ❌ Mauvaise approche (permissions individuelles)

```sql
-- Donner les mêmes permissions à chaque user individuellement
GRANT SELECT ON dbo.Ventes TO Marie;
GRANT SELECT ON dbo.Ventes TO Pierre;
GRANT SELECT ON dbo.Ventes TO Paul;
GRANT SELECT ON dbo.Ventes TO Sophie;
-- ... et ainsi de suite pour chaque nouveau user

-- Si vous devez ajouter une table :
GRANT SELECT ON dbo.Clients TO Marie;
GRANT SELECT ON dbo.Clients TO Pierre;
GRANT SELECT ON dbo.Clients TO Paul;
GRANT SELECT ON dbo.Clients TO Sophie;
-- ... cauchemar de maintenance !
```

**Problèmes** :
- Fastidieux et répétitif
- Erreurs possibles (oubli d'un user)
- Maintenance difficile (modifier les permissions = modifier chaque user)
- Audit complexe

### ✅ Bonne approche (permissions via rôles)

```sql
-- 1. Créer un rôle
CREATE ROLE RoleAnalystesVentes;

-- 2. Donner les permissions au rôle (une seule fois)
GRANT SELECT ON SCHEMA::Ventes TO RoleAnalystesVentes;
GRANT SELECT ON dbo.Clients TO RoleAnalystesVentes;

-- 3. Ajouter les users au rôle
ALTER ROLE RoleAnalystesVentes ADD MEMBER Marie;
ALTER ROLE RoleAnalystesVentes ADD MEMBER Pierre;
ALTER ROLE RoleAnalystesVentes ADD MEMBER Paul;
ALTER ROLE RoleAnalystesVentes ADD MEMBER Sophie;

-- Nouvel arrivant ? Une seule ligne :
ALTER ROLE RoleAnalystesVentes ADD MEMBER Thomas;

-- Besoin d'ajouter une permission ? Une seule modification :
GRANT SELECT ON dbo.Produits TO RoleAnalystesVentes;
-- Tous les membres du rôle en bénéficient automatiquement !
```

**Avantages** :
- ✅ Permissions centralisées
- ✅ Facile à maintenir
- ✅ Cohérence garantie
- ✅ Audit simplifié

## Permissions cumulatives et hiérarchiques

### Les permissions s'accumulent

Si un user appartient à plusieurs rôles, il obtient **toutes** les permissions de tous ses rôles.

```sql
-- Créer deux rôles avec des permissions différentes
CREATE ROLE RoleLecture;
GRANT SELECT ON dbo.Produits TO RoleLecture;

CREATE ROLE RoleEcriture;
GRANT INSERT, UPDATE ON dbo.Produits TO RoleEcriture;

-- Ajouter un user aux deux rôles
ALTER ROLE RoleLecture ADD MEMBER Jean;
ALTER ROLE RoleEcriture ADD MEMBER Jean;

-- Résultat : Jean peut SELECT, INSERT et UPDATE sur Produits
```

### Les permissions héritent de la hiérarchie

Les permissions accordées à un niveau élevé s'appliquent automatiquement aux niveaux inférieurs.

```sql
-- Permission au niveau SCHÉMA
GRANT SELECT ON SCHEMA::Ventes TO Analyste;

-- Automatiquement, Analyste peut faire SELECT sur :
-- - Ventes.Commandes
-- - Ventes.LignesCommande
-- - Ventes.Produits
-- - Toute future table ajoutée au schéma Ventes
```

**Hiérarchie complète** :
```
Serveur
  ↓ (permissions héritées)
Base de données
  ↓ (permissions héritées)
Schéma
  ↓ (permissions héritées)
Objet (Table, Vue, Procédure)
  ↓ (permissions héritées)
Colonne
```

## Vérifier les permissions accordées

### Voir les permissions d'un user spécifique

```sql
USE MaBaseDeDonnees;
GO

-- Voir toutes les permissions de Jean
EXECUTE AS USER = 'Jean';
SELECT * FROM fn_my_permissions(NULL, 'DATABASE');
REVERT;

-- Ou utiliser cette requête
SELECT
    USER_NAME(grantee_principal_id) AS UserName,
    permission_name AS Permission,
    OBJECT_NAME(major_id) AS ObjectName,
    state_desc AS PermissionState
FROM
    sys.database_permissions
WHERE
    USER_NAME(grantee_principal_id) = 'Jean'
ORDER BY
    permission_name, ObjectName;
```

### Voir toutes les permissions sur un objet

```sql
-- Qui a des permissions sur la table Clients ?
SELECT
    USER_NAME(grantee_principal_id) AS UserName,
    permission_name AS Permission,
    state_desc AS PermissionState
FROM
    sys.database_permissions
WHERE
    major_id = OBJECT_ID('dbo.Clients')
ORDER BY
    UserName, permission_name;
```

### Voir les membres d'un rôle

```sql
-- Qui est dans le rôle RoleAnalystes ?
SELECT
    r.name AS RoleName,
    m.name AS MemberName,
    m.type_desc AS MemberType
FROM
    sys.database_role_members rm
    JOIN sys.database_principals r ON rm.role_principal_id = r.principal_id
    JOIN sys.database_principals m ON rm.member_principal_id = m.principal_id
WHERE
    r.name = 'RoleAnalystes';
```

### Tester les permissions

Vous pouvez vous mettre "dans la peau" d'un autre user pour tester ses permissions :

```sql
-- Se mettre dans le contexte de Jean
EXECUTE AS USER = 'Jean';

-- Tenter une requête
SELECT * FROM dbo.Clients;  -- Fonctionne si Jean a SELECT sur Clients

-- Revenir à votre contexte normal
REVERT;
```

💡 **Très utile** pour vérifier que vos permissions sont correctement configurées avant de les déployer en production.

## Permissions spéciales et cas avancés

### 1. GRANT ALL (déconseillé)

```sql
-- Donner TOUTES les permissions sur une table
GRANT ALL ON dbo.Produits TO SuperUser;
```

⚠️ **Déconseillé** : Trop vague et dangereux. Préférez lister explicitement les permissions nécessaires.

### 2. Permissions en cascade sur les objets liés

```sql
-- Créer une procédure qui lit une table
CREATE PROCEDURE dbo.ObtenirClients
AS
BEGIN
    SELECT * FROM dbo.Clients;
END;
GO

-- Donner seulement EXECUTE sur la procédure
GRANT EXECUTE ON dbo.ObtenirClients TO AppUser;

-- AppUser peut exécuter la procédure MÊME SANS permission SELECT sur Clients
-- C'est le "ownership chaining"
```

💡 **Chaînage de propriété** : Si la procédure et la table ont le même propriétaire (généralement `dbo`), les permissions sont "enchaînées". L'utilisateur hérite temporairement des permissions du propriétaire pendant l'exécution.

### 3. Permissions sur les vues

```sql
-- Créer une vue qui filtre les données
CREATE VIEW dbo.VueEmployesDepartement AS
SELECT EmployeID, Nom, Prenom, Poste
FROM dbo.Employes
WHERE Departement = 'Ventes';
GO

-- Donner accès à la vue seulement
GRANT SELECT ON dbo.VueEmployesDepartement TO ManagerVentes;

-- ManagerVentes voit seulement son département via la vue
-- Il ne peut PAS accéder directement à dbo.Employes
```

**Avantage** : Contrôle très fin sur ce que chaque user peut voir.

### 4. Permissions sur les colonnes calculées et encryptées

```sql
-- Table avec colonne encryptée
CREATE TABLE dbo.CartesCredit (
    CarteID INT PRIMARY KEY,
    ClientID INT NOT NULL,
    NumeroCarteEncrypte VARBINARY(256) NOT NULL,
    DateExpiration DATE
);

-- User peut voir tout SAUF le numéro de carte
GRANT SELECT ON dbo.CartesCredit (CarteID, ClientID, DateExpiration) TO EmployeService;

-- Seul l'administrateur peut voir le numéro encrypté
GRANT SELECT ON dbo.CartesCredit TO AdminSecurite;
```

## Permissions et procédures stockées : pattern de sécurité

Une technique courante est de **ne jamais donner accès direct aux tables**, mais seulement via des procédures stockées.

### Pattern de sécurité recommandé

```sql
-- 1. Tables (aucune permission directe pour les users)
CREATE TABLE dbo.Commandes (
    CommandeID INT PRIMARY KEY IDENTITY,
    ClientID INT NOT NULL,
    DateCommande DATE NOT NULL,
    Montant DECIMAL(10,2) NOT NULL
);

-- 2. Procédures stockées (logique métier contrôlée)
CREATE PROCEDURE dbo.CreerCommande
    @ClientID INT,
    @Montant DECIMAL(10,2)
AS
BEGIN
    -- Validation métier
    IF @Montant <= 0
        THROW 50001, 'Le montant doit être positif', 1;

    IF NOT EXISTS (SELECT 1 FROM dbo.Clients WHERE ClientID = @ClientID)
        THROW 50002, 'Client inconnu', 1;

    -- Insertion
    INSERT INTO dbo.Commandes (ClientID, DateCommande, Montant)
    VALUES (@ClientID, GETDATE(), @Montant);
END;
GO

-- 3. Permissions (SEULEMENT sur les procédures)
GRANT EXECUTE ON dbo.CreerCommande TO AppWeb;

-- AppWeb peut créer des commandes UNIQUEMENT via la procédure
-- AppWeb ne peut PAS faire INSERT direct (contournant les validations)
```

**Avantages** :
- ✅ Logique métier centralisée
- ✅ Validations garanties
- ✅ Audit facilité (toutes les actions passent par les procédures)
- ✅ Sécurité renforcée (impossible de contourner les règles)

## Erreurs courantes et solutions

### Erreur 1 : "The SELECT permission was denied on the object"

**Cause** : Le user essaie de lire une table sans permission SELECT.

**Solution** :
```sql
-- Donner la permission SELECT
GRANT SELECT ON dbo.Clients TO Jean;
```

### Erreur 2 : "Cannot find the user because it does not exist"

**Cause** : Vous essayez de donner une permission à un user qui n'existe pas.

**Solution** :
```sql
-- Créer d'abord le user
CREATE USER Jean FOR LOGIN [DOMAINE\JeanDupont];

-- Puis donner la permission
GRANT SELECT ON dbo.Clients TO Jean;
```

### Erreur 3 : Permission donnée mais l'user ne peut toujours pas accéder

**Cause possible 1** : Un DENY explicite bloque l'accès (DENY est plus fort que GRANT).

**Solution** :
```sql
-- Vérifier s'il y a un DENY
SELECT
    permission_name,
    state_desc
FROM
    sys.database_permissions
WHERE
    USER_NAME(grantee_principal_id) = 'Jean'
    AND state_desc = 'DENY';

-- Retirer le DENY (voir section 8.4.3)
REVOKE SELECT ON dbo.Clients TO Jean;
```

**Cause possible 2** : Le user n'est pas connecté à la bonne base de données.

**Solution** :
```sql
-- Vérifier que le user existe dans la base
USE MaBaseDeDonnees;
GO

SELECT name FROM sys.database_principals WHERE name = 'Jean';
```

### Erreur 4 : "Cannot grant, deny or revoke permissions to sa, dbo, information_schema, sys or yourself"

**Cause** : Vous essayez de modifier les permissions des users système.

**Solution** : Ne modifiez jamais les permissions des users système (`sa`, `dbo`, `sys`, etc.).

## Bonnes pratiques GRANT

### 1. Utilisez les rôles, pas les users individuels ✅

```sql
-- ✅ BON
CREATE ROLE RoleVentes;
GRANT SELECT ON SCHEMA::Ventes TO RoleVentes;
ALTER ROLE RoleVentes ADD MEMBER Jean;

-- ❌ MAUVAIS
GRANT SELECT ON SCHEMA::Ventes TO Jean;
```

### 2. Principe du moindre privilège ✅

Donnez uniquement ce qui est strictement nécessaire.

```sql
-- ✅ BON : Permissions précises
GRANT SELECT ON dbo.Clients TO Analyste;
GRANT SELECT ON dbo.Commandes TO Analyste;

-- ❌ MAUVAIS : Trop large
GRANT SELECT ON SCHEMA::dbo TO Analyste;  -- Accès à TOUT !
```

### 3. Préférez les schémas pour grouper les objets ✅

```sql
-- ✅ BON : Permission au niveau schéma
GRANT SELECT ON SCHEMA::Ventes TO RoleVentes;
-- S'applique automatiquement à toutes les tables du schéma

-- ❌ MAUVAIS : Permission sur chaque table
GRANT SELECT ON dbo.Commandes TO RoleVentes;
GRANT SELECT ON dbo.Clients TO RoleVentes;
GRANT SELECT ON dbo.Produits TO RoleVentes;
-- ... répétitif et sujet aux oublis
```

### 4. Documentez vos permissions ✅

```sql
-- Créer un script de documentation
/*
ROLE: RoleAnalystesVentes
OBJECTIF: Permettre aux analystes de consulter les données de ventes
PERMISSIONS:
- SELECT sur SCHEMA::Ventes (toutes les tables de ventes)
- SELECT sur SCHEMA::Rapports (vues de rapports)
- EXECUTE sur SCHEMA::Statistiques (procédures de calcul)
MEMBRES: Marie, Pierre, Paul
*/

CREATE ROLE RoleAnalystesVentes;
GRANT SELECT ON SCHEMA::Ventes TO RoleAnalystesVentes;
GRANT SELECT ON SCHEMA::Rapports TO RoleAnalystesVentes;
GRANT EXECUTE ON SCHEMA::Statistiques TO RoleAnalystesVentes;
```

### 5. Évitez WITH GRANT OPTION sauf nécessité absolue ⚠️

```sql
-- ⚠️ À ÉVITER : Perte de contrôle
GRANT SELECT ON dbo.Clients TO Manager WITH GRANT OPTION;
-- Manager peut maintenant donner cette permission à n'importe qui

-- ✅ PRÉFÉRABLE : Gérez vous-même les permissions
GRANT SELECT ON dbo.Clients TO Manager;
```

### 6. Testez les permissions avant la production ✅

```sql
-- Créer un script de test
EXECUTE AS USER = 'AppUser';

-- Test 1 : Doit fonctionner
SELECT * FROM dbo.Commandes;

-- Test 2 : Doit échouer (pas de DELETE)
DELETE FROM dbo.Commandes WHERE CommandeID = 1;

REVERT;
```

### 7. Auditez régulièrement les permissions ✅

```sql
-- Qui a des permissions sur les tables sensibles ?
SELECT
    OBJECT_NAME(major_id) AS TableName,
    USER_NAME(grantee_principal_id) AS UserName,
    permission_name AS Permission,
    state_desc AS State
FROM
    sys.database_permissions
WHERE
    OBJECT_NAME(major_id) IN ('Employes', 'Salaires', 'CartesCredit')
ORDER BY
    TableName, UserName;
```

## Récapitulatif : Matrice des permissions courantes

### Permissions DML (données)

| Besoin | Commande |
|--------|----------|
| Lire une table | `GRANT SELECT ON dbo.Clients TO User` |
| Ajouter des lignes | `GRANT INSERT ON dbo.Clients TO User` |
| Modifier des lignes | `GRANT UPDATE ON dbo.Clients TO User` |
| Supprimer des lignes | `GRANT DELETE ON dbo.Clients TO User` |
| Tout faire avec les données | `GRANT SELECT, INSERT, UPDATE, DELETE ON dbo.Clients TO User` |

### Permissions DDL (structure)

| Besoin | Commande |
|--------|----------|
| Créer des tables | `GRANT CREATE TABLE TO User` |
| Modifier une table | `GRANT ALTER ON dbo.Clients TO User` |
| Supprimer une table | `GRANT DROP ON dbo.Clients TO User` (rarement utilisé) |
| Voir le code source | `GRANT VIEW DEFINITION ON dbo.MaProcedure TO User` |

### Permissions sur procédures/fonctions

| Besoin | Commande |
|--------|----------|
| Exécuter une procédure | `GRANT EXECUTE ON dbo.MaProcedure TO User` |
| Exécuter toutes les procédures d'un schéma | `GRANT EXECUTE ON SCHEMA::MonSchema TO User` |

### Permissions au niveau schéma

| Besoin | Commande |
|--------|----------|
| Lecture complète d'un schéma | `GRANT SELECT ON SCHEMA::Ventes TO User` |
| Écriture complète d'un schéma | `GRANT INSERT, UPDATE, DELETE ON SCHEMA::Ventes TO User` |
| Exécution de toutes les procédures | `GRANT EXECUTE ON SCHEMA::Ventes TO User` |

## Conclusion

La commande **GRANT** est la clé pour **autoriser des accès** dans SQL Server. Elle vous permet de contrôler précisément :

- **Qui** peut accéder (Users, Rôles)
- **À quoi** ils peuvent accéder (Tables, Vues, Procédures, Schémas)
- **Ce qu'ils peuvent faire** (SELECT, INSERT, UPDATE, DELETE, EXECUTE, etc.)

**Points essentiels à retenir** :

1. 🎯 **Soyez précis** : Donnez uniquement les permissions nécessaires (principe du moindre privilège)
2. 👥 **Utilisez les rôles** : Ne donnez pas de permissions directement aux users individuels
3. 📁 **Exploitez les schémas** : Permissions au niveau schéma = maintenance simplifiée
4. 🧪 **Testez** : Utilisez `EXECUTE AS USER` pour vérifier vos permissions
5. 📝 **Documentez** : Expliquez pourquoi chaque permission est accordée
6. 🔍 **Auditez** : Vérifiez régulièrement qui a accès à quoi

Dans les prochaines sections, nous verrons **DENY** (refuser explicitement) et **REVOKE** (retirer une permission), qui complètent le triptyque de gestion des permissions en SQL Server.

---

**Points clés à retenir** :
- GRANT = Donner une permission
- Syntaxe : `GRANT permission ON objet TO principal`
- Permissions DML : SELECT, INSERT, UPDATE, DELETE
- Permissions DDL : CREATE, ALTER, DROP
- Granularité : Serveur → Base → Schéma → Objet → Colonne
- WITH GRANT OPTION = Permet de transmettre la permission
- Toujours privilégier les rôles aux users individuels
- Principe du moindre privilège = Sécurité maximale
