# 6.4.6 SNAPSHOT ISOLATION

## Introduction

Nous avons vu que **SERIALIZABLE** offre une isolation totale (empêche toutes les anomalies de concurrence), mais au prix de performances très faibles et de blocages massifs. Le niveau d'isolation **SNAPSHOT** représente l'**approche moderne** : il bloque **les trois anomalies classiques** (dirty / non-repeatable / phantom reads), comme SERIALIZABLE, mais en utilisant le **versioning de lignes** au lieu des verrous. (Sa sémantique reste toutefois **légèrement différente** de SERIALIZABLE — voir plus bas l'anomalie du *write skew*.)

Résultat : **isolation maximale** avec de **bien meilleures performances** et **aucun blocage en lecture**. C'est souvent considéré comme le "meilleur des deux mondes".

---

## Qu'est-ce que SNAPSHOT ISOLATION ?

### Définition

**SNAPSHOT ISOLATION** est un niveau d'isolation qui :
1. Fournit une **vue cohérente** de la base de données au début de la transaction
2. Cette vue reste **figée** pendant toute la durée de la transaction
3. Utilise le **versioning de lignes** (stocké dans tempdb) au lieu des verrous
4. Empêche **toutes les anomalies de concurrence** (dirty/non-repeatable/phantom reads)
5. Les lecteurs **ne bloquent jamais** et **ne sont jamais bloqués**

### Caractéristiques principales

| Caractéristique | SNAPSHOT ISOLATION |
|-----------------|-------------------|
| **Dirty Reads** | ❌ Bloquées |
| **Non-Repeatable Reads** | ❌ Bloquées |
| **Phantom Reads** | ❌ Bloquées |
| **Mécanisme** | Versioning de lignes (tempdb) |
| **Verrous de lecture** | ❌ Aucun |
| **Blocage en lecture** | ❌ Jamais |
| **Performances lecture** | ⭐⭐⭐⭐⭐ Excellentes |
| **Performances écriture** | ⭐⭐⭐⭐ Bonnes |
| **Overhead tempdb** | ⚠️ Modéré à élevé |
| **Cohérence** | ⭐⭐⭐⭐⭐ Maximale |

### Analogie : La machine à remonter le temps

Imaginez que vous avez une **machine à photographier le temps** :
- Au début de votre transaction, vous prenez une **photo complète** de la base de données
- Pendant toute votre transaction, vous travaillez avec cette **photo figée**
- Même si d'autres personnes modifient les données réelles, **votre photo ne change pas**
- Vous voyez toujours les données telles qu'elles étaient au **moment du snapshot**
- Quand vous terminez, la photo est détruite

C'est exactement le comportement de SNAPSHOT : vous travaillez avec une "photographie" cohérente et immuable des données.

## Comment fonctionne SNAPSHOT ISOLATION ?

### Le principe du versioning

Avec SNAPSHOT ISOLATION :
1. Au **début de la transaction**, SQL Server enregistre un "timestamp" logique
2. Toutes les lectures voient les données telles qu'elles étaient **à ce moment précis**
3. Les anciennes versions sont **stockées dans tempdb**
4. Les modifications d'autres transactions ne sont **pas visibles**
5. À la fin de la transaction, les versions ne sont plus nécessaires

### Schéma de fonctionnement

```
État initial de la base de données (10:00:00)
┌──────────┬────────┬────────┐
│ ProduitID│  Nom   │  Prix  │
├──────────┼────────┼────────┤
│    1     │ Laptop │  100   │
│    2     │ Mouse  │   20   │
└──────────┴────────┴────────┘

Transaction A commence (10:00:05)
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
-- Snapshot timestamp : 10:00:05
-- Transaction A voit la base telle qu'elle était à 10:00:05

Transaction B modifie les données (10:00:10)
BEGIN TRANSACTION;
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
COMMIT;

Base de données actuelle (10:00:15)
┌──────────┬────────┬────────┐
│ ProduitID│  Nom   │  Prix  │
├──────────┼────────┼────────┤
│    1     │ Laptop │  150   │ ← Nouvelle version (dans la table)
│    2     │ Mouse  │   20   │
└──────────┴────────┴────────┘

tempdb (version store)
┌──────────┬────────┬────────┬──────────┐
│ ProduitID│  Nom   │  Prix  │Timestamp │
├──────────┼────────┼────────┼──────────┤
│    1     │ Laptop │  100   │ 10:00:05 │ ← Ancienne version pour Transaction A
└──────────┴────────┴────────┴──────────┘

Transaction A lit (10:00:20)
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Résultat : 100 (lit depuis tempdb, version à 10:00:05)
-- Même si la valeur actuelle est 150 !

COMMIT;  -- Transaction A termine
-- La version dans tempdb peut être nettoyée
```

**Résultat :** Transaction A voit toujours Prix = 100, même si B a validé Prix = 150 entre-temps.

## Différence avec SERIALIZABLE

### SERIALIZABLE : Approche par verrous

```sql
-- Transaction A (SERIALIZABLE)
BEGIN TRANSACTION;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT * FROM Produits WHERE ProduitID = 1;
-- Verrous placés sur la ligne
-- Verrous de plage pour empêcher insertions

-- Transaction B tente de modifier
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
-- BLOQUÉE ! Doit attendre A

COMMIT;
```

**Problème :** Blocage. Transaction B attend Transaction A.

### SNAPSHOT : Approche par versioning

```sql
-- Transaction A (SNAPSHOT)
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

SELECT * FROM Produits WHERE ProduitID = 1;
-- Résultat : 100
-- AUCUN verrou placé
-- Lit la version du snapshot

-- Transaction B modifie
UPDATE Produits SET Prix = 150 WHERE ProduitID = 1;
COMMIT;
-- PAS DE BLOCAGE !

-- Transaction A relit
SELECT * FROM Produits WHERE ProduitID = 1;
-- Résultat : 100 (toujours la même)
-- Voit toujours la version du snapshot

COMMIT;
```

**Avantage :** Aucun blocage. Les deux transactions progressent librement.

### Tableau comparatif

| Aspect | SERIALIZABLE | SNAPSHOT |
|--------|--------------|----------|
| **Mécanisme** | Verrous de plage | Versioning (tempdb) |
| **Dirty Reads** | ❌ | ❌ |
| **Non-Rep. Reads** | ❌ | ❌ |
| **Phantom Reads** | ❌ | ❌ |
| **Blocage lecture** | ✅ Fréquent | ❌ Jamais |
| **Performance** | ⭐⭐ Faible | ⭐⭐⭐⭐ Bonne |
| **Overhead tempdb** | ❌ Aucun | ✅ Modéré |
| **Usage** | Rare (< 5%) | Plus fréquent |

### ⚠️ SNAPSHOT n'est PAS exactement équivalent à SERIALIZABLE

Au niveau des **trois anomalies classiques** (dirty / non-repeatable / phantom reads), SNAPSHOT et SERIALIZABLE offrent la même protection. Mais leur sémantique **diffère** : SERIALIZABLE garantit une véritable **sérialisabilité** (le résultat est équivalent à une exécution des transactions l'une après l'autre), alors que SNAPSHOT garantit seulement que chaque transaction voit un **instantané cohérent**.

La différence se manifeste dans une anomalie que SNAPSHOT **n'empêche pas** : le **write skew** (« biais d'écriture »). Deux transactions SNAPSHOT lisent le même instantané, puis modifient des **lignes différentes** d'après ce qu'elles ont lu — chacune est valide isolément, mais leur combinaison viole une règle métier globale.

```sql
-- Règle métier : au moins UN médecin doit rester de garde.
-- État initial : Dr Martin = de garde, Dr Durand = de garde.

-- Transaction A (SNAPSHOT)               -- Transaction B (SNAPSHOT)
-- Voit : 2 médecins de garde             -- Voit : 2 médecins de garde
-- « OK, je peux me retirer »             -- « OK, je peux me retirer »
UPDATE Medecins SET DeGarde = 0           UPDATE Medecins SET DeGarde = 0
WHERE Nom = 'Martin';                     WHERE Nom = 'Durand';
COMMIT;  -- succès                        COMMIT;  -- succès (lignes DIFFÉRENTES → pas de conflit 3960)

-- Résultat : PLUS AUCUN médecin de garde → la règle métier est violée !
```

Comme les deux transactions modifient des **lignes différentes**, il n'y a **pas** de conflit de mise à jour (erreur 3960), et les deux réussissent. **SERIALIZABLE**, lui, aurait empêché ce scénario. Si votre logique dépend d'un invariant portant sur **plusieurs lignes**, utilisez **SERIALIZABLE**, ou forcez un verrou explicite (`UPDLOCK`, `HOLDLOCK`) sur les lignes lues.

## Différence avec READ COMMITTED SNAPSHOT (RCSI)

Nous avons déjà vu RCSI (section 6.4.3). Quelle est la différence avec SNAPSHOT ?

### READ COMMITTED SNAPSHOT (RCSI)

**Vue cohérente : Par requête**

```sql
-- Avec RCSI activé
BEGIN TRANSACTION;
-- Pas besoin de SET TRANSACTION ISOLATION LEVEL

-- Première lecture (10:00:05)
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Résultat : 100
-- Snapshot pris à 10:00:05

-- Transaction B modifie et valide
-- UPDATE ... SET Prix = 150; COMMIT;

-- Deuxième lecture (10:00:20)
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Résultat : 150 (nouveau snapshot à 10:00:20)
-- Chaque requête voit la dernière version validée

COMMIT;
```

**Comportement :** Chaque SELECT voit la dernière version validée au moment de cette requête.

### SNAPSHOT ISOLATION

**Vue cohérente : Toute la transaction**

```sql
-- Avec SNAPSHOT
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
-- Snapshot pris au début de la transaction

-- Première lecture (10:00:05)
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Résultat : 100
-- Snapshot de toute la transaction : 10:00:05

-- Transaction B modifie et valide
-- UPDATE ... SET Prix = 150; COMMIT;

-- Deuxième lecture (10:00:20)
SELECT Prix FROM Produits WHERE ProduitID = 1;
-- Résultat : 100 (toujours le même snapshot)
-- Voit toujours la version du début de la transaction

COMMIT;
```

**Comportement :** Toutes les lectures voient la même version (celle du début de la transaction).

### Tableau comparatif RCSI vs SNAPSHOT

| Aspect | RCSI | SNAPSHOT |
|--------|------|----------|
| **Type** | Variante de READ COMMITTED | Niveau d'isolation distinct |
| **Snapshot pris** | À chaque requête | Au début de la transaction |
| **Non-Rep. Reads** | ✅ Autorisées | ❌ Bloquées |
| **Phantom Reads** | ✅ Autorisées | ❌ Bloquées |
| **Vue cohérente** | Par requête | Toute la transaction |
| **Activation** | Option de base | Option de base + SET TRANSACTION |
| **Usage typique** | Applications web | Rapports, analyses |

## Les conflits d'écriture (Write Conflicts)

### Le défi de SNAPSHOT

Avec SNAPSHOT, il y a un cas particulier : les **conflits d'écriture**. Si deux transactions SNAPSHOT tentent de modifier la **même ligne**, l'une d'elles sera **annulée**.

### Exemple de conflit

```sql
-- Transaction A (SNAPSHOT)
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Lit le stock actuel : 10
SELECT @Stock = Stock FROM Produits WHERE ProduitID = 1;

-- Transaction B (SNAPSHOT - en parallèle)
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Lit aussi le stock : 10
SELECT @Stock = Stock FROM Produits WHERE ProduitID = 1;

-- Transaction A modifie
UPDATE Produits SET Stock = @Stock - 5 WHERE ProduitID = 1;
-- Stock = 5
COMMIT;  -- Succès

-- Transaction B tente de modifier LA MÊME ligne
UPDATE Produits SET Stock = @Stock - 3 WHERE ProduitID = 1;
-- ERREUR 3960 !
-- "Snapshot isolation transaction aborted due to update conflict"

ROLLBACK;
```

### Erreur 3960 : Update Conflict

Quand un conflit d'écriture se produit, SQL Server retourne l'erreur **3960** :

```
Msg 3960, Level 16, State 2, Line 1
Snapshot isolation transaction aborted due to update conflict.
You cannot use snapshot isolation to access table 'Produits'
directly or indirectly in database 'MaBase' to update, delete,
or insert the row that has been modified or deleted by another
transaction. Retry the transaction or change the isolation level
for the update/delete statement.
```

### Pourquoi ce conflit ?

```
Transaction A snapshot : Stock = 10
Transaction B snapshot : Stock = 10

Transaction A écrit : Stock = 5 (10 - 5)
Transaction B veut écrire : Stock = 7 (10 - 3)

Problème : Transaction B baserait sa décision sur des données obsolètes (10)
alors que la valeur actuelle est 5 !

SQL Server empêche cela en annulant Transaction B.
```

### Gestion des conflits : Retry Logic

L'application doit être capable de **réessayer** la transaction :

```sql
DECLARE @Tentatives INT = 0;
DECLARE @MaxTentatives INT = 3;
DECLARE @Success BIT = 0;

WHILE @Tentatives < @MaxTentatives AND @Success = 0
BEGIN
    BEGIN TRY
        SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
        BEGIN TRANSACTION;

        -- Lire et modifier
        DECLARE @Stock INT;
        SELECT @Stock = Stock FROM Produits WHERE ProduitID = 1;
        UPDATE Produits SET Stock = @Stock - 5 WHERE ProduitID = 1;

        COMMIT;
        SET @Success = 1;
    END TRY
    BEGIN CATCH
        IF ERROR_NUMBER() = 3960  -- Update conflict
        BEGIN
            SET @Tentatives = @Tentatives + 1;
            ROLLBACK;
            -- Attendre un peu avant de réessayer
            WAITFOR DELAY '00:00:00.100';  -- 100ms
        END
        ELSE
        BEGIN
            -- Autre erreur, propager
            ROLLBACK;
            THROW;
        END
    END CATCH
END

IF @Success = 0
BEGIN
    RAISERROR('Échec après plusieurs tentatives', 16, 1);
END
```

## Activation de SNAPSHOT ISOLATION

### Important : Configuration au niveau de la base de données

Comme RCSI, SNAPSHOT nécessite une activation au niveau de la base de données.

### Activer SNAPSHOT

```sql
-- 1. Activer l'option SNAPSHOT pour la base de données
ALTER DATABASE VotreBaseDeDonnees
SET ALLOW_SNAPSHOT_ISOLATION ON;
```

**⚠️ Important :** Cette opération peut prendre du temps selon la taille de la base.

### Utiliser SNAPSHOT dans vos transactions

```sql
-- 2. Définir le niveau d'isolation SNAPSHOT AVANT de démarrer la transaction
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Vos opérations...
SELECT * FROM Produits;

COMMIT;
```

> ⚠️ **Ordre impératif** : pour SNAPSHOT, le `SET TRANSACTION ISOLATION LEVEL SNAPSHOT` doit être exécuté **avant** le `BEGIN TRANSACTION`. Si l'on tente de basculer en SNAPSHOT alors qu'une transaction est **déjà ouverte**, SQL Server lève l'erreur **Msg 3951** (« …the transaction did not start in snapshot isolation »). C'est une particularité de SNAPSHOT : les autres niveaux (READ COMMITTED, REPEATABLE READ, SERIALIZABLE) tolèrent, eux, un changement de niveau en cours de transaction.

### Vérifier si SNAPSHOT est activé

```sql
-- Vérifier l'état de SNAPSHOT
SELECT
    name,
    snapshot_isolation_state_desc,
    is_read_committed_snapshot_on
FROM sys.databases
WHERE name = 'VotreBaseDeDonnees';
```

### Désactiver SNAPSHOT

```sql
-- Désactiver SNAPSHOT (revenir au comportement par défaut)
ALTER DATABASE VotreBaseDeDonnees
SET ALLOW_SNAPSHOT_ISOLATION OFF;
```

## Avantages de SNAPSHOT ISOLATION

### 1. Aucun blocage en lecture

**Le principal avantage :** Les lecteurs ne bloquent jamais et ne sont jamais bloqués.

```sql
-- Transaction A : Lecture longue (SNAPSHOT)
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

SELECT * FROM GigantesqueTable;  -- 10 millions de lignes
-- Prend 5 minutes

COMMIT;

-- Transaction B : Écriture simultanée
UPDATE GigantesqueTable SET ... WHERE ...;
-- PAS DE BLOCAGE ! Peut modifier pendant que A lit
```

### 2. Cohérence maximale (comme SERIALIZABLE)

Empêche toutes les anomalies de concurrence :
- ❌ Dirty Reads
- ❌ Non-Repeatable Reads
- ❌ Phantom Reads

```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Ces trois lectures donneront le même résultat
SELECT Prix FROM Produits WHERE ProduitID = 1;  -- 100
-- ... autres transactions modifient ...
SELECT Prix FROM Produits WHERE ProduitID = 1;  -- 100 (garanti)
-- ... autres transactions modifient ...
SELECT Prix FROM Produits WHERE ProduitID = 1;  -- 100 (garanti)

COMMIT;
```

### 3. Performances excellentes

Bien meilleures que SERIALIZABLE, proches de READ COMMITTED.

```
Benchmark (environnement avec concurrence) :
SERIALIZABLE     : 150 transactions/seconde
SNAPSHOT         : 500 transactions/seconde
READ COMMITTED   : 600 transactions/seconde

→ SNAPSHOT est 3x plus rapide que SERIALIZABLE !
```

### 4. Vue cohérente pour toute la transaction

Idéal pour les rapports et analyses qui nécessitent une vue figée.

```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Rapport multi-étapes sur des données cohérentes
SELECT @T1 = SUM(Montant) FROM Ventes WHERE Trimestre = 1;
SELECT @T2 = SUM(Montant) FROM Ventes WHERE Trimestre = 2;
SELECT @T3 = SUM(Montant) FROM Ventes WHERE Trimestre = 3;
SELECT @T4 = SUM(Montant) FROM Ventes WHERE Trimestre = 4;

-- Tous les calculs sont basés sur la même version des données
-- Même si d'autres transactions modifient les ventes

COMMIT;
```

### 5. Réduction des deadlocks

Moins de verrous = moins de risque de deadlock.

## Inconvénients de SNAPSHOT ISOLATION

### 1. Utilisation intensive de tempdb

Les versions sont stockées dans **tempdb**, qui peut grossir significativement.

```
Sans SNAPSHOT : tempdb = 2 GB
Avec SNAPSHOT (application active) : tempdb = 10-20 GB
```

**Recommandation :** Provisionner suffisamment d'espace pour tempdb.

### 2. Overhead sur les écritures

Chaque modification doit créer une version dans tempdb.

**Impact :** Les écritures peuvent être 5-15% plus lentes qu'avec READ COMMITTED.

### 3. Conflits d'écriture (erreur 3960)

Les applications doivent gérer les conflits d'écriture avec une logique de retry.

```sql
-- Nécessite du code supplémentaire pour gérer l'erreur 3960
BEGIN TRY
    -- Transaction...
END TRY
BEGIN CATCH
    IF ERROR_NUMBER() = 3960
        -- Réessayer...
END CATCH
```

### 4. Transactions longues problématiques

Les transactions SNAPSHOT longues conservent les versions dans tempdb.

```sql
-- ❌ PROBLÉMATIQUE
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Transaction qui dure 2 heures
SELECT * FROM HistoriqueComplet;  -- Analyse très longue
-- tempdb doit conserver toutes les versions pendant 2 heures !

COMMIT;
```

### 5. Configuration requise

Nécessite l'activation au niveau de la base de données (contrairement aux autres niveaux).

## Quand utiliser SNAPSHOT ISOLATION ?

### Cas d'usage appropriés ✅

**1. Rapports et analyses complexes**
```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Rapport financier multi-étapes
-- Nécessite une vue cohérente sans bloquer les écritures
SELECT @RevenuTotal = SUM(Montant) FROM Ventes;
SELECT @DepensesTotal = SUM(Montant) FROM Depenses;
SELECT @BeneficeNet = @RevenuTotal - @DepensesTotal;

-- Calculs supplémentaires sur des données cohérentes
-- Pendant ce temps, les écritures continuent sans blocage

COMMIT;
```

**2. Applications nécessitant une cohérence stricte sans blocage**
```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Système de réservation complexe
-- Besoin de cohérence mais sans bloquer les autres réservations
DECLARE @PlacesDisponibles INT;
SELECT @PlacesDisponibles = COUNT(*) FROM Places WHERE Statut = 'Disponible';

IF @PlacesDisponibles >= @NombreDemande
    -- Procéder à la réservation
    -- Vue cohérente garantie

COMMIT;
```

**3. Opérations de lecture longues**
```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Export de données qui prend 10 minutes
-- Ne bloque pas les écritures pendant ce temps
SELECT * FROM GrosseTable ORDER BY DateCreation;

COMMIT;
```

**4. Alternative moderne à SERIALIZABLE**
```sql
-- Au lieu de SERIALIZABLE (qui bloque tout)
-- Utiliser SNAPSHOT (mêmes garanties, sans blocage)
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Opération critique nécessitant isolation maximale
-- Mais sans paralyser le système

COMMIT;
```

**5. Environnements avec forte concurrence lecture/écriture**
```
Scénario : 500 lecteurs + 50 écrivains simultanés
SERIALIZABLE : Blocages massifs
SNAPSHOT : Tous progressent sans blocage
```

### Cas où NE PAS utiliser SNAPSHOT ❌

**1. Opérations d'écriture intensives**
```
Application avec 80% d'écritures, 20% de lectures
→ L'overhead de SNAPSHOT peut être excessif
→ Préférer READ COMMITTED
```

**2. tempdb déjà sous pression**
```sql
-- Si tempdb est déjà proche de ses limites
-- SNAPSHOT va aggraver la situation
-- → Provisionner plus d'espace ou éviter SNAPSHOT
```

**3. Transactions très courtes**
```sql
-- ❌ INUTILE : SNAPSHOT est overkill
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
SELECT * FROM Produits WHERE ProduitID = 1;
COMMIT;

-- → READ COMMITTED suffit
```

**4. Opérations simples sans besoin de cohérence stricte**
```sql
-- Pour des opérations CRUD simples
-- READ COMMITTED ou RCSI sont suffisants
```

**5. Espace disque limité**
```
Serveur avec peu d'espace disque
→ tempdb peut grossir de manière importante avec SNAPSHOT
→ Risque de saturation
```

## Exemple pratique complet

### Scénario : Système de reporting en temps réel

```sql
-- ========================================
-- DASHBOARD DE REPORTING TEMPS RÉEL
-- Utilise SNAPSHOT pour :
-- - Vue cohérente des données
-- - Pas de blocage des opérations transactionnelles
-- - Garantie : Tous les chiffres correspondent
-- ========================================

-- 1. Activer SNAPSHOT (une fois, par l'administrateur)
ALTER DATABASE ECommerce
SET ALLOW_SNAPSHOT_ISOLATION ON;

-- 2. Génération du rapport (exécuté toutes les 5 minutes)
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
-- Snapshot pris : Maintenant (ex: 14:35:00)

DECLARE @DateRapport DATETIME = GETDATE();

-- Statistiques de ventes du jour
DECLARE @NombreCommandes INT;
DECLARE @ChiffreAffaires DECIMAL(15,2);
DECLARE @PanierMoyen DECIMAL(10,2);

SELECT
    @NombreCommandes = COUNT(*),
    @ChiffreAffaires = SUM(MontantTotal)
FROM Commandes
WHERE CAST(DateCommande AS DATE) = CAST(@DateRapport AS DATE);

SET @PanierMoyen = @ChiffreAffaires / NULLIF(@NombreCommandes, 0);

-- Produits les plus vendus (même snapshot)
DECLARE @TopProduits TABLE (
    ProduitID INT,
    NomProduit NVARCHAR(100),
    NombreVentes INT
);

INSERT INTO @TopProduits
SELECT TOP 10
    p.ProduitID,
    p.Nom,
    COUNT(*) AS NombreVentes
FROM LignesCommande cl
INNER JOIN Commandes c ON cl.CommandeID = c.CommandeID
INNER JOIN Produits p ON cl.ProduitID = p.ProduitID
WHERE CAST(c.DateCommande AS DATE) = CAST(@DateRapport AS DATE)
GROUP BY p.ProduitID, p.Nom
ORDER BY COUNT(*) DESC;

-- Statistiques par catégorie (même snapshot)
DECLARE @VentesParCategorie TABLE (
    Categorie NVARCHAR(50),
    ChiffreAffaires DECIMAL(15,2),
    NombreProduits INT
);

INSERT INTO @VentesParCategorie
SELECT
    p.Categorie,
    SUM(cl.PrixUnitaire * cl.Quantite) AS ChiffreAffaires,
    COUNT(DISTINCT cl.ProduitID) AS NombreProduits
FROM LignesCommande cl
INNER JOIN Commandes c ON cl.CommandeID = c.CommandeID
INNER JOIN Produits p ON cl.ProduitID = p.ProduitID
WHERE CAST(c.DateCommande AS DATE) = CAST(@DateRapport AS DATE)
GROUP BY p.Categorie;

-- Enregistrement du rapport cohérent
INSERT INTO RapportsJournaliers (
    DateRapport,
    NombreCommandes,
    ChiffreAffaires,
    PanierMoyen,
    DateGeneration
)
VALUES (
    @DateRapport,
    @NombreCommandes,
    @ChiffreAffaires,
    @PanierMoyen,
    GETDATE()
);

-- Enregistrement des détails (tous cohérents)
INSERT INTO RapportTopProduits SELECT * FROM @TopProduits;
INSERT INTO RapportCategories SELECT * FROM @VentesParCategorie;

COMMIT;

-- Grâce à SNAPSHOT :
-- ✅ Toutes les statistiques sont cohérentes (même version des données)
-- ✅ Le rapport n'a pas bloqué les commandes en cours
-- ✅ Les clients ont pu commander pendant la génération du rapport
-- ✅ Aucun conflit entre lectures (rapport) et écritures (commandes)
-- ✅ Performances excellentes (pas d'attente)

PRINT 'Rapport généré avec SNAPSHOT ISOLATION';
PRINT 'Vue cohérente garantie au timestamp : ' + CAST(@DateRapport AS VARCHAR);
```

**Pourquoi SNAPSHOT est parfait ici :**
1. ✅ **Cohérence** : Tous les chiffres correspondent (même snapshot)
2. ✅ **Pas de blocage** : Les commandes continuent pendant le rapport
3. ✅ **Performance** : Rapport rapide sans attente
4. ✅ **Fréquence** : Rapport toutes les 5 minutes (acceptable)
5. ✅ **Fiabilité** : Aucune anomalie de concurrence

## Comparaison récapitulative de tous les niveaux

### Tableau complet

| Niveau | Dirty | Non-Rep. | Phantom | Mécanisme | Blocage | Perf. | Usage |
|--------|-------|----------|---------|-----------|---------|-------|-------|
| **READ UNCOMMITTED** | ✅ | ✅ | ✅ | Aucun verrou | ❌ | ⭐⭐⭐⭐⭐ | Rapports approx. |
| **READ COMMITTED** | ❌ | ✅ | ✅ | Verrous temp. | Modéré | ⭐⭐⭐⭐ | Usage général |
| **RCSI** | ❌ | ✅ | ✅ | Versioning | ❌ | ⭐⭐⭐⭐⭐ | Apps web |
| **REPEATABLE READ** | ❌ | ❌ | ✅ | Verrous maintenus | Élevé | ⭐⭐⭐ | Rapports critiques |
| **SERIALIZABLE** | ❌ | ❌ | ❌ | Verrous + range | Très élevé | ⭐⭐ | Très rare |
| **SNAPSHOT** | ❌ | ❌ | ❌ | Versioning | ❌ | ⭐⭐⭐⭐ | Alternative moderne |

### Arbre de décision

```
Besoin d'empêcher toutes les anomalies ?
│
├─ NON → Quelle anomalie est acceptable ?
│   ├─ Dirty Reads OK → READ UNCOMMITTED
│   └─ Non-Rep/Phantom OK → READ COMMITTED ou RCSI
│
└─ OUI → Pouvez-vous utiliser tempdb ?
    ├─ OUI → SNAPSHOT (recommandé)
    └─ NON → SERIALIZABLE (dernier recours)
```

## Bonnes pratiques

### 1. Privilégier SNAPSHOT sur SERIALIZABLE

```sql
-- ❌ Éviter (performances médiocres)
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- ✅ Préférer (mêmes garanties, meilleures performances)
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
```

### 2. Dimensionner tempdb correctement

```sql
-- tempdb doit avoir :
-- - Taille initiale généreuse (20-30% de la base principale)
-- - Plusieurs fichiers (1 par cœur, max 8)
-- - Croissance automatique raisonnable

ALTER DATABASE tempdb
MODIFY FILE (NAME = tempdev, SIZE = 15360MB, FILEGROWTH = 1024MB);
```

### 3. Gérer les conflits d'écriture

```sql
-- Toujours implémenter une logique de retry pour l'erreur 3960
BEGIN TRY
    SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
    BEGIN TRANSACTION;
    -- Opérations...
    COMMIT;
END TRY
BEGIN CATCH
    IF ERROR_NUMBER() = 3960
    BEGIN
        -- Réessayer la transaction
        ROLLBACK;
        WAITFOR DELAY '00:00:00.100';
        -- Retry logic...
    END
    ELSE
        THROW;
END CATCH
```

### 4. Éviter les transactions longues

```sql
-- ❌ MAUVAIS
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
SELECT * FROM GrosseTable;  -- 2 heures
COMMIT;

-- ✅ BON
-- Limiter la durée de la transaction
-- Ou décomposer en plusieurs transactions courtes
```

### 5. Surveiller tempdb

```sql
-- Créer des alertes pour surveiller tempdb
SELECT
    SUM(version_store_reserved_page_count) * 8 / 1024 AS VersionStoreMB,
    SUM(unallocated_extent_page_count) * 8 / 1024 AS FreeSpaceMB
FROM sys.dm_db_file_space_usage;

-- Alerte si version store > seuil
IF (SELECT SUM(version_store_reserved_page_count) * 8 / 1024
    FROM sys.dm_db_file_space_usage) > 10240  -- 10 GB
BEGIN
    RAISERROR('tempdb version store trop grand !', 16, 1);
END
```

### 6. Combiner avec RCSI pour une architecture complète

```sql
-- Configuration recommandée pour applications modernes :

-- 1. Activer RCSI pour l'usage général (READ COMMITTED automatique)
ALTER DATABASE MaBase SET READ_COMMITTED_SNAPSHOT ON;

-- 2. Activer SNAPSHOT pour les rapports et analyses
ALTER DATABASE MaBase SET ALLOW_SNAPSHOT_ISOLATION ON;

-- 3. Utilisation :
-- - READ COMMITTED (via RCSI) : Opérations transactionnelles courantes
-- - SNAPSHOT : Rapports nécessitant une vue cohérente
```

## Résumé

### Points clés

| Aspect | Description |
|--------|-------------|
| **Niveau d'isolation** | Moderne, basé sur le versioning |
| **Principe** | Vue cohérente figée pour toute la transaction |
| **Dirty Reads** | ❌ Bloquées |
| **Non-Repeatable Reads** | ❌ Bloquées |
| **Phantom Reads** | ❌ Bloquées |
| **Mécanisme** | Versioning dans tempdb |
| **Blocage en lecture** | ❌ Jamais |
| **Conflits d'écriture** | ⚠️ Possibles (erreur 3960) |
| **Performance** | ⭐⭐⭐⭐ Excellente |
| **Cohérence** | ⭐⭐⭐⭐⭐ Maximale |

### Quand l'utiliser

✅ **OUI** pour :
- Rapports et analyses complexes nécessitant cohérence
- Applications avec forte concurrence lecture/écriture
- Alternative moderne à SERIALIZABLE
- Opérations de lecture longues
- Dashboards et reporting en temps réel

❌ **NON** si :
- Opérations d'écriture très intensives
- tempdb déjà saturé
- Espace disque limité
- Transactions très courtes (overkill)

### L'essentiel à retenir

1. SNAPSHOT offre **l'isolation maximale sans blocage**
2. Utilise le **versioning** (tempdb) au lieu des verrous
3. **Meilleure alternative** à SERIALIZABLE dans la plupart des cas
4. Vue **cohérente pour toute la transaction** (vs RCSI par requête)
5. Nécessite **gestion des conflits d'écriture** (erreur 3960)
6. Requiert **activation au niveau base de données**
7. **tempdb doit être dimensionné** correctement
8. Idéal pour **rapports et analyses** avec forte concurrence

### Configuration et utilisation

```sql
-- 1. Activer SNAPSHOT (une fois)
ALTER DATABASE MaBase SET ALLOW_SNAPSHOT_ISOLATION ON;

-- 2. Utiliser dans vos transactions
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;

-- Vos opérations avec isolation maximale sans blocage
SELECT * FROM Produits;

COMMIT;
```

### Recommandation

```
SNAPSHOT = Alternative moderne et performante à SERIALIZABLE

Pour l'isolation maximale :
✅ SNAPSHOT (premier choix)
❌ SERIALIZABLE (seulement si SNAPSHOT impossible)

Pour l'usage général :
✅ READ COMMITTED (défaut) ou RCSI
```

---

**Conclusion du chapitre 6.4 :** Nous avons maintenant exploré tous les niveaux d'isolation de SQL Server, de READ UNCOMMITTED (le moins restrictif) à SERIALIZABLE (le plus strict par verrous) et SNAPSHOT (le plus strict par versioning). Le choix du niveau d'isolation approprié dépend des besoins spécifiques de votre application en termes de cohérence, de performance et de concurrence. Pour la plupart des applications modernes, **READ COMMITTED** (avec ou sans RCSI) suffit pour l'usage général, tandis que **SNAPSHOT** est excellent pour les rapports et analyses nécessitant une cohérence stricte sans blocage.
