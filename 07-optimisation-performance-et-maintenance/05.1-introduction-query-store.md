# 7.5.1 Introduction au Query Store

## Qu'est-ce que le Query Store ?

Le **Query Store** (Magasin de requêtes) est une fonctionnalité de SQL Server introduite à partir de SQL Server 2016. On peut le considérer comme une "boîte noire" ou un "enregistreur de vol" pour votre base de données : il capture automatiquement l'historique des requêtes exécutées, leurs plans d'exécution et leurs statistiques de performance.

### Analogie simple

Imaginez que vous gérez un restaurant. Le Query Store serait comme un système de surveillance qui enregistre :
- Quels plats ont été commandés (les requêtes)
- Comment les plats ont été préparés (les plans d'exécution)
- Combien de temps a pris chaque préparation (les performances)
- Combien de ressources (ingrédients) ont été utilisées

Avec ces informations, vous pourriez facilement identifier quel plat prend trop de temps à préparer ou quelle recette pourrait être améliorée.

## Pourquoi le Query Store est-il important ?

### Le problème sans Query Store

Avant le Query Store, les administrateurs de bases de données et les développeurs rencontraient des difficultés majeures :

1. **Perte d'informations au redémarrage** : Lorsque SQL Server redémarrait, toutes les informations sur les performances des requêtes étaient perdues.

2. **Difficultés à identifier les régressions** : Si une requête devenait soudainement lente, il était difficile de savoir :
   - Quand le problème a commencé
   - Quel plan d'exécution était utilisé auparavant
   - Ce qui a causé le changement

3. **Diagnostic réactif uniquement** : On ne pouvait analyser que ce qui se passait "maintenant", sans vision historique.

### Les avantages du Query Store

Le Query Store résout ces problèmes en offrant :

#### 1. **Persistance des données**
Les informations de performance sont stockées dans la base de données elle-même et survivent aux redémarrages.

#### 2. **Vision historique**
Vous pouvez voir comment les performances d'une requête ont évolué dans le temps (heures, jours, semaines).

#### 3. **Identification facile des régressions**
Si une requête ralentit soudainement, vous pouvez :
- Voir exactement quand cela s'est produit
- Comparer l'ancien et le nouveau plan d'exécution
- Forcer le retour à l'ancien plan si nécessaire

#### 4. **Analyse proactive**
Vous pouvez identifier les requêtes problématiques avant qu'elles ne deviennent critiques.

## Comment fonctionne le Query Store ?

### Les trois composants principaux

Le Query Store collecte et organise les informations en trois catégories :

#### 1. **Le texte des requêtes**
Le Query Store enregistre le texte SQL de chaque requête exécutée. Il regroupe intelligemment les requêtes similaires (paramétrisées) ensemble.

**Exemple :**
```sql
SELECT * FROM Clients WHERE ClientID = 1
SELECT * FROM Clients WHERE ClientID = 2
```
Ces deux requêtes seront regroupées comme une seule "requête paramétrisée".

#### 2. **Les plans d'exécution**
Pour chaque requête, SQL Server peut utiliser différents plans d'exécution au fil du temps. Le Query Store enregistre tous ces plans avec :
- La date de première utilisation
- La date de dernière utilisation
- Le nombre d'exécutions

#### 3. **Les statistiques de runtime**
Pour chaque plan d'exécution, le Query Store collecte des métriques de performance :
- Temps d'exécution (durée)
- Utilisation CPU
- Lectures logiques (accès mémoire)
- Lectures physiques (accès disque)
- Nombre d'exécutions

### Le cycle de collecte

```
Requête exécutée → Texte capturé → Plan d'exécution enregistré →
Statistiques collectées → Agrégation périodique → Stockage dans la DB
```

## Activation du Query Store

Par défaut, le Query Store est **désactivé** sur les nouvelles bases de données. Voici comment l'activer :

### Méthode 1 : Via SQL Server Management Studio (SSMS)

1. Dans l'Explorateur d'objets, faites un clic droit sur votre base de données
2. Sélectionnez **Propriétés**
3. Allez dans la section **Query Store**
4. Changez **Mode d'opération (demandé)** de `Off` à `Read Write`
5. Cliquez sur **OK**

### Méthode 2 : Via T-SQL

```sql
-- Activer le Query Store sur une base de données
ALTER DATABASE VotreBaseDeDonnees
SET QUERY_STORE = ON;
```

### Configuration recommandée pour débuter

```sql
ALTER DATABASE VotreBaseDeDonnees
SET QUERY_STORE = ON
(
    OPERATION_MODE = READ_WRITE,              -- Mode lecture-écriture
    DATA_FLUSH_INTERVAL_SECONDS = 900,        -- Écriture sur disque toutes les 15 min
    INTERVAL_LENGTH_MINUTES = 60,             -- Intervalle d'agrégation de 1 heure
    MAX_STORAGE_SIZE_MB = 100,                -- Espace maximum : 100 MB
    QUERY_CAPTURE_MODE = AUTO,                -- Capture automatique des requêtes importantes
    SIZE_BASED_CLEANUP_MODE = AUTO            -- Nettoyage automatique si l'espace est plein
);
```

## Consulter les informations du Query Store

### Accès via SSMS

Dans l'Explorateur d'objets :
1. Développez votre base de données
2. Développez le dossier **Query Store**
3. Vous verrez plusieurs rapports prédéfinis :
   - **Regressed Queries** : Requêtes qui sont devenues plus lentes
   - **Overall Resource Consumption** : Consommation globale des ressources
   - **Top Resource Consuming Queries** : Requêtes les plus gourmandes
   - **Queries With Forced Plans** : Requêtes avec plans forcés
   - **Tracked Queries** : Suivi de requêtes spécifiques

### Exemple de requête simple pour explorer le Query Store

```sql
-- Voir les 10 requêtes les plus lentes (par durée moyenne)
SELECT TOP 10
    q.query_id,
    qt.query_sql_text,
    rs.avg_duration / 1000.0 AS avg_duration_ms,
    rs.count_executions,
    rs.last_execution_time
FROM sys.query_store_query AS q
INNER JOIN sys.query_store_query_text AS qt
    ON q.query_text_id = qt.query_text_id
INNER JOIN sys.query_store_plan AS p
    ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats AS rs
    ON p.plan_id = rs.plan_id
ORDER BY rs.avg_duration DESC;
```

**Explication de la requête :**
- `sys.query_store_query` : Contient les métadonnées des requêtes
- `sys.query_store_query_text` : Contient le texte SQL des requêtes
- `sys.query_store_plan` : Contient les plans d'exécution
- `sys.query_store_runtime_stats` : Contient les statistiques de performance

## Cas d'utilisation typiques

### 1. Identifier une régression de performance

**Scénario :** Depuis ce matin, les utilisateurs se plaignent que l'application est lente.

**Solution avec Query Store :**
1. Ouvrez le rapport **Regressed Queries**
2. Identifiez les requêtes dont les performances ont chuté récemment
3. Comparez l'ancien et le nouveau plan d'exécution
4. Si l'ancien plan était meilleur, forcez son utilisation

### 2. Analyser l'impact d'un changement

**Scénario :** Vous venez de créer un nouvel index.

**Solution avec Query Store :**
1. Comparez les performances avant/après la création de l'index
2. Vérifiez que les requêtes utilisent bien le nouvel index
3. Mesurez l'amélioration (ou la dégradation) des performances

### 3. Optimisation proactive

**Scénario :** Vous voulez améliorer les performances globales.

**Solution avec Query Store :**
1. Consultez le rapport **Top Resource Consuming Queries**
2. Identifiez les requêtes les plus gourmandes en CPU ou en I/O
3. Optimisez ces requêtes en priorité (elles auront le plus d'impact)

## Bonnes pratiques

### 1. Activer le Query Store dès le début
N'attendez pas d'avoir un problème de performance pour activer le Query Store. Il a besoin de temps pour collecter des données historiques.

### 2. Surveiller l'espace disque
Le Query Store consomme de l'espace dans votre base de données. Configurez une taille maximale appropriée et activez le nettoyage automatique.

### 3. Utiliser le mode de capture AUTO
Le mode `AUTO` capture les requêtes importantes et ignore les requêtes triviales (très rapides ou peu fréquentes), ce qui évite de saturer le Query Store.

### 4. Consulter régulièrement les rapports
Prenez l'habitude de consulter les rapports du Query Store, même quand tout va bien. Cela vous permet de :
- Connaître votre baseline (performances normales)
- Détecter les problèmes tôt
- Comprendre l'évolution de votre application

## Limitations à connaître

### 1. Overhead minimal mais existant
Le Query Store consomme des ressources (CPU, mémoire, disque). Cet impact est généralement négligeable (< 5%), mais il existe.

### 2. Pas de capture en temps réel absolu
Les statistiques sont agrégées par intervalles (par défaut 60 minutes). Vous ne verrez pas des changements seconde par seconde.

### 3. Espace de stockage limité
Si l'espace maximal est atteint et que le nettoyage automatique est désactivé, le Query Store passera en mode lecture seule.

### 4. Requêtes système non capturées
Le Query Store se concentre sur les requêtes utilisateur, pas sur les opérations système internes de SQL Server.

## Résumé

Le Query Store est un outil puissant et essentiel pour :
- **Comprendre** comment votre base de données est utilisée
- **Identifier** les requêtes problématiques
- **Diagnostiquer** les régressions de performance
- **Optimiser** proactivement votre application

En tant que développeur ou DBA débutant, pensez au Query Store comme à votre meilleur allié pour la résolution de problèmes de performance. Il transforme le diagnostic de performance d'un art obscur en une science basée sur des données concrètes et historiques.

---

**Points clés à retenir :**
- Le Query Store enregistre l'historique des requêtes et leurs performances
- Il est persistant (survit aux redémarrages)
- Il permet d'identifier et de corriger rapidement les régressions
- Il doit être activé explicitement sur chaque base de données
- Les rapports intégrés dans SSMS facilitent l'analyse
- C'est un outil de diagnostic proactif, pas seulement réactif
