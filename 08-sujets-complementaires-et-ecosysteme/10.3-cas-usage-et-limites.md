# 8.10.3 Cas d'usage et limites

## Introduction

Nous avons vu les deux piliers d'In-Memory OLTP : les tables à mémoire optimisée (§8.10.1) et les procédures natives (§8.10.2). Cette dernière sous-section répond aux questions décisives : **dans quels cas concrets cette technologie apporte-t-elle vraiment quelque chose**, et **quelles limites** connaître avant de se lancer ?

---

## Les cas d'usage où In-Memory OLTP brille

### 1. Ingestion de données à haute fréquence

Des milliers d'événements par seconde (IoT, télémétrie, clics, capteurs). Les écritures concurrentes saturent une table classique par contention. Une table à mémoire optimisée encaisse le débit sans file d'attente.

### 2. Tables de sessions / état applicatif

Les sessions web (panier, état de connexion) sont lues et écrites en permanence. Avec `DURABILITY = SCHEMA_ONLY`, on obtient un stockage **ultra-rapide** et **jetable** — parfait, car perdre les sessions à un redémarrage est acceptable.

### 3. Files d'attente et tables de travail

Les patterns « file d'attente » (insertion d'un côté, consommation de l'autre) souffrent particulièrement de la contention sur les tables classiques. In-Memory OLTP supprime ce point chaud.

### 4. Zone de transit (staging) pour l'ETL

Charger des données dans une table `SCHEMA_ONLY` à mémoire optimisée, les transformer, puis les écrire en base : très rapide, sans surcoût de journalisation pour le transit.

### 5. Le « caching » applicatif dans la base

Remplacer un cache externe par des tables à mémoire optimisée, pour garder la logique dans SQL Server tout en obtenant des temps d'accès proches de la mémoire.

## Les limites à connaître absolument

| Limite | Détail |
|--------|--------|
| 💾 **Tout en mémoire** | Les données résident en RAM : la taille est bornée par la mémoire disponible. À surveiller de près. |
| 🧩 **Sous-ensemble T-SQL en natif** | Les procédures natives n'autorisent pas tout le T-SQL (selon la version). |
| 🔗 **Clés étrangères** | Une FK ne peut pas relier une table mémoire et une table sur disque ; les relations doivent rester dans le même « monde ». |
| 🔁 **Conflits optimistes** | Pas de blocage, mais des transactions peuvent **échouer** au commit → logique de **retry** obligatoire (§8.10.1). |
| 🧱 **Modifications de schéma** | `SCHEMABINDING` fige les procédures natives ; modifier une table liée impose de les recréer. |
| ⚙️ **Complexité** | Conception, dimensionnement (bucket count, mémoire) et exploitation plus exigeants. |

---

## Évolution selon les versions

In-Memory OLTP s'est beaucoup assoupli depuis ses débuts :

- **SQL Server 2014** : première version, très restreinte (beaucoup de limites sur les types, contraintes, T-SQL natif).
- **SQL Server 2016** : levée de nombreuses limites (taille, ALTER de tables/procédures, plus de constructions T-SQL, FK entre tables mémoire, etc.).
- **SQL Server 2016 SP1 et au-delà** : la fonctionnalité devient disponible dans **toutes les éditions** (y compris Standard et Express), avec une **limite de mémoire par base** selon l'édition (l'édition Enterprise/Developer n'a pas cette limite).
- **Versions récentes (2017 → 2022)** : maturité, meilleure intégration et diagnostics.

> 💡 Utilisez une **version récente** (2019/2022) si vous visez In-Memory OLTP : l'expérience y est bien plus complète et fiable qu'en 2014.

---

## Quand NE PAS utiliser In-Memory OLTP

- ❌ **Les performances sont déjà suffisantes** : n'ajoutez pas de complexité sans gain mesuré.
- ❌ **Charges analytiques** (agrégations massives) : c'est le **columnstore** (§8.7) qu'il vous faut, pas l'In-Memory OLTP.
- ❌ **Très grandes tables** qui ne tiendraient pas en mémoire.
- ❌ **Sans avoir mesuré** : si le goulot n'est pas la contention de verrous/latches, le gain sera faible.

> 🧠 **Règle d'or** : In-Memory OLTP est un **scalpel**, pas un marteau. On l'applique sur un **point chaud précis**, identifié et mesuré (voir §7.3 sur les plans d'exécution et les goulots d'étranglement).

---

## La méthode : mesurer avant d'agir

1. **Identifier** le goulot avec les outils de diagnostic (attentes sur verrous/latches, statistiques d'attente, plans d'exécution — §7.3).
2. **Évaluer** le gain potentiel : SSMS propose historiquement des rapports d'aide à la migration (*Transaction Performance Analysis*, *Memory Optimization Advisor*).
3. **Migrer** la table/procédure ciblée et **comparer** avant/après sur une charge réaliste.
4. **Surveiller** la consommation mémoire dans la durée.

---

## In-Memory OLTP face aux autres optimisations

| Besoin | Bonne réponse |
|--------|---------------|
| Accélérer des **recherches** ponctuelles | Index B-tree adaptés (§7.1, §7.2) |
| Accélérer l'**analytique** sur gros volumes | Index **columnstore** (§8.7) |
| Supprimer la **contention** de verrous sur un point chaud OLTP | **In-Memory OLTP** |
| Réduire la **perte de données** | Sauvegarde/restauration (§7.8) |

Ces techniques ne s'opposent pas : une même base peut combiner index classiques, columnstore et tables à mémoire optimisée selon les besoins de chaque partie.

## Questions fréquentes

**Q : Par où commencer pour adopter In-Memory OLTP ?**
R : Par la **mesure** : identifiez un point chaud de contention (attentes sur verrous/latches, §7.3) avant de migrer quoi que ce soit.

**Q : Faut-il migrer toute la base ?**
R : Surtout pas. On cible la **ou les quelques** tables/procédures réellement en cause, pas l'ensemble.

**Q : Avec `SCHEMA_ONLY`, je perds vraiment les données au redémarrage ?**
R : Oui — seule la **structure** survit. C'est voulu : réservé aux données **jetables** (sessions, staging), pour une vitesse maximale.

---

## Résumé

- In-Memory OLTP excelle sur l'**ingestion haute fréquence**, les **sessions**, les **files d'attente**, le **staging ETL** et le caching dans la base.
- Limites majeures : **tout en mémoire**, sous-ensemble T-SQL en natif, FK restreintes, **conflits optimistes** (retry), schéma figé.
- La technologie s'est **beaucoup assouplie** depuis 2014 ; disponible dans toutes les éditions depuis 2016 SP1 (avec limite mémoire hors Enterprise).
- C'est un **outil de niche** : à appliquer sur un point chaud **mesuré**, pas partout.
- Il **complète** (sans remplacer) les index classiques, le columnstore et les sauvegardes.
