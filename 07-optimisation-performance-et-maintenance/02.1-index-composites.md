# 7.2.1 Index composites (Multi-colonnes) et importance de l'ordre

## Introduction

Dans les sections précédentes (7.1), nous avons vu les index sur **une seule colonne** :
- Index sur Email
- Index sur Ville
- Index sur DateInscription

Mais que se passe-t-il quand vous recherchez fréquemment sur **plusieurs colonnes en même temps** ?

```sql
-- Recherche sur deux colonnes
SELECT * FROM Clients
WHERE Ville = 'Paris' AND Statut = 'Actif';

-- Recherche sur trois colonnes
SELECT * FROM Commandes
WHERE ClientID = 123 AND DateCommande >= '2024-01-01' AND Statut = 'En cours';
```

C'est là qu'interviennent les **index composites** (ou index multi-colonnes).

## Qu'est-ce qu'un Index Composite ?

### Définition

Un **index composite** est un index qui porte sur **plusieurs colonnes** en même temps, dans un **ordre spécifique**.

```sql
-- Index composite sur deux colonnes
CREATE INDEX IX_Clients_Ville_Statut
ON Clients (Ville, Statut);

-- Index composite sur trois colonnes
CREATE INDEX IX_Commandes_Client_Date_Statut
ON Commandes (ClientID, DateCommande, Statut);
```

**Caractéristiques** :
- ✅ Combine plusieurs colonnes dans un seul index
- ✅ L'**ordre des colonnes** est crucial
- ✅ Peut être clustered ou non-clustered
- ✅ Peut être unique ou non-unique

### L'analogie de l'annuaire téléphonique

Pour comprendre les index composites, pensez à un **annuaire téléphonique** classique :

**Annuaire trié par (Nom, Prénom)** :

```
BERNARD, Alice
BERNARD, Jacques
BERNARD, Marie
DUPONT, André
DUPONT, Sophie
MARTIN, Jean
MARTIN, Paul
```

**Observations importantes** :
1. **Premier tri** : Les noms sont triés alphabétiquement (BERNARD, DUPONT, MARTIN)
2. **Second tri** : Pour chaque nom, les prénoms sont triés (Alice, Jacques, Marie)
3. **L'ordre compte** : Trié par (Nom, Prénom), PAS par (Prénom, Nom)

**Utilisation efficace** :
- ✅ Chercher "DUPONT" → Très rapide (premier niveau de tri)
- ✅ Chercher "DUPONT, Sophie" → Très rapide (les deux niveaux)
- ❌ Chercher "Sophie" (sans nom) → Impossible d'utiliser l'annuaire efficacement

**C'est exactement comme un index composite !**

## Création d'Index Composites

### Syntaxe de base

```sql
-- Index composite non-clustered (le plus courant)
CREATE INDEX nom_index
ON nom_table (colonne1, colonne2, colonne3, ...);

-- Index composite clustered
CREATE CLUSTERED INDEX nom_index
ON nom_table (colonne1, colonne2, ...);

-- Index composite unique
CREATE UNIQUE INDEX nom_index
ON nom_table (colonne1, colonne2, ...);
```

### Exemple 1 : Index sur Ville et Statut

```sql
-- Table Clients
CREATE TABLE Clients (
    ClientID INT IDENTITY(1,1) PRIMARY KEY,
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    Ville NVARCHAR(100),
    Statut NVARCHAR(20)  -- 'Actif', 'Inactif', 'Suspendu'
);

-- Index composite sur (Ville, Statut)
CREATE INDEX IX_Clients_Ville_Statut
ON Clients (Ville, Statut);
```

**Structure de l'index** :

```
Index IX_Clients_Ville_Statut (trié par Ville puis Statut)
┌────────┬──────────┬──────────┐
│ Ville  │ Statut   │ ClientID │
├────────┼──────────┼──────────┤
│ Lille  │ Actif    │ 5        │ ← Trié d'abord par Ville
│ Lille  │ Inactif  │ 12       │
│ Lyon   │ Actif    │ 1        │
│ Lyon   │ Actif    │ 3        │
│ Lyon   │ Inactif  │ 9        │ ← Puis par Statut pour chaque Ville
│ Paris  │ Actif    │ 2        │
│ Paris  │ Actif    │ 4        │
│ Paris  │ Inactif  │ 7        │
│ Paris  │ Suspendu │ 11       │
└────────┴──────────┴──────────┘
```

### Exemple 2 : Index sur ClientID, DateCommande et Statut

```sql
-- Table Commandes
CREATE TABLE Commandes (
    CommandeID INT IDENTITY(1,1) PRIMARY KEY,
    ClientID INT,
    DateCommande DATE,
    Statut NVARCHAR(20),
    MontantTotal DECIMAL(10,2)
);

-- Index composite sur (ClientID, DateCommande, Statut)
CREATE INDEX IX_Commandes_Client_Date_Statut
ON Commandes (ClientID, DateCommande, Statut);
```

**Structure de l'index** :

```
Index IX_Commandes_Client_Date_Statut
┌──────────┬──────────────┬────────────┬───────────┐
│ ClientID │ DateCommande │ Statut     │CommandeID │
├──────────┼──────────────┼────────────┼───────────┤
│ 100      │ 2024-01-15   │ Livré      │ 1001      │ ← Trié par ClientID
│ 100      │ 2024-02-20   │ En cours   │ 1005      │ ← Puis par Date
│ 100      │ 2024-02-20   │ Livré      │ 1008      │ ← Puis par Statut
│ 101      │ 2024-01-10   │ Livré      │ 1002      │
│ 101      │ 2024-03-05   │ En cours   │ 1009      │
│ 102      │ 2024-02-01   │ Annulé     │ 1006      │
│ 102      │ 2024-02-15   │ Livré      │ 1007      │
└──────────┴──────────────┴────────────┴───────────┘
```

## L'Importance Cruciale de l'Ordre des Colonnes

C'est **LE** concept le plus important pour les index composites : **l'ordre des colonnes détermine l'efficacité de l'index**.

### Règle fondamentale : L'index est trié de gauche à droite

Un index composite `(A, B, C)` est trié dans cet ordre :
1. **D'abord** par la colonne A
2. **Ensuite** par la colonne B (pour chaque valeur de A)
3. **Enfin** par la colonne C (pour chaque combinaison de A et B)

**Conséquence** : L'index peut être utilisé efficacement si votre requête filtre sur :
- ✅ A seul
- ✅ A et B
- ✅ A, B et C
- ❌ B seul (pas efficace)
- ❌ C seul (pas efficace)
- ⚠️ B et C (pas efficace sans A)

### Visualisation : Index (Ville, Statut)

```sql
CREATE INDEX IX_Clients_Ville_Statut
ON Clients (Ville, Statut);
```

**Requêtes efficaces** :

```sql
-- ✅ EFFICACE : Filtre sur Ville (première colonne)
SELECT * FROM Clients WHERE Ville = 'Paris';
-- Index Seek : Très rapide

-- ✅ EFFICACE : Filtre sur Ville ET Statut
SELECT * FROM Clients WHERE Ville = 'Paris' AND Statut = 'Actif';
-- Index Seek : Très rapide (utilise les deux colonnes)
```

**Requête inefficace** :

```sql
-- ❌ INEFFICACE : Filtre uniquement sur Statut (deuxième colonne)
SELECT * FROM Clients WHERE Statut = 'Actif';
-- Index Scan ou Table Scan : Lent
-- L'index ne peut pas être utilisé efficacement !
```

**Pourquoi ?** Repensez à l'annuaire téléphonique :
- Chercher "DUPONT" → Facile (trié par nom)
- Chercher "Sophie" (sans nom) → Vous devez parcourir TOUT l'annuaire !

### Exemple détaillé avec (Ville, Statut)

**L'index physique** :

```
Index IX_Clients_Ville_Statut
┌────────┬──────────┬──────────┐
│ Ville  │ Statut   │ ClientID │
├────────┼──────────┼──────────┤
│ Lille  │ Actif    │ 5        │
│ Lille  │ Inactif  │ 12       │
│ Lyon   │ Actif    │ 1        │
│ Lyon   │ Actif    │ 3        │
│ Lyon   │ Inactif  │ 9        │
│ Paris  │ Actif    │ 2        │
│ Paris  │ Actif    │ 4        │
│ Paris  │ Inactif  │ 7        │
│ Paris  │ Suspendu │ 11       │
└────────┴──────────┴──────────┘
```

**Requête 1** : `WHERE Ville = 'Paris'`
```
SQL Server cherche "Paris" (première colonne) :
┌────────┬──────────┬──────────┐
│ Ville  │ Statut   │ ClientID │
├────────┼──────────┼──────────┤
│ Paris  │ Actif    │ 2        │ ← Début de "Paris"
│ Paris  │ Actif    │ 4        │ ←
│ Paris  │ Inactif  │ 7        │ ←
│ Paris  │ Suspendu │ 11       │ ← Fin de "Paris"
└────────┴──────────┴──────────┘

Index Seek : Trouve directement toutes les lignes de Paris
Lectures : ~3-5 pages
```

**Requête 2** : `WHERE Ville = 'Paris' AND Statut = 'Actif'`
```
SQL Server cherche "Paris" puis "Actif" :
┌────────┬──────────┬──────────┐
│ Ville  │ Statut   │ ClientID │
├────────┼──────────┼──────────┤
│ Paris  │ Actif    │ 2        │ ← Début de "Paris, Actif"
│ Paris  │ Actif    │ 4        │ ← Fin de "Paris, Actif"
└────────┴──────────┴──────────┘

Index Seek : Utilise les deux colonnes efficacement
Lectures : ~2-3 pages
```

**Requête 3** : `WHERE Statut = 'Actif'` (INEFFICACE)
```
SQL Server doit parcourir TOUT l'index pour trouver "Actif" :
┌────────┬──────────┬──────────┐
│ Ville  │ Statut   │ ClientID │
├────────┼──────────┼──────────┤
│ Lille  │ Actif    │ 5        │ ← Trouvé (mais loin)
│ Lille  │ Inactif  │ 12       │
│ Lyon   │ Actif    │ 1        │ ← Trouvé
│ Lyon   │ Actif    │ 3        │ ← Trouvé
│ Lyon   │ Inactif  │ 9        │
│ Paris  │ Actif    │ 2        │ ← Trouvé
│ Paris  │ Actif    │ 4        │ ← Trouvé
│ Paris  │ Inactif  │ 7        │
│ Paris  │ Suspendu │ 11       │
└────────┴──────────┴──────────┘

Index Scan : Parcourt tout l'index
Lectures : Toutes les pages de l'index
```

## La Règle du "Préfixe de gauche"

### Principe

Un index composite `(A, B, C)` peut être utilisé efficacement pour :

| Prédicat WHERE | Utilisation de l'index | Efficacité |
|----------------|------------------------|------------|
| `WHERE A = ...` | ✅ Utilise A | Très efficace |
| `WHERE A = ... AND B = ...` | ✅ Utilise A, B | Très efficace |
| `WHERE A = ... AND B = ... AND C = ...` | ✅ Utilise A, B, C | Très efficace |
| `WHERE A = ... AND C = ...` | ⚠️ Utilise A seulement | Moyennement efficace |
| `WHERE B = ...` | ❌ N'utilise pas l'index | Inefficace |
| `WHERE C = ...` | ❌ N'utilise pas l'index | Inefficace |
| `WHERE B = ... AND C = ...` | ❌ N'utilise pas l'index | Inefficace |

**Règle** : L'index peut être utilisé si vous filtrez sur un **préfixe continu** à partir de la **première colonne**.

### Exemple avec Index (ClientID, DateCommande, Statut)

```sql
CREATE INDEX IX_Commandes_Client_Date_Statut
ON Commandes (ClientID, DateCommande, Statut);
```

**Scénarios** :

```sql
-- ✅ EFFICACE : Utilise ClientID
SELECT * FROM Commandes WHERE ClientID = 100;

-- ✅ EFFICACE : Utilise ClientID, DateCommande
SELECT * FROM Commandes
WHERE ClientID = 100 AND DateCommande >= '2024-01-01';

-- ✅ EFFICACE : Utilise ClientID, DateCommande, Statut
SELECT * FROM Commandes
WHERE ClientID = 100
  AND DateCommande >= '2024-01-01'
  AND Statut = 'Livré';

-- ⚠️ MOYENNEMENT EFFICACE : Utilise ClientID seulement (saute DateCommande)
SELECT * FROM Commandes
WHERE ClientID = 100 AND Statut = 'Livré';
-- SQL Server ne peut pas utiliser Statut efficacement

-- ❌ INEFFICACE : Ne commence pas par ClientID
SELECT * FROM Commandes
WHERE DateCommande >= '2024-01-01' AND Statut = 'Livré';
-- Index Scan ou Table Scan

-- ❌ INEFFICACE : Ne commence pas par ClientID
SELECT * FROM Commandes WHERE Statut = 'Livré';
-- Index Scan ou Table Scan
```

### Pourquoi SQL Server ne peut-il pas "sauter" une colonne ?

Imaginez l'index comme un **annuaire téléphonique (Nom, Prénom, Ville)** :

```
BERNARD, Alice, Paris
BERNARD, Jacques, Lyon
BERNARD, Marie, Paris
DUPONT, André, Lyon
DUPONT, Sophie, Paris
MARTIN, Jean, Lille
MARTIN, Paul, Paris
```

**Question** : Trouvez toutes les personnes de Paris, sans connaître leur nom.

**Réponse** : Vous devez parcourir **tout** l'annuaire ! L'annuaire n'est pas trié par Ville directement, il est trié par Nom d'abord.

**C'est la même chose dans SQL Server** : Un index `(A, B, C)` ne peut pas être utilisé efficacement pour chercher sur B ou C sans A.

## Comment Choisir l'Ordre des Colonnes ?

C'est **LA** question la plus importante pour les index composites. Voici les règles à suivre :

### Règle 1 : Égalité avant Plage

**Principe** : Mettez les colonnes avec égalité (`=`) **avant** les colonnes avec plage (`>`, `<`, `BETWEEN`, `LIKE`).

**Exemple** :

```sql
-- Requête fréquente
SELECT * FROM Commandes
WHERE ClientID = 100
  AND DateCommande >= '2024-01-01';

-- ✅ BON ORDRE : Égalité (ClientID) avant Plage (DateCommande)
CREATE INDEX IX_Commandes_Client_Date
ON Commandes (ClientID, DateCommande);

-- ❌ MAUVAIS ORDRE : Plage avant Égalité
CREATE INDEX IX_Commandes_Date_Client
ON Commandes (DateCommande, ClientID);
-- Moins efficace pour cette requête
```

**Pourquoi ?**
- Avec `(ClientID, DateCommande)` : SQL Server trouve ClientID=100 puis scanne les dates
- Avec `(DateCommande, ClientID)` : SQL Server doit scanner une large plage de dates puis filtrer par ClientID

### Règle 2 : Sélectivité Élevée en Premier

**Principe** : Mettez les colonnes avec **haute sélectivité** (beaucoup de valeurs distinctes) **avant** les colonnes avec faible sélectivité.

**Sélectivité** :
- 📊 **Haute** : ClientID (unique), Email (unique), NumeroCommande (unique)
- 📊 **Moyenne** : Ville (10-100 valeurs), Catégorie (5-50 valeurs)
- 📊 **Faible** : Statut (2-5 valeurs), Sexe (2 valeurs), Boolean (2 valeurs)

**Exemple** :

```sql
-- Requête fréquente
SELECT * FROM Clients
WHERE Ville = 'Paris' AND Statut = 'Actif';

-- ✅ BON ORDRE : Ville (haute sélectivité) avant Statut (faible sélectivité)
CREATE INDEX IX_Clients_Ville_Statut
ON Clients (Ville, Statut);
-- Ville a ~100 valeurs, Statut a ~3 valeurs

-- ⚠️ MOINS BON : Statut avant Ville
CREATE INDEX IX_Clients_Statut_Ville
ON Clients (Statut, Ville);
-- Moins efficace : Statut a peu de valeurs
```

**Pourquoi ?**
- Avec `(Ville, Statut)` : SQL Server trouve d'abord Paris (~10 000 clients sur 1 million), puis filtre par Actif (~8 000)
- Avec `(Statut, Ville)` : SQL Server trouve d'abord Actif (~800 000 sur 1 million), puis filtre par Paris (~10 000)

Le premier ordre réduit plus rapidement le nombre de lignes.

### Règle 3 : Fréquence d'Utilisation

**Principe** : Mettez les colonnes **les plus fréquemment utilisées seules** en premier.

**Exemple** :

```sql
-- Requêtes fréquentes :
-- 1. SELECT * FROM Commandes WHERE ClientID = 100;  (80% des requêtes)
-- 2. SELECT * FROM Commandes WHERE ClientID = 100 AND DateCommande >= '2024-01-01';  (20%)

-- ✅ BON ORDRE : ClientID en premier (utilisé dans 100% des cas)
CREATE INDEX IX_Commandes_Client_Date
ON Commandes (ClientID, DateCommande);
-- Optimise les deux requêtes

-- ❌ MAUVAIS ORDRE : DateCommande en premier
CREATE INDEX IX_Commandes_Date_Client
ON Commandes (DateCommande, ClientID);
-- La première requête (80%) ne peut pas utiliser l'index efficacement
```

### Règle 4 : Cardinalité (Nombre de Valeurs Distinctes)

**Principe** : En général, mettez les colonnes avec **plus de valeurs distinctes** en premier.

**Exemple** :

```sql
-- Table Produits : 100 000 produits
-- CategorieID : 20 catégories différentes (~5 000 produits par catégorie)
-- FournisseurID : 500 fournisseurs différents (~200 produits par fournisseur)

-- Requête fréquente
SELECT * FROM Produits
WHERE CategorieID = 5 AND FournisseurID = 123;

-- ✅ BON ORDRE : FournisseurID (500 valeurs) avant CategorieID (20 valeurs)
CREATE INDEX IX_Produits_Fournisseur_Categorie
ON Produits (FournisseurID, CategorieID);
```

**Pourquoi ?**
- Avec `(FournisseurID, CategorieID)` : 200 produits → puis filtrer sur catégorie → ~10 produits
- Avec `(CategorieID, FournisseurID)` : 5 000 produits → puis filtrer sur fournisseur → ~10 produits

Le premier ordre est plus efficace car il réduit plus rapidement l'ensemble des lignes.

### Tableau Récapitulatif

| Critère | Ordre Recommandé |
|---------|------------------|
| **Type de prédicat** | Égalité (`=`) avant Plage (`>`, `<`, `BETWEEN`) |
| **Sélectivité** | Haute sélectivité avant Faible sélectivité |
| **Fréquence d'utilisation** | Colonnes utilisées seules en premier |
| **Cardinalité** | Plus de valeurs distinctes en premier |
| **Unicité** | Colonnes uniques en premier |

**Note** : Ces règles peuvent parfois se contredire. Dans ce cas, analysez vos requêtes réelles et testez !

## Exemples Pratiques Complets

### Exemple 1 : Recherche de Commandes

**Scénario** : Application e-commerce

**Requêtes fréquentes** :
```sql
-- Requête 1 (60%) : Commandes d'un client
SELECT * FROM Commandes WHERE ClientID = 100;

-- Requête 2 (30%) : Commandes d'un client sur une période
SELECT * FROM Commandes
WHERE ClientID = 100 AND DateCommande >= '2024-01-01';

-- Requête 3 (10%) : Commandes d'un client avec un statut
SELECT * FROM Commandes
WHERE ClientID = 100 AND Statut = 'En cours';
```

**Analyse** :
- ClientID : haute sélectivité (chaque client a ses propres commandes), égalité, utilisé dans 100% des requêtes → **En premier**
- DateCommande : plage, moyenne sélectivité, utilisé dans 30% → **En deuxième**
- Statut : faible sélectivité (3-5 valeurs), utilisé dans 10% → **En troisième**

**Index optimal** :
```sql
CREATE INDEX IX_Commandes_Client_Date_Statut
ON Commandes (ClientID, DateCommande, Statut);
```

**Résultat** :
- ✅ Requête 1 : Utilise ClientID → Très efficace
- ✅ Requête 2 : Utilise ClientID, DateCommande → Très efficace
- ✅ Requête 3 : Utilise ClientID (puis scanne pour Statut) → Efficace

### Exemple 2 : Recherche de Produits

**Scénario** : Site e-commerce avec catalogue de produits

**Requêtes fréquentes** :
```sql
-- Requête 1 (50%) : Produits d'une catégorie
SELECT * FROM Produits WHERE CategorieID = 10;

-- Requête 2 (40%) : Produits d'une catégorie et d'une marque
SELECT * FROM Produits
WHERE CategorieID = 10 AND MarqueID = 25;

-- Requête 3 (10%) : Produits d'une catégorie dans une fourchette de prix
SELECT * FROM Produits
WHERE CategorieID = 10 AND Prix BETWEEN 10 AND 50;
```

**Analyse** :
- CategorieID : moyenne sélectivité (20-50 catégories), égalité, utilisé dans 100% → **En premier**
- MarqueID : moyenne sélectivité (100-200 marques), égalité, utilisé dans 40% → **En deuxième**
- Prix : plage (BETWEEN), utilisé dans 10% → **En troisième**

**Index optimal** :
```sql
CREATE INDEX IX_Produits_Categorie_Marque_Prix
ON Produits (CategorieID, MarqueID, Prix);
```

### Exemple 3 : Logs d'Application

**Scénario** : Table de logs avec millions d'entrées

**Requêtes fréquentes** :
```sql
-- Requête 1 (70%) : Logs d'erreur des dernières 24h
SELECT * FROM Logs
WHERE TypeLog = 'ERROR' AND DateLog >= DATEADD(day, -1, GETDATE());

-- Requête 2 (20%) : Logs d'un utilisateur spécifique
SELECT * FROM Logs
WHERE UtilisateurID = 12345 AND DateLog >= '2024-01-01';

-- Requête 3 (10%) : Tous les logs récents
SELECT * FROM Logs WHERE DateLog >= '2024-11-01';
```

**Analyse** :
- TypeLog : faible sélectivité (5 valeurs : INFO, WARNING, ERROR, DEBUG, FATAL)
- DateLog : haute sélectivité (valeurs continues), plage
- UtilisateurID : haute sélectivité

**Stratégie** : Créer **deux index** différents

```sql
-- Index 1 : Pour les requêtes par type et date (70% des cas)
CREATE INDEX IX_Logs_Type_Date
ON Logs (TypeLog, DateLog);

-- Index 2 : Pour les requêtes par utilisateur (20% des cas)
CREATE INDEX IX_Logs_Utilisateur_Date
ON Logs (UtilisateurID, DateLog);
```

**Pourquoi deux index ?**
- Les patterns d'accès sont très différents
- Un seul index composite ne pourrait pas optimiser les deux types de requêtes
- Le coût de maintenance de deux index est acceptable vu l'importance des requêtes

## Index Composites vs Index Séparés

### La question

**Vaut-il mieux créer** :
- **Option A** : Un index composite `(A, B)`
- **Option B** : Deux index séparés, un sur `A` et un sur `B`

### Réponse générale : Index Composite

**Dans la plupart des cas, un index composite est meilleur**.

**Exemple** :

```sql
-- Requête fréquente
SELECT * FROM Clients WHERE Ville = 'Paris' AND Statut = 'Actif';

-- Option A : Index composite (RECOMMANDÉ)
CREATE INDEX IX_Clients_Ville_Statut ON Clients (Ville, Statut);

-- Option B : Deux index séparés (MOINS BON)
CREATE INDEX IX_Clients_Ville ON Clients (Ville);
CREATE INDEX IX_Clients_Statut ON Clients (Statut);
```

**Pourquoi l'option A est meilleure ?**

1. **Index Intersection** : SQL Server peut parfois combiner deux index (Index Intersection), mais c'est moins efficace qu'un index composite
2. **Lectures réduites** : Un index composite nécessite moins de lectures
3. **Espace disque** : Un index composite prend moins d'espace que deux index séparés

**Performance** :

| Approche | Index utilisé | Lectures approximatives |
|----------|---------------|-------------------------|
| Index composite `(Ville, Statut)` | Index Seek direct | 3-5 lectures |
| Index sur Ville + Index sur Statut | Index Intersection | 10-20 lectures |
| Aucun index | Table Scan | 100 000+ lectures |

### Quand créer des index séparés ?

Créez des index séparés si :

1. **Les colonnes sont rarement utilisées ensemble**
```sql
-- 50% des requêtes : WHERE Ville = ...
-- 50% des requêtes : WHERE Statut = ...
-- Rarement : WHERE Ville = ... AND Statut = ...

-- Deux index séparés ont du sens
CREATE INDEX IX_Clients_Ville ON Clients (Ville);
CREATE INDEX IX_Clients_Statut ON Clients (Statut);
```

2. **Une colonne est très sélective et l'autre non**
```sql
-- Email est unique (haute sélectivité)
-- Statut a 3 valeurs (faible sélectivité)

-- Index séparés peuvent avoir du sens
CREATE UNIQUE INDEX IX_Clients_Email ON Clients (Email);
CREATE INDEX IX_Clients_Statut ON Clients (Statut);
```

3. **Contraintes de taille d'index**
```sql
-- Si un index composite serait trop large
-- Colonnes individuelles avec index séparés
```

## Limites et Considérations

### Nombre maximum de colonnes

SQL Server autorise **jusqu'à 32 colonnes** dans un index composite (16 pour les versions plus anciennes).

**En pratique** :
- ✅ 2-3 colonnes : Très courant et efficace
- ⚠️ 4-6 colonnes : Rare mais parfois justifié
- ❌ 7+ colonnes : Presque jamais une bonne idée

**Pourquoi limiter ?**
- Plus l'index est large, plus il est coûteux en espace et en maintenance
- Au-delà de 3-4 colonnes, les gains de performance diminuent

### Taille totale de l'index

**Limite** : La taille maximale d'une clé d'index est de **900 octets** pour un index non-clustered (900 bytes).

**Exemple problématique** :

```sql
-- ❌ ERREUR potentielle : Taille trop grande
CREATE INDEX IX_Clients_Large
ON Clients (
    Nom NVARCHAR(200),      -- 400 octets
    Prenom NVARCHAR(200),   -- 400 octets
    Adresse NVARCHAR(200)   -- 400 octets
);
-- Total : 1200 octets > 900 octets → ERREUR
```

**Solution** : Utilisez INCLUDE pour les grandes colonnes

```sql
-- ✅ BON : Colonnes étroites dans l'index, colonnes larges en INCLUDE
CREATE INDEX IX_Clients_Nom_Prenom
ON Clients (Nom, Prenom)
INCLUDE (Adresse);
```

### Ordre des colonnes et ORDER BY

L'ordre des colonnes dans l'index **doit correspondre** à l'ORDER BY pour éviter un tri.

**Exemple** :

```sql
-- Requête avec ORDER BY
SELECT * FROM Commandes
WHERE ClientID = 100
ORDER BY DateCommande DESC;

-- ✅ BON : L'ordre correspond
CREATE INDEX IX_Commandes_Client_Date
ON Commandes (ClientID, DateCommande DESC);
-- Pas de tri nécessaire, données déjà dans le bon ordre

-- ⚠️ MOINS BON : L'ordre ne correspond pas
CREATE INDEX IX_Commandes_Client_Date
ON Commandes (ClientID, DateCommande ASC);
-- SQL Server doit trier les résultats (coûteux)
```

**Note** : Vous pouvez spécifier ASC ou DESC pour chaque colonne :

```sql
CREATE INDEX IX_Example
ON MaTable (Col1 ASC, Col2 DESC, Col3 ASC);
```

## Stratégies d'Indexation pour Requêtes Multiples

### Problème : Plusieurs patterns de requêtes

Souvent, vous avez plusieurs types de requêtes avec différents prédicats WHERE.

**Exemple** : Table Commandes

```sql
-- Requête 1 (40%) : Par client et date
SELECT * FROM Commandes
WHERE ClientID = 100 AND DateCommande >= '2024-01-01';

-- Requête 2 (30%) : Par client et statut
SELECT * FROM Commandes
WHERE ClientID = 100 AND Statut = 'En cours';

-- Requête 3 (20%) : Par date et statut
SELECT * FROM Commandes
WHERE DateCommande >= '2024-01-01' AND Statut = 'En cours';

-- Requête 4 (10%) : Par client, date et statut
SELECT * FROM Commandes
WHERE ClientID = 100
  AND DateCommande >= '2024-01-01'
  AND Statut = 'En cours';
```

### Stratégie 1 : Un index pour le cas le plus fréquent

```sql
-- Optimise les requêtes 1 et 4 (50% des cas)
CREATE INDEX IX_Commandes_Client_Date_Statut
ON Commandes (ClientID, DateCommande, Statut);
```

**Avantages** :
- ✅ Simple (un seul index)
- ✅ Optimise 50% des requêtes parfaitement
- ✅ Aide partiellement les autres requêtes

**Inconvénients** :
- ⚠️ Requêtes 2 et 3 moins efficaces

### Stratégie 2 : Plusieurs index ciblés

```sql
-- Index 1 : Pour requêtes par client
CREATE INDEX IX_Commandes_Client_Date_Statut
ON Commandes (ClientID, DateCommande, Statut);

-- Index 2 : Pour requêtes par date
CREATE INDEX IX_Commandes_Date_Statut
ON Commandes (DateCommande, Statut);
```

**Avantages** :
- ✅ Optimise la plupart des requêtes

**Inconvénients** :
- ❌ Plus d'espace disque
- ❌ Maintenance plus coûteuse (2 index à mettre à jour)

### Recommandation

**En pratique** :
1. Identifiez les **20% de requêtes** qui représentent **80% de la charge**
2. Créez des **index pour ces requêtes critiques**
3. Acceptez que certaines requêtes rares soient moins optimales
4. **Ne créez pas 10 index "au cas où"**

## Bonnes Pratiques

### ✅ À FAIRE

#### 1. Analysez vos requêtes avant de créer l'index

```sql
-- ❌ Mauvaise approche
"Je crée un index composite sur toutes les colonnes"

-- ✅ Bonne approche
"Voici les 5 requêtes les plus fréquentes, créons des index pour les optimiser"
```

#### 2. Respectez l'ordre : Égalité avant Plage

```sql
-- ✅ BON
CREATE INDEX IX_Commandes_Client_Date
ON Commandes (ClientID, DateCommande);
-- ClientID avec égalité (=) avant DateCommande avec plage (>=)

-- ❌ MOINS BON
CREATE INDEX IX_Commandes_Date_Client
ON Commandes (DateCommande, ClientID);
```

#### 3. Mettez les colonnes les plus sélectives en premier

```sql
-- ✅ BON
CREATE INDEX IX_Clients_Email_Statut
ON Clients (Email, Statut);
-- Email (haute sélectivité) avant Statut (faible sélectivité)
```

#### 4. Testez l'ordre avec les plans d'exécution

```sql
-- Activez les plans d'exécution dans SSMS
-- Comparez les performances avec différents ordres
```

#### 5. Documentez votre choix d'ordre

```sql
-- ✅ Commentaire expliquant le choix
-- Index optimisé pour la requête "commandes d'un client sur une période"
-- Ordre : ClientID (égalité, haute sélectivité) puis DateCommande (plage)
CREATE INDEX IX_Commandes_Client_Date
ON Commandes (ClientID, DateCommande);
```

### ❌ À ÉVITER

#### 1. Ne créez pas d'index composites trop larges

```sql
-- ❌ Mauvais : 7 colonnes
CREATE INDEX IX_Trop_Large
ON MaTable (Col1, Col2, Col3, Col4, Col5, Col6, Col7);
-- Coût de maintenance élevé, gains marginaux
```

#### 2. N'inversez pas l'ordre sans raison

```sql
-- Si 90% de vos requêtes sont : WHERE A = ... AND B = ...
-- ❌ Mauvais
CREATE INDEX IX_BA ON MaTable (B, A);

-- ✅ Bon
CREATE INDEX IX_AB ON MaTable (A, B);
```

#### 3. Ne créez pas d'index redondants

```sql
-- ❌ Redondant
CREATE INDEX IX_ABC ON MaTable (A, B, C);
CREATE INDEX IX_AB ON MaTable (A, B);
-- Le deuxième est inutile : le premier couvre déjà (A) et (A, B)
```

#### 4. N'oubliez pas le coût de maintenance

```sql
-- Table avec beaucoup d'INSERT/UPDATE/DELETE
-- ❌ Trop d'index composites
CREATE INDEX IX1 ON MaTable (A, B, C);
CREATE INDEX IX2 ON MaTable (A, C, B);
CREATE INDEX IX3 ON MaTable (B, C, A);
CREATE INDEX IX4 ON MaTable (C, A, B);
-- Les INSERT seront très lents !
```

## Vérification de l'Utilisation d'un Index

### Voir les index existants

```sql
-- Liste des index d'une table
EXEC sp_helpindex 'Clients';

-- Détails des index
SELECT
    i.name AS IndexName,
    STUFF((
        SELECT ', ' + c.name
        FROM sys.index_columns ic
        INNER JOIN sys.columns c ON ic.object_id = c.object_id AND ic.column_id = c.column_id
        WHERE ic.object_id = i.object_id AND ic.index_id = i.index_id
        ORDER BY ic.key_ordinal
        FOR XML PATH('')
    ), 1, 2, '') AS IndexColumns
FROM sys.indexes i
WHERE i.object_id = OBJECT_ID('Clients')
  AND i.type_desc != 'HEAP';
```

### Statistiques d'utilisation

```sql
-- Voir si l'index est utilisé
SELECT
    OBJECT_NAME(s.object_id) AS TableName,
    i.name AS IndexName,
    s.user_seeks AS Seeks,
    s.user_scans AS Scans,
    s.user_lookups AS Lookups,
    s.user_updates AS Updates,
    s.last_user_seek AS LastSeek
FROM sys.dm_db_index_usage_stats s
INNER JOIN sys.indexes i ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE s.database_id = DB_ID()
  AND OBJECT_NAME(s.object_id) = 'Clients'
ORDER BY s.user_seeks + s.user_scans + s.user_lookups DESC;
```

**Interprétation** :
- **Seeks élevés** : L'index est très utilisé ✅
- **Scans élevés** : L'index est parcouru entièrement (peut-être mal conçu) ⚠️
- **Updates élevés, peu de Seeks** : L'index coûte cher sans bénéfice ❌

## Résumé et Points Clés

### 🎯 Concepts essentiels

1. **Index composite = Index sur plusieurs colonnes dans un ordre spécifique**
   - `CREATE INDEX IX_ABC ON Table (A, B, C)`

2. **L'ordre des colonnes est CRUCIAL**
   - L'index (A, B, C) peut être utilisé pour : (A), (A,B), (A,B,C)
   - Ne peut PAS être utilisé efficacement pour : (B), (C), (B,C)

3. **Règle du préfixe de gauche**
   - L'index peut être utilisé si vous filtrez sur un préfixe continu depuis la gauche

4. **Ordre recommandé**
   - Égalité (`=`) avant Plage (`>`, `<`, `BETWEEN`)
   - Haute sélectivité avant Faible sélectivité
   - Colonnes fréquemment utilisées seules en premier

5. **Index composite > Index séparés**
   - Dans la plupart des cas, un index composite est plus efficace que plusieurs index séparés

### ✅ Checklist de conception

Avant de créer un index composite, demandez-vous :

- [ ] Quelles sont mes requêtes les plus fréquentes ?
- [ ] Quelles colonnes sont utilisées ensemble dans le WHERE ?
- [ ] Quels prédicats sont des égalités vs des plages ?
- [ ] Quelle colonne a la plus haute sélectivité ?
- [ ] Quelle colonne est utilisée seule le plus souvent ?
- [ ] L'ordre choisi optimise-t-il mes requêtes principales ?
- [ ] Ai-je testé avec les plans d'exécution ?

### 📋 Exemples à retenir

```sql
-- ✅ BON : Égalité avant plage, haute sélectivité avant faible
CREATE INDEX IX_Commandes_Client_Date_Statut
ON Commandes (ClientID, DateCommande, Statut);

-- ✅ BON : Pour requêtes fréquentes sur (Ville, Statut)
CREATE INDEX IX_Clients_Ville_Statut
ON Clients (Ville, Statut);

-- ✅ BON : Pour tri et recherche
CREATE INDEX IX_Produits_Categorie_Prix
ON Produits (CategorieID, Prix DESC);

-- ❌ À ÉVITER : Trop de colonnes
CREATE INDEX IX_TropLarge
ON Table (A, B, C, D, E, F, G);

-- ❌ À ÉVITER : Mauvais ordre (plage avant égalité)
CREATE INDEX IX_MauvaisOrdre
ON Commandes (DateCommande, ClientID);
```

## Conclusion

Les **index composites** sont un outil puissant pour optimiser les requêtes qui filtrent sur plusieurs colonnes. Mais leur efficacité dépend **entièrement de l'ordre des colonnes**.

**La règle d'or** :
> L'ordre des colonnes dans un index composite doit refléter l'ordre d'utilisation dans vos requêtes, avec les égalités avant les plages et la haute sélectivité avant la faible sélectivité.

Maîtriser les index composites, c'est comprendre que **l'ordre n'est pas arbitraire** : c'est une décision stratégique basée sur l'analyse de vos requêtes réelles.
