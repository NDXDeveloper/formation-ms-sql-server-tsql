# 5.6.3 Fonctions Table (TVF) - Multi-instructions (Multi-statement)

## Introduction

Les **fonctions table multi-instructions** (ou Multi-Statement Table-Valued Functions - MSTVF) sont des fonctions qui, comme les fonctions inline, retournent une **table**, mais avec une différence majeure : elles peuvent contenir **plusieurs instructions** et une **logique procédurale complexe** (variables, boucles, conditions, etc.).

**Analogie simple :** Si une fonction table inline est comme un filtre direct qui transforme instantanément des données, une fonction table multi-instructions est comme un atelier qui peut effectuer plusieurs étapes de transformation, stocker des résultats intermédiaires, et construire progressivement la table finale.

---

## Qu'est-ce qu'une fonction table multi-instructions ?

Une fonction table multi-instructions (MSTVF) est une fonction qui :
- Accepte **zéro ou plusieurs paramètres** en entrée
- **Retourne une table** définie explicitement (structure déclarée)
- Contient **plusieurs instructions** dans un bloc BEGIN...END
- Peut utiliser des **variables, boucles, conditions** et toute logique procédurale T-SQL
- Construit la table de retour **ligne par ligne** avec INSERT
- Est **moins performante** que les fonctions inline mais plus flexible

**Différence clé avec les fonctions inline :**
- Fonction inline → **une seule** requête SELECT, très performante
- Fonction multi-instructions → **plusieurs instructions**, logique complexe, moins performante

---

## Syntaxe de base

Voici la structure pour créer une fonction table multi-instructions :

```sql
CREATE FUNCTION nom_schema.nom_fonction
(
    @parametre1 type_donnees,
    @parametre2 type_donnees,
    ...
)
RETURNS @nom_table_retour TABLE
(
    -- Structure de la table retournée (obligatoire !)
    colonne1 type_donnees,
    colonne2 type_donnees,
    ...
)
AS
BEGIN
    -- Déclaration de variables (optionnel)
    DECLARE @variable1 type;
    DECLARE @variable2 type;

    -- Logique procédurale : conditions, boucles, etc.
    -- Instructions multiples

    -- Insertion des données dans la table de retour
    INSERT INTO @nom_table_retour (colonne1, colonne2, ...)
    SELECT ...;

    -- Autres traitements...

    -- Retour de la table
    RETURN;
END;
```

**Éléments clés :**
- `RETURNS @nom_table_retour TABLE` : On **déclare explicitement** la structure de la table retournée
- `BEGIN...END` : Bloc contenant plusieurs instructions (obligatoire)
- `@nom_table_retour` : Variable table qui sera retournée
- `INSERT INTO @nom_table_retour` : On remplit la table ligne par ligne
- `RETURN` : À la fin, on retourne la table (pas besoin de spécifier la variable)

**Différence majeure avec inline :** On doit **définir la structure** de la table de retour !

## Exemple 1 : Fonction simple avec logique conditionnelle

Créons une fonction qui retourne différentes informations selon un paramètre :

```sql
CREATE FUNCTION dbo.ObtenirInfosProduit
(
    @produitID INT
)
RETURNS @resultat TABLE
(
    ProduitID INT,
    NomProduit VARCHAR(100),
    Statut VARCHAR(50),
    Message VARCHAR(200)
)
AS
BEGIN
    DECLARE @stock INT;
    DECLARE @prix DECIMAL(10,2);

    -- Récupérer les informations du produit
    SELECT
        @stock = Stock,
        @prix = PrixUnitaire
    FROM Produits
    WHERE ProduitID = @produitID;

    -- Logique conditionnelle pour déterminer le statut
    IF @stock IS NULL
    BEGIN
        -- Produit n'existe pas
        INSERT INTO @resultat (ProduitID, Statut, Message)
        VALUES (@produitID, 'Erreur', 'Produit introuvable');
    END
    ELSE IF @stock = 0
    BEGIN
        -- Rupture de stock
        INSERT INTO @resultat (ProduitID, NomProduit, Statut, Message)
        SELECT
            @produitID,
            NomProduit,
            'Rupture',
            'Produit en rupture de stock'
        FROM Produits
        WHERE ProduitID = @produitID;
    END
    ELSE IF @stock < 10
    BEGIN
        -- Stock faible
        INSERT INTO @resultat (ProduitID, NomProduit, Statut, Message)
        SELECT
            @produitID,
            NomProduit,
            'Stock faible',
            'Seulement ' + CAST(@stock AS VARCHAR) + ' unités disponibles'
        FROM Produits
        WHERE ProduitID = @produitID;
    END
    ELSE
    BEGIN
        -- Stock normal
        INSERT INTO @resultat (ProduitID, NomProduit, Statut, Message)
        SELECT
            @produitID,
            NomProduit,
            'Disponible',
            CAST(@stock AS VARCHAR) + ' unités en stock'
        FROM Produits
        WHERE ProduitID = @produitID;
    END

    RETURN;
END;
```

**Utilisation :**
```sql
-- Tester avec différents produits
SELECT * FROM dbo.ObtenirInfosProduit(1);
SELECT * FROM dbo.ObtenirInfosProduit(999);  -- Produit inexistant

-- Vérifier plusieurs produits
SELECT p.*
FROM
    (VALUES (1), (2), (3), (4)) AS ProduitsList(ID)
    CROSS APPLY dbo.ObtenirInfosProduit(ID) AS p;
```

**Explication :**
- On déclare la structure de la table de retour avec 4 colonnes
- On utilise des variables pour stocker des valeurs intermédiaires
- On utilise IF/ELSE pour appliquer différentes logiques
- On insère des données dans `@resultat` selon les conditions
- On retourne la table à la fin

## Exemple 2 : Fonction avec boucle WHILE

Créons une fonction qui génère une série de dates (calendrier) :

```sql
CREATE FUNCTION dbo.GenererCalendrier
(
    @dateDebut DATE,
    @dateFin DATE
)
RETURNS @calendrier TABLE
(
    DateJour DATE,
    Annee INT,
    Mois INT,
    Jour INT,
    NomJour VARCHAR(20),
    EstWeekend BIT
)
AS
BEGIN
    DECLARE @dateCourante DATE;
    DECLARE @numeroJour INT;

    SET @dateCourante = @dateDebut;

    -- Boucle pour générer toutes les dates
    WHILE @dateCourante <= @dateFin
    BEGIN
        -- Numéro de jour INDÉPENDANT de SET DATEFIRST et de la langue : 1 = lundi … 7 = dimanche
        -- (le jour 0, soit 1900-01-01, était un lundi)
        SET @numeroJour = (DATEDIFF(DAY, 0, @dateCourante) % 7) + 1;

        INSERT INTO @calendrier (DateJour, Annee, Mois, Jour, NomJour, EstWeekend)
        VALUES (
            @dateCourante,
            YEAR(@dateCourante),
            MONTH(@dateCourante),
            DAY(@dateCourante),
            DATENAME(WEEKDAY, @dateCourante),
            CASE WHEN @numeroJour IN (6, 7) THEN 1 ELSE 0 END  -- 6 = samedi, 7 = dimanche
        );

        -- Passer au jour suivant
        SET @dateCourante = DATEADD(DAY, 1, @dateCourante);
    END

    RETURN;
END;
```

**Utilisation :**
```sql
-- Générer un calendrier pour novembre 2025
SELECT * FROM dbo.GenererCalendrier('2025-11-01', '2025-11-30');

-- Compter les jours ouvrés
SELECT
    COUNT(*) AS JoursOuvres
FROM dbo.GenererCalendrier('2025-11-01', '2025-11-30')
WHERE EstWeekend = 0;

-- Obtenir tous les lundis
SELECT
    DateJour,
    NomJour
FROM dbo.GenererCalendrier('2025-01-01', '2025-12-31')
WHERE NomJour = 'Monday'
ORDER BY DateJour;
```

**Explication :**
- On utilise une boucle WHILE pour itérer sur chaque date
- À chaque itération, on insère une ligne dans la table de retour
- On incrémente la date avec DATEADD
- Cette approche serait impossible avec une fonction inline (pas de boucle)

> ⚠️ **Piège classique — `DATEPART(WEEKDAY, …)` dépend de `SET DATEFIRST` et de la langue !** En `us_english`, `DATEFIRST` vaut 7 (dimanche = 1) ; en **français**, il vaut 1 (lundi = 1). Un test du type `DATEPART(WEEKDAY, d) IN (1, 7)` donne donc des résultats **différents** selon la configuration de la session. Pour détecter le week-end de façon **fiable**, on calcule un numéro de jour indépendant : `(DATEDIFF(DAY, 0, d) % 7) + 1` donne toujours `1 = lundi … 7 = dimanche`, donc week-end = `IN (6, 7)`.
>
> De même, `DATENAME(WEEKDAY, …)` renvoie le nom du jour **dans la langue de la session** (`Monday` en anglais, `lundi` en français). Le filtre `WHERE NomJour = 'Monday'` ci-dessous ne fonctionne donc que sur une instance configurée en anglais — préférez filtrer sur le numéro de jour calculé plus haut.

## Exemple 3 : Fonction avec plusieurs insertions conditionnelles

Créons une fonction qui analyse les commandes d'un client et retourne des recommandations :

```sql
CREATE FUNCTION dbo.GenererRecommandationsClient
(
    @clientID INT
)
RETURNS @recommandations TABLE
(
    TypeRecommandation VARCHAR(50),
    Message VARCHAR(500),
    Priorite INT
)
AS
BEGIN
    DECLARE @totalAchats DECIMAL(10,2);
    DECLARE @nombreCommandes INT;
    DECLARE @derniereCommande DATE;
    DECLARE @joursDepuisDerniereCommande INT;

    -- Récupérer les statistiques du client
    SELECT
        @totalAchats = SUM(MontantTotal),
        @nombreCommandes = COUNT(*),
        @derniereCommande = MAX(DateCommande)
    FROM Commandes
    WHERE ClientID = @clientID;

    SET @joursDepuisDerniereCommande = DATEDIFF(DAY, @derniereCommande, GETDATE());

    -- Recommandation : Client inactif
    IF @joursDepuisDerniereCommande > 90
    BEGIN
        INSERT INTO @recommandations (TypeRecommandation, Message, Priorite)
        VALUES (
            'Client inactif',
            'Le client n''a pas commandé depuis ' + CAST(@joursDepuisDerniereCommande AS VARCHAR) + ' jours. Envisager une relance.',
            1
        );
    END

    -- Recommandation : Client fidèle
    IF @nombreCommandes > 10 AND @totalAchats > 1000
    BEGIN
        INSERT INTO @recommandations (TypeRecommandation, Message, Priorite)
        VALUES (
            'Client fidèle',
            'Client VIP avec ' + CAST(@nombreCommandes AS VARCHAR) + ' commandes pour un total de ' + CAST(@totalAchats AS VARCHAR) + '€. Offrir des avantages.',
            2
        );
    END

    -- Recommandation : Opportunité de vente
    IF @nombreCommandes BETWEEN 3 AND 5
    BEGIN
        INSERT INTO @recommandations (TypeRecommandation, Message, Priorite)
        VALUES (
            'Opportunité',
            'Client régulier (' + CAST(@nombreCommandes AS VARCHAR) + ' commandes). Proposer un programme de fidélité.',
            3
        );
    END

    -- Recommandation : Nouveau client
    IF @nombreCommandes IS NULL OR @nombreCommandes = 0
    BEGIN
        INSERT INTO @recommandations (TypeRecommandation, Message, Priorite)
        VALUES (
            'Nouveau prospect',
            'Aucune commande enregistrée. Prévoir une offre de bienvenue.',
            4
        );
    END

    RETURN;
END;
```

**Utilisation :**
```sql
-- Obtenir les recommandations pour un client
SELECT * FROM dbo.GenererRecommandationsClient(5)
ORDER BY Priorite;

-- Obtenir toutes les recommandations pour tous les clients
SELECT
    c.ClientID,
    c.NomClient,
    r.TypeRecommandation,
    r.Message
FROM Clients AS c
CROSS APPLY dbo.GenererRecommandationsClient(c.ClientID) AS r
ORDER BY c.ClientID, r.Priorite;
```

**Explication :**
- On évalue plusieurs conditions indépendantes
- Chaque condition peut ajouter une ou plusieurs lignes à la table de retour
- Un même client peut avoir plusieurs recommandations simultanées
- Cette logique métier complexe serait difficile à exprimer avec une seule requête SELECT

## Exemple 4 : Fonction avec traitement de données complexes

Créons une fonction qui calcule des statistiques glissantes sur plusieurs périodes :

```sql
CREATE FUNCTION dbo.CalculerStatistiquesVentesPeriode
(
    @annee INT
)
RETURNS @stats TABLE
(
    Periode VARCHAR(50),
    ChiffreAffaires DECIMAL(15,2),
    NombreVentes INT,
    PanierMoyen DECIMAL(10,2),
    Evolution DECIMAL(10,2)  -- % par rapport à période précédente
)
AS
BEGIN
    DECLARE @trimestre INT;
    DECLARE @caActuel DECIMAL(15,2);
    DECLARE @caPrecedent DECIMAL(15,2);
    DECLARE @nbVentes INT;
    DECLARE @evolution DECIMAL(10,2);

    SET @trimestre = 1;
    SET @caPrecedent = 0;

    -- Boucle sur les 4 trimestres
    WHILE @trimestre <= 4
    BEGIN
        -- Calculer le CA du trimestre
        SELECT
            @caActuel = ISNULL(SUM(MontantTotal), 0),
            @nbVentes = COUNT(*)
        FROM Commandes
        WHERE YEAR(DateCommande) = @annee
            AND DATEPART(QUARTER, DateCommande) = @trimestre;

        -- Calculer l'évolution par rapport au trimestre précédent
        IF @caPrecedent > 0
            SET @evolution = ((@caActuel - @caPrecedent) / @caPrecedent) * 100;
        ELSE
            SET @evolution = NULL;

        -- Insérer les statistiques du trimestre
        INSERT INTO @stats (Periode, ChiffreAffaires, NombreVentes, PanierMoyen, Evolution)
        VALUES (
            'T' + CAST(@trimestre AS VARCHAR) + ' ' + CAST(@annee AS VARCHAR),
            @caActuel,
            @nbVentes,
            CASE WHEN @nbVentes > 0 THEN @caActuel / @nbVentes ELSE 0 END,
            @evolution
        );

        -- Préparer pour le prochain trimestre
        SET @caPrecedent = @caActuel;
        SET @trimestre = @trimestre + 1;
    END

    -- Ajouter une ligne pour le total annuel
    INSERT INTO @stats (Periode, ChiffreAffaires, NombreVentes, PanierMoyen, Evolution)
    SELECT
        'Total ' + CAST(@annee AS VARCHAR),
        SUM(MontantTotal),
        COUNT(*),
        AVG(MontantTotal),
        NULL
    FROM Commandes
    WHERE YEAR(DateCommande) = @annee;

    RETURN;
END;
```

**Utilisation :**
```sql
-- Statistiques pour 2025
SELECT * FROM dbo.CalculerStatistiquesVentesPeriode(2025);

-- Comparer plusieurs années
SELECT * FROM dbo.CalculerStatistiquesVentesPeriode(2023)
UNION ALL
SELECT * FROM dbo.CalculerStatistiquesVentesPeriode(2024)
UNION ALL
SELECT * FROM dbo.CalculerStatistiquesVentesPeriode(2025)
ORDER BY Periode;
```

**Explication :**
- On utilise une boucle pour traiter chaque trimestre
- On calcule l'évolution par rapport au trimestre précédent (nécessite de mémoriser la valeur précédente)
- On ajoute une ligne de total à la fin
- Cette logique séquentielle est typique des fonctions multi-instructions

## Exemple 5 : Fonction avec gestion d'erreurs et validation

Créons une fonction qui valide et normalise des données avant de les retourner :

```sql
CREATE FUNCTION dbo.NormaliserDonneesClient
(
    @clientID INT
)
RETURNS @clientNormalise TABLE
(
    ClientID INT,
    Nom VARCHAR(100),
    Email VARCHAR(100),
    Telephone VARCHAR(20),
    Pays VARCHAR(50),
    Statut VARCHAR(50),
    MessageErreur VARCHAR(200)
)
AS
BEGIN
    DECLARE @nom VARCHAR(100);
    DECLARE @email VARCHAR(100);
    DECLARE @tel VARCHAR(20);
    DECLARE @pays VARCHAR(50);
    DECLARE @erreurs VARCHAR(200) = '';

    -- Récupérer les données brutes
    SELECT
        @nom = NomClient,
        @email = Email,
        @tel = Telephone,
        @pays = Pays
    FROM Clients
    WHERE ClientID = @clientID;

    -- Vérifier si le client existe
    IF @nom IS NULL
    BEGIN
        INSERT INTO @clientNormalise
        VALUES (@clientID, NULL, NULL, NULL, NULL, 'Erreur', 'Client introuvable');
        RETURN;
    END

    -- Normaliser le nom (Capitaliser)
    SET @nom = UPPER(LEFT(@nom, 1)) + LOWER(SUBSTRING(@nom, 2, LEN(@nom)));

    -- Valider l'email
    IF @email NOT LIKE '%@%.%'
    BEGIN
        SET @erreurs = @erreurs + 'Email invalide. ';
        SET @email = NULL;
    END

    -- Normaliser le téléphone (supprimer les espaces)
    SET @tel = REPLACE(@tel, ' ', '');
    SET @tel = REPLACE(@tel, '-', '');

    -- Valider le téléphone (doit contenir 10 chiffres)
    IF LEN(@tel) != 10 OR @tel LIKE '%[^0-9]%'
    BEGIN
        SET @erreurs = @erreurs + 'Téléphone invalide. ';
        SET @tel = NULL;
    END

    -- Normaliser le pays (Code ISO)
    SET @pays = UPPER(@pays);
    IF @pays NOT IN ('FR', 'BE', 'CH', 'LU', 'CA')
    BEGIN
        SET @erreurs = @erreurs + 'Pays non supporté. ';
    END

    -- Insérer le résultat normalisé
    INSERT INTO @clientNormalise (ClientID, Nom, Email, Telephone, Pays, Statut, MessageErreur)
    VALUES (
        @clientID,
        @nom,
        @email,
        @tel,
        @pays,
        CASE WHEN @erreurs = '' THEN 'Valide' ELSE 'Erreurs détectées' END,
        CASE WHEN @erreurs = '' THEN NULL ELSE RTRIM(@erreurs) END
    );

    RETURN;
END;
```

**Utilisation :**
```sql
-- Valider un client
SELECT * FROM dbo.NormaliserDonneesClient(5);

-- Valider tous les clients et identifier ceux avec des erreurs
SELECT *
FROM Clients AS c
CROSS APPLY dbo.NormaliserDonneesClient(c.ClientID) AS n
WHERE n.Statut = 'Erreurs détectées';
```

**Explication :**
- On effectue plusieurs étapes de validation et de normalisation
- On accumule les messages d'erreur dans une variable
- On retourne les données nettoyées avec un statut
- Cette logique procédurale serait complexe à réaliser en une seule requête

## Différences avec les fonctions table inline

| Aspect | Fonction Inline | Fonction Multi-instructions |
|--------|----------------|----------------------------|
| **Syntaxe** | AS RETURN (SELECT...) | BEGIN...END avec RETURNS @table TABLE(...) |
| **Instructions** | Une seule SELECT | Multiples instructions possibles |
| **Structure de retour** | Implicite (définie par SELECT) | Explicite (déclarée) |
| **Variables** | ❌ Non | ✅ Oui (DECLARE) |
| **Boucles/Conditions** | ❌ Non | ✅ Oui (IF/WHILE) |
| **Performance** | ✅ Excellente | ❌ Moins bonne |
| **Optimisation** | Intégrée au plan de requête | Variable table temporaire |
| **Complexité** | Simple | Complexe possible |

**Exemple comparatif :**

```sql
-- ✅ Fonction inline (préférable si possible)
CREATE FUNCTION dbo.ObtenirCommandesClient_Inline(@clientID INT)
RETURNS TABLE AS RETURN (
    SELECT CommandeID, DateCommande, MontantTotal
    FROM Commandes
    WHERE ClientID = @clientID
);

-- ❌ Fonction multi-instructions (inutilement complexe ici)
CREATE FUNCTION dbo.ObtenirCommandesClient_Multi(@clientID INT)
RETURNS @result TABLE (
    CommandeID INT,
    DateCommande DATE,
    MontantTotal DECIMAL(10,2)
)
AS BEGIN
    INSERT INTO @result
    SELECT CommandeID, DateCommande, MontantTotal
    FROM Commandes
    WHERE ClientID = @clientID;

    RETURN;
END;
```

**Dans cet exemple, la version inline est meilleure !** N'utilisez multi-instructions que quand nécessaire.

## Impact sur les performances

### Pourquoi les fonctions multi-instructions sont plus lentes ?

1. **Variable table** : La table de retour est matérialisée temporairement (tempdb)
2. **Pas d'inlining** : contrairement à une fonction inline, la logique n'est pas fusionnée dans la requête appelante — la fonction reste une « boîte noire »
3. **Estimation de cardinalité** : historiquement, SQL Server estimait un nombre de lignes **fixe** (1 ligne avant SQL Server 2014, **100 lignes** de 2014 à 2016), souvent très éloigné de la réalité. Depuis **SQL Server 2017** (niveau de compatibilité 140+), l'*Interleaved Execution* exécute d'abord la fonction pour obtenir une estimation **réelle**, ce qui améliore nettement les plans — mais la fonction reste non fusionnée
4. **Exécution séquentielle** : Les boucles et instructions sont exécutées une par une

**Exemple de problème de performance :**

```sql
-- Cette requête peut être TRÈS lente
SELECT
    c.ClientID,
    c.NomClient,
    s.ChiffreAffaires
FROM Clients AS c
CROSS APPLY dbo.CalculerStatistiquesClient(c.ClientID) AS s  -- Appelée pour CHAQUE client !
WHERE c.Actif = 1;

-- Si vous avez 10,000 clients actifs, la fonction sera appelée 10,000 fois !
```

### Conseils pour minimiser l'impact :

1. **Préférez inline quand possible** : Si votre logique peut tenir en une requête SELECT, utilisez inline
2. **Limitez les appels** : Évitez d'appeler la fonction sur de grosses tables
3. **Indexez les données sources** : Assurez-vous que les tables utilisées dans la fonction sont bien indexées
4. **Évitez les boucles** : Utilisez des opérations ensemblistes quand possible
5. **Considérez des alternatives** : Procédures stockées avec tables temporaires, vues matérialisées, etc.

## Quand utiliser les fonctions multi-instructions ?

### ✅ Bons cas d'usage

1. **Logique conditionnelle complexe** qui ne peut pas être exprimée en une seule requête
   ```sql
   IF condition1 THEN insert lignes type A
   ELSE IF condition2 THEN insert lignes type B
   ELSE insert lignes type C
   ```

2. **Génération de données** (calendriers, séries numériques)
   ```sql
   WHILE @date <= @dateFin
   BEGIN
       INSERT INTO @result ...
       SET @date = DATEADD(DAY, 1, @date);
   END
   ```

3. **Transformations itératives** où chaque étape dépend de la précédente
   ```sql
   WHILE @condition
   BEGIN
       -- Calcul basé sur résultat précédent
       SET @value = @value * 1.05;
       INSERT INTO @result ...
   END
   ```

4. **Validation et nettoyage de données** avec multiples vérifications
   ```sql
   IF @email LIKE '%@%' SET @status = 'Valid'
   IF @phone NOT LIKE '[0-9]%' SET @error = @error + 'Invalid phone. '
   INSERT INTO @result ...
   ```

### ❌ Mauvais cas d'usage

1. **Simple filtrage** → Utilisez une fonction inline
2. **Jointures simples** → Utilisez une fonction inline ou une vue
3. **Agrégations directes** → Utilisez une fonction inline
4. **Sur de très grosses tables** → Envisagez d'autres solutions (procédures stockées, vues indexées)

---

## Limitations et contraintes

### Restrictions communes à toutes les fonctions

- Pas de modifications de données (INSERT/UPDATE/DELETE sur des tables réelles)
- Pas de DDL (CREATE/ALTER/DROP)
- Pas de transactions explicites (BEGIN TRAN/COMMIT)

### Limitations spécifiques aux multi-instructions

1. **Performance** : Plus lentes que les fonctions inline (logique non fusionnée dans la requête)
2. **Estimation de cardinalité** : longtemps fixe (1 ligne avant SQL Server 2014, 100 ensuite). Améliorée depuis SQL Server 2017 par l'*Interleaved Execution* (estimation réelle), mais elle reste moins précise qu'avec une fonction inline
3. **Pas de TRY...CATCH** : la gestion structurée des erreurs (TRY...CATCH, RAISERROR, THROW) est interdite — dans **toutes** les versions
4. **Variable table de retour** : on **peut** l'indexer via une contrainte `PRIMARY KEY` ou `UNIQUE` dans la déclaration (et, depuis SQL Server 2014, via un index inline), mais on ne peut pas ajouter d'index après coup avec `CREATE INDEX`

## Bonnes pratiques

### 1. N'utilisez multi-instructions QUE si nécessaire

```sql
-- ❌ Inutilement complexe
CREATE FUNCTION dbo.GetActiveProducts()
RETURNS @result TABLE (ProductID INT, Name VARCHAR(100))
AS BEGIN
    INSERT INTO @result
    SELECT ProductID, Name FROM Products WHERE Active = 1;
    RETURN;
END;

-- ✅ Beaucoup mieux
CREATE FUNCTION dbo.GetActiveProducts()
RETURNS TABLE AS RETURN (
    SELECT ProductID, Name FROM Products WHERE Active = 1
);
```

### 2. Commentez abondamment

La logique complexe nécessite des explications :

```sql
CREATE FUNCTION dbo.CalculerStatistiques(@param INT)
RETURNS @result TABLE (...)
AS
BEGIN
    -- Étape 1 : Récupération des données de base
    DECLARE @value INT;
    SELECT @value = SomeColumn FROM SomeTable WHERE ID = @param;

    -- Étape 2 : Validation
    IF @value IS NULL RETURN;  -- Sortie anticipée si pas de données

    -- Étape 3 : Calculs complexes
    -- ... (expliquer la logique)

    RETURN;
END;
```

### 3. Gérez les cas limites

```sql
-- Vérifier si les paramètres sont valides
IF @dateDebut > @dateFin
    RETURN;  -- Retourne une table vide

-- Vérifier si les données existent
IF NOT EXISTS (SELECT 1 FROM Clients WHERE ClientID = @clientID)
BEGIN
    INSERT INTO @result VALUES (NULL, 'Client introuvable', NULL);
    RETURN;
END;
```

### 4. Évitez les boucles quand possible

```sql
-- ❌ Boucle (lent)
WHILE @i <= @max
BEGIN
    INSERT INTO @result
    SELECT @i, @i * 2;
    SET @i = @i + 1;
END;

-- ✅ Opération ensembliste (rapide)
INSERT INTO @result (Value, DoubleValue)
SELECT
    Number,
    Number * 2
FROM master.dbo.spt_values
WHERE Type = 'P' AND Number BETWEEN 1 AND @max;
```

### 5. Documentez la complexité de performance

```sql
/*
Fonction : dbo.CalculerStatistiquesComplexes
ATTENTION : Cette fonction contient des boucles et peut être lente.
- Ne PAS appeler sur des tables de plus de 1000 lignes
- Prévoir un délai d'exécution de ~500ms par appel
- Envisager une procédure stockée pour des volumes importants
*/
```

## Alternatives à considérer

Si vos fonctions multi-instructions posent des problèmes de performance :

### 1. Procédures stockées

```sql
-- Au lieu d'une fonction lente
CREATE PROCEDURE dbo.GenererRapportClient
    @clientID INT
AS
BEGIN
    -- Créer une table temporaire
    CREATE TABLE #Resultat (...);

    -- Logique complexe
    ...

    -- Retourner les résultats
    SELECT * FROM #Resultat;

    DROP TABLE #Resultat;
END;
```

**Avantages :**
- Peuvent modifier des données
- Meilleures performances avec tables temporaires
- Plus de flexibilité

**Inconvénients :**
- Ne peuvent pas être utilisées dans FROM
- Syntaxe différente

### 2. Vues indexées (pour données agrégées)

```sql
-- Si vous calculez souvent les mêmes statistiques
CREATE VIEW dbo.VueStatistiquesClients
WITH SCHEMABINDING
AS
SELECT
    ClientID,
    COUNT_BIG(*) AS NombreCommandes,
    SUM(MontantTotal) AS TotalAchats
FROM dbo.Commandes
GROUP BY ClientID;

-- Créer un index
CREATE UNIQUE CLUSTERED INDEX IX_Stats ON dbo.VueStatistiquesClients(ClientID);
```

### 3. Tables calculées persistées

```sql
-- Matérialiser les résultats complexes
CREATE TABLE StatsClientsCache (
    ClientID INT PRIMARY KEY,
    StatType VARCHAR(50),
    Value DECIMAL(10,2),
    CalculeAt DATETIME
);
```

## Résumé

Les **fonctions table multi-instructions** en T-SQL permettent :
- De retourner une **table** avec une **logique procédurale complexe**
- D'utiliser des **variables, boucles, conditions**
- De construire des résultats **étape par étape**

**Points clés à retenir :**
- Elles retournent une **table** (structure explicite)
- Elles utilisent **BEGIN...END** avec plusieurs instructions
- Elles sont **moins performantes** que les fonctions inline
- À utiliser **uniquement quand nécessaire**

**Quand les utiliser :**
- ✅ Logique conditionnelle complexe qu'on ne peut pas exprimer en une requête
- ✅ Génération de données (calendriers, séries)
- ✅ Transformations itératives
- ❌ PAS pour des filtres/jointures simples (utilisez inline)
- ❌ PAS sur de gros volumes (considérez des alternatives)

**Règle d'or :** Privilégiez toujours les fonctions inline pour la performance. N'utilisez multi-instructions que lorsque la complexité le justifie vraiment !
