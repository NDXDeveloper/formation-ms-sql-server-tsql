# 8.7.2 Columnstore cluster (CCI) et non-cluster (NCCI)

## Introduction

Il existe **deux façons** de mettre en place un index columnstore, selon que l'on veut transformer **toute la table** en columnstore, ou **ajouter** une vue analytique en colonnes par-dessus une table classique :

- L'index columnstore **cluster** (*Clustered Columnstore Index*, CCI) ;
- L'index columnstore **non-cluster** (*Nonclustered Columnstore Index*, NCCI).

Cette sous-section explique la différence, la syntaxe, le fonctionnement interne (delta store), et comment choisir.

---

## L'index columnstore cluster (CCI)

Un **CCI** transforme **la table entière** en stockage colonne. Il n'y a plus de copie rowstore : **la table EST le columnstore**.

```sql
-- Sur une table de faits volumineuse
CREATE CLUSTERED COLUMNSTORE INDEX CCI_Ventes
ON Ventes;
```

**Caractéristiques :**
- ✅ Compression et performances analytiques **maximales**.
- ✅ Idéal pour les **tables de faits** d'un entrepôt de données.
- ✅ Disponible depuis **SQL Server 2014** (et pleinement modifiable — INSERT/UPDATE/DELETE — depuis cette version).
- ⚠️ Une table ne peut avoir **qu'un seul** index cluster (qu'il soit rowstore ou columnstore) : choisir un CCI, c'est renoncer à un index cluster rowstore classique.

> 💡 **SQL Server 2022** introduit l'**ordered clustered columnstore index** : les données sont triées à la création sur une ou plusieurs colonnes, ce qui améliore encore l'élimination de segments pour les requêtes filtrées sur ces colonnes.

---

## L'index columnstore non-cluster (NCCI)

Un **NCCI** est un index **secondaire** en colonnes, **ajouté** à une table qui reste stockée en rowstore. On a alors **les deux représentations** des mêmes données en même temps.

```sql
-- La table reste rowstore (OLTP), mais gagne une vue analytique columnstore
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Ventes
ON Ventes (Date, Region, Produit, Montant);
```

**Caractéristiques :**
- ✅ Permet l'**analytique en temps réel** sur une table **transactionnelle** : c'est l'approche **HTAP** (*Hybrid Transactional/Analytical Processing*).
- ✅ Disponible depuis **SQL Server 2012** (en **lecture seule** à l'époque) ; **modifiable** depuis **SQL Server 2016**.
- ⚠️ Coûte de l'espace supplémentaire (les données existent en double) et un léger surcoût en écriture (il faut maintenir les deux structures).

> 🧠 **CCI ou NCCI ?**  
> - Table **purement analytique** (entrepôt, table de faits) → **CCI**.  
> - Table **OLTP** sur laquelle on veut *aussi* faire de l'analytique sans copier les données ailleurs → **NCCI**.

---

## Fonctionnement interne : delta store et tuple mover

Le columnstore est optimisé pour les **insertions en masse**, pas pour les insertions ligne par ligne. SQL Server gère cela élégamment avec un mécanisme tampon :

```
   INSERT de petites quantités
            │
            ▼
   ┌─────────────────────┐      quand un groupe atteint
   │  DELTA STORE        │      ~1 048 576 lignes...
   │  (rowstore tampon)  │ ──────────────┐
   └─────────────────────┘               ▼
                              ┌──────────────────────────┐
                              │  TUPLE MOVER : compresse  │
                              │  en rowgroup columnstore  │
                              └──────────────────────────┘
```

- Les **petits INSERT** vont d'abord dans un **delta store** (un stockage rowstore temporaire).
- Quand un delta rowgroup atteint ~1 million de lignes, un processus appelé **tuple mover** le **compresse** en un rowgroup columnstore définitif.
- Les **gros chargements** (`BULK INSERT`, `INSERT ... SELECT` massif) vont **directement** en rowgroups compressés, sans passer par le delta store — d'où l'intérêt de charger par lots volumineux.
- Les **DELETE** ne suppriment pas physiquement : ils marquent les lignes dans une **deleted bitmap** ; l'espace est récupéré lors d'une reconstruction.

> 💡 **Conseil de chargement** : pour profiter pleinement du columnstore, insérez par **lots d'au moins ~100 000 lignes** (idéalement ≥ 1 million). Les insertions unitaires encombrent le delta store et dégradent la compression.

## Maintenance des index columnstore

Avec le temps (beaucoup de DELETE/UPDATE, petits rowgroups), l'index columnstore se fragmente. On le maintient comme un index classique (voir §7.7) :

```sql
-- Réorganiser : compresse les delta rowgroups et fusionne les petits groupes (en ligne)
ALTER INDEX CCI_Ventes ON Ventes REORGANIZE;

-- Reconstruire : recrée des rowgroups optimaux et purge les lignes supprimées
ALTER INDEX CCI_Ventes ON Ventes REBUILD;
```

On surveille l'état des rowgroups via la vue système dédiée :

```sql
SELECT object_name(object_id) AS Tbl, state_desc, total_rows, deleted_rows
FROM sys.dm_db_column_store_row_group_physical_stats
WHERE object_id = OBJECT_ID('Ventes');
```

Un grand nombre de `deleted_rows` ou beaucoup de petits rowgroups `OPEN` indiquent qu'une reconstruction serait bénéfique.

## Exemple complet

```sql
-- 1) Table de faits d'un entrepôt
CREATE TABLE FaitVentes (
    VenteID    BIGINT       NOT NULL,
    DateVente  DATE         NOT NULL,
    RegionID   INT          NOT NULL,
    ProduitID  INT          NOT NULL,
    Quantite   INT          NOT NULL,
    Montant    DECIMAL(12,2) NOT NULL
);

-- 2) On la transforme en columnstore pour l'analytique
CREATE CLUSTERED COLUMNSTORE INDEX CCI_FaitVentes ON FaitVentes;

-- 3) Requête analytique : ultra-rapide grâce au mode batch + élimination de segments
SELECT RegionID, YEAR(DateVente) AS Annee, SUM(Montant) AS CA
FROM FaitVentes
WHERE DateVente >= '2024-01-01'
GROUP BY RegionID, YEAR(DateVente)
ORDER BY Annee, RegionID;
```

## Exemple HTAP : analytique en temps réel sur une table OLTP

Cas concret : une table de commandes très sollicitée en écriture, sur laquelle on veut *aussi* produire des analyses sans créer de base séparée. On ajoute un **NCCI** :

```sql
-- La table reste rowstore (INSERT/UPDATE rapides)...
CREATE TABLE Commandes (
    CommandeID   INT IDENTITY PRIMARY KEY,    -- index cluster rowstore (OLTP)
    ClientID     INT,
    DateCommande DATETIME2,
    Montant      DECIMAL(12,2)
);

-- ... mais gagne une vue analytique columnstore (OLAP en temps réel)
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Commandes
ON Commandes (DateCommande, ClientID, Montant);
```

Les recherches ponctuelles (`WHERE CommandeID = ...`) utilisent l'index cluster rowstore ; les agrégations (`SUM(Montant) ... GROUP BY ...`) utilisent le NCCI en mode batch. C'est l'essence de l'**HTAP**.

## Pièges courants

| Piège | Conséquence | Bon réflexe |
|-------|-------------|-------------|
| Petits INSERT répétés | Delta store encombré, rowgroups `OPEN` | Charger par lots ≥ ~100 000 lignes |
| Gros volume de DELETE/UPDATE | Beaucoup de `deleted_rows`, fragmentation | `ALTER INDEX ... REBUILD` périodique |
| NCCI sur **toutes** les colonnes | Surcoût d'espace et d'écriture | N'inclure que les colonnes utiles à l'analytique |
| Attendre un temps réel parfait | Les lignes en delta store ne sont pas encore compressées | `REORGANIZE` pour forcer leur passage |

## Questions fréquentes

**Q : Peut-on avoir plusieurs index columnstore sur une même table ?**
R : Non, **un seul** index columnstore par table (CCI ou NCCI). On peut en revanche ajouter des index **non-cluster rowstore** à côté.

**Q : CCI ou NCCI, comment choisir ?**
R : Table **purement analytique** → CCI. Table **OLTP** sur laquelle on veut aussi de l'analytique → NCCI (HTAP).

**Q : Comment savoir si une reconstruction est nécessaire ?**
R : Surveillez `sys.dm_db_column_store_row_group_physical_stats` : beaucoup de `deleted_rows` ou de petits rowgroups `OPEN` justifient un `REBUILD`.

---

## Résumé

- Le **CCI** (cluster) transforme toute la table en columnstore : compression et perfs analytiques maximales (SQL 2014+). Une table n'a qu'un seul index cluster.
- Le **NCCI** (non-cluster) ajoute une vue colonne sur une table rowstore : idéal pour l'**HTAP** (analytique sur données OLTP), modifiable depuis SQL 2016.
- Les petits INSERT transitent par un **delta store**, compressé en rowgroups par le **tuple mover** ; chargez par **gros lots** pour de meilleures performances.
- Les DELETE sont logiques (deleted bitmap) ; on récupère l'espace via `REBUILD`.
- On entretient l'index columnstore avec `ALTER INDEX ... REORGANIZE / REBUILD` et on surveille `sys.dm_db_column_store_row_group_physical_stats`.
