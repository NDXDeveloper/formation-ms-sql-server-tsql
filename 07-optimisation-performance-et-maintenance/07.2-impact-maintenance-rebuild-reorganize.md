# 7.7.2 L'Impact de la Maintenance : REBUILD vs. REORGANIZE

## Introduction

Comme nous l'avons vu dans la section précédente, la fragmentation d'index dégrade les performances de votre base de données au fil du temps. Pour résoudre ce problème, SQL Server propose deux opérations de maintenance principales :

- **REORGANIZE** (Réorganisation)
- **REBUILD** (Reconstruction)

Chacune a ses avantages, ses inconvénients et ses cas d'usage appropriés. Comprendre ces différences est essentiel pour maintenir une base de données performante.

---

## Analogie : La Maintenance d'une Bibliothèque

Pour mieux comprendre ces deux opérations, reprenons notre analogie de la bibliothèque :

### REORGANIZE : Le Rangement

Imaginez que vous **rangez les livres** dans la bibliothèque sans fermer l'établissement :
- Vous déplacez les livres mal placés vers leur emplacement correct
- Vous combinez les étagères partiellement vides
- Les visiteurs peuvent continuer à emprunter des livres pendant que vous travaillez
- C'est un processus progressif et moins perturbant
- Vous ne créez pas une nouvelle bibliothèque, vous arrangez l'existante

### REBUILD : La Reconstruction Complète

Imaginez que vous **reconstruisez entièrement la bibliothèque** :
- Vous démolissez les anciennes étagères
- Vous construisez de nouvelles étagères toutes neuves
- Vous replacez tous les livres dans un ordre parfait
- Vous pouvez fermer la bibliothèque pendant les travaux (ou garder une copie temporaire ouverte)
- C'est plus radical, plus complet, mais plus perturbant

## REORGANIZE : La Réorganisation

### Qu'est-ce que REORGANIZE ?

`ALTER INDEX ... REORGANIZE` est une opération de maintenance **légère et incrémentale** qui défragmente l'index en réorganisant les pages existantes.

### Comment fonctionne REORGANIZE ?

Cette opération :
1. **Compacte les pages** : Remplit les pages partiellement vides en déplaçant des données
2. **Réorganise l'ordre logique** : Tente d'améliorer l'ordre physique des pages pour correspondre à l'ordre logique
3. **Libère les pages vides** : Supprime les pages complètement vides
4. **Travaille page par page** : Traite l'index de manière progressive

### Syntaxe de Base

```sql
-- Réorganiser un index spécifique
ALTER INDEX IX_NomIndex ON MaTable REORGANIZE;

-- Réorganiser tous les index d'une table
ALTER INDEX ALL ON MaTable REORGANIZE;
```

### Caractéristiques Principales

#### ✅ Avantages

1. **Opération EN LIGNE** :
   - L'index reste accessible pendant la réorganisation
   - Les utilisateurs peuvent continuer à lire et écrire des données
   - Pas de verrouillage bloquant prolongé

2. **Consommation minimale de ressources** :
   - Utilise peu de CPU
   - Nécessite peu d'espace disque supplémentaire
   - Peut s'exécuter en arrière-plan sans impact majeur

3. **Interruptible** :
   - Peut être annulée à tout moment sans perdre le progrès déjà réalisé
   - Reprise possible là où elle s'était arrêtée

4. **Toujours compresse les LOB** :
   - Compacte automatiquement les données LOB (Large Object)

#### ❌ Inconvénients

1. **Efficacité limitée** :
   - Ne corrige pas complètement la fragmentation externe
   - Moins efficace sur les index très fragmentés (> 30%)
   - Peut prendre beaucoup de temps pour de gros index

2. **Ne réinitialise pas les statistiques** :
   - Les statistiques ne sont pas automatiquement mises à jour
   - Nécessite une opération séparée (`UPDATE STATISTICS`)

3. **Pas de contrôle sur le Fill Factor** :
   - Ne peut pas modifier le facteur de remplissage
   - Utilise le Fill Factor existant

### Quand utiliser REORGANIZE ?

REORGANIZE est approprié quand :

- **La fragmentation est modérée** (entre 10% et 30%)
- **La disponibilité est critique** (vous ne pouvez pas bloquer l'accès)
- **Vous avez des contraintes de ressources** (CPU, mémoire, espace disque)
- **L'index est petit à moyen** (moins de quelques GB)
- **Vous effectuez une maintenance fréquente** (quotidienne ou hebdomadaire)

### Exemple Pratique

```sql
-- Vérifier la fragmentation
SELECT
    OBJECT_NAME(object_id) AS TableName,
    index_id,
    avg_fragmentation_in_percent
FROM
    sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('MaTable'), NULL, NULL, 'DETAILED')
WHERE
    index_id > 0;

-- Si fragmentation entre 10% et 30%
ALTER INDEX IX_MaTable_Colonne ON MaTable REORGANIZE;

-- Mettre à jour les statistiques après
UPDATE STATISTICS MaTable;
```

## REBUILD : La Reconstruction

### Qu'est-ce que REBUILD ?

`ALTER INDEX ... REBUILD` est une opération de maintenance **complète et radicale** qui reconstruit entièrement l'index de zéro.

### Comment fonctionne REBUILD ?

Cette opération :
1. **Crée une nouvelle structure d'index** : Construit un index complètement nouveau
2. **Copie toutes les données** : Transfère les données vers la nouvelle structure
3. **Supprime l'ancienne structure** : Remplace l'ancien index par le nouveau
4. **Élimine toute fragmentation** : L'index résultant a 0% de fragmentation

### Syntaxe de Base

```sql
-- Reconstruire un index spécifique
ALTER INDEX IX_NomIndex ON MaTable REBUILD;

-- Reconstruire tous les index d'une table
ALTER INDEX ALL ON MaTable REBUILD;

-- Avec options
ALTER INDEX IX_NomIndex ON MaTable REBUILD
WITH (
    ONLINE = ON,           -- Reconstruction en ligne (Enterprise Edition)
    FILLFACTOR = 80,       -- Nouveau facteur de remplissage
    SORT_IN_TEMPDB = ON    -- Utiliser tempdb pour le tri
);
```

### Caractéristiques Principales

#### ✅ Avantages

1. **Efficacité maximale** :
   - Élimine **complètement** la fragmentation (0% après rebuild)
   - Compacte totalement les pages
   - Index optimisé comme s'il était nouvellement créé

2. **Mise à jour des statistiques** :
   - Les statistiques sont automatiquement recalculées avec un échantillonnage complet
   - Plus besoin d'exécuter `UPDATE STATISTICS` séparément

3. **Contrôle complet** :
   - Permet de modifier le Fill Factor
   - Permet de modifier les options de l'index
   - Peut changer la compression (si applicable)

4. **Plus rapide pour haute fragmentation** :
   - Pour une fragmentation > 30%, REBUILD est plus rapide que REORGANIZE

#### ❌ Inconvénients

1. **Opération HORS LIGNE par défaut** :
   - L'index est verrouillé pendant la reconstruction
   - Les utilisateurs ne peuvent pas accéder aux données
   - **Exception** : `ONLINE = ON` disponible en Enterprise Edition

2. **Consommation élevée de ressources** :
   - Utilise beaucoup de CPU
   - Nécessite de l'espace disque temporaire (jusqu'à 2x la taille de l'index)
   - Génère beaucoup de logs de transaction

3. **Atomique et non interruptible** :
   - Si annulée, tout le travail est perdu (rollback complet)
   - Doit recommencer depuis le début

4. **Impact sur les sauvegardes** :
   - Génère énormément de logs, augmentant la taille des sauvegardes de logs

### Quand utiliser REBUILD ?

REBUILD est approprié quand :

- **La fragmentation est élevée** (> 30%)
- **Vous pouvez tolérer une indisponibilité** (ou avez Enterprise Edition avec ONLINE = ON)
- **Vous voulez un résultat optimal**
- **L'index est volumineux et très fragmenté**
- **Vous effectuez une maintenance peu fréquente** (mensuelle, trimestrielle)
- **Vous voulez mettre à jour les statistiques en même temps**

### Exemple Pratique

```sql
-- Vérifier la fragmentation
SELECT
    OBJECT_NAME(object_id) AS TableName,
    index_id,
    avg_fragmentation_in_percent
FROM
    sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('MaTable'), NULL, NULL, 'DETAILED')
WHERE
    index_id > 0;

-- Si fragmentation > 30%
ALTER INDEX IX_MaTable_Colonne ON MaTable REBUILD
WITH (
    FILLFACTOR = 85,
    SORT_IN_TEMPDB = ON
);

-- Les statistiques sont déjà mises à jour automatiquement
```

## Comparaison Directe : REBUILD vs REORGANIZE

| Critère | REORGANIZE | REBUILD |
|---------|-----------|---------|
| **Niveau de fragmentation ciblé** | 10% - 30% | > 30% |
| **Efficacité de défragmentation** | Partielle | Complète (0%) |
| **Disponibilité** | Toujours en ligne | Hors ligne par défaut<br/>(En ligne avec `ONLINE = ON` en Enterprise) |
| **Consommation CPU** | Faible | Élevée |
| **Espace disque requis** | Minimal | Important (jusqu'à 2x la taille) |
| **Logs de transaction** | Modérés | Importants |
| **Mise à jour des statistiques** | Non (manuel) | Oui (automatique) |
| **Modification du Fill Factor** | Non | Oui |
| **Interruptible** | Oui | Non |
| **Vitesse (index fragmenté)** | Plus lente | Plus rapide |
| **Impact sur les utilisateurs** | Minimal | Significatif (si offline) |

## Options Importantes de REBUILD

### ONLINE = ON (Enterprise Edition uniquement)

Cette option permet de reconstruire l'index **sans bloquer l'accès** aux données :

```sql
ALTER INDEX IX_NomIndex ON MaTable REBUILD
WITH (ONLINE = ON);
```

**Comment ça fonctionne ?**
- SQL Server maintient une copie temporaire de l'ancien index
- Les utilisateurs continuent à utiliser l'ancien index pendant la reconstruction
- À la fin, SQL Server bascule rapidement vers le nouvel index
- Nécessite plus d'espace disque (deux copies de l'index temporairement)

**Limitations** :
- Disponible uniquement en **Enterprise Edition** (ou Developer Edition)
- Ne fonctionne pas avec certains types d'index (XML, Spatial)
- Plus lent qu'un rebuild offline

### SORT_IN_TEMPDB = ON

Cette option utilise la base de données `tempdb` pour les opérations de tri pendant la reconstruction :

```sql
ALTER INDEX IX_NomIndex ON MaTable REBUILD
WITH (SORT_IN_TEMPDB = ON);
```

**Avantages** :
- Réduit l'impact sur la base de données principale
- Peut être plus rapide si tempdb est sur un disque différent et plus rapide
- Libère de l'espace dans la base de données principale

**Inconvénients** :
- Nécessite plus d'espace dans tempdb
- Si tempdb est lente ou surchargée, peut ralentir l'opération

### FILLFACTOR

Définit le pourcentage de remplissage des pages après reconstruction :

```sql
ALTER INDEX IX_NomIndex ON MaTable REBUILD
WITH (FILLFACTOR = 80);
```

- **FILLFACTOR = 100** : Pages pleines, pas d'espace libre (défaut)
- **FILLFACTOR = 80** : Laisse 20% d'espace libre pour réduire les page splits futurs

**Recommandation** :
- Tables statiques ou en lecture seule : `FILLFACTOR = 100`
- Tables avec beaucoup d'insertions : `FILLFACTOR = 70-90`

## Stratégie de Maintenance Recommandée

Voici une approche pragmatique et largement adoptée :

### Règle des Seuils

```sql
-- Pseudocode de décision
IF fragmentation < 10% THEN
    -- Ne rien faire

ELSE IF fragmentation >= 10% AND fragmentation < 30% THEN
    -- REORGANIZE
    ALTER INDEX ... REORGANIZE;
    UPDATE STATISTICS ...;

ELSE IF fragmentation >= 30% THEN
    -- REBUILD
    ALTER INDEX ... REBUILD;

END IF
```

### Script de Maintenance Automatisé (Exemple Conceptuel)

```sql
-- Identifier les index fragmentés
DECLARE @TableName NVARCHAR(255);
DECLARE @IndexName NVARCHAR(255);
DECLARE @Fragmentation FLOAT;

DECLARE index_cursor CURSOR FOR
SELECT
    OBJECT_NAME(ips.object_id) AS TableName,
    i.name AS IndexName,
    ips.avg_fragmentation_in_percent AS Fragmentation
FROM
    sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'DETAILED') AS ips
INNER JOIN
    sys.indexes AS i
    ON ips.object_id = i.object_id
    AND ips.index_id = i.index_id
WHERE
    ips.index_id > 0 -- Exclure les heaps
    AND ips.page_count > 1000 -- Ignorer les petits index
    AND ips.avg_fragmentation_in_percent > 10;

OPEN index_cursor;

FETCH NEXT FROM index_cursor INTO @TableName, @IndexName, @Fragmentation;

WHILE @@FETCH_STATUS = 0
BEGIN
    IF @Fragmentation >= 30
    BEGIN
        -- REBUILD pour fragmentation élevée
        PRINT 'REBUILD: ' + @IndexName + ' sur ' + @TableName;
        EXEC('ALTER INDEX ' + @IndexName + ' ON ' + @TableName + ' REBUILD');
    END
    ELSE
    BEGIN
        -- REORGANIZE pour fragmentation modérée
        PRINT 'REORGANIZE: ' + @IndexName + ' sur ' + @TableName;
        EXEC('ALTER INDEX ' + @IndexName + ' ON ' + @TableName + ' REORGANIZE');
        EXEC('UPDATE STATISTICS ' + @TableName);
    END

    FETCH NEXT FROM index_cursor INTO @TableName, @IndexName, @Fragmentation;
END

CLOSE index_cursor;
DEALLOCATE index_cursor;
```

### Planification de la Maintenance

**Maintenance régulière (Hebdomadaire)** :
- REORGANIZE sur les index modérément fragmentés
- Peut s'exécuter pendant les heures de production (faible impact)

**Maintenance lourde (Mensuelle/Trimestrielle)** :
- REBUILD sur les index fortement fragmentés
- Planifier pendant une fenêtre de maintenance (hors heures de production)

## Considérations Importantes

### 1. Taille de l'Index

**Petits index (< 1000 pages)** :
- La fragmentation a peu d'impact
- Ne perdez pas de temps à les maintenir
- Ajoutez une clause `AND page_count > 1000` dans vos scripts

**Gros index (> 10 GB)** :
- REBUILD peut prendre des heures
- Nécessite beaucoup d'espace disque
- Planifiez soigneusement

### 2. Modèle de Récupération

Si votre base est en mode **FULL** ou **BULK_LOGGED** :
- REBUILD génère énormément de logs
- Cela peut remplir votre log de transaction
- Les sauvegardes de logs seront volumineuses
- Planifiez des sauvegardes de logs pendant/après la maintenance

### 3. Impact sur les Applications

**REORGANIZE** :
- Peut ralentir légèrement les requêtes pendant l'exécution
- Pas d'interruption de service

**REBUILD (offline)** :
- Bloque complètement l'accès à la table
- Les applications recevront des erreurs de timeout
- Nécessite une fenêtre de maintenance

**REBUILD (online - Enterprise)** :
- Impact minimal, mais peut causer des ralentissements
- Brève période de verrouillage à la fin (quelques secondes)

### 4. Fréquence de Maintenance

**Systèmes OLTP (transactionnels)** :
- Fragmentation rapide en raison des nombreuses insertions/mises à jour
- Maintenance hebdomadaire recommandée

**Systèmes OLAP/Data Warehouse** :
- Fragmentation plus lente (principalement des lectures)
- Maintenance mensuelle ou après chargements massifs

### 5. Index Columnstore

Les index **Columnstore** (optimisés pour l'analytique) ont leurs propres mécanismes :
- Utilisez `ALTER INDEX ... REORGANIZE` pour compresser les rowgroups
- REBUILD est rarement nécessaire

## Erreurs Courantes à Éviter

### ❌ Erreur 1 : Reconstruire tous les index systématiquement

**Problème** : Exécuter `ALTER INDEX ALL ... REBUILD` sur toutes les tables sans vérifier la fragmentation.

**Impact** :
- Gaspillage de ressources
- Génération inutile de logs
- Temps de maintenance prolongé

**Solution** : Vérifiez toujours la fragmentation et ne maintenez que les index qui en ont besoin.

### ❌ Erreur 2 : Oublier UPDATE STATISTICS après REORGANIZE

**Problème** : REORGANIZE ne met pas à jour les statistiques.

**Impact** :
- L'optimiseur de requêtes peut choisir de mauvais plans d'exécution
- Performances dégradées malgré la défragmentation

**Solution** : Toujours exécuter `UPDATE STATISTICS` après un REORGANIZE.

### ❌ Erreur 3 : REBUILD en production sans ONLINE = ON

**Problème** : Exécuter REBUILD offline pendant les heures de production.

**Impact** :
- Blocage complet des utilisateurs
- Erreurs d'application
- Interruption de service

**Solution** : Utilisez `ONLINE = ON` (Enterprise) ou planifiez pendant une fenêtre de maintenance.

### ❌ Erreur 4 : Ignorer la taille du log de transaction

**Problème** : REBUILD sans espace suffisant dans le log.

**Impact** :
- Échec de la maintenance
- Log plein, blocage de toutes les écritures

**Solution** : Surveillez l'espace disque et le log avant de lancer la maintenance.

### ❌ Erreur 5 : Maintenance trop fréquente sur de petits index

**Problème** : Maintenir quotidiennement de petits index (< 1000 pages).

**Impact** :
- Gaspillage de ressources
- Aucun gain de performance

**Solution** : Ignorez les petits index dans vos scripts de maintenance.

## Cas Pratique : Scénario de Décision

### Situation

Vous avez une table `Commandes` avec 50 millions de lignes et un index sur `DateCommande`.

**Données** :
- Fragmentation : 45%
- Nombre de pages : 500,000
- Remplissage moyen : 65%
- Édition SQL Server : Standard (pas d'option ONLINE)
- Fenêtre de maintenance : Dimanche 2h-6h AM

### Analyse

1. **Fragmentation > 30%** → REBUILD recommandé
2. **Index volumineux** → REBUILD sera long (plusieurs heures potentiellement)
3. **Pas d'option ONLINE** → Interruption de service nécessaire
4. **Fenêtre de maintenance disponible** → OK pour REBUILD offline

### Décision

```sql
-- Exécuter pendant la fenêtre de maintenance
ALTER INDEX IX_Commandes_DateCommande ON Commandes REBUILD
WITH (
    FILLFACTOR = 85,           -- Laisser un peu d'espace pour futures insertions
    SORT_IN_TEMPDB = ON,       -- Réduire l'impact sur la base principale
    MAXDOP = 4                 -- Limiter le parallélisme pour ne pas saturer le serveur
);
```

**Résultat attendu** :
- Fragmentation réduite à 0%
- Statistiques mises à jour
- Remplissage optimisé à 85%
- Performance des requêtes améliorée

## Monitoring de la Maintenance

### Vérifier le Progrès d'un REBUILD

Pendant l'exécution d'un REBUILD, vous pouvez surveiller la progression :

```sql
SELECT
    session_id,
    command,
    percent_complete,
    estimated_completion_time / 1000 / 60 AS minutes_restantes,
    start_time
FROM
    sys.dm_exec_requests
WHERE
    command LIKE 'ALTER INDEX%';
```

### Historique de la Fragmentation

Pour suivre l'évolution de la fragmentation dans le temps, créez une table d'audit :

```sql
CREATE TABLE IndexFragmentationHistory (
    CaptureDate DATETIME DEFAULT GETDATE(),
    TableName NVARCHAR(255),
    IndexName NVARCHAR(255),
    Fragmentation FLOAT,
    PageCount INT,
    PageDensity FLOAT
);

-- Capturer l'état actuel
INSERT INTO IndexFragmentationHistory (TableName, IndexName, Fragmentation, PageCount, PageDensity)
SELECT
    OBJECT_NAME(ips.object_id),
    i.name,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    ips.avg_page_space_used_in_percent
FROM
    sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'DETAILED') AS ips
INNER JOIN
    sys.indexes AS i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE
    ips.index_id > 0;
```

## Conclusion

La maintenance des index est un équilibre entre **performance**, **disponibilité** et **ressources** :

**REORGANIZE** est votre outil pour la maintenance quotidienne et non-invasive :
- Fragmentation modérée (10-30%)
- Toujours en ligne
- Faible impact

**REBUILD** est votre outil pour la maintenance approfondie :
- Fragmentation élevée (>30%)
- Résultat optimal (0% fragmentation)
- Impact important (sauf avec ONLINE = ON)

**Règles d'or** :
1. ✅ Mesurez toujours avant d'agir (vérifiez la fragmentation)
2. ✅ Ignorez les petits index (< 1000 pages)
3. ✅ Planifiez les REBUILD pendant les fenêtres de maintenance
4. ✅ N'oubliez pas les statistiques après REORGANIZE
5. ✅ Surveillez l'espace disque et le log de transaction

La maintenance d'index n'est pas une tâche à prendre à la légère, mais avec une bonne compréhension de ces outils, vous pouvez maintenir une base de données performante et fiable.
