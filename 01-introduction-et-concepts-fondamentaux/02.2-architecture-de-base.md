# 1.2.2 Architecture de Base : Instance, Services, Bases de données

## Introduction

Pour bien travailler avec Microsoft SQL Server, il est essentiel de comprendre comment il est organisé. L'architecture de SQL Server peut sembler complexe au premier abord, mais elle repose sur trois concepts clés que nous allons explorer : les **instances**, les **services**, et les **bases de données**.

Imaginez SQL Server comme un immeuble d'appartements : l'immeuble entier est le serveur physique, chaque appartement est une instance, les services sont les équipements (eau, électricité, chauffage), et les bases de données sont les pièces à l'intérieur de chaque appartement.

## Qu'est-ce qu'une Instance SQL Server ?

### Définition simple

Une **instance** est une installation complète et indépendante de SQL Server sur une machine (serveur physique ou virtuel).

### Analogie : Les appartements d'un immeuble

Imaginez un immeuble (votre serveur Windows ou Linux) :
- Chaque **appartement** est une instance SQL Server
- Vous pouvez avoir **plusieurs appartements** (instances) dans le même immeuble (serveur)
- Chaque appartement fonctionne de manière **indépendante**
- Chaque appartement a son propre **compteur** (processus), ses propres **meubles** (bases de données)

### Types d'instances

#### 1. Instance par défaut (Default Instance)

**Caractéristiques :**
- S'appelle simplement par le **nom du serveur**
- Il ne peut y avoir **qu'une seule** instance par défaut par serveur
- Installée en premier généralement
- Nom du service : `MSSQLSERVER`

**Exemple de connexion :**
```
Nom du serveur : SERVEUR01
```

**Analogie :** C'est comme l'appartement principal de l'immeuble, celui qui porte le numéro de l'immeuble sans complément.

#### 2. Instances nommées (Named Instances)

**Caractéristiques :**
- Portent un **nom personnalisé**
- Vous pouvez avoir **plusieurs** instances nommées sur le même serveur
- Nécessitent le format : `SERVEUR\NomInstance`
- Nom du service : `MSSQL$NomInstance`

**Exemple de connexion :**
```
Nom du serveur : SERVEUR01\PRODUCTION
Nom du serveur : SERVEUR01\DEVELOPPEMENT
Nom du serveur : SERVEUR01\TEST
```

**Analogie :** Ce sont les autres appartements de l'immeuble, chacun avec son numéro distinct (1A, 1B, 2A, etc.).

### Pourquoi utiliser plusieurs instances ?

#### Avantages de la multi-instance

1. **Isolation des environnements**
   - Instance PRODUCTION (données réelles)
   - Instance DEVELOPPEMENT (pour les développeurs)
   - Instance TEST (pour les tests)

2. **Isolation des applications**
   - Instance pour l'ERP
   - Instance pour le CRM
   - Instance pour le site web

3. **Versions différentes**
   - Instance SQL Server 2019
   - Instance SQL Server 2022
   - Sur le même serveur !

4. **Sécurité renforcée**
   - Permissions séparées par instance
   - Équipes différentes avec accès à des instances différentes

#### Inconvénients

- ❌ **Ressources partagées** : Toutes les instances se partagent CPU, RAM et disque du serveur
- ❌ **Complexité** : Plus difficile à gérer
- ❌ **Coût de licence** : Chaque instance peut nécessiter une licence séparée

## Les Services SQL Server

### Qu'est-ce qu'un service ?

Un **service** est un programme qui s'exécute en arrière-plan sur le serveur, de manière continue, sans intervention de l'utilisateur.

**Analogie :** C'est comme les équipements d'un immeuble (eau, électricité, ascenseur) qui fonctionnent en permanence pour que les appartements soient utilisables.

### Les principaux services SQL Server

SQL Server utilise plusieurs services pour fonctionner. Voici les plus importants :

#### 1. SQL Server Database Engine (Le moteur principal)

**Nom du service :**
- Instance par défaut : `MSSQLSERVER`
- Instance nommée : `MSSQL$NomInstance`

**Rôle :**
- C'est le **cœur** de SQL Server
- Gère le stockage des données
- Exécute les requêtes SQL
- Gère les transactions
- Assure la sécurité

**État :**
- Doit être **démarré** pour que SQL Server fonctionne
- Peut être configuré pour démarrer automatiquement au démarrage du serveur

**Analogie :** C'est le système d'électricité de l'appartement : sans lui, rien ne fonctionne !

#### 2. SQL Server Agent

**Nom du service :**
- Instance par défaut : `SQLSERVERAGENT`
- Instance nommée : `SQLAgent$NomInstance`

**Rôle :**
- **Planification de tâches** automatiques
- Exécution de sauvegardes programmées
- Exécution de scripts à des heures définies
- Gestion des alertes
- Envoi d'emails automatiques

**Important :**
- ⚠️ **Non disponible** dans SQL Server Express
- Disponible dans toutes les autres éditions

**Analogie :** C'est le gardien de l'immeuble qui effectue des tâches régulières (nettoyage, maintenance) selon un planning.

**Exemple d'utilisation :**
- Sauvegarder toutes les bases de données chaque nuit à 2h du matin
- Supprimer les anciennes données tous les dimanches
- Envoyer un rapport par email chaque lundi matin

#### 3. SQL Server Browser

**Nom du service :** `SQLBrowser`

**Rôle :**
- Aide les clients à **trouver les instances** SQL Server sur le réseau
- Fonctionne sur le port UDP 1434
- Particulièrement utile quand vous avez plusieurs instances

**Fonctionnement :**
```
Client : "Hé SQL Server Browser, où est l'instance SERVEUR01\PRODUCTION ?"
Browser : "Elle écoute sur le port TCP 52341"
Client : "Merci !" → Se connecte sur ce port
```

**Analogie :** C'est la réception de l'immeuble qui vous indique dans quel appartement (instance) vous devez aller.

#### 4. SQL Server Integration Services (SSIS)

**Nom du service :** `MsDtsServer` ou `MsDtsServer###` (### = version)

**Rôle :**
- **ETL** : Extract, Transform, Load (Extraire, Transformer, Charger)
- Import/Export de données
- Transformation de données entre différentes sources
- Automatisation de flux de données

**Analogie :** C'est le service de déménagement qui transfère vos affaires d'un endroit à un autre et les réorganise.

**Exemple d'utilisation :**
Importer des données depuis un fichier Excel vers SQL Server toutes les nuits.

#### 5. SQL Server Analysis Services (SSAS)

**Nom du service :** `MSSQLServerOLAPService`

**Rôle :**
- **Business Intelligence** et analyse de données
- Création de cubes OLAP
- Analyses multidimensionnelles
- Data mining

**Analogie :** C'est le département d'analyse qui transforme vos données brutes en rapports et tableaux de bord.

#### 6. SQL Server Reporting Services (SSRS)

**Nom du service :** `ReportServer` et `ReportServer$NomInstance`

**Rôle :**
- Création de **rapports** et tableaux de bord
- Génération de PDF, Excel, etc.
- Publication de rapports sur le web
- Planification de distribution de rapports

**Analogie :** C'est l'imprimerie qui crée et distribue les documents de synthèse.

### Tableau récapitulatif des services

| Service | Nom | Obligatoire ? | Disponible Express ? |
|---------|-----|---------------|----------------------|
| **Database Engine** | MSSQLSERVER | ✅ Oui | ✅ Oui |
| **SQL Server Agent** | SQLSERVERAGENT | Non | ❌ Non |
| **SQL Browser** | SQLBrowser | Non (utile) | ✅ Oui |
| **Integration Services** | MsDtsServer | Non | ✅ Oui (basique) |
| **Analysis Services** | MSSQLServerOLAPService | Non | ❌ Non |
| **Reporting Services** | ReportServer | Non | ❌ Non |

### Gestion des services

Les services peuvent être dans différents **états** :

#### États possibles
- **Démarré** (Running) : Le service fonctionne ✅
- **Arrêté** (Stopped) : Le service ne fonctionne pas ⛔
- **En pause** (Paused) : Le service est temporairement suspendu ⏸️

#### Types de démarrage
- **Automatique** : Démarre automatiquement quand le serveur démarre
- **Manuel** : Doit être démarré manuellement
- **Désactivé** : Ne peut pas être démarré

#### Comment gérer les services ?

**Sous Windows :**
1. **Services Windows** (`services.msc`)
2. **SQL Server Configuration Manager**
3. **Ligne de commande** : `net start MSSQLSERVER`

**Sous Linux :**
```bash
sudo systemctl start mssql-server
sudo systemctl stop mssql-server
sudo systemctl status mssql-server
```

## Les Bases de Données

### Qu'est-ce qu'une base de données dans SQL Server ?

Une **base de données** est un conteneur logique qui regroupe :
- Des **tables** (contenant les données)
- Des **vues** (requêtes sauvegardées)
- Des **procédures stockées** (code réutilisable)
- Des **fonctions** (calculs réutilisables)
- Des **index** (pour la performance)
- Et bien d'autres objets...

**Analogie :** C'est comme une pièce spécifique dans votre appartement (instance). La chambre, le salon, la cuisine sont des pièces différentes avec des fonctions différentes, tout comme les bases de données ont des objectifs différents.

### Types de bases de données

#### 1. Bases de données système (System Databases)

Ce sont des bases de données **créées automatiquement** par SQL Server. Elles sont **essentielles** au fonctionnement du système.

##### a) master

**Rôle :** Le cerveau de SQL Server
- Stocke toutes les informations **système** de l'instance
- Liste de toutes les bases de données
- Informations de connexion (logins)
- Configuration de l'instance

**Importance :** 🔴 **CRITIQUE**
- Si elle est corrompue, SQL Server ne démarre pas !
- À sauvegarder **très régulièrement**

##### b) model

**Rôle :** Le modèle/template
- Sert de **modèle** pour toutes les nouvelles bases de données
- Tout ce que vous mettez dans model sera copié dans chaque nouvelle base

**Exemple d'utilisation :**
Si vous ajoutez une table "Audit" dans model, toutes les nouvelles bases de données créées auront automatiquement cette table !

##### c) msdb

**Rôle :** La base des tâches automatisées
- Stocke les informations du **SQL Server Agent**
- Historique des sauvegardes
- Historique des tâches planifiées
- Alertes et jobs

**Importance :** 🟡 **Important** (surtout si vous utilisez l'Agent)

##### d) tempdb

**Rôle :** La base de données temporaire
- Stocke les **données temporaires**
- Tables temporaires (#temp)
- Variables de table
- Résultats intermédiaires de requêtes complexes

**Particularités :**
- ♻️ **Recréée à chaque redémarrage** de SQL Server
- Partagée par **toutes les bases de données**
- Ne peut pas être sauvegardée (elle est temporaire !)

**Analogie :** C'est comme un bureau ou un plan de travail temporaire qui est nettoyé chaque soir.

#### 2. Bases de données utilisateur (User Databases)

Ce sont les bases de données que **vous créez** pour vos applications.

**Exemples :**
- `GestionCommerciale` : Pour un logiciel de gestion
- `SiteWeb_Ecommerce` : Pour un site de vente en ligne
- `RH_Entreprise` : Pour gérer les employés
- `Comptabilite2024` : Pour la comptabilité

### Fichiers physiques d'une base de données

Chaque base de données est composée physiquement de **fichiers** stockés sur le disque dur :

#### 1. Fichier de données (.mdf et .ndf)

**Fichier principal (.mdf) :**
- Contient les **données** et la structure de la base
- Une base a **toujours** un fichier .mdf
- Nom par défaut : `NomBase.mdf`

**Fichiers secondaires (.ndf) :**
- Fichiers de données **supplémentaires** (optionnels)
- Permettent de répartir les données sur plusieurs disques
- Nom : `NomBase_1.ndf`, `NomBase_2.ndf`, etc.

**Contenu :**
- Tables
- Index
- Vues matérialisées
- Toutes les données utilisateur

#### 2. Fichier journal (.ldf)

**Rôle :**
- Enregistre **toutes les transactions**
- Permet la récupération en cas de panne
- Essentiel pour les sauvegardes
- Une base a **toujours** au minimum un fichier .ldf

**Nom par défaut :** `NomBase_log.ldf`

**Fonctionnement :**
Chaque modification (INSERT, UPDATE, DELETE) est d'abord écrite dans le journal, puis dans le fichier de données. En cas de crash, SQL Server peut "rejouer" le journal pour récupérer les transactions.

**Analogie :** C'est comme le journal de bord d'un navire qui enregistre tous les événements.

### Exemple de structure physique

```
Emplacement sur disque : C:\Program Files\Microsoft SQL Server\MSSQL15.MSSQLSERVER\MSSQL\DATA\

📄 GestionCommerciale.mdf        (Fichier de données - 500 Mo)
📄 GestionCommerciale_log.ldf    (Fichier journal - 100 Mo)

📄 SiteWeb_Ecommerce.mdf         (Fichier de données - 2 Go)
📄 SiteWeb_Ecommerce_log.ldf     (Fichier journal - 500 Mo)

📄 model.mdf
📄 modellog.ldf
📄 msdbdata.mdf
📄 msdblog.ldf
📄 tempdb.mdf
📄 templog.ldf
```

### Le cycle de vie d'une requête

Voyons ce qui se passe quand vous exécutez une requête SQL :

```
1. CLIENT (SSMS, Application)
   │
   │ Envoie : SELECT * FROM Clients
   ▼
2. SQL Browser (si instance nommée)
   │
   │ Indique le bon port
   ▼
3. DATABASE ENGINE (Service MSSQLSERVER)
   │
   ├─→ Vérifie la sécurité (droits d'accès)
   │
   ├─→ Parse et compile la requête
   │
   ├─→ Consulte le CACHE (déjà exécutée ?)
   │
   ├─→ Optimise la requête (meilleur plan)
   │
   ├─→ Accède aux FICHIERS (.mdf)
   │
   ├─→ Lit les données
   │
   └─→ Enregistre dans le LOG (.ldf) si modification
   │
   ▼
4. Retourne les résultats au CLIENT
```

## Scénario pratique : Une entreprise type

### Configuration d'exemple

**Serveur :** SERVPROD01 (Windows Server)

**Instance par défaut :** SERVPROD01
- Base de données : `ERP_Production`
- Base de données : `CRM_Clients`
- Base de données : `Comptabilite`

**Instance nommée :** SERVPROD01\TEST
- Base de données : `ERP_Test`
- Base de données : `CRM_Test`

**Services actifs :**
- ✅ Database Engine (les deux instances)
- ✅ SQL Server Agent (instance de production uniquement)
- ✅ SQL Browser
- ⛔ SSAS (non installé)
- ⛔ SSRS (non installé)

**Fichiers physiques (Production) :**
```
D:\SQLData\
  ├─ ERP_Production.mdf (10 Go)
  ├─ ERP_Production_log.ldf (2 Go)
  ├─ CRM_Clients.mdf (5 Go)
  ├─ CRM_Clients_log.ldf (1 Go)
  └─ ...
```

**Connexions :**
- Développeurs → `SERVPROD01\TEST`
- Applications production → `SERVPROD01`
- Outils de sauvegarde → `SERVPROD01` (toutes les bases)

## Bonnes pratiques

### Pour les instances

1. ✅ **Instance par défaut** pour la production principale
2. ✅ **Instances nommées** pour séparer les environnements (TEST, DEV)
3. ✅ **Nommage cohérent** : `SERVEUR\PROD`, `SERVEUR\TEST`, `SERVEUR\DEV`
4. ❌ Éviter trop d'instances sur un même serveur (max 3-4)

### Pour les services

1. ✅ **Database Engine** : Démarrage automatique
2. ✅ **SQL Server Agent** : Démarrage automatique (si utilisé)
3. ✅ **SQL Browser** : Démarrage automatique (si instances nommées)
4. ❌ Ne pas désactiver les services nécessaires
5. ✅ Surveiller régulièrement l'état des services

### Pour les bases de données

1. ✅ **Nommage clair** : `App_Production`, `App_Test`
2. ✅ **Séparer** les bases système et utilisateur
3. ✅ **Ne jamais modifier** directement master, model, msdb
4. ✅ **Sauvegarder régulièrement** master et msdb
5. ✅ **Surveiller** la taille de tempdb

### Pour les fichiers

1. ✅ Placer les fichiers .mdf et .ldf sur des **disques différents** (si possible)
2. ✅ Prévoir de l'**espace libre** (au moins 25% de marge)
3. ✅ **Nommer explicitement** les fichiers
4. ✅ Configurer la **croissance automatique** des fichiers
5. ❌ Ne pas placer les fichiers sur le disque système (C:\)

## Résumé

### Les trois piliers de l'architecture SQL Server

| Concept | Définition | Analogie |
|---------|------------|----------|
| **Instance** | Installation complète de SQL Server | Appartement dans un immeuble |
| **Services** | Programmes en arrière-plan | Équipements (eau, électricité) |
| **Base de données** | Conteneur de données et objets | Pièce dans l'appartement |

### Points clés à retenir

1. **Instance**
   - Une instance = une installation SQL Server
   - Instance par défaut : `SERVEUR`
   - Instance nommée : `SERVEUR\NomInstance`
   - Plusieurs instances possibles sur un serveur

2. **Services principaux**
   - **Database Engine** : Le cœur (obligatoire)
   - **SQL Server Agent** : Automatisation (recommandé en production)
   - **SQL Browser** : Navigation entre instances (utile)

3. **Bases de données**
   - **Système** : master, model, msdb, tempdb (créées automatiquement)
   - **Utilisateur** : Vos bases créées pour vos applications
   - Chaque base = fichiers .mdf (données) + .ldf (journal)

4. **Hiérarchie**
   ```
   Serveur
    └─ Instance(s)
        └─ Services
            └─ Base(s) de données
                └─ Tables, Vues, Procédures...
                    └─ Fichiers physiques (.mdf, .ldf)
   ```

### Commandes utiles à connaître

Pour voir les bases de données d'une instance :
```sql
SELECT name FROM sys.databases;
```

Pour voir les informations sur les fichiers :
```sql
SELECT name, physical_name, size/128 AS Size_MB
FROM sys.master_files;
```
