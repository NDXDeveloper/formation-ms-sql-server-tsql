# 2.1.4 Autres types (BIT, UNIQUEIDENTIFIER, etc.)

## Introduction

Au-delà des types numériques, de chaînes et de dates que nous avons vus, SQL Server propose d'autres types de données spécialisés pour des besoins spécifiques. Ces types permettent de stocker des valeurs booléennes, des identifiants uniques globaux, des données binaires, et bien plus encore.

Dans cette section, nous allons découvrir ces types particuliers et comprendre quand et comment les utiliser efficacement.

---

## 1. BIT : Le type booléen

### Qu'est-ce que BIT ?

Le type **BIT** est utilisé pour stocker des valeurs booléennes (vrai/faux, oui/non, 1/0). C'est l'équivalent en SQL Server du type boolean d'autres langages de programmation.

**Syntaxe :** `BIT`

**Caractéristiques :**
- **Valeurs possibles** : 0, 1, ou NULL
- **Interprétation** : 0 = Faux, 1 = Vrai
- **Stockage** : 1 bit (mais SQL Server optimise en regroupant jusqu'à 8 colonnes BIT dans 1 octet)
- **Usage** : drapeaux, indicateurs, états binaires

### Comment fonctionne BIT ?

```sql
CREATE TABLE Utilisateurs (
    UtilisateurID INT,
    Nom NVARCHAR(100),
    Email VARCHAR(255),
    EstActif BIT,                   -- Compte actif ou non
    EstAdministrateur BIT,          -- Est-ce un admin ?
    NewsletterOptIn BIT,            -- A accepté la newsletter
    EmailVerifie BIT                -- Email vérifié ou non
);
```

### Insertion de valeurs BIT

SQL Server accepte plusieurs formats pour insérer des valeurs BIT :

```sql
-- Méthode 1 : Utiliser 0 et 1 (recommandé)
INSERT INTO Utilisateurs (UtilisateurID, Nom, EstActif, EstAdministrateur)
VALUES (1, N'Marie Dupont', 1, 0);  -- Actif, pas admin

-- Méthode 2 : Utiliser les chaînes 'true'/'false' (converties automatiquement en 1/0)
INSERT INTO Utilisateurs (UtilisateurID, Nom, EstActif, EstAdministrateur)
VALUES (2, N'Julie Leroux', 'true', 'false');

-- NULL est également valide (BIT a trois états : 0, 1, NULL)
INSERT INTO Utilisateurs (UtilisateurID, Nom, EstActif, EstAdministrateur)
VALUES (3, N'Luc Petit', 1, NULL);
```

> ⚠️ **Attention** — Contrairement à d'autres SGBD (PostgreSQL, MySQL…), T-SQL **ne possède pas** de littéraux booléens `TRUE`/`FALSE`. Écrire `VALUES (..., TRUE, FALSE)` **sans guillemets** provoque une **erreur**. Utilisez `1`/`0` (recommandé), ou éventuellement les chaînes `'true'`/`'false'`, automatiquement converties.

### Utilisation dans les requêtes

```sql
-- Rechercher tous les utilisateurs actifs
SELECT * FROM Utilisateurs
WHERE EstActif = 1;

-- Rechercher les administrateurs
SELECT * FROM Utilisateurs
WHERE EstAdministrateur = 1;

-- Rechercher les utilisateurs actifs qui ne sont pas admins
SELECT * FROM Utilisateurs
WHERE EstActif = 1 AND EstAdministrateur = 0;

-- Compter les utilisateurs par statut
SELECT
    EstActif,
    COUNT(*) AS NombreUtilisateurs
FROM Utilisateurs
GROUP BY EstActif;
```

### Exemples pratiques avec BIT

**Exemple 1 : Gestion de produits e-commerce**

```sql
CREATE TABLE Produits (
    ProduitID INT,
    Nom NVARCHAR(200),
    Prix DECIMAL(10, 2),
    EnStock BIT,                    -- Disponible ou non
    EstNouveaute BIT,               -- Nouveau produit
    EstPromotion BIT,               -- En promotion
    EstVisible BIT,                 -- Visible sur le site
    LivraisonGratuite BIT           -- Livraison gratuite
);

INSERT INTO Produits
VALUES
    (1, N'Ordinateur portable', 899.99, 1, 1, 0, 1, 1),
    (2, N'Souris sans fil', 29.99, 1, 0, 1, 1, 0),
    (3, N'Clavier mécanique', 149.99, 0, 0, 0, 1, 0);

-- Trouver les nouveautés disponibles
SELECT * FROM Produits
WHERE EstNouveaute = 1 AND EnStock = 1;

-- Trouver les produits en promotion avec livraison gratuite
SELECT * FROM Produits
WHERE EstPromotion = 1 AND LivraisonGratuite = 1;
```

**Exemple 2 : Paramètres utilisateur**

```sql
CREATE TABLE ParametresUtilisateur (
    UtilisateurID INT,
    NotificationsEmail BIT DEFAULT 1,
    NotificationsSMS BIT DEFAULT 0,
    ProfilPublic BIT DEFAULT 0,
    PartagerLocalisation BIT DEFAULT 0,
    ModeNocturne BIT DEFAULT 0
);

-- Insertion avec valeurs par défaut
INSERT INTO ParametresUtilisateur (UtilisateurID)
VALUES (1);

-- Modification des paramètres
UPDATE ParametresUtilisateur
SET NotificationsEmail = 0, ModeNocturne = 1
WHERE UtilisateurID = 1;
```

### Optimisation du stockage avec BIT

**Information importante sur le stockage :**

```sql
-- SQL Server optimise automatiquement le stockage des colonnes BIT
-- Jusqu'à 8 colonnes BIT dans une table sont stockées dans 1 seul octet

CREATE TABLE OptimisationBit (
    Col1 BIT,  -- \
    Col2 BIT,  --  |
    Col3 BIT,  --  |
    Col4 BIT,  --  |-- Ces 8 colonnes occupent 1 octet
    Col5 BIT,  --  |
    Col6 BIT,  --  |
    Col7 BIT,  --  |
    Col8 BIT,  -- /
    Col9 BIT   -- Cette colonne commencera un nouvel octet
);
```

### BIT et logique ternaire (NULL)

```sql
-- BIT peut avoir trois états : 0, 1, ou NULL
CREATE TABLE Test (
    ID INT,
    Condition BIT
);

INSERT INTO Test VALUES (1, 1), (2, 0), (3, NULL);

-- Recherche avec NULL
SELECT * FROM Test WHERE Condition IS NULL;

-- Attention : NULL n'est ni vrai ni faux
SELECT * FROM Test WHERE Condition = 1;     -- Trouve seulement ID = 1
SELECT * FROM Test WHERE Condition = 0;     -- Trouve seulement ID = 2
SELECT * FROM Test WHERE Condition IS NULL; -- Trouve seulement ID = 3

-- Pour inclure NULL comme "faux"
SELECT * FROM Test WHERE Condition = 0 OR Condition IS NULL;
```

## 2. UNIQUEIDENTIFIER : Les identifiants uniques globaux (GUID)

### Qu'est-ce qu'un UNIQUEIDENTIFIER ?

Le type **UNIQUEIDENTIFIER** stocke un GUID (Globally Unique Identifier), un identifiant unique de 128 bits garantissant l'unicité à l'échelle globale.

**Syntaxe :** `UNIQUEIDENTIFIER`

**Caractéristiques :**
- **Format** : 32 caractères hexadécimaux groupés (ex: '6F9619FF-8B86-D011-B42D-00C04FC964FF')
- **Taille** : 16 octets
- **Unicité** : Quasi-certitude d'unicité globale (probabilité de collision infinitésimale)
- **Génération** : Fonction NEWID() ou NEWSEQUENTIALID()

### Format d'un GUID

Un GUID ressemble à ceci :
```
6F9619FF-8B86-D011-B42D-00C04FC964FF
│      │ │  │ │  │ │  │ │          │
└──────┴─┴──┴─┴──┴─┴──┴─┴──────────┘
  8-4-4-4-12 caractères hexadécimaux
```

### Quand utiliser UNIQUEIDENTIFIER ?

**UNIQUEIDENTIFIER est idéal pour :**
- ✅ Systèmes distribués (plusieurs bases de données)
- ✅ Réplication de données entre serveurs
- ✅ Identifiants devant être générés côté client
- ✅ Intégration avec des systèmes externes
- ✅ APIs publiques (masquer les IDs séquentiels)
- ✅ Besoin d'unicité absolue sans coordination centrale

**UNIQUEIDENTIFIER n'est PAS recommandé pour :**
- ❌ Tables avec des millions de lignes (performance)
- ❌ Clés primaires de tables très sollicitées (fragmentation)
- ❌ Systèmes simples mono-serveur (INT suffit)

### Création et utilisation de base

```sql
-- Création d'une table avec UNIQUEIDENTIFIER
CREATE TABLE Commandes (
    CommandeID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    ClientID INT,
    DateCommande DATETIME2(3),
    MontantTotal DECIMAL(10, 2)
);

-- Insertion automatique avec NEWID()
INSERT INTO Commandes (ClientID, DateCommande, MontantTotal)
VALUES (100, SYSDATETIME(), 159.99);
-- Le CommandeID est généré automatiquement

-- Insertion manuelle avec une valeur explicite
INSERT INTO Commandes (CommandeID, ClientID, DateCommande, MontantTotal)
VALUES ('A0B1C2D3-E4F5-6789-ABCD-EF0123456789', 101, SYSDATETIME(), 89.50);

-- Génération d'un nouveau GUID
SELECT NEWID() AS NouveauGUID;
-- Résultat : 6F9619FF-8B86-D011-B42D-00C04FC964FF (unique à chaque exécution)
```

### NEWID() vs NEWSEQUENTIALID()

```sql
-- NEWID() : GUID complètement aléatoire
CREATE TABLE TableNewID (
    ID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    Nom NVARCHAR(100)
);

-- NEWSEQUENTIALID() : GUID séquentiel (meilleure performance pour l'indexation)
CREATE TABLE TableNewSequentialID (
    ID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWSEQUENTIALID(),
    Nom NVARCHAR(100)
);

-- ⚠️ NEWSEQUENTIALID() ne peut être utilisé que comme DEFAULT
-- ✅ Correct
CREATE TABLE Test1 (ID UNIQUEIDENTIFIER DEFAULT NEWSEQUENTIALID());

-- ❌ Incorrect (générera une erreur)
-- SELECT NEWSEQUENTIALID();  -- Ne peut pas être utilisé dans un SELECT
```

**Différences clés :**

| Aspect | NEWID() | NEWSEQUENTIALID() |
|--------|---------|-------------------|
| **Valeurs** | Complètement aléatoires | Séquentielles (croissantes) |
| **Performance insert** | Plus lente (fragmentation) | Plus rapide |
| **Fragmentation index** | Élevée | Faible |
| **Prédictibilité** | Imprévisible | Partiellement prévisible |
| **Utilisation** | Partout | Uniquement comme DEFAULT |

### Exemples pratiques avec UNIQUEIDENTIFIER

**Exemple 1 : Système de tickets**

```sql
CREATE TABLE Tickets (
    TicketID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    NumeroTicket AS CAST(TicketID AS VARCHAR(36)),  -- Version texte pour affichage
    ClientID INT,
    Sujet NVARCHAR(200),
    Statut NVARCHAR(50),
    DateCreation DATETIME2(3) DEFAULT SYSDATETIME()
);

INSERT INTO Tickets (ClientID, Sujet, Statut)
VALUES (100, N'Problème de connexion', N'Ouvert');

-- Récupérer un ticket par son GUID
DECLARE @ticketID UNIQUEIDENTIFIER = 'A0B1C2D3-E4F5-6789-ABCD-EF0123456789';
SELECT * FROM Tickets WHERE TicketID = @ticketID;
```

**Exemple 2 : Liens de réinitialisation de mot de passe**

```sql
CREATE TABLE TokensReset (
    TokenID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    UtilisateurID INT,
    DateCreation DATETIME2(3) DEFAULT SYSDATETIME(),
    DateExpiration DATETIME2(3),
    EstUtilise BIT DEFAULT 0
);

-- Générer un token pour un utilisateur
INSERT INTO TokensReset (UtilisateurID, DateExpiration)
VALUES (42, DATEADD(HOUR, 24, SYSDATETIME()));

-- Récupérer le token généré
SELECT TOP 1 TokenID FROM TokensReset
WHERE UtilisateurID = 42 AND EstUtilise = 0
ORDER BY DateCreation DESC;
-- Résultat : 8E2F5B3A-1C4D-7E9F-A2B5-C6D8E9F0A1B2
-- Ce GUID peut être envoyé dans un email comme lien de reset
```

**Exemple 3 : Système multi-tenant**

```sql
-- Tables pour plusieurs clients avec garantie d'unicité globale
CREATE TABLE Organisations (
    OrganisationID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    Nom NVARCHAR(200),
    DateCreation DATETIME2(3)
);

CREATE TABLE UtilisateursOrganisation (
    UtilisateurID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    OrganisationID UNIQUEIDENTIFIER,
    Email VARCHAR(255),
    Nom NVARCHAR(100)
);

-- Avantage : les IDs sont uniques même si plusieurs organisations
-- ont des utilisateurs créés simultanément sur différents serveurs
```

### Conversion et manipulation de GUID

```sql
-- Conversion UNIQUEIDENTIFIER vers VARCHAR
DECLARE @guid UNIQUEIDENTIFIER = NEWID();
SELECT CAST(@guid AS VARCHAR(36)) AS GUIDTexte;
-- Résultat : '6F9619FF-8B86-D011-B42D-00C04FC964FF'

-- Conversion VARCHAR vers UNIQUEIDENTIFIER
DECLARE @texte VARCHAR(36) = '6F9619FF-8B86-D011-B42D-00C04FC964FF';
DECLARE @guidFromTexte UNIQUEIDENTIFIER = CAST(@texte AS UNIQUEIDENTIFIER);
SELECT @guidFromTexte AS GUID;

-- Validation d'un GUID (vérifier le format)
-- Utiliser TRY_CAST pour éviter les erreurs
DECLARE @texteInvalide VARCHAR(36) = 'pas-un-guid';
SELECT TRY_CAST(@texteInvalide AS UNIQUEIDENTIFIER) AS Resultat;
-- Résultat : NULL si invalide
```

## 3. MONEY et SMALLMONEY : Types monétaires

### Qu'est-ce que MONEY ?

Les types **MONEY** et **SMALLMONEY** sont des types spécialisés pour stocker des valeurs monétaires avec une précision fixe.

**Caractéristiques :**

| Type | Plage | Précision | Taille |
|------|-------|-----------|--------|
| **SMALLMONEY** | -214,748.3648 à 214,748.3647 | 4 décimales | 4 octets |
| **MONEY** | ±922,337,203,685,477.5807 | 4 décimales | 8 octets |

### Utilisation de MONEY

```sql
CREATE TABLE Transactions (
    TransactionID INT,
    Montant MONEY,
    Description NVARCHAR(200)
);

-- Insertion avec le symbole monétaire (optionnel)
INSERT INTO Transactions VALUES (1, $99.99, N'Achat produit');
INSERT INTO Transactions VALUES (2, 149.50, N'Remboursement');
INSERT INTO Transactions VALUES (3, -25.00, N'Frais');

-- Calculs avec MONEY
DECLARE @prix MONEY = $199.99;
DECLARE @reduction MONEY = $20.00;
SELECT @prix - @reduction AS PrixFinal;  -- 179.99
```

### MONEY vs DECIMAL : Que choisir ?

**⚠️ Important : DECIMAL est généralement préféré à MONEY**

```sql
-- ❌ Problème avec MONEY : arrondi lors des divisions
DECLARE @montantMoney MONEY = 10.00;
SELECT @montantMoney / 3;  -- Résultat : 3.3333 (arrondi)

-- ✅ DECIMAL maintient la précision
DECLARE @montantDecimal DECIMAL(10, 4) = 10.00;
SELECT @montantDecimal / 3;  -- Résultat : 3.3333 (mais plus précis)
```

**Recommandation moderne :** Utilisez **DECIMAL(18, 2)** ou **DECIMAL(19, 4)** pour les montants monétaires plutôt que MONEY.

## 4. BINARY et VARBINARY : Données binaires

### Qu'est-ce que BINARY et VARBINARY ?

Les types **BINARY** et **VARBINARY** stockent des données binaires brutes (octets).

**Syntaxe :**
- `BINARY(n)` : longueur fixe (n octets)
- `VARBINARY(n)` : longueur variable (jusqu'à n octets)
- `VARBINARY(MAX)` : jusqu'à 2 Go

**Caractéristiques :**
- **Stockage** : octets bruts (non interprétés)
- **Affichage** : format hexadécimal (0x...)
- **Usage** : fichiers, images, données chiffrées, hash, etc.

### Quand utiliser BINARY/VARBINARY ?

**Cas d'usage courants :**
- ✅ Hash de mots de passe (SHA-256, etc.)
- ✅ Signatures numériques
- ✅ Données chiffrées
- ✅ Petits fichiers (icônes, miniatures)
- ✅ Jetons de sécurité (tokens)

**À éviter :**
- ❌ Stockage de gros fichiers (utilisez plutôt le système de fichiers)
- ❌ Images volumineuses (impact sur les performances)

### Exemples pratiques avec VARBINARY

**Exemple 1 : Stockage de hash de mots de passe**

```sql
CREATE TABLE CompteUtilisateur (
    UtilisateurID INT PRIMARY KEY,
    NomUtilisateur VARCHAR(50),
    MotDePasseHash VARBINARY(64),  -- SHA-256 = 32 octets, mais on prévoit plus
    Sel VARBINARY(32),              -- Salt pour le hash
    DateCreation DATETIME2(3)
);

-- Insertion d'un hash (simulé ici, en pratique utilisez une fonction de hash)
INSERT INTO CompteUtilisateur (UtilisateurID, NomUtilisateur, MotDePasseHash, Sel)
VALUES (1, 'marie.dupont', 0x5E884898DA28047151D0E56F8DC62927, 0x1234567890ABCDEF);

-- Le hash est stocké en binaire pour optimiser l'espace et la comparaison
```

**Exemple 2 : Stockage d'images miniatures**

```sql
CREATE TABLE ProfilUtilisateur (
    UtilisateurID INT PRIMARY KEY,
    Nom NVARCHAR(100),
    PhotoMiniature VARBINARY(MAX),  -- Image en format binaire
    TypeMIME VARCHAR(50)             -- 'image/jpeg', 'image/png', etc.
);

-- Note : en pratique, pour de grosses images,
-- stockez plutôt le chemin du fichier, pas le fichier lui-même
```

**Exemple 3 : Jetons de session**

```sql
CREATE TABLE Sessions (
    SessionID UNIQUEIDENTIFIER PRIMARY KEY,
    UtilisateurID INT,
    JetonSecurite VARBINARY(256),   -- Jeton cryptographique
    DateCreation DATETIME2(3),
    DateExpiration DATETIME2(3)
);

-- Génération d'un jeton aléatoire
DECLARE @jeton VARBINARY(256) = CRYPT_GEN_RANDOM(256);
INSERT INTO Sessions (SessionID, UtilisateurID, JetonSecurite, DateCreation, DateExpiration)
VALUES (NEWID(), 42, @jeton, SYSDATETIME(), DATEADD(HOUR, 24, SYSDATETIME()));
```

### Fonctions utiles avec BINARY

```sql
-- Conversion texte vers binaire
SELECT CAST('Hello' AS VARBINARY(10));
-- Résultat : 0x48656C6C6F

-- Conversion binaire vers texte
DECLARE @binaire VARBINARY(10) = 0x48656C6C6F;
SELECT CAST(@binaire AS VARCHAR(10));
-- Résultat : 'Hello'

-- Génération d'octets aléatoires
SELECT CRYPT_GEN_RANDOM(16) AS OctetsAleatoires;
-- Résultat : 0x8E2F5B3A1C4D7E9FA2B5C6D8E9F0A1B2

-- Fonction de hash
SELECT HASHBYTES('SHA2_256', 'MonMotDePasse') AS Hash;
-- Résultat : 0x... (32 octets)
```

## 5. XML : Le type de données XML

### Qu'est-ce que le type XML ?

SQL Server possède un type de données natif **XML** pour stocker et manipuler des documents XML structurés.

**Syntaxe :** `XML`

**Caractéristiques :**
- **Stockage** : jusqu'à 2 Go
- **Validation** : optionnelle avec des schémas XML
- **Requêtes** : support XQuery natif
- **Indexation** : possibilité d'index XML

### Utilisation de base du type XML

```sql
CREATE TABLE DocumentsXML (
    DocumentID INT PRIMARY KEY,
    Titre NVARCHAR(200),
    Contenu XML
);

-- Insertion de données XML
INSERT INTO DocumentsXML (DocumentID, Titre, Contenu)
VALUES (1, N'Configuration serveur',
    '<configuration>
        <serveur>localhost</serveur>
        <port>1433</port>
        <database>MaBase</database>
    </configuration>');

-- Requête XQuery sur le XML
SELECT
    DocumentID,
    Titre,
    Contenu.value('(/configuration/serveur)[1]', 'VARCHAR(50)') AS Serveur,
    Contenu.value('(/configuration/port)[1]', 'INT') AS Port
FROM DocumentsXML;
```

### Exemples pratiques avec XML

**Exemple 1 : Stockage de configurations**

```sql
CREATE TABLE ConfigurationsApp (
    ApplicationID INT,
    NomApplication NVARCHAR(100),
    Parametres XML
);

INSERT INTO ConfigurationsApp VALUES
(1, N'MonApp',
'<parametres>
    <connection timeout="30" retry="3"/>
    <logging level="INFO" destination="file"/>
    <cache enabled="true" duration="3600"/>
</parametres>');

-- Extraire une valeur spécifique
SELECT
    NomApplication,
    Parametres.value('(/parametres/connection/@timeout)[1]', 'INT') AS Timeout
FROM ConfigurationsApp;
```

**Exemple 2 : Historique de modifications (audit)**

```sql
CREATE TABLE AuditChangements (
    AuditID INT PRIMARY KEY,
    TableName NVARCHAR(100),
    DateModification DATETIME2(3),
    AnciennesValeurs XML,
    NouvellesValeurs XML
);

-- Stocker les changements en XML pour flexibilité
INSERT INTO AuditChangements VALUES
(1, 'Clients', SYSDATETIME(),
    '<client><nom>Ancien Nom</nom><email>ancien@email.com</email></client>',
    '<client><nom>Nouveau Nom</nom><email>nouveau@email.com</email></client>'
);
```

## 6. Autres types spécialisés

### GEOGRAPHY et GEOMETRY : Données spatiales

Types pour stocker des coordonnées géographiques et des formes géométriques.

```sql
-- Type GEOGRAPHY pour des coordonnées géographiques réelles
CREATE TABLE Lieux (
    LieuID INT,
    Nom NVARCHAR(100),
    Position GEOGRAPHY
);

-- Insertion d'un point (latitude, longitude)
INSERT INTO Lieux (LieuID, Nom, Position)
VALUES (1, N'Tour Eiffel',
    GEOGRAPHY::Point(48.8584, 2.2945, 4326)); -- 4326 = WGS 84

-- Calcul de distance entre deux points
DECLARE @tourEiffel GEOGRAPHY = GEOGRAPHY::Point(48.8584, 2.2945, 4326);
DECLARE @louvre GEOGRAPHY = GEOGRAPHY::Point(48.8606, 2.3376, 4326);

SELECT @tourEiffel.STDistance(@louvre) AS DistanceMetres;
-- Résultat : distance en mètres
```

### HIERARCHYID : Données hiérarchiques

Type spécialisé pour représenter des structures en arbre (organigrammes, catégories, etc.).

```sql
CREATE TABLE Employes (
    EmployeID INT,
    Nom NVARCHAR(100),
    Position HIERARCHYID,  -- Position dans la hiérarchie
    Niveau AS Position.GetLevel()  -- Niveau calculé
);

-- Insertion avec hiérarchie
INSERT INTO Employes (EmployeID, Nom, Position)
VALUES
    (1, N'PDG', HIERARCHYID::GetRoot()),
    (2, N'Directeur RH', HIERARCHYID::Parse('/1/')),
    (3, N'Manager RH', HIERARCHYID::Parse('/1/1/'));

-- Requête : trouver tous les subordonnés d'un manager
DECLARE @manager HIERARCHYID = HIERARCHYID::Parse('/1/');
SELECT * FROM Employes
WHERE Position.IsDescendantOf(@manager) = 1;
```

### SQL_VARIANT : Type polymorphe

Type pouvant contenir n'importe quel autre type de données (sauf quelques exceptions).

```sql
CREATE TABLE ParametresDynamiques (
    CleParametre NVARCHAR(50),
    ValeurParametre SQL_VARIANT  -- Peut être INT, VARCHAR, DATE, etc.
);

INSERT INTO ParametresDynamiques VALUES
    ('MaxConnexions', 100),              -- INT
    ('NomServeur', 'localhost'),         -- VARCHAR
    ('DateMaintenance', '2024-12-25'),   -- DATE
    ('TauxCommission', 0.05);            -- DECIMAL

-- Récupérer le type de la valeur
SELECT
    CleParametre,
    ValeurParametre,
    SQL_VARIANT_PROPERTY(ValeurParametre, 'BaseType') AS TypeDonnees
FROM ParametresDynamiques;
```

## 8. Guide de choix rapide

### Décisions de type par cas d'usage

**Pour des drapeaux/indicateurs :**
```sql
EstActif BIT                    -- ✅ Oui/Non
```

**Pour des identifiants uniques :**
```sql
-- Système simple, mono-serveur
ProduitID INT                   -- ✅ Simple et performant

-- Système distribué, réplication
ProduitID UNIQUEIDENTIFIER      -- ✅ Unicité garantie
```

**Pour des montants monétaires :**
```sql
Prix DECIMAL(18, 2)             -- ✅ Recommandé (précision exacte)
Prix MONEY                      -- ⚠️ Acceptable (mais DECIMAL préférable)
```

**Pour des fichiers/images :**
```sql
-- Petits fichiers (<1 Mo)
Miniature VARBINARY(MAX)        -- ✅ OK en base

-- Gros fichiers (>1 Mo)
CheminFichier VARCHAR(500)      -- ✅ Stocker le chemin, pas le fichier
```

**Pour des données structurées flexibles :**
```sql
Configuration XML               -- ✅ Structure XML
-- ou
Configuration NVARCHAR(MAX)     -- ✅ Stocker du JSON en texte (SQL Server 2022)
```

> 🔎 **JSON natif (SQL Server 2025 / Azure SQL)** — Jusqu'à SQL Server 2022, le JSON se stocke dans une colonne `NVARCHAR(MAX)`, manipulée avec les fonctions `JSON_VALUE`, `JSON_QUERY`, `OPENJSON`, etc. Les versions récentes (Azure SQL Database et SQL Server 2025) ajoutent un **type `json` natif**, qui valide et stocke le document de façon optimisée. Sur SQL Server 2022, retenez la règle : **JSON = `NVARCHAR(MAX)` + fonctions `JSON_*`**.

## 9. Bonnes pratiques

### Utilisation de BIT

```sql
-- ✅ Nommage clair pour les colonnes BIT
CREATE TABLE Produits (
    EstDisponible BIT,          -- Clair : indique un état
    EstPromotion BIT,
    AStockAlerteActive BIT
);

-- ❌ Nommage ambigu
CREATE TABLE Produits (
    Disponible BIT,             -- Moins clair
    Promotion BIT
);

-- ✅ Valeurs par défaut utiles
CREATE TABLE Utilisateurs (
    EstActif BIT DEFAULT 1,     -- Actif par défaut
    EstVerifie BIT DEFAULT 0    -- Non vérifié par défaut
);
```

### Utilisation de UNIQUEIDENTIFIER

```sql
-- ✅ Pour les APIs et systèmes distribués
CREATE TABLE Ressources (
    RessourceID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWSEQUENTIALID(),
    Nom NVARCHAR(200)
);

-- ❌ Éviter pour les tables volumineuses à forte écriture
-- (fragmentation et taille d'index importants)

-- ✅ Utiliser un index clustering sur une autre colonne
CREATE TABLE GrandeTable (
    ID INT IDENTITY(1,1) PRIMARY KEY,  -- Clé primaire clustering
    GUID UNIQUEIDENTIFIER DEFAULT NEWID() UNIQUE,  -- Index non-clustering
    Donnees NVARCHAR(MAX)
);
```

### Utilisation de VARBINARY

```sql
-- ✅ Pour les hash et données cryptographiques
CREATE TABLE Securite (
    MotDePasseHash VARBINARY(64),   -- SHA-256 ou SHA-512
    Sel VARBINARY(32)
);

-- ⚠️ Attention : ne pas stocker de gros fichiers
-- Pour les fichiers > 1 Mo, stockez sur le système de fichiers

-- ✅ Alternative pour gros fichiers
CREATE TABLE Documents (
    DocumentID INT,
    NomFichier NVARCHAR(255),
    CheminStockage VARCHAR(500),    -- Chemin vers le fichier
    TailleMo DECIMAL(10, 2)
);
```

## 10. Pièges courants à éviter

### Piège 1 : Confusion avec BIT et NULL

```sql
-- ⚠️ BIT accepte NULL, attention dans les comparaisons
CREATE TABLE Test (Active BIT);
INSERT INTO Test VALUES (NULL);

-- ❌ Ceci ne trouvera PAS la ligne NULL
SELECT * FROM Test WHERE Active = 0;

-- ✅ Pour inclure NULL
SELECT * FROM Test WHERE Active = 0 OR Active IS NULL;
-- ou
SELECT * FROM Test WHERE ISNULL(Active, 0) = 0;
```

### Piège 2 : Performance avec UNIQUEIDENTIFIER en clé primaire

```sql
-- ❌ Mauvaise performance pour grosses tables
CREATE TABLE MauvaisPerf (
    ID UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),  -- Fragmentation !
    Donnees NVARCHAR(100)
);

-- ✅ Meilleure approche
CREATE TABLE BonnePerf (
    ID INT IDENTITY PRIMARY KEY,  -- Clé primaire clustering performante
    GUID UNIQUEIDENTIFIER DEFAULT NEWID() UNIQUE,  -- GUID en index secondaire
    Donnees NVARCHAR(100)
);
```

### Piège 3 : Stockage excessif en VARBINARY

```sql
-- ❌ Stocker de gros fichiers en base (mauvaise idée)
CREATE TABLE Photos (
    PhotoID INT,
    ImageComplete VARBINARY(MAX)  -- Peut atteindre 2 Go !
);
-- Problème : base de données volumineuse, sauvegardes lentes, performances dégradées

-- ✅ Stocker uniquement les miniatures + chemin
CREATE TABLE Photos (
    PhotoID INT,
    Miniature VARBINARY(MAX),        -- Petite image (< 100 Ko)
    CheminFichierOriginal VARCHAR(500),  -- Chemin vers le stockage
    NomFichier NVARCHAR(255)
);
```

### Piège 4 : Conversion MONEY dans les calculs

```sql
-- ⚠️ MONEY peut avoir des arrondis inattendus
DECLARE @montant MONEY = 100.00;
DECLARE @resultat MONEY = @montant / 3 * 3;
SELECT @resultat;  -- Peut ne pas être exactement 100.00

-- ✅ Préférer DECIMAL pour les calculs précis
DECLARE @montantDecimal DECIMAL(18, 4) = 100.00;
DECLARE @resultatDecimal DECIMAL(18, 4) = @montantDecimal / 3 * 3;
SELECT @resultatDecimal;  -- Plus précis
```

## Points clés à retenir

✅ **BIT** : pour tous les drapeaux et indicateurs booléens (EstActif, EstVisible, etc.)

✅ **UNIQUEIDENTIFIER** : pour les systèmes distribués et les identifiants publics d'API

✅ **DECIMAL** plutôt que MONEY : pour les montants monétaires (meilleure précision)

✅ **VARBINARY** : pour les hash, tokens, petits fichiers binaires (< 1 Mo)

✅ **XML** : pour les données structurées flexibles et les configurations

✅ Types spécialisés (GEOGRAPHY, HIERARCHYID) : pour des besoins spécifiques

❌ **Évitez** UNIQUEIDENTIFIER comme clé primaire clustering sur de grosses tables

❌ **Évitez** de stocker de gros fichiers en VARBINARY (utilisez le système de fichiers)

❌ **Évitez** MONEY pour des calculs financiers complexes (préférez DECIMAL)

---

## Conclusion

SQL Server offre une riche variété de types de données spécialisés :

- **BIT** pour les valeurs booléennes simples et efficaces
- **UNIQUEIDENTIFIER** pour l'unicité globale dans les systèmes distribués
- **VARBINARY** pour les données binaires et cryptographiques
- **XML** pour les structures flexibles
- Types spécialisés (GEOGRAPHY, HIERARCHYID) pour des besoins avancés

**En pratique :**
- Utilisez BIT généreusement pour tous vos indicateurs
- Réservez UNIQUEIDENTIFIER aux cas où l'unicité globale est nécessaire
- Préférez DECIMAL à MONEY pour les montants
- Stockez les gros fichiers sur le système de fichiers, pas en base
- Choisissez le type le plus spécifique pour votre besoin

Avec ces connaissances, vous êtes maintenant capable de choisir le type de données le plus approprié pour chaque situation spécifique dans vos bases de données SQL Server !
