# 7.1.4 Index Uniques

## Introduction

Nous avons vu dans les sections précédentes :
- Pourquoi utiliser des index (7.1.1)
- Les index clustered qui déterminent l'ordre physique (7.1.2)
- Les index non-clustered qui sont des structures séparées (7.1.3)

Maintenant, découvrons les **index uniques** (unique indexes), qui ajoutent une garantie supplémentaire : **l'unicité des valeurs**.

## Qu'est-ce qu'un Index Unique ?

### Définition

Un **index unique** est un index (clustered ou non-clustered) qui garantit que **toutes les valeurs** de la colonne indexée sont **différentes** (uniques).

**Caractéristiques** :
- ✅ Empêche les doublons
- ✅ Accélère les recherches (comme un index normal)
- ✅ Garantit l'intégrité des données
- ✅ Peut être clustered ou non-clustered

### L'analogie du répertoire téléphonique

Imaginez deux types de répertoires :

**Répertoire classique (index non-unique)** :
- Plusieurs personnes peuvent avoir le même nom "Dupont"
- Le nom n'est pas unique
- Vous pouvez chercher rapidement par nom, mais il peut y avoir plusieurs résultats

**Répertoire d'emails (index unique)** :
- Chaque email est unique : `marie@email.com` n'existe qu'une seule fois
- Si quelqu'un essaie d'ajouter `marie@email.com` une deuxième fois → REFUSÉ
- Vous cherchez par email et vous êtes certain d'avoir un seul résultat

## Index Unique vs Contrainte UNIQUE

C'est une source de confusion fréquente. Quelle est la différence entre :
- Une **contrainte UNIQUE**
- Un **index unique**

### La contrainte UNIQUE

```sql
-- Contrainte UNIQUE
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Email NVARCHAR(255) UNIQUE,  -- Contrainte UNIQUE
    Nom NVARCHAR(100)
);
```

**Ce qui se passe en coulisses** :
1. SQL Server crée **automatiquement** un index unique sur la colonne Email
2. Cet index est par défaut **non-clustered**
3. La contrainte UNIQUE est une **règle métier** (intégrité des données)

### L'index unique explicite

```sql
-- Index unique explicite
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Email NVARCHAR(255),
    Nom NVARCHAR(100)
);

-- Création explicite de l'index unique
CREATE UNIQUE INDEX IX_Clients_Email ON Clients(Email);
```

**Ce qui se passe** :
1. Vous créez manuellement l'index unique
2. Vous contrôlez le nom, le type (clustered/non-clustered), les options
3. Même résultat : l'unicité est garantie

### Quelle est la différence ?

| Aspect | Contrainte UNIQUE | Index Unique |
|--------|-------------------|--------------|
| **Objectif principal** | Intégrité des données | Performance + Intégrité |
| **Apparaît dans** | Schéma de table | Structures d'index |
| **Création automatique d'index** | Oui (index unique) | Non, explicite |
| **Contrôle du nom** | Nom généré automatiquement | Vous choisissez le nom |
| **Type d'index** | Non-clustered par défaut | Vous choisissez (clustered/non-clustered) |
| **Sémantique** | "Cette valeur doit être unique" | "Optimisation avec garantie d'unicité" |

### En pratique

**La plupart du temps** :
- Utilisez **UNIQUE** pour exprimer une règle métier
- SQL Server créera automatiquement l'index unique nécessaire
- C'est plus clair et plus lisible

**Parfois** :
- Créez un **index unique explicite** si vous avez besoin de contrôle avancé (index filtré, colonnes incluses, etc.)

## Création d'Index Uniques

### Syntaxe de base

```sql
-- Index unique non-clustered (le plus courant)
CREATE UNIQUE INDEX nom_index
ON nom_table (colonne);

-- Index unique clustered (rare)
CREATE UNIQUE CLUSTERED INDEX nom_index
ON nom_table (colonne);
```

### Exemple 1 : Index unique sur Email

```sql
-- Table Clients
CREATE TABLE Clients (
    ClientID INT IDENTITY(1,1) PRIMARY KEY,
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    Email NVARCHAR(255),
    Telephone NVARCHAR(20)
);

-- Index unique sur Email
CREATE UNIQUE INDEX IX_Clients_Email
ON Clients(Email);
```

**Effet** :

```sql
-- ✅ Insertion réussie
INSERT INTO Clients (Nom, Prenom, Email)
VALUES ('Dupont', 'Marie', 'marie@email.com');

-- ✅ Insertion réussie (email différent)
INSERT INTO Clients (Nom, Prenom, Email)
VALUES ('Durand', 'Paul', 'paul@email.com');

-- ❌ ERREUR : Violation d'index unique
INSERT INTO Clients (Nom, Prenom, Email)
VALUES ('Martin', 'Sophie', 'marie@email.com');
-- Cannot insert duplicate key in object 'Clients'.
-- The duplicate key value is (marie@email.com).
```

### Exemple 2 : Index unique sur numéro de sécurité sociale

```sql
-- Table Employes
CREATE TABLE Employes (
    EmployeID INT IDENTITY(1,1) PRIMARY KEY,
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    NumeroSecuriteSociale NVARCHAR(15)
);

-- Index unique sur NumeroSecuriteSociale
CREATE UNIQUE INDEX IX_Employes_NumeroSecu
ON Employes(NumeroSecuriteSociale);
```

**Règle métier** : Chaque numéro de sécurité sociale doit être unique.

### Exemple 3 : Index unique composite (sur plusieurs colonnes)

```sql
-- Table Inscriptions
CREATE TABLE Inscriptions (
    InscriptionID INT IDENTITY(1,1) PRIMARY KEY,
    EtudiantID INT,
    CoursID INT,
    Semestre NVARCHAR(20),
    DateInscription DATE
);

-- Index unique composite : un étudiant ne peut s'inscrire qu'une fois par cours
CREATE UNIQUE INDEX IX_Inscriptions_Etudiant_Cours
ON Inscriptions(EtudiantID, CoursID);
```

**Effet** :

```sql
-- ✅ Insertion réussie
INSERT INTO Inscriptions (EtudiantID, CoursID, Semestre)
VALUES (1, 101, 'Automne 2024');

-- ✅ Insertion réussie (cours différent)
INSERT INTO Inscriptions (EtudiantID, CoursID, Semestre)
VALUES (1, 102, 'Automne 2024');

-- ✅ Insertion réussie (étudiant différent)
INSERT INTO Inscriptions (EtudiantID, CoursID, Semestre)
VALUES (2, 101, 'Automne 2024');

-- ❌ ERREUR : Violation (même étudiant + même cours)
INSERT INTO Inscriptions (EtudiantID, CoursID, Semestre)
VALUES (1, 101, 'Hiver 2025');
```

**La combinaison (EtudiantID, CoursID) doit être unique**, mais les valeurs individuelles peuvent se répéter.

## Gestion des valeurs NULL dans les Index Uniques

### La question des NULL

**NULL** = "valeur inconnue" ou "absence de valeur"

**Question importante** : Si un index unique garantit que toutes les valeurs sont uniques, que se passe-t-il avec les NULL ?

### Comportement par défaut dans SQL Server

**Dans SQL Server** :
- Un index unique autorise **UN SEUL NULL** par défaut
- NULL = NULL est considéré comme "égal" dans le contexte d'un index unique
- Si vous essayez d'insérer plusieurs NULL → ERREUR (sauf avec un index filtré)

### Exemple avec NULL

```sql
-- Table avec index unique sur Email
CREATE TABLE Clients (
    ClientID INT IDENTITY(1,1) PRIMARY KEY,
    Nom NVARCHAR(100),
    Email NVARCHAR(255)
);

CREATE UNIQUE INDEX IX_Clients_Email ON Clients(Email);

-- ✅ Insertion réussie
INSERT INTO Clients (Nom, Email) VALUES ('Dupont', 'dupont@email.com');

-- ✅ Insertion réussie (Email = NULL)
INSERT INTO Clients (Nom, Email) VALUES ('Martin', NULL);

-- ❌ ERREUR : Violation (deuxième NULL)
INSERT INTO Clients (Nom, Email) VALUES ('Bernard', NULL);
-- Cannot insert duplicate key in object 'Clients'.
```

### Solution : Index Filtré pour autoriser plusieurs NULL

Si vous voulez autoriser **plusieurs NULL** tout en gardant l'unicité des valeurs non-NULL :

```sql
-- Index unique FILTRÉ (exclut les NULL)
CREATE UNIQUE INDEX IX_Clients_Email_Filtered
ON Clients(Email)
WHERE Email IS NOT NULL;  -- Filtre : index uniquement les valeurs non-NULL
```

**Effet** :

```sql
-- ✅ Insertion réussie
INSERT INTO Clients (Nom, Email) VALUES ('Dupont', 'dupont@email.com');

-- ✅ Insertion réussie (Email = NULL, ignoré par l'index)
INSERT INTO Clients (Nom, Email) VALUES ('Martin', NULL);

-- ✅ Insertion réussie (Email = NULL, ignoré par l'index)
INSERT INTO Clients (Nom, Email) VALUES ('Bernard', NULL);

-- ✅ Insertion réussie (Email = NULL, ignoré par l'index)
INSERT INTO Clients (Nom, Email) VALUES ('Durand', NULL);

-- ❌ ERREUR : Violation (doublon d'une valeur non-NULL)
INSERT INTO Clients (Nom, Email) VALUES ('Petit', 'dupont@email.com');
```

**Avec un index filtré** :
- Les lignes avec NULL ne sont **pas incluses** dans l'index
- Vous pouvez avoir **autant de NULL que vous voulez**
- L'unicité est garantie uniquement pour les valeurs non-NULL

### Tableau récapitulatif NULL

| Scénario | Index Unique Standard | Index Unique Filtré (WHERE ... IS NOT NULL) |
|----------|----------------------|----------------------------------------------|
| Valeurs non-NULL | Doivent être uniques | Doivent être uniques |
| Première valeur NULL | ✅ Autorisée | ✅ Autorisée |
| Deuxième valeur NULL | ❌ Refusée | ✅ Autorisée |
| Multiples NULL | ❌ Refusés | ✅ Autorisés |
| Cas d'usage | Email obligatoire | Email optionnel |

## Avantages des Index Uniques

### 1. ✅ Intégrité des données garantie

L'index unique **empêche physiquement** l'insertion de doublons.

```sql
-- Tentative d'insertion d'un doublon
INSERT INTO Clients (Email) VALUES ('dupont@email.com');
-- ERREUR immédiate, pas besoin de vérifier manuellement
```

**Sans index unique** :
```sql
-- Vous devriez vérifier manuellement avant chaque insertion
IF NOT EXISTS (SELECT 1 FROM Clients WHERE Email = 'dupont@email.com')
BEGIN
    INSERT INTO Clients (Email) VALUES ('dupont@email.com');
END
-- Risque de "race condition" si deux insertions simultanées
```

### 2. ✅ Performance de recherche

Un index unique est **aussi rapide** qu'un index non-unique pour les recherches.

```sql
SELECT * FROM Clients WHERE Email = 'dupont@email.com';
-- Index Seek : très rapide ⚡
```

**Bonus** : SQL Server sait qu'il n'y a qu'une seule ligne possible, il peut optimiser encore mieux.

### 3. ✅ Clarté du modèle de données

Un index unique **documente** votre intention :

```sql
CREATE UNIQUE INDEX IX_Employes_Matricule ON Employes(Matricule);
-- "Le matricule doit être unique" est explicite dans la structure
```

### 4. ✅ Optimisation des jointures

SQL Server peut faire des optimisations spéciales quand il sait qu'une colonne est unique.

```sql
-- Si Email est unique dans Clients
SELECT c.Nom, co.NumeroCommande
FROM Clients c
INNER JOIN Commandes co ON c.Email = co.EmailClient;

-- SQL Server sait : 1 email = 1 client maximum
-- Il peut optimiser la jointure
```

## Inconvénients et Coûts des Index Uniques

### 1. ❌ Vérification à chaque écriture

À chaque INSERT ou UPDATE, SQL Server doit vérifier l'unicité.

```sql
INSERT INTO Clients (Email) VALUES ('nouveau@email.com');

-- Opérations :
-- 1. Vérifier dans l'index unique : "nouveau@email.com" existe-t-il déjà ?
-- 2. Si non, insérer dans la table
-- 3. Mettre à jour l'index unique
```

**Coût** : Léger ralentissement des écritures (généralement négligeable).

### 2. ❌ Impossible d'insérer des doublons (évidemment !)

Si votre logique métier **nécessite** des doublons, vous ne pouvez pas utiliser un index unique.

```sql
-- Table Logs : on peut vouloir plusieurs logs avec le même type
CREATE TABLE Logs (
    LogID INT IDENTITY(1,1) PRIMARY KEY,
    TypeLog NVARCHAR(50),  -- Peut se répéter : "INFO", "INFO", "ERROR"...
    Message NVARCHAR(MAX)
);

-- ❌ Mauvaise idée : index unique sur TypeLog
CREATE UNIQUE INDEX IX_Logs_TypeLog ON Logs(TypeLog);
-- Les doublons sont nécessaires ici !
```

### 3. ❌ Gestion des NULL délicate

Comme vu précédemment, la gestion des NULL peut être contre-intuitive.

## Cas d'Usage des Index Uniques

### ✅ Cas d'usage recommandés

#### 1. Identifiants alternatifs (clés candidates)

```sql
-- ClientID = clé primaire (déjà unique via index clustered)
-- Email = clé candidate (doit aussi être unique)
CREATE UNIQUE INDEX IX_Clients_Email ON Clients(Email);

-- NumeroSecuriteSociale = clé candidate
CREATE UNIQUE INDEX IX_Employes_NumeroSecu ON Employes(NumeroSecuriteSociale);

-- Matricule = clé candidate
CREATE UNIQUE INDEX IX_Employes_Matricule ON Employes(Matricule);
```

#### 2. Contraintes métier d'unicité

```sql
-- Un produit ne peut avoir qu'un seul code-barres
CREATE UNIQUE INDEX IX_Produits_CodeBarre ON Produits(CodeBarre);

-- Un employé ne peut occuper qu'un seul bureau
CREATE UNIQUE INDEX IX_Employes_NumeroBureau ON Employes(NumeroBureau)
WHERE NumeroBureau IS NOT NULL;  -- Filtré : certains n'ont pas de bureau

-- Une commande ne peut avoir qu'un numéro de facture
CREATE UNIQUE INDEX IX_Commandes_NumeroFacture ON Commandes(NumeroFacture);
```

#### 3. Prévention des doublons dans les relations plusieurs-à-plusieurs

```sql
-- Table de liaison : Etudiants ↔ Cours
CREATE TABLE Inscriptions (
    InscriptionID INT IDENTITY(1,1) PRIMARY KEY,
    EtudiantID INT,
    CoursID INT,
    DateInscription DATE
);

-- Un étudiant ne peut s'inscrire qu'une fois à un cours
CREATE UNIQUE INDEX IX_Inscriptions_Etudiant_Cours
ON Inscriptions(EtudiantID, CoursID);
```

#### 4. Username / Login

```sql
-- Table Utilisateurs pour une application
CREATE TABLE Utilisateurs (
    UtilisateurID INT IDENTITY(1,1) PRIMARY KEY,
    Username NVARCHAR(50),
    MotDePasse NVARCHAR(255),
    Email NVARCHAR(255)
);

-- Username doit être unique
CREATE UNIQUE INDEX IX_Utilisateurs_Username ON Utilisateurs(Username);

-- Email doit être unique
CREATE UNIQUE INDEX IX_Utilisateurs_Email ON Utilisateurs(Email);
```

### ❌ Quand NE PAS utiliser d'index unique

#### 1. Colonnes avec doublons normaux et attendus

```sql
-- ❌ Mauvaise idée : ville, nom, statut, catégorie...
CREATE UNIQUE INDEX IX_Clients_Ville ON Clients(Ville);
-- Plusieurs clients peuvent habiter Paris !
```

#### 2. Colonnes descriptives

```sql
-- ❌ Mauvaise idée : description, commentaire, notes...
CREATE UNIQUE INDEX IX_Produits_Description ON Produits(Description);
-- Deux produits peuvent avoir la même description
```

#### 3. Données avec duplications légitimes

```sql
-- Table de ventes
CREATE TABLE Ventes (
    VenteID INT IDENTITY(1,1) PRIMARY KEY,
    ProduitID INT,  -- Peut se répéter (même produit vendu plusieurs fois)
    ClientID INT,   -- Peut se répéter (même client achète plusieurs fois)
    Quantite INT
);

-- ❌ Mauvaise idée
CREATE UNIQUE INDEX IX_Ventes_ProduitID ON Ventes(ProduitID);
-- Un produit peut être vendu plusieurs fois !
```

## Index Unique Clustered vs Non-Clustered

### Index Unique Clustered

**Rare** : Utilisé uniquement pour des cas très spécifiques.

```sql
-- Table avec index unique clustered sur une colonne naturelle
CREATE TABLE Pays (
    CodeISO CHAR(2) PRIMARY KEY,  -- 'FR', 'US', 'DE'...
    NomPays NVARCHAR(100)
);

-- Par défaut, PRIMARY KEY crée un index UNIQUE CLUSTERED
-- CodeISO est unique ET détermine l'ordre physique
```

**Cas d'usage** :
- Clé primaire "naturelle" (ex : code pays, code postal)
- Colonnes avec large plage de valeurs uniques
- Colonnes fréquemment utilisées dans ORDER BY

### Index Unique Non-Clustered

**Courant** : Le cas standard.

```sql
-- Table avec clé primaire numérique + autres colonnes uniques
CREATE TABLE Clients (
    ClientID INT IDENTITY(1,1) PRIMARY KEY,  -- Index clustered
    Email NVARCHAR(255),
    Telephone NVARCHAR(20)
);

-- Index unique non-clustered
CREATE UNIQUE INDEX IX_Clients_Email ON Clients(Email);
CREATE UNIQUE INDEX IX_Clients_Telephone ON Clients(Telephone);
```

**Cas d'usage** :
- Clés alternatives (email, numéro de téléphone, matricule...)
- Garantir l'unicité sur des colonnes de recherche
- La plupart des index uniques dans vos applications

### Comparaison

| Aspect | Index Unique Clustered | Index Unique Non-Clustered |
|--------|------------------------|----------------------------|
| **Nombre par table** | 1 maximum (comme tout clustered) | Jusqu'à 999 |
| **Ordre physique** | Détermine l'ordre | N'affecte pas l'ordre |
| **Usage typique** | Clé primaire naturelle | Clés alternatives |
| **Fréquence** | Rare (sauf PRIMARY KEY) | Très courant |

## Index Unique et PRIMARY KEY / FOREIGN KEY

### PRIMARY KEY

Par défaut, **PRIMARY KEY** crée un index **UNIQUE CLUSTERED**.

```sql
-- Ces deux syntaxes sont équivalentes :

-- Syntaxe 1 (courante)
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Nom NVARCHAR(100)
);

-- Syntaxe 2 (explicite)
CREATE TABLE Clients (
    ClientID INT,
    Nom NVARCHAR(100)
);
CREATE UNIQUE CLUSTERED INDEX PK_Clients_ClientID ON Clients(ClientID);
ALTER TABLE Clients ADD CONSTRAINT PK_Clients PRIMARY KEY (ClientID);
```

**Caractéristiques de PRIMARY KEY** :
- ✅ UNIQUE (pas de doublons)
- ✅ NOT NULL (pas de valeur nulle)
- ✅ Clustered par défaut (peut être changé)
- ✅ Une seule PRIMARY KEY par table

### FOREIGN KEY

Une **FOREIGN KEY** référence souvent une PRIMARY KEY (qui est unique).

```sql
-- Table Clients
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,  -- Index unique clustered
    Nom NVARCHAR(100)
);

-- Table Commandes
CREATE TABLE Commandes (
    CommandeID INT PRIMARY KEY,
    ClientID INT,  -- Foreign Key vers Clients
    DateCommande DATE,
    FOREIGN KEY (ClientID) REFERENCES Clients(ClientID)
);

-- Recommandation : Index (non-unique) sur la foreign key
CREATE INDEX IX_Commandes_ClientID ON Commandes(ClientID);
-- NON-UNIQUE car un client peut avoir plusieurs commandes
```

**Important** :
- La colonne **référencée** (Clients.ClientID) doit être unique (PRIMARY KEY ou UNIQUE)
- La colonne **référençante** (Commandes.ClientID) n'est généralement **pas unique** (plusieurs commandes par client)

## Requêtes pour gérer les Index Uniques

### Voir les index uniques d'une table

```sql
-- Liste tous les index avec leur type
SELECT
    i.name AS IndexName,
    i.type_desc AS IndexType,
    i.is_unique AS IsUnique,
    c.name AS ColumnName
FROM sys.indexes i
INNER JOIN sys.index_columns ic ON i.object_id = ic.object_id AND i.index_id = ic.index_id
INNER JOIN sys.columns c ON ic.object_id = c.object_id AND ic.column_id = c.column_id
WHERE i.object_id = OBJECT_ID('Clients')
ORDER BY i.name, ic.key_ordinal;
```

### Supprimer un index unique

```sql
-- Suppression d'un index unique
DROP INDEX IX_Clients_Email ON Clients;
```

### Modifier un index unique

```sql
-- On ne peut pas modifier un index directement
-- Il faut le supprimer puis le recréer

-- Étape 1 : Supprimer
DROP INDEX IX_Clients_Email ON Clients;

-- Étape 2 : Recréer avec les nouvelles options
CREATE UNIQUE INDEX IX_Clients_Email
ON Clients(Email)
WHERE Email IS NOT NULL;  -- Nouvelle option : filtré
```

### Désactiver temporairement un index unique

```sql
-- Désactiver l'index (utile pour chargement en masse)
ALTER INDEX IX_Clients_Email ON Clients DISABLE;

-- Insertion en masse (plus rapide sans vérification d'unicité)
INSERT INTO Clients (Email) VALUES ('user1@email.com');
INSERT INTO Clients (Email) VALUES ('user2@email.com');
-- ... milliers de lignes

-- Réactiver l'index (reconstruit et vérifie l'unicité)
ALTER INDEX IX_Clients_Email ON Clients REBUILD;
```

**Attention** : Si des doublons ont été insérés pendant que l'index était désactivé, le REBUILD échouera !

## Bonnes Pratiques

### ✅ À FAIRE

#### 1. Utilisez des contraintes UNIQUE pour les règles métier

```sql
-- ✅ Clair et explicite
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Email NVARCHAR(255) UNIQUE,  -- Règle métier : email unique
    Nom NVARCHAR(100)
);
```

#### 2. Nommez vos index uniques clairement

```sql
-- ✅ Bon nommage
CREATE UNIQUE INDEX IX_Clients_Email ON Clients(Email);
CREATE UNIQUE INDEX UX_Employes_Matricule ON Employes(Matricule);

-- Préfixes courants :
-- IX_ = Index
-- UX_ = Unique indeX (pour distinguer des index non-uniques)
```

#### 3. Utilisez des index filtrés pour gérer les NULL

```sql
-- ✅ Autorise plusieurs NULL, garantit l'unicité des non-NULL
CREATE UNIQUE INDEX IX_Clients_Telephone
ON Clients(Telephone)
WHERE Telephone IS NOT NULL;
```

#### 4. Indexez les clés alternatives

```sql
-- ✅ ClientID = PRIMARY KEY (unique, clustered)
-- ✅ Email = Clé alternative (unique, non-clustered)
CREATE UNIQUE INDEX IX_Clients_Email ON Clients(Email);

-- ✅ Matricule = Clé alternative
CREATE UNIQUE INDEX IX_Employes_Matricule ON Employes(Matricule);
```

#### 5. Documentez l'intention métier

```sql
-- ✅ Commentaire expliquant la règle métier
-- Règle métier : Un étudiant ne peut s'inscrire qu'une fois à un cours donné
CREATE UNIQUE INDEX IX_Inscriptions_Etudiant_Cours
ON Inscriptions(EtudiantID, CoursID);
```

### ❌ À ÉVITER

#### 1. N'abusez pas des index uniques

```sql
-- ❌ Trop d'index uniques sur des colonnes qui ne devraient pas être uniques
CREATE UNIQUE INDEX IX_Produits_Nom ON Produits(Nom);
-- Deux produits différents peuvent avoir le même nom !
```

#### 2. Ne créez pas d'index uniques et de contraintes UNIQUE redondants

```sql
-- ❌ Redondant
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,
    Email NVARCHAR(255) UNIQUE  -- Crée déjà un index unique
);

-- Pas besoin de :
CREATE UNIQUE INDEX IX_Clients_Email ON Clients(Email);
-- C'est en double !
```

#### 3. N'oubliez pas les NULL

```sql
-- ⚠️ Attention : un seul NULL sera autorisé
CREATE UNIQUE INDEX IX_Clients_Telephone ON Clients(Telephone);

-- ✅ Mieux : index filtré si le téléphone est optionnel
CREATE UNIQUE INDEX IX_Clients_Telephone
ON Clients(Telephone)
WHERE Telephone IS NOT NULL;
```

#### 4. Ne créez pas d'index uniques sur des colonnes de faible cardinalité

```sql
-- ❌ Mauvaise idée : seulement 2 valeurs possibles (M, F)
CREATE UNIQUE INDEX IX_Employes_Sexe ON Employes(Sexe);
-- Impossible d'avoir plus de 2 lignes dans la table !
```

## Exemples Pratiques Complets

### Exemple 1 : Système d'authentification

```sql
-- Table Utilisateurs
CREATE TABLE Utilisateurs (
    UtilisateurID INT IDENTITY(1,1) PRIMARY KEY,  -- Index unique clustered
    Username NVARCHAR(50) NOT NULL,
    Email NVARCHAR(255) NOT NULL,
    MotDePasseHash NVARCHAR(255) NOT NULL,
    DateInscription DATETIME2 DEFAULT SYSDATETIME(),
    DerniereConnexion DATETIME2
);

-- Index unique sur Username (connexion)
CREATE UNIQUE INDEX IX_Utilisateurs_Username
ON Utilisateurs(Username);

-- Index unique sur Email (alternative de connexion, récupération de mot de passe)
CREATE UNIQUE INDEX IX_Utilisateurs_Email
ON Utilisateurs(Email);
```

**Avantages** :
- Empêche deux utilisateurs avec le même username
- Empêche deux utilisateurs avec le même email
- Recherche rapide lors de la connexion

### Exemple 2 : Système de facturation

```sql
-- Table Factures
CREATE TABLE Factures (
    FactureID INT IDENTITY(1,1) PRIMARY KEY,
    NumeroFacture NVARCHAR(20) NOT NULL,  -- Ex: "FAC-2024-00001"
    ClientID INT NOT NULL,
    DateFacture DATE NOT NULL,
    MontantTotal DECIMAL(10,2) NOT NULL
);

-- Index unique sur NumeroFacture
CREATE UNIQUE INDEX IX_Factures_NumeroFacture
ON Factures(NumeroFacture);

-- Index non-unique sur ClientID (un client a plusieurs factures)
CREATE INDEX IX_Factures_ClientID
ON Factures(ClientID);
```

### Exemple 3 : Gestion des stocks

```sql
-- Table Produits
CREATE TABLE Produits (
    ProduitID INT IDENTITY(1,1) PRIMARY KEY,
    SKU NVARCHAR(50) NOT NULL,  -- Stock Keeping Unit
    CodeBarre NVARCHAR(50),  -- Peut être NULL (certains produits n'en ont pas)
    NomProduit NVARCHAR(200) NOT NULL,
    Prix DECIMAL(10,2) NOT NULL
);

-- Index unique sur SKU (identifiant interne)
CREATE UNIQUE INDEX IX_Produits_SKU
ON Produits(SKU);

-- Index unique filtré sur CodeBarre (certains produits n'en ont pas)
CREATE UNIQUE INDEX IX_Produits_CodeBarre
ON Produits(CodeBarre)
WHERE CodeBarre IS NOT NULL;  -- Permet plusieurs NULL
```

## Résumé et Points Clés

### 🎯 Points essentiels à retenir

1. **Index unique = Garantie d'unicité + Performance**
   - Empêche les doublons
   - Accélère les recherches comme un index normal

2. **Contrainte UNIQUE ≈ Index Unique**
   - Une contrainte UNIQUE crée automatiquement un index unique
   - Dans la plupart des cas, utilisez UNIQUE (plus clair)

3. **Gestion des NULL**
   - Index unique standard : UN SEUL NULL autorisé
   - Index unique filtré : PLUSIEURS NULL autorisés (WHERE ... IS NOT NULL)

4. **Clustered vs Non-Clustered**
   - Unique Clustered : Rare (sauf PRIMARY KEY)
   - Unique Non-Clustered : Courant (clés alternatives)

5. **Cas d'usage principaux**
   - Identifiants alternatifs (email, matricule, username)
   - Contraintes métier d'unicité
   - Prévention des doublons

6. **Coût**
   - Léger ralentissement des écritures (vérification d'unicité)
   - Espace disque supplémentaire (comme tout index)

### ✅ Checklist : Quand créer un index unique

Créez un index unique si **toutes** ces conditions sont remplies :

- [ ] La colonne doit contenir des valeurs uniques (règle métier)
- [ ] Vous recherchez souvent sur cette colonne
- [ ] Les doublons causeraient des problèmes dans votre application
- [ ] La colonne a une forte cardinalité (beaucoup de valeurs différentes)

### 📋 Syntaxes à retenir

```sql
-- Contrainte UNIQUE (recommandé pour la clarté)
CREATE TABLE Clients (
    Email NVARCHAR(255) UNIQUE
);

-- Index unique explicite (pour plus de contrôle)
CREATE UNIQUE INDEX IX_Clients_Email ON Clients(Email);

-- Index unique filtré (pour gérer les NULL)
CREATE UNIQUE INDEX IX_Clients_Email
ON Clients(Email)
WHERE Email IS NOT NULL;

-- Index unique composite
CREATE UNIQUE INDEX IX_Inscriptions_Etudiant_Cours
ON Inscriptions(EtudiantID, CoursID);
```

## Conclusion

Les **index uniques** sont un outil puissant pour garantir l'**intégrité des données** tout en optimisant les **performances**. Ils combinent deux fonctions essentielles :
1. Empêcher les doublons (intégrité)
2. Accélérer les recherches (performance)

**Règle d'or** : Utilisez des index uniques sur toutes les colonnes qui doivent contenir des valeurs uniques selon votre logique métier (email, username, matricule, numéro de facture, etc.).
