# 7.1.2 Index Cluster (Clustered) : La table elle-même (Heap vs Clustered)

## Introduction

Dans la section précédente, nous avons vu pourquoi les index sont importants. Maintenant, nous allons découvrir un type d'index très spécial : **l'index clustered** (ou index cluster en français).

**L'index clustered est unique** car contrairement aux autres index qui sont des structures séparées de la table, **l'index clustered EST la table elle-même**. C'est un concept fondamental à comprendre.

## L'analogie du dictionnaire

Pour bien comprendre, utilisons une analogie simple :

### Le dictionnaire (Index Clustered)

Un **dictionnaire** est un exemple parfait d'index clustered :
- Les mots sont **physiquement rangés** dans l'ordre alphabétique
- Vous ne cherchez pas le mot "Zèbre" au début du dictionnaire, vous allez directement vers la fin
- **Les données (définitions) sont stockées directement avec les clés (mots)** dans l'ordre
- Il n'y a **qu'un seul ordre possible** : alphabétique

### Le carnet d'adresses désorganisé (Heap)

Imaginez maintenant un **carnet** où vous notez les contacts **dans l'ordre où vous les rencontrez** :
- Page 1 : Marie (rencontrée en janvier)
- Page 2 : Paul (rencontré en février)
- Page 3 : Alice (rencontrée en mars)
- Page 4 : Bernard (rencontré en avril)

Les données ne sont **pas triées**, elles sont simplement **empilées** dans l'ordre d'arrivée. C'est ce qu'on appelle un **Heap** (tas, en français).

## Qu'est-ce qu'un Heap ?

### Définition

Un **Heap** est une table **sans index clustered**. Les lignes sont stockées **sans ordre particulier**, simplement dans l'ordre où elles ont été insérées.

### Création d'un Heap

Quand vous créez une table sans spécifier de clé primaire ou d'index clustered, vous créez un Heap :

```sql
-- Cette table est un Heap (pas d'index clustered)
CREATE TABLE Clients_Heap (
    ClientID INT,
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    Email NVARCHAR(255),
    DateInscription DATE
);

-- Insertion de données
INSERT INTO Clients_Heap VALUES (5, 'Martin', 'Sophie', 'sophie@email.com', '2024-01-15');
INSERT INTO Clients_Heap VALUES (2, 'Durand', 'Paul', 'paul@email.com', '2024-01-10');
INSERT INTO Clients_Heap VALUES (8, 'Bernard', 'Marie', 'marie@email.com', '2024-01-20');
INSERT INTO Clients_Heap VALUES (1, 'Petit', 'Luc', 'luc@email.com', '2024-01-05');
```

### Comment les données sont stockées dans un Heap

```
Stockage physique (dans l'ordre d'insertion) :
┌──────────┬─────────┬─────────┬───────────────────┐
│ ClientID │ Nom     │ Prenom  │ Email             │
├──────────┼─────────┼─────────┼───────────────────┤
│ 5        │ Martin  │ Sophie  │ sophie@email.com  │ ← Inséré en premier
│ 2        │ Durand  │ Paul    │ paul@email.com    │ ← Inséré en deuxième
│ 8        │ Bernard │ Marie   │ marie@email.com   │ ← Inséré en troisième
│ 1        │ Petit   │ Luc     │ luc@email.com     │ ← Inséré en quatrième
└──────────┴─────────┴─────────┴───────────────────┘

Remarquez : Pas d'ordre logique sur ClientID (5, 2, 8, 1)
```

### Avantages d'un Heap

✅ **Insertions très rapides** : Les nouvelles lignes sont simplement ajoutées à la fin, sans réorganisation

✅ **Pas de maintenance** : Pas besoin de maintenir un ordre

✅ **Utilisation spécifique** : Bon pour les tables temporaires ou de staging où vous insérez en masse puis lisez tout

### Inconvénients d'un Heap

❌ **Recherches lentes** : Pour trouver une ligne spécifique, SQL Server doit faire un **Table Scan** (parcourir toutes les lignes)

❌ **Pas d'ordre physique** : Les données ne sont pas triées

❌ **Fragmentation** : Après beaucoup d'UPDATE et DELETE, des espaces vides se créent, gaspillant de l'espace

**Conclusion sur les Heaps** : Ils sont rarement recommandés pour les tables de production avec beaucoup de lectures.

## Qu'est-ce qu'un Index Clustered ?

### Définition

Un **index clustered** détermine **l'ordre physique** des données dans la table. Les lignes sont **réorganisées et stockées dans l'ordre** de la clé de l'index clustered.

**Point crucial** : Une table peut avoir **un seul et unique** index clustered, car les données ne peuvent être physiquement triées que d'une seule façon.

### L'index clustered EST la table

C'est le point le plus important à comprendre :

- Pour un index non-clustered : index et table sont **séparés**
- Pour un index clustered : index et table sont **la même chose**

**Analogie** :
- Index non-clustered = Index d'un livre (séparé du contenu)
- Index clustered = Dictionnaire (le contenu EST déjà trié)

### Création d'un Index Clustered

Il y a deux façons principales de créer un index clustered :

#### Méthode 1 : Avec une clé primaire (la plus courante)

```sql
-- Par défaut, PRIMARY KEY crée automatiquement un index clustered
CREATE TABLE Clients_Clustered (
    ClientID INT PRIMARY KEY,  -- Crée automatiquement un index clustered sur ClientID
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    Email NVARCHAR(255),
    DateInscription DATE
);
```

#### Méthode 2 : Explicitement avec CREATE CLUSTERED INDEX

```sql
-- Création explicite d'un index clustered
CREATE TABLE Produits (
    ProduitID INT,
    Nom NVARCHAR(100),
    Prix DECIMAL(10,2),
    CategorieID INT
);

-- Création de l'index clustered sur ProduitID
CREATE CLUSTERED INDEX IX_Produits_ProduitID ON Produits(ProduitID);
```

### Comment les données sont stockées avec un Index Clustered

Reprenons notre exemple avec les mêmes insertions :

```sql
CREATE TABLE Clients_Clustered (
    ClientID INT PRIMARY KEY,  -- Index clustered
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    Email NVARCHAR(255),
    DateInscription DATE
);

-- Même ordre d'insertion qu'avant
INSERT INTO Clients_Clustered VALUES (5, 'Martin', 'Sophie', 'sophie@email.com', '2024-01-15');
INSERT INTO Clients_Clustered VALUES (2, 'Durand', 'Paul', 'paul@email.com', '2024-01-10');
INSERT INTO Clients_Clustered VALUES (8, 'Bernard', 'Marie', 'marie@email.com', '2024-01-20');
INSERT INTO Clients_Clustered VALUES (1, 'Petit', 'Luc', 'luc@email.com', '2024-01-05');
```

**Stockage physique** (automatiquement trié par ClientID) :

```
Stockage physique (TRIÉ par ClientID, la clé clustered) :
┌──────────┬─────────┬─────────┬───────────────────┐
│ ClientID │ Nom     │ Prenom  │ Email             │
├──────────┼─────────┼─────────┼───────────────────┤
│ 1        │ Petit   │ Luc     │ luc@email.com     │ ← Automatiquement en premier
│ 2        │ Durand  │ Paul    │ paul@email.com    │ ← Trié
│ 5        │ Martin  │ Sophie  │ sophie@email.com  │ ← Trié
│ 8        │ Bernard │ Marie   │ marie@email.com   │ ← Automatiquement en dernier
└──────────┴─────────┴─────────┴───────────────────┘

Les données sont physiquement TRIÉES par ClientID !
```

### Recherche dans une table avec Index Clustered

Quand vous faites une recherche sur la clé clustered :

```sql
SELECT * FROM Clients_Clustered WHERE ClientID = 5;
```

**SQL Server peut utiliser l'index clustered** :
1. Il sait que les données sont triées par ClientID
2. Il peut faire une recherche **binaire** (très rapide)
3. Il trouve directement la ligne sans parcourir toute la table

C'est comme chercher un mot dans un dictionnaire : vous savez que "Maison" est au milieu, donc vous ouvrez le dictionnaire au milieu et vous affinez.

## Structure B-Tree de l'Index Clustered

L'index clustered utilise une structure en arbre appelée **B-Tree** (Balanced Tree - Arbre équilibré).

### Analogie : L'organigramme d'entreprise

Imaginez une entreprise avec :
- **Un PDG** au sommet (Racine de l'arbre)
- **Des directeurs** au niveau intermédiaire (Nœuds intermédiaires)
- **Des employés** au niveau le plus bas (Feuilles = les données)

```
Structure B-Tree simplifiée pour un index clustered :

                    Niveau Racine
                    ┌─────────┐
                    │ 1 - 100 │  "Les IDs de 1 à 100 sont quelque part en dessous"
                    └────┬────┘
                         │
            ┌────────────┴────────────┐
            │                         │
     Niveau Intermédiaire      Niveau Intermédiaire
     ┌──────────┐              ┌──────────┐
     │  1 - 50  │              │ 51 - 100 │
     └─────┬────┘              └─────┬────┘
           │                         │
      ┌────┴────┐               ┌────┴────┐
      │         │               │         │
   Feuilles  Feuilles       Feuilles  Feuilles
   (Données) (Données)      (Données) (Données)

   ID: 1-25  ID: 26-50     ID: 51-75  ID: 76-100
   + toutes  + toutes      + toutes   + toutes
   les       les           les        les
   colonnes  colonnes      colonnes   colonnes
```

### Pourquoi une structure en arbre ?

Cette structure permet des recherches **extrêmement rapides** :

**Exemple** : Chercher le ClientID = 73 dans une table de 1 million de lignes

Sans index (Heap) :
- Parcourir potentiellement 1 000 000 de lignes
- Temps : proportionnel à la taille de la table

Avec index clustered (B-Tree) :
- Niveau 1 (Racine) : "73 est entre 1 et 1 000 000" → aller à droite
- Niveau 2 : "73 est entre 1 et 500 000" → aller à gauche
- Niveau 3 : "73 est entre 1 et 100 000" → continuer...
- Quelques niveaux plus tard : trouver la page contenant 73
- **Maximum 3-4 lectures**, quelle que soit la taille de la table !

C'est la puissance de la recherche logarithmique : log₂(1 000 000) ≈ 20 comparaisons maximum.

## Heap vs Clustered : Comparaison détaillée

### Tableau comparatif

| Critère | Heap | Index Clustered |
|---------|------|-----------------|
| **Ordre physique** | Aucun (ordre d'insertion) | Trié selon la clé clustered |
| **Recherche sur la clé** | Table Scan (lent) | Index Seek (très rapide) |
| **Insertion** | Très rapide (ajout à la fin) | Plus lent (maintien de l'ordre) |
| **Fragmentation** | Importante avec le temps | Gérée mais peut exister |
| **Espace disque** | Minimal (pas de structure d'index) | Un peu plus (structure B-Tree) |
| **Nombre possible** | 1 (ou 0 si index clustered existe) | 1 maximum par table |
| **Usage recommandé** | Tables temporaires, staging | Tables de production (lecture fréquente) |

### Exemple visuel : INSERT dans un Heap vs Clustered

**INSERT dans un Heap** :

```
Avant insertion :
┌───┬─────────┐
│ 5 │ Martin  │
│ 2 │ Durand  │
│ 8 │ Bernard │
└───┴─────────┘

INSERT INTO ... VALUES (3, 'Petit');

Après insertion (simplement ajouté à la fin) :
┌───┬─────────┐
│ 5 │ Martin  │
│ 2 │ Durand  │
│ 8 │ Bernard │
│ 3 │ Petit   │ ← Ajouté à la fin, pas de tri
└───┴─────────┘

Opération : RAPIDE ⚡
```

**INSERT dans une table avec Index Clustered** :

```
Avant insertion (trié par ID) :
┌───┬─────────┐
│ 2 │ Durand  │
│ 5 │ Martin  │
│ 8 │ Bernard │
└───┴─────────┘

INSERT INTO ... VALUES (3, 'Petit');

Après insertion (maintien de l'ordre) :
┌───┬─────────┐
│ 2 │ Durand  │
│ 3 │ Petit   │ ← Inséré à sa place logique
│ 5 │ Martin  │ ← Les autres lignes peuvent être déplacées
│ 8 │ Bernard │
└───┴─────────┘

Opération : Plus lent (maintien du tri) 🐌
```

## Quand utiliser un Heap vs Index Clustered ?

### Utilisez un Heap quand :

✅ **Table de staging** : Vous chargez massivement des données puis les traitez
```sql
-- Table temporaire pour import CSV
CREATE TABLE Import_Donnees_Temporaire (
    Colonne1 NVARCHAR(100),
    Colonne2 NVARCHAR(100),
    Colonne3 NVARCHAR(100)
);
-- Pas besoin d'index clustered, on insère puis on lit tout
```

✅ **Table d'audit/logs** : Insertions massives, lectures rares
```sql
-- Table de logs, on écrit beaucoup, on lit rarement
CREATE TABLE Logs_Application (
    LogID INT IDENTITY(1,1),
    DateLog DATETIME DEFAULT GETDATE(),
    Message NVARCHAR(MAX)
);
-- Un Heap peut être acceptable ici
```

### Utilisez un Index Clustered quand :

✅ **Table de production** : C'est le cas par défaut, recommandé pour presque toutes les tables

✅ **Recherches fréquentes** : Vous interrogez souvent la table
```sql
-- Table Clients consultée fréquemment
CREATE TABLE Clients (
    ClientID INT PRIMARY KEY,  -- Index clustered recommandé
    Nom NVARCHAR(100),
    Email NVARCHAR(255)
);
```

✅ **Jointures fréquentes** : La colonne de jointure bénéficie d'un index clustered
```sql
-- Table Commandes jointe sur CommandeID
CREATE TABLE Commandes (
    CommandeID INT PRIMARY KEY,  -- Index clustered
    ClientID INT,
    DateCommande DATE
);
```

✅ **Tri fréquent** : Vous utilisez souvent ORDER BY sur une colonne
```sql
-- Souvent trié par date
CREATE TABLE Articles (
    ArticleID INT,
    Titre NVARCHAR(200),
    DatePublication DATE
);

-- Index clustered sur la date pour les tris chronologiques
CREATE CLUSTERED INDEX IX_Articles_DatePublication
ON Articles(DatePublication DESC);
```

## Choix de la clé d'Index Clustered

Le choix de la clé clustered est **crucial** car il détermine l'ordre physique des données.

### Critères pour une bonne clé clustered

#### 1. **Unique** (ou presque)
La clé doit identifier chaque ligne de manière unique.

✅ Bon : `ClientID` (identifiant unique)
❌ Mauvais : `Ville` (beaucoup de doublons)

#### 2. **Étroit** (peu d'octets)
Une clé plus petite = structure B-Tree plus compacte = meilleures performances

✅ Bon : `INT` (4 octets)
✅ Acceptable : `BIGINT` (8 octets)
❌ Mauvais : `NVARCHAR(200)` (jusqu'à 400 octets)

#### 3. **Statique** (ne change jamais)
Si la clé change, SQL Server doit réorganiser physiquement la table !

✅ Bon : `ClientID` (ne change jamais)
❌ Mauvais : `Email` (peut changer)

#### 4. **Toujours croissant** (IDENTITY, DATE, GUID séquentiel)
Les insertions se font à la fin, évitant la fragmentation.

✅ Bon : `ClientID INT IDENTITY(1,1)` (1, 2, 3, 4, ...)
✅ Bon : `DateCreation` (2024-01-01, 2024-01-02, ...)
❌ Mauvais : `NEWID()` (GUIDs aléatoires causent de la fragmentation)

### Exemples de bons choix de clé clustered

```sql
-- Excellent : ID auto-incrémenté
CREATE TABLE Clients (
    ClientID INT IDENTITY(1,1) PRIMARY KEY,  -- Parfait pour clustered
    Nom NVARCHAR(100),
    Email NVARCHAR(255)
);

-- Bon : Date toujours croissante pour une table d'historique
CREATE TABLE Historique_Commandes (
    HistoriqueID INT IDENTITY(1,1),
    DateEvenement DATETIME2 DEFAULT SYSDATETIME(),
    CommandeID INT,
    Statut NVARCHAR(50)
);
CREATE CLUSTERED INDEX IX_Historique_DateEvenement
ON Historique_Commandes(DateEvenement);

-- Acceptable : Clé composite unique
CREATE TABLE CommandesDetails (
    CommandeID INT,
    ProduitID INT,
    Quantite INT,
    PRIMARY KEY CLUSTERED (CommandeID, ProduitID)  -- Clé composite
);
```

### Exemples de mauvais choix

```sql
-- ❌ Mauvais : GUID aléatoire (fragmentation)
CREATE TABLE Utilisateurs (
    UtilisateurID UNIQUEIDENTIFIER DEFAULT NEWID() PRIMARY KEY,
    -- NEWID() génère des GUIDs aléatoires
    -- Insertions partout dans la table = fragmentation
    Nom NVARCHAR(100)
);

-- ❌ Mauvais : Colonne large
CREATE TABLE Entreprises (
    Email NVARCHAR(255) PRIMARY KEY,  -- Trop large pour clustered
    NomEntreprise NVARCHAR(200)
);

-- ❌ Mauvais : Colonne modifiable
CREATE TABLE Employes (
    CodeEmploye NVARCHAR(20) PRIMARY KEY,  -- Peut changer
    Nom NVARCHAR(100)
);
-- Si CodeEmploye change, toute la table est réorganisée !
```

## Impact sur les autres index

Voici un concept important : **l'index clustered affecte tous les autres index de la table** (les index non-clustered que nous verrons dans la section suivante).

### Les index non-clustered "pointent" vers le clustered

- Dans une table **Heap** : les index non-clustered contiennent un "RID" (Row Identifier - pointeur physique)
- Dans une table avec **index clustered** : les index non-clustered contiennent **la clé clustered**

**Conséquence** : Si votre clé clustered est large (ex: NVARCHAR(200)), tous vos index non-clustered seront également plus volumineux !

```
Exemple avec clé clustered étroite (INT - 4 octets) :
Index non-clustered sur Email → contient Email + ClientID (4 octets)
Total raisonnable

Exemple avec clé clustered large (NVARCHAR(200) - 400 octets) :
Index non-clustered sur Email → contient Email + Clé (400 octets)
Total énorme ! Performance dégradée.
```

C'est une autre raison pour choisir une **clé clustered étroite**.

## Résumé et Points Clés

### 🎯 Points essentiels à retenir

1. **Index Clustered = Table triée**
   - L'index clustered détermine l'ordre physique de stockage des données
   - Il ne peut y avoir qu'un seul index clustered par table

2. **Heap = Table non triée**
   - Un Heap stocke les données sans ordre particulier
   - Bon pour les insertions massives, mauvais pour les recherches

3. **Par défaut, PRIMARY KEY crée un index clustered**
   - C'est le comportement par défaut dans SQL Server
   - Vous pouvez le changer si nécessaire

4. **Choisissez bien votre clé clustered**
   - Unique, étroite, statique, toujours croissante
   - Généralement un ID auto-incrémenté (IDENTITY)

5. **L'index clustered utilise une structure B-Tree**
   - Permet des recherches en temps logarithmique (très rapide)
   - Quelques lectures même pour des millions de lignes

6. **Impact sur les performances**
   - Recherches : Clustered >> Heap
   - Insertions : Heap > Clustered (si pas de maintien d'ordre)

### ✅ Bonnes pratiques

```sql
-- ✅ Recommandé : Table de production avec clé IDENTITY
CREATE TABLE Clients (
    ClientID INT IDENTITY(1,1) PRIMARY KEY,  -- Index clustered
    Nom NVARCHAR(100),
    Prenom NVARCHAR(100),
    Email NVARCHAR(255)
);

-- ✅ Acceptable : Heap pour table temporaire
CREATE TABLE #TempImport (
    Colonne1 NVARCHAR(100),
    Colonne2 NVARCHAR(100)
);
-- Pas d'index clustered nécessaire
```

### ❌ À éviter

```sql
-- ❌ Éviter : Pas d'index clustered sur table de production
CREATE TABLE Clients (
    ClientID INT,
    Nom NVARCHAR(100)
);
-- Aucune clé primaire = Heap = performances dégradées

-- ❌ Éviter : Clé clustered large et modifiable
CREATE TABLE Produits (
    NomProduit NVARCHAR(500) PRIMARY KEY,  -- Trop large !
    Prix DECIMAL(10,2)
);
```

## Conclusion

L'**index clustered** est probablement l'élément le plus important de l'optimisation des performances d'une table SQL Server. Comprendre la différence entre un **Heap** et une table avec **index clustered** est fondamental.

**La règle d'or** : Presque toutes vos tables de production devraient avoir un index clustered, généralement sur une clé primaire auto-incrémentée de type INT ou BIGINT.

Dans la prochaine section, nous découvrirons les **index non-clustered**, qui sont des structures séparées de la table et permettent d'accélérer encore davantage les recherches sur d'autres colonnes.
