# 7.6.3 Éviter SELECT *

## Introduction

`SELECT *` est probablement l'instruction SQL la plus utilisée par les débutants, et c'est compréhensible : elle est simple, rapide à écrire, et fonctionne. Cependant, dans le code de production, `SELECT *` est considéré comme une **mauvaise pratique** qui peut causer de sérieux problèmes de performance et de maintenance.

Cette section explique pourquoi et vous montre comment écrire des requêtes plus performantes et maintenables.

## Qu'est-ce que SELECT * ?

`SELECT *` signifie "sélectionne toutes les colonnes de la table".

```sql
-- Sélectionne TOUTES les colonnes de la table Customers
SELECT * FROM Customers;

-- Équivalent explicite (si la table a 5 colonnes)
SELECT
    CustomerID,
    CustomerName,
    Email,
    Phone,
    Address
FROM Customers;
```

### Analogie : Le buffet à volonté

**SELECT * = Prendre tout au buffet**
```
Vous allez à un buffet avec 50 plats différents
Vous prenez UN PEU DE TOUT, même :
- Les plats que vous n'aimez pas
- Les plats que vous ne mangerez jamais
- Des quantités énormes que vous ne finirez pas

Résultat :
- Votre assiette est pleine et lourde
- Vous gaspillez de la nourriture
- Vous mettez plus de temps à manger
- Vous êtes inconfortable
```

**SELECT colonnes spécifiques = Choisir ce dont vous avez besoin**
```
Vous prenez uniquement :
- Salade
- Poulet
- Riz

Résultat :
- Assiette légère
- Pas de gaspillage
- Repas rapide et agréable
```

## Pourquoi éviter SELECT * ?

### 1. Performance : Transfert de données inutiles

#### Le problème

```sql
-- Table Employees avec 20 colonnes
-- Vous avez besoin uniquement du nom et de l'email
SELECT * FROM Employees;

-- Cela transfère 20 colonnes alors que vous n'en utilisez que 2
-- Ratio d'efficacité : 10% (2/20)
```

**Conséquences :**
- Plus de données transitent sur le réseau
- Plus de mémoire utilisée côté SQL Server
- Plus de mémoire utilisée côté application
- Temps de réponse plus long

#### Impact quantitatif

**Exemple avec une table de 100,000 employés :**

```sql
-- ❌ SELECT * (20 colonnes, moyenne 50 octets par colonne)
SELECT * FROM Employees;
-- Données transférées : 100,000 × 20 × 50 = 100 MB
-- Temps de transfert réseau : 2 secondes (sur réseau 400 Mbps)

-- ✅ SELECT colonnes spécifiques (2 colonnes)
SELECT EmployeeID, FullName FROM Employees;
-- Données transférées : 100,000 × 2 × 50 = 10 MB
-- Temps de transfert réseau : 0.2 secondes

→ Amélioration de 10x en volume de données
→ Amélioration de 10x en temps de transfert
```

### 2. Empêche l'utilisation d'index couvrants

#### Qu'est-ce qu'un index couvrant ?

Un **index couvrant** (covering index) est un index qui contient TOUTES les colonnes nécessaires à votre requête. SQL Server peut répondre entièrement depuis l'index sans lire la table.

**Analogie : L'index d'un livre**
```
Livre avec index :
- Index : Contient les mots-clés et numéros de pages
- Pages : Contenu détaillé du livre

Index couvrant = L'index contient déjà la réponse
→ Pas besoin d'ouvrir le livre !

Index non-couvrant = L'index vous dit où chercher
→ Vous devez ouvrir le livre à la page indiquée
```

#### Exemple concret

```sql
-- Index existant
CREATE INDEX IX_Orders_CustomerDate
ON Orders(CustomerID, OrderDate)
INCLUDE (TotalAmount);

-- ✅ Requête couverte par l'index (rapide)
SELECT CustomerID, OrderDate, TotalAmount
FROM Orders
WHERE CustomerID = 123;

-- Plan d'exécution : Index Seek (IX_Orders_CustomerDate)
-- Toutes les colonnes sont dans l'index !
-- Coût : 0.01 (très faible)

-- ❌ Requête NON couverte (plus lente)
SELECT * FROM Orders
WHERE CustomerID = 123;

-- Plan d'exécution : Index Seek + Key Lookup
-- SQL Server doit :
-- 1. Consulter l'index (CustomerID, OrderDate, TotalAmount)
-- 2. Retourner à la table pour les 15 autres colonnes
-- Coût : 0.85 (85x plus coûteux)
```

**Key Lookup = Recherche supplémentaire dans la table = LENT**

### 3. Problèmes de maintenance et évolutivité

#### Problème 1 : Ordre des colonnes imprévisible

```sql
-- Quelle colonne est à quelle position ?
SELECT * FROM Customers;

-- Si la structure change (ajout/suppression de colonne)
-- L'ordre peut changer
-- Le code qui accède par index (position) va casser
```

**Exemple de bug :**

```csharp
// Code C# qui utilise SELECT *
var result = database.Query("SELECT * FROM Customers");
string name = result[1];  // Suppose que Name est en position 1
string email = result[2]; // Suppose que Email est en position 2

// Un DBA ajoute une nouvelle colonne "Title" en position 1
ALTER TABLE Customers ADD Title VARCHAR(50);

// Le code casse maintenant :
// result[1] = Title (au lieu de Name)
// result[2] = Name (au lieu de Email)
```

#### Problème 2 : Ajout de colonnes impacte toutes les requêtes

```sql
-- État initial : Table avec 10 colonnes, 100 octets par ligne
SELECT * FROM Products;  -- Lit 100 octets

-- 6 mois plus tard : Un développeur ajoute une colonne Description (2000 octets)
ALTER TABLE Products ADD Description VARCHAR(2000);

-- Maintenant SELECT * lit 2100 octets par ligne
-- Toutes les applications qui utilisent SELECT * sont impactées
-- Performance dégradée de 21x sans changement de code !
```

#### Problème 3 : Difficile à optimiser

```sql
-- Le DBA ne sait pas quelles colonnes sont vraiment utilisées
SELECT * FROM Orders;

-- Doit-il créer un index avec INCLUDE ?
-- Sur quelles colonnes ?
-- Impossible de savoir sans analyser le code applicatif
```

### 4. Impact sur les jointures

```sql
-- ❌ SELECT * dans une jointure
SELECT *
FROM Orders o
INNER JOIN Customers c ON o.CustomerID = c.CustomerID;

-- Si Orders a 15 colonnes et Customers a 20 colonnes
-- Résultat : 35 colonnes !
-- Dont plusieurs en doublon (CustomerID apparaît 2 fois)

-- ✅ SELECT explicite
SELECT
    o.OrderID,
    o.OrderDate,
    o.TotalAmount,
    c.CustomerName,
    c.Email
FROM Orders o
INNER JOIN Customers c ON o.CustomerID = c.CustomerID;

-- Résultat : 5 colonnes (exactement ce dont vous avez besoin)
```

### 5. Sécurité et confidentialité

```sql
-- Table Employees avec colonnes sensibles
CREATE TABLE Employees (
    EmployeeID INT,
    FirstName VARCHAR(50),
    LastName VARCHAR(50),
    Email VARCHAR(100),
    Salary DECIMAL(10,2),      -- Sensible !
    SSN VARCHAR(11),            -- Très sensible !
    PerformanceReview TEXT      -- Confidentiel !
);

-- ❌ Risque de fuite de données
SELECT * FROM Employees;
-- Expose TOUTES les colonnes, même les sensibles

-- ✅ Sélection explicite
SELECT EmployeeID, FirstName, LastName, Email
FROM Employees;
-- Expose uniquement ce qui est nécessaire
```

### 6. Consommation mémoire côté application

**Exemple en C# :**

```csharp
// ❌ SELECT * charge toutes les colonnes en mémoire
var employees = database.Query("SELECT * FROM Employees").ToList();
// Mémoire utilisée : 100,000 employés × 2 KB par employé = 200 MB

// ✅ SELECT spécifique
var employees = database.Query(
    "SELECT EmployeeID, FirstName, LastName FROM Employees"
).ToList();
// Mémoire utilisée : 100,000 employés × 150 octets = 15 MB

→ Économie de 185 MB de RAM
```

## Exceptions : Quand SELECT * est acceptable

### 1. Requêtes ad-hoc pour l'exploration

```sql
-- ✅ Acceptable : Vous explorez une nouvelle table
SELECT * FROM NewTable;

-- Pour voir rapidement toutes les colonnes et leurs valeurs
-- Dans SSMS, pendant le développement
```

### 2. Dans une sous-requête EXISTS

```sql
-- ✅ Acceptable dans EXISTS
SELECT CustomerID, CustomerName
FROM Customers c
WHERE EXISTS (
    SELECT * FROM Orders o
    WHERE o.CustomerID = c.CustomerID
);

-- Dans EXISTS, les colonnes sont ignorées
-- Seule l'existence d'une ligne compte
-- SELECT 1 est une alternative commune
```

**Note :** Même dans EXISTS, certains préfèrent `SELECT 1` pour la clarté :

```sql
-- Équivalent plus clair
WHERE EXISTS (
    SELECT 1 FROM Orders o
    WHERE o.CustomerID = c.CustomerID
);
```

### 3. Dans une CTE temporaire (avec usage immédiat)

```sql
-- ⚠️ Discutable mais parfois acceptable
WITH TempData AS (
    SELECT * FROM Orders
    WHERE OrderDate >= '2024-01-01'
)
SELECT
    CustomerID,
    SUM(TotalAmount) as Total
FROM TempData
GROUP BY CustomerID;

-- Mais il est TOUJOURS mieux de spécifier les colonnes
-- même dans la CTE
```

### 4. Tables très petites de configuration

```sql
-- ✅ Acceptable : Table de 10 lignes avec 5 colonnes
SELECT * FROM ApplicationSettings;

-- Impact négligeable
-- Mais restez cohérent : spécifiez quand même les colonnes
```

### 5. Scripts de sauvegarde/copie

```sql
-- ✅ Acceptable : Copie complète de table
INSERT INTO Orders_Backup
SELECT * FROM Orders;

-- Copie TOUTES les colonnes intentionnellement
```

### 6. COUNT(*) pour compter les lignes

```sql
-- ✅ Totalement acceptable
SELECT COUNT(*) FROM Customers;

-- COUNT(*) est optimisé par SQL Server
-- Différent de SELECT *
```

## Bonnes pratiques

### 1. Toujours spécifier les colonnes explicitement

```sql
-- ❌ Mauvais
SELECT * FROM Customers WHERE City = 'Paris';

-- ✅ Bon
SELECT CustomerID, CustomerName, Email
FROM Customers
WHERE City = 'Paris';
```

### 2. Utiliser des alias pour les jointures

```sql
-- ❌ Ambiguïté avec SELECT *
SELECT *
FROM Orders o
INNER JOIN Customers c ON o.CustomerID = c.CustomerID;
-- CustomerID apparaît deux fois !

-- ✅ Préfixe clair
SELECT
    o.OrderID,
    o.OrderDate,
    c.CustomerID,    -- Explicite : vient de Customers
    c.CustomerName
FROM Orders o
INNER JOIN Customers c ON o.CustomerID = c.CustomerID;
```

### 3. Documenter les colonnes nécessaires

```sql
-- ✅ Bon : Les colonnes révèlent l'intention
SELECT
    CustomerID,      -- Pour l'identification
    CustomerName,    -- Pour l'affichage
    Email,           -- Pour la notification
    City             -- Pour le filtrage géographique
FROM Customers
WHERE Country = 'France';
```

### 4. Créer des vues pour les ensembles de colonnes fréquents

```sql
-- Si vous utilisez souvent les mêmes colonnes
CREATE VIEW vw_CustomersSummary AS
SELECT
    CustomerID,
    CustomerName,
    Email,
    Phone,
    City,
    Country
FROM Customers;

-- Utilisation
SELECT * FROM vw_CustomersSummary WHERE Country = 'France';

-- Acceptable ici car la vue définit explicitement les colonnes
-- Et vous contrôlez ce que contient la vue
```

### 5. Utiliser des ORM avec projections

**Entity Framework (C#) :**

```csharp
// ❌ Charge toutes les colonnes
var customers = context.Customers.ToList();

// ✅ Projection (sélection spécifique)
var customers = context.Customers
    .Select(c => new { c.CustomerID, c.CustomerName, c.Email })
    .ToList();
// Génère : SELECT CustomerID, CustomerName, Email FROM Customers
```

### 6. Profiler et mesurer

```sql
-- Activer les statistiques
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Comparer
SELECT * FROM LargeTable WHERE ID = 123;
-- vs
SELECT Col1, Col2, Col3 FROM LargeTable WHERE ID = 123;

-- Analyser :
-- - Logical reads
-- - Scan count
-- - CPU time
-- - Elapsed time
```

## Stratégies de refactoring

### Stratégie 1 : Audit du code existant

```sql
-- Trouver les SELECT * dans les procédures stockées
SELECT
    OBJECT_NAME(object_id) AS ProcedureName,
    definition
FROM sys.sql_modules
WHERE definition LIKE '%SELECT *%'
  AND OBJECTPROPERTY(object_id, 'IsProcedure') = 1;

-- Trouver dans les vues
SELECT
    OBJECT_NAME(object_id) AS ViewName,
    definition
FROM sys.sql_modules
WHERE definition LIKE '%SELECT *%'
  AND OBJECTPROPERTY(object_id, 'IsView') = 1;
```

### Stratégie 2 : Priorisation

**Critères pour prioriser le refactoring :**

1. **Requêtes fréquentes** (>1000 exécutions/jour)
2. **Tables larges** (>20 colonnes)
3. **Tables volumineuses** (>1M de lignes)
4. **Requêtes avec jointures multiples**
5. **Code appelé depuis l'API public**

### Stratégie 3 : Transformation progressive

**Étape 1 : Identifier les colonnes utilisées**

```sql
-- Exemple : Une procédure avec SELECT *
CREATE PROCEDURE sp_GetCustomerOrders_OLD
    @CustomerID INT
AS
BEGIN
    SELECT * FROM Orders WHERE CustomerID = @CustomerID;
END;
```

**Étape 2 : Analyser l'utilisation**

```csharp
// Code C# qui appelle la procédure
var orders = database.Execute("sp_GetCustomerOrders", customerId);
foreach (var order in orders)
{
    Console.WriteLine(order.OrderID);      // Utilisé
    Console.WriteLine(order.OrderDate);    // Utilisé
    Console.WriteLine(order.TotalAmount);  // Utilisé
    // Les 15 autres colonnes ne sont jamais utilisées !
}
```

**Étape 3 : Refactorer**

```sql
-- Version optimisée
CREATE PROCEDURE sp_GetCustomerOrders_NEW
    @CustomerID INT
AS
BEGIN
    SELECT
        OrderID,
        OrderDate,
        TotalAmount
    FROM Orders
    WHERE CustomerID = @CustomerID;
END;
```

**Étape 4 : Tester et comparer**

```sql
-- Tester les deux versions
SET STATISTICS TIME ON;
EXEC sp_GetCustomerOrders_OLD @CustomerID = 123;
EXEC sp_GetCustomerOrders_NEW @CustomerID = 123;

-- Comparer CPU time et elapsed time
```

### Stratégie 4 : Utiliser des outils d'analyse

**Query Store - Identifier les requêtes SELECT * coûteuses :**

```sql
SELECT
    qt.query_sql_text,
    rs.avg_duration / 1000.0 AS avg_duration_ms,
    rs.avg_logical_io_reads,
    rs.count_executions
FROM sys.query_store_query_text qt
INNER JOIN sys.query_store_query q ON qt.query_text_id = q.query_text_id
INNER JOIN sys.query_store_plan p ON q.query_id = p.query_id
INNER JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
WHERE qt.query_sql_text LIKE '%SELECT *%'
  AND qt.query_sql_text NOT LIKE '%COUNT(*)%'  -- Exclure COUNT(*)
ORDER BY rs.avg_logical_io_reads DESC;
```

## Impact des index couvrants

### Exemple détaillé

**Configuration :**

```sql
-- Table avec 20 colonnes
CREATE TABLE Orders (
    OrderID INT PRIMARY KEY,
    CustomerID INT,
    OrderDate DATE,
    ShipDate DATE,
    TotalAmount DECIMAL(10,2),
    Status VARCHAR(20),
    -- ... 14 autres colonnes ...
    Notes TEXT  -- Colonne volumineuse
);

-- Index non-clustered
CREATE INDEX IX_Orders_Customer
ON Orders(CustomerID)
INCLUDE (OrderDate, TotalAmount);
```

**Test de performance :**

```sql
-- ❌ SELECT * (Plan : Index Seek + Key Lookup)
SELECT *
FROM Orders
WHERE CustomerID = 123;

-- Opérations :
-- 1. Index Seek sur IX_Orders_Customer → Trouve 50 commandes
-- 2. Key Lookup × 50 → Va chercher les 17 colonnes manquantes dans la table
-- Coût : Index Seek (5%) + Key Lookup (95%) = 100%
-- Lectures logiques : 500 pages

-- ✅ SELECT colonnes de l'index (Plan : Index Seek uniquement)
SELECT OrderID, CustomerID, OrderDate, TotalAmount
FROM Orders
WHERE CustomerID = 123;

-- Opérations :
-- 1. Index Seek sur IX_Orders_Customer → Trouve tout ce qu'il faut
-- Pas de Key Lookup !
-- Coût : Index Seek (100%) = 5% du coût précédent
-- Lectures logiques : 3 pages

→ Amélioration de 20x !
→ 99.4% de lectures en moins
```

### Visualisation dans le plan d'exécution

**Avec SELECT * :**
```
[Index Seek] (5%) → [Key Lookup] (95%)
        ↓                    ↓
    Index                  Table
  (3 colonnes)        (17 colonnes)
```

**Avec SELECT spécifique :**
```
[Index Seek] (100%)
        ↓
    Index couvrant
  (tout est dedans)
```

## Impact sur les applications web

### Exemple : API REST

**❌ Mauvaise pratique :**

```csharp
// Controller ASP.NET Core
[HttpGet("customers")]
public IActionResult GetCustomers()
{
    // SELECT * de 50 colonnes
    var customers = _context.Customers.ToList();

    // Sérialisation JSON de TOUTES les colonnes
    return Ok(customers);
}

// Réponse JSON : 5 MB pour 1000 clients
// Temps de chargement : 2 secondes
```

**✅ Bonne pratique :**

```csharp
// DTO (Data Transfer Object)
public class CustomerListDto
{
    public int CustomerID { get; set; }
    public string CustomerName { get; set; }
    public string Email { get; set; }
}

// Controller optimisé
[HttpGet("customers")]
public IActionResult GetCustomers()
{
    var customers = _context.Customers
        .Select(c => new CustomerListDto
        {
            CustomerID = c.CustomerID,
            CustomerName = c.CustomerName,
            Email = c.Email
        })
        .ToList();

    return Ok(customers);
}

// Réponse JSON : 150 KB pour 1000 clients
// Temps de chargement : 0.1 secondes
// Amélioration : 33x plus rapide, 33x moins de données
```

## Cas réels de problèmes

### Cas 1 : La colonne volumineuse oubliée

**Situation :**
```sql
-- Table de produits
CREATE TABLE Products (
    ProductID INT,
    ProductName VARCHAR(100),
    Price DECIMAL(10,2),
    Category VARCHAR(50),
    LargeImage VARBINARY(MAX),  -- Image de 2 MB en moyenne !
    Description TEXT
);

-- 10,000 produits dans la table
```

**Code problématique :**

```sql
-- Page de listing des produits
SELECT * FROM Products
WHERE Category = 'Electronics';
-- Retourne 500 produits

-- Données transférées : 500 × 2 MB = 1 GB !
-- Temps de chargement : 30 secondes
-- Utilisateur frustré, quitte le site
```

**Solution :**

```sql
-- Sélectionner uniquement ce qui est affiché
SELECT ProductID, ProductName, Price, Category
FROM Products
WHERE Category = 'Electronics';

-- Données transférées : 500 × 200 octets = 100 KB
-- Temps de chargement : 0.1 secondes
-- Amélioration : 300x plus rapide !

-- Charger l'image uniquement quand le produit est consulté
SELECT ProductID, LargeImage
FROM Products
WHERE ProductID = @SelectedProductID;
```

### Cas 2 : Le rapport mensuel qui bloque le serveur

**Situation :**

```sql
-- Rapport mensuel des ventes
CREATE PROCEDURE sp_MonthlySalesReport
AS
BEGIN
    -- SELECT * sur une table de 10 millions de lignes !
    SELECT *
    FROM SalesTransactions
    WHERE YEAR(TransactionDate) = YEAR(GETDATE())
      AND MONTH(TransactionDate) = MONTH(GETDATE());
    -- Retourne 500,000 transactions avec 30 colonnes
END;

-- Problème :
-- - 15 GB de données transférées
-- - Serveur SQL Server à 100% CPU pendant 5 minutes
-- - Autres requêtes bloquées
-- - Timeout de l'application
```

**Solution :**

```sql
-- Version optimisée : Agrégation côté serveur
CREATE PROCEDURE sp_MonthlySalesReport_Optimized
AS
BEGIN
    DECLARE @StartOfMonth DATE = DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1);
    DECLARE @EndOfMonth DATE = DATEADD(MONTH, 1, @StartOfMonth);

    SELECT
        ProductID,
        ProductName,
        SUM(Quantity) AS TotalQuantity,
        SUM(Amount) AS TotalSales,
        COUNT(*) AS TransactionCount
    FROM SalesTransactions
    WHERE TransactionDate >= @StartOfMonth
      AND TransactionDate < @EndOfMonth
    GROUP BY ProductID, ProductName;
    -- Retourne 1,000 produits seulement
END;

-- Résultat :
-- - 50 KB de données transférées (300,000x moins)
-- - Exécution en 0.5 secondes
-- - Pas d'impact sur les autres requêtes
```

### Cas 3 : L'ORDER BY implicite cassé

**Situation :**

```sql
-- Code original
SELECT * FROM Customers;
```

**Code applicatif :**

```csharp
// Le développeur suppose que les clients sont triés par CustomerID
var customers = database.Query("SELECT * FROM Customers");
int firstCustomerID = customers[0].CustomerID;  // Suppose que c'est le plus petit
```

**Problème :**
- SQL Server ne garantit AUCUN ordre sans ORDER BY
- Ordre peut changer après une réindexation
- Après ajout d'un index clustered sur Name, l'ordre change
- Bug en production !

**Solution :**

```sql
-- Toujours spécifier ORDER BY quand l'ordre importe
SELECT CustomerID, CustomerName
FROM Customers
ORDER BY CustomerID;
```

## Migration progressive

### Plan de migration sur 6 mois

**Mois 1-2 : Audit et sensibilisation**
```
- Identifier tous les SELECT * dans le code
- Mesurer l'impact (profiling)
- Former l'équipe
- Créer des guidelines
```

**Mois 3-4 : Quick wins**
```
- Refactorer les requêtes les plus coûteuses (top 20)
- Créer des vues pour remplacer SELECT * courants
- Mise en place de code reviews
```

**Mois 5-6 : Refactoring systématique**
```
- Refactorer toutes les procédures stockées
- Créer des DTOs explicites dans le code applicatif
- Mise à jour de la documentation
- Tests de performance
```

### Checklist de refactoring

Pour chaque SELECT * identifié :

- [ ] Identifier le contexte d'utilisation
- [ ] Lister les colonnes réellement utilisées
- [ ] Vérifier s'il existe des index couvrants potentiels
- [ ] Réécrire avec colonnes explicites
- [ ] Tester fonctionnellement (résultats identiques)
- [ ] Comparer les performances (avant/après)
- [ ] Documenter le changement
- [ ] Mettre à jour les tests unitaires
- [ ] Code review
- [ ] Déployer en test puis production

## Mesures et métriques

### Métriques à suivre

**Avant optimisation :**
```sql
-- Baseline
SELECT
    OBJECT_NAME(s.object_id) AS ObjectName,
    s.avg_logical_reads,
    s.avg_elapsed_time / 1000.0 AS avg_ms,
    s.execution_count
FROM sys.dm_exec_procedure_stats s
WHERE OBJECT_NAME(s.object_id) LIKE '%Customer%'
ORDER BY s.avg_logical_reads DESC;
```

**Après optimisation :**
```sql
-- Comparer
-- Objectif :
-- - Réduction de 50%+ des logical reads
-- - Réduction de 30%+ du temps d'exécution
-- - Même nombre d'executions (pas de régression fonctionnelle)
```

### Rapport d'amélioration

```sql
-- Créer un tableau de suivi
CREATE TABLE OptimizationTracking (
    OptimizationID INT IDENTITY PRIMARY KEY,
    ObjectName VARCHAR(200),
    OptimizationDate DATE,
    BeforeLogicalReads BIGINT,
    AfterLogicalReads BIGINT,
    BeforeAvgMs FLOAT,
    AfterAvgMs FLOAT,
    ImprovementPercent AS
        ((BeforeLogicalReads - AfterLogicalReads) * 100.0 / BeforeLogicalReads)
);

-- Exemple d'insertion
INSERT INTO OptimizationTracking
    (ObjectName, OptimizationDate, BeforeLogicalReads, AfterLogicalReads,
     BeforeAvgMs, AfterAvgMs)
VALUES
    ('sp_GetCustomers', '2024-11-18', 45000, 150, 2500, 8);

-- Rapport global
SELECT
    COUNT(*) AS TotalOptimizations,
    AVG(ImprovementPercent) AS AvgImprovement,
    SUM(BeforeLogicalReads - AfterLogicalReads) AS TotalReadsReduction
FROM OptimizationTracking;
```

-- Job SQL Agent quotidien
CREATE PROCEDURE sp_DetectSelectStarQueries
AS
BEGIN
    -- Envoyer un email si des SELECT * coûteux sont détectés
    DECLARE @SelectStarCount INT;

    SELECT @SelectStarCount = COUNT(*)
    FROM sys.query_store_query_text

    END
END;

## Résumé

`SELECT *` est pratique pour l'exploration rapide, mais c'est une mauvaise pratique dans le code de production.

**Problèmes causés par SELECT * :**

1. 📊 **Performance dégradée**
   - Transfert de données inutiles
   - Empêche les index couvrants
   - Key Lookups coûteux

2. 🔧 **Difficultés de maintenance**
   - Ordre des colonnes imprévisible
   - Changements de structure impactent tout
   - Difficile à optimiser

3. 🔒 **Risques de sécurité**
   - Exposition de données sensibles
   - Pas de contrôle granulaire

4. 💾 **Consommation mémoire excessive**
   - Côté serveur SQL
   - Côté application
   - Côté réseau

**Bénéfices de spécifier les colonnes :**

- ✅ Performance optimale (10x à 100x plus rapide)
- ✅ Index couvrants exploitables
- ✅ Code maintenable et prévisible
- ✅ Sécurité renforcée
- ✅ Consommation mémoire réduite
- ✅ Documentation implicite (intention claire)

**Exceptions acceptables :**

- Exploration ad-hoc (SSMS)
- Sous-requêtes EXISTS
- COUNT(*)
- Scripts de sauvegarde/copie complète

**Règle d'or :** Toujours demandez-vous "Ai-je vraiment besoin de TOUTES les colonnes ?" La réponse est presque toujours "Non".

---

**Points clés à retenir :**

- ✅ SELECT * = mauvaise pratique en production
- ✅ Spécifier explicitement les colonnes nécessaires
- ✅ Impact majeur sur les performances (10x-100x)
- ✅ Empêche l'utilisation d'index couvrants
- ✅ Cause des Key Lookups coûteux
- ✅ Problèmes de maintenance (ordre imprévisible)
- ✅ Risques de sécurité (exposition de données sensibles)
- ✅ Toujours mesurer l'impact (avant/après)
- ✅ Utiliser Query Store pour identifier les problèmes
- ✅ Automatiser la détection (linting, pre-commit hooks)

**Réflexe à développer :** Avant d'écrire `SELECT *`, listez mentalement les colonnes dont vous avez réellement besoin. Vous serez surpris de constater que c'est souvent 10-20% du total.
